The idea: protect the site, not just the code

Most websites ship with bugs, and fixing every one takes time. HDD puts a protective layer in front of the whole site, so attacks are stopped at the edge while you fix the code behind it.

Defend at the edge

One platform for the web application firewall, the reverse proxy, TLS and DNS, instead of stitching together separate tools.

See what and why

Every decision is explained: which rule fired, on which field, with redacted evidence. No black box, no invented numbers.

Prove it works

HDD is built to test its own protection and to say plainly when a site is not yet protected, for example when the origin can still be reached directly.

How it works

Three steps, and no change to your application code to get started.

1

Put HDD in front of your site

Point your domain at HDD (or run it behind Caddy, Cloudflare or nginx). HDD forwards clean requests to your real server, the origin.

2

Every request is inspected

HDD decodes the URL, form fields, JSON, headers and cookies, then checks them against detection rules that know what each field is for.

3

Attacks are blocked and explained

A malicious request gets a 403 page and never reaches your site. The panel shows why it was blocked and lets you review, unban or switch modes.

The same attack, with and without HDD

A login form that builds its query from user input can be bypassed with one line.

Without HDD

  • The payload ' OR 1=1-- reaches the database
  • The login check is bypassed and the admin panel opens
  • Nothing is recorded about who tried it

With HDD in block mode

  • The request is stopped at the proxy with a 403 page
  • The sender is banned, with the rule and evidence recorded
  • Normal logins keep working through the proxy

Capabilities, and where each one stands

The platform is built in layers. Each card says honestly whether it is working today, an early build, or planned.

Working today

SQL injection defence

Tautologies, comment break-outs, UNION, stacked and blind patterns, with decoding for URL, Unicode and comment tricks. Field-aware, so names and passwords are treated sensibly.

Working today

Explainable blocks and bans

Every block records the rule, the field, redacted evidence and a reference ID. Senders get short bans that grow with repeat offences, and you can unban in one click.

Working today

Honest protection state

A site is shown as protected only when block mode is on and the origin lockdown check passed, because a site that can be reached directly can be bypassed.

Working today

Control panel and accounts

Owner and viewer roles, hashed passwords, rate-limited logins, API tokens, and a setup wizard with ready-made DNS, Caddy, Cloudflare, nginx and Vercel steps.

Early build

Self-verification

An acceptance runner and a canary check are designed to prove the protection works on your own site with safe test requests, instead of asking you to trust a badge.

Planned

More attack families

Cross-site scripting, path traversal, command injection and other classes, measured against benign traffic so legitimate users are not blocked.

Planned

Bots and DDoS defence

Rate limits, a proof-of-work challenge, reputation data and an escalation shield that can tighten step by step and always be undone.

Planned

DNS, TLS and certificates

Authoritative DNS, TLS termination and automatic certificates, so a domain can be delegated to HDD and protected end to end.

Planned

Vulnerability board and virtual patches

Track what you run, match it to advisories, and apply temporary virtual patches, always labelled as a stopgap until the code is fixed.

Principles that shape HDD

Honest by default

No absolute claims. Gaps and known limits are written down, and a site is called protected only when it really is.

Explainable, never opaque

Bans and blocks come with the rule, the field, the evidence and a way to undo them.

A stopgap is not a fix

HDD reduces risk while you repair the code. A virtual patch or a block never replaces fixing the vulnerability.

Self-hosted and under your control

Run it on your own machine or server. Reversible actions, no silent changes, and no secrets in the configuration file.

What HDD does not do

Read this before you rely on it

  • This build ships the SQL injection layer only. The other layers above are planned or early.
  • A proxy hides a vulnerability, it does not fix it. Fix the vulnerable code (use parameterised queries).
  • If attackers can reach your origin directly, they can skip HDD. Lock the origin down and verify it.
  • HDD does not terminate TLS yet; run it behind Caddy, Cloudflare or nginx.
  • Detection is measured against HDD's own test sets. New payloads can slip through, so keep monitoring.
