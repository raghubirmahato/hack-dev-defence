### Egress allowlist (R-22, section 2.1)

Every outbound connection of HDD goes through `hdd-common::egress`; `cargo xtask verify` (step `rules`) fails on a direct socket or HTTP client construction anywhere else.

`egress_allowlist` in `hdd.live.yaml` lists the destinations that may be contacted. Entry grammar: `[scheme://]host[:port][/path-prefix]`.

| Part | Meaning |
| --- | --- |
| scheme | `https` (default), `http`, `tcp` (raw connects such as SMTP; the port is required) or `dns` (resolver traffic; port 53 by default) |
| host | an exact name, an IP literal, or `*.suffix` (the suffix itself and any subdomain; never a wildcard anywhere else) |
| port | defaults to the scheme's port |
| path prefix | optional, aligned on `/` boundaries (`/directory` permits `/directory` and `/directory/new-order`, not `/directory2`) |

Examples: `acme-staging-v02.api.letsencrypt.org`, `tcp://smtp.example.org:587`, `dns://1.1.1.1`, `dns://9.9.9.9`, `*.cdn.example.net`. An empty list denies everything, and `hddctl preflight` then reports the outbound checks as UNVERIFIED(`human_step_pending`).

Two clients share one engine. `Client` contacts allowlisted destinations only. `UserUrlClient` is for user-supplied URLs (tenant webhooks, origins) and enforces section 2.9: public unicast addresses only (loopback, RFC 1918, CGNAT, link-local including `169.254.169.254`, multicast, unspecified, documentation, unique-local, translation prefixes and IPv4-mapped forms of those are refused), a port allowlist (80, 443, 8080, 8443 by default), HDD's own platform addresses refused, and no redirects unless a call opts in. For both: names are resolved once per hop and **every** returned address is validated, the connection goes to the validated address, a followed redirect passes the full policy again, TLS verification cannot be switched off, there are connect and total timeouts and size caps, and the kill switch aborts a request in flight. Metadata, link-local, multicast, unspecified and broadcast addresses are unreachable even when listed.

Denied attempts are logged as one JSON line each (`destination` without its query, `reason`, `caller`, `class`, `suppressed_before`), at most 20 per minute; the counters keep counting.

**Requesting an addition.** Adding an egress destination needs the operator's approval (section 0.5, E8.1). Open a request that names the host, scheme and port, the component that needs it, and why; the operator approves it in chat, the approval is recorded in `docs/OPERATOR-CONFIRMATIONS.md`, and only then is the entry added to `hdd.live.yaml`. `docs/EGRESS.md` (T-0413) will carry the per-class view and the `hddctl egress disable` commands.

### Kill switch

A file at `/var/run/hdd-acceptance.stop` (on non-Unix builders `hdd-acceptance.stop` in the temp directory) aborts every test and long-running tool within one second. The switch is latched: removing the file does not resume a stopped tool in the same process. Tools hold a `KillSwitch` handle (`check()` in loops, `tripped().await` in `select!`); the egress clients accept one in their configuration.

### Target guard

`TargetGuard` derives the targets that attack-shaped traffic may reach from the profile: in live mode `test_hostname` and `sandbox_hostname` (and, after resolution, only the platform addresses, with no CNAME leaving the set); in lab mode only `lab.host` and addresses inside `lab.cidr`. A resolver that cannot report CNAMEs makes a live-mode check fail closed.

### Canary sidecar and verification (T-0210)

The origin-side canary is inert static files under `origin.canary.base_path` (default `/__hdd_canary/`) plus, when installed, the `hdd-canary` sidecar. The sidecar serves **only** the five C16.1 files (`ok.txt`, `leak.txt`, `static.css`, `static.js`, `search.html`) and `GET <base_path>echo-headers` (received request headers as JSON); the manifest is never served. Limits: 1 KB request line, 8 KB header section, 100 headers, a bounded pool of 4 workers with a 64-deep accept queue (a full queue answers a fixed `503` + `Connection: close` + `Retry-After: 1` and counts `connections_shed`), and a 5 s absolute per-connection deadline measured from **accept** (read, write and drain), with a 200 ms post-response drain cap; no request body is read; every other request gets one opaque `404 not found`, and a served 200 with trailing client bytes is drained so the body is not lost. A worker panic is caught and counted (`worker_panics`) and the worker survives; a failed worker spawn fails startup and losing all workers exits non-zero. Echo-headers is an allowlist: values are echoed only for the forwarding/HDD names (`x-forwarded-for`, `x-forwarded-proto`, `x-forwarded-host`, `forwarded`, `x-real-ip`, `hdd-connecting-ip`, `hdd-ray-id`, the probe header), with `host` and `user-agent` length- and character-capped (256 printable ASCII); every other header is counted as one `[not-echoed-name]` entry, and `hdd-origin-auth` keeps only `v1;<kid>` for the exact C21.3 signed shape (nonce 16-64 hex/base64url, signature 43 base64url) — a static token or malformed value is never echoed. Install either the sidecar (`deploy/hdd-canary.service`: no capabilities, `ProtectSystem=strict`, read-only data directory, `@system-service` syscall filter, `IPAddressDeny=any` plus an allow list; run `systemd-analyze security hdd-canary.service` at install) or the plain files in the origin web root with `CANARY.md` section 5 (nginx/Apache snippets). Both install modes, query-string invariance, private-bind/lockdown guidance and the uninstall steps are in `CANARY.md`.

Commands: `hddctl canary generate --dir <dir> [--base-path <path>]` writes the five files and `manifest.sha256` with real SHA-256 values (idempotent); `hddctl canary verify [--file hdd.live.yaml] [--dir <dir>] [--direct-url <base>] [--through-url <base>] [--runner-ip <ip>] [--local-only] [--kill-switch <path>] [--with-spoof-probe]` re-hashes the files, compares the manifest `base_path`, fetches them directly (only while `origin.lockdown_state: pending`) and through HDD, checks query-string invariance and the header echo, and prints one PASS/FAIL/UNVERIFIED(reason) line per rule. It exits 1 only when a rule FAILs, and every `UNVERIFIED` uses the closed eight-code reason set only (an invented reason is a FAIL in the taxonomy test). The five probes are `CANARY-MANIFEST`, `CANARY-DIRECT`, `CANARY-HDD`, `CANARY-QUERY`, `CANARY-ECHO`; the fail-closed input rules are `CANARY-PROFILE`, `CANARY-BASE-PATH`, `CANARY-TARGET` and `CANARY-ALLOWLIST`. Override targets are validated before any request: with a profile they must be its `origin.url`/`test_hostname` host with the profile's own scheme and port (origin URL's for the origin host, `https:443` for `test_hostname`); without a profile only a loopback literal is accepted and only with `--local-only` (any loopback scheme/port); public names, private ranges, metadata addresses and credential-in-URL forms are refused. A `CANARY-HDD`/`CANARY-ECHO` PASS needs HDD-specific evidence only: the response header `Server: Hack-Dev-Defence` or `HDD-Ray-ID`. With `--with-spoof-probe` (default off; the flag is printed before any request) the echo probe plants a bogus forwarding token and the claims about the runner IP are shown and compared, but without the response-header evidence the status stays `UNVERIFIED(capability_not_supplied)`; a surviving spoof or an absent runner is a FAIL with the exact finding. An origin nginx `$proxy_add_x_forwarded_for`, a different host or a bare runner token is never evidence. A through-HDD `Resolve` negative answer for the profile `test_hostname` is `human_step_pending`; any other resolver failure is `UNVERIFIED(environment_unsupported)` naming what failed. Echo-headers is an allowlist, not a denylist: only the names listed in the sidecar description above are echoed by value and every other header is counted, not echoed. A through-HDD transport failure is `UNVERIFIED(human_step_pending)` only when it is a `Resolve` failure of the profile's `test_hostname` (the pilot delegation may not exist yet); a literal IP or loopback target, or a connect/timeout/TLS failure in any other case, is a FAIL, and a non-200 reports that a response arrived. The profile has no delegation-done field: `origin.lockdown_state` is the STOP #2 origin-firewall/secret-header state, not delegation. A kill-switch abort is `UNVERIFIED(skipped_by_operator)`; an oversized response is its own FAIL. Missing `nosniff` on the contract files is a WARN (C16.1 does not require it); missing `nosniff` on the echo JSON is a FAIL (C16). Every probe is a benign GET through `hdd-common::egress::Client` (timeouts, size cap, denial log, kill switch); the allowlist is built only from profile-named hosts or the explicit validated overrides, and every target is printed before the first request. Without `hdd.live.yaml` the profile-dependent checks are `UNVERIFIED(human_step_pending)` with the exact operator steps; a static-file install is declared with `origin.canary.use_hdd_canary_agent: false`, which makes the per-request echo `UNVERIFIED(capability_not_supplied)` unless `origin_access_log` is provided (the file checks and the response-header through-HDD evidence still run). The systemd sandbox effectiveness and the through-HDD half are `UNVERIFIED(environment_unsupported)` and `UNVERIFIED(human_step_pending)` on this Windows builder.

### Acceptance runner (T-0215 skeleton)

`hdd-acceptance` carries every acceptance check of Appendix E3. The skeleton implements the safety envelope first and has **no live check and no sender**: `cargo run -p hdd-acceptance -- registry` prints the 63 rows `AC-00`..`AC-62`; `cargo run -p hdd-acceptance -- run --dry-run --out <dir>` writes `report.md`, `report.json` and `run.log` (all `UNVERIFIED(stage_not_reached)`) into a git-ignored `acceptance-<stamp>-<mode>/` directory. A run with `--profile hdd.live.yaml` validates the profile, the egress allowlist, the target set, the profile/mode matrix, the load approval and the runner-IP rule first and refuses (exit 3) before writing an `acceptance-*/` directory; in this tree it then sends nothing. A `load` run needs `load_profile_approved: true` and `--operator-approval "run=<id>; window=<window>"` bound to the run id (format checked, not a signature); `--resume <run-dir>` uses one resume path shared by the executor and the report: it re-hashes the referenced evidence inside the report directory, copies the verified files into the new run directory (the resumed line points at the copy), binds the report to the config revision, target hostnames and a maximum age, applies the age to each line's original timestamp (a resume chain cannot extend a PASS), refuses a mismatch, an invalid previous run and future timestamps, always re-runs AC-00, and a resumed PASS satisfies its dependents (check granularity; T-0491 adds in-check resume; the binding is self-asserted JSON without a MAC, so it guards against stale or accidentally edited reports, not forgery). A non-empty `--out` is refused, including an in-place resume, and a PASS needs evidence written by the same check in the same run. An invalid run (any safety-envelope denial latched) is reported with its check/run audit line in JSON and Markdown and the CLI exits 3. The check framework enforces `CheckSpec.destructive` and the check profile, orders dependencies, runs a `finally` cleanup stack, applies per-check timeouts (a timeout fails only that check; dependents are `UNVERIFIED(stage_not_reached)` with the dependency id in the message, and the run stops unless AC-00 is PASS), latches one persistent signal listener and isolates panics (`R-09`, panics carried into the report). The executor owns the validated profile and the one inspect gate and is built only through `Executor::from_config(RunnerConfig, ...)` (which derives the gate revision, the revision source and the resume-binding revision in one place and refuses a limiter/lifecycle/revision mismatch); a check receives `ctx.connector()` and `ctx.inspect()`, never a profile or a ticket constructor. The connector refuses hop-by-hop and override headers (`Content-Length`, `Transfer-Encoding`, `Host`, `Expect`, `Upgrade`, `Connection`, `X-HTTP-Method-Override`), caps headers at 64 names / 8 KB, rejects leading/trailing whitespace in values, and refuses a body over the inspect cap before any send. The inspect request carries the headers, cookies and body (UTF-8, or base64 when not UTF-8) up to 64 KB, with the body/header digest binding the ticket. A kill-switch or signal abort is `UNVERIFIED(skipped_by_operator)` for the interrupted and remaining checks, and any safety-envelope denial (target, stage, payload class, inspect required, runner not bannable) latches the run invalid with its audit record and stops the run. The inspect-first gate requires a matching, single-use ticket (site, method, path, class digest, unchanged `config_revision` re-read at send, block mode with safe mode off) before any attack-shaped send; a spent token is not reused and the request expires quickly.

Safety limits: one shared limiter enforces the rate cap for every check of a run as **at most N grants in any closed 1000 ms sliding interval** (a grant exactly 1000 ms after another still counts; the next one is refused; checks may lower a ceiling, never raise it) — `functional` at most 20 in any 1000 ms for 300 s (the duration cap is half-open: a grant at exactly 300 s is refused), `burst` 100 HTTP / 500 DNS total, `protocol-abuse` 5 connections / 2,000 frames / 10 MiB (sandbox only), `load` only with `load_profile_approved: true` **and** a recorded per-run approval (sandbox only), `lab` at most 500 in any 1000 ms for 600 s. A requested rate of 0 on a rate lane is refused. Bucket/window allowances and the numeric `load`/`burst` guard rails are authored in code, not profile values: the v5 profile has no numeric load caps (see `docs/ACCEPTANCE.md`, operator question) and section 2.3 gives no `burst` duration. A `production` lifecycle stage refuses destructive checks without the approval of that run; `pilot` allows them with a warning. The kill switch (`/var/run/hdd-acceptance.stop`) aborts a running check within one second and the cleanup stack runs. Evidence: each saved log gets a SHA-256 and a redacted 20-line tail in the report; evidence values are capped at 512 bytes after redaction, on a UTF-8 boundary, in both renderers; redaction is structural (field name and exact value, raw and JSON-escaped), keeps the JSON parseable, and the Markdown fence is longer than any backtick run in a tail. Nobody hand-edits the registry: it is projected from `hdd_common::buildplan::ACCEPTANCE_CHECKS` and a test compares ids and titles with E3.5. Exact secrets are registered for redaction with `--redact-secret <value>` (a secret shorter than 4 bytes is refused with exit 2); redaction is linear per line, ends an unquoted value at the next delimiter (except after `Bearer`/`Basic`), matches field names as whole tokens, caps each log-tail line at 2 KB after redaction and keeps the JSON valid. The known threat-model limits (a forged resume report's check/run binding, an `EvidenceStore` clone, a check tripping the abort latch) are listed in `docs/ACCEPTANCE.md`. The real send seam arrives with T-0491; until then `docs/ACCEPTANCE.md` is the runbook.

### Live profile and preflight (T-0006)

`hdd.live.yaml` (git-ignored) is validated against `docs/profile.schema.json`; the commented template is `hdd.live.example.yaml`. The parser rejects unknown keys (the error names the key path), duplicate keys, anchors, aliases, merge keys, deep nesting and files over 256 KiB. Fields that refer to a secret hold only the NAME of an environment variable; a value that looks like a credential is rejected without being echoed, and key file paths are printed as their file name only. `hddctl preflight --profile-only` prints the rule table; the rule catalog is `RULES` in `crates/hdd-common/src/profile/validate.rs`.

### Runtime profiles (T-0561, R-31)

`runtime.profile` is `hosted` (default) or `local`. The capability matrix of C18.2 is code (`hdd_common::profile::capability`): `Profile::availability(cap)` answers `allowed`, `allowed_with_ack` or `unavailable(ERR-LOCAL-001, reason)`, and config load fails when the profile asks for something it cannot have (`saas`, open signup in `local`). The environment overrides the file through `hdd_common::profile::env::RuntimeEnv` (`HDD_RUNTIME_PROFILE`, `HDD_DATA_DIR`, `HDD_LOCAL_DATABASE`, `HDD_KV_BACKEND`, `HDD_LOCAL_PORTS`, `HDD_LOCAL_SUFFIX`, `HDD_LOCAL_TLS`, `HDD_LOCAL_LAN_EXPOSURE`, `HDD_LOCAL_LAN_ACK`, `HDD_LOCAL_DOGFOOD`, `HDD_LOCAL_LOOPBACK_IDENTITY`, `HDD_HOSTING_PROFILE`); a bad value names the variable and shows a short preview, and every bad variable is reported. Schemas: `docs/profile.schema.json`, `docs/runtime-env.schema.json`. User documentation: `docs/LOCAL.md`, `docs/HOSTING.md` (skeletons until T-0564 and T-0571).

### Store traits and the two backends (T-0562)

Runtime state (bans, sessions, rate counters, nonces, campaign sets, flow counters, the config and event bus) is reached only through `hdd_common::kv`: `KvStore`, `Bus` and `Limiter` (usage contract in the module documentation). `MemoryKv` is the in-process backend of the `local` profile; `RedisKv` and `RedisBus` (feature `redis`, on by default) are the hosted backend. `HDD_KV_BACKEND` selects (`memory` is refused with `hosted` and more than one registered service process, `kv::startup_check`); `HDD_REDIS_URL` must be `rediss://` with a password (plain `redis://` is accepted only for a loopback test server). `MemoryKv` is bounded (`MemoryLimits`: keys, bytes, shards), evicts expired keys first and then the least recently used one, and never evicts the pinned namespaces `hdd:banned_ips`, `hdd:ban:`, `hdd:sess:` and `hdd:gate:sess:`, which are capped together and fail with a clear error instead. Everything durable is rebuilt from Postgres by `kv::rehydrate` before the listeners open; rate counters, nonces, campaign sets and flow counters reset on restart (a reset only forgives). Metrics: `hdd_kv_ops_total`, `hdd_kv_latency_seconds` (wrap any store in `Instrumented`), `hdd_kv_rehydrate_rows`, `hdd_kv_rehydrate_seconds`.

Testing against a real Redis: start a throw-away Redis 7 or newer server, set `HDD_TEST_REDIS_URL` and run `cargo xtask verify --only kv-redis`.

### Embedded PostgreSQL (T-0563, ADR-0029)

`crates/hdd-local/postgres-manifest.toml` pins the distribution: PostgreSQL 17.11.1 from `theseus-rs/postgresql-binaries`, one archive per target (Windows x64, macOS arm64 and x64, Linux x64 and arm64) with its size and SHA-256. The download needs these `egress_allowlist` entries: `https://github.com/theseus-rs/postgresql-binaries/releases/download/17.11.1/` and `https://release-assets.githubusercontent.com/`. What the manager creates: a cluster with data checksums, `scram-sha-256` as the only authentication method, `listen_addresses = '127.0.0.1'`, a `pg_hba.conf` with two loopback lines, a generated 256-bit password for the superuser `hdd_admin` and for `hdd_owner`, all in owner-only files; the passwords reach the bundled programs through a `PGPASSFILE` or standard input, never a command line or an environment variable. A data directory of another major version is refused (migrate with `backup`, a fresh data directory and `restore`). Backups are `pg_dump -Fc --no-unlogged-table-data`, sealed in 1 MiB chunks with ChaCha20-Poly1305 under `secrets/backup.key`. Metrics and audit events: `hdd_embedded_db_up`, `runtime.embedded_db` (recorded by `Telemetry` until the central registry and audit log exist). Honest limits: the server is not tied to the life of the front end on Windows (a Job Object needs `unsafe`, so it belongs to the supervisor, T-0564); the SLSA provenance and SBOM attestations of the archive are not verified; only the Windows x64 archive was run here.

### Dependencies (R-08)

`docs/vetting.toml` records, for every external crate, the version, licence, MSRV and last-release date as read from the registry on the vetting date, plus the reason it fits. Tools installed on the builder (`tokei`, `cargo-vet`, `cargo-geiger`, `cargo-nextest`, `cargo-deny`, `cargo-audit`, `cargo-machete`) are listed in the header of that file. `cargo vet` currently passes with every third-party crate exempted and no imported audit sets: importing a published audit set is a trust decision for the operator (open item in `STATUS.md`).

### Settings

Environment variables are validated at startup, printed by `hddctl preflight` and documented here by the tasks that add them. The catalog is Appendix B10 (`docs/spec/B4.md`);
`.env.example` lists every name with its default and rules, commented out. There is no `DEV_MODE`. Secrets are accepted as `NAME`, `NAME_FILE` (0600) or systemd credentials.

## HK1 demo proxy (hackathon demo track, 2026-10-23)

Status: **demo track only.** This section documents the vertical slice built for HK1 (COLLAB.md, `docs/DEVIATIONS.md` ASM-HK1): an HTTP/1.1 reverse proxy with the C4 SQL-injection detector, a ban ladder, a JSONL event log and a loopback admin listener with an embedded web UI. It is one code path for the local and hosted runtime profiles; the difference is the configuration file, never a code mode (R-31, no `DEV_MODE`).

### What runs where

| Part | Address | Notes |
| --- | --- | --- |
| `hdd-proxy` data plane | `listen` in the YAML, default `127.0.0.1:8080` | TLS terminates in front of it (Caddy or Cloudflare); the proxy itself is plain HTTP/1.1, documented limit |
| `hdd-proxy` admin listener + web UI | `admin_listen`, default `127.0.0.1:9090` | Loopback by default; first run opens `/setup` (available only while no account exists and only over loopback) |
| Deliberately vulnerable rehearsal origin | `127.0.0.1:8081` (`lab/demo/vuln_login`) | Lab only, never shipped, never exposed; real string-concatenated SQL, seeded users with randomly generated passwords printed once |
| Operator's origin | `sites[].origin` | HTTP or HTTPS; forwarded to directly (see ASM-HK1(c)); never a host outside the loaded config |

### Running the rehearsal

```bash
npm run dev        # build if needed, then vulnerable app 8081 + proxy 8080 + admin UI 9090, prefixed logs
npm run attack     # attack.ps1/.sh against the local proxy in block mode
npm test           # Rust gates that matter for the demo: fmt check, clippy -D warnings, nextest
```

`npm run dev` creates `hdd-data/` (git-ignored, owner-only), generates `HDD_ADMIN_TOKEN` in the process environment if it is unset, prints the three URLs, the `/setup` link and a one-line attack command, and stops all children on Ctrl+C. Live reload is used only when `cargo-watch` is installed; otherwise the launcher says it is unavailable. The demo origin is the lab shop (`lab/demo/shop`, loopback 8082, `SHOP_VULN` switch; fake data, never exposed). `demo/hdd-dev.yaml` is the local profile; `demo/hdd-live.example.yaml` is the template for the operator's live site.

### Findings, attacker impact, remediation and AI explanation (Addendum 6)

Every blocked request is grouped into a finding by site, method, path, vector, field and family. The Findings screen and `GET /api/findings` show the exact detected request line (`detected`), the inferred weakness (worded as an inference from the payload shape, never as proof), what an attacker could do (`attacker_impact`, per family and per endpoint kind), and how to fix it (`remediation`: steps plus a stack-specific parameterised-query example selected by the site's `stack` hint: `node`, `php`, `python`, `java` or `other`). Each finding can be exported as Markdown or JSON. Findings are grouped in memory for the demo session; the JSONL event log remains the durable raw record (ASM-HK1-A6(c)).

**Confirm vulnerability (owner-triggered).** A finding page has a button that sends at most four inert read-only probes to the origin of the registered site only: a benign baseline, a quote probe and a boolean pair (`X' AND '1'='1` versus `X' AND '1'='2`) in the one finding field. The button requires the owner to type the site host; detection is deliberately skipped for these probes and every probe is recorded in the audit log as `finding.confirm_probe`; the request bodies are never logged. Verdicts are `confirmed_injectable`, `not_confirmed` or `inconclusive`, and an `confirmed_injectable` result only raises the finding's confidence - it never changes a block or ban decision. The probes are POST requests, a recorded deviation from the class A GET/HEAD rule (ASM-HK1-A6(b)).

**AI explanation (optional, off by default).** Set the `ai:` block in the profile and the environment variable it names (`api_key_env`, default `DEEPSEEK_API_KEY`) to let the owner request a model explanation of a finding. The key is read only from that variable at call time: it is never stored in the profile, the data directory, the event log, a test or an API response. The call goes through the one egress path with an allowlist limited to the configured `base_url` host (`https://api.deepseek.com` by default, model `deepseek-flash`, 20 s timeout, 30 calls per hour), the prompt carries only the finding facts (family, rule id, vector, field kind, method, path, redacted evidence, stack, language), and the answer is validated, size-capped, cached per finding and rendered as escaped text labelled "AI-generated, verify before use". The model never decides a block or a ban (R-33); without the variable the UI says AI is off and the deterministic text stays. Nothing is sent to the model until the owner presses the button, so the demo runs air-gapped by default.

### Settings and secrets

`admin_token_env` is the **name** of the environment variable holding the bootstrap/break-glass admin token; there is no default value in the file or the binary and the process refuses to start when the variable is missing (R-03). The admin listener is loopback-only by default: a non-loopback `admin_listen` is refused unless the profile sets the explicit `admin_non_loopback_ack: true`, and the process then logs a warning at start (R1-9); prefer a loopback admin listener behind an SSH tunnel. Owner accounts are created by the first-run wizard and stored as argon2id hashes in the owner-only data directory; the token stays usable for scripts and break-glass. `origin_secret_env` is likewise a variable name, never a value; the proxy injects that header on every upstream request and strips any client-supplied copy (Addendum 5). No secret is written to the YAML, the event log or the dashboard.

### Protection honesty (R-34)

The dashboard shows `off`, `monitor`, `blocking-unverified` or `blocking-locked-down`; only the last is presented as protected, and it requires both the origin lockdown check (the origin refuses a direct request, or a serverless origin enforces the shared-secret header) and the two-request verify probe. A site in `block` mode with a reachable origin is shown as not protected. A site is never described as protected because a mode is set.

### Known limits of the HK1 slice

- No TLS termination and no ACME in the proxy; a TLS terminator (Caddy, Cloudflare) is required in front.
- Request bodies larger than 256 KB are refused with a branded 413 page (`INSPECT_BODY_CAP`); admin API bodies are capped at 64 KB. The proxy never forwards a body it has not inspected.
- The committed dev profile listens on 8080/9090; if one of those ports is busy, `npm run dev` writes a generated profile under `hdd-data/` with the first free pair (18080/19090) and prints the actual URLs (ASM-HK1(j)).
- Responses are not inspected; only requests are. HTTP/2 is not served (HTTP/1.1 only).
- One tenant, no billing/SaaS features; accounts live in a local atomic JSON file, not the PostgreSQL control plane.
- Password reset by email is out of scope; the offline one-time reset is `hdd-proxy admin reset-password <user>` (prints a generated password to the terminal once).
- Serverless origins are locked down by a shared-secret header (Addendum 5); the edge middleware comparison is not constant-time and is documented as such.
- The live-site details (domain, origin URL, how the origin is locked down, where the TLS terminator runs) are still needed from the operator before the live rehearsal; see the HK1 report in `docs/COLLAB.md`.

## Front door for serverless origins (Addendum 7)

Status: **demo track only** (Addendum 7; `docs/DEVIATIONS.md` ASM-HK2). A serverless origin (for example a Vercel Node handler) can keep the address visitors use while HDD still decides every request: the app keeps its own Vercel address, a small front-door block at the edge forwards anything that did not come through HDD to HDD, and HDD inspects it and forwards clean requests to a second address of the same project. This is the Addendum 7 connection method `vercel_front_door`; the default Vercel lock (Addendum 5) is unchanged.

### Routing by `X-HDD-Gate-Host`

- HDD uses `X-HDD-Gate-Host` instead of `Host` for the site lookup and for the events only when the TCP peer is inside `trusted_proxies`; an untrusted peer can never choose the site this way.
- The value must be a valid lower-case DNS name (at most 253 bytes, no port, no slashes). A malformed value is ignored, and an unknown gate host gets the same neutral 404 as an unknown `Host`, so the response does not reveal which hosts are registered.
- The header is stripped before forwarding: it never reaches the origin.
- Therefore the forwarding hop must be listed in `trusted_proxies`. With the demo tunnel the SSH client connects to HDD from loopback, so `127.0.0.1/32`. With a hosted HDD it is the address or CIDR HDD sees for the front door's requests; a serverless front door's egress addresses can change, so keep the list current and check the events after a change. If the hop is not trusted, HDD ignores the gate header and answers the neutral 404.

### Site configuration (wizard `vercel_front_door`, or the same keys in YAML)

| Key | Value for a front-door site |
| --- | --- |
| `host` | the public address visitors keep using, for example `hdd-demo-shop.vercel.app` |
| `origin` | a **second** address of the same Vercel project; never shared with visitors and never equal to `host` (the wizard refuses that) |
| `upstream_host` | the origin's host name, so HDD sends the right `Host` header to the second address |
| `origin_secret_header` / `origin_secret_env` | as in the Addendum 5 lock (for example `x-hdd-origin-secret` and an environment-variable name); the file holds only names |
| `public_url` | the public host (`https://<host>`), so Verify protection probes the front door end to end |
| `trusted_proxies` | must contain the forwarding hop (see above) |

The wizard fills these, generates the origin secret once and shows the paste block plus the exact Vercel steps; the secret value is never accepted over the API and never written to the YAML. When the site is configured by hand, `origin_secret_env` names the environment variable HDD reads for the secret value.

### The front-door block (what it does, and its limits)

- A request that carries HDD's secret header (constant-time compare) is served by the app.
- Any other request is forwarded to HDD (`HDD_GATE_URL`): method, path, query and a body up to 1 MiB; it marks the hop (`x-hdd-gate-hop: 1`), sets `X-HDD-Gate-Host` to the original host, passes the client address in `X-Forwarded-For` and sends `Host` as HDD's host. A request with the gate-hop marker and no secret is refused (loop guard).
- **When HDD cannot be reached the front door answers 503 with a short HTML page and never serves the app uninspected.** A retry happens only when replaying cannot deliver the request twice (GET/HEAD, or a reused-socket failure).
- While `HDD_ORIGIN_SECRET` is empty or unset, the front door and the Addendum 5 lock are **off**: the app answers everyone. The generated block states this in its first comment; set the variable on the Vercel side and redeploy before any protection statement (HDD keeps the matching value in its owner-only secret storage, or in the environment variable the site names for a hand-configured site).
- The block is for CommonJS Node handlers (`module.exports`); Next.js apps use the default (non-front-door) Vercel mode. Vercel Deployment Protection / Vercel Authentication must be off for the proxied path.

### The demo tunnel

`npm run tunnel` (`scripts/hdd-tunnel.mjs`) runs `ssh -o ServerAliveInterval=15 -o ServerAliveCountMax=3 -o ExitOnForwardFailure=yes -R 80:127.0.0.1:<port> nokey@localhost.run` and prints `HDD_GATE_URL=<url>`; set that value in Vercel, then redeploy. The helper sends a `GET <url>/healthz` every 8 s (the free service resets the first request after idle), restarts ssh with a bounded exponential backoff (1 s, 2 s, 4 s, ... capped at 30 s, reset after a run of 60 s) and stops cleanly on Ctrl+C/SIGTERM. It refuses to start without the OpenSSH client and prints how to install it, and it never reads or prints environment values. The tunnel is **temporary and demo-only**: while it runs the loopback proxy is reachable from the internet, the free service gives a new URL on every restart, and the permanent answer for a live site is hosting HDD on a server with a fixed public address and a TLS terminator in front of it.

### Reading the events and being honest

- A request through the front door is recorded under the site's public host (the gate host HDD used), with the usual action (`block`, `would_block` in monitor mode, or forwarded), rule id, field and Ray ID; the client IP is taken from the front door's `X-Forwarded-For` only because the hop is in `trusted_proxies`.
- A 503 answered because HDD is unreachable happens at Vercel and is not an HDD event; the Vercel function log holds the front door's own error line, which prints no secret.
- A site is presented as protected only after the lockdown check and Verify protection both pass (R-34); `public_url` must be the public host so Verify probes the front door. For a front-door site the lockdown check's direct request to the second address is forwarded by the wrapper to HDD, whose neutral unknown-host 404 carries an HDD Ray ID; that response shows the app was not served directly and counts as the front-door refusal. A 2xx (the app answered directly) or a Ray-ID-less 404 stays not confirmed.
- No secret values in files: profiles, this document and the repository hold only environment-variable names. The wizard-generated secret is kept by HDD in an owner-only file and shown once; the Vercel side holds the value in its environment. Rotate it by adding the site again (a new secret) or by updating the environment variable and redeploying.
