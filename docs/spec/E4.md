## E5. Gate report template and gate table

### E5.1 Gate report (fixed format, used at every gate and mirrored in `STATUS.md`)

Each gate task writes `docs/gates/Gnn.md` (two-digit gate number) using exactly this structure. Output tails are pasted verbatim; full logs are stored under `docs/gates/evidence/Gnn/` with their SHA-256 listed.

```markdown
# Gate Gnn: <phase name>

- Phase / milestone: Pnn / Mx   - Commit: <git sha>   - Date: <UTC>   - Author role: <agent role>
- Environment: stage=<pilot|production> mode=<live|lab|ci> host=<id> kernel=<uname -r> toolchain=<rustc -V>

## 1. Commands run (with output tails)
| # | Command | Exit | Output tail (last 20 lines) | Full log sha256 |
| --- | --- | --- | --- | --- |

## 2. Acceptance criteria
| Task | Criterion | Status | Evidence ref | Notes |
| --- | --- | --- | --- | --- |
(one line per criterion A1..A5 of every task in the phase)

## 3. Acceptance checks (AC-xx) touched by this phase
| Check | Status | Reason code if UNVERIFIED | What the operator must supply | Evidence |

## 4. Metrics
rust-share | tokei totals | test count | coverage (lines/branches) | mutation score | clippy | audit | deny | vet | unsafe-scan | claims-lint | docs-test | a11y violations | perf deltas

## 5. Deviations and assumptions
New or changed entries in docs/DEVIATIONS.md (id, reason, approver, expiry) and assumptions made.

## 6. UNVERIFIED register
Every UNVERIFIED with its reason code and the exact operator action that resolves it.

## 7. Findings
| Id | Severity | Area | Summary | Status (fixed / accepted-with-owner / open) | Link |

## 8. Risks and open questions
Top 5 risks with mitigation; questions awaiting the operator.

## 9. Rollback
How this phase's changes (migrations, config, units) are rolled back and the test that proves it.

## 10. Next steps
Next 10 tasks (ids and titles) and their blockers.
```

### E5.3 Failure budget and diagnosis template

A task or check that fails three times with different attempted fixes stops (R-14). The agent writes `docs/diagnoses/<task>-<n>.md` with: symptom; exact commands and outputs; the three hypotheses and what each attempt changed; what was observed; options (with cost and risk) for the operator; the recommended option; the task state (`blocked`) and what unblocks it. The agent then moves to the next unblocked task whose dependencies are met; blocked tasks are listed in `STATUS.md`. The failure counter resets only when a root cause is recorded.

## E6. Hostile review checklists

Every diff gets a hostile self-review before it is committed (task lifecycle step 8, section 0): read it as an attacker, a malicious tenant, a careless operator and a failing dependency. The universal list applies always; area lists apply when the diff touches the area. Findings are recorded in the PR description or commit body; unresolved items become tasks or `docs/diagnoses/` entries.

### E6.1 Universal (every diff)

- [ ] Does any new input reach a parser, a query, a path, a command, a template or a URL without validation at the boundary and a size/time bound?
- [ ] Is every buffer, queue, cache, map, loop, retry and recursion bounded (and is the bound tested)?
- [ ] Can an unauthenticated or low-privileged caller trigger work that costs the platform more than it costs them?
- [ ] Does the error path leak secrets, stack traces, internal hostnames, SQL or tenant identifiers?
- [ ] Are secrets kept out of logs, metrics labels, events, panics, `Debug` output, URLs and test fixtures?
- [ ] Is there any `unwrap`/`expect`/indexing/arithmetic that can panic or overflow on attacker-controlled data?
- [ ] Does the change fail closed on inspection and fail safe elsewhere, and is that documented where it differs?
- [ ] Is the new behavior covered by a failing-then-passing test and, for security properties, a negative test?
- [ ] Are time, randomness and I/O injectable so tests are deterministic?
- [ ] Does the change add a dependency, and if so does it pass deny/audit/vet and justify its unsafe and transitive surface?
- [ ] Does the change alter a claim in the UI/docs? Is it still true, evidenced and limited (claims-lint)?
- [ ] Does it weaken a threshold from E4? If so, is there approval and a DEVIATIONS entry?
- [ ] Can this change lock the operator out (SSH, admin, firewall, DNS) and does it have the timed revert / preview?
- [ ] Is the audit event written exactly once with actor, reason, before and after?
- [ ] Is the migration expand/contract safe under version skew and is rollback documented?
- [ ] Are tenant boundaries enforced in the query (RLS plus explicit scoping) and in the cache key?
- [ ] Does anything depend on the order of concurrent operations without a lock, version check or idempotency key?
- [ ] Is the behavior identical for IPv4 and IPv6, and for h1, h2 (and h3 once present)?
- [ ] Are accessibility, reduced motion, no-JS fallback and both themes preserved for UI changes?
- [ ] Is the documentation or runbook updated, and does its sample command still run (docs-test)?

### E6.2 Web UI and templates

- [ ] Is every dynamic value escaped by default; is `SafeHtml` constructed only from sanitizer output or constants?
- [ ] Does the page work with CSP nonces and Trusted Types and without inline handlers or `eval`?
- [ ] Are forms protected by CSRF tokens bound to session, Origin/Fetch-Metadata checks, and idempotency/PRG?
- [ ] Are HTMX endpoints returning partials only to HX requests and full pages otherwise, with correct `Vary`?
- [ ] Are focus management, labels, error association, live regions and keyboard operation correct?
- [ ] Are destructive actions behind typed confirmation or step-up with an audit preview?
- [ ] Does the screen show real data or an honest empty state (never mock numbers)?
- [ ] Are charts accompanied by tables and non-color encodings?
- [ ] Does any link use `target=_blank` without `rel=noopener noreferrer`?
- [ ] Are cookies `__Host-` prefixed with `Secure; HttpOnly; SameSite` where applicable?

### E6.3 API and control plane

- [ ] Does the route have a permission annotation and a negative authorization test for every role?
- [ ] Are object ids authorized against the caller's org on every access (BOLA), including list filters and bulk endpoints?
- [ ] Are request bodies strict (`deny_unknown_fields`), size-capped, depth-capped and content-type checked?
- [ ] Are pagination, filtering and sorting parameters allowlisted and bound (no injection into SQL fragments)?
- [ ] Are `If-Match` and idempotency keys honored for mutating endpoints?
- [ ] Is rate limiting per key and per IP present, with stricter limits for expensive endpoints?
- [ ] Are error responses RFC 9457 with stable ERR codes and no internals?
- [ ] Are responses shaped by role (field-level permissions) and free of secrets?
- [ ] Are webhook/URL/host inputs passed through the egress guard?
- [ ] Is the OpenAPI document updated and the contract test passing?

### E6.4 Identity and sessions

- [ ] Are tokens opaque, high-entropy, stored hashed, single-use where required and constant-time compared?
- [ ] Do login, reset and signup responses and timings avoid account enumeration?
- [ ] Are sessions rotated on privilege change and revoked on password/MFA/role change?
- [ ] Is step-up required and fresh for sensitive actions, and bound to the session?
- [ ] Are lockouts and rate limits resistant to attacker-induced victim lockout?
- [ ] Is MFA enrollment forced for platform roles and are recovery paths documented and audited?
- [ ] Are passkey/TOTP replay protections tested (sign counter, last used step)?
- [ ] Is the pepper/key versioning present for rotation?
- [ ] Is impersonation read-only, time-boxed, bannered and audited?
- [ ] Are API keys scoped, hashed, shown once and re-evaluated against the creator's permissions on each call?

### E6.5 Database and migrations

- [ ] Does every new tenant table have `org_id`, RLS and an index leading with it; are policies tested with a forged `app.org_id`?
- [ ] Are `SECURITY DEFINER` functions avoided or reviewed with a fixed `search_path`?
- [ ] Are queries parameterized (sqlx compile-time checked) with no string-built SQL?
- [ ] Are migrations additive, lock-timeout bounded, reversible where claimed, and linted?
- [ ] Are partitions created ahead and retention implemented by partition drop?
- [ ] Are secrets stored with envelope encryption and AAD binding?
- [ ] Are long transactions, unbounded `IN` lists and sequential scans avoided in hot paths?
- [ ] Is the deletion ledger replayed after restore?

### E6.6 Proxy and data plane

- [ ] Is the hot path free of awaits on the database and of unbounded allocation?
- [ ] Is inspection performed before any upstream I/O and before cache lookup; does it fail closed in `block` mode?
- [ ] Are client-supplied forwarding headers stripped and the real client IP resolved from the socket or trusted proxies only?
- [ ] Are request smuggling vectors (CL/TE, obs-fold, duplicate headers, h2→h1 translation) rejected?
- [ ] Does the origin client verify certificates with no bypass path and refuse private/platform addresses at connect time?
- [ ] Are redirects never followed and loops detected?
- [ ] Are per-tenant fairness budgets and global shed policies in place?
- [ ] Do panics stay isolated per request and fail closed with a Ray ID?
- [ ] Is the secret origin header never emitted to clients, logs or events?
- [ ] Are branded pages free of tenant cross-leakage and rule names?
- [ ] Is `/__hdd/` handled before routing to the origin and unreachable by tenants' paths?
- [ ] Are websocket/gRPC upgrades inspected at handshake and capped afterwards?

### E6.7 WAF engine and detectors

- [ ] Is the engine pure (no I/O, no clock, no randomness) and deterministic for identical input?
- [ ] Are all three views (raw, decoded, canonical) evaluated and decoding bounded (depth, size, iterations)?
- [ ] Do regexes avoid catastrophic backtracking (automata engine or bounded) and have worst-case tests?
- [ ] Does the new rule have positive, negative and counter-example fixtures and a benign-corpus run?
- [ ] Are hard versus soft semantics, hardness tags and field-kind policy respected?
- [ ] Can an attacker use a new rule to cause bans of victims (cross-site context, spoofed headers, shared addresses)?
- [ ] Are evidence snippets redacted and ≤ 512 bytes?
- [ ] Is performance measured (p50/p99, worst-case input) and within budget?
- [ ] Does the change keep `monitor` mode honest (records `would_block`, no side effects)?
- [ ] Is the detector registered in the attack-matrix check with ATK ids?

### E6.8 DNS

- [ ] Does the query path touch only the immutable snapshot (no DB, no network except bounded flatten tasks)?
- [ ] Are responses minimal, size-capped, correct for NXDOMAIN/NODATA/wildcard/ENT/CNAME cases, and tested against the reference implementation?
- [ ] Is HDD unable to act as a reflector (no recursion, RRL, cookies, TC=1 behavior, ANY minimal)?
- [ ] Are zone transfers TSIG-only with source allowlists and no information leak on refusal?
- [ ] Can a tenant create names that collide with platform names or other tenants' zones?
- [ ] Does the proxied-answer path guarantee that origin addresses never leave in answers or hints?
- [ ] Are serials monotonic across imports, rollbacks and restores?
- [ ] Is DNSSEC never claimed without validation?

### E6.9 TLS, ACME and certificates

- [ ] Are private keys only ever stored encrypted and decrypted in the proxy process, zeroized on drop?
- [ ] Is production issuance gated on the operator's approval and the failed-validation budget?
- [ ] Are CAA, CT and ARI considered; are validation guards tenant-safe (no cross-tenant challenge hijack)?
- [ ] Is unknown/absent SNI refused and HSTS gated on a valid certificate?
- [ ] Is the minimum TLS version and cipher policy enforced and tested with an oracle?
- [ ] Does certificate hot reload leave in-flight connections unaffected?

### E6.10 Firewall, XDP and host

- [ ] Does the change preserve SSH and admin access and use the timed auto-revert?
- [ ] Are never-ban/never-drop lists consulted on every kernel path?
- [ ] Is `unsafe` confined to the allowlisted module and each block justified?
- [ ] Are map updates atomic and legitimate-traffic regressions tested?
- [ ] Are commands built as argument arrays and inputs parsed to typed values first?
- [ ] Can the operator undo every host change exactly (before/after hash)?

### E6.11 Shield and escalation

- [ ] Can an attacker trigger a harmful escalation by spoofing signals or poisoning bans?
- [ ] Does every action record `skipped(feature_absent)` or its result, with an undo?
- [ ] Does the system fail safe (revert) if the shield dies?
- [ ] Are capacity statements limited to the three provenance-labeled numbers?

### E6.12 Vulnerability management and scanning

- [ ] Is feed content treated as untrusted data (escaped, size-bounded, no actions)?
- [ ] Does the matcher avoid guessing versions and mark unknowns?
- [ ] Can a virtually patched item ever be marked resolved or stop its SLA clock?
- [ ] Is the scanner restricted to the allowlist, rate-limited and incapable of sending exploit payloads?

### E6.13 Operations, deployment and supply chain

- [ ] Are artifacts verified (signature, checksum, provenance) before install, and is rollback automatic on failure?
- [ ] Are secrets generated, stored 0600 and never baked into images or compose files?
- [ ] Are services least-privileged (capabilities, users, sandboxing) and scored by `systemd-analyze security`?
- [ ] Are backups encrypted with keys not stored on the host and restore-tested?
- [ ] Does the dependency change pass deny/audit/vet and keep the SBOM correct?
- [ ] Is the lab (Vuln-Lab, chaos, oracles) excluded from release artifacts?

### E6.14 Documentation and claims

- [ ] Does every statement about protection, performance, availability or compliance map to evidence and carry its limits?
- [ ] Are forbidden phrases absent (unhackable, complete protection, guaranteed, compliant, certified, AI-powered without evidence)?
- [ ] Are mandatory disclosures present (readiness footnote, mitigated-not-fixed, partial scan, geolocation approximation, lab-proven labels)?
- [ ] Do documented commands and routes exist and run?

### E6.15 Lab, fixtures and tests

- [ ] Does every fixture carry a class and obey target rules (A live test host GET/HEAD, B sandbox, C inspect API only)?
- [ ] Do lab tools refuse non-lab targets and public addresses?
- [ ] Are held-out sets untouched by tuning?
- [ ] Is every sleeping or time-dependent test using injected clocks?
- [ ] Do chaos and flood tools clean up faults on exit and on crash?

### E6.16 Runtime profiles and local mode (new in v5.1)

- [ ] Does any new code branch on the runtime profile outside `hdd-local`, `hdd-common::kv`, `hdd-common::profile` or the `Enforcer` factory? (It must not; R-31.)
- [ ] Does any new runtime state bypass the `KvStore`, `Bus` and `Limiter` traits, and does it have a conformance test on both backends?
- [ ] Is every new durable state rebuildable from Postgres at startup (the `MemoryKv` restart contract)?
- [ ] Can a web page the operator opens reach, read or change anything in the local control plane (Host, Origin, Fetch Metadata, CSRF, CORS, Private Network Access)?
- [ ] Is every listener loopback-only unless the data-plane LAN exposure acknowledgement is present, and is that tested from a non-loopback address?
- [ ] Does any action touch the OS (trust store, hosts file, firewall, autostart, ports below 1024) without an explicit consent step, a precise diff and a reversal that restores the original?
- [ ] Could a loopback ban, a never-ban change or a rate limit lock the operator out of the dashboard (R-19)?
- [ ] Are secrets absent from command lines, child environments, logs and the process table?
- [ ] Does any copy imply that local mode is always on or highly available (section 4)?

### E6.17 Access gate, API discovery and business flows (new in v5.1)
