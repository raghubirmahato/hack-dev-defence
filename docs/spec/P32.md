## PHASE P32: Backlog, Tier 2 to Tier 6 (T-0541 to T-0560) · after milestone M12 · gate G32

Requirement prefix `BKL`. Goal: a prioritized, fully specified backlog of capabilities that extend the product after the Tier 1 minimums are proven. Tasks in this phase begin only after gate G31 passes (or earlier on explicit operator request for a named task) and follow every rule of the constitution: ADR first for anything with an architectural choice, honest claims, acceptance evidence, and the same gate discipline.

**Tier map.**

| Tier | Theme | Tasks |
| --- | --- | --- |
| Tier 2 | Customer-value extensions on the existing architecture | T-0541 to T-0546 |
| Tier 3 | Protocol and DNS depth | T-0548 to T-0550 |
| Tier 4 | Scale-out and resilience | T-0552 to T-0555 |
| Tier 5 | Extensibility | T-0547 |
| Tier 6 | Ecosystem and enterprise | T-0551, T-0556 to T-0559 |
| Governance | Backlog management | T-0560 |

Non-negotiables: no Tier 2 to 6 feature may weaken a Tier 1 guarantee (inspection never fails open in `block` mode, hot path never awaits the database, tenant isolation, claims policy); each task states its operator-dependent inputs; features that add attack surface (plugins, SSO, caches, provider adapters) require a STRIDE delta and a lab pentest note before merge; any new outbound call goes through the central egress client and the allowlist; cost and complexity are weighed against the single-VPS-first philosophy and recorded in the ADR.

Gate G32 is the per-task closing review used each time a backlog item completes (the gate report format is the same, appended to `docs/gates/G32-<task>.md`).

### T-0541 · Tier 2: DNS provider import adapters (read-only) for common providers
`P32` `[API][UI][SEC]` · deps: T-0157, T-0184, T-0413 · size: L · owner: dns
**Objective.** Let owners import their existing zone by connecting a provider API token with read-only scope, reducing onboarding friction and errors.
**Steps.**
1. Write a short **ADR** selecting the first adapters by user demand and API stability (candidates: Cloudflare, AWS Route 53, DigitalOcean, Google Cloud DNS, Azure DNS, Namecheap, GoDaddy, Hetzner DNS, deSEC); record scopes needed (read-only), rate limits, record-type coverage and proprietary features per provider.
2. Extend the `ImportAdapter` trait (T-0157) with `authenticate`, `list_zones`, `export_zone` (normalized records plus provider-specific metadata such as proxied/orange-cloud flags and ALIAS/ANAME/redirect rules mapped to the HDD unsupported-type report); tokens are held encrypted for the import session only (default) and deleted after the import completes unless the owner opts into "re-sync later".
3. Implement each adapter against the provider API through the egress client with pinned hosts; pagination, rate-limit backoff, error mapping to owner-readable messages; no write operations exist in the adapter code (a static check forbids non-GET methods in the adapter modules).
4. Map provider semantics: Cloudflare proxied → HDD proxied with explicit confirmation, page rules/redirects reported as unsupported, Route 53 alias records → flatten/ALIAS handling or unsupported report, health-check-based routing → unsupported with explanation, geo/weighted routing → unsupported with explanation.
5. Present the import results in the existing parity UI (S-047) with a provider-specific section and the instructions for the NS change at the provider (human step) — HDD never changes anything at the provider.
6. Add **scoped token guidance**: step-by-step creation of minimal read-only tokens per provider (documented and screenshot-tested in docs tests where possible), token validation that rejects tokens with write scopes when the provider API exposes scopes (warn strongly otherwise).
7. Write tests against recorded provider API fixtures (VCR-style, sanitized) and against local fake servers for error conditions; no live provider calls in CI (live smoke tests optional with operator-provided read-only tokens).
8. Update docs and the capability matrix.
**Deliverables.**
- ADR, adapters, UI sections, docs, fixture-based tests
**Acceptance.**
- A1: for each adapter the fixture zones import with the documented mapping and unsupported-type report.
- A2: adapters cannot perform non-GET calls (static gate).
- A3: tokens are deleted after import by default (test).
- A4: provider hosts are pinned in the egress allowlist and nothing else is contacted.
- A5: tokens with write scopes trigger the documented warning/rejection where detectable.
**Tests.**
- Fixture replay, fake-server error tests, static gates.
**Notes.** Live smoke tests need operator tokens: UNVERIFIED(`capability_not_supplied`) otherwise.

### T-0542 · Tier 2: origin pools, load balancing and active health-based failover between origins
`P32` `[DP][API][UI]` · deps: T-0365, T-0369, T-0405 · size: XL · owner: dp
**Objective.** Support multiple origins per site with health-aware distribution, preserving all security guarantees.
**Steps.**
1. ADR on the model: pools with weighted round robin, least-connections, consistent hashing by cookie/header (sticky sessions), priority tiers (primary/secondary), health-check definitions (path, interval, thresholds, expected status/body hash), and failover semantics; per-origin TLS settings and lockdown state; interaction with the SSRF guard (every origin validated independently).
2. Extend the data model (`origin_pools`, `origins`, memberships), snapshot representation (immutable per-site pool structures with precomputed weights), and API/UI (S-052 gains a pool editor; S-053 shows per-origin health).
3. Implement the **selector** in the proxy: lock-free per-request choice honoring weights and health, retry-on-another-origin for idempotent requests on connection failure (once), outlier ejection (passive health: consecutive 5xx/timeouts), slow-start for recovered origins, and connection pools per origin with bounded size.
4. Implement **active health checks** (T-0369 extension) with jitter, per-origin state machine (healthy, degraded, unhealthy, draining), hysteresis, and event/alert integration; maintenance mode ("drain") for planned changes.
5. Implement **sticky sessions** options safely: cookie-based affinity (`__Host-hdd_aff`, signed, no origin data), IP-hash affinity, header-hash; documented limitations with CGNAT.
6. Implement **security invariants:** a pool never mixes origins with different TLS verification modes without explicit per-origin settings; the secret origin header/mTLS is applied per origin; failover never sends traffic to origins failing lockdown verification when `strict_lockdown` is enabled; the WAF decision is made before pool selection (so failover cannot bypass inspection).
7. Implement metrics, events, and S-053 visualizations (table alternatives), plus bulk operations and API.
8. Write tests: distribution accuracy (chi-square tests for weights), failover timing, outlier ejection, retry rules, sticky behavior, drain, invariants, performance overhead (≤ 50 µs per request), chaos tests (origin flapping).
**Deliverables.**
- ADR, data model, selector, health logic, UI, tests
**Acceptance.**
- A1: weighted distribution within 2% of configured weights over 100k requests.
- A2: unhealthy origins are ejected within the configured threshold and re-admitted with slow start.
- A3: no request bypasses inspection through failover (test).
- A4: draining stops new connections without dropping in-flight requests.
- A5: overhead target met.
**Tests.**
- Unit/statistical, integration with multiple fake origins, chaos.
**Notes.** Tier 4 multi-region origin steering is out of scope.

### T-0544 · Tier 2: opt-in static content cache with purge API
`P32` `[DP][API][UI][SEC]` · deps: T-0365, T-0410 · size: L · owner: dp
**Objective.** Reduce origin load and improve resilience during attacks for static assets, without risking cache poisoning or leaking private content.
**Steps.**
1. ADR on scope and risk: cache only explicitly enabled path patterns/extensions, `GET`/`HEAD`, 200/301/404 within limits, honoring `Cache-Control`/`Expires`/`Vary` conservatively, never caching responses with `Set-Cookie`, `Authorization` requests, `Cache-Control: private/no-store`, or non-idempotent methods; cache key = (site, normalized host, path, normalized allowlisted query params, `Accept-Encoding` variant, `Vary` headers); default off.
2. Implement an in-memory + optional disk cache (bounded: per-site and global size caps, LRU/TinyLFU, file-backed with `O_NOFOLLOW`, content-addressed names, no path derived from user input), request coalescing (collapsed forwarding), stale-while-revalidate/stale-if-error (bounded), and byte-range support.
3. Implement **cache poisoning defenses**: normalized keys; unkeyed header detection (headers that influence the response without being in `Vary` flagged via differential probing in monitor mode); reject responses with `Content-Type` mismatching extension for executable types; strip hop-by-hop; limit cached object size (default 5 MiB); never cache error pages generated by HDD; respect `Vary: *`; cache-deception protection (path-extension tricks like `/profile.php/x.css` are not cached unless the origin marks them public).
4. Implement **WAF ordering:** cache lookup occurs after inspection and ban checks (a banned IP is never served from cache); cache hits skip origin but still apply outbound policies (header policy; the outbound scanner runs at fill time for cacheable bodies).
5. Implement the **purge API** (`POST D/cache/purge` by URL, prefix, tag (surrogate keys via `Cache-Tag` header), or all) with rate limits, audit and permission; purge propagates to all proxy processes within 2 s.
6. UI: cache settings (patterns, TTL overrides within bounds, query param allowlist), hit ratio charts, purge dialog, and "cache bypass test" tool; metrics for hits/misses/stale/bytes saved.
7. Integrate with the shield (`cache.serve_static` action in ATTACK state, serving stale content when the origin is overloaded).
8. Write tests: key normalization properties, poisoning corpora (unkeyed header attacks, web cache deception patterns), concurrency (coalescing), eviction, disk safety, purge propagation, performance, claims-lint.
**Deliverables.**
- ADR, cache module, purge API/UI, tests
**Acceptance.**
- A1: responses with cookies, private directives or authorization are never cached (test corpus).
- A2: banned IPs never receive cached content.
- A3: web-cache-deception and unkeyed-header corpora do not result in cross-user content exposure.
- A4: purge takes effect ≤ 2 s across proxy workers.
- A5: memory and disk caps are enforced.
**Tests.**
- Unit, property, integration, security corpora.
**Notes.** HDD is not a CDN; the cache is a resilience and cost optimization, off by default.

### T-0547 · Tier 5: WebAssembly plugin runtime (`wasmtime`) for custom detectors and transformations

**Objective.** Allow safe extension of the pipeline with sandboxed, resource-limited plugins without risking the data plane.
**Steps.**
1. ADR on the extension model and threat analysis: plugin stages limited to **pure inspection hooks** (`inspect_request(view) -> Findings`, `transform_response_headers`) operating on read-only views; no I/O, no clock, no randomness, no network; deterministic execution; why `wasmtime` (fuel metering, memory limits, WASI-free, component model) versus alternatives (`wasmer`, `wasm3`, native dynamic libraries rejected).

Implement the **host runtime:** per-plugin instance pools, fuel limits per invocation (e.g., 2 M instructions), memory cap (e.g., 16 MiB), wall-clock watchdog via epoch interruption, trap handling (a trapping plugin is treated as `no finding` plus a metric and auto-disable after repeated traps, never as fail-open of core rules), compile caching with signature verification, and per-tenant isolation (instances are never shared across tenants).

Implement **signing and distribution:** plugins are signed by the platform key (platform plugins) or by tenant keys (tenant plugins in enterprise plans) and uploaded through the API with validation (ABI conformance, size ≤ 2 MiB, static analysis for imports: only allowed host functions), lifecycle states (draft → monitor → enforce → retired) identical to rules, and rollback.

6. Implement **performance and fairness:** plugin budgets added to inspection budgets (T-0256); global fuel accounting per tenant; shed plugin execution before core inspection under load.
7. Security review: plugin escape attempts (malicious wasm: infinite loops, memory growth, out-of-bounds, huge tables), side channels documented, supply chain of plugins, and a lab pentest note.
8. Write tests: ABI conformance, limit enforcement, determinism (same input same output), trap handling, signature enforcement, tenant isolation, load/fairness simulation, and a corpus of hostile wasm modules.
**Deliverables.**
- ADR, runtime, ABI, SDK, UI/API for plugin lifecycle, tests
**Acceptance.**

- A2: plugin traps never cause fail-open of core detection.
- A3: unsigned/non-conforming plugins are rejected.
- A4: results are deterministic across runs.
- A5: overhead of a no-op plugin ≤ 20 µs per request.
**Tests.**
- Unit, hostile corpus, performance, integration.
