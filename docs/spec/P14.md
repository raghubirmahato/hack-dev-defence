## PHASE P14: SQL injection shield (T-0263 to T-0284) · milestone M6 · gate G14

Requirement prefix `SQLI`. Goal: deliver the capability at the center of the product: **any SQL injection attempt against any form, login page, URL, header or cookie is detected and blocked, and the attacker's IP is banned, even when the origin application is itself vulnerable.** The phase builds the SQL tokenizer and fingerprint engine, the six hard signature families (H1 to H8 of C4.5) including the six mandated payloads, evasion handling, field-kind context policy, the SQLi ban policy, auth-endpoint behavior, NoSQL/LDAP/XPath/GraphQL injection detectors, write-path hardening for second-order attacks, time-based attack detection, the fixture and benign suites, the sqlmap campaign harness, metrics and UI integration.

This phase implements detection and the ban *decision* (the `BanIntent` and the policy table of C4.10). Ban *storage and enforcement* (Redis, kernel) arrive in P16 and the end-to-end lab proof (AC-38, AC-39) is completed there; here the proof is at the engine, inspect-API and proxy-verdict level plus a sqlmap campaign in `monitor` mode through the walking-skeleton proxy.

Doctrine reminders (C4): hard hits ban on first occurrence outside cross-site subresource context; password-field H2 is the one documented relaxation (soft 4 in Balanced); benign names such as `O'Brien` must pass; the mandated set is the six payloads supplied by the operator plus the variant families.

Gate G14 passes when: the mandated set and all variant fixtures are 100% `would_block` with category `sqli` in every vector of C4.2; held-out detection ≥ 95%; benign corpora produce zero false positives; the sqlmap monitor-mode campaign coverage ≥ 95% of injection-bearing requests (exact figure and unflagged classes reported); mutation score on SQLi modules ≥ 80%; fuzz smoke is clean.

### T-0263 · SQL tokenizer with dialect awareness
`P14` `[DP][SEC]` · deps: T-0242, T-0262 · size: XL · owner: waf
**Objective.** Tokenize attacker-controlled text as SQL would see it, in several starting contexts, without depending on a database.
**Steps.**
1. Define token classes: `Keyword`, `Function`, `Operator`, `Number`, `String` (single, double, backtick, `$$`, `N'...'`, `E'...'`, `X'...'`), `Identifier`, `Comment` (`--`, `#`, `/* */`, `/*! */` unwrapped by the canonical view), `Punct` (`;`, `,`, `(`, `)`), `Variable` (`@x`, `@@x`, `$1`, `:name`), `Whitespace`, `Unknown`, plus a synthetic `BreakoutQuote` token representing a quote that closes an assumed enclosing string.
2. Implement the tokenizer as a hand-written, allocation-light lexer over `&str`/bytes with bounded steps (maximum tokens 2,048 per field; beyond that flag `ParserLimit`), handling dialect differences: MySQL/MariaDB (backslash escapes, `#`, `--` requiring whitespace, `/*!`), PostgreSQL (`$$`, `E''`, `::`, `||`), MSSQL (`[ident]`, `--`, `;`, `+` concat, `@@`, `0x`), Oracle (`||`, `q'[...]'`, `dual`), SQLite (`[ident]`, double-quote identifiers, `||`), ANSI baseline.
3. Evaluate three **starting contexts** per input: `none` (as if in an unquoted numeric position), `single_quote` (as if the value is inside `'...'`), `double_quote` (inside `"..."`), plus `backtick` for MySQL identifiers; for the quote contexts, the first matching closing quote becomes a `BreakoutQuote` and tokenization continues in normal mode, which is how `' OR 1=1--` is understood.
4. Provide keyword/function tables per dialect with a compact perfect-hash lookup, categorized (boolean connectors, set operators, DML/DDL, time/delay functions, metadata names, string/hex functions).
5. Provide token stream helpers: reduced token codes (a short alphabet used by fingerprints), position mapping back to the `decoded` view for evidence spans, and a streaming iterator to avoid allocating vectors on hot paths.
6. Document the design with a table of sample inputs and resulting token sequences for each mandated payload in each context.
7. Write 400 table tests across dialect features and 200 adversarial inputs (unterminated strings/comments, nested quotes, huge numbers).
8. Fuzz the tokenizer for panics and quadratic behavior.
**Deliverables.**
- `hdd-waf-core::sql::tokenizer`, tables, docs, tests, fuzz target
**Acceptance.**
- A1: `' OR 1=1--` tokenizes in `single_quote` context as BreakoutQuote, OR, Number, Operator, Number, Comment.
- A2: `admin' --`, `admin' #`, `admin'/*` produce Identifier, BreakoutQuote-or-Quote, Comment tokens in the relevant contexts.
- A3: tokenization is linear time on adversarial inputs (property test with measured scaling).
- A4: token and step caps produce `ParserLimit` flags instead of panics or long loops.
- A5: tables cover all five dialects with at least 60 cases each.
**Tests.**
- Table (400) / adversarial (200) / proptest (scaling) / fuzz.
**Notes.** The tokenizer is an original implementation; no third-party SQLi library code is copied.

### T-0264 · Fingerprint engine and fingerprint database tooling
`P14` `[DP][QA]` · deps: T-0263, T-0254 · size: L · owner: waf
**Objective.** Recognize SQL injection by token-sequence shape, learning from labeled corpora without overfitting.
**Steps.**
1. Define fingerprints as short strings of reduced token codes (for example `q o n o n c`) computed from the first N significant tokens after the breakout point, in each starting context, with rules for collapsing repeated tokens.
2. Build the fingerprint database tooling (`xtask sqli-fingerprints build`): input labeled corpora (attack-labeled fixtures from `tests/fixtures/sqli`, benign corpora), output sets `attack_fp`, `benign_fp` with counts; fingerprints observed in both are flagged for manual review and excluded from automatic blocking.
3. Implement the runtime matcher: a perfect hash set lookup of fingerprints (embedded in the binary, versioned) used as a *soft* signal (score 3) unless the fingerprint is on the curated `hard` list (derived from H-families) ; unknown fingerprints with SQL-like token composition get a low soft score.
4. Enforce the **license and provenance discipline**: only original fixtures and permissively licensed or explicitly allowed public corpora (recorded in the fixture headers) feed the database; held-out sets are excluded from training (lint on the build tool).
5. Implement cross-validation tooling reporting precision/recall on held-out data and per-subtype confusion; produce a report included in gate documentation.
6. Implement database update safety: the generated set is checked in as a data file with a hash, regenerated deterministically, and reviewed as a diff (counts added/removed).
7. Implement size and performance constraints (set size under 1 MB, lookup under 100 ns).
8. Test with the mandated payloads and variants to ensure they map to hard fingerprints.
**Deliverables.**
- fingerprint builder, runtime matcher, generated data, reports, tests
**Acceptance.**
- A1: the builder refuses held-out fixtures and unlicensed corpora (tests).
- A2: fingerprints present in both attack and benign sets are never auto-hard.
- A3: the mandated payloads map to fingerprints marked hard.
- A4: held-out recall report is generated (≥ 95% target at the gate).
- A5: the database file is deterministic (hash stable across two builds).
**Tests.**
- Unit: reduction and collapsing rules; integration: build and cross-validate; benchmark lookup.
**Notes.** The fingerprint layer supplements, never replaces, the explicit hard families.

### T-0265 · Hard family H1: tautologies and always-true predicates
`P14` `[DP][SEC]` · deps: T-0264 · size: L · owner: waf
**Objective.** Detect boolean-condition injections regardless of operands, quoting and spacing.
**Steps.**
1. Implement the semantic evaluator over token streams: after a boolean connector (`or`, `and`, `xor`, `||`, `&&`, possibly preceded by closing parentheses `)` sequences or a breakout quote), parse a bounded expression (comparison of operands, `like`, `rlike`, `regexp`, `in (...)`, `between`, `is [not] null`, `not`, `true/false`, bare literals) and evaluate it over literals: numbers, strings (quote-normalized so `'1'` equals `1`), booleans, NULL, identical identifiers (`a=a`), with MySQL-style loose comparisons (string to number) and case-insensitive string compare.
2. Classify as tautology when the expression evaluates to true (including trivially true shapes `1`, `true`, `'x'`, `1<2`, `2>1`, `'a'='a'`, `'a' like 'a'`, `1 in (1)`, `1 between 0 and 2`, `not 0`, `1=1`, `1 is not null`), with variants wrapped in parentheses `((...))` and quote/paren mixtures (`') or ('1'='1`, `")) or (("1"="1`).
3. Define subtype `tautology`; hardness rules: **hard** when a boolean connector appears together with either a breakout quote/paren in the preceding tokens or a SQL-ish token (keyword, comment, `limit`) around, or when the field kind is numeric; **soft 4** for a bare `or 1=1` in prose-like text without breakout (e.g., "x or 1=1 is true").
4. Cover all the mandated forms: `' OR 1=1--`, `' OR '1'='1`, `' or 1=1 LIMIT 1 --`, plus `1' or '1'='1`, `' || '1'='1`, `' OR 'x'='x`, `" or ""="`, `' or 1 --`, `' OR TRUE--`, `' or 'a' like 'a`, `' or 1 in (1)--`.
5. Implement operand evaluation limits (maximum expression length 64 tokens) and timeouts via token counters.
6. Write rule metadata (`HDD-SQLI-0001..`) with examples and counter-examples (`O'Brien`, `rock 'n' roll`, `1=1 is a tautology in math`, `select your plan or save`, `what is 2>1 ?`) and link ATK-001.
7. Test across the vector/field-kind matrix.
8. Measure false positives against the benign corpora (must be zero).
**Deliverables.**
- H1 evaluator and rule files, fixtures (≥ 80 variants), tests
**Acceptance.**
- A1: every H1 fixture variant is hard and categorized `sqli/tautology`.
- A2: counter-examples produce no hard match.
- A3: M1, M2 and M6 are hard hits in every vector.
- A4: evaluation never exceeds its token cap; adversarial long expressions are flagged not looped.
- A5: zero false positives on benign corpora for H1.
**Tests.**
- Table (200) / proptest (spacing, case, encoding permutations of M1 to M6 stay detected) / fuzz.
**Notes.** The proptest generator applies the evasion catalog (C4.8) transformations to the mandated set.

### T-0266 · Hard family H2: quote breakout followed by comment or terminator
`P14` `[DP][SEC]` · deps: T-0264 · size: L · owner: waf
**Objective.** Catch authentication-bypass idioms such as `admin' --`, `admin' #` and `admin'/*` without flagging ordinary apostrophes.
**Steps.**
1. Implement the H2 rule over token streams: a quote (single, double, backtick, or `)` after a closing quote) that immediately (ignoring whitespace) precedes a comment starter (`--`, `#`, `/*`) or a statement terminator sequence (`;--`, `;#`), where the token before the quote is an Identifier, String-like, Number or `)` (so it plausibly closes a SQL value).
2. Handle dialect specifics: MySQL `-- ` needs trailing whitespace or end of input (still flag `--` at end or before newline), `#` as comment, `/*` unterminated; PostgreSQL/Oracle/MSSQL `--` immediately after quote; also `-- -`, `--+`, `%23` encoded hash after decoding.
3. Define subtype `comment_termination` (with alias `auth_bypass` when the surrounding field kind is username/email/password or on an auth endpoint) and hardness rules from C4.5: **hard** in all kinds except `password`, where it is **soft 4** under Balanced and **hard** under Paranoid; on declared auth endpoints in the `strict` profile it is hard everywhere except password-kind in Balanced.
4. Cover the mandated forms `admin' --`, `admin' #`, `admin'/*`, and variants `admin'--`, `admin')--`, `admin"--`, `' --`, `'--`, `') --`, `'; --`, `1'#`, `admin' -- -`, `admin'%23`, `admin'/**/--`, `admin'/*!`.
5. Define counter-examples that must not match: `O'Brien`, `D'Angelo`, `it's -- fine` (quote not directly followed by the comment), `l'#1` and `I'#1 fan` (**soft 2** only in `free_text` and `search` field kinds, where `'#<digit>` is numbering in prose; hard in `username`, `email`, `numeric_id`, unknown kinds and on auth endpoints, and `'#` followed by a letter is hard in every kind but `password`; boundary cases are listed in E1.11 and read from `h2-boundary.txt`), `5'10" tall`, `rock 'n' roll`, `'Hello' -- he said` (quote closes a quoted word; flagged soft not hard unless the preceding token pattern is an identifier directly adjacent to the quote with no space and the quote is unbalanced).
6. Implement the **balance heuristic**: if quotes in the field are balanced and the comment follows a closing quote of a complete quoted word separated by spaces, downgrade to soft; if the quote count is odd and the quote touches an identifier/number, treat as breakout (hard).
7. Write rule metadata with examples/counter-examples and link ATK-002, ATK-011.
8. Test across vectors and field kinds, including password-kind behavior in both strictness modes.
**Deliverables.**
- H2 rule logic, rule files, fixtures (≥ 80 variants), tests
**Acceptance.**
- A1: M3, M4, M5 are hard hits in username, email, search, free-text, header and cookie vectors.
- A2: in password-kind fields under Balanced they are soft 4 (blocked only if the threshold is reached or on Paranoid) and the verdict explains why.
- A3: all counter-examples produce no hard match.
- A4: encoded forms (`%27%20--`, `%27%23`, `%2527--`) are detected.
- A5: zero false positives on benign corpora for H2 (names with apostrophes are covered).
**Tests.**
- Table (200) / proptest (evasion permutations) / fuzz; benign gate.
**Notes.** The password-kind relaxation is `DEV-V5-003`-adjacent policy documented in C4.6 and visible in S-057.

### T-0267 · Hard family H3: UNION-based extraction and column probing
`P14` `[DP][SEC]` · deps: T-0264 · size: M · owner: waf
**Objective.** Detect result-set injection attempts.
**Steps.**
1. Implement the `UNION [ALL|DISTINCT] SELECT` detector over the canonical view and token stream (comments/whitespace/versioned comments between tokens are already normalized), including `UNION` split by comments (`UN/**/ION` is not valid SQL, so ignore) and `UNION` with `(SELECT ...)` parentheses.
2. Implement column-count probing detection: `ORDER BY <n>` / `GROUP BY <n>` where `n` is a small integer immediately following a breakout quote/closing paren or in a numeric-context field; `NULL,NULL,...` padding in a select list; `SELECT 1,2,3...` literal lists.
3. Implement the **select-after-breakout** rule: after a breakout quote/paren, a `SELECT ... FROM|,|--` shape is hard (subquery injection) even without UNION (`' AND (SELECT ...)`, `' OR EXISTS(SELECT ...)`).
4. Define subtype `union` and `probe`, hardness hard; soft-only for isolated `ORDER BY 5` without breakout in free text (2).
5. Add metadata functions that appear in union payloads (`@@version`, `version()`, `user()`, `database()`, `current_user`, `schema()`, `concat(`, `group_concat(`) to strengthen confidence (bonus soft weight, not required for hard).
6. Write rule metadata and fixtures (≥ 60) including obfuscated forms, case variations, versioned comments, whitespace variants, JSON-escaped, double-encoded.
7. Define counter-examples: "union station", "selection of items from our store", "order by 5 pm" (prose), SQL tutorial text with `UNION` in a sentence without `SELECT` adjacent.
8. Link ATK-003, ATK-004 and test benign.
**Deliverables.**
- H3 detector, rules, fixtures, tests
**Acceptance.**
- A1: `' UNION SELECT NULL,NULL--`, `1 UNION ALL SELECT username,password FROM users`, `-1 union/**/select 1,@@version,3`, `' ORDER BY 5--` are hard.
- A2: counter-examples do not match.
- A3: encoded and obfuscated forms (double URL encoding, comment-as-space, case mix) match.
- A4: sentences containing both words far apart (more than 3 tokens) do not hard-match.
- A5: zero false positives on benign corpora.
**Tests.**
- Table (150) / proptest / benign gate.
**Notes.** Prose heuristics only affect soft signals; hard shapes require grammatical adjacency.

### T-0268 · Hard family H4: stacked queries and dangerous statements
`P14` `[DP][SEC]` · deps: T-0264 · size: M · owner: waf

**Steps.**
1. Implement detection of `;` (statement terminator) followed (ignoring whitespace/comments) by DDL/DML/administrative keywords: `drop`, `alter`, `create`, `truncate`, `insert`, `update`, `delete`, `exec`, `execute`, `declare`, `shutdown`, `grant`, `revoke`, `merge`, `call`, `copy`, `load`, `attach`, `pragma`, `vacuum`, `set`, `use`, `begin`, `commit`, `rollback`, `waitfor`, `backup`, `restore`.

4. Handle `;` encoded as `%3b`, `&#59;`, fullwidth `；` (folded), and splitting by comments.

**Tests.**

### T-0271 · Authentication-bypass idioms (H7) and evasion constructs (H8)
`P14` `[DP][SEC]` · deps: T-0265, T-0266 · size: L · owner: waf
**Objective.** Close the remaining classic idioms and the encoding/obfuscation tricks that attackers use against signature filters.
**Steps.**
1. H7 explicit idioms: `' or ''='`, `'='`, `' or 1 --`, `admin' or '1'='1'--`, `' or username like '%admin%'--`, `' having 1=1--`, `' group by x having 1=1--`, `admin' and 1=1--`, `') or true--`, `' or 'a'='a`; implement as semantic checks reusing H1/H2 evaluators with subtype `auth_bypass`.
2. H8 evasion: version-comment keywords (`/*!50000select*/`), hex/CHAR/CHR construction of quotes or keywords near SQL tokens (`concat(0x27,...)`, `char(39)`), scientific-notation glue (`1e0union`, `1.e(`), `%00` inside keywords, concatenation of keyword parts, mixed-case keywords with comment-as-space, nested comments, `+`/`%0b` whitespace variants, and unusual separators (`/*!*/`, `\N`, `+-` sign noise before numbers).

4. Implement double-parse differentials: detect inputs where `decoded` and `raw` yield different SQL interpretations (one benign, one malicious) and treat as hard (`evasion.differential`).
5. Handle parameter pollution splits: concatenated duplicates view is analyzed with the same detectors (T-0240).
6. Write rule metadata and fixtures (≥ 100) covering the full C4.8 catalog items 1 to 12, 14, 15, 17 to 20 (transport-level ones are tested at the proxy layer).
7. Counter-examples for evasion rules: legitimate uses of fullwidth characters in Asian text, scientific notation in numeric fields ("1e5" as a number), legitimate hex strings (colors `#ff00aa`, hashes).
8. Validate against benign corpora; add tests for the `aggressive` view limits.
**Deliverables.**
- H7/H8 logic, aggressive view, fixtures, tests
**Acceptance.**
- A1: each C4.8 evasion item has at least 5 fixtures that are detected as hard (or soft with explicit documented reason).
- A2: legitimate CJK, hex colors, hashes and scientific notation do not trigger.
- A3: differential interpretations are flagged.
- A4: detection results are stable under 3 levels of re-encoding.
- A5: zero false positives on benign corpora.
**Tests.**
- Table (250) / proptest (transformations of the mandated set) / fuzz.
**Notes.** The proptest transformation set is the executable form of C4.8.

### T-0272 · Field-kind context policy and learned parameter shapes
