## PHASE P21: Origin protection and outbound filter (T-0405 to T-0416) · milestone M8 · gate G21

Requirement prefix `ORG`. Goal: make the protected site safe even when its code is weak and even when attackers know where it lives. Origin lockdown (secret header, mTLS, firewall allowlist, drift detection), the lockdown wizard, continuous origin-exposure monitoring, the outbound leak filter (database errors, stack traces, secrets, source code, directory listings), the response header policy, cookie and session protection, client-side supply-chain visibility (CSP reports, SRI, third-party scripts), tenant egress safety, bulk-exfiltration guards, and the end-to-end proofs for the lockdown and outbound behaviors.

Non-negotiables: HDD never reads, stores or relays response bodies beyond the bounded scan window (the scanner keeps at most a 512-byte redacted snippet as evidence, R-22); the outbound filter never corrupts binary or streaming responses; it never sends scan results to third parties; header and cookie rewriting is explicit and reversible per site; HDD does not claim origin lockdown is applied until a probe from a non-HDD vantage proves direct access is refused (`lockdown_state=verified`); every claim about leaked data is "detected patterns", never "no leak".

Gate G21 passes when: AC-10 (outbound leak control) passes with the canary `leak.txt` and the lab leak fixtures including binary and streaming negatives; AC-18 passes or is `UNVERIFIED(human_step_pending)` only for the operator-side firewall change; AC-05 header checks pass with the canary echo; AC-17 connect-time SSRF checks pass in the proxy; zero false positives on the benign outbound corpus; and the claims-lint passes for every new string.

### T-0405 · Origin lockdown model: states, secret header enforcement, mTLS selection and allowlist publication
`P21` `[DB][API][SEC][DP]` · deps: T-0361, T-0383, T-0163, T-0165 · size: L · owner: sec
**Objective.** Define what "locked down" means, make it a state machine with evidence, and publish the exact data an owner needs to apply it.
**Steps.**
1. Add the `origin_lockdown` model (migration): per site `state` in `pending | instructed | applied_unverified | verified | degraded | disabled`, `method` in `header | mtls | both | firewall_only`, `last_probe_at`, `last_probe_result`, `evidence_ref`, `secret_current_id`, `secret_previous_id`, `rotation_started_at`, `allowlist_version`, `acknowledged_risk` (typed confirmation when the owner chooses `disabled`).
2. Implement the **HDD egress address set** publication: `GET /api/v1/platform/egress-ips` (public, cacheable 5 minutes) returns the IPv4/IPv6 addresses from which the proxy and probe workers connect to origins, a `version` and `valid_from`. Changes to the set (IP migration) require a 30-day overlap announcement via notifications and the status page; the set is generated from the profile and never includes the control-plane worker unless it also connects to origins (documented).
3. Implement **secret header enforcement semantics** for the origin side as documentation plus a verification probe (HDD cannot enforce on the origin); on the HDD side ensure the header is always sent, is stripped from inbound client requests, and never appears in responses, logs, events or error pages (grep tests over a corpus of 10,000 requests).
4. Implement **rotation**: create next secret, enter `rotation_started_at`, send both-accepting instructions, switch HDD to the new secret only after the owner confirms the origin accepts both (confirmation by probe: HDD sends requests with old-only and new-only secrets to a test path and checks acceptance), then retire the old; rotation expires after 14 days with a reminder cadence; audit every step.
5. Implement mTLS selection: toggling `method` between header, mtls and both with preflight (certificate issued, CA downloadable, origin handshake test) and automatic fallback prevention (if `mtls` is selected and the handshake fails, HDD does not silently downgrade to header-only; it records `degraded` and alerts).
6. Implement **allowlist drift detection**: the verification probe from a non-HDD vantage (the operator's runner in the pilot, an external probe service the operator configured in production, or a "bring your own probe" token page for SaaS) checks that a direct connection to `origin:port` (with and without SNI/Host) fails or returns a non-site response; a success downgrades `verified` to `degraded` within 24 h and raises an attention item.
7. Implement the origin-side **canary** hook: when `hdd-canary` is installed, its `echo-headers` endpoint is used to confirm that the secret header and source IP seen by the origin are HDD's.
8. Expose API/permissions: `GET/PUT D/origin/lockdown`, `POST D/origin/lockdown:probe`, `POST D/origin/lockdown:rotate`, with `PERM-origin.lockdown` for owner/admin and read for analyst.
9. Add readiness-score inputs (T-0172): lockdown verified (+), applied_unverified (partial), disabled (penalty), plus a prominent warning that WAF protection is bypassable while direct access works.
10. Write tests: state transitions, rotation with simulated origin acceptance, secret never leaving the encrypted store, probe results from simulated vantage points, API permissions, RLS.
**Deliverables.**
- migration, services, API, OpenAPI, tests, docs
**Acceptance.**
- A1: the state machine rejects illegal transitions and records evidence for every transition.
- A2: the secret header is absent from every response/log/event in the corpus test.
- A3: rotation never produces a window where the origin rejects HDD (simulated origin accepting both).
- A4: drift detection downgrades state within one probe interval in a simulation.
- A5: `egress-ips` includes IPv6 when enabled and is versioned.
**Tests.**
- Integration with simulated origins (header-required, mTLS-required, open); unit: state machine; RLS tests.
**Notes.** "Verified" requires an off-platform probe; a probe from the VPS itself proves nothing (C9.12).

9. Write end-to-end tests with a headless browser against local stacks (nginx and Apache containers in the lab) following the generated snippets and verifying the probe outcomes before and after.

**Acceptance.**

- A2: every snippet includes the timed-revert variant or a "keep your management access" warning (static test over templates).

**Tests.**

### T-0408 · Outbound leak detection engine (pure library) and signature catalog
`P21` `[DP][SEC]` · deps: T-0311, T-0239, T-0253 · size: L · owner: dp
**Objective.** Detect, in response bodies, the content that helps attackers or reveals secrets, with a low false-positive rate.
**Steps.**
1. Implement `hdd-waf-core::leak` as a pure library: input `(content_type, status, decompressed_prefix_bytes, flags)`, output `LeakFindings` with category, confidence, pattern id, offset and a redacted 512-byte snippet (via T-0253). No allocation per byte; patterns compiled into automata at snapshot load.
2. Define **categories and patterns** (all documented in `docs/OUTBOUND.md`, each with a positive and negative fixture):
   - Database errors: MySQL (`You have an error in your SQL syntax`, `mysql_fetch_`, `Warning: mysqli_`), PostgreSQL (`PG::SyntaxError`, `ERROR:  syntax error at or near`, `pg_query()`), SQL Server (`Unclosed quotation mark after the character string`, `Microsoft OLE DB Provider for SQL Server`, `ODBC SQL Server Driver`), Oracle (`ORA-\d{5}`, `quoted string not properly terminated`), SQLite (`SQLiteException`, `sqlite3.OperationalError`, `near "…": syntax error`), MongoDB (`MongoError`, `E11000 duplicate key`), generic JDBC/Hibernate/Sequelize/GORM/Doctrine exceptions.
   - Stack traces: Java (`at com.…(File.java:123)` blocks, `java.lang.*Exception`), .NET (`at System.…` lines, `Server Error in '/' Application`), Python (`Traceback (most recent call last):`), PHP (`Fatal error:`, `Stack trace:`, `on line \d+`), Ruby/Rails, Node (`at Object.<anonymous> (/path`), Go panics (`goroutine 1 [running]`), Rust panics (`thread 'main' panicked at`).
   - Secrets: private-key PEM headers, AWS access key ids (`AKIA…`, `ASIA…`) with secret-shaped neighbors, GitHub/GitLab/Slack/Stripe token formats (prefix + length + charset), JWTs in HTML/JSON that look like admin tokens (only when `Set-Cookie`-less body leak patterns), `.env`-style lines (`DB_PASSWORD=`, `APP_KEY=base64:`), connection strings with credentials (`postgres://user:pass@`).
   - Source code markers: raw `<?php` / `<%@ ` / `<% ` in responses served as text/html where the origin should have executed them, `#!/usr/bin/env` heads, `__pycache__` paths.
   - Directory listings: `Index of /`, `<title>Index of`, Apache/nginx/IIS listing structures, S3-style `ListBucketResult` bodies.
   - Version banners and internal paths: `/var/www/`, `C:\inetpub\`, `/home/<user>/`, with a minimum-evidence rule (two or more path occurrences or a path adjacent to an error marker).
3. Apply **confidence scoring** (high: error + context, medium: single marker, low: weak path/version) and a **context filter**: documentation sites, security blogs and code hosting pages may legitimately contain these strings; the filter downgrades findings when the response is `text/html` with `<pre>`/`<code>` density over a threshold or the path is on the owner's `outbound_exclusions`. Findings from `application/json` and `text/plain` carry higher confidence.
4. Implement **streaming-friendly scanning** API (`LeakScanner::feed(chunk)` with a bounded rolling window so patterns spanning chunk boundaries are found) used by the proxy buffer in T-0409.
5. Implement **false-positive controls**: benign corpus of 500 pages (docs about SQL errors, StackOverflow-like pages, tutorials, changelogs) that must produce zero `high` findings in `block` eligibility; patterns that fail the corpus are downgraded or require context.
6. Provide pattern pack versioning (signed packs with rollout stages like WAF packs, rollback via config revisions) so false-positive fixes ship without a release.
7. Write unit tests (≥ 300 positive fixtures across languages, ≥ 300 negatives), property tests (chunk-boundary invariance: scanning in any chunking equals scanning whole), and fuzz targets for the scanner.
8. Benchmark: ≥ 400 MB/s scan throughput on cached patterns for 64 KiB windows on the builder; document.
**Deliverables.**
- `leak` module, pattern packs, fixtures, benches, `docs/OUTBOUND.md`
**Acceptance.**
- A1: all positive fixtures are detected with the documented category and confidence; no negative fixture yields a `high` finding.
- A2: chunk-boundary invariance holds for 100,000 random chunkings.
- A3: the canary `leak.txt` sentence is detected as `high` database error.
- A4: scanner memory is bounded (window ≤ 128 KiB + pattern state).
- A5: the throughput target is met or the deviation is documented.
**Tests.**
- Unit/property/fuzz/bench as above.
**Notes.** The scanner reports patterns; it never claims the response "contains no sensitive data".

### T-0409 · Outbound filter in the proxy: modes, buffering window, actions and S-097
`P21` `[DP][UI][API]` · deps: T-0408, T-0362, T-0363, T-0222 · size: L · owner: dp
**Objective.** Apply the leak engine safely to live responses and let owners control it.
**Steps.**
1. Implement the response-phase stage (pipeline stage 17): eligibility rules — only `GET/POST/...` responses with status 2xx/4xx/5xx and text-like content types (`text/*`, `application/json`, `application/xml`, `application/javascript` configurable), `Content-Encoding` of identity/gzip/br/deflate/zstd decompressed in a bounded streaming decoder (decompression bomb limits: decompressed size ≤ 10 MiB and ratio ≤ 20:1 per Appendix E4), skip for `Range`/`206`, WebSocket upgrades, server-sent events, gRPC, `Content-Length` > the large-body threshold (stream through, tag `skipped_large`), and per-path exclusions.
2. Implement the **hold window**: buffer up to the first 64 KiB of the decompressed body (configurable 16–256 KiB) before releasing headers; bodies larger than the window are scanned over the prefix and tagged `partial_scan`; the proxy documents the latency effect (added time to first byte bounded by origin send time of the first window, with a 250 ms hold timeout after which streaming proceeds and the response is tagged `scan_timeout`).
3. Implement modes: `off`, `monitor` (record events, pass body), `block` (high-confidence findings replace the response with the branded 500 `S-143`-style page and record a `critical` `data_leak` event; medium findings are masked or recorded per policy, see below), plus `mask` (replace only the matched span with a fixed marker when the content type is JSON/text and the replacement preserves syntactic validity; otherwise fall back to block). Masking is limited to database error and path patterns; secrets always block.
4. Recompute `Content-Length`, strip `Content-Encoding` only when the body had to be rewritten (recompress is not attempted; document the cost), keep `ETag`/`Last-Modified` semantics sane (drop the strong `ETag` on rewritten bodies), preserve `Vary`, never touch HEAD or 304 responses.
5. Implement the **fail-safe**: scanner errors or panics fall back to pass-through with a metric and an alert (the outbound filter fails open for availability by design because it is a secondary control; this is documented and the opposite of the request-side rule R-26; the readiness page states it).
6. Implement `S-097` backend: mode, exclusions (path + method + content type), pattern pack version, per-category toggles (database errors, stack traces, secrets, source code, directory listings, paths), confidence thresholds, test tool ("scan a pasted response" using the pure engine with redaction), event table, and the canary `leak.txt` verification button that runs the AC-10 probe via the pilot path.
7. Record events with ray id, path template, category, confidence, mode, action, response status, `partial_scan`, and the redacted snippet (≤ 512 B), applying the 30-day default retention; send `critical` findings to notifications (owner may opt out of snippet storage).
8. Emit metrics: scanned bytes, hold latency histogram, findings by category/action, skipped reasons, timeouts, masking successes/failures.
9. Write tests: origins returning each pattern in plain/gzip/br/chunked/HTTP2, boundary-spanning patterns, large bodies, binary data (images, PDFs, zips) untouched, streaming responses untouched, SSE untouched, HEAD/304 untouched, JSON validity after masking, monitor vs block behavior, exclusions, panic injection.
**Deliverables.**
- proxy stage, S-097 backend and screen wiring, metrics, tests
**Acceptance.**
- A1: AC-10 canary leak is blocked in `block` mode and recorded in `monitor` mode.
- A2: binary/streaming/Range/HEAD/304 responses are byte-identical to the origin response (differential test).
- A3: HDD-side scan and mask time p99 ≤ 3 ms per 64 KiB window on the builder (origin body-wait during the hold is origin time, C14.9); hold timeout behavior verified.
- A4: scanner panic injection leads to pass-through with an alert and no connection reset.
- A5: masked JSON responses remain valid JSON in 100% of fixtures.
**Tests.**
- Integration (proxy + fault origins), differential, property (chunking), performance.
**Notes.** The documented limit (prefix-only scan beyond the window) is shown in S-097 and the readiness page.

### T-0410 · Response header policy engine (security headers, disclosure removal, per-site overrides)
`P21` `[DP][UI][API]` · deps: T-0361, T-0409, T-0200 · size: M · owner: dp
**Objective.** Set safe defaults on every response without breaking the origin's own choices.
**Steps.**
1. Implement the **policy document** per site: `strip` (list of headers to remove, defaults `Server`, `X-Powered-By`, `X-AspNet-Version`, `X-AspNetMvc-Version`, `X-Generator`, `X-Drupal-*`, `X-Pingback`), `set_always` (`X-Content-Type-Options: nosniff`, `X-XSS-Protection: 0`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` conservative default or none if the origin sets one), `set_if_absent` (`X-Frame-Options: SAMEORIGIN` and CSP `frame-ancestors 'self'` only when neither is present; opt-out per site/path), `hsts` per TLS policy, `server_banner` (`Hack-Dev-Defence` default, override or removal), and `custom` (additional headers with allowlisted names; forbidden: `Set-Cookie`, `Content-Length`, hop-by-hop).
2. Implement precedence: the origin's explicit security headers win over `set_if_absent`; `set_always` wins over the origin only for `X-Content-Type-Options` and `X-XSS-Protection`; per-path overrides win over site defaults; every decision is traceable (`header_policy_trace` in debug mode for the sandbox).
3. Implement **safe testing of CSP and framing risks**: before enabling `X-Frame-Options`, a preview scanner warns when the site is known to be embedded (owner marks `allowed_embedders` list); the policy supports `frame-ancestors` allowlists.
4. Add a **CSP report-only suggestion helper** (links to T-0412) that never enables enforcement automatically; enforcement requires an explicit toggle with a reminder of breakage risk, a staged rollout (report-only for ≥ 7 days recommended in the UI) and an easy revert.
5. Implement HSTS interplay with certificate state (HSTS only when a valid certificate exists and the HTTPS redirect is on; preload guidance but no preload submission by HDD).
6. Implement header-size and count limits on responses (reject or truncate the origin's oversized `Set-Cookie` bursts with a 502 and a clear event instead of passing malformed headers), duplicate `Content-Length` handling, and removal of `Via` when configured.
7. Wire the UI in S-052/S-097 sections: toggle each group, show effective headers for a sample URL ("Preview with the sandbox canary"), explain each header in plain language, and show a diff of origin headers versus final headers from the last sampled response (headers only, no bodies).
8. Write tests: precedence matrix (≥ 120 cases), per-path overrides, absent/present origin headers, HSTS gating, oversize header handling, no alteration of `Set-Cookie` here (cookie policy is T-0411), HEAD/304 handling, and HTTP/2 header casing.
**Deliverables.**
- header policy module, schema, UI wiring, tests, docs
**Acceptance.**
- A1: the precedence matrix passes in all 120+ cases.
- A2: origin-set CSP/XFO are never overridden by `set_if_absent`.
- A3: HSTS is never sent without a valid certificate and the redirect enabled.
- A4: `Set-Cookie` is untouched by this stage (differential test).
- A5: policy preview matches live canary output byte-for-byte for the chosen URL.
**Tests.**
- Unit (matrix), integration (canary), differential.
**Notes.** The defaults aim to be non-breaking; anything with breakage potential is opt-in and reversible.

### T-0411 · Cookie and session protection (flag upgrades, scope hardening, fixation signals)
`P21` `[DP][SEC][UI]` · deps: T-0410, T-0361 · size: M · owner: dp
**Objective.** Reduce the damage of weak session handling in the protected application without changing application logic.
**Steps.**
1. Implement the cookie policy per site (all opt-in, default `report` mode): `secure_upgrade` (add `Secure` when the request was HTTPS), `httponly_upgrade` (add `HttpOnly` to cookies whose names match a configurable session-like pattern: `sess`, `sid`, `token`, `auth`, `PHPSESSID`, `JSESSIONID`, `connect.sid`, `laravel_session`, `ASP.NET_SessionId`, excluding cookies the app reads from JavaScript, listed by the owner), `samesite_default` (add `SameSite=Lax` when absent; `None` requires `Secure`), `prefix_hardening` (suggest `__Host-` prefixes; only report), `domain_narrowing` (drop broad `Domain=` attributes when the owner enables it), and `max_age_cap` (cap session cookie lifetime).
2. In `report` mode, record findings (cookie name hashed + attribute gaps, never values) in a per-site `cookie_audit` aggregate, displayed in S-043/S-097 with remediation text ("set these flags in your framework: …") for the common stacks.
3. Implement **session-fixation and hijack signals** (monitor first): the same session cookie value (HMAC'd keyed hash, never stored raw) seen from a new IP /24 and a new user-agent family within 60 s raises `session_anomaly` (soft score) with a tunable sensitivity; a session cookie value presented after the origin set a new value for the same cookie name on the same client (fixation indicator) is recorded; optional step-up (challenge) on high-risk anomalies for configured sensitive paths.
4. Implement a **session binding option** for strict sites (off by default): HDD adds a signed binding cookie (`__Host-hdd_bind`) containing a keyed hash of (client IP /24 or /56, UA family) and, if the application cookie arrives with a mismatching binding, applies the configured action (log, challenge, block). The option explains its drawbacks (mobile networks, privacy) and is rate limited to avoid lockouts; it fails open on missing binding to avoid breaking logged-in users during enablement (grace period 7 days).
5. Implement **cookie size/count protections**: reject responses with more than the configured number or total size of cookies (protects browsers and origin from cookie bombing), and strip cookies with invalid names.
6. Add **admin-path token tripwires**: the HDD-issued challenge clearance cookie (`__Host-hdd_cl`) is never forwarded to the origin (strip on the upstream request) and never logged.
7. Wire controls and explanations in the UI with a "what changes for your users" summary and a "revert" button; log every enablement as an audit event.
8. Write tests: attribute rewriting matrix (≥ 150 cases including multiple `Set-Cookie` headers, folded values, quoted values, unusual casing, partitioned cookies, `__Host-` and `__Secure-` prefixes), no mutation in `report` mode, binding behavior with grace period, clearance cookie stripping, performance (rewriting adds ≤ 50 µs per response with cookies).
**Deliverables.**
- cookie policy module, signals, UI, tests, docs
**Acceptance.**
- A1: in `report` mode no `Set-Cookie` header is modified (differential test over 10,000 responses).
- A2: with upgrades enabled all matrix cases produce the documented output; `SameSite=None` without `Secure` is never emitted.
- A3: the clearance cookie never reaches the origin or logs.
- A4: session binding with a mismatch triggers the configured action only after the grace period.
- A5: cookie values never appear in events, logs or metrics (grep test).
**Tests.**
- Unit matrix; integration with test origins; privacy greps.
**Notes.** Session binding is an advanced option marked "may log out users on network changes".
