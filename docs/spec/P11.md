## PHASE P11: Walking skeleton on the pilot (T-0207 to T-0220) · milestone M5 · gate G11

Requirement prefix `WSK`. Goal: prove on the operator's real VPS and real domain that the hardest unknowns work before deep security work begins: binding port 53, serving authoritative answers to the public internet, obtaining real (staging) certificates through ACME, terminating TLS, proxying to the real origin with strict verification, receiving configuration from the control plane, deploying and rolling back safely, and running the acceptance runner over the real internet path. The skeleton is thin by design: minimal DNS, minimal proxy, minimal certificate flow, the canary, deploy v0, telemetry v0, and the first acceptance checks.

This phase contains **STOP #1**: after T-0216 the agent halts and gives the operator exact steps (canary installation, pilot NS/A delegation, hosting provider acceptable-use confirmation) and resumes only after the operator confirms. Everything before T-0216 is built and tested locally; everything after needs the live pilot.

Safety reminders for this phase: the pilot delegates only `test_hostname` and `sandbox_hostname` subzones; the apex site is untouched; SSH-lockout protection applies to every host change (section 2.5); backups of the existing zone and firewall rules precede any change; the runner's IP is never in `admin_cidrs`; no volumetric tests.

Gate G11 passes when: AC-00 passes, AC-03 (basic), AC-04 (staging HTTP-01 and DNS-01 wildcard), and AC-05 (canary subset) pass on the pilot with pasted real output, the deploy path including rollback has been exercised, and the walking-skeleton report records the ADR confirmations.

### T-0207 · Minimal `hdd-dns` and the server-core spike
`P11` `[DP][DNS][SEC]` · deps: T-0179 · size: XL · owner: dns
**Objective.** Serve authoritative answers over UDP and TCP from an immutable snapshot, and decide the server core.
**Steps.**
1. Spike (time-boxed two days): evaluate `hickory-server` customization (EDNS cookies, response rate limiting, minimal responses, 0x20-safe case preservation, custom authority from our snapshot, TC handling, per-source limits) versus a custom server loop over `hickory-proto`; measure code size, control over limits, and fuzz resilience; write a **preliminary ADR stub** recording the options, the measurements and the provisional choice with a rollback plan; the final, signed-off ADR is written by T-0387 after the full-feature work (RRL, cookies, flattening) has been tried on the chosen core.
2. Implement the chosen core: UDP and TCP listeners (configurable bind, `SO_REUSEPORT`, bounded concurrency, TCP idle timeout 10 s, at most 256 TCP connections), wire parsing with strict bounds, and mapping to the pure answer engine (T-0179).
3. Implement v0 features: A, AAAA, NS, SOA, TXT, CNAME, MX at apex and subzones; NXDOMAIN with SOA, NODATA, REFUSED for foreign zones, RA=0, AA=1, EDNS0 with payload cap 1232, UDP truncation with TC=1, case-preserving question echo, `ANY` minimal, no recursion, no AXFR (refused).
4. Implement snapshot loading from Postgres (read-only role) at startup and via the config bus (T-0211); until then, a file loader used only in tests.
5. Implement basic protection: per-source QPS cap (50 qps without valid cookie, v0 without cookies), global malformed-packet handling that never panics, and counters (`MET-hdd_dns_queries_total`).
6. Run under systemd with `CAP_NET_BIND_SERVICE` only, `NoNewPrivileges`, `ProtectSystem=strict`, read-only root, private tmp, memory and task limits.
7. Write `hickory-client` based tests (UDP and TCP, EDNS, truncation, NXDOMAIN, wildcard, foreign zone).
8. Fuzz the packet parser entry point for 60 seconds in `verify`.
**Deliverables.**
- `crates/hdd-dns` v0, ADR, systemd unit template, tests
**Acceptance.**
- A1: `dig` against the loopback server returns correct answers for 30 reference queries (oracle check).
- A2: malformed packets (fuzz corpus) never crash the process.
- A3: truncated responses set TC and succeed over TCP.
- A4: the process runs without root after binding (capability-only) in the container test.
- A5: AXFR/IXFR from any source is refused in v0.
**Tests.**
- Integration with `hickory-client`; fuzz smoke; unit: limit logic; container test for capability dropping.
**Notes.** Full DNS features (RRL, cookies, flattening, transfers) are P20.

### T-0208 · Minimal `hdd-proxy`: TLS, host routing, origin forwarding, challenge serving
`P11` `[DP][SEC]` · deps: T-0211, T-0195 · size: XL · owner: dp
**Objective.** Terminate TLS and forward real requests to the real origin, safely, as the thinnest vertical slice.
**Steps.**
1. Decide the proxy core (own on `hyper`/`tokio-rustls` versus Pingora): short spike confirming required hooks (custom SNI resolver from snapshot, per-request pipeline, h2 limits); write the ADR stub (full ADR in T-0353) and proceed with the own core by default.
2. Implement listeners on :80 and :443 (host network, `SO_REUSEPORT`), ALPN `h2` and `http/1.1`, TLS 1.2+ via a custom `ResolvesServerCert` reading the snapshot's certificate map, and **refusal of unknown or absent SNI** (`unrecognized_name`).
3. Implement host routing by SNI plus normalized `Host`, rejecting duplicate Host headers, producing a branded 404 for unknown hosts (neutral page), and HTTP→HTTPS redirect except for ACME and canary paths.
4. Implement the v0 pipeline skeleton (stage trait, per-stage timing histograms) with stages 3 (route), 4 (client IP: peer only, trusted proxies empty), 16 (upstream request build: set `X-Forwarded-For`, `X-Real-IP`, `HDD-Connecting-IP`, `X-Forwarded-Proto`, `HDD-Ray-ID`, secret origin header), 17 (origin exchange), 18 (response headers: strip `Server`/`X-Powered-By`, set `Server: Hack-Dev-Defence`, add `nosniff`).
5. Implement the origin client: connection pooling, 3 s connect and 30 s read timeouts, no redirect following, TLS verification per the site's mode (webpki default; there is no disable switch), SNI and Host header per config, SSRF connect-time guard, loop detection.
6. Implement the sandbox route behavior: forward only GET/HEAD for the exact canary path allowlist; every other path and method answers 404/405 without contacting the origin; no request bodies forwarded.
7. Implement ACME HTTP-01 response serving from Redis/Postgres tokens on :80 and the Ray ID generator (`16 hex + -HDD1`).
8. Implement graceful shutdown/drain, body size cap 10 MiB (413), header block 32 KiB (431), header-read timeout 10 s.
**Deliverables.**
- `crates/hdd-proxy` v0, ADR stub, systemd unit template, tests
**Acceptance.**
- A1: requests to a hostname not in the snapshot get the neutral 404 and unknown SNI is refused (test with `openssl s_client` oracle).
- A2: forwarded requests carry the documented headers and the origin cannot be reached with disabled verification (no such option exists; test proves verification failure yields 502).
- A3: sandbox route never contacts the origin for non-allowlisted paths or methods (origin-side counter stays zero).
- A4: graceful drain finishes in-flight requests within the configured window.
- A5: `HDD-Ray-ID` is present on every response with the correct format.
**Tests.**
- Integration with local TLS/HTTP origins including faulty ones; `h2` client tests; fuzz smoke on the HTTP header parser path.
- Oracle: `openssl s_client` and `curl --http2`.
**Notes.** WAF stages arrive in P13 to P17; this skeleton is deliberately inspection-free (monitor-only `L7 pass`).

### T-0211 · Configuration distribution v0: snapshots, config bus and resync
`P11` `[DP][DB][OPS]` · deps: T-0179, T-0153 · size: L · owner: dp
**Objective.** Deliver control-plane changes to the data plane quickly and robustly.
**Steps.**
1. Implement the snapshot compiler in `hdd-common`: from Postgres rows (sites, hostnames, origins, zones, records, certificates, TLS settings, policies) to an immutable `Snapshot { revision, sites_by_host, certs_by_sni, zones, platform, ... }` with validation and a content hash.
2. Implement the config outbox: control-plane transactions insert `config_outbox(revision, scope, kind, payload_hash)` rows; a publisher task sends `hdd:events:config` messages with monotonic `revision` after commit (outbox pattern to avoid lost messages).
3. Implement subscribers in proxy and DNS: on message, if `revision == local+1` apply an incremental rebuild or fetch the new snapshot; on a **gap** or reconnect, resync immediately from Postgres; plus a 30 s timer safety net.
4. Implement atomic swap with `ArcSwap` and a retained previous snapshot for instant rollback on compile errors; failed compiles keep the last good snapshot and raise an alert and metric.
5. Implement delivery SLO measurement: time from commit to applied at each node (`MET-hdd_config_resync_total`, apply latency histogram), target under 2 s.
6. Implement snapshot size limits and memory accounting per tenant to prevent one tenant from bloating the snapshot (caps by plan).
7. Implement the revision gap test harness (drop messages deliberately) and Redis-down behavior (timer-based Postgres polling continues).
8. Document the protocol and the failure semantics.
**Deliverables.**
- snapshot compiler, publisher, subscribers, tests, docs
**Acceptance.**
- A1: a change committed in the control plane is applied on both proxy and DNS within 2 s p95 in the integration test.
- A2: dropping pub/sub messages leads to convergence via gap resync.
- A3: a snapshot compile failure keeps serving the last good snapshot and alerts.
- A4: Redis outage does not stop updates (poll fallback within 30 s).
- A5: snapshot memory per site stays within the configured cap.
**Tests.**
- Integration with real Redis/Postgres; chaos tests dropping messages and restarting nodes; unit: compile determinism.
**Notes.** AC-16 verifies convergence under node loss in P29. The bus is the `Bus` trait of `hdd-common::kv` (R-31): Redis when hosted, an in-process revisioned broadcast in the local profile; the Postgres poll fallback is the same in both. After each swap the snapshot is also written to the snapshot cache directory (C18.11) so a restart without stores serves the last good policy.
