# PART B: PRODUCT DEFINITION

## B1. Personas and jobs to be done

Design every screen for these people. Each persona has accessibility needs that are requirements, not afterthoughts.

### B1.1 Maya, the site owner (primary)

| Attribute | Detail |
| --- | --- |
| Who | Runs a small online shop or content site on WordPress or a custom PHP/Node app; hired a freelancer once; not a network engineer. |
| Goals | "Stop the weird traffic and the hacking attempts without breaking my site." Understand what is happening in plain language. Add a domain in minutes. |
| Fears | Breaking the live site during DNS changes; being locked out; paying for something she cannot verify; jargon. |
| Context | Laptop and phone; low tolerance for multi-page docs; edits DNS at a registrar UI she barely understands. |
| Needs from HDD | A guided wizard that detects her current DNS, offers the simplest integration (CNAME or nameservers), says what each step changes, tests before cutover, offers an instant way back, and shows a Protection Readiness checklist. A block page her customers can understand. |
| Success | Site is proxied, in monitor mode for a few days, then block mode, with an email when something serious happens. |
| Key journeys | J-02, J-07, J-08/J-09, J-12, J-15, J-16, J-22/J-23, J-25 |
| Accessibility | Screen magnification, large text, keyboard use after injury; reduced motion. |

| Attribute | Detail |
| --- | --- |

### B1.7 Adversary A (design for them, never for their convenience)

Scanners (sqlmap, nikto, nuclei), credential stuffers, scrapers, botnets, a curious attacker reading error pages, an attacker who tries to poison bans by luring victims, an attacker who tries to hijack signup or password reset, an attacker who tries to claim someone else's domain. Every flow is reviewed with an abuse case (T-0011 to T-0028, `[SEC]` tasks). Rule: error pages, block pages and API errors give attackers no rule names, no stack traces, no internal hostnames, no confirmation of account existence.

## B2. Information architecture

### B2.1 Surfaces and hosts

| Surface | Host | Audience | Exposure |
| --- | --- | --- | --- |
| `public` | `www.{{PLATFORM_DOMAIN}}` | anyone | public (proxied by HDD itself in dogfood mode) |
| `app` | `app.{{PLATFORM_DOMAIN}}` | signed-in tenant users, plus auth pages | public when `deployment_mode: saas`; allowlist or tunnel in `owner_only` |
| `admin` | `admin.{{PLATFORM_DOMAIN}}` | platform staff | never public by default: tunnel/WireGuard, or routed with `admin_cidrs` + MFA + step-up |
| `api` | `api.{{PLATFORM_DOMAIN}}` | API clients | public in `saas`; **bearer API keys only** (no cookies are accepted or set on this host); rate-limited |
| `status` | `status.{{PLATFORM_DOMAIN}}` | anyone | hosted outside the VPS where possible |
| `ns1/ns2` | `ns1.{{PLATFORM_DOMAIN}}` | DNS clients | UDP/TCP 53 |
| Customer domains | tenant-owned | their visitors | HDD data plane; reserved path prefix `/__hdd/` |

**Same-origin API mount.** The browser UI never calls `api.` cross-origin. `app.{{PLATFORM_DOMAIN}}/api/v1/*` and `admin.{{PLATFORM_DOMAIN}}/api/v1/*` are mounted same-origin by the router (T-0355) and forwarded to `hdd-api`, so cookie sessions, `__Host-` cookies, SameSite=Strict and CSRF checks work without CORS. The `admin` mount serves only `/api/v1/admin/*` and platform-scoped routes and is subject to the same `admin_cidrs`/tunnel rule as the admin host. The `api.` host serves the same OpenAPI document but accepts only `Authorization: Bearer` credentials; a request to it that carries a session cookie is answered `ERR-AUTH-001` and the cookie is ignored.

**Local profile hosts.** With `runtime.profile: local` (C18), `{{PLATFORM_DOMAIN}}` is `hdd.localhost`: the surfaces are `www.`, `app.`, `admin.`, `api.` and `status.` under it on the unprivileged web port (default 8443), `admin` is always loopback-only, and protected local sites are `<slug>.hdd.localhost` (Chromium and Firefox resolve every `*.localhost` name to loopback; Safari and command-line tools may need the hosts helper, C18.8).

The break-glass path (SSH tunnel to loopback `:3000` and `:8000`, plus `hddctl`) always works regardless of proxy state.

### B2.3 Navigation model

- **Org sidebar** (left, collapsible, icons plus labels): Overview, Domains, Live events, Bans, Analytics, Reports, Notifications, Integrations, Team, API keys, Audit log, Plan and usage, Settings. Items the user lacks permission for are hidden, not disabled with a mystery tooltip; where the feature exists but needs a higher plan, show a clearly labeled upgrade note that never hides security controls (R-28).
- **Top bar**: org switcher, domain switcher (type-ahead), global search / command palette (Ctrl/Cmd+K), notification bell with unread count, theme toggle, help menu, user menu.
- **Domain context**: a header (domain name, status pill, mode pill WAF `block|monitor|log|off`, readiness ring) and tabs: Overview, DNS, SSL/TLS, Security, Origin, Events, Bans, Analytics, Settings. **Security** has a secondary list: WAF, Categories, Shield, Rules, Rate limits, Bots and challenge, Access lists, Access gate, API, Business flows, Exceptions, Honeypots, Outbound, Block page, Coverage, Revisions, Emergency.
- **Breadcrumbs** on every nested screen; **page title** (`<title>`) always `Screen · Domain · Org · Hack Dev Defence`.
- **Keyboard shortcuts** (discoverable with `?`): `g o` overview, `g d` domains, `g e` events, `g b` bans, `/` search, `c` copy focused value, `Esc` close.
- **Admin surface** uses a visually distinct accent (a persistent "Platform admin" banner color band) so staff never confuse it with the tenant app.

## B3. Core user journeys

Each journey lists persona, trigger, steps, success criteria, failure paths, screens, and the acceptance check that proves it. Tasks reference journeys by ID.

### J-01 Visitor discovers HDD and reads honest claims
Persona Maya. Trigger: search result or referral. Steps: (1) lands on S-001 and reads a one-sentence value statement; (2) opens S-003 and reads what is and is not protected; (3) opens a docs quickstart; (4) clicks "Create account". Success: reaches S-020 in three clicks or fewer; page weight within budget; no tracking cookies. Failure paths: JavaScript disabled still renders everything; slow connection loads text first. Check: AC-40, AC-41 (public pages), claims-lint.

### J-02 Visitor signs up and verifies email
Persona Maya. Preconditions: `signup.mode` is `open`, or the visitor holds an invite. Steps: (1) S-020 enters email, name, password; strength meter and breach check give live, kind feedback; (2) submits; always sees S-021 "Check your email" regardless of whether the address already exists; (3) receives the verification message; (4) opens link, S-022 shows a confirm button; (5) confirms (POST) and is signed in or sent to login; (6) lands in S-035 onboarding. Success: account is `active`, org created, audit event written. Failure paths: expired token shows a resend form (rate-limited); disposable email triggers the configured policy with a neutral message; password found in breach list is rejected with guidance; signup closed shows a request-invite message. Check: AC-35, AC-46.

### J-03 New user enrolls MFA
Persona any. Trigger: forced for platform roles and for orgs that require it; recommended for others. Steps: (1) S-030 shows a QR code (SVG) and manual key; (2) user scans, enters a six-digit code; (3) S-031 shows ten recovery codes once, with download/print/copy and a required "I saved these" confirmation; (4) optional passkey enrollment. Success: MFA active; recovery codes hashed at rest. Failure paths: wrong code (with drift window); lost phone (recovery code); reset by owner (org) or `hddctl` (platform). Check: AC-35.

### J-04 Returning user logs in
Steps: (1) S-023 email + password; (2) if MFA or passkey: S-024/S-026; (3) device cookie suppresses repeat prompts only where policy allows; (4) lands on the last org overview. Failure paths: generic "Email or password is incorrect"; lockout/backoff message that does not confirm existence (S-034 when locked); suspicious login triggers email notice. Check: AC-35.

### J-05 User resets a forgotten password
Steps: (1) S-027 enters email; (2) always sees "If an account exists, we sent instructions"; (3) link opens S-028 (confirm, then set new password); (4) all sessions revoked; notification email sent. Failure paths: expired or used token; rate limit. Check: AC-35, AC-46.

### J-06 User accepts a team invite
Steps: (1) invite email; (2) S-029 shows org name and role; (3) existing user signs in or new user signs up with the invited email locked; (4) membership created; owner notified. Failure: expired/revoked invite; email mismatch. Check: AC-35, AC-36.

### J-07 Owner completes the onboarding checklist
Steps: S-035 wizard: profile, org name and slug, MFA recommendation, first domain CTA, alert email, notification preferences. The checklist persists on S-040 until done or dismissed. Success: first domain started. Check: AC-37.

### J-08 Owner adds a domain using full nameserver delegation
Steps (S-042): (1) enter `example.org`; (2) HDD scans existing DNS and shows what it found; (3) choose "Use HDD nameservers (recommended)"; (4) review imported records, proxy toggles, mail records forced grey, parity report; (5) prove ownership (TXT) if required by mode; (6) configure origin and test connectivity; (7) TLS pre-issuance plan; (8) choose protection preset (starts in monitor); (9) copy the two nameservers; HDD polls delegation; (10) go-live checklist; rollback instructions shown before the NS change. Success: domain `active`, traffic proxied, readiness at least 70. Failure paths: DS record present at parent (warning with steps); unsupported record types (acknowledge); delegation not propagated (live status with next check time). Check: AC-37, AC-02, AC-03.

### J-09 Owner adds a domain using CNAME (partial) setup
Steps: as J-08 but step 3 chooses "Keep my DNS provider; point `www` to HDD". HDD gives `www CNAME <site-id>.edge.{{PLATFORM_DOMAIN}}`, the verification TXT, and an optional `_acme-challenge` CNAME for pre-issuance. HDD polls until the CNAME resolves. Success: `www` proxied; apex handled by J-10. Check: AC-37.

### J-10 Owner attaches an apex via A/ALIAS or only a subdomain
Steps: wizard explains that CNAME cannot sit at the apex; offers (a) A records to HDD IPs, (b) ALIAS/ANAME to the edge name if the provider supports it, (c) full NS delegation. Warns that A-record mode needs the operator to keep HDD IPs current (HDD announces changes with 30 days notice). Check: AC-37.

### J-11 Owner verifies ownership
Steps: HDD shows both methods (DNS TXT, HTTP file); copy buttons; verification poller with timestamps; re-verify later automatically. Failure: wrong content; CDN caching the file; wildcard TXT conflicts. Check: AC-37.

### J-12 Owner configures and tests the origin
Steps: scheme, host/IP, port, Host header, SNI name, TLS verification mode (webpki, pinned CA, pinned SPKI, or acknowledged plaintext), health-check path; "Test connection" shows DNS result, connect time, TLS result, status code, response headers (redacted), and clear remedies. SSRF guard errors are explained. Check: AC-17, AC-37.

### J-13 Owner imports existing DNS and resolves parity warnings
Steps: S-047 shows source vs HDD diff per record; unsupported types listed with explanations; owner acknowledges each; parity must be clean before the NS step. Check: AC-02.

### J-14 Owner edits DNS and toggles orange/grey
Steps: S-045 table; inline edit; S-046 type-specific editor; preview "what will resolve"; toggle proxied with consequence text; change history S-048. Failure paths: CNAME conflicts, wildcard shadowing, mail records proxied (blocked). Check: AC-03.

### J-15 Owner issues TLS and enables HSTS
Steps: S-050 shows TLS mode and status; S-051 shows certificates and renewal; enabling HSTS shows a preload caution and a staged max-age ramp. Check: AC-04.

### J-16 Owner enables protection in monitor mode, reviews, switches to block
Steps: preset "Monitor first"; after traffic, S-054 shows "would have blocked" counts with examples; owner reviews false positives via S-065/S-066, creates exceptions (S-064) if needed; "Switch to Block" dialog states consequences, shows 48-hour readiness hint, offers scheduled switch; undo within one click. Check: AC-06, AC-13.

### J-17 Owner enables the Vulnerable-Origin Shield
Steps: S-057 explains in plain language ("Assume your site has bugs"); sets strictness (Balanced or Paranoid), marks auth endpoints, enables ban-on-first-hard-hit, shows the exact payload classes blocked, offers a "Try a payload" box that calls the inspect API; shows learning-mode suggestions. Success: shield on, SQLi ban policy visible. Check: AC-38, AC-39.

### J-18 Analyst investigates an attack
Steps: S-065 live monitor; filter by category `sqli`; open S-066 for evidence (redacted), rule, policy branch; see the IP's other events; ban/unban; create exception for a false positive; link to the Ray ID. Check: AC-07, AC-08.

### J-19 Owner builds a custom rule
Steps: S-059 builder: conditions (field, operator, value), action (block, log, allow, ban, challenge), scope (path/method), expiry; "Test" runs the inspect API on samples and dry-runs against recent traffic (S-060); save creates a revision; auto-rollback explained. Check: AC-12, AC-13.

### J-20 Owner configures rate limits for login
Steps: S-061 pick preset "Login protection" (e.g., 5/min per IP per path with progressive ban), apply to detected auth endpoints; test with the burst helper. Check: AC-11.

### J-21 Owner configures alerts and webhooks
Steps: S-076 choose events (critical attack, mass ban, cert expiry, origin down), channels (email, webhook, Slack, Discord, Telegram, PagerDuty), quiet hours; S-078 create a webhook, see the signing secret once, send a test; S-079 inspect deliveries and retries. Check: AC-45.

### J-22 Blocked visitor files an appeal
Steps: S-140 shows Ray ID and a short explanation; visitor opens S-145, enters optional contact and a note, passes a light proof-of-work, submits; sees S-146. Owner is notified. Failure: abuse attempts rate-limited. Check: AC-43.

### J-23 Owner handles an appeal
Steps: S-069 inbox lists appeals with Ray ID and evidence; owner can unban, allowlist for N days, create a scoped exception, or decline with a reason. Check: AC-43.

### J-24 Owner locks down the origin
Steps: S-098 wizard: select stack; copy firewall allowlist of HDD IPs; set the secret origin header and a snippet to enforce it; verify with real probes; mark `applied`. Check: AC-18.

### J-25 Owner views Protection Readiness and fixes items
Steps: S-044 lists checks with weight, status, "why it matters", and a one-click path to fix; score animates only if reduced motion is off; footnote about meaning. Check: AC-53.

### J-26 Owner invites teammates and assigns roles
Steps: S-081/S-082/S-083; role descriptions; last-owner protection; invitation expiry. Check: AC-36.

### J-27 Developer creates an API key and uses the API
Steps: S-080 create key with scopes, expiry, IP restriction; secret shown once; example `curl`; usage graph; revoke. Check: AC-35, AC-45.

### J-28 Owner exports reports and audit logs
Steps: S-073/S-074 generate or schedule reports; S-084 filter and export CSV/JSON; hash-chain verification indicator. Check: AC-47.

### J-29 Platform admin onboards and manages tenants
Steps: S-101/S-102 view usage, plan, domains, abuse flags; suspend with reason (customer notified); delete with grace period. Check: AC-42.

### J-30 Platform admin investigates abuse and global bans
Steps: S-114 triage; S-106 global jail; S-109 never-ban management with collision warnings. Check: AC-51.

### J-31 Platform admin toggles safe mode, maintenance, checks infra
Steps: S-110/S-111 health; S-122 emergency controls with typed confirmation; S-121 maintenance banner. Check: AC-13, AC-42.

### J-32 Owner removes a domain safely
Steps: S-094: choose desired end state (return DNS to previous provider, or keep DNS-only), export zone, show exact record changes to revert, revoke certificates optional, type-to-confirm. Success: domain `removed`, no dangling HDD references. Check: AC-37.

### J-33 User exports data or deletes the account
Steps: S-090: request export (async, emailed link), request deletion (grace period, owner transfer prerequisites). Check: AC-47.

### J-34 Incident: attack spike
Steps: alert fires; S-054 shows elevated state; owner enables "Under attack" (challenge all new clients) from S-093; analyst bans campaign IPs/ASNs; after calm the mode de-escalates; incident timeline saved. Check: AC-44, AC-27.

## B4. Roles and permissions

### B4.1 Roles

| Scope | Role | Purpose |
| --- | --- | --- |
| Org | `owner` | Full control incl. billing/plan, deletion, transfer. At least one per org (last-owner protection). |
| Org | `admin` | Everything except org deletion, ownership transfer and plan changes. |
| Org | `analyst` | Read all security data; manage bans, exceptions, appeals, rules (not DNS or TLS or team). |
| Org | `viewer` | Read-only on domains, events, analytics. |
| Org | `billing` | Plan and usage only (no security data). |
| Platform | `platform_owner` | All platform permissions; may manage platform staff. Exactly the bootstrap admin initially. |
| Platform | `platform_admin` | Operate the platform; cannot manage other platform admins or change signup/legal settings without step-up. |
| Platform | `platform_support` | Read tenant metadata; read-only impersonation; no mutations. |
| Platform | `platform_auditor` | Read platform audit logs and reports only. |
| API key | scoped by permission IDs | A key never exceeds the creating user's permissions at creation time and is re-evaluated on each call. |

Platform roles and org roles are independent. Platform roles require MFA (forced), a distinct session cookie scope, short idle timeout (15 min), absolute timeout (8 h), and step-up re-authentication for mutations flagged `S`.

### B4.3 Authorization rules

1. Every handler declares its permission ID; a missing declaration fails the build (xtask check of the route table).
2. Org-scoped handlers resolve the org from the path, verify membership, then verify the permission for that role, then verify the resource's `org_id` (defense in depth on top of RLS).
3. Step-up (`S`) requires a successful re-authentication within the last 10 minutes (platform: 5 minutes); the UI prompts with S-032 and retries the action.
4. Platform staff reach tenant data only through explicit platform endpoints (`/api/v1/platform/...`) that log a reason string for every access to tenant resources; there is no "superuser bypass" of RLS in application code.
5. Impersonation sessions carry a flag that makes every non-GET request fail with `ERR-AUTH-014` at the middleware layer, and every page shows a non-dismissible banner with the remaining time.
6. API keys carry explicit permission IDs; the effective permission is the intersection of the key's scopes and the creator's current role.
7. Permission checks are unit-tested by a generated matrix test: for every route and every role, the expected status code is asserted from this table.
