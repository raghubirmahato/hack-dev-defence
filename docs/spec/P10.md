## PHASE P10: TLS and certificate management (T-0195 to T-0206) · milestone M4 · gate G10

Requirement prefix `TLM`. Goal: the control plane for certificates and TLS policy: encrypted key storage, TLS settings with a staged HSTS ramp, certificate lifecycle views, ACME order state and CA rate-limit budgeting, custom certificate upload, CAA and CT monitoring, origin TLS verification and pin management, and expiry alerting with lifetime-relative thresholds. The ACME protocol client and the live certificate resolver are built in P11/P19; here everything that can be done and tested without them is done.

Gate G10 passes when: private keys are only ever stored under envelope encryption, TLS settings changes publish snapshot revisions, the budget service is verified against the CA's published limits at build time, custom certificate validation passes the hostile-input corpus, and all screens meet the UI definition of done.

### T-0195 · Certificate data model and envelope encryption
`P10` `[DB][SEC]` · deps: T-0153 · size: L · owner: sec
**Objective.** Store certificates and keys safely from the first line of code.
**Steps.**
1. Implement `hdd-common::crypto::envelope`: AES-256-GCM with a per-secret random data key wrapped by `HDD_MASTER_KEY` (AES-256-GCM key wrap or an HKDF-derived key-encryption-key per `key_version`), 96-bit random nonces, AAD binding `table|id|column|org_id`, output format `v1|key_version|wrapped_dk|nonce|ciphertext|tag`, zeroization of plaintext buffers, and constant-time operations where applicable.
2. Implement master key loading from env/file/systemd credentials with strength validation, a key ring supporting multiple versions for rotation, and the rewrap job (`hddctl rotate-keys` in T-0526) design.
3. Write migration 0008: `certificates`, `acme_accounts`, `acme_orders`, `acme_challenges`, `ct_observations` per B5.5 with RLS where tenant-owned (ACME accounts platform-level), uniqueness and indexes (renew_after, not_after).
4. Implement repositories that decrypt only in the proxy/worker contexts through a narrow `KeyAccess` interface and never log secrets (`secrecy` types, no `Debug`).
5. Implement certificate chain storage (PEM, leaf first) with parsed metadata columns (names, issuer, serial, validity, key type, SPKI hash).
6. Implement tests for tamper detection (modifying ciphertext, AAD mismatch, wrong org), nonce uniqueness, rewrap, and downgrade attempts.
7. Document the key hierarchy and recovery with the escrowed master key.
8. Add fuzz targets for the envelope decoder.
**Deliverables.**
- envelope module, migration 0008, repositories, docs, tests
**Acceptance.**
- A1: changing any byte of ciphertext, AAD or version causes decryption failure.
- A2: a key encrypted for org A cannot be decrypted with org B context (AAD).
- A3: rewrapping to a new master key version preserves plaintext and invalidates old wrap (test).
- A4: no secret type implements `Debug` or `Display` (compile-fail tests).
- A5: the decoder never panics on arbitrary bytes (fuzz).
**Tests.**
- Unit/property/fuzz; integration with Postgres; compile-fail tests.
**Notes.** The envelope module is reused for TOTP secrets, TSIG keys, webhook secrets and provider tokens.

### T-0198 · ACME order state machine and CA rate-limit budget service
`P10` `[API][OPS][SEC]` · deps: T-0195 · size: L · owner: api
**Objective.** Orchestrate issuance safely and avoid burning CA rate limits.
**Steps.**
1. Define the order state machine (`queued → authorizing → validating → finalizing → issued | failed | canceled`) and persistence in `acme_orders` with attempt history and next attempt scheduling (exponential backoff with jitter; hard stop after N failures with an attention item).
2. Implement the **budget service**: records issuance activity per CA directory and per registered domain/account; encodes the CA's published limits (new orders, duplicate certificates per week, failed validations per hostname per hour, accounts per IP, certificates per registered domain) as configuration verified at build time against the CA's current documentation (the agent must fetch the policy through the egress client if allowlisted, or record `UNVERIFIED(capability_not_supplied)` with conservative defaults).
3. Implement admission control: before enqueuing an order, check budgets and either schedule for the next available slot or reject with `ERR-TLS-004` and the estimated retry time.
4. Implement staging vs production directory handling (`acme.directory`); production orders require the platform setting `acme_production_enabled` (set only after the operator's approval and staging success, audit logged).
5. Implement duplicate detection (same name set within the duplicate window) to reuse existing certificates instead of ordering again.
6. Implement renewal planning (renew at one third of remaining lifetime or on ARI hint; jitter within a window; skip if domain no longer active).
7. Implement metrics and alerts (`MET-hdd_acme_orders_total`).
8. Test with a local ACME test server (Pebble-class), including simulated rate-limit responses and failures.
**Deliverables.**
- order state machine, budget service, tests
**Acceptance.**
- A1: attempts beyond conservative budgets are delayed or rejected before contacting the CA (egress log assertion).
- A2: production orders are refused until the approval flag is set.
- A3: duplicate orders reuse existing certificates.
- A4: failure backoff and the hard-stop attention item work with the test clock.
- A5: renewal planning follows the one-third rule and ARI hints (test server provides ARI).
**Tests.**
- Integration with the local ACME server; unit: budget windows (property tests on sliding windows).
**Notes.** The actual protocol client (`instant-acme`) wrapper is T-0376.

### T-0199 · Custom certificate upload and validation
`P10` `[UI][API][SEC]` · deps: T-0195, T-0196 · size: L · owner: sec
**Objective.** Support customer-supplied certificates safely.
**Steps.**
1. Implement upload (PEM text or files) with strict size limits (chain 64 KB, key 16 KB) and format detection (PKCS#8, PKCS#1, SEC1; encrypted keys are refused with guidance to decrypt locally, since HDD cannot safely prompt for passphrases).
2. Validate: key parses and matches the leaf public key, chain order and completeness (build to a trusted root using the system/webpki roots; missing intermediates are reported, optional AIA fetching disabled by default since it is an egress risk), SAN/CN coverage for the site's hostnames, validity period (not expired; warn under 30 days), key strength (RSA at least 2048, EC P-256 or stronger), signature algorithms (no MD5/SHA-1), basic constraints (leaf not a CA), and extended key usage includes server auth.
3. Reject certificates for names the org has not verified, wildcards for unverified parent zones, and self-signed certificates unless the owner explicitly selects "origin-only" use (never served to visitors).
4. Store encrypted, record metadata, and activate via snapshot revision; support multiple certificates per site with selection by SAN specificity and key type (RSA/ECDSA) in the resolver (P19).
5. Implement deletion and replacement with overlap period.
6. Implement notifications for expiry and for newly uploaded certificates.
7. Run the hostile-input corpus: malformed ASN.1, huge extensions, deep chains, name constraints, duplicated SANs, IDN SANs, wildcard misuse, CN-only legacy certificates.
8. Document why HDD never auto-fetches missing intermediates by default.
**Deliverables.**
- upload handler, validators, UI, tests
**Acceptance.**
- A1: mismatched key and certificate are rejected with `ERR-TLS-001`.
- A2: certificates not covering the domain are rejected with `ERR-TLS-002`.
- A3: incomplete chains return `ERR-TLS-003` with the missing issuer name.
- A4: the hostile corpus never panics or hangs (fuzz, time limits).
- A5: private keys are zeroized after storage and never appear in logs.
**Tests.**
- Unit/table tests (60 certificates generated at runtime); fuzz on ASN.1 paths via the parsing library; integration: end-to-end upload.
**Notes.** Passphrase-protected keys are refused to avoid handling user passphrases.

### T-0200 · HSTS, redirect and minimum TLS policy engine with preload guidance
`P10` `[API][UI][SEC]` · deps: T-0196 · size: M · owner: sec
**Objective.** Prevent HSTS mistakes that lock sites out.
**Steps.**
1. Implement the staged HSTS ramp: off → 5 minutes → 1 day → 1 week → 1 month → 6 months → 1 year+, with each step requiring a minimum time at the previous step (configurable, default 24 h) and a successful check that all configured hostnames serve valid HTTPS (probe results from the data plane or the preview), preventing jumps.
2. Implement `includeSubDomains` guard: requires verification that all known subdomains in the zone (A/AAAA/CNAME names) are HTTPS-capable (best-effort check using probes through HDD for proxied names; grey names are unknown and warned).
3. Implement `preload` guard: requires max-age at least 1 year (31,536,000), includeSubDomains, valid HTTPS on the apex and www, redirect from HTTP, and a typed confirmation acknowledging that preload is hard to undo; HDD never submits to the preload list itself.
4. Implement HTTP→HTTPS redirect semantics (301/308 choice, preserve method for 308, exclude ACME and verification paths, exclude `/__hdd/health`).
5. Implement minimum TLS version enforcement flags in the snapshot.
6. Provide previews of response headers and a test button that fetches the domain's headers through HDD preview.
7. Add warnings when HSTS is enabled while the certificate lifetime is short or auto-renewal is failing.
8. Test the ramp logic with the test clock.
**Deliverables.**
- policy engine, UI, tests
**Acceptance.**
- A1: skipping ramp steps is impossible through UI or API (`ERR-TLS-006`).
- A2: preload settings require all guards and the typed confirmation.
- A3: redirect excludes ACME/verification paths (data-plane test in P18).
- A4: warnings appear when renewals are failing.
- A5: the UI explains irreversibility of preload in plain language.
**Tests.**
- Unit: ramp state machine (proptest on sequences with time); integration: validation; browser: dialogs.
**Notes.** HSTS values are server-generated; clients cannot send arbitrary header strings.

### T-0203 · Certificate expiry alerting with lifetime-relative thresholds
`P10` `[OPS][API]` · deps: T-0197, T-0198 · size: S · owner: ops
**Objective.** Alert before expiry regardless of certificate lifetime.
**Steps.**
1. Implement threshold computation relative to total validity: warn at one quarter of lifetime remaining, critical at one eighth or 7 days whichever is sooner (with minimums for very short lifetimes), failure alerts when renewal attempts fail.
2. Implement the scanning job and the platform-wide minimum days metric (`MET-hdd_cert_days_remaining`, `MET-hdd_cert_expiring`).
3. Implement notifications to owners and admins with links and the renewal diagnostics, and deduplication so repeated alerts are rate-limited (once per day per certificate, escalating severity).
4. Implement the attention items and readiness impact.
5. Implement platform-level alerts for ACME account issues and rate budget exhaustion.
6. Implement the dashboard widgets (admin S-112) hooks.
7. Add tests with the clock across lifetimes (90 days, 45 days, 6 days).
8. Document thresholds.
**Deliverables.**
- job, metrics, notifications, tests
**Acceptance.**
- A1: thresholds scale correctly for 90-day, 47-day and 6-day certificates.
- A2: duplicates are suppressed within the window.
- A3: failed renewals produce alerts with the reason.
- A4: metrics reflect the minimum remaining across active certificates.
- A5: custom certificates alert with the same logic.
**Tests.**
- Unit: threshold function (table + proptest); integration: job with the test clock.
**Notes.** CA lifetimes are shrinking, hence relative thresholds (C9.14).

6. Implement UI states in S-051 for wildcard flows with clear explanations.
7. Add tests with the local ACME server and a real local DNS server serving the TXT records.
8. Document security implications of delegating `_acme-challenge` (CNAME only for that label).
**Deliverables.**
- DNS-01 module, helper zone logic, UI states, tests
**Acceptance.**
