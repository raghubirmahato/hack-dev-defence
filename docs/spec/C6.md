## C20. Machine-learning-assisted detection: Sentinel (new in v5.2)

### C20.1 Premise and honest limits

Signatures and tokenizers catch what is known. **Sentinel** adds learned components that look for what is *unusual*, to shrink the window in which a new technique works. It is not a replacement for the deterministic engine, it is not a guarantee, it can be evaded, and it produces false positives. The deterministic engine stays authoritative (rule R-33). Product text says "machine-learning-assisted" and "advisory" and cites held-out measurements; it never says "AI-powered protection" (section 4.2).

### C20.2 Layers

| Layer | Runs | Latency | May it block alone? | Learns from | If it fails |
| --- | --- | --- | --- | --- | --- |
| A. Deterministic engine (C4, C5) | in-process | p50 under 1 ms | yes (hard signatures) | rules and fixtures | blocks per R-26 |
| B. Per-site baseline (benign profile per path template and parameter) | in-process | within the Sentinel budget | no | this site's accepted traffic | skipped, counter |
| C. Global attack-shape classifier | in-process | within the Sentinel budget | only in `block` mode and only under the corroboration rules of C20.5 | offline corpora, fixtures, synthetic mutations | skipped, counter |
| D. Session-sequence model (bounded) | in-process | within the Sentinel budget | no | this site's sessions | skipped, counter |
| E. Analyst (optional language model) | asynchronous, **never on the request path** | seconds | never | none (no training on tenant data) | disabled, nothing changes |

The Sentinel budget is 200 µs p99 per request in total. A cheap prefilter (shape novelty, entropy, view mismatch, token-class anomalies) decides whether the models run at all, so most requests pay a few microseconds.

### C20.3 Features and privacy

Features come from the three normalized views and the SQL, HTML and shell tokenizers: hashed token n-grams (2^18 buckets, used only inside the in-memory scoring and never stored), token-class sequences, character-class ratios, entropy, nesting depth, encoding-layer count, disagreement between the raw, decoded and canonical views, length z-scores per (template, parameter), keyword density, header order and set, and content-type versus body-shape agreement. Features are computed in memory and discarded; only the top contributing features, expressed as feature **classes** (never hashed content buckets), and the redacted evidence snippet (at most 512 bytes, passed through the redaction library of T-0253 with a pattern set for credentials, tokens and personal data) are stored for flagged events; sequence-model state is kept in memory and in a per-site snapshot for at most 24 hours. Opt-in sharing sends aggregate class counts only, with a minimum population of 50 distinct clients per cell and added noise, so rare values of small tenants cannot be recovered. No raw request bodies are kept for training, and no tenant data leaves the platform for model improvement unless the tenant opts in (aggregate features only, T-0598 notes).

### C20.4 Models

- **Per-site baseline.** Bounded memory per (path template, parameter): length distribution (t-digest), character-class histogram, token-class bigram counts (count-min sketch), plus a site-wide isolation forest over aggregated features. Cold start: no influence before 10,000 requests and 7 days.
- **Global attack-shape classifier.** Gradient-boosted trees or a small character-level convolutional network exported to an inference-only runtime (T-0581). Trained offline (`cargo xtask ml train`) on public corpora with licenses recorded, HDD fixtures and a synthetic mutation generator; calibrated at an operating point with a benign false-positive rate of at most 0.01% of requests. Evaluation includes **leave-one-family-out** runs (train without a whole attack family, test on it) so claims about *unseen* techniques are measured, not assumed.
- **Session-sequence model.** A bounded first-order model of path-template transitions that scores implausible sequences (for example a login page followed directly by a data-export endpoint at machine speed); advisory only.

### C20.5 Influence policy (the bounds)

| Mode | Effect | Default |
| --- | --- | --- |
| `off` | nothing runs | |
| `shadow` | scores and findings are recorded, **no effect on any response** | yes, for every new site and every new model |
| `assist` | adds a **soft score** capped at 3 points and **never enough to cross the block threshold**: the total with the deterministic score is clamped to threshold minus 1, and the request is escalated to a proof-of-work challenge on non-authentication GET requests instead; Sentinel alone can therefore never turn a deterministic `pass` into a `block` | owner opt-in |
| `block` | may block alone only when classifier probability is at least 0.99, the vector lies in a field kind where the baseline is mature, and the model's measured false-positive budget is met | owner opt-in, per site, step-up |

Rules that apply in every mode: (1) a learned component **never bans alone**: a ban always requires a deterministic signal in the same request; repeated high-confidence Sentinel findings from one identity may only raise that identity's challenge level and priority for human review, never create a ban; (2) no ban in cross-site subresource context (C6.5) and none for password fields; (3) hard-signature doctrine is unchanged; (4) a Sentinel failure, timeout or oversized input is skipped with `MET-hdd_sentinel_fallback_total` and the deterministic verdict stands; (5) every finding stores the top five features in plain language ("parameter far longer than usual for this endpoint; rare character mix") and is labeled advisory; (6) promotion from `shadow` needs at least 14 days, an owner review of the 100 highest-scoring findings, a baseline-replay false-positive rate within budget, and a measured detection uplift on the held-out novel set; (7) a spike in appeals or owner "mark as normal" labels, counted only from distinct cleared or verified clients with a capped weight per client, or drift beyond a threshold, auto-demotes the site to `shadow`, raises an alert that says the spike may itself be an attack, and requires owner confirmation to re-promote; (8) `hddctl sentinel off` is the break-glass.

### C20.6 Training and lifecycle

Reproducible pipeline with pinned data hashes, a fixed split protocol, calibration, model cards (`docs/ml/`), signed artifacts and staged rollout (shadow canary, then stable) exactly like rule packs, with rollback. Baselines are per site and never leave it. Global models update through signed packs.

### C20.7 Threat model of the learned components

| Threat | Control |
| --- | --- |
| Evasion by mimicry, padding, homoglyphs, token insertion | Deterministic layer first; adversarial augmentation in training; robustness suite with a measured evasion rate (T-0585); Sentinel is never the only control |
| Poisoning of the baseline by an attacker | Baselines learn only from requests that passed the deterministic engine and came from cleared clients or established sessions; trimmed, rate-limited, per-identity-capped updates; flagged requests are quarantined from learning |
| Model extraction by probing | Scores are never returned to clients; per-identity probing is rate limited |
| Prompt injection into the analyst | Analyst input is structured data marked untrusted; no tools, no write access, schema-validated output, human approval, dry-run before any rule exists |
| Drift and stale models | Age and drift metrics; auto-demotion; scheduled retraining |
| Resource exhaustion | Prefilter, hard CPU budget, bounded memory per template, global cap |

### C20.8 The analyst (optional language model)

Off by default (`HDD_ANALYST_MODE=off`). When enabled it summarizes campaigns, explains a blocked event in plain language, ranks the triage queue and drafts a candidate rule or exception **as a diff for a human**. It receives only redacted evidence (at most 512 bytes) and features inside a structured, labeled-untrusted field, never secrets, cookies or other tenants' data. It runs through the egress client to an allowlisted endpoint or a local model on loopback, with cost caps. Its output is validated against a schema, never applied automatically, and any proposed rule is replayed through the dry-run harness (T-0229) before an owner can approve it.

## C21. Bypass Guard: closing and verifying the direct path to the origin (new in v5.2)

### C21.1 Premise and honest limits

HDD cannot configure the origin host. What it can do is (a) remove the direct path in tunnel mode when the origin's inbound ports are closed and that closure has been verified from outside, (b) make direct requests rejected by every deployed verifier by requiring a signed per-request authentication (the signing key is shared with the verifier, so a compromised verifier host can forge), (c) **verify continuously** from outside and from inside, and (d) **refuse to call a site protected** until verification passes (rule R-34). It cannot protect an origin whose host is compromised, whose signing key is stolen, or whose neighbors share its network.

### C21.2 Ways around HDD, and the control for each

| Bypass path | Control |
| --- | --- |
| Direct connection to the origin IP | Signed origin authentication, firewall allowlist, or tunnel (C21.3); active probes from outside |
| Origin IP leaked by history (old DNS, certificate transparency, mail headers, other subdomains) | Exposure scan (T-0165, T-0407), re-IP assistant, signed authentication makes a known IP useless |
| Another hostname or virtual host on the same origin | Verifier rejects unsigned requests for every host; probe tries every name found |
| Other ports and services (alternate web ports, admin consoles, databases, SSH, FTP) | Port probe of the origin's own address from outside; firewall generator closes everything but HDD's egress set |
| IPv6 or HTTP/3 side doors | Probe covers IPv6 and UDP 443; generator covers both families |
| Grey-cloud (unproxied) DNS records that expose the origin | Hard blocker in the go-live gate and a continuous check |
| Wildcard or forgotten subdomains, staging and dev names | Dangling and unproxied-name scan; wildcard policy |
| Another proxy or CDN in front of the origin | Detected by the echo canary; warns |
| SSRF from a neighboring service to the origin's private address | Signed authentication still required; network segmentation guidance |
| Host or SNI confusion at HDD to reach another tenant or an internal route | Host and SNI consistency (T-0355), neutral 404, no default tenant |
| Spoofed forwarding headers | Stripped inbound; signature covers method, host, path and query |
| Replay of a captured signed request | Timestamp window (30 s) and nonce cache at the verifier |

### C21.3 Controls

1. **Signed origin authentication (default).** HDD adds `HDD-Origin-Auth: v1;<kid>;<unix-ts>;<nonce>;<sig>` with `sig = HMAC-SHA-256(key, canonical)` where `canonical` is newline-terminated, length-prefixed fields: version, `kid`, uppercase method, lowercase host without port, port, the raw request-target bytes as forwarded, SHA-256 of the body (or the literal `nobody`; for streamed bodies the signature covers `Content-Length` or `chunked` and states that the body is not covered), `ts`, `nonce`, `ray_id`, and the marker `via=tunnel|direct`; test vectors fix every byte. The origin must be reached over TLS or the tunnel so a signed request cannot be altered in transit. The verifier rejects unknown `kid`, timestamp skew over 30 s, replayed nonces and bad signatures, with a generic 403 that reveals nothing. Nonces are retained for at least twice the skew window; a full cache fails closed; multi-instance origins use a shared nonce store or sticky routing, and the wizard says so. Origins need a clock within 5 s (NTP); a skewed clock returns the same generic 403 and a heartbeat reason code. The verifier in signed mode **rejects the static header of T-0361**. Keys rotate with overlap. Key handling: one key per site, scoped per `kid`, shown once to a user holding `PERM-bypass.key_view`, held in HDD envelope-encrypted and in the proxy's memory only (zeroized on rotation); rotation retires the old key only after every verifier instance has acknowledged the new one, or after a rolling probe confirms every origin target accepts it. The wizard generates verifier modules or snippets for nginx, Apache, Caddy, HAProxy, Node (Express, Fastify), Python (WSGI/ASGI), PHP (`auto_prepend_file`), Java (servlet filter) and .NET middleware, each a short, reviewed, tested file. The static secret header of T-0361 remains available for simple setups, is marked weaker, and caps the lockdown state at `applied_unverified`.
2. **Mutual TLS** (T-0383) as an alternative or in addition.
3. **Tunnel mode (`hdd-tunnel`).** A small connector on the origin dials out to HDD over mutually authenticated TLS and carries the requests; the origin host closes all inbound web ports. With inbound ports closed there is no listener to connect to directly. The connector dials one configured `host:port` only (not a range), enrollment tokens are single-use, bound to the site, valid for 15 minutes and confirmed by a fingerprint shown on both sides, and origins that trust loopback peers (admin paths, `/server-status`, metrics) are flagged by the wizard because tunnel traffic arrives from the connector; verifiers use the `via=tunnel` marker rather than the peer address.
4. **Network allowlist.** Generators for nftables, iptables, ufw, and the main cloud firewalls that allow only HDD's published egress addresses (T-0405) and deny the rest. Removed addresses expire automatically after the overlap and the probe verifies the old set is closed. If HDD's egress range is shared infrastructure, co-tenants of that range can reach the origin; a firewall-only setup is therefore never eligible for `verified` without signed authentication or the tunnel.
5. **Origin-side tripwire.** The verifier counts unsigned or invalid requests and reports them to HDD in a signed heartbeat (through the tunnel or an HTTPS callback). The verifier distinguishes a **bypass attempt** (an unsigned or invalid request that was rejected: informational, aggregated by rate, never changes the state) from a **confirmed bypass** (site content served without a valid signature, or a successful direct probe: a `bypass_events` row, a critical alert and `bypass_detected`). The heartbeat is signed with its own key, separate from the origin-authentication key.
6. **Active verification** every hour (configurable) from at least two vantage points outside HDD's network (the operator's runner, an operator-configured probe, or a bring-your-own-probe token page): direct connections to the origin address on the common web ports, the configured ports and the top-100 web ports (rate-limited, each probed address and name first proven to belong to the site's owner by a DNS or HTTP challenge, resolved once and pinned, never a private, loopback, link-local or cloud-metadata range, with a per-target cost cap and every probe target written to the audit log), with and without SNI and with different `Host` values, over IPv4, IPv6 and UDP 443, plus every historic and certificate-transparency name found. Results are classified `blocked`, `site_content` (matched by the echo canary token or a content hash), `exposed_service` (any non-HDD service that answers, such as an admin console, database or default virtual host) and `inconclusive`; `site_content` and `exposed_service` both fail verification. At least one vantage is HDD-operated with rotating, unpublished addresses, owner-run probes sign their results with a per-probe key and nonce, and a probe whose results never vary is treated as suspect. Before any result counts, an **origin-address check** shows that a request to the probed address reaches the same origin as the proxied path (a unique token seen on both); otherwise the state stays `applied_unverified`.
7. **DNS hygiene.** Every hostname of a protected site is proxied, no unproxied record shares the origin address, wildcards are explicit.
8. **The gate (R-34).** See C21.4.

### C21.4 States and the go-live gate

States: `unprotected`, `lockdown_instructed`, `applied_unverified`, `verified`, `degraded`, `bypass_detected`. `protection_state()` maps the six states to the surface labels: `verified` → `protected` (shown with date and vantage count); `applied_unverified` and `lockdown_instructed` → `unverified`; `degraded` → `monitoring` (verification overdue or a vantage outage); `bypass_detected` and `unprotected` → `bypassable`. A site already in `block` mode that becomes `degraded` keeps blocking (never weaker than before) but shows `monitoring`; at `bypass_detected` it keeps blocking, raises the incident and cannot be promoted or have its protections relaxed. A risk acceptance shows `bypassable` until the state is `verified`, at which point the acceptance is cleared and the label follows the state. `degraded` begins only after 24 hours without a valid verification and never from a single outage. In the local profile `verified` means tunnel mode with a verified closed inbound plus at least one owner-attested vantage; without any vantage, `block` mode needs the typed risk acceptance. A site cannot enter `block` mode or show "protected" in any surface unless it is `verified`; the owner may override only with a typed risk acceptance, which shows "bypassable" in readiness, the dashboard and reports. In tunnel mode with a verified closed inbound (and, outside the local profile, at least two independent vantages including one HDD-operated), the state is `verified` and the surfaces say "no direct path found from N vantage points on <date>", never "cannot be bypassed". `bypass_detected` raises a critical alert, offers one-click key rotation and a tightening wizard, blocks promotion to `block` mode, and is shown on S-138 until two consecutive clean verifications; attempts alone never keep the state pinned.

### C21.5 What the guard cannot do

A stolen signing key lets an attacker forge requests until rotation; keys are stored with web-server-only permissions and rotated on suspicion. A compromised origin host is outside HDD. Services on the same host that are not HTTP are covered only by the port probe and firewall advice. Shared hosting cannot close ports and is flagged as `weak` in the wizard.

## C22. Known-vulnerability coverage and additional hardening (new in v5.2)

### C22.1 What "all well-known vulnerabilities" can honestly mean

No product can contain every vulnerability ever found. HDD instead provides (a) a **Known-Vulnerability Knowledge Base (VKB)** that tracks named CVEs (CISA KEV first, then high-EPSS and high-severity items), vulnerability classes (OWASP, CWE, CAPEC) and misconfiguration classes; (b) a **pipeline** that turns request-visible exploit shapes into tested, signed, staged rules within a stated time; (c) the **attack matrix** (C5, now ATK-001 to ATK-390) and the coverage map (E15) that show what exists, what is tested and what is not covered; and (d) **per-site relevance**, so a site running a product gets that product's rules prioritized and enabled.

### C22.2 The VKB

Entry fields: key (CVE, GHSA, OSV or class id), kind, product and version range (purl/CPE), CWE and CAPEC, severity, KEV flag, EPSS, **request-visible** (does an exploit leave a pattern in the request or response HDD can see), rule reference, status (`candidate`, `monitor`, `block`, `retired`, `not_applicable`), source and license, lab-tested date. Sources: CISA KEV, NVD, OSV, GitHub advisories, vendor advisories, Exploit-DB metadata, CWE and CAPEC, and community detection templates (for example the Nuclei templates, MIT-licensed) with each license recorded and reviewed before use. Feeds are fetched only by the worker through the egress client and verified (T-0481); unsigned community templates are pinned by commit, diff-reviewed and converted only with a human approval, because a hostile upstream change is a supply-chain risk.

### C22.3 Pipeline and service levels

Ingest, classify request-visibility, find or derive the pattern (own research, community template, rule-set patterns), convert to HDD rule format, lint (ReDoS, budget), measure false positives against the benign corpora, prove against a vulnerable container in the lab where one exists, sign, roll out in stages (1%, 10%, 100% of opted-in sites) with auto-rollback, and retire when the component is patched across the fleet and aged. **Targets (measured, not promised):** a request-visible KEV entry becomes a `candidate` within 24 hours and, where a pattern can be derived, a `monitor` rule within 72 hours. An emergency channel (two-person approval, offline signing key, `monitor` start, 24-hour expiry) pushes a signed rule to 95% of a test fleet within 10 minutes and, in production, within a measured time that is reported; `hddctl vkb apply` works offline with serial numbers and expiry. A virtual patch never marks the vulnerability resolved (R-11).

### C22.4 Matrix expansion

Four new attack groups: **AG-18** named vulnerabilities (ATK-301 to ATK-340), **AG-19** modern techniques and evasion (ATK-341 to ATK-360), **AG-20** AI-system and modern-stack exposure (ATK-361 to ATK-370), **AG-21** additional techniques from the independent review (ATK-371 to ATK-390). Rows whose action is `P`, `L` or `Q` are mitigations or posture items, not detections, and are labeled so in the coverage map. CVE-specific rows use pattern *shapes*; the exact CVE list is refreshed from the KEV catalog at build time and monthly thereafter.
