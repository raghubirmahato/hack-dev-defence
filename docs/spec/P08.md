## PHASE P08: Domain onboarding and verification (T-0153 to T-0176) · milestone M4 · gate G08

Requirement prefix `DOM`. Goal: a safe, guided flow that attaches a domain to HDD in any integration mode, with ownership proof, DNS scan and import, origin configuration under the SSRF guard, TLS planning, protection presets, pre-cutover testing helpers, activation, rollback, readiness scoring, and decommissioning. This phase builds the control plane side; actual traffic handling arrives with the walking skeleton (P11) and data plane phases (P18 to P21), but every step that can be verified without the data plane (DNS lookups, TXT/HTTP proofs, origin probes) is real here.

The ownership verification engine, DNS import, origin configuration and TLS planning tasks are the control-plane inputs the walking skeleton (P11) consumes, so they are built first and in this order.

Gate G08 passes when: AC-37 passes for all integration modes against the operator's pilot subzones (`test_hostname`, `sandbox_hostname`) and against local test zones, AC-17 (SSRF/config safety) passes for onboarding paths, and the wizard is completable with keyboard and screen reader checks recorded.

### T-0153 · Domain data model and lifecycle state machine
`P08` `[DB][API]` · deps: T-0126 · size: L · owner: api
**Objective.** Define the domain/site schema and the legal state transitions.
**Steps.**
1. Write migration 0006: `sites`, `site_hostnames`, `domain_verifications`, `domain_claims`, `dns_scans`, `delegation_checks`, `origins`, `origin_pools`, `origin_health`, `config_revisions` (initial), with RLS, indexes, uniqueness (global unique hostname constraint for active claims), and check constraints for enumerations.
2. Define the state machine: `draft → pending_verification → pending_delegation → active → paused → suspended → removing → removed`, with permitted transitions, actors (user, system, platform) and side effects; encode as a typed `DomainState` with a transition table and a single `transition()` function that writes audit events and publishes snapshot revisions.
3. Define derived flags (`serving`, `proxied_names`, `needs_attention`) computed from state and checks.
4. Define invariants: a hostname can be active in at most one org; `active` requires verified ownership; `paused` keeps DNS but passes traffic through without inspection (pass-through) or stops proxying per user choice (documented); `suspended` is a platform action serving the neutral suspended page.
5. Implement repository functions with `OrgTx` and optimistic concurrency.
6. Implement the snapshot revision hook: any transition affecting serving increments the site's `config_revision` and notifies the config bus (built in P11/P18; here it writes to an outbox table consumed later).
7. Generate state-machine documentation and a diagram from the table.
8. Add tests for illegal transitions.
**Deliverables.**
- migration, state machine module, docs
**Acceptance.**
- A1: illegal transitions are rejected by type or runtime with `ERR-DOM-005`.
- A2: two orgs cannot both activate the same hostname (unique constraint test).
- A3: every transition writes an audit event.
- A4: state documentation is generated from code and matches.
- A5: RLS isolation tests pass for all new tables.
**Tests.**
- Unit: exhaustive transition table test; integration: constraints and concurrency; proptest on random transition sequences keeping invariants.
**Notes.** The `config_revisions` outbox is read by the data plane in P11.

**Acceptance.**

### T-0156 · Existing-DNS scan job (step 2)
`P08` `[API][OPS][SEC]` · deps: T-0155, T-0009 · size: L · owner: dns
**Objective.** Discover a domain's current DNS using only lawful, rate-limited lookups through allowlisted resolvers.
**Steps.**
1. Implement the scan job in `hdd-worker` using `hickory-client` through the egress client policy (resolvers from `egress_allowlist`; at least two named public resolvers plus iterative queries to the domain's authoritative servers discovered via NS lookups, all under the egress class `dns_resolution` of section 2.1: public-unicast targets only, port 53 only), with global and per-domain rate limits (at most 10 qps per scan, 3 concurrent scans).
2. Query the parent NS delegation, apex NS, SOA, A, AAAA, CNAME, MX, TXT, SRV, CAA, HTTPS/SVCB at the apex and on a candidate name list (`www`, `mail`, `smtp`, `imap`, `pop`, `webmail`, `ftp`, `ssh`, `vpn`, `api`, `app`, `dev`, `staging`, `autodiscover`, `autoconfig`, `_dmarc`, `_domainkey` selectors discovered from TXT, `_acme-challenge`, `selector1/2._domainkey`, SRV standards), wildcard detection by querying random labels, and optional AXFR attempt only if the owner opts in (against their own NS, with TSIG options).
3. Detect provider by NS suffix and common record patterns (informational only).
4. Detect DNSSEC (DS at parent, DNSKEY at apex) and flag the DS risk early.
5. Classify results into groups (web, mail, other, unknown) and mark records proxiable vs non-proxiable with reasons.
6. Store results in `dns_scans.findings` with timestamps and resolver evidence; handle partial failures with explicit gaps.
7. Provide progress via polling or SSE to the wizard; respect cancellation.
8. Add tests using a real local authoritative server (hickory-server on loopback) serving varied zones including weird cases (wildcards, CNAME chains, large TXT).
**Deliverables.**
- scan job, findings schema, tests
**Acceptance.**
- A1: scanning never queries non-allowlisted resolvers (egress denial test).
- A2: wildcard zones are detected and flagged.
- A3: scanning a zone with 500 candidate-name misses stays within the rate limit.
- A4: DS presence is reported with the parent evidence.
- A5: results are deterministic for a fixed zone (ordering and formatting).
**Tests.**
- Integration against loopback authoritative servers with crafted zones; unit: classification tables.
- Fuzz: DNS response handling via the library boundary.
**Notes.** The scan does not send HTTP requests to the domain.
