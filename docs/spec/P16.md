## PHASE P16: Bans, jail, appeals and end-to-end proof (T-0315 to T-0332) · milestone M7 · gate G16

Requirement prefix `BAN`. Goal: turn detection into containment. Every hard detection in `block` mode (outside cross-site subresource context) bans the attacker's IP key; the ban is enforced in the proxy within 100 ms on the creating node and within 2 s everywhere, mirrored to the kernel for proxied ports, visible and reversible in the UI and API, resistant to poisoning and self-lockout, appealable by legitimate visitors, and explainable. This phase also adds platform-wide promotion, evasion defenses, collateral-damage controls and a builder-local end-to-end proof that an exploitable test origin is protected: exploit succeeds directly, fails through HDD, and the source is banned.

Design invariants (C6): bans are by IP key (IPv4 /32, IPv6 /64 by default); the hot path never awaits the database; Postgres is the durable source of truth, Redis the fast shared store, local memory the enforcement copy; unban effect ≤ 2 s; the runner IP is bannable; bans apply to proxied ports only (80/443, UDP 443) so SSH and DNS remain available; every ban stores its reason and evidence (R-24).

Gate G16 passes when: AC-08 (ban persistence and unban), AC-34 (ban-poisoning resistance), AC-22 (IP resolution) subsets, the builder-local vulnerable-origin proof, loom/shuttle concurrency tests and all P16 UI checks pass; AC-38/AC-39 full lab proofs remain scheduled for P28 with the minimal local equivalent passing now.

### T-0315 · Client IP resolution and IP keys
`P16` `[DP][SEC]` · deps: T-0208, T-0262 · size: M · owner: dp
**Objective.** Determine the true client address safely, and derive stable ban keys.
**Steps.**
1. Implement `resolve_client_ip(peer, headers, trusted_cidrs) -> ClientIp`: the TCP peer unless the peer is in the site/platform trusted proxy list (`upstream_cdn.trusted_cidrs`, `HDD_TRUSTED_PROXIES`), in which case parse `X-Forwarded-For` from right to left to the first untrusted entry, validate each entry (IP syntax, no ports or garbage), cap chain length (20), and ignore `Forwarded`/`X-Real-IP` unless the peer is trusted and the header is configured; default trusts nothing.
2. Strip inbound `X-Forwarded-*`, `Forwarded`, `X-Real-IP`, `HDD-*` headers from untrusted peers before setting HDD's own (also for h2).
3. Implement IP key derivation: IPv4 `/32`; IPv6 to configurable prefix (default `/64`, options `/56`, `/48`, `/128`), IPv4-mapped IPv6 collapsed to IPv4, zone IDs rejected, canonical text and compact binary forms.
4. Provide `ClientIp` with both the address (for display and kernel enforcement) and key (for lookups), plus `source: Peer | Xff(depth)` for audit.
5. Handle PROXY protocol (v1/v2) as an opt-in listener mode for operators behind L4 load balancers, with an allowlist of sender addresses; reject unsolicited PROXY headers otherwise.
6. Write spoofing tests: untrusted peers sending `X-Forwarded-For`, `Forwarded`, `X-Real-IP`, `HDD-Connecting-IP`; chained headers with mixed trusted/untrusted hops; IPv6 forms; malformed lists.
7. Add property tests: resolved IP is never an entry to the right of the first untrusted hop; keys are stable under textual variations.
8. Document operational guidance for CDNs and load balancers.
**Deliverables.**
- `hdd-common::clientip`, listener support for PROXY protocol, tests, docs
**Acceptance.**
- A1: spoofed headers from untrusted peers never influence the resolved IP.
- A2: with a trusted CDN peer, the right-to-left rule yields the expected client in 30 table cases.
- A3: IPv6 addresses within the same /64 map to one key; different /64s do not.
- A4: unsolicited PROXY protocol headers are rejected.
- A5: resolution is allocation-free in the common case (alloc test).
**Tests.**
- Table (80) / proptest / fuzz on header parsing / alloc test.
**Notes.** AC-22 verifies this live with spoofed headers from the runner.

### T-0316 · Ban store: local enforcement copy, Redis, Postgres and resync
`P16` `[DP][DB]` · deps: T-0315, T-0211 · size: XL · owner: dp
**Objective.** Make bans fast to check, durable, and consistent across nodes.
**Steps.**
1. Write migration for `ip_bans`, `ban_offences`, `ban_appeals` (if not yet present), and `campaign_clusters` per B5.7 with RLS (platform bans have `org_id` null and use platform-owned access paths).
2. Implement the local enforcement structure in each proxy node: three sharded maps (platform, org, site) keyed by `IpKey` with `expires_at` and a compact `BanInfo`, wrapped for lock-free reads (`ArcSwap` snapshots for bulk resync plus a sharded concurrent map for incremental updates), size cap 100,000 entries with oldest-expiry eviction that never evicts manual or platform bans, and a background reaper for expired entries.
3. Implement the **hot path check**: O(1) local lookup (platform, org, site in order) with no network I/O; a miss means not banned; Redis is not consulted on the request path.
4. Implement creation: write local immediately, then asynchronously (a) Redis (`hdd:banned_ips` zset score=expiry plus `hdd:ban:{scope}:{key}` hash with TTL), (b) publish `hdd:events:ban` with a monotonic revision, (c) enqueue the durable Postgres insert through the event pipeline with an idempotency key; failures retry with backoff and surface in metrics.
5. Implement subscribers: on `ban`/`unban` messages apply to the local structure; on a revision gap or reconnect, resync the full active set from Redis and verify against Postgres periodically (every 30 s incremental check, every 5 minutes full reconciliation) to heal divergence.
6. Implement unban: remove locally, Redis, publish, mark Postgres `released_at` with actor; ensure unban beats stale create messages (tombstones with revision ordering).
7. Implement Redis-down behavior: local bans continue to work; creation continues locally and queues Redis writes (bounded); node restarts rebuild from Postgres.
8. Add loom/shuttle tests for the concurrent structure and chaos tests (drop messages, restart nodes, partition Redis).
**Deliverables.**
- `hdd-common::banstore`, migration, tests, docs
**Acceptance.**
- A1: the hot-path check performs no I/O (verified by a test harness that panics on socket use) and costs under 200 ns p99 for 100k entries.
- A2: a ban created on node A is enforced on node B within 2 s p95 (integration with two proxy instances).
- A3: dropped pub/sub messages heal via gap resync or reconciliation.
- A4: unban wins over delayed create messages (ordering test).
- A5: eviction never removes manual or platform bans (property test).
**Tests.**
- loom/shuttle model tests; chaos integration (Redis/Postgres restarts); benchmark.
**Notes.** The store implements the "never await the DB on the hot path" rule (C2).

### T-0325 · Ban evasion defenses: campaign detector and fingerprint-linked escalation
`P16` `[DP][SEC]` · deps: T-0317, T-0306 · size: L · owner: dp
**Objective.** Defend against attackers who rotate IPs.
**Steps.**
1. Implement the campaign detector: for each (site, endpoint pattern, signature id) maintain a bounded set (HyperLogLog) of distinct IP keys producing hard or soft matches in a 10-minute window; when distinct keys ≥ N (default 20) open a `campaign_cluster` row, mark the (site, endpoint) as **elevated**, alert owners and platform, and apply the campaign policy.
2. Define campaign policies: challenge all *new* clients (no clearance cookie, no prior good sessions) on that endpoint; tighten rate limits for that endpoint; optionally block the signature entirely for new keys; auto-expire after 30 minutes of calm.
3. Implement fingerprint-linked escalation: after a hard-hit ban, remember a salted hash of (header order, selected header values, UA, accept-language) and the TLS fingerprint if available for the ban duration; new IP keys presenting the same fingerprint **and** the same attack signature are challenged first and banned on the second hit; fingerprints alone never ban.

Implement IPv6 rotation defense: when ≥ 5 distinct /64s inside the same /48 (or /56) are banned within 60 minutes, escalate to a ban of the covering prefix (/56 or /48) for a short TTL with owner notification, never above the prefix of a known ISP aggregate without review (ASN-based allowlist of broad prefixes).
5. Implement residential-proxy handling: no per-IP bans for low-evidence cases; rely on challenge and endpoint hardening.
6. Provide UI: campaign view in the security overview (active campaigns, endpoints, counts, actions, end), and events grouped into incidents.
7. Add tests simulating rotating-IP attacks (builder-local multi-source via loopback aliases/netns) and measuring detection time.
8. Document limitations.
**Deliverables.**
- campaign detector, escalation logic, UI, tests
**Acceptance.**
- A1: 30 rotating sources hitting one endpoint with the same payload shape open a campaign within the window and trigger challenge for new clients.
- A2: legitimate users with clearance cookies are unaffected during a campaign.
- A3: fingerprint-only matches never ban.
- A4: IPv6 prefix escalation respects ASN safeguards.
