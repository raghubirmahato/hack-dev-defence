## PHASE P04: Frontend foundation (T-0071 to T-0094) · milestone M2 · gate G04

Requirement prefix `FEF`. Goal: a running `hdd-web` server that serves the design system through real templates, with the security headers, asset pipeline, forms, CSRF, i18n, live-feed plumbing, charts and the complete browser test harness in place, so later phases only add screens and domain logic. Nothing here shows product data; all pages are infrastructure, the component gallery and error pages.

Gate G04 passes when: `hdd-web` starts from environment configuration, serves the gallery at `/admin/design-system` behind a placeholder-free authorization hook (loopback-only until P06), CSP has no violations, axe reports zero serious/critical on the gallery and error pages, JS/CSS budgets pass, visual baselines exist, and the frontend security suite is green.

### T-0071 · UI stack spike and ADR: askama + HTMX + vanilla islands versus Leptos SSR
`P04` `[UI][DOC]` · deps: T-0052 · size: M · owner: ui
**Objective.** Decide the interactive UI stack with evidence rather than preference, within the Rust-first constraints.
**Steps.**
1. Define evaluation criteria with weights: total shipped bytes (JS+WASM) on a representative screen, accessibility of generated markup, server-render simplicity, form handling and progressive enhancement without JS, testability with `chromiumoxide`, build time, maintenance risk (crate activity, MSRV), compile times, hot-path memory, and fit with CSP (no `unsafe-eval`, no inline script).
2. Build two minimal vertical slices of the same screen (a data table with filters, a modal confirm, a live feed list, and a form with server validation): slice A with `axum` + `askama` + HTMX + 2 islands, slice B with Leptos SSR (and islands/WASM only if required).
3. Measure: bytes over the wire, time to interactive in the harness, markup quality via axe, lines of code, build time, test ergonomics, and behavior with JavaScript disabled.
4. Evaluate CSP compatibility specifically: nonce propagation, WASM instantiation requirements (`wasm-unsafe-eval`), and Trusted Types.
5. Evaluate the maintenance risk: release cadence, breaking-change history (from the registries and changelogs, read through the egress client if allowlisted, otherwise from the repositories' tags), license, and bus-factor notes.
6. Score both options and write the ADR with the decision, the rejected alternative and why, risks, and the rollback plan (how to switch if the decision proves wrong).
7. Record the default (askama + HTMX + islands) as the baseline if the spike is inconclusive and note `DEV-V5-005` if Leptos is chosen (rust-share implications).
8. Delete the spike code or move it to `design/spikes/` (not part of the workspace build).
**Deliverables.**
- `docs/adr/00NN-ui-stack.md`, `design/spikes/ui-stack/` (non-shipping), measurement tables
**Acceptance.**
- A1: both slices are measured with the same harness and conditions; numbers are in the ADR.
- A2: JS-disabled behavior is evaluated and recorded for both.
- A3: CSP implications (including WASM) are explicit.
- A4: the ADR includes a concrete rollback plan.
- A5: the decision does not violate the JS and CSS caps of DEV-V5-002 and Part A budgets.
**Tests.**
- Spike measurement script outputs are stored with SHA-256 under `acceptance-ui/`.
- ADR review checklist: every criterion has a measured or documented value.
**Notes.** The rest of this specification assumes the default (askama + HTMX + islands); if the ADR chooses otherwise, the affected tasks are revised through `docs/UX/spec-patches.md` before use.

### T-0072 · Asset pipeline: CSS and JS bundling, SRI manifest, precompression
`P04` `[UI][OPS]` · deps: T-0032, T-0035, T-0071 · size: M · owner: ui
**Objective.** Produce the shipped assets deterministically, with integrity data and precompressed variants, without Node.
**Steps.**
1. Implement the JS bundling step in `xtask ui build`: islands are authored as ES modules under `crates/hdd-ui/js/`; the step resolves imports, concatenates per surface, and minifies with a vetted Rust minifier (ADR) or ships unminified modules if the budget allows (record the decision).
2. Verify there is no use of `eval`, `new Function`, `document.write`, or `innerHTML` with non-constant data; implement a JS lint (token-level) in `xtask ui lint` to enforce this.
3. Produce hash-named outputs (`core.<hash>.css`, `app.<hash>.js`), and the manifest `assets.json` with SRI (`sha384`) values consumed by templates for `<link>` and `<script>` tags with `integrity` and `crossorigin`.
4. Precompress assets with Brotli (level 11) and gzip (level 9) at build time, storing `.br` and `.gz` siblings; verify decompressed equality.
5. Vendor HTMX and axe-core as static files with recorded version, license and SHA-256 in `design/vendor.lock`; add a verification step that fails if a vendored file's checksum drifts.
6. Add the budgets: first-party JS at most 45 KB gzip total and 20 KB per route bundle; HTMX counted separately and reported; CSS limits from T-0035.
7. Generate the service-worker-free offline fallback page asset (S-018) as a static file.
8. Document the pipeline and the reproducibility guarantee.
**Deliverables.**
- extended `xtask ui build`, `design/vendor.lock`, `assets.json` format docs, JS lint
**Acceptance.**
- A1: building twice yields identical hashes.
- A2: templates reference assets only through the manifest (lint rejects hard-coded asset URLs).
- A3: modifying a vendored file without updating `vendor.lock` fails `xtask verify`.
- A4: budgets are reported and enforced; a synthetic oversized bundle fails.
- A5: the JS lint rejects `eval`, `new Function`, and unsafe DOM sinks in fixtures.
**Tests.**
- Unit tests for manifest generation and SRI correctness; JS lint fixture tests; determinism test.
- Integration: serve assets and verify SRI in a headless browser load (no integrity errors).
**Notes.** Node is never required in any build or test step.

### T-0075 · Security headers, CSP with nonces, Trusted Types and violation reporting

**Steps.**
1. Implement per-response nonce generation (128 random bits, base64) passed to templates for any permitted inline script (theme bootstrap only) and verified absent elsewhere.
2. Compose CSP per surface: `default-src 'none'; script-src 'self' 'nonce-…'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'; object-src 'none'; manifest-src 'self'; upgrade-insecure-requests; require-trusted-types-for 'script'; trusted-types hdd-islands; report-to hdd-csp` with the exact directives documented and tested; allow `wasm-unsafe-eval` only if the ADR chose WASM islands.
3. Set the companion headers: `Strict-Transport-Security` (2 years, includeSubDomains; preload only after operator approval), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` (no-referrer on token pages), `Permissions-Policy` denying camera, microphone, geolocation, payment, USB and others, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`, `Cross-Origin-Embedder-Policy` evaluated but not enabled unless needed, `Cache-Control: no-store` for authenticated pages and token pages.

6. Add an `xtask` check that fetches every route from a running instance and validates headers against the expected policy.
7. Document each directive and why; document how to relax in a development override that is rejected in production configuration (there is no dev mode: tests use the same policy).
8. Add the clickjacking protections test (frame-ancestors) and a CSP bypass checklist (JSONP, `base`, dangling markup).
**Deliverables.**

**Tests.**

### T-0076 · Static asset serving: caching, compression, ranges and path safety

6. Add font preload `Link` headers for the critical font and `103 Early Hints` evaluation (documented, optional).

8. Document the cache invalidation story (new build means new hashes).
**Deliverables.**
- `crates/hdd-web/src/assets.rs`, tests, docs
**Acceptance.**
- A1: requests with `..`, encoded traversal, absolute paths and null bytes never read outside the asset root.
- A2: `If-None-Match` returns 304 and `Accept-Encoding: br` returns Brotli.
- A3: unknown extensions are rejected with 404.
- A4: HTML responses are never served with `immutable`.
- A5: the asset server has no directory listing and returns identical errors for missing and forbidden files.
**Tests.**
- Unit: path canonicalization table; integration: range and conditional tests.

### T-0077 · HTMX integration policy and configuration
`P04` `[UI][SEC]` · deps: T-0072, T-0075 · size: M · owner: ui

**Steps.**

Vendor the HTMX file and set the configuration in a nonce-allowed bootstrap or `meta` tag: `allowEval=false`, `allowScriptTags=false`, `selfRequestsOnly=true`, `includeIndicatorStyles=false`, `historyCacheSize=0` (no cached snapshots of authenticated pages), `refreshOnHistoryMiss=true`, `defaultSwapStyle=outerHTML` or `innerHTML` per documented rule, `scrollIntoViewOnBoost=false`.

6. Define progressive enhancement rules: every HTMX interaction has a non-HTMX fallback (full-page form post or link) for critical flows (auth, add-domain, destructive confirms).
7. Create a lint that scans templates for forbidden attributes and missing targets.
8. Write the developer documentation with patterns for tables, filters, inline edit, polling, SSE.
**Deliverables.**
- vendored HTMX with lock entry, config bootstrap, error-handling island, template lint, docs
**Acceptance.**
- A1: injected `<script>` in an HTMX response is not executed (`allowScriptTags=false`).
- A2: cross-origin `hx-get` is refused (`selfRequestsOnly`).
- A3: after a swap, focus lands on the documented target (browser test).
- A4: critical flows work with HTMX removed (JS-disabled tests).
- A5: template lint flags `hx-on` and `hx-confirm`.
**Tests.**
- Browser tests for swap/error/network failure; JS-disabled fallback tests; lint unit tests.
**Notes.** The CSRF design is in T-0080; history cache is disabled to avoid exposing authenticated pages through back/forward cache on shared machines.

### T-0080 · CSRF protection and request-origin verification
`P04` `[SEC]` · deps: T-0075, T-0079 · size: M · owner: sec
**Objective.** Defend every state-changing request against cross-site attacks with layered checks.
**Steps.**
1. Implement signed double-submit tokens: random value stored in a `__Host-hdd_csrf` cookie (`Secure; SameSite=Strict`) and an HMAC-bound token embedded in forms/meta; the HMAC binds the session (or an anonymous pre-session identifier for pre-auth forms) to defeat token fixation.
2. Verify, for every non-safe method: token validity, `Origin` header equals the expected origin (or, if absent, `Referer` origin), and `Sec-Fetch-Site` is `same-origin` (or `none` for top-level user-initiated navigations to GET only).
3. Reject cross-site requests with `ERR-AUTH-016` without revealing which check failed; log the failing check internally with request ID.
4. Rotate the token on authentication changes and periodically; support multiple tabs.
5. Provide the HTMX integration (token meta tag read by the loader) and for API-key authenticated JSON clients skip CSRF (bearer tokens are not ambient credentials) while forbidding cookie auth on API-key routes.
6. Define the pre-auth forms (login, signup, reset) token source (anonymous pre-session cookie with short TTL).
7. Add negative tests for JSON content-type CSRF, form-encoded forgery from other origins, missing/forged `Origin`, subdomain attacker (`evil.example.com` on the same site), and method override tricks.
8. Document the design and the exceptions list (none for browser-session routes).
**Deliverables.**
- `crates/hdd-web/src/security/csrf.rs`, tests, docs
**Acceptance.**
- A1: a cross-origin form post with a valid cookie but no token is rejected.
- A2: a request with a stolen token for another session is rejected.
- A3: the subdomain-attacker test (cookie tossing) fails to bypass `__Host-` cookies.
- A4: GET routes never mutate state (route table check).
- A5: API-key routes ignore cookies entirely.
**Tests.**
- Unit: token generation/verification tables; browser test with a hostile origin page posting to the app.
- Fuzz: header parsing of Origin/Referer.
- Security regression suite named `csrf_*` listed in the capability matrix.
**Notes.** Pairs with SameSite cookies as defense in depth, not as the only control.
