## PHASE P26: Shield, escalation and DNS survivability (T-0473 to T-0480) · milestone M10 · gate G26

Requirement prefix `SHD`. Goal: implement `hdd-shield`, the host service that watches the machine, decides when an attack is large enough to need stronger measures, and carries out documented escalation steps: tightening XDP and challenges, calling provider mitigation (when contracted), failing DNS over to standby edges, and alerting the operator even when the VPS is saturated. Capacity statements remain honest.

Non-negotiables: the shield never claims volumetric protection beyond contracted and measured upstream capacity (R-10); it never bans provider ranges, `admin_cidrs` or the origin; every transition and action is audited with an undo; actions whose features are absent are recorded as `skipped(feature_absent)`, never silently ignored; de-escalation is one step at a time after a quiet period; all state machine tests use recorded counter traces through the real binary's telemetry input.

Gate G26 passes when: the state machine passes the recorded-trace test suite (including flapping, slow-ramp and saturation traces); live low-rate checks confirm alerts, heartbeat and audit events; provider activation dry-run documentation exists; manual standby-edge failover is rehearsed in the pilot with measured TTL-bound timing; AC-25 and AC-27 are PASS or UNVERIFIED with exact reasons.

### T-0473 · `hdd-shield` telemetry: collectors, signals and the recorded-trace input mode
`P26` `[DP][OPS]` · deps: T-0214, T-0467, T-0400 · size: L · owner: infra
**Objective.** Measure the right signals cheaply and make them replayable for testing.
**Steps.**
1. Create the `hdd-shield` host service with collectors reading `/proc` and `/sys` (no external agents): NIC rx/tx bytes and packets (`/sys/class/net/*/statistics`), SYN rate and half-open counts (`/proc/net/netstat`, `/proc/net/tcp*` counters), UDP receive errors (`/proc/net/snmp`), conntrack usage (`/proc/sys/net/netfilter/nf_conntrack_count`, `max`, drops), accept-queue overflows (`ListenOverflows`, `ListenDrops`), softirq CPU (`/proc/stat`, `/proc/softirqs`), memory pressure (PSI), DNS qps and drops (from `hdd-dns` metrics), proxy in-flight and shed counts, origin health and proxy-added latency p99 (from proxy metrics), and XDP drop counters by reason.
2. Normalize signals into a `SignalFrame` every second: raw values, rates over 1/10/60 s windows, and thresholds relative to the configured `platform.uplink_mbps` (if unknown, relative thresholds only with `capacity_known=false`).
3. Define the **threshold configuration** (profile `shield.thresholds`): per signal, `elevated_pct` (50%), `attack_pct` (80%), `saturated_pct` (90%), absolute guards (for example SYN/s above N), and weights; thresholds are validated, versioned and shown in S-127.
4. Implement the **recorded-trace input mode**: the same collector interface can read from a trace file (`--trace file.jsonl` with timestamped `SignalFrame`s), a replay mode with time acceleration, and the live mode; the real binary runs in all modes through its normal telemetry interface (not a mock) and writes its decisions to the same outputs.
5. Implement **trace recording**: `hdd-shield record --out trace.jsonl` captures live frames for later replay and for incident bundles (T-0477), with size caps and compression.
6. Implement sanity guards: missing or stale collectors produce `unknown` signals and the state machine treats unknowns conservatively (never de-escalates on unknown); counter wrap/reset handling; negative rates clamped with a warning; clock jump detection.
7. Export metrics for every signal and its state, plus collector health.
8. Write tests: collector parsers against captured `/proc` fixtures from several kernels, counter-wrap tests, trace record/replay equality (replaying a recording yields identical frames), time acceleration determinism, unknown-signal handling, and performance (≤ 1% CPU of one core at 1 Hz).
**Deliverables.**
- `hdd-shield` telemetry module, trace tooling, fixtures, tests
**Acceptance.**
- A1: parsers handle the fixture corpus from at least three kernel versions without error.
- A2: replaying a trace through the real binary reproduces the same frames and decisions on every run.
- A3: collector failures yield `unknown` and are visible in S-127.
- A4: counter wraps and resets never produce spikes in the rates.
- A5: collection overhead is under 1% CPU.
**Tests.**
- Parser fixtures, replay determinism, performance.
**Notes.** The recorded-trace mode is a test input to the real service, not a separate test double.

### T-0474 · Shield state machine: hysteresis, dwell times, de-escalation and manual control
`P26` `[DP][OPS]` · deps: T-0473 · size: L · owner: infra
**Objective.** Decide reliably and calmly between NORMAL, ELEVATED, ATTACK and SATURATED.
**Steps.**
1. Implement the state machine per C11.6: NORMAL (all signals below 50% of thresholds), ELEVATED (any signal above 50% for 30 s), ATTACK (any signal above 80% for 30 s), SATURATED (uplink above 90% or provider null-route signal); minimum dwell 60 s per state; transitions evaluated each second with hysteresis (enter at threshold, leave at 90% of the entry threshold).
2. Implement **de-escalation**: one step at a time after a 30-minute quiet period below the lower state's entry thresholds (configurable but never below 10 minutes); SATURATED de-escalates only when the provider signal clears and uplink is below 60% for 10 minutes; unknown signals block de-escalation.
3. Implement **manual control**: `hddctl shield status|set <state>|hold|release`, API (`POST P/shield/state|hold|release`), and UI: `hold` freezes the current state (maximum 6 h, then auto-release with notification); `set` overrides to a chosen state for a bounded duration with a reason, recorded as an `operator_override` and followed by normal evaluation after expiry.
4. Persist state in Postgres (through the control plane API when reachable) and in a local file (`/var/lib/hdd/shield-state.json`) so restarts resume the correct state and dwell clocks; document behavior when the clock changes.
5. Emit on every transition: an audit event (with the signal values at the time), a metric, an alert through notification routing and the heartbeat channel, an entry in the incident timeline, and the list of actions triggered with their outcomes.
6. Implement flapping protection (more than 4 transitions in 10 minutes enters `HOLD_SUGGESTED` with an alert) and an `attack-end` summary with duration, peak values and actions taken.
7. Write the **trace test suite** (≥ 20 recorded/synthetic traces): slow ramp, spike, sawtooth flapping, sustained plateau, saturation with provider null-route, collector dropout, false alarm (short burst), multi-signal mixed traces, long quiet recovery; each trace has an expected transition timeline with tolerance, and the suite runs the real binary in replay mode comparing audit events.
8. Write property tests: state never skips more than one level on escalation unless a SATURATED condition is met directly, never de-escalates faster than the quiet period, and transitions are deterministic for identical traces.
**Deliverables.**
- state machine, persistence, CLI/API, trace suite, tests, docs `docs/SHIELD.md`
**Acceptance.**
- A1: all traces produce the expected transition timelines within tolerance.
- A2: no trace causes de-escalation sooner than the configured quiet period.
- A3: a restart in the middle of ATTACK resumes ATTACK with correct dwell.
- A4: manual hold/override expire automatically and are audited.
- A5: flapping protection triggers on the sawtooth trace.
**Tests.**
- Trace replay, property, restart tests, manual-control tests.
**Notes.** The state table is also rendered in S-127 and in the operator runbook.

### T-0475 · Escalation actions: tighten, challenge, shed, DNS attack mode, and `skipped(feature_absent)` semantics
`P26` `[DP][OPS][SEC]` · deps: T-0474, T-0339, T-0393, T-0467 · size: L · owner: infra
**Objective.** Wire each shield state to concrete, reversible actions across the stack.
**Steps.**
1. Define the **action registry**: each action has an id, preconditions (feature present?), apply/undo functions, idempotency, a maximum duration, and an audit template. Actions: `xdp.tighten` (lower per-source rate thresholds by factor), `xdp.strict` (drop all non-essential UDP except DNS from known peers and DNS to port 53 subject to RRL), `proxy.under_attack_new_clients` (enable the under-attack challenge for new clients platform-wide using the mechanism of T-0339), `proxy.shed_nonessential` (return 503 with `Retry-After` for configured non-essential routes such as the public docs search or the app's analytics endpoints), `dns.attack_mode` (cookie-required responses with TC=1 for non-exempt sources, T-0393), `notify.page_operator`, `provider.activate` (T-0476), `dns.failover_standby` (T-0478), `cache.serve_static` (if a cache exists; otherwise skipped), `ban.escalate_ladder` (raise ban TTL ladder one rung for L7 offenders during ATTACK).
2. Map states to actions as a **configurable table** (default per C11.6): ELEVATED → `xdp.tighten`, `proxy.under_attack_new_clients`, `notify.alert`; ATTACK → `xdp.strict`, `provider.activate` (if configured), `notify.page_operator`, `proxy.shed_nonessential`, `cache.serve_static`, `dns.attack_mode`, `ban.escalate_ladder`; SATURATED → incident bundle, `dns.failover_standby` (if `standby_edge_ips` exist), keep secondary authoritative.
3. Implement the **feature-absent semantics**: before executing, check preconditions; absent features record `skipped(feature_absent: <what>)` in the audit event, metrics (`MET-hdd_shield_actions_total{action,result}`) and the incident timeline; the S-127 table shows each action's last result; unit tests assert nothing is silently dropped.
4. Implement **safety rules**: actions never target `admin_cidrs`, provider ranges or the origin; `xdp.strict` always keeps the dead-man timer armed; `proxy.under_attack_new_clients` exempts verified bots and operator CIDRs as configured; shedding lists must be explicitly configured (default empty) and cannot include the block page, challenge endpoints, appeal endpoints, ACME challenge paths or health endpoints.
5. Implement **undo on de-escalation** in reverse order with confirmation of effect (each undo verifies the previous state is restored, e.g., XDP thresholds equal the baseline), and a `shield undo-all` break-glass command.
6. Implement the integration contracts: the shield publishes its state in Redis (`hdd:shield:state`) so the proxy and DNS react within 2 s without direct coupling; a heartbeat key ensures components revert to normal if the shield is dead for more than 10 minutes (fail-safe to avoid permanent strict modes).
7. Add action budget limits: an action that fails 3 times is disabled for the incident with an alert; total actions per hour capped to avoid runaway loops.
8. Write tests: action registry unit tests, state→action table validation, trace replay with a fake effector registry that records calls plus a live integration test in the lab applying real XDP threshold changes and verifying restoration, feature-absent recording, fail-safe revert when the shield stops, and exempt-list guarantees.
**Deliverables.**
- action registry, effectors, state-action table, tests, docs
**Acceptance.**
- A1: every state transition in the trace suite produces the expected action list with results.
- A2: removing the shield process leads proxy and DNS to revert to normal behavior within 10 minutes.
- A3: absent features are recorded as `skipped(feature_absent)` and never as success.
- A4: undo restores the exact baseline values in the lab test.
- A5: safety rules prevent targeting exempt ranges (unit tests with hostile configs).
**Tests.**
- Unit, trace replay with effector recorder, lab integration.
**Notes.** The shield-driven triggers referenced from P17 (T-0339) connect here.

### T-0477 · External heartbeat, incident bundle and timeline
`P26` `[OPS][DP]` · deps: T-0474, T-0473 · size: M · owner: infra
**Objective.** Make sure the operator learns about saturation even when the VPS cannot send alerts, and capture what happened.
**Steps.**
1. Implement the **heartbeat sender**: periodic HTTPS GET/POST (default every 60 s, jittered) to `alerts.heartbeat_url_env` (an external dead-man monitor such as a cron-monitoring service or self-hosted checker the operator runs), including a compact JSON body with state, version and a monotonically increasing counter; failure handling with backoff; the heartbeat uses the egress client (allowlisted host) and never blocks the shield loop.
2. Document the **missed-heartbeat interpretation**: a missing heartbeat means saturation, outage, or host failure; the operator runbook has the checklist and escalation contacts; provide ready-made configurations for common dead-man services (documentation only).
3. Implement **incident bundles**: on entering ATTACK/SATURATED the shield starts recording a rolling trace (T-0473) plus top sources (/24 and /56 aggregates), XDP and nftables counters, DNS stats, proxy shed counts, and action results; at incident end it writes `incident-<ts>.tar.zst` containing the trace, timeline, config snapshot (secrets redacted), and a generated Markdown summary; bundles are stored with a size cap (50 MB each, 10 retained) and listed in S-127.
4. Implement the **incident timeline** model (`shield_incidents`, `shield_events`) in Postgres through the API (queued locally when the API is unreachable and flushed after) and the UI timeline in S-127 with filtering and export.
5. Implement notifications: transition alerts via routing core and direct fallback channels that do not require the VPS's saturated uplink to be healthy (queue + retry; the external heartbeat is the primary signal for total loss); email/SMS provider hooks are documented rather than implemented.
6. Implement privacy: bundles contain aggregated source prefixes only (no full IPs of visitors), and have a retention policy (30 days) with deletion tooling.
7. Add `hddctl shield bundle <incident>` to export a bundle, `verify` to check its manifest (hash list), and import for support analysis offline.
8. Write tests: heartbeat scheduling and backoff (injected clock), failure isolation (a blocked heartbeat endpoint never delays state decisions), bundle content and size caps, redaction tests (no secrets/IPs), queue-and-flush behavior when the API is down, and timeline correctness against trace replays.
**Deliverables.**
- heartbeat sender, bundle writer, timeline persistence, UI hooks, tests, runbook
**Acceptance.**
- A1: stopping the shield (or blocking its network) produces a missed-heartbeat condition detected by the fake external monitor within 3 intervals.
- A2: bundles contain the documented files and pass manifest verification.
- A3: bundle redaction scan finds no secrets or full visitor IPs.
- A4: heartbeat failures never delay state evaluation (timing test).
- A5: incidents are visible in S-127 after API recovery.
**Tests.**
- Unit, trace replay integration, redaction scans.
**Notes.** A saturated VPS cannot reliably alert; the heartbeat absence is the design answer.

### T-0478 · Edge failover (L6, Tier 1): standby edge swap of proxied answers, TTL-aware, with rehearsal
`P26` `[DP][OPS][API]` · deps: T-0475, T-0390, T-0394 · size: L · owner: dns
**Objective.** Provide a manual and shield-driven way to move proxied answers to standby edge addresses when the primary edge is lost or saturated.
**Steps.**
1. Define the **standby model**: `standby_edge_ips` (IPv4/IPv6) in the profile and platform settings, optional second provider/region metadata, readiness state (`unconfigured | configured | verified | active`), and the rule that the standby must run a compatible `hdd-proxy` with the same configuration snapshot (documented: Tier 1 provides the DNS mechanism; keeping the standby's configuration in sync is an operator-run replica using the same signed snapshot distribution or a read-only replica; Tier 4 automates).
2. Implement the **failover operation** (`hddctl dns failover to-standby|to-primary [--zones <list>|--all] [--dry-run]` and API/UI equivalents with step-up): the control plane publishes a platform-wide `edge_address_set` revision in which proxied answers resolve to the standby set instead of the primary; DNS answers change within 2 s of the revision; NOTIFY goes to secondaries (hidden_primary topology) and the operation reports the **expected propagation delay** computed from the effective TTLs (proxied TTL default 300 s, or lower when pre-lowered) and observed resolver behavior.
3. Implement **pre-failover verification**: the standby edge must pass health probes (TLS handshake with SNI for a sample of hosts, HTTP checks with the secret origin header, certificate validity, snapshot revision parity) before activation; `--force` is allowed only with an explicit typed confirmation and is audited.
4. Implement the **origin allowlist note**: the origin must allow the standby addresses (T-0405 egress IP set includes the standby set when configured), and the failover command refuses if the lockdown allowlist is `verified` without the standby set (warns and requires acknowledgment).
5. Implement **failback** with the same checks and a cool-down (default 30 minutes) to prevent oscillation; the shield-driven failover action (`dns.failover_standby`) respects a minimum interval and requires the `auto_failover_enabled` flag (off by default) in the profile; otherwise it alerts and prints the exact manual command.
6. Implement TTL strategy: guidance and tooling to pre-lower proxied TTLs (`hddctl dns ttl-prepare`), measurement of actual cache decay via the propagation checker, and honest messaging ("clients may take up to X minutes").
7. Implement the S-127 failover panel: current edge set, standby readiness, last rehearsal result, estimated propagation, and buttons with typed confirmation.
8. Write tests: dry-run output correctness, revision publication and DNS answer change in ≤ 2 s (integration), pre-verification failures blocking activation, failback cool-down, oscillation prevention, interaction with the origin lockdown note, audit completeness, and a pilot rehearsal using a second pilot address (or the same host's second IP) measured from public resolvers.
**Deliverables.**
- failover command/API/UI, verification probes, TTL tooling, tests, runbook `docs/FAILOVER.md`
**Acceptance.**
- A1: failover changes DNS answers within 2 s of the command and reports expected propagation bounded by TTL.
- A2: activation is refused when the standby fails verification unless forced with confirmation.
- A3: failback respects the cool-down.
- A4: auto-failover remains disabled unless explicitly enabled and then respects minimum intervals.
- A5: the pilot rehearsal records measured resolver convergence times (UNVERIFIED if no second address is available).
**Tests.**
- Integration, dry-run goldens, pilot rehearsal.
**Notes.** Tier 4 (T-0553) adds health-probed automatic failover.

### T-0479 · Shield and survivability acceptance: AC-25, AC-27 and end-to-end escalation drills
`P26` `[QA][LAB]` · deps: T-0475, T-0476, T-0477, T-0478, T-0470 · size: L · owner: qa
**Objective.** Prove the escalation chain works with recorded traces and live low-rate checks, and document the limits.
**Steps.**
1. Run the full trace suite against the real `hdd-shield` binary and compare audit/action timelines; include the saturation trace with provider null-route signal and standby failover action in dry-run.
2. Run a **lab escalation drill**: using the closed lab (T-0470), drive a SYN flood plus L7 flood against the lab stack and observe ELEVATED → ATTACK transitions, XDP tightening, under-attack challenge for new clients, DNS attack mode, shedding of configured routes, and legitimate-client success rates; then stop the attack and observe one-step de-escalation after the (time-accelerated) quiet period.

6. Verify the failover rehearsal results and update the readiness document with measured delays.
7. Hostile review: attempt to cause harmful escalation by an attacker (ban poisoning to trigger states, signals spoofing via proxy metrics, abuse of the manual override endpoints), and verify guards (rate limits, authz, signal sources are host-local).
8. Record AC-25 (documentation and dry-run only; capacity stays UNVERIFIED) and AC-27 (failover/escalation rehearsal) with evidence and SHA-256.
**Deliverables.**
- drill reports, evidence, updated docs, status lines
**Acceptance.**
- A1: trace suite passes with zero deviations beyond tolerance.

- A3: fail-safe revert works after killing the shield.

**Tests.**

**Notes.** All numbers are lab-only; verified-live capacity stays empty unless the provider gives measurable evidence.
