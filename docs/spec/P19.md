## PHASE P19: TLS, ACME and certificate store (data plane) (T-0375 to T-0386) · milestone M8 · gate G19

Requirement prefix `ACM`. Goal: production-grade certificate operations: encrypted certificate store with hot reload, the ACME client wrapper with HTTP-01 and DNS-01 (including wildcard and CNAME-delegated validation), the issuance and renewal scheduler with rate budgets and ARI, multi-tenant validation guards, CT monitoring wiring, default-certificate policy, HSTS/redirect behavior, OCSP decision, origin mTLS, internal PKI, TLS end-to-end tests and the production issuance gate.

Gate G19 passes when: AC-04 (staging) passes in full including DNS-01 wildcard, forced short-window renewal, CT observation, TLS policy checks via oracles; the production issuance procedure is rehearsed on staging and documented; and nothing in this phase issues production certificates without the operator's approval.

### T-0375 · Certificate store, SNI resolver cache and hot reload
`P19` `[DP][SEC]` · deps: T-0195, T-0354 · size: M · owner: dp
**Objective.** Serve certificates from an encrypted store with O(1) lookup and zero-downtime updates.
**Steps.**
1. Implement the in-memory certificate map in the snapshot: per SNI (exact and wildcard) a set of `CertifiedKey` entries (RSA/ECDSA) decrypted at snapshot load in the proxy process only, zeroized on drop/replace, never logged, never written to disk.
2. Implement decryption using the envelope module with the master key held in memory; failure to decrypt a certificate marks it unavailable with an alert while other certificates continue.
3. Implement lifecycle: new certificate versions swap atomically; old versions retained for in-flight handshakes until connections close; expired certificates are not served unless no alternative (then serve with a critical alert to avoid total outage? decision: serve expired only for `owner_only` configured fallback; default refuses and returns handshake failure to avoid hiding the problem — document the choice and make it configurable).
4. Implement certificate selection: choose the most specific SAN match, prefer ECDSA for modern clients, fall back to RSA; handle multi-certificate sites (custom upload plus ACME).
5. Implement secure memory handling: `mlock` optional via capability, no swap guidance in docs, core dump disabled for the process (systemd `LimitCORE=0`), `PR_SET_DUMPABLE=0`.
6. Implement warm-up on startup (load all certificates before accepting traffic) and a readiness gate.
7. Add metrics (certificates loaded, decryption failures, expiry gauge) and tests for swap behavior under load.
8. Document the memory model and risks.
**Deliverables.**
- store module, tests, docs
**Acceptance.**
- A1: private keys exist in plaintext only in proxy memory (disk/DB inspection tests; core dump disabled).
- A2: swap under load causes no handshake failures (load test with continuous handshakes).
- A3: decryption failure for one certificate does not affect others.
- A4: the selection logic chooses the right certificate in 40 table cases.
- A5: expired-certificate behavior follows the configured policy.
**Tests.**
- Integration/load; unit: selection tables; security: memory/disk inspection.
**Notes.** Keys never leave the proxy except via backups in encrypted form.

### T-0376 · ACME client wrapper (`instant-acme`): accounts, orders, HTTP-01, DNS-01 and ARI
`P19` `[DP][OPS][SEC]` · deps: T-0209, T-0198 · size: L · owner: dp
**Objective.** Make the ACME protocol layer robust, testable and rate-aware.
**Steps.**
1. Wrap `instant-acme` behind a trait (`AcmeClient`) to allow a local test server and future alternatives: account management (one account per directory, key encrypted), order creation, authorization fetching, challenge selection, readiness polling with timeouts, finalization (CSR with ECDSA P-256 default, RSA 2048 option), certificate download, and revocation.
2. Implement HTTP-01: publish tokens through the shared store (Redis with Postgres fallback, TTL), served by the proxy on port 80 at `/.well-known/acme-challenge/{token}` for any hostname in an active order, with strict token format validation and no path traversal.
3. Implement DNS-01: create `_acme-challenge` TXT records through the DNS API for `full_ns` zones and the acme helper zone for CNAME-delegated names, wait for local authoritative availability plus optional external verification via allowlisted resolvers before notifying the CA, and clean up after validation (T-0204).
4. Implement ARI (renewal info) client if supported by the CA directory (feature detection), returning suggested renewal windows to the scheduler.
5. Implement error mapping from ACME problem documents (`rateLimited`, `unauthorized`, `caa`, `dns`, `connection`, `tls`, `serverInternal`) to our error classes and user messages (T-0197).
6. Implement challenge failure handling with retry policy and avoidance of failed-validation rate limits (budget service).
7. Test against a local ACME server (Pebble-class) for all flows, and the real staging directory when allowed.
8. Document operational procedures.
**Deliverables.**
- ACME wrapper, tests, docs
**Acceptance.**
- A1: HTTP-01, DNS-01, wildcard and revocation flows pass against the local ACME server.
- A2: token endpoints reject invalid tokens and traversal attempts.
- A3: ARI hints are consumed when the CA provides them.
- A4: errors are classified and surfaced with remedies.
- A5: no secrets appear in logs (scanner).
**Tests.**
- Integration (local ACME and staging); fuzz token validation; scanner tests.
**Notes.** Production directory use requires the approval flag (T-0198).

### T-0377 · Issuance and renewal scheduler with jitter and alerts
`P19` `[OPS][API]` · deps: T-0376, T-0203 · size: M · owner: ops
**Objective.** Renew certificates reliably and early, without thundering herds.
**Steps.**
1. Implement the scheduler job in `hdd-worker`: scans certificates every 15 minutes, plans renewal at one third of remaining lifetime (or ARI window start), applies jitter (up to ±10% of the remaining window) and spreads orders across the budget windows.
2. Implement renewal for domain state changes (skip when paused/removed; pause renewals when ownership verification fails, with alerts), custom certificates (no automatic renewal, only alerts), wildcard certificates (DNS-01 path).
3. Implement failure policy: retry with exponential backoff and alternative challenge type when available (HTTP-01 fallback from DNS-01 where safe), alert tiers (first failure warning, third failure critical), and escalation when remaining lifetime falls below one quarter (alert) or one eighth (critical).
4. Implement forced short-window renewal for staging tests (`renew_after` override via test-only API flag disabled in production profile).
5. Implement leader election for the scheduler (Postgres advisory lock) so multiple workers do not double-order.
6. Implement observability (orders, successes, failures, time to renew) and a calendar view of upcoming renewals in the admin panel (S-112).
7. Test with the test clock, local ACME server and failure injection.
8. Document the algorithm and parameters.
**Deliverables.**
- scheduler, leader election, tests
**Acceptance.**
- A1: renewals occur at the planned time ±jitter with the test clock across 90-day, 47-day and 6-day lifetimes.
- A2: concurrent workers never double-order (advisory lock test).
- A3: failures escalate alerts per tier.
- A4: forced short-window renewal works on staging.
- A5: removed or paused domains do not renew.
**Tests.**
- Integration with test clock; chaos with multiple workers.
**Notes.** Renewal planning logic lives in T-0198; this task is the executor.

### T-0378 · Multi-tenant domain validation guards for issuance
`P19` `[SEC][API]` · deps: T-0376, T-0160 · size: M · owner: sec
**Objective.** Ensure certificates are only requested for names the org controls and the platform may serve.
**Steps.**
1. Implement pre-order guards: every name must belong to an active or pending site of the requesting org with verified ownership, resolve (for HTTP-01) to HDD edge addresses at order time (or have the CNAME/NS for DNS-01), not be reserved/denied, and pass CAA pre-check (including parent CAA).
2. Implement wildcard guards: wildcard issuance only for apex zones the org verified, DNS-01 only, no wildcards for public suffixes.
3. Implement abuse limits: orders per org per day (plan), names per certificate (max 100), and a global platform cap aligned with CA limits; refuse suspicious patterns (many names from newly created orgs).
4. Implement ownership re-check at issuance and renewal time (a lapsed verification blocks renewal).
5. Implement cross-tenant isolation tests (an org cannot request certificates for another org's active domain; dispute flows respected).
6. Implement audit events for each issuance decision with reasons.
7. Implement the CAA pre-check caching (1 hour) with bounded cost.
8. Test with hostile scenarios (claiming someone else's domain, dangling DNS).
**Deliverables.**
- guards, tests
**Acceptance.**
- A1: cross-tenant order attempts are refused with audit events.
- A2: lapsed ownership blocks issuance and renewal.
- A3: CAA that forbids the CA blocks orders before contacting the CA (egress log assertion).
- A4: wildcard rules are enforced.
- A5: abuse limits apply and are visible to admins.
**Tests.**
- Integration scenario tests; security tests for squatting.
**Notes.** ATK-290.

### T-0380 · Default certificate policy and `unrecognized_name` behavior

### T-0382 · OCSP stapling decision and certificate status practices
`P19` `[DOC][SEC]` · deps: T-0376 · size: S · owner: sec
**Objective.** Decide on OCSP stapling based on current CA behavior, not assumption.
**Steps.**
1. At build time, inspect the configured CA(s): whether their certificates still include OCSP responder URLs/Must-Staple, and whether the CA still operates OCSP responders (use the egress client to read published CA policy documents if allowlisted; otherwise record `UNVERIFIED(capability_not_supplied)`).
2. Decide (ADR): implement stapling only if CA certificates in use contain OCSP URLs and the responders are available; otherwise document that stapling is not implemented and certificate revocation checking relies on short-lived certificates and CRL/CRLite client behavior.
3. If implementing: fetch/cached OCSP responses with validation (signature, nextUpdate, nonce policy), staple via rustls API if supported, refresh at half-validity, and fall back safely when unavailable; privacy and failure considerations documented.
4. If not: ensure no code paths assume stapling and the docs/UI avoid claiming OCSP features.
5. Record the decision in the TLS posture docs and S-003 limits (if any).
6. Add tests proportional to the decision.
7. Re-evaluate annually (task in the docs maintenance list).
8. Update claims-lint dictionary if needed.
**Deliverables.**
- ADR, docs, optional implementation
**Acceptance.**
- A1: the ADR records CA facts with dates and sources (or UNVERIFIED).
- A2: if not implemented, docs explicitly state it.
- A3: no UI/doc claims contradict the decision.
- A4: if implemented, stapling is validated by oracle output.
- A5: re-evaluation reminder exists.
**Tests.**
- Doc consistency checks; if implemented, integration tests.
**Notes.** v4.1: do not build OCSP stapling unless the CA still supports it.

Implement owner UX in the lockdown wizard (T-0406): enable mTLS, download the issuing CA PEM, snippets for nginx (`ssl_client_certificate`, `ssl_verify_client on`), Apache (`SSLVerifyClient require`), HAProxy/Caddy equivalents, and a verification probe (HDD connects with and without cert and compares origin behavior).

5. Implement revocation (rotate on suspected compromise) and CRL not required (short life + rotation).
6. Test with local origins requiring client certificates.
7. Document security properties (stronger than header secrets; origin config required).
8. Ensure private keys never leave the platform except to the proxy memory.
**Deliverables.**
- mTLS support, UI integration hooks, tests, docs
**Acceptance.**

- A3: private keys never appear in API responses or logs.

### T-0384 · Internal PKI and mTLS between platform services (`hddctl pki`)
`P19` `[OPS][SEC]` · deps: T-0212 · size: M · owner: ops
**Objective.** Authenticate and encrypt internal service communication.
**Steps.**
1. Implement `hddctl pki init|issue|rotate|status`: create an offline-capable root CA (ECDSA P-256, 10-year, key encrypted with a passphrase and stored separately) and an online intermediate (1-year) for issuing service certificates (90 days) with SANs for service names; secure file permissions (0600) and ownership.
2. Implement service integration: proxy, DNS, API, web, worker, fw-agent, shield use mTLS (or Unix sockets on a single host) for control-plane communication; Postgres and Redis use TLS with verify-full when networked; configuration defaults prefer Unix sockets on single-host deployments.
3. Implement automatic rotation (renewal at one third of lifetime) with reload hooks (SIGHUP or socket reload) and rotation tests.
4. Implement trust distribution (CA bundle files) and strict verification everywhere (no `danger_accept_invalid_certs` anywhere; lint).
5. Implement revocation by short lifetimes and `hddctl pki revoke` marking certificates denied in an allow-list checked by services (serial denylist).
6. Implement audit events for PKI operations and backup instructions for the root CA (offline, documented).
7. Test cross-service connectivity under rotation and failure scenarios.
8. Document the PKI model and recovery.
**Deliverables.**
- `hddctl pki`, integration, docs, tests
**Acceptance.**
- A1: services refuse connections with certificates from other CAs (test).
- A2: rotation does not interrupt service (continuous requests during rotation).
- A3: a lint prevents disabling certificate verification in code.
- A4: root CA key material is never present on the VPS in normal operation (docs + preflight check).
- A5: PKI state can be restored from backup in a drill.
**Tests.**
- Integration; lint; drill.
**Notes.** The internal PKI never issues customer-facing certificates (R rcgen policy).
