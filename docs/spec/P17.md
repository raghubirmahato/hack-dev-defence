## PHASE P17: Rate limits, bots, challenge and reputation (T-0333 to T-0352) · milestone M7 · gate G17

Requirement prefix `BOT`. Goal: behavioral defenses that work even when no signature matches: sliding-window rate limiting with Redis and a local fallback, per-path and auth-endpoint limits, automatic bans for violators, slow-attack mitigation, the proof-of-work challenge and clearance system, under-attack mode, bot scoring, verified bots, TLS fingerprint spike, credential-stuffing and password-spraying detection, form-abuse defenses, local reputation and external lists, GeoIP/ASN enrichment, feed ingestion, adaptive thresholds and anti-scraping. No third-party CAPTCHA, no tracking, no cognitive puzzles.

Principles: challenge is preferred over ban for ambiguous evidence; bans require hard evidence or repeated violations; shared-address risk is considered (P16); every action is explainable with metrics and events; defaults are conservative and tuned by measurement on the benign traffic corpora and by the operator.

Gate G17 passes when: AC-11 (rate limiting), AC-44 (challenge and bots), credential-stuffing lab tests, and AC-48 (scanner/bot detection) subsets pass; challenge pass rates and solve times meet targets on a reference device matrix; false-positive tests on benign traffic replays show zero blocks and bounded challenge rates; and all UI screens meet the UI definition of done.

### T-0333 · Rate limiter core: Redis sliding window with local fallback
`P17` `[DP][SEC]` · deps: T-0316, T-0261 · size: L · owner: dp
**Objective.** Provide accurate, fast, shared rate limiting that keeps working when Redis does not.
**Steps.**
1. Decide key structure and algorithm in an ADR: sliding window log vs sliding window counter vs GCRA. Default for ordinary limits: **sliding window counter with two sub-windows** (documented error bound: the estimate can differ from the exact count by at most the weight of the previous window's tail, which is at most one limit per boundary; tests measure it). **Authentication endpoints and ban-triggering limits use an exact algorithm** (sliding window log capped at the limit, or GCRA) so their counts are never approximate. Redis Lua scripts give atomicity with keys `hdd:rl:{site}:{scope}:{key}`; scopes: `ip`, `ip_path`, `session`, `asn`, `fingerprint`, `api_key`, `global_ip`.
2. Implement the Lua script returning (allowed, remaining, reset_ms, violation_count) in a single round trip with `EVALSHA`, script loading on startup and recovery from `NOSCRIPT`, pipelining multiple scopes per request (cap 4 scopes) to keep p99 under 1 ms in-datacenter.
3. Implement the local fallback with `governor`-style in-memory limiters (sharded, bounded memory with TTL eviction) used when Redis is unreachable (circuit breaker with half-open probes), logging the degraded mode and exposing `MET-hdd_rate_limiter_fallback_total`.
4. Implement limit definitions in the snapshot: default (60 requests / 10 s per IP per site), per-rule overrides (T-0334), allowlist bypass (T-0318), verified bot exemptions, challenge clearance modifiers (cleared clients get 2x limits).
5. Implement the stage 9 pipeline integration (after jail, before body acquisition): compute keys, call limiter asynchronously with a 5 ms timeout; on timeout use local fallback decision (fail-open for ordinary limits but fail-closed for auth endpoints under Paranoid).
6. Implement response headers (`RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`, `Retry-After`) for 429 responses only (avoid leaking limits to attackers on normal responses unless the owner enables).
7. Add benchmarks (limiter overhead) and chaos tests (Redis kill, latency injection).
8. Document semantics, accuracy bounds and memory use.
**Deliverables.**
- `hdd-proxy::ratelimit`, Lua scripts, ADR, tests, benches
**Acceptance.**
- A1: a burst of 100 requests with limit 60/10 s yields 60 allowed (±5% for the counter algorithm, exactly 60 for the exact algorithm used on auth endpoints) and the rest 429, measured against a reference implementation.
- A2: Redis outage switches to local limiting within 100 ms and recovers automatically.
- A3: limiter overhead p99 under 1 ms with Redis and 5 µs local.
- A4: memory of the local limiter is bounded (cap and eviction tested).
- A5: auth endpoints fail closed under Paranoid when both limiters are unavailable.
**Tests.**
- Integration with real Redis; chaos; proptest of window arithmetic; benchmark.
**Notes.** Counters are never written to Postgres on the hot path.

### T-0336 · Slow-attack mitigation at application layer
`P17` `[DP][SEC]` · deps: T-0208 · size: M · owner: dp
**Objective.** Protect against Slowloris, slow POST (RUDY) and slow-read attacks beyond protocol timeouts.
**Steps.**
1. Implement header-read timeout (10 s) enforcement with per-IP concurrency of half-open connections (default 30 per IP, 10,000 per node) and drop policy for stragglers.
2. Implement minimum body throughput enforcement: after the first 5 s, require a sustained minimum rate (default 100 bytes/s measured over 10 s windows) for request bodies; exceeding violations closes the connection and counts toward a `slow_attack` intent; allow exceptions for declared upload endpoints (lower minimums with total time caps).
3. Implement slow-read protection: write timeouts and bounded response buffering per connection; connections that do not read within 30 s are closed; h2 flow-control window checks.
4. Implement per-IP/connection caps with a fairness scheduler so slow clients cannot starve others (bounded accept queue, shed policy documented).
5. Implement metrics (`MET-hdd_proxy_shed_total{reason}`), events (aggregated), and ban policy hooks (repeat offenders get rate-limit bans).
6. Test with a controllable slow client generator in the `protocol-abuse` profile against the sandbox hostname and builder-local stacks (5 connections, capped).
7. Validate that legitimate slow mobile clients on weak networks are not cut off (lower bounds, grace).
8. Document tuning.
**Deliverables.**
- timeouts and throughput enforcement, tests
**Acceptance.**
- A1: Slowloris-style header dribbling is cut off at 10 s and counted.
- A2: RUDY-style slow bodies are closed after the grace period at the default minimum rate.
- A3: slow-read connections are closed after 30 s.
- A4: 5 slow connections cannot degrade fast clients (latency test).
- A5: legitimate clients at 5 KB/s uploading small forms succeed.
**Tests.**
- Raw-socket attack generators (builder-local and sandbox profile); fairness tests.
**Notes.** Raw protocol tests (AC-14) cover HTTP/2-specific attacks in P18.

### T-0337 · Challenge engine: proof-of-work tokens, clearance cookies and replay protection
`P17` `[DP][SEC]` · deps: T-0108, T-0333 · size: L · owner: sec
**Objective.** Implement the data-plane challenge from C7.2.
**Steps.**
1. Write the ADR for challenge cryptography (HMAC-SHA-256 signing, nonce store, difficulty semantics, key rotation with overlap) and calibrate difficulty: build a device benchmark page and measure solve times on desktop, mid-range phone and low-end phone (via browser harness CPU throttling); define difficulty tiers (baseline 14 bits, elevated 18, suspected automation 20 to 22) with a cap such that the median mid-range phone solves within 3 s.
2. Implement endpoints on customer domains: `GET /__hdd/challenge` (serves S-141 for interstitial display), `POST /__hdd/challenge/verify` (verifies token and solution), and the transparent interstitial flow: a challenged request receives a 403/429-like interstitial (status 403 with `HDD-Challenge: 1`? choose 403 with the challenge page; for XHR/fetch expectations an `application/json` variant with `challenge_url`), then after verification redirects (303) to the original URL (validated same-origin, preserving method only for GET/HEAD; non-GET requests ask the user to retry the action).
3. Implement token issuance (bound to site, route class, IP bucket, UA hash, expiry 60 s, one-time nonce in Redis with local fallback) and verification (constant-time compare, replay prevention, difficulty check, clock skew tolerance).
4. Implement the **clearance cookie** `__Host-hdd_cl` (Secure, HttpOnly, SameSite=Lax, Path=/): payload `{v, site_id, ip_bucket, ua_hash, exp, level}` with HMAC; validity default 30 minutes (5 min to 24 h per site setting); cookie does not bypass inspection, bans or rate limiter (it modifies challenge decisions and grants 2x rate limits).
5. Implement IP bucket tolerance (IPv4 /24, IPv6 /56) for mobile networks and fail-safe when UA changes (re-challenge).
6. Implement abuse resistance: limit challenge issuance per key (10 per minute), cap outstanding nonces per key, protect verify endpoint against brute force, and ensure the challenge endpoints cannot be used as an oracle for site existence (neutral on unknown hosts).
7. Implement metrics (`MET-hdd_challenge_issued_total`, `solved`, `failed`, solve-time histogram) and events.
8. Test replay, cross-site token reuse, tampering, expired tokens, UA/IP changes, and key rotation overlap.
**Deliverables.**
- `hdd-challenge` data-plane module, endpoints, ADR, tests, calibration report
**Acceptance.**
- A1: tokens cannot be replayed, transferred across sites or IP buckets, or used after expiry (test suite of 30 cases).
- A2: median solve time on the reference mid-range phone profile ≤ 3 s at baseline difficulty (CDP throttling profile recorded).
- A3: clearance does not bypass inspection or bans (tests).
- A4: key rotation with overlap does not invalidate valid in-flight challenges.
- A5: verify endpoint brute force is rate limited.
**Tests.**
- Unit/integration; browser tests with throttled CPU; fuzz on token parsing.
**Notes.** Accessibility: automatic solve, no puzzle (WCAG 3.3.8).

### T-0342 · TLS fingerprint spike (JA3/JA4) and ADR
`P17` `[DP][SEC]` · deps: T-0208 · size: L · owner: dp
**Objective.** Decide whether and how to capture TLS ClientHello fingerprints for bot detection.
**Steps.**
1. Spike `tls-parser` (or equivalent) to peek the ClientHello from the TCP stream before handing it to rustls: design a peeking acceptor that buffers the first TLS record (bounded 16 KB), parses cipher suites, extensions, curves, point formats, ALPN, SNI, supported versions, signature algorithms, then replays the buffered bytes into rustls.
2. Compute JA3 (MD5 of fields) and JA4-style fingerprints (sorted, truncated hashes, more stable against extension randomization) using our own implementation (document formats and license considerations; no copying of third-party code), store as short hashes.
3. Measure overhead (latency and CPU), robustness against malformed ClientHellos (fuzz), TLS 1.3 ECH/encrypted ClientHello considerations (fingerprint limited), and compatibility with session resumption and early data.
4. Evaluate usefulness: collect fingerprints from the browser harness (Chromium, Firefox, WebKit versions), common HTTP libraries (curl, Python requests, Go, Java) and scanners (sqlmap via Python, nikto), measuring separability; document the limits (Chromium extension randomization, spoofing by uTLS).
5. Decide the integration: fingerprints as one bot-score feature and as a ban-evasion linking signal (T-0325), never a sole blocking basis; store only hashes (no raw ClientHello).
6. Write the ADR (accept/defer), including privacy analysis (fingerprints as quasi-identifiers; retention limits).
7. If accepted, implement the peeking acceptor behind a feature flag and wire into bot scoring; if deferred, record the effort estimate and defer to P32 with reasons (R-08 spike-first).
8. Add fuzz targets and perf benchmarks.
**Deliverables.**
- spike code (or implementation), ADR, evaluation report
**Acceptance.**
- A1: the ADR states a decision with measurements.
- A2: if implemented, the acceptor never loses or reorders bytes (differential test vs direct rustls handshake) and passes fuzzing.
- A3: overhead under 100 µs per new connection (measured).
- A4: separability results are documented with honest caveats.
- A5: only hashes are stored.
**Tests.**
- Fuzz; differential handshake tests; benchmark.
**Notes.** HTTP/2 SETTINGS fingerprinting (Tier 3) is deferred to P32.

### T-0343 · Credential-stuffing and brute-force detector
`P17` `[DP][SEC]` · deps: T-0334, T-0274, T-0340 · size: L · owner: sec
**Objective.** Detect and slow account-takeover attacks against the protected site's login.
**Steps.**
1. Implement username observation on declared auth endpoints: extract the username/email field (by field-kind inference and declared field names) and compute `HMAC(site_key, normalized_username)` immediately; never store or log the plaintext username; keys per site rotate on demand.
2. Track per client key: distinct username HMACs attempted in sliding 10-minute windows (HyperLogLog), failure counts, and attempt rate; thresholds: > 5 distinct usernames with failures → challenge, > 15 → ban (`credential_stuffing`), > 30 attempts/min → rate action.
3. Track per username HMAC across IPs: failures in 10 minutes from ≥ 3 distinct IP keys (distributed brute force) → step-up challenge for logins to that username and an owner alert; HDD cannot lock the origin's account but can challenge and slow attempts.
4. Implement response-pattern learning (success-like vs failure-like) per endpoint (shared with T-0274) with owner correction and confidence; when unknown, rely on request volume only.
5. Detect password spraying: one client key or small key set trying many usernames with few attempts each, same password hint (cannot see passwords, so approximate with identical request body length/shape hashes) → challenge.
6. Integrate with breached-credential signals when the origin is HDD itself (platform dogfood): use the results of the app's own breach checker; for tenants this is not available.
7. Implement dashboards and events: `credential_stuffing` incidents with counts of distinct usernames (HMAC counts only), top sources, success-like outcomes after attack (critical alert when a spray is followed by many success-like responses).
8. Test with lab-style generators (10,000 synthetic usernames, distributed sources) and benign login traffic (shared offices, password managers retries).
**Deliverables.**
- detector, learning, events, tests
**Acceptance.**
- A1: stuffing from one IP with 100 usernames is challenged within 6 usernames and banned by 16.
- A2: distributed attack on one username triggers step-up for that username and an alert.
- A3: no plaintext usernames are stored or logged (inspection test).
- A4: benign shared-office logins (20 users, 5 failures each) do not ban.
- A5: success-like spikes after sprays create a critical alert.
**Tests.**
- Simulation (builder-local multi-source); privacy inspection; benign replay.
**Notes.** ATK-157 to ATK-160, ATK-285.
