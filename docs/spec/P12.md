## PHASE P12: Security control center (T-0221 to T-0238) · milestone M6 · gate G12

Requirement prefix `SEC`. Goal: every per-domain security control is a first-class, guided, auditable, reversible screen backed by a validated policy document: overview, WAF mode and thresholds, attack categories, the Vulnerable-Origin Shield, declared auth endpoints, exceptions, rules and the rule builder, dry-run, rate limits, bots and challenge, access lists, honeypots, outbound protection settings, block page customization, configuration revisions, and emergency controls. The detection engines arrive in P13 to P17; this phase delivers the policy schema, compile path, validation, previews and UI so the engines read real configuration, and so users can already review and tune settings in monitor mode as soon as the engines land.

**Ordering note.** Within this phase T-0237 (policy schema and backend) is executed first; the UI tasks list it as a dependency even though it is numbered last in the phase (the numbers keep cross-references stable).

Gate G12 passes when: every policy change is validated, versioned, diffable, and rollbackable; self-lockout guards work for access lists, rules and mode changes; all screens meet the UI definition of done; and the policy snapshot reaches the proxy within 2 s.

### T-0228 · Rule builder (S-059): server-side validation, sentence preview, sample tester
`P12` `[UI][API][SEC]` · deps: T-0227, T-0049, T-0248 · size: XL · owner: api
**Objective.** Let users author rules safely with immediate, precise feedback.
**Steps.**
1. Implement the `Condition` schema (versioned) and server validation endpoint `POST D/security/rules/validate` returning diagnostics (position, code, message key, suggestion) for each condition: operator/field compatibility, value syntax (CIDR, country codes need GeoIP, ASN numbers), regex subset validation (linear-time engine only; reject lookaround/backreferences; limits: pattern length 512, compiled size cap, complexity heuristics), list sizes (max 1,000 values), and total rule size.
2. Implement the sentence generator (human-readable preview) in all shipped locales using Fluent with parameters, and tests ensuring the sentence is faithful to the structure.
3. Implement the sample tester `POST D/security/rules/test`: accepts a sample request (URL, method, headers, body snippet up to 4 KB) or a Ray ID of a past event, runs the rule (and optionally the full inspect pipeline) in dry-run, and explains which condition matched or failed.
4. Implement self-lockout analysis: evaluate the rule against the caller's recent requests (their own IP/session in the last hour of events if available) and against their current request context; warn or block when the rule would deny the user's own traffic.
5. Implement safe defaults: new `allow`/`bypass` rules require an expiry and a narrow scope; `ban` rules require a confirmation and cap TTL; rules affecting all paths with `block` require typed confirmation.
6. Implement save with revision note, audit event and optional "start in log mode first" toggle (recommended).
7. Implement regex safety: compile with a time/size budget in an isolated task, reject slow patterns found by a pathological-input benchmark (heuristic), and never run user regex in the control plane against untrusted large inputs without limits.
8. Add tests with a corpus of 200 valid and invalid rules and hostile regexes.
**Deliverables.**
- validation service, tester, UI wiring, tests
**Acceptance.**
- A1: unsupported regex constructs return `ERR-WAF-001` with the exact construct and position.
- A2: oversized or too-complex rules return `ERR-WAF-002`.
- A3: the sentence preview is faithful for 50 reference rules in two locales.
- A4: the self-lockout analysis blocks saving a rule that denies the caller's own recent traffic without acknowledgment.
- A5: hostile regexes never hang the control plane (time-limited test).
**Tests.**
- Unit/table tests (200 rules); fuzz target on the rule validator; browser flows; security tests for ReDoS inputs.
**Notes.** Evaluation semantics live in `hdd-waf-core` (T-0248); the control plane reuses the same crate.

7. Add tests with synthetic-but-real-pipeline samples (generated through the proxy test harness).

**Deliverables.**

**Acceptance.**

- A2: dry-run results are reproducible for a fixed sample.
- A3: the traffic sample contains no request bodies or parameter values (schema test).
- A4: activation of a blocking rule requires a dry-run less than 15 minutes old.
- A5: runs are bounded in time and memory.
**Tests.**
- Unit: evaluation over samples; integration: sample ingestion and replay; privacy schema test.
**Notes.** The sample is also the base for the automatic-rollback probes (T-0371).
