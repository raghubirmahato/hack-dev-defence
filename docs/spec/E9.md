### E9.2 What v5 adds

- **A product, not only an engine:** UX research, a dark-first design system with verified WCAG 2.2 AA tokens, 143 designed screens, a public site, signup and login with MFA and passkeys, organizations and roles, a customer dashboard, an admin panel, analytics, reports, notifications, a public API and SDK (P01 to P08, P22 to P24).
- **Multi-tenancy and SaaS safety:** `deployment_mode`, ownership verification, five integration modes, per-tenant fairness, row-level security with a BOLA suite, SSRF-safe egress, abuse tooling (P06, P08, P21, P22).
- **Domain onboarding and full domain controls:** an eight-step wizard, DNS import and parity, record editor, TLS and certificate management, origin configuration, lockdown wizard, readiness score, decommission (P08 to P10, P20, P21).
- **The SQL-injection doctrine and the vulnerable-origin shield:** a three-view normalizer, SQL tokenizer with fingerprints, hard families H1 to H8, field-kind policy, ban-on-first-hard-hit with a progressive ladder, ban-poisoning defenses, auth-endpoint strict mode, outbound leak control, virtual patches and the Vuln-Lab proof (C3, C4, P14, P16, P21, P27, P28).
- **A 390-row attack coverage matrix** with action codes and per-row fixtures and tests (C5, P15, P28).
- **Challenge, bots and reputation:** proof-of-work challenge, verified bots, bot scoring, credential-stuffing detection, anti-scraping (P17).
- **Operational completeness:** backup and restore drills, expand/contract upgrades, key rotation, monitoring and runbooks, disaster-recovery drill, signed releases (P29, P30).
- **Honesty machinery:** claims policy with lint and audit, the three capacity numbers, UI disclosures, UNVERIFIED reason codes, lab-proven labeling (A section 4, E3, T-0534).
- **Backlog design:** Tier 2 to Tier 6 tasks specified to the same level as Tier 1 (P32).
- **Two runtime profiles (v5.1):** `local` (a personal computer, no Docker, live only while HDD runs) and `hosted` (a server, 24/7), one code path (R-31), store traits with Redis and in-process backends, embedded PostgreSQL, local CA, loopback identity, control-plane hardening against hostile pages, hosting profiles H1 to H5 and `hddctl hosting check`, watchdog supervision, last-known-good snapshot autonomy, backups and runbooks (C18, P33).
- **Defense completeness (v5.1):** access gate for sensitive paths, API discovery with positive security, business-flow protection, and the coverage map with the permanent "does not cover" list (C19, E15, P33), under the rule that no absolute claim is made (R-32).
- **Learned detection, bypass control and known vulnerabilities (v5.2):** Sentinel (bounded, advisory-first, explainable machine learning plus an optional off-path analyst, C20, R-33), the Bypass Guard (signed origin authentication, outbound tunnel, firewall generators, continuous outside verification, go-live gate, R-34, C21), the Known-Vulnerability Knowledge Base with exploit-signature pipeline, 90 more matrix rows (ATK-301 to ATK-390) and additional hardening (C22, P34, AC-59 to AC-62).
- **Delivery slices (v5.1):** DS0 to DS6, computed dependency closures with planning effort (section 0.8, E13.5).

### E12.2 Walkthrough: what happens when an attacker submits `' OR 1=1--` to a login form on a vulnerable protected site

This is the primary scenario, expressed as the sequence of control points and the tasks that build them. It assumes the domain is in `block` mode with the Vulnerable-Origin Shield (Balanced) preset and the `/login` path declared as an auth endpoint.

| # | Control point | What happens | Tasks |
| --- | --- | --- | --- |
| 1 | Connection | The attacker connects over TLS; the SNI selects the tenant certificate; the HTTP/1.1 or HTTP/2 front end applies protocol hardening (stage 0 to 5). | T-0353 to T-0358, T-0375 |
| 2 | Client IP | The real client IP is resolved from the socket (spoofed forwarding headers are ignored); IP key is /32 or /64. | T-0315 |
| 3 | Jail check | If the IP is already banned, the request gets the branded 403 immediately and no further work happens. | T-0319 |
| 4 | Host routing | The normalized Host selects the site snapshot; unknown hosts get a neutral 404. | T-0355 |
| 5 | Body handling | The form body is read with caps; the body is decoded and inspected (never skipped on write paths). | T-0249, T-0360, T-0276 |
| 6 | Normalization | Three views are built: raw, decoded (percent/HTML/unicode escapes) and canonical (case, whitespace, comments, quote folding). | T-0241, T-0242 |
| 7 | Field kind | `username` is recognized (or declared) as a username field; policy is strict on auth endpoints. | T-0251, T-0225 |
| 8 | Detection | The SQL tokenizer and semantic evaluator see quote breakout + always-true predicate + comment truncation: H1 and H2 hard hits (rules fire under all three views). | T-0263 to T-0271 |
| 9 | Verdict | Hard hit in `block` mode outside cross-site subresource context: 403 with Ray ID; no request reaches the origin. | T-0252, T-0261, T-0273 |
| 10 | Ban | A `BanIntent` creates a ban for the IP key: TTL step 1 of the ladder (1 h), reason `hard_attack`, rule/subtype/vector/field recorded. | T-0317, T-0320 |
| 11 | Propagation | Ban is stored locally, in Redis and Postgres; the signed stream tells the host agent; kernel set drops the IP on 80/443 and XDP if enabled (≤ 2 s). | T-0316, T-0322, T-0464, T-0467 |
| 12 | Evidence | An event with redacted evidence (≤ 512 B) and the policy branch is stored; the owner sees it live and in the IP jail. | T-0252, T-0253, T-0446 |
| 13 | Notification | An alert rule for SQLi on auth endpoints notifies the owner (grouped, rate-limited). | T-0453 |
| 14 | Follow-up | Any further request from the same IP (even benign) gets the jail response; the attacker's scanner is cut off. | T-0319 |
| 15 | If something slipped | The outbound filter would mask database errors; the V13 tripwire raises a critical event on success-after-attack in monitor mode; virtual patches cover known CVEs. | T-0274, T-0408, T-0485 |
| 16 | Appeal | A mistaken block can be appealed with a light proof-of-work; the owner decides; the attacker cannot self-unban. | T-0324 |
| 17 | Proof | In the Vuln-Lab, the same payloads succeed directly against the vulnerable app and fail through HDD with a ban (AC-38/AC-39). | T-0494 to T-0499 |

### E12.3 Honest limits of the walkthrough

- Signature and structure based detection can be evaded by techniques not yet in the rules; the held-out sets and the red exercise measure this and the numbers are published with their limits.
- A cross-site subresource request carrying the payload is blocked but does not ban (to prevent ban poisoning); repeated hits convert to a rate-limit ban.
- Password fields are softened for the comment-breakout family in Balanced to protect users with symbol-heavy passwords; Paranoid makes them hard.
- Direct-to-origin traffic bypasses HDD; origin lockdown is part of the protection profile and its status is shown honestly.
- A WAF does not fix the vulnerable code; the exposure board and hardening report track what must be fixed, and virtual patches never close an item.

### E12.4 Walkthrough: the same attack against a local instance

1. The operator runs `hdd-local run` on a Windows laptop without Docker; the embedded database starts, migrations run, the setup URL appears (T-0563, T-0564).
2. In the browser, `/setup` takes the one-time token, creates the owner with MFA, and offers the local trust choice (T-0567, T-0566).
3. The operator adds a local site `shop` pointing at an application on `127.0.0.1:3001` and chooses Monitor first, then Balanced (T-0568).
4. A test client sends `admin' --` as a query parameter (GET) to `https://shop.hdd.localhost:8444/login` and as a POST body to `https://sandbox.hdd.localhost:8444/`; the inspect-first gate confirms `would_block` before each live request (section 2.2, E3.1 rule 4).
5. In `block` mode the request receives 403 with a Ray ID; the identity `lo:<hash>` of that client is banned for the site, the dashboard (browser identity) is unaffected (T-0565).
6. Stopping `hdd-local` stops protection: the site's tunnel, if any, has no listener (fail closed, C18.9). S-135 and the docs say so in plain words.

### E12.5 Walkthrough: 24/7 on a server

1. `hddctl bootstrap` hardens a fresh VM (T-0573); `hddctl hosting check` lists any gaps (T-0571).
2. `hddctl deploy` installs the services with watchdog and restart policy (T-0522, T-0572); ACME staging, then production after approval (T-0538).
3. Backups run nightly to a remote target; a restore-to-scratch runs weekly (T-0574).
4. The VM reboots after a kernel update; services return within five minutes with no manual step; proxy and DNS first serve from the last-known-good snapshot if the stores are late (T-0572).
5. The external heartbeat and uptime probe record the outage window; the status page shows the measured figure with its method (T-0574).
