## B5. Data model (PostgreSQL) and Redis

### B5.1 Conventions

- Primary keys are `uuid` generated as UUIDv7 in the database default (`gen_uuidv7()` function created by migration 1 if the server lacks one). The API exposes prefixed base32 identifiers (B2.2). Every table has `created_at timestamptz not null default now()`; mutable tables also have `updated_at` maintained by trigger and `version int not null default 1` for optimistic concurrency (`ETag` = `W/"<version>"`).
- **Every tenant-owned table has `org_id uuid not null references orgs(id)` from migration 1** and a row-level-security policy: `using (org_id = nullif(current_setting('app.org_id', true), '')::uuid)`. The application roles never have `BYPASSRLS`; only `hdd_backup` does, and it cannot write (with `FORCE ROW LEVEL SECURITY`, a dump by any other role would silently contain no tenant rows). Platform operations use `SECURITY DEFINER` functions that insert an audit row with a mandatory `reason`.
- Roles: `hdd_owner` (migrations only), `hdd_api` (read/write, subject to RLS), `hdd_worker` (read/write, subject to RLS plus system tables), `hdd_proxy` and `hdd_dns` (read-only on config tables; their only write is `INSERT`/`COPY` into the unpartitioned `waf_events_ingest` table described in B5.7), `hdd_readonly` (analytics, subject to RLS), `hdd_backup` (`LOGIN`, `BYPASSRLS`, `SELECT` only; used solely by backup jobs, never by services).
- Enumerations are Postgres `text` with `check` constraints (easier expand/contract than native enums).
- Time-partitioned tables: `waf_events` (monthly), `audit_log` (monthly), `login_attempts` (monthly), `webhook_deliveries` (monthly), `mail_outbox` (monthly), `rollup_*` (yearly). Retention drops partitions; there is no row-by-row delete job on the hot tables.
- **Partitioned-table rules (PostgreSQL).** A primary key or unique constraint on a partitioned table must contain the partition key, so these tables use composite keys: `waf_events (ray_id, ts)`, `audit_log (id, ts)`, `login_attempts (id, ts)`, `webhook_deliveries (id, created_at)`, `mail_outbox (id, created_at)`, `rollup_* (org_id, site_id, bucket, dimension, key)` with `bucket` as the partition key. **No foreign key references a partitioned table**; references to them (for example `ip_bans.ray_id`, `ban_appeals.ray_id`) are logical, resolved by `(ray_id, ts)` lookups and checked by a nightly integrity job. Foreign keys *from* a partitioned table to an ordinary table (for example `waf_events.ban_id`) are allowed. Each migration that creates a partitioned table also creates the next two partitions and registers it with the partition manager (T-0442).
- Secrets at rest (TLS private keys, ACME keys, TOTP secrets, SMTP/webhook secrets, provider tokens) use an envelope: `HDD_MASTER_KEY` wraps per-secret data keys (AES-256-GCM, 96-bit random nonce, AAD = table+id+column). Stored as `bytea` with a `key_version int`.
- Indexes follow query patterns listed in each migration's header comment. Every foreign key is indexed.
- Expand/contract only: add nullable column, backfill, enforce, then (later release) drop.

All of these keys and channels are accessed through the `KvStore`, `Bus` and `Limiter` traits of `hdd-common::kv` (R-31). The Redis backend implements them with Redis; the in-process backend of the `local` profile implements the same semantics (TTL, atomic increment and compare operations, ordered revisions on the bus) and is checked by the same conformance suite (T-0562). Extra keys: `hdd:gate:sess:{site}:{token_hash}` (access-gate session, hash + TTL), `hdd:flow:{site}:{flow}:{key}` (business-flow counters and sequence state, hash + TTL), `hdd:lo:{ua_hash}` (local loopback identity registry, local profile only).

Proxy and DNS hold immutable compiled `Arc<Snapshot>` values swapped atomically (`ArcSwap`) plus `moka` caches. After every swap they also write the snapshot atomically to `HDD_SNAPSHOT_CACHE_DIR` (the last-known-good snapshot, C18.11) so a restart without Postgres or Redis still serves with the last good policy. Migrations are expand/contract only, each tested forward and with a restore from backup.
