## C18. Runtime profiles: local and hosted (new in v5.1)

### C18.1 Purpose and honest premise

The operator needs one platform that can (a) run on a personal computer and be live only while it is running, and (b) be hosted on a server so that it runs 24/7. v5.1 delivers both as **two runtime profiles of the same product** (rule R-31), selected by `runtime.profile` in the live profile or `HDD_RUNTIME_PROFILE`.

Honest premise. No software makes a single machine run 24/7: availability comes from the host, the supervisor, the network and operating discipline. `local` is for learning, development, demonstrations and attended use. `hosted` is for unattended production. HDD never presents `local` as production-grade availability, never presents a single server as highly available, and measures uptime instead of promising it.

### C18.2 Profile comparison

| Aspect | `local` | `hosted` |
| --- | --- | --- |
| Intended use | Development, demos, learning, attended protection of a site through an operator-run tunnel | Unattended production, 24/7 |
| Supported OS | Windows 10/11 x64, macOS 13+ (arm64, x64), Linux (x64, arm64) | Linux x64 or arm64 (Debian 12+, Ubuntu 22.04+, RHEL 9 class); kernel 5.15+ for XDP (optional) |
| Process model | `hdd-local` supervisor runs web, api, worker, proxy and (optionally) dns as supervised tasks in one process (in-process mode), or as the normal service binaries when `kv: redis` | Separate services under systemd or containers |
| Product surfaces (`www`, `app`, `admin`, `api`, `status`) | Served directly by `hdd-web` and `hdd-api` on the web port with the control-plane hardening of C18.7; routing them through the proxy (`dogfood`) is optional and off by default | Always behind the proxy as `platform_internal` (dogfood, section 2.9) |
| PostgreSQL | Embedded and managed by `hdd-local`, or external, or Docker Compose | External or host-local server, hardened (T-0521) |
| Redis | Not needed (`MemoryKv`); optional | Required when more than one service process exists |
| Ports | Unprivileged: web 8443, proxy 8080 and 8444, dns 5300 | 80, 443, 53 (and UDP 443) |
| TLS | Name-constrained local CA, `*.hdd.localhost` | ACME (staging first, production by approval) |
| DNS | Optional authoritative server on 5300 for tooling and tests; Chromium and Firefox resolve `*.localhost` themselves | Authoritative on 53 with `ns1`/`ns2`, delegation, DNSSEC state |
| Integration modes | `local_only` (no DNS change), and `subdomain_only`, `cname_partial`, `a_record_partial` through a tunnel or port forward | All modes of C17 |
| Client identity | Peer IP for LAN and tunnel clients; keyed identity for loopback clients (C18.5) | Peer IP or trusted-proxy header |
| Kernel enforcement | None (the `Enforcer` is `Noop`); the L7 jail enforces | nftables sets, XDP, host agent |
| Shield and DDoS | L7 behavior only; the shield state machine runs without kernel actions | Full (C11) |
| Uptime | Only while running and awake; optional start at login | Watchdog, auto-restart, boot start, backups, signed upgrades (C18.11) |
| Mail | SMTP if configured; otherwise the admin-only outbox viewer (S-135) | SMTP required for multi-user installs |
| Acceptance | Unit, integration and browser tests, `profile-parity`, and the `local` tier (AC-55); hosted-only checks are UNVERIFIED(`environment_unsupported`) | Everything |

### C18.3 One code path: the store traits and the enforcer

Profile-dependent code is confined to `hdd-local`, `hdd-common::kv`, `hdd-common::profile` and the `Enforcer` factory. `cargo xtask profile-lint` fails if a profile check appears in the detection, pipeline, authentication or tenancy crates.

- **`KvStore`:** `get`, `set` (with TTL), `del`, `incr` (with TTL), hash get/set, sorted-set add/range-by-score/remove, set add/members, `compare_and_set`, and **named atomic operations** that replace the Lua scripts: `rate_window_check`, `challenge_nonce_consume` (get-and-delete), `offence_incr_with_decay`, `flow_signal_update`. `RedisKv` implements the named operations as Lua; `MemoryKv` implements them under shard locks.
- **`Bus`:** `publish(channel, message)` where every message carries a monotonic `revision`; `subscribe(channel)` returns a bounded stream; a gap or a lagging subscriber yields a `resync` signal (consumers reload from Postgres immediately). Bounded buffers with drop counters; no unbounded queue exists.
- **`Limiter`:** `check(keys, limit, window, algorithm)` with `counter` (two sub-windows), `exact` (log or GCRA) and `gcra` algorithms (T-0333).
- **Conformance suite** `kv_conformance` runs against both backends (T-0562): TTL expiry within ±50 ms, atomicity under 64 concurrent tasks, bus ordering and gap detection, memory bound with eviction by TTL then LRU (pinned namespaces for bans and sessions are never evicted), and the restart contract below.
- **Restart contract.** `MemoryKv` starts empty. Everything durable must be rebuildable from Postgres before listeners open: bans (`ip_bans`), offences (`ban_offences`), sessions (`user_sessions`), the compiled snapshot. Non-durable state (rate counters, challenge nonces, campaign sets, flow counters) resets on restart; this is documented, tested and safe (a reset only forgives, it never blocks).
- **`Enforcer`:** `Noop` in `local`; the jail check at stage 6 uses the in-memory ban cache, so enforcement at L7 is identical in both profiles.

### C18.4 The `hdd-local` supervisor

Commands: `run`, `status`, `stop`, `doctor`, `selftest`, `open`, `logs`, `backup`, `restore`, `export`, `reset`, `unban`, `hosts apply|remove|status`, `trust install|remove|status`, `autostart enable|disable`, `token show`, `upgrade`.

- **Modes.** *In-process* (default): every service crate exposes `run(ctx)` and is linked into `hdd-local`; a panic is caught at the task boundary (R-09), the task is restarted with backoff, and the other services keep running. *Multi-process* (`kv: redis` or Compose): the supervisor starts the normal service binaries.
- **Start order and readiness.** (1) single-instance lock in the data directory plus a port probe; (2) light doctor; (3) start the embedded database and wait for readiness (60 s limit, then `ERR-LOCAL-004` guidance); (4) run migrations as `hdd_owner`; (5) rehydrate bans, offences and sessions into `MemoryKv`; (6) compile the snapshot and write the snapshot cache; (7) start api, web, worker; (8) open the data-plane listeners and DNS; (9) print the URLs and, if requested, open the browser. Shutdown is the reverse with a 10 s drain, a fast database shutdown and lock release; on Windows the console-close, logoff and shutdown handlers get only a few seconds, so they run an abbreviated 3 s drain and `pg_ctl stop -m fast` with a 2 s budget, and the embedded server runs in a Job Object with `KILL_ON_JOB_CLOSE` so no orphan survives (crash recovery handles the rest); at start a stale `postmaster.pid` or an orphaned server is detected and stopped.
- **Crash policy.** Task restart with exponential backoff (1 s to 30 s); more than five restarts of one task in ten minutes stops that task, raises a banner in the UI and an audit event, and leaves the others running. The supervisor itself exits non-zero on unrecoverable store failure.
- **Sleep and wake.** Resume is detected by OS power events (`PowerRegisterSuspendResumeNotification` on Windows, wake notifications on macOS, logind `PrepareForSleep` on Linux), with a 1 s ticker whose observed lateness exceeds 5 s as the portable fallback (monotonic clocks do not all stop during sleep, and an NTP step also moves the wall clock). On resume the supervisor re-checks listeners and the database, expires time-bound state using wall-clock timestamps, and records `resumed_after_seconds` in the runtime page.
- **First run.** Generates secrets into the data directory (0600), initializes the database, runs migrations, creates a one-time bootstrap token written to a 0600 file (the terminal prints only the file path and the setup URL; `hdd-local token show` reveals it to an interactive terminal), and serves `/setup` (S-136) until the first platform owner exists. The token is stored hashed, single use, and expires after 15 minutes.
- **Autostart (opt-in).** Windows Task Scheduler "at logon", macOS LaunchAgent, Linux `systemd --user`. `run --keep-awake` asks the OS to prevent idle sleep while HDD runs (SetThreadExecutionState, `caffeinate`, `systemd-inhibit`); it never prevents a user-requested sleep.
- **Logs and state.** JSON logs rotate at 10 MiB, five files, under the data directory; redaction is always on. `status` prints real values only.

### C18.5 Client identity and bans on loopback

When every client is `127.0.0.1`, a single identity would make the first test ban the operator's own browser. The local profile therefore keys loopback clients:

| Source | Identity key | Notes |
| --- | --- | --- |
| Peer is not loopback (LAN, WireGuard, forwarded port) | peer IP (IPv6 `/64`) | Same as hosted |
| Peer is loopback, request arrives on the dedicated tunnel listener, and the provider header is present (`CF-Connecting-IP` for cloudflared, `X-Forwarded-For` for ngrok, or the configured header) | the client IP from the header | Headers are trusted **only** on the tunnel listener (default loopback port 8081); the normal listeners never trust them |
| Peer is loopback, no trusted header | `lo:<first 12 hex of HMAC(key, user-agent + "\|" + accept-language)>` | Browsers, curl, sqlmap and test tools each get their own identity |
| Peer is loopback with `X-HDD-Test-Client: <label>` (label `[a-z0-9-]{1,32}`) | `lo:<label>` | Honoured only on a normal loopback listener, only while `lan_exposure` is false and no tunnel is configured, and only when `runtime.local.test_client_header` is true (default false; `selftest` and acceptance runs enable it); stripped and ignored on the `tunnel_http` listener |

Rules. (1) Loopback is **not** in the never-ban list in `local` (an explicit, tested override of the never-ban rules in C6.6 and C9.2); instead, `lo:` bans are **scoped to the protected site**; the platform surfaces (`app`, `admin`, `api`, `www`) are never jailed by them (they keep their own login throttles), so the dashboard stays reachable (R-19). (2) The dashboard offers one-click unban and `hdd-local unban --all-loopback`. (3) `loopback_client_identity: single` is allowed only while every site is in `monitor` or `log` mode and is refused (`ERR-LOCAL-001`) when a site is in `block`. (4) The registry of `lo:` identities is bounded (4,096 entries, LRU) so a flood of user-agents cannot exhaust memory. (5) A request on the `tunnel_http` listener without the configured provider header is refused with `421` rather than keyed by user-agent, and the client address is read from the rightmost trusted hop of `X-Forwarded-For`. (6) Honest limit: a local process can vary its user-agent at will, so `lo:` bans demonstrate and test the shield; they do not contain a hostile local process. Bans against LAN and tunnel clients use real addresses and behave as in hosted.

### C18.6 Local TLS and trust

- **Local CA.** Generated on first run with `rcgen` (ECDSA P-256), 2-year validity, **name-constrained**: permitted DNS names `localhost` (which covers every `*.localhost` name) and the configured suffix, permitted IP ranges `127.0.0.0/8` and `::1/128`; nothing else. The private key never leaves the data directory and is wrapped with the OS key store where available (DPAPI, Keychain) or kept 0600 on Linux. Name constraints limit the damage if the key leaks; some old clients ignore them, and the docs say so.
- **Leaf certificates.** One per site (`<slug>.hdd.localhost`, plus names added through the hosts helper that fall under the constraints), 90-day validity, renewed at two thirds of the lifetime, served by the same SNI resolver as hosted (the certificate source is `local_ca` instead of `acme`).
- **Trust.** `hdd-local trust install` shows the CA fingerprint and requires explicit consent. It uses what the OS allows without elevation: the current-user root store on Windows (the OS shows its own confirmation), the login keychain on macOS (the OS prompts), the NSS database for Chrome profiles on Linux, and the Firefox profile database (`cert9.db`, through NSS `certutil`) on every OS, because Firefox keeps its own store unless `security.enterprise_roots.enabled` is set; where Firefox cannot be updated the command reports "Firefox not covered" with the manual steps. A system-wide install on Linux needs root and is documented, never automatic. `trust remove` removes exactly what was installed. HDD never installs a trust root silently.
- **`http_only` mode.** Loopback names only. Because `Secure` cookies are rejected by some browsers over plain HTTP (Safari does not treat `localhost` as a secure context), this mode uses unprefixed cookie names (`hdd_session`, `hdd_csrf`, `hdd_gate`, `hdd_cl`; `HttpOnly`, no `Secure`) and binds the CSRF token to the server-side session (synchronizer token) instead of relying on the cookie; a request carrying more than one `hdd_session` cookie is rejected (a sibling site could otherwise plant one); it shows the readiness warning and is refused when `lan_exposure` is true.
- **HSTS.** The local profile sends no `Strict-Transport-Security` header, or at most `max-age=300` without `includeSubDomains` or `preload`: HSTS pins are host-based and browsers allow no certificate-error bypass for pinned hosts, which would defeat CA rotation, `trust remove` and the documented fallbacks for up to two years. This is a permitted profile difference (R-31).
- **Tooling note.** Chromium and Firefox resolve `*.localhost` names internally; Safari, `curl` before 7.78 and other tools may not, so for those and for tests use `--resolve` or the hosts helper (C18.8).

### C18.7 Control-plane hardening for a browser-reachable local instance

A local control plane is reachable by every web page the operator opens. Controls (all tested in AC-55 with a hostile page served from another origin and a rebinding server):

1. **Host allowlist** (`HDD_ALLOWED_HOSTS`, exact names and ports; only the `*.hdd.localhost` surface names or the configured suffix); any other `Host` gets `ERR-LOCAL-003` before routing, which defeats DNS rebinding. `localhost`, `127.0.0.1` and `[::1]` are not control-plane names (cookies are host-scoped, not port-scoped, so a session cookie set there would be sent to every other development server on that host): they answer `308` to the surface name (`https://app.<suffix>:<port>/`, or the `http` form in `http_only`) without setting cookies and serve nothing else except `/healthz`.
2. **Origin and Fetch Metadata**, for cookie-authenticated requests only (a request that carries `Authorization: Bearer` and no cookie is exempt, and a cookie sent to the `api` host is still refused with `ERR-AUTH-001`): *WebSocket upgrades* require `Origin` equal to an allowed origin of the active scheme; *SSE and other GET requests*: if `Sec-Fetch-Site` is present it must be `same-origin` (or `none` for top-level navigations), and if it is absent `Origin` must be absent or same-origin and `Referer`, if present, must be same-origin (browsers send no `Origin` on same-origin GET); *mutations*: `Origin` must be same-origin, plus `Sec-Fetch-Site: same-origin` when present, and a mutation with neither `Origin` nor `Referer` is refused. The allowed origin scheme follows the active TLS mode (`https` for `local_ca`, `http` for `http_only`).
3. **CSRF token** on every mutation (as hosted) and the **same cookie attributes as hosted** (E7.5: `SameSite=Lax` for the app, Strict for admin, `__Host-` prefix over HTTPS). SameSite is defense in depth only: protected sites (`shop.hdd.localhost`) and surfaces are same-site, so the real controls are item 2 and the CSRF token, and no protected site (including a deliberately vulnerable lab origin) is ever served from a surface hostname.
4. **No CORS and no Private Network Access grant**: preflights get no `Access-Control-Allow-*` headers, and a request carrying `Access-Control-Request-Private-Network` is answered without `Access-Control-Allow-Private-Network`.
5. **Bootstrap token** for first-run setup (C18.4); `/setup` disappears once the first platform owner exists.
6. **Loopback-only binding verified**: `hdd-local selftest` enumerates its own listeners and, from a non-loopback local address, attempts to connect to each control-plane port; any success fails the self-test.
7. **MFA for platform roles** applies in `local` too (TOTP works offline).
8. **No secrets on command lines or in child-process environments**; secrets reach children through files or inherited handles.
9. **Shared machines.** Other local users can reach loopback ports; the session, MFA and CSRF defenses apply to them as to anyone, but `local` on a multi-user shared machine is outside the supported envelope and the docs say so.

### C18.8 Local names, DNS and the hosts helper

- **Local sites.** A site named `shop` is served at `https://shop.hdd.localhost:8444`. The add-domain wizard (S-042) has a `local_only` variant: choose the name, set the origin (loopback and RFC 1918 origins are allowed through `egress.private_origin_allowlist`, never the metadata ranges, with the readiness warning of section 2.9), TLS comes from the local CA, and "Go live" prints the URL. No DNS change is needed.
- **Real hostnames through a tunnel.** To protect `shop.example.com` while HDD runs locally, the operator runs a tunnel to the `tunnel_http` listener and points a CNAME at it (integration mode `subdomain_only` or `cname_partial`); DNS stays with the existing provider. Ownership proof (TXT or HTTP file) works as in hosted.
- **Hosts helper.** `hdd-local hosts apply` writes one marked block (`# BEGIN HDD LOCAL` to `# END HDD LOCAL`) mapping chosen names to `127.0.0.1` and `::1`, shows the diff, backs up the original into the data directory, and prints the exact elevated command when it lacks permission. It never edits outside its block; `hosts remove` deletes only the marked block (other software such as Docker Desktop, WSL and VPN clients edits the same file, so the backup is never restored automatically; `hosts restore-backup` shows a diff first).
- **Embedded DNS (optional, port 5300, not the multicast-DNS port 5353 that mDNS responders usually hold).** Authoritative for `hdd.localhost` and operator-added zones for tooling such as `dig @127.0.0.1 -p 5300` and for the DNS-layer tests (no recursion, minimal `ANY`, RRL, EDNS cookies). The operating system's resolver does not use it.
- **Cookie scope.** Cookies are not port-specific, so a protected site is never served on a surface hostname; protected sites always use their own hostnames.

### C18.9 Exposing a local instance, and failing closed

Options, in increasing risk: (1) loopback only (default); (2) LAN, for testing from another machine (`lan_exposure` with the acknowledgement `I-UNDERSTAND-LOCAL-IS-NOT-24x7`; data-plane listeners only; persistent banner; audit event). It needs a configured suffix that LAN clients can resolve (for example `lab.test` through the router or their hosts files) and the CA installed on each client, because the CA can issue only names under `localhost` and the configured suffix and loopback addresses; otherwise `lan_exposure` is refused with a clear reason, and a client without the CA sees a certificate error (documented); (3) an operator-run tunnel (cloudflared, ngrok or WireGuard) to the dedicated `tunnel_http` listener (HDD does not bundle or call any tunnel provider); (4) router port forwarding (discouraged: dynamic addresses, blocked ports); (5) move to `hosted`.

Before exposure HDD requires: origin lockdown applied or the origin bound to loopback (C9.12), the site first run in `monitor` mode, and the S-135 notice acknowledged. **Fail-closed:** when HDD stops or the machine sleeps, a tunnel has no listener and the site becomes unreachable instead of unprotected, as long as the origin accepts connections only from HDD. If the origin is directly reachable, the readiness view marks "origin bypass possible" as a failed check.

### C18.11 Running 24/7: supervision, autonomy, backups, upgrades, runbooks

1. **Supervision (systemd).** Every HDD unit is `Type=notify` with `NotifyAccess=main`, `Restart=always`, `RestartSec=2` and, in `[Unit]`, `StartLimitIntervalSec=0` so systemd never gives up (a unit that fails at once because a store is unreachable or the disk is full would otherwise exhaust a start limit within seconds and stay down until `systemctl reset-failed`); crash loops are made visible by `OnFailure=hdd-alert@%n` and a restart-rate alert instead. Where systemd is 254 or newer add `RestartSteps=5` and `RestartMaxDelaySec=60`; Debian 12, RHEL 9 and Ubuntu 22.04 ship 252 or older and use the plain form. `WatchdogSec=30` (each service pings `sd_notify(WATCHDOG=1)` from its main loop, so a stuck event loop is restarted), `MemoryMax`, `LimitNOFILE` and `TimeoutStopSec` complete the unit. Data-plane units use `Wants=` rather than `Requires=` on Postgres and Redis so a store outage never stops them; the data plane has `OOMScoreAdjust=-500` so the kernel kills other processes first. Compose uses `restart: unless-stopped` and healthchecks.
2. **Autonomy of the data plane.** After every snapshot swap, proxy and DNS write the snapshot atomically to `HDD_SNAPSHOT_CACHE_DIR`. On start without Postgres or Redis they load it and serve with the last good policy, local ban cache and local limiter; events go to a bounded disk spool (256 MiB, then dropped with a counter); configuration changes are disabled; the UI shows "control plane unavailable". Inspection never fails open (R-26).
3. **Reboot safety.** Units are enabled; ordering needs no manual step; `hddctl hosting reboot-test` proves it.
4. **Disk guard.** At `HDD_DISK_GUARD_PCT` (90%) events are sampled and exports refused; at 95% the oldest spool and log files are removed; bans, audit rows and the database are never auto-deleted. Alerts fire at both levels.
5. **Certificates.** Renewal at two thirds of the lifetime (ARI when supported), alert at 20 days remaining, retry with backoff; a failing renewal never takes the proxy down.
6. **Backups.** Daily `pg_dump -Fc --no-unlogged-table-data` run as the `hdd_backup` role (retention 14 daily, 8 weekly, 12 monthly), optional WAL archiving for a 15-minute RPO, encrypted with a key the operator holds, targets `local`, `sftp` or `s3` (egress allowlist entry required); the master key and pepper are escrowed separately, never inside the data archive; a weekly automatic restore into a scratch database that compares tenant row counts, not only the schema, and a monthly drill (AC-33 family, T-0574).
7. **Upgrades.** `hddctl upgrade`: signature verification, staged swap, health check, automatic rollback; proxy upgrades use socket handoff (`SO_REUSEPORT`) and graceful drain; operating-system security updates via unattended upgrades, kernel updates with a scheduled reboot window.
8. **Monitoring.** External dead-man heartbeat, an external uptime probe from the operator's vantage point, the status page, alert rules (T-0521 family). Uptime is **measured** from heartbeat and probe data and reported as such; HDD does not state an uptime promise.
9. **Runbooks** in `docs/RUNBOOKS/`: server rebooted or lost power; disk full; out of memory; PostgreSQL down; Redis down; certificate failure; DNS not answering; mass false positives or a wrong ban set; locked out of the admin panel; attack in progress; provider outage and standby-edge failover.
10. **High availability, honestly.** One server is a single point of failure. H2 plus two nameservers at different providers reduces it; HDD does not claim any availability percentage.

### C18.12 Moving between profiles

`hdd-local export` produces an archive: logical database dump, profile, rule and policy data, and an inventory of secrets **without** the master key. The operator carries the master key separately (explicit step). `hddctl import --archive` on a hosted install restores it. What does not transfer: certificates from the local CA (reissued through ACME), `lo:` bans, local-only sites (kept, flagged "needs integration", and the wizard resumes at step 3 of S-042), local ports. The reverse direction (hosted to local) is supported for `owner_only` single-tenant installs.

### C18.13 Threats specific to the local profile

| Threat | Mitigation | Test |
| --- | --- | --- |
| Hostile web page calls the local control plane (CSRF, Private Network Access) | C18.7 items 2 to 4 | Browser test with a hostile page on another origin |
| DNS rebinding to `127.0.0.1` | Host allowlist (C18.7 item 1) | Lab rebinding server |
| Another process or user reads secrets | Owner-only directory or ACL, secrets 0600, no secrets in child arguments or environment | Permission and process-listing test |
| Misuse of the local CA | Name constraints, key wrapping, consent for trust | Validation of a certificate for an out-of-scope name must fail |
| Embedded database reachable from the network | Unix socket or loopback, generated password, restrictive `pg_hba` | Listener scan |
| Tampered embedded-database binaries | Pinned digest and signature verification | Checksum mismatch test |
| Machine sleeps or HDD stops unnoticed | S-135 notice, resume detection, fail-closed tunnel | Simulated clock jump and listener-absent test |
| Operator bans their own browser | Keyed loopback identity, site-scoped bans, one-click unban | Ban test from the same browser identity |
| Exposed LAN listener in front of a weak origin | Acknowledgement, origin-bypass readiness check | Exposure test |
| Data directory deleted or corrupted | Backups, doctor detection, restore | Restore drill |

## C19. Defense completeness: access gate, API discovery, business flows, coverage map (new in v5.1)

### C19.1 Principle

No product can honestly promise absolute protection (R-32). HDD aims for **measured, mapped, disclosed coverage**: every attack class it claims is in the matrix (C5) with fixtures and checks; every standard category it maps to is in the coverage map (E15, S-134) with a status; everything it does not cover is stated. v5.1 adds three controls that close gaps the request-inspection layers cannot close alone: protecting sensitive paths before they reach the origin (access gate), knowing and constraining the API surface (API discovery and positive security), and detecting abuse of legitimate business functions (business flows). These sit alongside L8, L9 and L10 as layer **L14** in C1.

### C19.2 Access gate (S-131)

Purpose: administration areas, database tools and debug endpoints of a (possibly vulnerable) origin are among the most exploited surfaces. The gate lets the owner require a second, HDD-enforced barrier in front of selected paths, **before** inspection and before the origin sees the request (stage 8a of C2).

- **Policies.** `ip_allowlist` (client key in a CIDR list; IPv6 `/64`), `hdd_login` (HDD-hosted login at `/__hdd/gate/login` using gate credentials, optional TOTP; success sets the `__Host-hdd_gate` cookie bound to a server-side session in `KvStore`: idle 30 minutes, absolute 12 hours, bound to the user-agent hash and the IP bucket), `basic` (HTTP Basic validated by HDD; the `Authorization` header is consumed and never forwarded; rule creation warns when the origin has been seen to challenge with `WWW-Authenticate`), `signed_link` (an expiring, single-use, revocable link of the form `/__hdd/gate/link#<secret>`: the secret is in the fragment, so it is not sent to any server or logged until the nonce-protected confirm page POSTs it; the response sets the path-scoped cookie `__Secure-hdd_gate_p` with `Path=<prefix>`; the page sends `Referrer-Policy: no-referrer` and `Cache-Control: no-store`; default 24 hours, maximum 7 days), and `mtls` (reserved in the schema; refused with `ERR-VAL-005` until implemented).
- **Credential cost control.** Gate secrets are generated by HDD with at least 128 bits of entropy and stored as HMAC-SHA-256 under a per-site server key, so verification is cheap and constant-time; Argon2id (T-0106) is used only for an operator-chosen password. Before any password hash, a per-address token bucket and a global semaphore (at most half the CPU cores hashing at once) apply, and excess requests get 429 `ERR-GATE-005` without hashing. A successful `basic` verification is cached as HMAC(server key, `Authorization` header) for at most 60 s, so a credential is verified at most once a minute.
- **Matching is bypass-resistant, with stated limits.** The gate matches the **canonical** path and the **raw** path; a rule matches if either does. Canonicalization is: iterative percent-decoding (at most 3 passes), `%uXXXX` and overlong UTF-8 decoding, `\` to `/`, removal of NUL and other control characters and of zero-width and soft-hyphen characters, per-segment stripping of trailing dots and spaces, path parameters (`;jsessionid=`) stripped, dot-segments resolved, repeated slashes collapsed, Unicode NFKC, and case folding (**on by default**; `case_sensitive: true` turns it off for case-sensitive stacks). The query string is never part of the path. A pattern such as `/admin` matches at a boundary: the next canonical character is not `[A-Za-z0-9_-]`, so `/administrator` is not matched while `/admin.json`, `/admin;x=y` and `/admin~` are. Headers that some stacks use to rewrite the path (`X-Original-URL`, `X-Rewrite-URL`, `X-Override-URL`, `X-Forwarded-Prefix`, `X-Forwarded-Path`, `X-Original-Path`, `X-HTTP-Path-Override`, `Destination`) are matched as **additional candidate paths** and are stripped from the upstream request unless the site explicitly allows them. Paths over 2 KiB are decided as gated without full canonicalization. Requests that are malformed or not accepted at stages 2 and 3 (invalid request target, absolute-form targets, `CONNECT`, unknown methods, duplicate `Host` or `:path`, invalid `Host`, an `:authority` that does not match the SNI) are rejected before the gate (`rejected_early`). E1.12 lists the tested shapes, the negative controls that must not be gated and the early rejects; a canonicalization difference between HDD and a particular origin stack can still exist and belongs in the known-limitations list.
- **Exceptions inside a gated prefix** are explicit `allow_paths` (for example `/wp-admin/admin-ajax.php`), never implicit.
- **Failure behavior** is `deny` (403 with `ERR-GATE-002`, identical for unknown user and wrong secret), `challenge` (the gate login), or `redirect_login`. API-looking paths always `deny`. Repeated gate failures feed credential-stuffing detection (C7.6) and may ban. Throttling is keyed on (username, address bucket) pairs; a per-username global counter above a threshold escalates to proof of work and an alert but never hard-locks the account (R-19), and recognised devices (a valid gate cookie, an earlier success from the same address bucket) are exempt.
- **Templates:** WordPress admin and login (with `admin-ajax.php` allowed, `xmlrpc.php` denied), phpMyAdmin and Adminer, Spring actuator, generic `/admin` and `/manager`, `/server-status`, `/.env`, `/.git`, `/debug`, API documentation pages.
- **No self-lockout (R-19).** Creating or changing a rule shows a preview of what happens to the acting user's address and session (`ERR-GATE-004` unless acknowledged). `hddctl gate disable --site` is the break-glass.
- **The gate does not replace the WAF.** After a successful gate decision, the request continues through rate limiting, challenge, inspection and the outbound filter as normal.

### C19.3 API discovery and positive security (S-132)

- **Discovery.** From traffic in `monitor` or `block` mode, per `(method, path template)`; path segments become `{param}` when they match a typed pattern (integer, UUID, hex or base64 of 16 or more characters, e-mail, date), or when at least 50 distinct values appear at that position under the same parent template and no single value exceeds 20% of the requests; otherwise literal segments are kept, so `/api/users` and `/api/admin` stay distinct and a new endpoint cannot hide inside a collapsed template. HDD stores counts, parameter **types and bounds** (integer, uuid, string with min and max length and character class, boolean, object, array), JSON property **names** (collapsed to `{key}` beyond 64 distinct per object), and whether credentials were present. It stores no request values except operator-visible low-cardinality enumerations: a parameter keeps an enumeration (at most 20 values, each at most 32 bytes) only if its name is not on the sensitive-name list (password, token, secret, key, auth, email, phone, card, ssn, session and similar); otherwise only type, length bounds and character class are kept. Each path segment is classified by shape **before** counting: digits, UUID, hex or base64 of 16 or more characters, anything containing `@`, `%` or `:`, or longer than 24 characters is stored as `{param}` immediately, so an e-mail address or reset token in a path is never stored. A schema is proposed after at least 200 requests over at least 24 hours.
- **States.** `discovered` (seen), `approved` (owner accepted), `shadow` (seen in traffic but absent from an approved or imported description), `deprecated` (described but not seen for 30 days: a possible zombie endpoint), `blocked`.
- **Import.** OpenAPI 3.0 or 3.1 (JSON or YAML, at most 5 MiB, nesting depth at most 64, **local `$ref` only**; remote references are never fetched) and GraphQL SDL. Parsing runs with hard limits under the fuzzing regime of the other parsers.
- **Enforcement** (`off`, `monitor`, `block`; default `monitor`): method not allowed for the template; unknown endpoint (action configurable, default `log`); content type not matching; JSON unknown properties where `additionalProperties: false` was approved (mass assignment, ATK-175); type, range, length and required-property violations; per-endpoint size limits; a request without credentials to an endpoint that is normally authenticated (flagged); response properties not in the description (monitor only, excessive-exposure signal); GraphQL depth (default 10), cost (1,000), aliases (15), batch size (10), introspection off unless allowed, field-suggestion rewriting (ATK-179 to ATK-182); sequential object-id walks by one token (ATK-173).
- **Safety.** Schema violations are **soft** signals by default and **never ban on their own** (a client error is not an attack); they escalate only together with attack payloads. Switching an endpoint to `block` first runs the **seven-day preview** (replays observed traffic and lists what would have been blocked) and requires acknowledging it (`ERR-APIDISC-002`).

### C19.4 Business-flow protection (S-133)

A business flow is a function of the application whose abuse is harmful even when every request is syntactically valid (OWASP Automated Threats, OAT; mapped in E15). Flows are defined per site from templates and run in `monitor` by default.

| Flow kind | Default signals (all counted in `KvStore`, no values stored) |
| --- | --- |
| `login` | failures per IP, username (HMAC) and device; distinct-username ratio per IP; success after many failures (takeover); success from a new ASN or country after failures |
| `signup` | velocity per IP, ASN and fingerprint; disposable domains; time-to-complete under 2 s; honey field filled; many accounts from one fingerprint |
| `reset`, `otp` | per-account and per-destination send limits; per-IP limits; premium-prefix and country allowlist option (cost-abuse and SMS-pumping defense) |
| `checkout` | repeated small attempts; many distinct card hints per session (a declared field that may hold only the last four digits or the first six plus last four; any 13-to-19-digit value that passes the Luhn check is dropped unhashed and raises a misconfiguration alert; hints are HMAC-SHA-256 truncated to 32 bits under a per-site key, kept only in `KvStore` with a TTL no longer than the session, never persisted or logged; HDD never stores card numbers, and this is not PCI scope reduction); declined-to-approved ratio; cart sequence integrity (checkout without a prior cart) |
| `search` | unique-URL breadth and depth-first walks; sequential pagination; missing static-asset fetches; low timing jitter; request rate against the human baseline |
| `contact` | proof of work, honey field, link count, duplicate content hash across IPs |
| `coupon`, `gift_card` | guess rate on the code endpoint, per-code attempt caps, distinct-code ratio |
| `custom` | operator-chosen signals |

The flow engine runs in three phases because the data it needs exists at different stages. **Phase A** (stages 9 and 10) uses request-line and header signals only: velocity per address, ASN and fingerprint, template match, and lookups of state written by earlier phases. **Phase B** (stage 12a, after extraction) computes declared-field signals: username HMAC, honey field, destination, card hint, content hash and time-to-complete. **Phase C** (stage 18a) records the outcome (login success or failure, checkout approved or declined) from the response status, a redirect or a declared body marker, and updates counters asynchronously. Signals combine into a score; the action ladder is `monitor` (event only), `challenge`, `block` (429 or 403), and `ban` only for high-confidence classes such as credential stuffing past its thresholds. Actions that depend on Phase C apply to subsequent requests, so takeover handling (success after many failures) is detect-and-notify with a challenge on the next attempt from that identity, not prevention. Clearance cookies relax limits, verified bots and allowlisted addresses bypass flow signals, and every event lists the signals and values that fired so a human can verify the decision. **Simulate** replays recent events against a definition before it leaves `monitor`.

### C19.5 Coverage map and the "does not cover" list

`design/coverage/*.toml` is the source of truth; `cargo xtask coverage` generates `docs/COVERAGE.md`, the data behind S-134 and `GET /public/coverage`. Each item:

```toml
[[item]]
standard  = "owasp-top10-2021"
id        = "A03"
title     = "Injection"
status    = "covered"            # covered | partial | signal_only | not_covered
mechanism = "Hard and soft signatures, structural tokenizers, positive-security hints"
atk       = ["AG-01", "AG-02"]
ac        = ["AC-06", "AC-07", "AC-09", "AC-38", "AC-39"]
tasks     = ["T-0263", "T-0283", "T-0499"]
limits    = "Novel techniques can evade signature-based detection."
```

**Status definitions.** `covered` = a detector is tested on held-out data with published detection and false-positive rates, the latest run has PASS evidence, and the limits name no structural blind spot for the main attack path. `partial` = part of the category is handled, or the lab proof is limited to inert interpreters, or detection depends on application behavior HDD cannot see. `signal_only` = a signal or monitor-mode event without a prevention claim. `not_covered` = outside what HDD can see or do.

`cargo xtask coverage check` fails the build when: a standard category from E15 is missing; a `covered` or `partial` item lacks an ATK group with fixtures, an AC and a task; a `not_covered` item lacks `limits`; a referenced ID does not exist; or claims-lint finds a forbidden phrase in any text field. The generated page shows the date and commit it was built from.

**What HDD does not cover (always shown, never collapsed):** flaws in the application's own business logic that look like valid use; vulnerabilities in client-side code that never cross HDD; zero-day techniques with no signature, structure or behavior signal; volumetric floods larger than the server uplink without an upstream provider; a compromised origin, credentials or CI pipeline; insider misuse; vulnerabilities in services that bypass HDD (a directly reachable origin); malicious content inside encrypted or opaque binary protocols HDD does not parse; and anything outside the HTTP, DNS and TLS paths HDD terminates.
