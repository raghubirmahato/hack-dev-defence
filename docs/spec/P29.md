## PHASE P29: Performance, chaos, fuzz and supply chain (T-0511 to T-0520) · milestone M11 · gate G29

Requirement prefix `PRF`. Goal: prove the system is fast enough, survives faults, resists malformed input at scale, and ships from a trustworthy build pipeline: HTTP performance measurement (AC-24), soak and capacity, automated chaos, the consolidated fuzzing program, mutation and coverage gates, dependency and supply-chain controls (AC-33), unsafe-code policy enforcement, signed releases and self-update, and a structured security review of HDD itself.

Non-negotiables: performance numbers are measured and labeled by environment (lab, pilot VPS) and never extrapolated to internet scale; load runs against live infrastructure happen only in operator-announced windows on the pilot with the `load` profile; fuzzing never runs on the production VPS; supply-chain exceptions have owners and expiry; an unsigned or tampered artifact can never be installed; every security-relevant finding is tracked to closure or explicit risk acceptance.

Gate G29 passes when: AC-24 numbers meet the budgets (or documented deviations exist with tracked tasks); soak runs show no leaks; chaos scenarios keep invariants (no fail-open in `block` mode); fuzz smoke is clean and the nightly campaign has no open crash; mutation and coverage gates pass; AC-33 passes (signed update with rollback exercised); and the self-security review has no open high finding.

### T-0511 · Performance measurement suite and budgets (AC-24)
`P29` `[QA][DP]` · deps: T-0372, T-0400, T-0470 · size: L · owner: perf
**Objective.** Measure latency, throughput and resource use of the real data plane with a repeatable method, so every performance statement cites AC-24.
**Steps.**
1. Define the **methodology** in `docs/PERFORMANCE.md`: hardware description captured automatically (CPU model, cores, RAM, kernel, NIC, virtualization), warm-up rules, steady-state windows (≥ 120 s), open-loop load generation (constant arrival rate to avoid coordinated omission), HDR histograms for latency, multiple runs with variance reporting (≥ 5 runs, median and range), and a statement that numbers are valid only for the recorded environment.
2. Extend `hdd-loadgen http` with scenarios: static GET pass-through, mixed GET/POST bodies (1 KB/64 KB/1 MB), HTTP/1.1 keep-alive and h2 multiplexing (100 concurrent streams), TLS handshakes per second (full and resumed), WebSocket idle connections (10k), blocked traffic (WAF verdict block, ban hits through the L7 jail), challenge issuance, large response streaming, and outbound-filter-on text responses; each against a local origin stub that is a real HTTP server with deterministic behavior (lab and builder only; on the pilot the canary files are the origin).
3. Measure and record **proxy-added latency** (time inside HDD excluding origin) at p50/p95/p99/p99.9 using server-side histograms, plus end-to-end client latency; budget: p99 ≤ 5 ms added at the functional load (2,000 rps) and p99 ≤ 15 ms at 80% of the measured saturation point; inspection p50 < 1 ms.
4. Measure **throughput and saturation**: max sustainable rps per core for pass-through and for full-inspection `block` mode, CPU utilization per mode, memory (RSS) per 10,000 idle connections (documented), allocation per request in steady state (counting allocator: zero heap growth), p99 degradation curves, behavior at overload (shed policy, 503 rate, recovery time).
5. Measure **per-feature cost**: marginal latency of each pipeline stage (histograms from T-0372), SQLi tokenizer on worst-case inputs, body inspection costs by size (1 KB to 8 MiB), outbound scan cost, challenge verification cost, ban lookup cost with 100k entries, and the cost of snapshot swaps on live traffic (latency spike ≤ 5 ms).
6. Run on three environments and report them separately: builder (developer-grade), lab machine (if supplied), and the pilot VPS (in an announced window with the `load` profile and operator approval; UNVERIFIED(`skipped_by_operator`) otherwise).
7. Add a **regression gate**: baselines stored in `tests/baselines/perf-<env>.json`; `xtask bench http --compare` fails when p99 added latency or throughput regresses by more than 10% without an approved baseline update (reviewed in the PR, recorded in `docs/DEVIATIONS.md` if a budget changes).
8. Publish the results: tables, charts (SVG with table alternatives) in `docs/PERFORMANCE.md` and the S-127 capacity panel's "lab-proven" figures; ensure marketing and docs cite only these numbers (claims-lint pattern `perf_claim`).
**Deliverables.**
- loadgen scenarios, methodology doc, baselines, regression gate, results
**Acceptance.**
- A1: budgets are met in the builder and lab environments, or deviations are documented with tracked tasks.
- A2: no per-request heap growth in steady state (counting allocator test).
- A3: the regression gate fails on a seeded 15% regression in a test branch.
- A4: all published numbers carry environment tags and variance.
- A5: pilot VPS measurement is performed (with approval) or marked UNVERIFIED with reason.
**Tests.**
- The benchmarks themselves; unit tests for histogram math and comparison logic.
**Notes.** Coordinated omission is avoided by open-loop arrival scheduling.

### T-0512 · Soak, capacity model and resource-leak detection
`P29` `[QA][OPS]` · deps: T-0511, T-0214 · size: M · owner: perf
**Objective.** Show that the system runs for days without degradation and describe how much load a given machine can take.
**Steps.**
1. Define soak scenarios (lab and pilot): 24 h and 72 h at 30% of measured saturation with a realistic mix (95% benign, 4% scanners and bots, 1% hard attack payloads from a rotating lab source pool, config changes every 15 minutes, certificate renewals via short-lived staging certs, daily rollup and retention jobs).
2. Collect time series every 10 s: RSS and heap by service, open file descriptors, threads, sockets by state, goroutine-equivalent task counts (tokio metrics), event queue depth, Redis memory and key counts, Postgres connections/locks/bloat/WAL, disk usage, ban-set sizes (L7, Redis, kernel), conntrack counts, latency percentiles and error rates.
3. Define leak criteria: linear regression on steady-state windows; RSS growth ≤ 2% over 24 h after warm-up, fd and socket counts flat (±5%), task counts flat, queue depths bounded, disk growth explained by retention policy; alert thresholds validated by injecting a deliberate leak into a test build (the detector must flag it within 6 h).
4. Verify **retention and housekeeping** under soak: partition creation/drop, rollups, log rotation, cache expiry, ban expiry, session cleanup, webhook delivery pruning; confirm no table or index bloat beyond thresholds (autovacuum behavior documented, settings tuned).
5. Build the **capacity model**: from the measured saturation and per-feature costs derive rps-per-core, connections-per-GB, DNS qps-per-core, ban-set capacity, event ingestion limits, and recommended VPS sizing tiers (S/M/L) with caveats; publish as `docs/CAPACITY.md` (lab-derived, explicitly not a guarantee) and surface in the S-127 capacity panel as "lab-proven".
6. Test **graceful degradation** at 120–200% of saturation: shed policy, priority of ban enforcement and health endpoints, recovery time after load drops, no cascading failures (Redis/Postgres connection storms).
7. Run **cert/ACME and config churn** during the soak and ensure hot reloads cause no errors (error rate delta < 0.01%).
8. Write the automated soak harness with a final report (graphs with table alternatives), plus a shortened 1-hour variant for CI nightly.
**Deliverables.**
- soak harness, reports, capacity model doc, nightly short soak
**Acceptance.**
- A1: no leak criteria violated in the 24 h run (and 72 h run before release).
- A2: the leak detector flags the seeded leak.
- A3: retention jobs keep storage within predicted bounds.
- A4: graceful degradation keeps ban enforcement and health endpoints responsive at 200% load.
- A5: capacity model values are traceable to measurements.
**Tests.**
- Soak runs and the CI short variant.
**Notes.** 72 h soak is a release-gate item executed once near M12.

- A3: detection and alert times are within documented targets for each experiment.
- A4: abort conditions work (seeded test).

**Tests.**

4. 6. Add **structure-aware protocol fuzzers**: HTTP/2 frame sequences (state machine fuzz for rapid reset, continuation floods, settings floods) against the real listener in the lab, with process health assertions.
7. Provide a quarterly **fuzz health report**: executions, new coverage, crashes found/fixed, stale targets (no new coverage in 30 days → corpus or harness improvement task).
8. Ensure all fuzz targets build in CI (`cargo fuzz build`) so they do not rot, and document how operators can run them.
**Deliverables.**
- target inventory, automation, triage workflow, differential fuzzers, reports
**Acceptance.**
- A1: every parser in the inventory has a fuzz target that builds in CI and runs in the nightly.
- A2: CI smoke completes with zero crashes; nightly campaigns have no open crash older than the SLA.
- A3: each fixed crash has a regression test committed.
- A4: differential fuzzers produce reports with all disagreements triaged.
- A5: coverage growth is tracked (report generated).
**Tests.**
- Campaigns themselves; unit tests for triage tooling.
**Notes.** Fuzzing on the production VPS is forbidden (C12.6).

### T-0518 · Release signing, artifact pipeline and signed self-update with rollback (AC-33, part 2)

**Acceptance.**
- A1: all tamper cases are rejected and leave the system on the old version.
- A2: injected failures at each upgrade step roll back to a healthy state.
- A3: `xtask release` refuses to produce artifacts when any release gate is red.

**Tests.**
