## PHASE P05: Public website, docs and status (T-0095 to T-0104) · milestone M3 · gate G05

Requirement prefix `PUB`. Goal: the honest, fast, accessible public surface: landing, features, how protection works (with limits), docs, API reference, status, legal, contact and disclosure. It works with JavaScript disabled, sets only essential cookies, loads no third-party resources, and publishes nothing that depends on operator-owned text until supplied.

Gate G05 passes when: every public page passes axe (zero serious/critical), keyboard, reflow and performance checks and works with JavaScript disabled; the network trap sees no third-party requests; only essential cookies are set; claims-lint, docs check, link check and i18n check pass; the evidence-driven claims display correctly with and without evidence; the legal guard and signup gating behave when legal text is unresolved; and the gate report lists every UNVERIFIED item (screen-reader checks, operator legal text, external status hosting).

### T-0097 · Documentation engine: Markdown rendering, sanitization, TOC and search
`P05` `[UI][SEC]` · deps: T-0074 · size: L · owner: docs
**Objective.** Render the documentation from Markdown safely, with navigation and search.
**Steps.**
1. Vet and select `pulldown-cmark` (or equivalent) and `ammonia` (sanitizer) with an ADR; define the allowed element/attribute/URL-scheme policy (no scripts, no iframes, no raw HTML pass-through except an allowlist of `details`, `kbd`, callout classes; images only from the docs asset directory).
2. Implement front-matter parsing (title key, summary, order, audience, last reviewed date, related), heading anchors with stable slugs, automatic TOC, callouts (`note`, `warning`, `limit`), tabs for per-provider instructions implemented as accessible sections (no JS requirement), and code blocks with copy buttons and language labels.
3. Implement the docs router with prev/next, breadcrumbs, "Edit on" link only if configured, and last reviewed badge with stale warning after 180 days.
4. Implement the search index at build time (inverted index with stemming rules for English, ADR on custom vs `tantivy`), served by a bounded in-memory structure and a `GET /docs/search?q=` endpoint with result highlighting by escaped markup; rate-limited; no logging of queries beyond aggregate counters.
5. Implement link checking (internal anchors and relative links) in `xtask docs check`; external links are listed but not fetched.
6. Implement the glossary tooltips linked to glossary entries (progressive).
7. Add the `include` mechanism to reuse generated snippets (error catalog, permission matrix, config table, metrics) so docs never drift.
8. Fuzz the Markdown pipeline with hostile inputs.
**Deliverables.**
- `crates/hdd-web/src/docs/*`, `docs/site/` structure, search index builder, ADR
**Acceptance.**
- A1: raw `<script>`, `javascript:` links, `onerror`, SVG scripts and iframes in Markdown are neutralized (fixture suite).
- A2: broken internal links fail `xtask docs check`.
- A3: search returns relevant results for 20 reference queries and never executes injected markup in result snippets.
- A4: the generated error catalog and permission matrix pages match their sources (tests).
- A5: stale pages display the warning after 180 days.
**Tests.**
- Unit: sanitizer policy tables; proptest on slug generation (unique, stable); fuzz target on Markdown rendering.
- Browser: docs navigation, search keyboard flow, copy buttons.
**Notes.** The same sanitizer policy is reused for any user-supplied Markdown later (none in Tier 1).

### T-0100 · Status page (S-008) with real probes
`P05` `[UI][OPS]` · deps: T-0095 · size: L · owner: ops
**Objective.** Show real service status, independent of the services it reports on.
**Steps.**
1. Implement the prober in `hdd-worker`: black-box checks of public endpoints (DNS answers for a probe zone, TLS handshake and HTTP 200 for the canary hostname, app login page, API health) at 60 s intervals from the VPS and, when configured, from `vantage_points`; store results in a small time-series table.
2. Implement the status model: components, current state (operational, degraded, outage, unknown), 90-day uptime bars computed from probes (unknown periods are shown as unknown), and incident posts authored by platform admins (title, timeline updates, resolved time).
3. Implement the public page (S-008) with an accessible table equivalent of the uptime bars and RSS/Atom feed.
4. Implement the **external hosting guidance**: because a status page on the same VPS fails when the VPS fails, support publishing a static snapshot to an operator-supplied location (object storage or a static host) through a configured egress destination, and the `HDD_STATUS_FEED_URL` to link the external page.
5. Implement the heartbeat sender (when configured) so an external monitor detects a dead platform.
6. Implement incident subscriptions by email (double opt-in, rate-limited) as an optional feature disabled by default.
7. Implement safeguards: probes never target third parties; probe traffic is labeled with a user agent and excluded from analytics.
8. Document how to interpret unknown states.
**Deliverables.**
- prober, status tables (migration `[DB]`), page, feed, static snapshot publisher, docs
**Acceptance.**
- A1: stopping the DNS service makes the DNS component degrade within two probe intervals (resilience test).
- A2: periods with no probe data display as unknown, never as operational.
- A3: the static snapshot contains no internal hostnames.
- A4: incident posts are authenticated (admin permission) and audited.
- A5: the RSS/Atom feed validates.
**Tests.**
- Integration: prober against local services with injected failures; unit: uptime computation with gaps; feed validation.
**Notes.** Status data is public by design; keep fields minimal.
