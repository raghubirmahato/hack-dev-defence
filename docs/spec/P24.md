## PHASE P24: Notifications, integrations, public API and SDK (T-0453 to T-0462) · milestone M9 · gate G24

Requirement prefix `NTF`. Goal: make HDD tell people what matters, where they already work, and make everything scriptable: the alert-rule engine and routing, integration channels, a reliable webhook delivery engine with signing, the complete public API v1 with governance, a Rust SDK and generated clients, developer documentation, and log forwarding to SIEM tools.

Non-negotiables: alerts are deduplicated and rate limited so an attack cannot flood owners' channels (alert-flood control is a security feature); every outbound call uses the central egress client with the SSRF guard; secrets for channels are write-only and encrypted; webhook payloads and notifications never contain request bodies, cookies, credentials or full IPs beyond the org's truncation setting; the public API is versioned with a deprecation policy, and the OpenAPI document is the single source of truth for the API reference, SDK and contract tests.

Gate G24 passes when: alert rules route correctly with dedupe, quiet hours and escalation; all channel integrations pass contract tests against local fakes (and live smoke tests where the operator supplied test destinations); webhooks are signed, retried and idempotent; the API contract tests and breaking-change detector pass; the SDK passes its integration tests; and AC-45 passes.

### T-0453 · Alert rules (S-076) and notification routing core
`P24` `[API][DB][UI]` · deps: T-0141, T-0368, T-0441 · size: XL · owner: api
**Objective.** Turn platform events into the right notifications with controlled volume.
**Steps.**
1. Define the **trigger catalog** (each with a stable key, default severity, parameters and the event source): `sqli_hard_hit_auth_endpoint`, `possible_auth_bypass` (V13), `data_leak_detected`, `exposure_detected`, `mass_ban` / `ban_spike`, `campaign_detected`, `never_ban_attack_attempt`, `global_jail_promoted`, `rate_limit_spike`, `challenge_failure_spike`, `origin_down` / `origin_degraded`, `certificate_expiring`, `certificate_issue_failed`, `dns_secondary_lag`, `domain_verification_failed`, `readiness_score_drop`, `rule_pack_rollback`, `safe_mode_enabled`, `appeal_received`, `member_added`/`role_changed`, `api_key_created`, `login_anomaly`, `shield_state_change`, `vuln_sla_overdue`, `virtual_patch_expiring`, `report_failed`, `backup_stale` (platform).
2. Implement the **rule model**: scope (org/domain/all domains), trigger, parameters (threshold, window, minimum severity, category filter), channels (list), schedule (always, business hours, custom), quiet hours with critical override, grouping key, cooldown, and escalation policy (if not acknowledged in X minutes, notify an escalation channel). System-default rules are seeded per org on creation (conservative set, editable, deletable with warnings) so a new org has alerts without configuration.
3. Implement the **routing pipeline** in `hdd-notify`: consumes domain events from the outbox, evaluates rules (windowed counting using Redis with a database fallback), creates durable notifications (S-075) and enqueues channel deliveries; delivery records are idempotent per (rule, event group, channel).
4. Implement **flood control**: per-rule cooldown, per-channel rate caps (default 10/h for chat channels, 60/h for email), grouping ("12 SQLi attempts from 3 IPs in 5 minutes" as one notification with a count that updates until the group closes), digest mode when caps are hit with a final "N more events suppressed" message, and a global per-org cap with an alert to the owner by email that suppression occurred.
5. Implement acknowledgment and snooze: acknowledge via UI/API/button links in messages (signed single-use links with expiry), snooze a rule or trigger for N hours with a reason, escalate on no acknowledgment, and mark resolved when the source condition clears (for state-based triggers).
6. Build S-076: rule list with search and status, rule editor with plain-language preview ("When 5 or more hard SQL injection attempts hit your login endpoints within 10 minutes, email Alex and post to #security"), threshold sanity hints, a **test event** button that generates a synthetic notification clearly labeled "Test", and a channel health indicator (last success/failure).
7. Respect user preferences (S-087): per-user notification channels and per-severity opt-outs, with enforced minimums for security-critical account notifications.
8. Implement the API (`/alert-rules`, `/notifications`, `POST /notifications/{id}:ack`), permissions (`PERM-alertrule.write`, `PERM-notify.read`), audit events, and metrics (notifications created, suppressed, delivered, failed by channel).
9. Write tests: trigger evaluation with time-injected windows, grouping and cooldown properties, flood simulation (10,000 events → bounded notifications), quiet hours and critical override, escalation flows, idempotency under retries and crashes, RLS/BOLA, and UI e2e for the editor.
**Deliverables.**
- trigger catalog, rule engine, routing, S-076, API, tests, docs `docs/ALERTS.md`
**Acceptance.**
- A1: a simulated SQLi campaign of 10,000 events produces a bounded number of notifications per channel (caps respected) with the suppression summary.
- A2: seeded default rules exist for a new org and can be edited or removed.
- A3: escalation triggers exactly once when unacknowledged and stops upon acknowledgment.
- A4: notification creation is idempotent across worker restarts (crash test).
- A5: the editor preview text matches the evaluated behavior (golden tests).
**Tests.**
- Unit, property, integration with Redis/Postgres, browser e2e.
**Notes.** Message content rules are enforced here (no sensitive data) and re-verified by T-0454.

### T-0455 · Webhook delivery engine: outbox, retries, circuit breaker and idempotency
`P24` `[API][DB][SEC][DP]` · deps: T-0453, T-0413, T-0109 · size: L · owner: api
**Objective.** Deliver customer webhooks reliably with at-least-once semantics and strict outbound safety.
**Steps.**
1. Define the event envelope: `{id, type, api_version, created_at, org_id, domain_id?, data{...}}` with documented event types (alert-aligned plus `domain.state_changed`, `certificate.issued`, `ban.created`, `ban.removed`, `appeal.created`, `report.generated`, `rule.changed`, `readiness.changed`); the `data` object follows versioned JSON schemas published in OpenAPI.
2. Implement the **outbox pattern**: events are written transactionally with the originating change (`webhook_outbox`), fanned out to subscribed endpoints as `webhook_deliveries` rows (partitioned monthly) with state (`pending|inflight|succeeded|failed|dead`), attempt counters and next-attempt time; workers claim rows with `FOR UPDATE SKIP LOCKED`.
3. Implement delivery: HTTPS only (HTTP only when the owner explicitly acknowledges risk for private test endpoints in `owner_only` mode), egress client with SSRF guard and no redirects, timeout 10 s, response body read capped to 8 KiB and stored truncated and redacted (first 1 KiB displayed), headers `Content-Type: application/json`, `User-Agent: HackDevDefence-Webhooks/1`, `HDD-Event-Id`, `HDD-Event-Type`, `HDD-Delivery-Id`, `HDD-Signature` (T-0456), `Idempotency-Key` equal to the event id.
4. Implement the retry schedule: success on 2xx; retry on network errors, 408, 429 (honor `Retry-After`), 5xx with exponential backoff and jitter (1 m, 5 m, 30 m, 2 h, 6 h, 12 h, 24 h, 24 h = 8 attempts over ~3 days), `dead` afterwards with a notification; 410 Gone disables the endpoint immediately; 3xx counts as failure with a hint to update the URL.
5. Implement ordering and concurrency semantics (documented): at-least-once, no global ordering guarantee, per-endpoint concurrency 4, per-event ordering hints via `created_at` and `sequence` per resource; consumers must dedupe by event id.
6. Implement the **circuit breaker**: after 100 consecutive failures or 48 h of failures the endpoint is auto-disabled with an owner notification; re-enable requires a manual test success; backlog is retained for 3 days then expired with a summary notification.
7. Implement rate protections: per-endpoint max 20 deliveries/s; global worker concurrency caps; poison payload handling (payloads > 256 KiB are replaced by a pointer event `data_url` that requires authentication); and tenant fairness (one tenant's backlog cannot starve others: weighted fair queue per org).
8. Implement replay and redelivery APIs (`POST /webhooks/{id}/deliveries/{did}:redeliver`, bulk redelivery for a time range with a cap), preserving the original event id and incrementing a `redelivery` header.
9. Write tests: crash recovery (kill worker mid-delivery → no loss, possible duplicate), exactly-once enqueue (transactional outbox with fault injection), retry timing with injected clock, circuit breaker, fairness simulation (noisy tenant with 1M queued deliveries does not delay others by more than 5 s), SSRF vectors (≥ 60), redirect refusal, large payload pointer behavior, and performance (1,000 deliveries/s on the lab machine to a local sink).
**Deliverables.**
- outbox, delivery workers, schemas, tests, docs `docs/WEBHOOKS.md`
**Acceptance.**
- A1: no event is lost when workers crash at any point in the delivery state machine (fault-injection matrix).
- A2: retries follow the documented schedule within jitter bounds (injected clock tests).
- A3: SSRF vectors and redirects are never followed or connected to.
- A4: a noisy tenant does not delay others beyond 5 s in the fairness simulation.
- A5: dead and expired deliveries notify owners exactly once.
**Tests.**
- Integration with fault injection, simulation, security tests, performance.
**Notes.** Delivery history retention is 90 days (partition drop).

### T-0456 · Webhook endpoints, signing secrets and delivery inspector (S-078, S-079)
`P24` `[UI][API][SEC]` · deps: T-0455, T-0124 · size: M · owner: web
**Objective.** Let owners manage endpoints and verify authenticity with a clear signing scheme.
**Steps.**
1. Implement endpoint CRUD (`/webhooks`): URL (validated: https, allowed ports 443/8443 plus operator-configurable, no userinfo, host passes the SSRF guard at save time and at each delivery), description, subscribed event types (multi-select with search, `*` allowed with a warning), enabled flag, org-level or domain-scoped, custom headers (allowlist of header names, values encrypted, max 5), API version pin.
2. Implement **signing**: per-endpoint signing secret (32 random bytes, base64url, prefix `whsec_`), shown once at creation and on rotation; signature header `HDD-Signature: t=<unix>,v1=<hex(HMAC-SHA256(secret, t + "." + raw_body))>` with a 5-minute recommended tolerance; support for multiple `v1` values during rotation (dual signing for 24 h by default); secrets are separate from API keys and stored with envelope encryption.
3. Implement **rotation**: "Rotate secret" creates a new secret, keeps the old valid for the overlap window (configurable 1 h–7 d), shows a countdown, and sends both signatures; after the window the old secret is deleted; audit events for creation/rotation (never the secret).
4. Build S-078: endpoint list with health (last success, failure streak, circuit state), editor with the verification snippets panel (curl, Node, Python, Go, Rust, PHP, Ruby, Java) generated from tested templates, a **Send test event** button (signed, labeled `test.ping`), and a "Pause deliveries" switch.

Build S-079 (delivery inspector): table of attempts (time, event type, status, latency, attempt number), filters, detail drawer with request headers (signature masked), payload (redacted for sensitive fields per schema), response status and excerpt (≤ 1 KiB, escaped), error classification, and actions (redeliver single/bulk with caps).
6. Implement a **local verifier tool**: the page includes an in-browser verifier (paste payload, signature header and secret; verification runs client-side only, secret never sent to the server; island JS with CSP-safe code) to help integrators debug signatures.
7. Implement guard rails: warning when the endpoint domain resolves to a private range (blocked), when TLS certificate verification fails (shown as a delivery error, never disabled), and when the endpoint returns 3xx.
8. Write tests: signature vectors (published in docs with expected outputs, reproduced by each language snippet in CI where runtimes are available), dual-signature rotation timeline, tamper tests (body modified → verify fails), timestamp tolerance edges, secret one-time display, BOLA on endpoints/deliveries, XSS in descriptions and response excerpts, and a11y for the inspector tables and drawers.
**Deliverables.**
- S-078/S-079, signing library (`hdd-common::webhook_sig`), verification snippets, tests
**Acceptance.**
- A1: every language snippet verifies the documented test vectors (CI where the runtime exists; otherwise UNVERIFIED(`tool_unavailable`) for that language only).
- A2: rotation overlap sends two valid signatures and the old one stops after the window.
- A3: the client-side verifier never transmits the secret (network log assertion).
- A4: secrets are shown exactly once and never retrievable via API.
- A5: response excerpts and descriptions render inert (XSS corpus).
**Tests.**
- Unit vectors, integration, browser e2e, security.
**Notes.** Webhook signing secrets are distinct from API keys (T-0124 note).

### T-0457 · Public API v1: completeness, governance, contract tests and breaking-change detection
`P24` `[API][DOC][QA]` · deps: T-0124, T-0125, T-0453, T-0455 · size: XL · owner: api
**Objective.** Make the API a stable product: every UI action available, consistent, documented and guarded against accidental breakage.
**Steps.**
1. Audit the API catalog (B6) against the screens: for every action in the UI there is an endpoint with the same permission, and for every endpoint there is a documented use; produce `docs/API-COVERAGE.md` generated by `xtask api-coverage` (fails on gaps).
2. Standardize conventions and verify them with a conformance linter over the OpenAPI document: resource naming, `snake_case` JSON, RFC 3339 timestamps (UTC with `Z`), cursor pagination (`limit`, `cursor`, `next_cursor`), consistent filtering syntax, `If-Match`/ETag for updates, `Idempotency-Key` for `POST` creation endpoints (24 h storage, replay returns the original response with `Idempotent-Replay: true`), RFC 9457 problem details with `ERR-*` codes, `Request-Id` header equal to the Ray ID format for API calls, field-level permissions (response shaping by role), and bulk endpoint limits.
3. Implement **rate limiting** for the API: per API key and per IP with headers (`RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`, `Retry-After`), plan-based limits, burst allowance, separate stricter limits for expensive endpoints (exports, rollups, inspect API), and clear `ERR-RATE-001` problem responses.
4. Implement API key scope enforcement end to end: scopes are permission IDs; keys can be restricted by IP/CIDR and expiry; usage metrics per key; the key can never exceed the creator's current permissions (evaluated on each call); a negative test suite covers every endpoint × a key lacking the scope.
5. Implement **versioning and deprecation policy**: `/api/v1` is stable; additive changes only; breaking changes require `/api/v2`; deprecated endpoints/fields carry `Deprecation` and `Sunset` headers plus OpenAPI `deprecated: true`, announced in the changelog and via in-app notices to key owners (`api_deprecation` notifications) at least 180 days before removal.
6. Build the **contract-test harness** (`hdd-acceptance::api`): property-based tests derived from OpenAPI (valid, boundary and invalid inputs) run against a live local stack; responses are validated against schemas; unknown-field handling (`additionalProperties: false` on requests) is tested; authorization tests for each role × endpoint × BOLA variant.
7. Implement the **breaking-change detector** (`xtask api-diff <old> <new>`): compares OpenAPI documents (removed endpoints/fields, narrowed enums, required-field additions, type changes, response code changes) and fails CI unless the change is classified compatible; baseline stored at each release tag.
8. Implement security tests specific to the API: mass assignment (extra fields ignored/rejected), content-type enforcement, large body caps, deep JSON nesting limits, integer overflow bounds, injection in filters (SQLi through filter parameters tested against the control plane's own storage layer), SSRF through URL fields, CORS (closed by default; opt-in allowlist for the browser SDK use case), and error message hygiene (no stack traces).
9. Generate `openapi.json` and `openapi.yaml` artifacts at build; serve them at `api.<platform_domain>/openapi.json` (public, cached) and publish the changelog at `/docs/api/changelog`.
**Deliverables.**
- conformance linter, rate limiter, idempotency layer, contract-test harness, `xtask api-coverage|api-diff`, docs
**Acceptance.**
- A1: `api-coverage` reports zero UI actions without an endpoint.
- A2: contract tests pass for 100% of endpoints with generated cases (≥ 20 cases per endpoint on average).
- A3: removing a response field in a test branch makes `api-diff` fail CI.
- A4: idempotent replay returns the identical response for the same key and rejects a mismatched payload with `ERR-IDEMP-001`.
- A5: every endpoint has at least one negative authorization test.
**Tests.**
- Contract/property, integration, security, CI diff tests.
**Notes.** The inspect API (`POST /waf/inspect`) has its own tighter limits and is labeled dry-run only.
