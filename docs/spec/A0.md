## 0. How to read and apply this specification

### 0.1 Loading strategy (this file is too large to hold in context)

This document is roughly 24,900 lines. Never try to hold all of it. The very first action of the first session is:

1. Save this file **verbatim** to `docs/SPEC.md` (git-tracked) and record its sha256 in `docs/SPEC.sha256`.
2. Split it once with a one-off bootstrap command (the only permitted non-Rust, non-`install.sh` script, recorded as `DEV-V5-000` in `docs/DEVIATIONS.md`, removed after T-0005 replaces it with `cargo xtask spec split`). The split cuts at the markers `<!-- PART:<id> -->` and `<!-- PHASE:<id> -->` into `docs/spec/<id>.md` and writes `docs/spec/INDEX.md` mapping every `T-nnnn` to its file and line.
3. From then on each session reads, in this order: `AGENTS.md` (digest, at most 150 lines), `STATUS.md`, `HANDOFF.md`, `git status`, then **this Part A, section 0 only** (once per session), then the phase file that holds the task in hand, then any registry rows the task references (grep by ID: `S-nnn` screens, `J-nn` journeys, `ATK-nnn` attack classes, `AC-nn` checks, `ERR-` codes, `MET-` metrics, `AUD-` audit events, `PERM-` permissions).
4. Never rely on chat memory. If a fact matters in a later session, it is in `STATUS.md`, `HANDOFF.md`, an ADR, `docs/DEVIATIONS.md`, or the capability matrix.

### 0.2 Priority when requirements conflict (highest first)

1. Section 2 safety envelope (Part A, file `01-constitution`).
2. Honesty and claims rules (rules R-02, R-10, R-11 and the claims policy).
3. Part C hardening baseline and the security doctrines (SQLi doctrine, vulnerable-origin shield, ban policy).
4. Numbered requirements and acceptance checks (`AC-nn`).
5. Tasks (`T-nnnn`) and phases.
6. Backlog (P32).

Within one level take the safer option, record it in `docs/DEVIATIONS.md`, and ask the operator only if it blocks the current gate.

### 0.3 Roles

| Role | Meaning |
| --- | --- |
| Builder | Machine where the agent compiles, runs unit tests, runs the headless browser for UI tests. |
| VPS | Machine that runs HDD in the pilot (data plane: proxy, DNS, firewall agent, shield) and, in single-node mode, the control plane too. |
| Runner | Machine that runs the live acceptance suite over the real internet path. Never the VPS. |
| Lab | A closed machine or Linux network-namespace pair for L3/L4 floods and for the Vuln-Lab (intentionally vulnerable test applications). Never the VPS, never reachable from the internet. |
| Origin | The operator's real site host. |
| Operator | The human who owns the domains, the VPS and the approvals ("me" in v4.1). |
| Local host | The personal computer that runs HDD in the `local` runtime profile (C18). It is never the runner or the lab for destructive tests, and it may be a Windows, macOS or Linux machine without Docker. |
| Tenant | A customer organization in `saas` deployment mode. In `owner_only` mode there is exactly one tenant: the operator. |
| Platform admin | A human with a platform role (Part B, section B4) operating the HDD installation itself. |

A builder may be any supported operating system (Track H: Linux with Docker; Track L: Windows, macOS or Linux using the embedded database, section 9). One machine may hold several roles, except that the runner and the lab are never the VPS, and release binaries are not compiled on the VPS (record target triple and libc in an ADR).

### 0.4 Status taxonomy (unchanged from v4.1)

Every check ends as **PASS**, **FAIL**, or **UNVERIFIED(reason)** with reason one of `capability_not_supplied`, `human_step_pending`, `environment_unsupported`, `stage_not_reached`. Anything else is FAIL. UNVERIFIED is never a way to avoid a failing check, and each UNVERIFIED lists what the operator must supply.

### 0.5 Decision authority

The agent **may decide**: crate choices inside the Part A stack (with an ADR), internal APIs, UI details inside the approved design system, thresholds stricter than Appendix E4, copy wording that passes claims-lint, and ordering of tasks whose dependencies are met.

The agent **must ask the operator** before: loosening any Appendix E4 value or any safety-envelope limit, adding an egress destination, any human-gated step, production ACME issuance, apex cutover, a `load` run, any provider-side test, enabling open signup on a public installation, sending any email to a real address other than the operator's, and changing the brand name, legal text or pricing.

Ask in one batched message and only when blocked. Questions that affect later phases go into the Open questions list in `STATUS.md` (seeded from Appendix E8).

### 0.6 Task lifecycle and per-task protocol

Task states recorded in `STATUS.md`: `todo`, `designing`, `red` (failing tests written), `green`, `verified` (`cargo xtask verify` and the task's live checks pass), `accepted` (gate evidence pasted), `done`, `blocked(<reason>)`, `deferred(<reason>, <effort estimate>)`.

For every task, in order:

1. Read the task block and every registry row it references. Copy its acceptance criteria into `STATUS.md` before coding.
2. Decide the tests first: unit, property, integration (real local services), browser e2e, lab, live. Write them failing (`red`) and commit.
3. Implement the minimum that satisfies the acceptance criteria. Reuse; do not duplicate.
4. Run `cargo xtask verify` (and `cargo xtask ui verify` for tasks tagged `[UI]`). Fix at the root cause (failure budget, rule R-14).
5. Run the live or lab checks the task names. Record PASS/FAIL/UNVERIFIED with evidence (output tail plus sha256 of the full log).
6. Apply the global definition of done for the task's tags (section 0.7).
7. Update `ARCHITECTURE.md` (module owner), `OPERATIONS.md` (settings), `docs/CAPABILITY-MATRIX.md`, `STATUS.md`.
8. Hostile self-review of the diff (checklist in Appendix E6). Fix findings before moving on.
9. Commit with a Conventional Commit message that ends with a `Task: T-nnnn` trailer. Never force-push. Never commit secrets (pre-commit scan).

If context is running low, write a precise `HANDOFF.md` (phase, failing tests, next 10 tasks, decisions, open questions) so a new session resumes without loss.

### 0.7 Global definition of done by task tag

Every task block carries tags. Each tag adds the following checklist. A task is not `done` until every checklist item of every tag is satisfied or explicitly marked not applicable with a reason in the commit body.

| Tag | Meaning | Added checklist |
| --- | --- | --- |
| `[UI]` | Renders HTML to a human | Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note. |
| `[API]` | Adds or changes an HTTP endpoint | OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document. |
| `[DB]` | Adds or changes schema | Expand/contract migration only; `org_id` and RLS policy for tenant-owned tables; indexes justified; `sqlx` offline data refreshed; forward migration plus restore-from-backup test; data-retention rule documented. |
| `[SEC]` | Security-relevant logic | Abuse cases written as tests; STRIDE delta in `docs/STRIDE.md`; no secret in logs; constant-time comparison where secrets are compared; failure modes fail closed; panic-free on hostile input (proptest or fuzz target). |
| `[DP]` | On the data-plane hot path (proxy, DNS, WAF, firewall) | Hot path never awaits the database; bounded memory and queues; criterion benchmark or histogram; fuzz or proptest; behavior when Redis or Postgres is down specified and tested; metric with drop counter. |
| `[OPS]` | Deployment, operations, runbooks | Idempotent; dry-run mode; documented undo; SSH-lockout protection for host-affecting changes; restore or rollback exercised. |
| `[DOC]` | Documentation | Every claim backed by a test ID or a command the reader can run; passes claims-lint; included in the docs site if user-facing. |
| `[QA]` | Test infrastructure | Real services only (no mocks); deterministic or seeded; evidence output stored under git-ignored `acceptance-*/` with sha256. |
| `[LAB]` | Needs the closed lab | Lab-only guard enforced in code; otherwise UNVERIFIED(`capability_not_supplied`). |
| `[HUMAN]` | Needs an operator action | Real probe detects the state; exact instructions printed; wait for confirmation. |

### 0.9 Conventions

- **Task order.** Task numbers are stable identifiers, not the execution order. The execution order is the **stable topological order** of the `deps:` graph: a task runs after everything it depends on, and ties are broken by number. `cargo xtask tasks order` (T-0005) prints it and `xtask tasks index --check` fails on a cycle. A dependency on a later number is therefore legal and means the later-numbered task runs first (for example T-0237 first in P12, T-0538 before T-0537 in P31, and T-0561 to T-0563 right after G00). Delivery slices (section 0.8) group the same tasks into usable products.
- **Runtime state means the store traits.** Wherever a task says "Redis" for runtime state, it means the `KvStore`, `Bus` and `Limiter` traits of `hdd-common::kv`; only that module talks to Redis (`xtask kv-lint`, R-31). Tests that say "real Redis" or "testcontainers" run against both backends, and on a builder without Docker against the embedded PostgreSQL and the in-process stores.
- **IDs.** Tasks `T-nnnn`; phases `Pnn`; gates `Gnn` (one per phase, same number order as the phase list in the gate table of Appendix E5); delivery slices `DSn`; hosting checks `HC-nn`; hosting profiles `H1` to `H5`; journeys `J-nn`; screens `S-nnn`; attack classes `ATK-nnn`; acceptance checks `AC-nn`; error codes `ERR-<AREA>-nnn`; metrics `MET-<name>`; audit events `AUD-<area>.<verb>`; permissions `PERM-<area>.<verb>`; ADRs `ADR-nnnn`; deviations `DEV-nnn`.
- **Section references.** `Cn`, `Bn` and `En` name sections of this document (for example `C4.6`, `B12.2`, `E5.1`); a reference such as `C13.2` or `C14.8` names the numbered item inside section `C13` or `C14`; `section N` refers to Part A.
- **Registries.** The registries in Part B (errors B7, audit events B8, metrics B9, environment variables B10, permissions B4.2, Redis keys B5.12) are seed catalogs. A task that needs a new entry adds it to the registry in the same change (with its owning task id); `xtask names check` fails when code, docs or tests reference a code or name that is not registered, or when a registered name is unused for two gates.
- **Requirement IDs.** Each phase declares a requirement prefix. The k-th task of a phase owns `REQ-<PREFIX>-<k>` (two digits). The capability matrix lists each `REQ` with its tests and evidence.
- **Markers.** `<!-- PART:<id> -->` and `<!-- PHASE:<id> -->` mark split points. Do not remove them.
- **Task block layout.** Heading `### T-nnnn · Title`; meta line (phase, tags, `deps:`, size, owner); then `Objective`, `Steps`, `Deliverables`, `Acceptance`, `Tests`, `Notes`. Sizes: S (under half a day), M (about one day), L (two to three days), XL (four days or more; commit per step, the Steps list is the split, and the gate reviews the whole).
- **Placeholders in this document.** `{{PLATFORM_DOMAIN}}` is the operator's platform apex (for example the domain that hosts `www.`, `app.`, `admin.`, `api.`, `ns1.`, `ns2.`). `{{OPERATOR_EMAIL}}` is the operator contact. These are filled from `hdd.live.yaml`; nothing in code hardcodes them.
- **Language.** Imperative voice. "Must" is mandatory, "should" is a default that may be changed with a recorded reason, "may" is optional.

### 0.10 Glossary

| Term | Definition |
| --- | --- |
| Pilot | Only the pilot subzones (test and sandbox hostnames) are delegated to HDD; no production traffic crosses it. |
| Apex cutover | Delegating the operator's real apex to HDD. Never automatic. |
| Never-ban list | Data-plane IPs that are never banned (admin CIDRs, loopback, platform IPs, origin). The acceptance runner is deliberately not on it. |
| Known-good probe | A request that must always pass, used by rule dry-runs and automatic rollback. |
| Orange cloud | A DNS record with `proxied=true`: answers resolve to HDD edge IPs and traffic is inspected. |
| Grey cloud | A DNS record with `proxied=false`: the stored value is returned and traffic bypasses HDD. |
| Integration mode | How a domain is attached to HDD: `full_ns`, `cname_partial`, `a_record_partial`, `hidden_primary`, `subdomain_only`. |
| Site / domain | A proxied hostname with its own policy. The UI says "domain"; the schema says `sites`. |
| Hard signature | A detection that always blocks (and, outside cross-site context, bans) regardless of score. |
| Soft signature | A detection that adds to an anomaly score; blocks only when the threshold is reached. |
| Paranoia level (PL) | 1 to 4; gates which rules are active. Separate from the score threshold. |
| Vulnerable-origin shield | HDD profile that assumes the origin application is exploitable and tightens everything accordingly (Part C, C3). |
| Vuln-Lab | Intentionally vulnerable applications that exist only in the closed lab, to prove the shield works against a truly exploitable origin. Never deployed, never public. |
| Inspect-first gate | Every live attack-shaped test request is first submitted to the dry-run inspect API; sent only if `would_block=true` and the config revision is unchanged. |
| Ray ID | Per-request identifier: 16 hex characters + `-HDD1`. Shown on block pages and in events. |
| Config revision | Monotonic version of a site's compiled policy snapshot; every change creates one. |
| Snapshot | Immutable compiled configuration held by proxy and DNS behind `ArcSwap`. |
| Jail | The set of banned IPs enforced at L7 (proxy), and in the kernel for proxied ports. |
| Clearance | A signed cookie proving a visitor passed the proof-of-work challenge. |
| Appeal | A visitor's request, filed from the block page with a Ray ID, to review a block. |
| Virtual patch | A narrowly scoped WAF rule mitigating a known component vulnerability. Never marks the vulnerability resolved. |
| VEX | Vulnerability Exploitability eXchange statement (`not_affected` with justification). |
| KEV | CISA Known Exploited Vulnerabilities catalog. |
| EPSS | Exploit Prediction Scoring System probability. |
| Readiness score | 0 to 100 measure, per domain, of how fully the domain is actually protected (Part B and T-0172). It measures configuration completeness, not security. |
| Surface | One of the web audiences served by `hdd-web`: `public`, `app`, `admin`. |
| Walking skeleton | The thinnest real vertical slice (DNS answer, TLS, proxy, deploy) proven live early. |
| Lifecycle stage | `pilot` or `production` (Part A, safety envelope). |
| Deployment mode | `owner_only` (single operator, signup disabled) or `saas` (multi-tenant, signup enabled by policy). |
| Runtime profile | `local` (a personal computer, live only while HDD runs) or `hosted` (a server, 24/7). Same code path, R-31, C18. |
| Embedded database | A private PostgreSQL server that `hdd-local` installs and manages inside its data directory (local profile). |
| Last-known-good snapshot | The most recent compiled configuration, written to disk after every swap, so proxy and DNS restart without the control plane. |
| Hosting profile | `H1` single server, `H2` edge and control split, `H3` container platform, `H4` unsupported platform-as-a-service, `H5` home server (C18.10). |
| Access gate | An HDD-enforced barrier in front of selected paths of a site (administration areas, database tools), evaluated before inspection (C19.2). |
| Business flow | A function of a protected application (login, signup, checkout, search, OTP) whose abuse is harmful even when requests are valid (C19.4). |
| Coverage map | The generated, tested table of standards categories with status covered, partial, signal only or not covered, plus the "does not cover" list (C19.5, E15). |
| Delivery slice | A set of tasks (the dependency closure of its root tasks) that ends in a usable product (section 0.8). |
| ADR | Architecture Decision Record in `docs/adr/`. |
| Gate | A phase-end checkpoint requiring a gate report with pasted real command output. |
