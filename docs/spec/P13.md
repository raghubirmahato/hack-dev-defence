## PHASE P13: WAF core engine (T-0239 to T-0262) · milestone M6 · gate G13

Requirement prefix `WAF`. Goal: a pure, I/O-free, deterministic, fuzz-hardened detection engine (`hdd-waf-core`) with vector extraction, three-view normalization, a prefilter plus linear-time signature engine, a rule and pack model, scoring, exclusions, custom rules, bounded parsers, field-kind context, redaction, verdict and event models, fixtures and a benign corpus, performance budgets, mutation testing, and integration into the proxy pipeline and the dry-run inspect API. The structural SQL detectors and the other detector families (P14, P15) plug into this engine.

Engine rules (apply to every task in P13 to P15):
- `hdd-waf-core` has no async, no filesystem, no network, no wall-clock reads; randomness is injected; GeoIP/ASN lookups are traits.
- Every regular expression is compiled with a linear-time engine; no backtracking engine, no lookaround, no backreferences.
- Every loop, buffer and recursion is bounded; every input has a size cap; exceeding a cap sets a flag and follows `over_limit_policy` (never silently passes in `block` mode, R-26).
- Every rule carries examples and counter-examples used as tests; rules without both are rejected by the pack linter.
- Detection changes are measured (R-23): benign corpus zero matches, core set 100%, held-out ≥ 95%, mutation score ≥ 80%.

Gate G13 passes when: unit, property and fuzz-smoke suites pass; coverage ≥ 85% on the crate; `cargo-mutants` score ≥ 80%; benign corpus yields zero matches; the inspect API and the proxy integration work end to end in monitor and block modes on the builder; and the inspection benchmark meets p50 < 1 ms on the reference corpus.

### T-0240 · Request model and vector extraction
`P13` `[DP]` · deps: T-0239, T-0249 · size: L · owner: waf
**Objective.** Turn a request into labeled, bounded input strings for every detector.
**Steps.**
1. Implement extraction for each vector of C4.2: path segments (each decoded separately, matrix parameters split), query keys and values, form fields, multipart text parts and part headers and filenames, JSON keys and string leaves, XML text/attributes/CDATA, GraphQL query text and variables, cookies (names and values), selected headers (`User-Agent`, `Referer`, `Origin`, `Accept-Language`, `X-Forwarded-*` when trusted, configured extras, and unlisted custom headers), WebSocket handshake and optional text frames.
2. Label each extracted value with `Vector`, `FieldRef` (name path such as `form:username`, `json:$.user.name[0]`), and `FieldKind` (T-0251), keeping a stable ordering for deterministic verdicts.
3. Implement duplicate handling: inspect each duplicate individually and also the concatenation of duplicates (HTTP parameter pollution), array notations (`a[]`, `a[0]`, `a[b]`).
4. Implement limits: max fields (default 2,000), max total inspected bytes (default `inspect_body_max_bytes` for bodies and 64 KiB for headers+URL), per-field cap (16 KiB; longer values are chunked into overlapping windows of 8 KiB with 256-byte overlap so payloads at boundaries are still seen).
5. Implement content-type handling with confusion defenses: parse by declared type but also sniff (JSON body sent as form, form sent as JSON, XML in `text/plain`), inspecting under both interpretations when ambiguous.
6. Implement the multi-encoding body handling: `Content-Encoding` gzip/deflate/br/zstd decoded with bounded ratio and size via the parsers (T-0249) before extraction.
7. Provide zero-copy views where possible (`Cow`) and reuse of the scratch arena.
8. Add table tests for every vector and hostile inputs (huge numbers of parameters, deep JSON, malformed multipart).
**Deliverables.**
- `extract` module, tests, benches
**Acceptance.**
- A1: payloads placed at chunk boundaries in long fields are detected (boundary test over 10,000 offsets).
- A2: parameter pollution splits are detected via the concatenation view.
- A3: ambiguous content types are inspected under both interpretations.
- A4: extraction respects all caps and flags `Truncated`/`ParserLimit` appropriately.
- A5: extraction never panics (fuzz).
**Tests.**
- Table/proptest/fuzz; benchmark of extraction throughput.
**Notes.** Header allowlists and extras are part of the compiled policy.

### T-0241 · Normalizer: the `decoded` view
`P13` `[DP][SEC]` · deps: T-0239 · size: XL · owner: waf
**Objective.** Implement the iterative, idempotent decoding pipeline defeating encoding evasions.
**Steps.**
1. Implement percent decoding iterated to a fixed point (max 3 layers) with strict handling of invalid sequences (leave literal, set flag), `%uXXXX` decoding, `+` to space in query/form contexts, and detection of overlong UTF-8 (`%c0%af`, `%e0%80%af`) with `OverlongUtf8` flag and conversion to the intended character for detection while the original raw view is kept.
2. Implement HTML entity decoding (named entities table, decimal and hexadecimal numeric entities with or without semicolons, with maximum expansion limits) and JSON/JS escape decoding (`\uXXXX`, `\xNN`, `\'`, `\"`, octal) in contexts where such escapes are meaningful (JSON values, script-ish contexts, SQL contexts that treat backslash as escape).
3. Implement Unicode normalization to NFKC and the **quote and operator folding** table (U+02BC, U+2018, U+2019, U+201B, U+FF07, U+00B4, U+2032 to `'`; U+201C, U+201D, U+FF02 to `"`; fullwidth ASCII variants U+FF01 to U+FF5E to ASCII; U+2010 to U+2015, U+FF0D to `-`; U+FF1D to `=`), recording `UnicodeFold` flags.
4. Implement wide-byte (GBK-style) handling: detect sequences like `%bf%27`, `%df%27`, `%a1%27` and decode the quote with flag `MultibyteQuote` (the lead byte consumption modeled by a documented rule).
5. Implement null-byte removal with `NullByte` flag, control character handling (strip or replace per context), and case folding via full Unicode lowercasing for matching (preserving the original for evidence).
6. Implement size bounds (output at most 4x input and hard cap 1 MiB per string), iteration bounds, and invalid UTF-8 handling policy (lossy conversion with replacement plus flag; attackers can exploit decoder differentials so both lossy and raw-byte views are available to byte-level signatures).
7. Provide the `NormalizedString { raw_range, decoded, flags }` type with source-offset mapping so evidence spans can be mapped back to the raw input.
8. Write 300 table cases covering every encoding trick in C4.8 (encoding group), including mixed and nested encodings.
**Deliverables.**
- `normalize::decoded` module, folding tables with provenance comments, tests
**Acceptance.**
- A1: `%252527`, `%u0027`, `&#39;`, `&#x27;`, `'`, `＇`, `ʼ`, `%bf%27` all fold to a detectable `'` (table test).
- A2: output length never exceeds 4x input or 1 MiB (property test).
- A3: the function is idempotent on its own output (proptest, excluding documented non-idempotent flags).
- A4: offset mapping returns valid raw spans for every output position (property test).
- A5: it never panics on arbitrary bytes (fuzz).
**Tests.**
- Table (300) / proptest / fuzz; benchmark ≤ 150 ns per 100-byte string typical.
**Notes.** Idempotence (decoding already-decoded text once more must not change it except through documented layers) is tested explicitly.

### T-0242 · Canonicalizer: the `canonical` view
`P13` `[DP][SEC]` · deps: T-0241 · size: L · owner: waf
**Objective.** Remove syntactic noise attackers add to hide SQL, expression-language and shell payloads.
**Steps.**
1. Implement SQL-context canonicalization: unwrap MySQL versioned comments (`/*!50000 union*/` becomes ` union `), replace inline comments `/**/` and `/*...*/` (non-versioned) with a single space while recording `CommentSeen` flags and positions, handle nested/unterminated comments conservatively.
2. Implement whitespace canonicalization: collapse tabs, newlines, vertical tab, form feed, carriage return, NBSP and Unicode spaces to a single space; treat `+` as space only in decoded query/form views.
3. Implement concatenation joining in evaluable cases: `'un'+'ion'`, `'un' 'ion'`, `CONCAT('un','ion')`, `'un'||'ion'`, adjacent string literals in SQL context, and `CHAR(39)`, `CHR(39)`, `0x27`, `X'27'`, `UNHEX('27')` to literals when appearing near SQL tokens (bounded evaluation to avoid blowups).
4. Implement lookup unwrapping for `${...}` syntaxes: `${lower:x}`, `${upper:x}`, `${::-x}`, `${env:NAME:-x}`, `${sys:...}`, `${date:...}`, `${j${::-n}di:`, nested up to depth 8, recording `LookupObfuscation` flags (shared with JNDI detection T-0291).
5. Implement shell-context canonicalization helpers: backslash/quote removal inside words (`c'a't`, `c""at`), `${IFS}` and `$IFS$9` expansion to space, brace expansion `{cat,/etc/passwd}`, ANSI-C quotes `$'\x63at'`, environment variable stripping, wildcard globbing hints (`/???/c?t`), recorded with flags (full lexer in T-0289).
6. Implement HTML/JS canonicalization helpers for XSS: attribute value unquoting, tag/attribute case folding, slash/whitespace separators between attributes, comment removal, entity decoding in attribute context (full tokenizer in T-0285).
7. Provide per-context entry points (`canon_sql`, `canon_shell`, `canon_html`, `canon_lookup`) so detectors request only needed views (performance), plus a combined `canonical` view for generic signatures.
8. Write 300 table cases including pathological nesting and ensure bounded runtime (budget 4x input).
**Deliverables.**
- `normalize::canonical` modules, tests
**Acceptance.**
- A1: `/*!50000UnIoN*//**/SeLeCt` becomes `union select` in SQL context.
- A2: `${${::-j}${::-n}di:ldap://x.invalid/a}` becomes `${jndi:ldap://x.invalid/a}`.
- A3: `c'a't /e'tc'/p"a"sswd` canonicalizes to `cat /etc/passwd` in shell context.
- A4: nesting beyond depth limits sets `DecodeDepthExceeded` instead of looping.
- A5: no function exceeds 4x output growth or panics (fuzz).
**Tests.**
- Table (300) / proptest / fuzz; bench.
**Notes.** The `decoded` view keeps comment tokens visible; `canonical` collapses them (C4.3).

### T-0244 · Prefilter and signature engine (Aho-Corasick plus regex automata)
`P13` `[DP]` · deps: T-0242 · size: XL · owner: waf
**Objective.** Make scanning fast: cheap token prefilter, then linear-time pattern sets.
**Steps.**
1. Implement the compile pipeline: rule definitions to (a) an Aho-Corasick automaton over required literal tokens per rule (extracted by a literal-extraction pass from the regex AST) and (b) per-group `regex-automata` sets (DFA/hybrid with size limits) for verification; groups by category and context so a field scans only relevant sets.
2. Implement size and complexity budgets at compile time: maximum DFA states per group (reject or fall back to the lazy/hybrid engine with a memory cap), maximum pattern length, total compiled memory per site (cap by plan), and reporting of the heaviest rules.
3. Implement the scan API: `scan(field_view, contexts, scratch) -> SmallVec<Match>` with early exit for hard matches when configured, per-request regex-scan budget (maximum bytes scanned across all sets) and `BudgetExceeded` handling.
4. Implement hot swap: compile in a background task off the hot path, validate against the self-test corpus (rule examples and counter-examples), then publish via `ArcSwap`; compile failures keep the last good set.
5. Implement match metadata: rule ID, group, start/end offsets in the scanned view, mapped back to raw offsets via the normalizer map.
6. Implement caching: LRU cache of verdicts keyed by (field hash, context, ruleset hash) for repeated identical values (headers like `User-Agent`) with strict size limits and TTL, safe because the engine is pure.
7. Provide a benchmark suite with realistic traffic corpora and adversarial inputs (long runs of near-matches).
8. Document engine limits and the rationale for linear-time-only.
**Deliverables.**
- `signatures` module, compiler, benches, tests, docs
**Acceptance.**
- A1: no pattern can cause super-linear scan time (property test with adversarial strings across all shipped rules).
- A2: compile rejects patterns exceeding budgets with precise errors.
- A3: hot swap does not drop requests and applies within 2 s of publication (integration with T-0211).
- A4: p50 scan time for a 200-byte field across all default rules is under 20 µs on the builder.
- A5: matches map back to correct raw offsets for 1,000 randomized encoded inputs.
**Tests.**
- Property/adversarial tests; benchmarks; unit: literal extraction correctness vs regex semantics (differential with plain `regex`).
**Notes.** Backtracking engines (PCRE) are never used.

### T-0250 · GraphQL light parser and vector extraction
`P13` `[DP]` · deps: T-0240 · size: M · owner: waf
**Objective.** Inspect GraphQL requests without a full server-side schema.
**Steps.**
1. Implement a tolerant GraphQL tokenizer/parser sufficient to extract operations, selection depth, field counts, alias counts, fragment spreads, variable definitions, directives, and string literals.
2. Compute metrics: maximum depth, total fields, aliases per operation, batch size (arrays of operations), introspection usage (`__schema`, `__type`), fragment cycle detection, and a cost estimate heuristic.
3. Extract inspectable strings (arguments, variable values from JSON `variables`) as vectors `graphql:variables.*` for the normal detectors.
4. Emit policy-driven signals: depth/alias/batch/introspection thresholds from the site policy (defaults: depth 12, aliases 30, batch 10, introspection blocked on production unless allowed).
5. Handle persisted queries and GET-based queries (`query` parameter), APQ hashes, and content types (`application/graphql`, JSON).
