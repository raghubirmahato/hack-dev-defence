## PHASE P28: Acceptance suite, closed lab and the Vuln-Lab (T-0491 to T-0510) · milestone M11 · gate G28

Requirement prefix `ACC`. Goal: complete the evidence machine. The acceptance runner reaches full capability, the safety envelope is proven by self-tests, the Vuln-Lab provides genuinely vulnerable applications in an isolated closed lab, and every remaining acceptance criterion is executed with honest PASS / FAIL / UNVERIFIED(reason) statuses. The centerpiece is the proof the product exists for: a vulnerable site, exploitable when accessed directly, is not exploitable through HDD, and the attacker's IP is banned (AC-38, AC-39).

Non-negotiables: the live suite touches only the profile's `test_hostname`, `sandbox_hostname` and the operator's own declared targets; Class B and body-bearing payloads go only to the sandbox or the Vuln-Lab; the inspect-first gate precedes any live enforcement attempt; the runner's IP is never in `admin_cidrs` and is protected by the never-ban list unless a test explicitly uses a second source; test bans use 60 s TTLs; external oracles (sqlmap, nikto, wapiti, nuclei, ZAP baseline, ffuf) run **only** against Vuln-Lab addresses; lab results are labeled `lab-proven` and never presented as live results; the Vuln-Lab never ships (release gate).

Gate G28 passes when: the runner executes the complete catalog AC-00 to AC-54 (AC-55 to AC-62 are registered and stay `UNVERIFIED(stage_not_reached)` until P33 and P34) with a rendered report in which every item is PASS, FAIL (none allowed at the gate) or UNVERIFIED with an enumerated reason; AC-38 and AC-39 pass in the lab including the oracle campaign figures; the safety self-tests (AC-00) pass; and no acceptance traffic left its allowlist (audit and packet-capture proof).

### T-0491 · Acceptance runner v1: full catalog, modes, profiles, evidence store and report
`P28` `[QA][OPS][SEC]` · deps: T-0215, T-0216, T-0217 · size: XL · owner: qa
**Objective.** Turn the runner skeleton into the production-grade engine that executes, records and renders every acceptance criterion.
**Steps.**
1. Finish the `hdd-acceptance` architecture: `Catalog` (all AC-00..AC-62 as typed `Check`s; AC-55 to AC-62 stay `UNVERIFIED(stage_not_reached)` until P33 and P34 with id, title, phase of first requirement, stage constraints, required capabilities, safety class, default profile, dependencies on other checks), `Executor` (plan → run → collect), `Evidence` store (content-addressed files + JSON records), `Report` renderer (Markdown, HTML and JSON), and a CLI/xtask front end (`xtask acceptance --only AC-39 --mode live|lab --stage pilot|production --profile functional|burst|protocol-abuse|load|lab`).
2. Implement the **status taxonomy** in the type system: `Pass`, `Fail { reason }`, `Unverified { reason: ReasonCode }` with the closed reason set (`capability_not_supplied`, `human_step_pending`, `environment_unsupported`, `oracle_unavailable`, `tool_unavailable`, `stage_forbids`, `skipped_by_operator`); there is no "skipped" and no "pending" outside this set; the renderer refuses to print a PASS without at least one evidence artifact reference.
3. Implement the **target and egress allowlists** read from `hdd.live.yaml` (live mode) or the lab profile (lab mode): every HTTP/DNS/TLS/raw-socket connection from the runner passes through one connector that enforces the allowlist, rate profile, per-target concurrency, global kill switch and payload class gating; a request outside the allowlist aborts the check, writes an audit record and marks the run invalid.
4. Implement **rate profiles**: functional (≤ 20 req/s sustained, ≤ 5 minutes continuous), burst (one capped burst of ≤ 100 HTTP requests and one capped DNS burst of ≤ 500 queries), protocol-abuse (sandbox only: ≤ 5 connections, ≤ 2,000 frames and ≤ 10 MiB on the wire per test), load (separate written operator approval per run, sandbox only, own hard caps, auto-abort when origin health degrades), lab (≤ 500 req/s per client process, 10 minutes, one client process per oracle tool); profile selection per check with hard ceilings that checks cannot raise.
5. Implement the **inspect-first gate**: before a live enforcement test with a payload, the runner calls `POST /api/v1/waf/inspect` for the same vector and requires the expected category/verdict (otherwise the enforcement test is skipped as `Fail("inspect_mismatch")` instead of sending traffic that would not be blocked); records both results.
6. Implement **payload classes**: A (inert, any live target in the allowlist), B (GET/HEAD attack shapes, `test_hostname` + `sandbox_hostname` only, sandbox preferred), C (body-bearing or higher-risk, `sandbox_hostname` or lab only); the class is part of the fixture metadata and enforced by the connector (fixtures without a class are rejected).
7. Implement **resume and idempotency**: each check has a deterministic run id; interrupted runs resume; evidence is append-only with SHA-256 manifests; reruns create new attempts linked to previous ones; flaky checks are annotated by the failure budget (3 attempts maximum, then FAIL).
8. Implement **report rendering** (`xtask report`): summary tables by phase/area/status, per-check detail with commands, outputs, hashes, environment facts, UNVERIFIED reasons with the remediation each needs from the operator ("what we need from you"), trend versus previous runs, and a claims appendix mapping product claims to evidence ids.
9. Write tests: allowlist violations (HTTP, DNS, raw sockets), rate ceilings, taxonomy enforcement (compile-fail tests for illegal statuses), inspect-first gate behavior, payload class enforcement, resume after crash, evidence manifest verification, and report golden tests with fixtures covering all statuses.
**Deliverables.**
- `hdd-acceptance` v1, catalog (AC-00..AC-54), report renderer, tests, docs `docs/ACCEPTANCE.md`
**Acceptance.**
- A1: every catalog entry exists with id, owner phase, required capabilities and safety class (static test against Appendix E3).
- A2: no network I/O in the crate bypasses the connector (static grep gate and runtime allowlist tests).
- A3: the renderer cannot output PASS without evidence references (test).
- A4: runs resume after being killed mid-check without duplicating destructive actions.
- A5: the report lists UNVERIFIED reasons with operator actions.
**Tests.**
- Unit, compile-fail, integration, golden.
**Notes.** The catalog is the executable form of Appendix E3; the two must stay identical (a CI test compares them).

### T-0492 · Safety-envelope self-tests (AC-00): prove the guard rails before using them
`P28` `[QA][SEC]` · deps: T-0491 · size: L · owner: qa
**Objective.** Demonstrate that the rules in section 2 are enforced by code, not by good intentions.
**Steps.**
1. Implement AC-00 as a suite that runs first in every acceptance session: preflight (`hddctl preflight`: profile validity, secrets strength, ports, DNS delegation facts, TLS stage, `lifecycle_stage` consistency, runner IP not in `admin_cidrs`, never-ban contains runner IP, canary reachability, clock sync) and the safety self-tests below.
2. **Allowlist tests:** attempt requests to a non-allowlisted hostname, an IP literal, a hostname that resolves to a non-allowlisted address (DNS rebinding simulation with a controllable resolver), and a redirect from an allowlisted host to an external one; all must be refused before any packet leaves (verified through a socket-layer recorder).
3. **Class-gating tests:** send a Class B fixture to a non-sandbox allowlisted host, a Class C fixture to the test hostname, and an unclassified fixture; all must be refused.
4. **Rate-profile tests:** a deliberately aggressive check definition is clipped to the profile ceiling; measured request rate against a counting local server never exceeds the ceiling over 60 s for each profile (functional, burst, protocol-abuse, lab).
5. **Kill-switch test:** creating the kill-switch file stops all runner traffic within 1 s and the run is marked `Unverified(skipped_by_operator)`; removing it requires an explicit `--resume`.
6. **Runner-IP guard tests:** the runner's source address is detected (STUN-free: from the sandbox echo endpoint) and compared to `admin_cidrs` (must not be present) and the never-ban list (must be present unless `--use-second-source`); a test that bans the runner's own IP through the API is refused by the guard.
7. **Stage tests:** in `lifecycle_stage: production` destructive checks (resilience, chaos, load, bans against real traffic sources) refuse to run without `--operator-approval <ticket>`; verify the refusal and its message.
8. **Secrets hygiene:** the runner redacts secrets from logs and evidence (scan of an evidence bundle from a run with known canary secrets finds none) and refuses to start when `.env` or profile files have lax permissions.
9. **Egress for oracles:** the oracle launcher refuses to run sqlmap/nikto/etc. unless the target is in the lab allowlist (`lab` mode), tested with live-host targets.
10. Record the AC-00 report with evidence and keep the suite in the non-destructive regression subset.
**Deliverables.**
- AC-00 suite, socket-recorder test utility, evidence
**Acceptance.**
- A1: every refusal test shows zero packets sent to the forbidden destination (socket recorder).
- A2: measured rates stay under the profile ceilings in 100% of runs.
- A3: the kill switch halts traffic within 1 s.
- A4: banning the runner IP is refused unless a second source is configured.
- A5: oracle launches against non-lab targets are refused.
**Tests.**
- The suite itself, executed in CI against local servers and on the pilot.
**Notes.** AC-00 failing blocks every other check from running.

2. Implement the **self-guard** (section 2.8) in a single `guard::enforce()` called first in `main`: requires `HDD_LAB_ACK=I-OWN-THIS-LAB`; verifies each bind address is loopback or inside `HDD_LAB_CIDR` (parsed, must be RFC 1918/ULA/loopback); inspects network interfaces and refuses if any interface outside the lab namespace carries a globally routable address; prints a prominent banner "HDD VULN-LAB: INTENTIONALLY VULNERABLE: LAB ONLY"; unit-test every refusal path and the happy path.
3. Create the **canary data stack**: databases per dialect (SQLite embedded, MySQL/MariaDB and PostgreSQL containers or embedded test servers, MSSQL optional if license permits) loaded with synthetic canary schemas (`users` with canary admin `labadmin` and hashed canary password, `products`, `orders`, `secrets_canary` table with a unique canary string per run), with snapshot/restore (`xtask lab reset`) before every test and unique per-run canary tokens used to prove exfiltration (if the token appears in a response, extraction occurred).
4. Implement the **network isolation**: compose `internal: true` network or netns with no default gateway; the Vuln-Lab cannot resolve or reach external hosts (egress blocked by namespace rules; tested by attempting outbound connections from within the lab apps, which must fail).
5. Implement **release exclusion**: `xtask release` inspects `cargo metadata` for any shipped binary's dependency graph and fails if `hdd-vulnlab` (or any `lab/` path crate) is present; CI test builds a release artifact and asserts absence in the SBOM; container image build files for the VPS never copy `lab/`.
6. Implement **license and provenance records** for optional third-party vulnerable containers (for example DVWA, OWASP Juice Shop, WebGoat; digest-pinned; license text copied to `lab/LICENSES.md`); they are optional extras for additional oracle coverage and are never required for gates.
7. Provide `lab/vulnlab/README.md` with the safety statement and the explicit "never run outside the lab" instructions, plus a banner in every HTTP response (`X-Vuln-Lab: intentionally-vulnerable`).
8. Write tests: guard refusal matrix (≥ 12 cases), isolation test (outbound connection attempts fail), release-exclusion test, snapshot/restore determinism, canary-token uniqueness, and a test that the binary refuses to start when run with a public bind address.
**Deliverables.**
- `hdd-vulnlab` skeleton, guard, data stack, release gate, docs
**Acceptance.**
- A1: the Vuln-Lab refuses to start in all unsafe configurations (matrix).
- A2: outbound connections from lab apps fail (isolation test).
- A3: release builds fail the gate if the lab crate appears in a shipped dependency graph (negative test).
- A4: database resets restore the canary state exactly (hash compare).
- A5: every response carries the lab header and no real data exists in the lab databases.
**Tests.**
- Unit (guard), integration (netns/compose), CI release-gate tests.
**Notes.** The Vuln-Lab is the one sanctioned exception to "no dummy origin" and exists only to prove protection claims (R-02).

### T-0494 · Vuln-Lab application set A: SQL injection family with direct-exploit proofs
`P28` `[LAB][QA]` · deps: T-0493 · size: XL · owner: lab
**Objective.** Provide authentically vulnerable SQLi endpoints in every context HDD must protect, each with a non-destructive proof that it is exploitable without HDD.
**Steps.**
1. Implement the **login family** (the user's scenario): a classic login form (`POST /login`, `username`, `password`) building SQL by string concatenation (`SELECT * FROM users WHERE username='$u' AND password='$p'`), a JSON login (`POST /api/login` JSON body), a login with the credentials in HTTP Basic auth, an "admin panel" login variant with a `LIMIT 1` query, and a "remember me" cookie lookup; each ships in MySQL, PostgreSQL and SQLite dialect variants where syntax differs (comment styles `--`, `#`, `/* */`).
2. Implement the **query context family**: search (`GET /search?q=` using `LIKE '%$q%'`), numeric ID (`GET /item?id=`), sort/order parameter (`ORDER BY $col`), pagination `LIMIT $n`, `IN (...)` lists, header-based (User-Agent and X-Forwarded-For stored in a visit-log INSERT), cookie-based (`session` cookie used in a lookup), path-parameter (`/user/{id}`), form-urlencoded and multipart fields, JSON nested field, and XML SOAP-style body.
3. Implement the **advanced family:** error-based (database errors echoed in HTML or JSON), UNION-capable (column count 4 with a string column), boolean-blind, time-based (SLEEP/`pg_sleep`/`randomblob` loop capped at 2 s by a lab-side guard), stacked queries (PostgreSQL/MSSQL variant only, against canary tables), and **second-order** (profile name stored, later concatenated into an admin report query).
4. For each endpoint publish a **direct-exploit proof** (`lab/vulnlab/proofs/sqli/*.yaml`): Class A, non-destructive only: login bypass returning the canary admin session marker; UNION extraction of the per-run canary token; boolean/time differential with ≤ 2 s sleeps; no `DROP`, no writes to non-canary tables; the proof runner executes against the Vuln-Lab directly and **must succeed** (a failing proof means the endpoint is not vulnerable and the test environment is invalid).
5. Include the **mandated payload set** M1–M6 (`' OR 1=1--`, `' OR '1'='1`, `admin' --`, `admin' #`, `admin'/*`, `' or 1=1 LIMIT 1 --`) in each applicable context with the dialect-correct form, and verify each succeeds as a direct exploit where syntax is valid (some are dialect-invalid; the proof matrix records which are valid for which endpoint, so "direct exploit failed because of syntax" is distinguished from "blocked").
6. Add **legitimate-use endpoints** next to each vulnerable one (normal login with valid canary credentials, search for ordinary words, apostrophe names such as `O'Brien`, a SQL tutorial comment form) used for false-positive checks and for ensuring HDD does not break the app.
7. Add structured **access logging** in the Vuln-Lab (request, query executed, rows returned) so tests can assert what reached the database; the log is part of the evidence (proves that blocked requests never hit the database).
8. Write self-tests: every proof succeeds on a fresh reset; legitimate flows succeed; the guard keeps the app lab-only; the app code is annotated as intentionally vulnerable with a static marker test so scanners do not mistake it for product code.
**Deliverables.**
- vulnerable SQLi apps, proof definitions, legit endpoints, logs, self-tests
**Acceptance.**
- A1: all direct-exploit proofs succeed on a fresh canary state (≥ 30 proofs across contexts and dialects).
- A2: the proof matrix records which of M1–M6 are valid per endpoint with expected direct outcomes.
- A3: time-based endpoints never sleep more than 2 s (lab guard).
- A4: legitimate flows succeed, including apostrophe inputs.
- A5: the access log shows exactly which queries reached the database for each test.
**Tests.**
- Self-tests; used by T-0497 and T-0499.
**Notes.** Only Class A proofs exist; no destructive exploit chain is implemented anywhere in the lab.

### T-0495 · Vuln-Lab application set B: other vulnerability classes with direct-exploit proofs
`P28` `[LAB][QA]` · deps: T-0493 · size: XL · owner: lab
**Objective.** Cover the non-SQLi classes the shield claims to mitigate, each with an authentic vulnerability and a safe proof.
**Steps.**
1. **XSS:** reflected (query parameter echoed unescaped in HTML body, attribute, script and URL contexts), stored (comment board with canary rendering), DOM-based (hash fragment sink); proof = a canary marker executes (headless browser records `window.__labxss`), no external requests.
2. **File access:** path traversal / LFI (`/download?file=`, `include=`) reading a **canary file** inside the lab (never real system files; the vulnerable code resolves against a lab directory containing `canary.txt` and a chroot-like jail so the proof cannot read host files); RFI simulation using lab-local URLs only.
3. **Command injection:** an endpoint that concatenates user input into a shell-like command executed by a **sandboxed interpreter that only implements a tiny allowlisted command set (`echo`, `date`, `canary`)** so the vulnerability is real syntactically (separators `;`, `|`, `&&`, backticks, `$()` change behavior) but cannot touch the host.
4. **SSRF:** a URL fetcher that follows user URLs and can reach an internal lab service (`http://169.254.169.254` is simulated by a lab-local metadata mock bound inside the lab namespace) returning a canary secret; proof = canary appears in response.
5. **Upload:** an upload endpoint accepting any extension and storing under a served directory in the lab with a "script-like" canary executor (files named `.labshell` are interpreted by a trivial lab interpreter that prints a canary); proof = upload then fetch executes the canary; archive and image bomb variants rejected by HDD are simulated with small safe fixtures.
6. **Deserialization:** an endpoint deserializing a lab-defined object format (JSON with type tags and a gadget-like `canary_action`) and a Java-serialization-signature-accepting stub that merely detects magic bytes and logs (no real gadget); proof = canary action triggered.
7. **XXE and XML:** an XML parser with external entities enabled resolving only to lab files; proof = canary file contents echoed.
8. **Other web flaws:** open redirect, CRLF/header injection, host header poisoning (password-reset link generation), IDOR/BOLA API (sequential ids), mass assignment (role field), GraphQL (introspection on, no depth limit, batching), JWT `alg=none` stub (lab-defined), CSRF-vulnerable state change, verbose error pages (stack traces), directory listing, exposed `.env`/`.git` canary files, default credentials page, and rate-limit-less login (for credential-stuffing tests with synthetic credentials).
9. Provide **legitimate-use endpoints** for each class and write proofs in `lab/vulnlab/proofs/<class>/*.yaml` (Class A, non-destructive); each proof must succeed against the Vuln-Lab directly.
10. Write self-tests: all proofs succeed on a fresh state; guards intact; the sandboxed interpreters cannot reach the host (attempt escapes in the test suite and verify they fail); legitimate flows succeed.
**Deliverables.**
- vulnerable apps for all classes, proofs, legitimate endpoints, self-tests
**Acceptance.**
- A1: every class has at least two proofs that succeed directly on a fresh state (≥ 40 proofs total).
- A2: sandboxed interpreters cannot execute outside their command allowlist (escape-attempt tests).
- A3: no proof reads real host files, contacts external hosts or modifies non-canary data (isolation tests and filesystem audit).
- A4: legitimate-use endpoints work.
- A5: the lab apps are tagged as intentionally vulnerable in code and docs.
**Tests.**
- Self-tests; consumed by T-0497, T-0508.
**Notes.** Where real-world gadgets would be dangerous, the lab uses faithful-but-inert stand-ins whose behavior is still a genuine injection (syntax-level) vulnerability. Results for command injection, deserialization, SSRF and upload execution are therefore reported as "lab-proven at the injection level using inert interpreters" (section 4.1 rule 5), never as proof of protection against real remote code execution.

### T-0497 · AC-38: vulnerable-origin proof (direct exploit works, through HDD it fails and the IP is banned)
