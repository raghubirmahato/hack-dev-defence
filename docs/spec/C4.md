## C11. Volumetric (layer 3/4) DDoS resilience (Tier 1 minimums are required)

### C11.1 Honest premise

A VPS has a finite uplink. A flood larger than that link saturates it before a single packet reaches HDD, so no software on the VPS can stop it. HDD therefore (1) never claims volumetric protection beyond what is contracted upstream and measured (R-10), (2) treats upstream scrubbing as a required dependency for production, (3) implements everything on the host that genuinely helps: early drop, state-exhaustion defense, amplification-proofing, detection and escalation, and (4) limits blast radius so that DNS survives loss of the VPS and the origin stays hidden and firewalled. The Layer 7 defenses work only while the link is not saturated and are never presented as L3/L4 protection.

### C11.2 Readiness questions (ask in the first response; store in `upstream_ddos`)

1. Which hosting provider and plan; is its DDoS mitigation always-on or on-demand; what is the advertised capacity; what exactly happens when it is exceeded (for example a null-route for N minutes)? What is the VPS uplink speed?
2. Is there a mitigation API, a support escalation path, or a separate scrubbing service that can front the VPS (reverse proxy or tunnel)?
3. Does the operator own an ASN (RTBH over BGP is possible only then)? Can a second provider host a secondary DNS and a standby edge?
4. **Decision rule:** `mode: none` is allowed for the pilot only. For apex cutover it is NO-GO unless the operator records `risk_acceptance_volumetric: true` in chat with the date. The agent never infers capacity from lab numbers.

### C11.3 Defense layers

| Layer | What it does | Rust implementation | Verified by |
| --- | --- | --- | --- |
| L0 Upstream scrubbing | Absorbs floods larger than the VPS link | Profile + provider API client in `hdd-shield`; activation runbook | AC-25 (documentation and dry-run only; capacity stays UNVERIFIED) |
| L1 Early drop at the NIC | Cheap per-packet verdicts before the kernel stack | `hdd-xdp-logic` + `hdd-xdp-ebpf` + `hdd-xdp` (aya); nftables `raw` fallback | AC-26 |
| L2 Stack tuning | SYN cookies, backlog and accept-queue sizing, `NOTRACK` for 53/80/443, conntrack sizing, `rp_filter`, socket buffers, IRQ/RSS guidance | `hddctl deploy` (idempotent, reversible) | AC-29 |
| L3 Amplification-proofing | HDD never acts as a reflector: no recursion, `ANY` minimal, RRL, DNS cookies, minimal responses, TC=1 for large answers, measured amplification ratio | `hdd-dns` | AC-28 |
| L4 DNS survivability | External secondary mandatory for cutover; recommended topology: HDD as hidden primary with public NS on an external anycast secondary | TSIG AXFR/IXFR + NOTIFY (AC-21) | AC-28 |
| L5 Blast radius | Origin reachable only from HDD IPs and never present in DNS, mail headers or CT-visible names | C9.12, AC-18 | AC-18 |
| L6 Edge failover | Tier 1: manual or shield-driven swap of proxied answers to `standby_edge_ips` (record change, NOTIFY, TTL-aware). Tier 4: health-probed automatic failover | `hdd-dns` + `hdd-shield` | AC-27 |

### C11.4 L1 specification (`hdd-xdp`)

1. **Stateless-safe default.** XDP acts only on traffic to HDD's public IPs and drops only categories that cannot hit legitimate return traffic: the banned-IP LPM trie (v4/v6, destination ports 80/443 and UDP 443 only, driven by the same ban stream as the fw-agent); TCP SYN without ACK to unpublished ports; invalid TCP flag combinations; bogon/martian and own-address sources; fragments (configurable); unsolicited UDP from reflection source ports (53, 123, 389, 1900, 11211, 19 and others from a configurable list) except from allowlisted peers; per-source token buckets for pps, bps, SYN/s and ICMP/s on published ports. Everything else is `XDP_PASS` to the kernel, where the nftables baseline (conntrack on tracked ports) drops unsolicited traffic. Return traffic for the host's own outbound needs (ACME, feeds, NTP, packages, resolvers) therefore keeps working. A stateful XDP design (for example an LRU map populated from a TC egress hook) needs an ADR.
2. **Allowed inbound by the baseline:** TCP 80/443 (UDP 443 only if HTTP/3 is enabled), TCP+UDP 53, TCP 22 from `ssh_allow_cidrs`, established/related traffic.
3. **Never dropped:** loopback, `admin_cidrs`, port 22 from `ssh_allow_cidrs`, configured provider health-probe and monitoring ranges, and the DNS secondary's addresses.
4. **Safety:** native/generic mode probe with a clear WARN on fallback (the report states the mode and the measured pps, because generic mode on a typical VPS gives modest gains); atomic map updates; a **dead-man detach timer** after every load or policy change (default 120 s) that detaches unless confirmed from a second session (section 2.5); `hddctl xdp status|detach|reload`; per-reason drop counters exported to Prometheus; if neither XDP nor nftables is available, run `Noop` with a WARN and mark AC-26 UNVERIFIED(`environment_unsupported`).
5. **Build and privilege:** the eBPF crate builds with the pinned nightly toolchain and `bpf-linker` through `xtask`; the loader runs in the host agent with only `CAP_BPF`, `CAP_NET_ADMIN`, `CAP_PERFMON`. The only `unsafe` in the workspace lives in `hdd-xdp-ebpf` (ADR required); all decision logic is in the safe, natively tested `hdd-xdp-logic`.

### C11.5 L2 tuning (applied and reverted by `hddctl deploy`, each setting documented with its undo)

`net.ipv4.tcp_syncookies=1`; tuned `tcp_max_syn_backlog`, `somaxconn`, `netdev_max_backlog`; raw-table `NOTRACK` applied **per direction** for the ports HDD serves (valid only because proxy and DNS use the host network without NAT): `PREROUTING` for inbound `tcp dport {80, 443}`, `tcp dport 53`, `udp dport {53, 443}`, and `OUTPUT` for the matching replies (`tcp sport {80, 443}`, `tcp sport 53`, `udp sport {53, 443}`); the host's own outbound client flows (ACME, feeds, SMTP, resolver queries to remote port 53 or 443) stay tracked so their return traffic is never broken; untracked packets get explicit accept rules in input and output; conntrack is sized from available RAM; `rp_filter` strict; `tcp_rfc1337`; ICMP rate limits; file-descriptor limits; NIC ring/RSS/IRQ affinity recommendations printed (applied only when the driver supports it). Settings are validated against the live host in preflight.

### C11.6 Detection and escalation (`hdd-shield`, a host service so it reads host NIC and conntrack counters)

Signals: NIC rx/tx bps and pps against `platform.uplink_mbps` and measured capacity, SYN/s, UDP/s, conntrack fill, softirq CPU, accept-queue overflows, DNS qps, origin health, p99 latency. If `uplink_mbps` is unknown the shield uses relative signals only and reports capacity as UNVERIFIED. States with hysteresis and minimum dwell times:

| State | Entry | Actions |
| --- | --- | --- |
| NORMAL | all signals below 50% of thresholds | baseline limits |
| ELEVATED | any signal above 50% for 30 s | tighten per-source XDP limits; enable under-attack challenge for new clients; alert |
| ATTACK | any signal above 80% for 30 s | strict XDP mode (drop all non-essential UDP); call provider on-demand mitigation API if configured; page the operator; shed non-essential routes; serve cached static content if a cache exists |
| SATURATED | uplink above 90% or the provider signals a null-route | cannot be fixed locally: alert with an incident bundle; if `standby_edge_ips` exist, fail DNS over to them (TTL-aware, expected delay stated); keep the DNS secondary authoritative; record timeline |

Actions that depend on features not yet built are recorded as `skipped(feature_absent)` in the audit event, never silently ignored. De-escalation is one step at a time after a 30-minute quiet period. Every transition writes an audit event, a metric and an alert. Because a saturated VPS cannot reliably alert, the shield also sends a periodic heartbeat to `alerts.heartbeat_url_env` (an external dead-man monitor the operator runs); a missed heartbeat is how the operator learns about saturation. The shield never auto-bans provider ranges, `admin_cidrs` or the origin. Manual control: `hddctl shield status|set <state>|hold|release`. Every action has a documented undo (R-13).

### C11.7 Verification boundaries

1. **Closed lab only** (section 2.6): `hdd-loadgen` generates SYN, UDP, fragment, invalid-flag and reflection-pattern floods inside a network namespace or between two machines the operator owns on a private link, with XDP on, off and in nftables fallback mode. Measure legitimate-traffic success, drop ratio, pps handled, CPU and memory. Publish the lab setup in `docs/lab/`.
2. **Escalation:** the state machine is tested by replaying recorded counter traces into the real `hdd-shield` binary through its normal telemetry interface (a recorded-trace input mode, not a mock), plus live low-rate checks that alerts, heartbeat and audit events fire. Provider API calls run in the provider's dry-run or test mode if it has one; otherwise UNVERIFIED.
3. **Capacity:** always reported as three separate numbers (lab-proven, provider-advertised, verified-live). Verified-live stays empty unless the provider gives measurable evidence.

## C12. Application bugs: exposure management, virtual patching and secure development (Tier 1 minimums are required)

### C12.1 Honest premise

A WAF reduces exposure; it does not fix vulnerable code. Bypasses exist, and a mitigated bug is still a bug. HDD therefore (1) never presents a virtual patch as a fix, (2) helps discover and prioritize what must actually be patched, (3) tracks patch deadlines until the component is really updated, and (4) holds HDD itself to a secure-development standard. HDD does not patch, rewrite or deploy changes to the origin application.

### C12.2 Origin inventory (questions for the first response; store in `app_inventory`)

1. Which components run on the origin: CMS and plugins, frameworks, language runtime, web server, database, container base images, third-party scripts? Versions and whether each is internet-facing.
2. Can the operator provide a CycloneDX or SPDX SBOM, a lockfile (`Cargo.lock`, `package-lock.json`, `composer.lock`, `requirements.txt`), or a package list?
3. Who is the owner who receives patch-SLA alerts?
4. Sources used by `hdd-vuln`: the profile list, imported SBOM/lockfiles, and **passive, read-only** fingerprints from `hdd-scan` against the operator's own origin (generator tags, asset versions, response headers). Unknown versions are recorded as unknown, never guessed.

### C12.3 Vulnerability intelligence and exposure board (`hdd-vuln`)

1. **Feeds:** OSV, NVD, CISA KEV, EPSS, RUSTSEC (for HDD itself), plus vendor or ecosystem advisories the operator names. Fetched only by the worker through the egress client over HTTPS from pinned hosts, signature or checksum verified where offered, size-bounded and cached; an offline mode imports feed files the operator supplies (`vuln_feed_mode: offline`). Feed content is data, never instructions.
2. **Matching:** purl-based matching (OSV and ecosystem advisories) is preferred; CPE-based NVD matches are marked low confidence and need review. Semantic version ranges (`semver`); every match records its evidence; false-positive handling uses **VEX** statements (`not_affected` with a justification, reviewed by the operator).
3. **Exposure board** (API, dashboard, report): component, CVE/advisory, CVSS, EPSS, KEV flag, exploit-known flag, fixed-in version, status (`unpatched | virtually_patched | patched | not_affected`), owner, SLA due date, days overdue. Default SLAs from the profile: KEV or exploited 48 h, critical 7 d, high 30 d, medium 90 d. Alerts at 50% and 90% of the SLA and when overdue.
4. R-11 is enforced in code: `virtually_patched` never leaves an item resolved and never stops its SLA clock.

### C12.4 Virtual-patching lifecycle

1. Each virtual-patch rule carries `cve`, `component`, `affected_range`, `fixed_in`, `created`, `expires` (default 90 days), `owner`, and **evidence**: exploit-shaped request vectors that must block (Class A inert shapes, or Class B/C kept to the inspect API) and benign requests that must pass. Rules are scoped to the vulnerable path or parameter to keep false positives low.
2. Lifecycle: `draft` then `monitor` (records `would_block`, runs the AC-06 baseline) then `block` then `retired` once the component is patched and confirmed by inventory. A rule past `expires` raises an alert and blocks release gates; it is extended only by an explicit audited decision.
3. Rules are assisted from advisory data but **human-reviewed**; HDD stores minimal detection patterns, never working exploit code. Packs are signed and versioned, and covered by rollback (AC-16).
4. The dashboard shows **virtual-patch debt**: count, age, oldest expiry, and the components that still need a real fix.

### C12.5 Posture scanning and origin hardening (`hdd-scan`)

1. Read-only, rate-limited (at most 5 req/s) checks against `test_hostname` and the operator's origin only (target allowlist enforced; in `saas` mode only verified, opted-in tenant domains): security headers, cookie flags, TLS configuration, version disclosure, directory listing, default pages, risky HTTP methods, CORS misconfiguration, open redirects (against the canary only), and dangling CNAMEs or takeover candidates in managed zones (DNS resolution only, no HTTP requests to third-party hosts).
2. Probes for sensitive paths and backup files (which would trip HDD's honeypots and ban the scanner) run against the origin directly from the VPS, which is on the origin allowlist, never through the jail.
3. It never exploits, fuzzes or brute-forces the real application. Active exploit-class tests run only against the sandbox canary or the Vuln-Lab.
4. Output: `docs/ORIGIN-HARDENING.md` (generated) and per-domain findings in S-043/S-044, ranked and each tied to a remediation step: dependency updates, least-privilege database credentials, parameterized queries, input validation, secrets management, authentication hardening, backups, logging. These are recommendations; HDD tracks them but does not perform them.

### C12.6 Secure development of HDD itself

1. **Threat model per feature** (STRIDE delta in `docs/STRIDE.md`), hostile self-review of every diff, `clippy` plus the workspace lint set, `cargo-geiger` (or substitute), and an optional `semgrep` run as an external oracle.
2. **Dependencies:** `cargo xtask deps` weekly (outdated report, `cargo audit`, `cargo deny`, `cargo vet` for new crates). **Advisory SLAs for HDD:** exploited or critical RUSTSEC within 72 h, others within 14 days; every exception documented with an expiry.
3. **Continuous fuzzing:** time-boxed nightly `cargo fuzz` runs on CI or the builder, never on the production VPS, for the normalizer, detectors, tokenizers, DNS parser, HTTP/multipart parsers, the template renderer inputs, and the XDP logic; corpora persisted; any crash blocks release and opens a diagnosis.
4. **Release integrity:** reproducible builds, `cargo-auditable` binaries, SBOM, checksums, `cosign` signatures, `SECURITY.md` disclosure policy and a `security.txt` template.
5. **Signed self-update:** `hddctl upgrade` verifies the signature, stages the new version beside the old one, runs health checks, switches atomically, and rolls back automatically on failure. A tampered or unsigned artifact is rejected. Updates never run unattended without the operator enabling them.

## C13. Authoritative DNS (`hdd-dns`)

1. Bind address and port are configuration (default 53 UDP+TCP with `CAP_NET_BIND_SERVICE`); tests on unprivileged ports use the same code path, there is no dev mode. Types: A, AAAA, CNAME, MX, TXT, NS, SOA, CAA, SRV, **HTTPS/SVCB**; wildcards; CNAME flattening at the apex (HDD resolves the target itself through a bounded, cached, TTL-respecting resolver and never recurses for clients); multi-record RRsets. Serve from an immutable in-memory snapshot (no DB on the query path).
2. **Topology (`dns.topology`).** `self_authoritative`: the NS RRset is `platform.ns_hostnames` and HDD answers the public. `hidden_primary`: the NS RRset is `dns.public_ns` (the external secondary), HDD answers only the secondary's addresses (TSIG transfers, NOTIFY) and refuses other sources. In that topology proxied answers are static data on the secondary, so TTLs stay low and ACME DNS-01 waits until the secondary serves the challenge TXT before validation. AC-03, AC-21 and AC-28 assert per topology.
3. **Orange cloud:** for `proxied=true` A/AAAA/CNAME answer only `platform.public_ipv4/6` (shuffled) and never reveal origin data. If `platform.public_ipv6` is empty, a proxied AAAA is NODATA (never the origin's IPv6). HTTPS/SVCB records of proxied names have `ipv4hint`/`ipv6hint` rewritten to HDD addresses or removed. **Grey cloud:** return the stored value. TXT/MX/NS/CAA/SRV are never proxied. Records for `non_http_services` are forced grey at import and flagged in the parity report, because HDD proxies only HTTP(S) ports.
4. **Import:** every record type is either supported or reported as unsupported or provider-proprietary (ALIAS/ANAME, URL redirects, and so on) in the parity report; parity FAILS on any unacknowledged unsupported type.
5. Auto NS/SOA per topology; SOA serial `YYYYMMDDnn` auto-increments on change; documented TTL and negative-caching (SOA minimum) policy; low TTLs during pilot.
6. **Protocol correctness:** AA flag, NXDOMAIN + SOA in authority, NODATA, correct wildcard and empty-non-terminal behavior, `REFUSED` for foreign zones, RA=0, `ANY` answered minimally (RFC 8482), minimal responses, EDNS0 with a default UDP payload cap of 1232, UDP truncation with TCP fallback, TCP idle timeouts and connection caps, case-insensitive matching with the question case preserved (0x20-safe), response-rate-limiting, DNS cookies, per-source QPS caps, malformed-packet resilience (fuzzed), ACME DNS-01 TXT support.
7. **Zone transfer:** public AXFR/IXFR refused. A **TSIG-authenticated** AXFR/IXFR plus NOTIFY path to the configured `secondary_dns` lets an external provider serve as secondary so the domain survives a VPS outage. Preflight warns when both NS names share one IP or one provider.
8. **DNSSEC:** online ECDSA P-256 signing is opt-in per zone (Tier 3, P32). Do not claim it unless `delv` validates it. Until then HDD serves unsigned zones, which makes the DS check at cutover mandatory (C17).
9. **Multi-tenant additions (v5):** each zone belongs to exactly one org; zone creation requires `domain.status` at least `pending_delegation`; NS pair assignment from the `ns_pairs` pool; per-zone record-count caps by plan; DNS changes publish a snapshot revision and apply within 2 s; the DNS service has no write access to Postgres (read-only role) and receives changes through snapshot revision messages; query logs are aggregated counters only.

## C14. Reverse proxy and TLS (`hdd-proxy`)

1. Ports 80/443 plus `extra_proxied_ports`. Route by SNI and normalized `Host` (reject duplicate Host headers). An HTTP/2 request whose authority is not covered by the connection's negotiated certificate gets **421 Misdirected Request**; coalesced requests that the certificate does cover are allowed. Unknown host gives a branded 404, never a default tenant. Origin client: pooling, connect/read timeouts, **active health checks**, mandatory origin certificate verification per the site's TLS verification mode, no redirect following, loop detection, branded 502/504, optional serve-stale, injection of the secret origin header.
2. Upstream headers: set `X-Forwarded-For` (append), `X-Real-IP`, `HDD-Connecting-IP`, `X-Forwarded-Proto`, `HDD-Ray-ID` (also on every response). Strip untrusted inbound variants first (C9.3).
3. **TLS:** real certificates only. ACME HTTP-01 (tokens in Redis with fallback, served on :80) and DNS-01 (own DNS server); `acme.directory=staging` first, production only after staging passes and only with the operator's confirmation; issuance rate budgeting; renewal when remaining lifetime falls to one third or when ARI says so; hot reload; TLS 1.2 or higher, modern suites, ALPN h2/http1.1; per-site HTTPS redirect and HSTS. **Unknown SNI (including no SNI) gets a TLS `unrecognized_name` alert or handshake failure** (an optional default cert exists behind an explicit flag). Do not build OCSP stapling unless the CA still supports it (verify at build time). Apex certificates are pre-issued through DNS-01 with a CNAME-delegated `_acme-challenge` before cutover.
4. **HTTP hardening:** reject conflicting `Content-Length`/`Transfer-Encoding`, malformed framing and over-long lines/headers; body cap (413); timeouts; strip hop-by-hop; streaming bodies; WebSocket and gRPC passthrough with handshake inspection; all h2 limits from Appendix E4.
5. **Outbound filter** (per-site `outbound_mode` `off|monitor|block`, per-path exclusions): applies to text-like, non-streaming responses only. It buffers a bounded window (default first 64 KiB of the decompressed body, held before headers are released); a larger body is scanned over its prefix and tagged `partial_scan`, and the window limit is documented as a known limitation. Detect DB error leaks (`SQL syntax.*MySQL`, `You have an error in your SQL syntax`, `PostgreSQL.*ERROR`, `ORA-[0-9]+`, `SQLiteException`, `Unclosed quotation mark`, stack traces), secrets and key material, source code markers, directory listings. On a leak in `block` mode return a branded 500 and record a `critical` `data_leak` event. Strip `Server`, `X-Powered-By`, `X-AspNet-Version`, `X-AspNetMvc-Version`; set `Server: Hack-Dev-Defence` (per-site override). Add `X-Content-Type-Options: nosniff` and `X-XSS-Protection: 0`; add `X-Frame-Options`/CSP `frame-ancestors` **only if the origin did not set them** (per-site override and opt-out). Recompute `Content-Length`; never corrupt binary responses.
6. **Resilience:** inspection is local and never fails open. Redis down: local ban cache and limiter. Postgres down: serve from the snapshot and queue events. Events flow through a bounded channel and are batch-inserted (`COPY`); **the hot path never awaits the DB**. Graceful shutdown drains in-flight requests. Backpressure: bounded accept queues and a documented shed policy under overload.
7. **Safe mode** (`hddctl safe-mode on|off`, API, file flag): every site stops inspection, jail and limits while TLS, routing and headers stay. Safe mode never bypasses the access gate (stage 8a) or reserved paths; the gate has its own audited break-glass, `hddctl gate disable --site`. Safe mode is visible in every surface and time-boxed in the UI.
8. **Automatic rollback:** after a rule or pack change, HDD replays known-good probes through the pipeline and watches the changed rule's own hits. If a known-good probe is blocked, or the changed rule blocks at least `rollback.min_distinct_ips` (default 5) distinct IPs within the window with a block-to-pass ratio above the threshold, the change is reverted through `config_revisions` and an alert fires. Site-wide 403/5xx rates alone never trigger rollback, so an attacker cannot force removal of a security rule by generating blocks or origin errors.
9. **Performance budgets (reported at each gate):** proxy-added p99 latency of 5 ms or less, measured server-side as time inside HDD excluding origin I/O wait (histograms). Origin wait is the time blocked on origin connect, TLS, first byte and further body bytes, **including while the outbound filter holds a window for the origin body**; HDD's own CPU time scanning or masking a held window, and queueing on HDD limiters, is HDD time, inspection p50 under 1 ms, memory per 10k idle connections documented, no per-request heap growth in steady state. Deploy tuning (fd limits, `somaxconn`, conntrack sizing, `SO_REUSEPORT`) is owned by `hddctl deploy`.
10. **Tenant additions (v5):** per-site compiled snapshot; per-tenant fairness budgets (max in-flight per site, max inspection CPU share) so one tenant's flood cannot starve others; tenant origin SSRF guard (section 2.9) at connect time; branded error pages use tenant branding and never reveal other tenants.

## C15. Kernel firewall (`hdd-firewall`, run by the host agent)

`Enforcer` trait (`ban(ip,ttl)`, `unban(ip)`, `list()`, `reconcile()`); backends: `Nftables` (primary: sets with native timeouts for v4/v6, rules generated and applied through `nft` with argument arrays or netlink), `IpsetIptables` (legacy fallback, idempotent `-C`/`-I`) and `Noop`. Argument arrays only (never a shell), IPs parsed to `IpAddr` first. Bans apply to the proxied ports only (section 2.4). Startup capability probe with a clear WARN and `Noop` fallback. The `hdd-fw-agent` runs on the host (systemd unit, or a container with `network_mode: host` and `cap_add: [NET_ADMIN]` under the `kernel-fw` compose profile), subscribes to Redis ban/unban and reconciles every 30 s. When the proxy is not in a container, the agent never touches Docker's chains. The agent accepts commands only from Redis messages signed with an internal key and from a root-owned Unix socket used by `hddctl`.

## C16. `hddctl`, `cargo xtask`, `hdd-canary`

**`hddctl` (break-glass; works with the API down):** `preflight`, `safe-mode`, `ban`, `unban`, `import-zone`, `parity-check`, `export-zone` (BIND format), `pki init|issue|rotate`, `deploy [--dry-run]` (Ubuntu/Debian via SSH or local), `backup`, `restore-drill`, `rollback-cutover`, `rotate-keys`, `audit verify`, `config rollback`, `xdp status|detach|reload`, `shield status|set <state>|hold|release`, `upgrade`, `scan`, `admin bootstrap|mfa-reset`, `maintenance on|off`, `signup freeze|unfreeze`.

**`cargo xtask`:** `verify` (fmt, clippy `-D warnings`, nextest, doc-tests, deny, audit, vet, geiger or substitute, machete, SBOM, secret scan, claims-lint, `rust-share`, coverage, i18n check, contrast check, route-permission check, attack-matrix check, OpenAPI contract tests), `ui build|verify` (assets, sprite, CSS bundle, budgets, a11y, visual diff), `spec split|show`, `tasks index`, `gen-secrets` (0600 files), `fixtures`, `bench`, `fuzz-smoke`, `deps`, `acceptance`, `lab`, `release` (build, checksum, cosign; fails if `hdd-vulnlab` is in any shipped graph), `report` (render acceptance report), `grafana`.

**`hdd-canary` (optional, runs on the operator's real origin host):** a tiny Rust static server, bound to the origin's private or allowed interface, serving only the canary files (C16.1) and `GET <base_path>echo-headers`, which returns received request headers as `application/json` with `nosniff` (used to verify `X-Forwarded-For`, `HDD-Connecting-IP`, the secret origin header and the runner's own IP as HDD sees it). It never executes or reflects request bodies. If the operator does not install it, they can install the canary files by hand and the header checks become UNVERIFIED(`capability_not_supplied`) unless `origin_access_log` is provided.

### C16.1 Canary contract (document in `CANARY.md`, generate the files for the operator to upload, then verify)

Inert static files only, under `canary.base_path`, served only for `test_hostname` and `sandbox_hostname` (the sandbox forwards only these exact paths, section 2.1):

1. `ok.txt` containing `hdd-canary-ok`.
2. `leak.txt` containing the harmless sentence `You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version` (verifies the outbound filter).
3. `static.css` or `static.js` with a published SHA-256 (verifies byte-exact pass-through).
4. `search.html`: echoes nothing, so live payloads sent here are inert.

Preflight checks that the files are reachable directly (while `origin.lockdown_state=pending`) and through HDD, and that query strings do not change what is served. If the operator cannot place them, the outbound-leak test is UNVERIFIED(`capability_not_supplied`); never fabricate a leaking endpoint.

## C17. Integration modes and live migration

### C17.1 Integration modes (new in v5)

| Mode | What the owner changes | HDD controls | Certificates | Best for |
| --- | --- | --- | --- | --- |
| `full_ns` | Nameservers at the registrar to HDD's pair | The whole zone, all records, ACME DNS-01 directly | Pre-issue before cutover | Owners who want complete control and apex protection |
| `hidden_primary` | Nameservers to an external secondary that HDD feeds by TSIG transfer | Zone content; the secondary serves | DNS-01 via secondary after it serves the TXT | Highest DNS survivability |
| `cname_partial` | `www` (or other subdomains) CNAME to `<site-id>.edge.{{PLATFORM_DOMAIN}}` plus verification TXT | Only the proxied names | `_acme-challenge` CNAME to `<zone-id>.acme.{{PLATFORM_DOMAIN}}` for pre-issuance, else HTTP-01 after switch | Owners who keep their DNS provider |
| `a_record_partial` | Apex A/AAAA to HDD addresses (or ALIAS/ANAME to the edge name) | Only the proxied names | As above | Apex without moving DNS; owner must track HDD IP changes |
| `subdomain_only` | A single subdomain delegated by `NS` to HDD or pointed by CNAME | One subdomain | As above | Protecting one app on a larger domain |

All modes require ownership proof before activation in `saas` mode. The wizard (S-042) explains each, and the Protection Readiness checks differ per mode (for example, `full_ns` can verify DS/DNSSEC and mail records, `cname_partial` cannot touch mail DNS and says so).

### C17.2 Live migration procedure for the operator's apex (`RUNBOOK-CUTOVER.md`, written and executable)

1. **Pilot:** the operator adds `NS` records delegating **only** the pilot subzone(s) (`test_hostname`, `sandbox_hostname`) to `ns1/ns2.<platform_domain>`, plus ordinary `A` records for `ns1/ns2` in the existing zone (the NS names sit outside the delegated subzone, so no glue is needed). The operator also installs the canary files. The apex site is untouched. The acceptance suite runs here.
2. **Parity gate:** import the full apex zone and run `parity-check`; resolve every unsupported or proprietary record type; confirm `non_http_services` are grey and mail records match (AC-23); run the **DS check** (an unsigned HDD zone behind an existing DS record causes a validation outage); lower TTLs at the old provider to 300 s or less at least one full old-TTL period before cutover and record the parent NS TTL (it bounds NS-based rollback time); take the `export-zone` backup; **pre-issue the apex certificate** through DNS-01 using a CNAME-delegated `_acme-challenge` (staging first, production with the operator's approval) so cutover has no TLS gap; confirm a secondary DNS plan (AC-21) or record the operator's written acceptance of single-VPS DNS risk.
3. **Monitor-first:** run the apex in `monitor` mode through HDD for a baseline period (default 48 h), report false positives, fix rules, then move to `block` per site.
4. **Cutover (only after the operator's written confirmation):** create registrar host objects (glue) for `ns1/ns2` at the registry where the NS names are in-bailiwick, then change NS at the registrar (or point NS at the external secondary for `hidden_primary`); run the propagation probe from several public resolvers; keep the old provider's zone live and mirrored until HDD's answers are confirmed globally; keep old TTLs low for at least one full old-TTL period.
5. **Rollback, two paths.** *Fast (HDD side):* `hddctl safe-mode on`, then switch affected records to grey in HDD's zone; this works only if the origin is reachable directly, so the runbook includes the exact origin-firewall relaxation and its undo. *Slow (registrar):* restore the old NS; time to full effect is bounded by the parent NS TTL (often 24 to 48 h), stated in the runbook. A rehearsed dry run of both paths exists in the pilot.

**Cutover gates.** Apex cutover is NO-GO unless every item holds, or the operator accepts the residual risk in writing in chat for that specific item:

1. `upstream_ddos.mode` is `always_on` or `on_demand` with the contract details recorded (AC-25), or `risk_acceptance_volumetric` is set by the operator with the date.
2. An external secondary DNS is live and answering (AC-21, AC-28), and the mitigation-activation procedure for the provider has been rehearsed in dry-run (AC-27).
3. The exposure board shows no overdue KEV or critical item for the origin and no virtual patch past its expiry (AC-30, AC-31).
4. The operator has reviewed `docs/ORIGIN-HARDENING.md` and the posture scan results (AC-32).
5. HDD's own supply-chain checks are green and a signed-update rollback has been exercised (AC-33).
6. AC-23 (including the DS check) and AC-18 (lockdown applied) pass, and the apex certificate is pre-issued.
7. (v5) Accessibility, identity and tenant-isolation checks (AC-35, AC-36, AC-40, AC-42) pass if the product surfaces are going to be exposed publicly.
