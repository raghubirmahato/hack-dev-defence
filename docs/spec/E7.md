## E7. Canonical names registry

One spelling for every name. Code, docs, tests, UI strings and fixtures use these exactly; a mismatch is a defect. `xtask names check` greps the repository for known variants (for example `hdd_proxy` versus `hdd-proxy`) and for names that appear in this registry but not in the code (or the reverse).

### E7.6 Reserved paths on customer domains

`/__hdd/` is handled by HDD before routing: `/__hdd/challenge/*`, `/__hdd/appeal/*`, `/__hdd/csp-report/<site-token>`, `/__hdd/gate/login` and `/__hdd/gate/link/<id>` (access gate, C19.2), `/__hdd/health` (disabled by default), `/__hdd/static/*` (block/challenge page assets, with SRI). Origins that use the prefix receive a warning at onboarding. Also reserved: `/.well-known/acme-challenge/*` (HTTP-01) and `/.well-known/hdd-verification/*`.

### E7.9 Redis keys and channels

The authoritative list is B5.12; all of it is reached only through the `KvStore`, `Bus` and `Limiter` traits (R-31), and v5.1 adds `hdd:gate:sess:{site}:{token_hash}`, `hdd:flow:{site}:{flow}:{key}` and `hdd:lo:{ua_hash}`. Additions in v5: `hdd:shield:state` (current shield state, heartbeat-guarded), `hdd:fw:ack:{revision}` (enforcement acknowledgments), `hdd:cache:purge` (cache purge channel, Tier 2), `hdd:events:{site}` capped streams for the live monitor, `hdd:node:{id}:hb` (node heartbeats). All keys use the `hdd:` prefix and a documented TTL; no key stores secrets in plaintext.

### E8.1 Decision confirmations the agent must ask for explicitly (never assume)

1. Switching any production-facing site from `monitor` to `block` (with the impact summary).
2. Production ACME issuance (one event per approved request).
3. Any `load` profile run and any destructive resilience/chaos test in production stage (with a maintenance window).
4. Opening public signup (`signup.mode: open`).
5. Cutover of the apex (registrar changes) and the rollback decision deadline.
6. Accepting any NO-GO cutover gate item (item-specific, written, dated).
7. Loosening any threshold in E4 or substituting any technology from section 6 (DEVIATIONS entry).
8. Enabling auto-update, auto-failover, or any Tier 2 to 6 feature that changes the attack surface.
9. Sending any email to an address other than `operator_email` during development.
10. Any volumetric test beyond the closed lab, which needs the provider's written permission.
