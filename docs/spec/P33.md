## PHASE P33: Runtime profiles, local mode, 24/7 hosting and defense completeness (T-0561 to T-0578) · milestone M13 · gate G33

Requirement prefix `RTM`. Goal: one product that runs in two ways. **Local:** on an operator's computer (Windows, macOS or Linux, no Docker required), live only while it runs. **Hosted:** on a server, running 24/7 under a supervisor with backups, upgrades and runbooks. Plus the controls that make coverage as complete as can honestly be shown: an access gate for sensitive paths, API discovery with positive security, business-flow protection, and a coverage map with a "does not cover" list. Read Part C, C18 and C19 and rules R-31 and R-32 first.

Design rules for this phase:
- One code path (R-31). Profile-dependent code lives only in `hdd-local`, `hdd-common::kv`, `hdd-common::profile` and the `Enforcer` factory; `xtask profile-lint` enforces it. Wherever another task says "Redis" for runtime state it means the `KvStore`, `Bus` and `Limiter` traits, and only `hdd-common::kv` talks to Redis (`xtask kv-lint`). Tests that say "real Redis" or "testcontainers" run against both backends, and on a builder without Docker (Track L) against the embedded PostgreSQL and in-process stores.
- Nothing weakens security to be convenient locally. There is no `DEV_MODE`.
- Honest availability: local protection exists only while HDD runs; hosted availability is measured, not promised (section 4).

**Execution order within P33 (the numbering is not the order).** T-0561 to T-0563 run immediately after gate G00 (delivery slice R0, section 0.8) because later phases build on the profile model, the store traits and the embedded database. T-0564 to T-0570 run as soon as their dependencies exist (slice R1, the local walking skeleton, and R2). T-0571 to T-0574 run with the deployment phases (slice R3). T-0575 to T-0577 run after P15 and P17 (slice R4). T-0578 and gate G33 close the phase.

Gate G33 passes when: AC-55 (local runtime, including `profile-parity` with zero verdict differences), AC-56 (24/7 hosting readiness), AC-57 (access gate, API discovery and business flows) and AC-58 (coverage map integrity and absolute-wording lint) pass; the local suite is green on Windows, macOS and Linux CI runners; the hosting check passes on the pilot server with a successful reboot test and a restore drill; and the coverage map lists every mapped category with a status and the "does not cover" section.

### T-0561 · Runtime profile model, capability matrix and the parity contract
`P33` `[OPS][SEC][DOC]` · deps: T-0004, T-0006, T-0009 · size: L · owner: infra
**Objective.** Make `local` and `hosted` first-class, validated profiles that share one code path, and make "same behavior in both" a tested contract.
**Steps.**
1. Write the ADR "One code path, two runtime profiles" recording R-31, the list of things a profile may change, and the enforcement mechanisms below.
2. Add `runtime:` to the live-profile schema (section 8) and the environment variables of B10 (`HDD_RUNTIME_PROFILE`, `HDD_DATA_DIR`, `HDD_LOCAL_*`, `HDD_KV_BACKEND`, `HDD_HOSTING_PROFILE`) in `hdd-common::profile`, with typed validation and JSON Schema output.
3. Encode the capability matrix of C18.2 as code (`Profile::capabilities()`): for each capability (authoritative DNS on 53, kernel enforcement, ACME, `saas`, open signup, `full_ns`, LAN exposure, embedded database, memory store) the result is `allowed`, `allowed_with_ack`, or `unavailable(ERR-LOCAL-001, reason)`. Every refusal path in the API and UI goes through this function.
4. Implement `xtask profile-lint`: fails if `runtime.profile`, `Profile::` or profile `cfg` checks appear in the detection, pipeline, authentication or tenancy crates, or if any crate other than `hdd-common::kv` uses the Redis client (`xtask kv-lint`).
5. Implement `xtask profile-parity`: runs the core SQLi set (M1 to M6 plus variants), the benign corpus, the BOLA suite and a ban lifecycle scenario under both profiles with the same fixtures and compares the decision fields (action, category, subtype, rule_id, hardness, score, threshold, vector, field, evidence) and the ban intent (reason, scope, TTL step), excluding identity key, enforcement backend, `config_revision` and timestamps; any other difference fails (AC-55).
6. Extend `hddctl preflight` with a "what can run here" section: for the detected platform and profile, which acceptance checks can run and which are UNVERIFIED(`environment_unsupported`) with the reason, so a Windows builder without Docker gets an honest plan instead of an error.
7. Extend the first-response protocol output (section 9) with the build-track decision (Track H or Track L) computed from discovery results.
8. Write `docs/LOCAL.md` and `docs/HOSTING.md` skeletons with the comparison table of C18.2.
**Deliverables.**
- profile schema and validation, capability matrix, `profile-lint`, `kv-lint`, `profile-parity` skeleton, preflight section, ADR, docs skeletons
**Acceptance.**
- A1: `local` with `deployment_mode: saas`, open signup or `full_ns` is refused with `ERR-LOCAL-001` at config load and in the API.
- A2: `xtask profile-lint` fails when a profile check is added to `hdd-waf-core` (injected-violation test) and passes on the clean tree.
- A3: `xtask kv-lint` fails when a Redis client call appears outside `hdd-common::kv`.
- A4: `profile-parity` runs on the available backends and reports zero differences on the seed corpus.
- A5: on a machine without Docker, Postgres, Redis, `nft` and `dig`, `hddctl preflight` prints Track L and a correct list of runnable and UNVERIFIED checks, and exits 0 for the build track.
**Tests.**
- Unit: matrix table tests; config validation; integration: parity harness; xtask lint tests with injected violations.
**Notes.** The matrix is the single place that decides what a profile may do. Adding a capability without adding it to the matrix fails `xtask profile-lint`.

### T-0562 · `KvStore`, `Bus` and `Limiter` traits with Redis and in-process backends, and the conformance suite
`P33` `[DP][SEC][QA]` · deps: T-0561 · size: XL · owner: dp
**Objective.** Let every runtime-state feature work against Redis (hosted) or in-process memory (local) with identical semantics, proven by one shared suite.
**Steps.**
1. Define the traits in `hdd-common::kv` exactly as C18.3: `KvStore` operations, the named atomic operations (`rate_window_check`, `challenge_nonce_consume`, `offence_incr_with_decay`, `flow_signal_update`), `Bus` with revisioned messages and gap detection, `Limiter` with `counter`, `exact` and `gcra` algorithms. Keys follow B5.12.
2. Implement `RedisKv` on `fred` with Lua scripts for the named operations (`EVALSHA`, `NOSCRIPT` recovery), pipelining, a circuit breaker with half-open probes, and TLS/auth required.
3. Implement `MemoryKv`: sharded maps with per-key TTL (hierarchical timing wheel or lazy expiry plus a sweeper), named operations under shard locks, a bounded `Bus` on `tokio::sync::broadcast` with revision counters and drop counters, size caps with eviction by TTL then LRU, and **pinned namespaces** (bans, sessions) that are never evicted but are capped with a clear error.
4. Implement the restart contract of C18.3: a `rehydrate(ctx)` step that loads bans, offences and sessions from Postgres into `MemoryKv` before listeners open, with a metric for rows loaded and time taken.
5. Write the conformance suite `kv_conformance` (TTL accuracy ±50 ms, atomicity under 64 concurrent tasks, bus ordering, gap detection and resync, eviction rules, pinned namespaces, large-value limits, key-length limits) and run it against both backends in CI; the Redis run uses testcontainers on Track H and is `UNVERIFIED(environment_unsupported)` on Track L.
6. Publish the usage contract for the tasks that consume the traits: ban store (T-0316), rate limiter (T-0333, including the exact algorithm for auth endpoints and the counter bound), challenge nonces (T-0108, T-0337), session cache (T-0113), config bus (T-0211), live event feed (T-0446), credential-stuffing counters (T-0343), campaign detection (T-0325) and the gate and flow engines (T-0575, T-0577). Those tasks use the traits from the start (section 0.9; `xtask kv-lint` fails any direct Redis use), so there is no later port; this task provides the traits, both backends, the helpers and the suite.
7. Add `MET-hdd_kv_ops_total` and `MET-hdd_kv_latency_seconds`, and a startup refusal: `HDD_KV_BACKEND=memory` with `runtime.profile: hosted` and more than one registered service process.
8. Benchmark both backends (criterion): `MemoryKv` limiter check ≤ 5 µs p99, `RedisKv` ≤ 1 ms p99 in-datacenter.
**Deliverables.**
- `hdd-common::kv` (traits, two backends), conformance suite, ports, metrics, benchmarks
**Acceptance.**
- A1: the conformance suite passes on `MemoryKv` and, where Redis is available, on `RedisKv` with identical results.
- A2: `rate_window_check` agrees with a reference model on 10,000 random request sequences for the counter algorithm (within its documented bound) and exactly for the exact algorithm, on both backends.
- A3: the `rehydrate` contract is tested against a fixture durable source (bans, offences, sessions); the end-to-end restart test with real tables is acceptance A6 of T-0564.
- A4: the bus delivers revisions in order and signals a resync on a forced gap.
- A5: memory use is bounded under a key flood (cap and eviction counters verified); pinned namespaces never evict.
**Tests.**
- Conformance, property tests of TTL and eviction, loom or shuttle tests on the shard-lock logic, chaos (kill Redis), benchmarks.
**Notes.** This task changes how existing tasks store state; it must not change what they decide. The differential check is `profile-parity`.

### T-0563 · Embedded PostgreSQL manager and `cargo xtask db up`
`P33` `[OPS][SEC][DB]` · deps: T-0561, T-0009 · size: L · owner: infra
**Objective.** Give a machine without Docker or a database server a real, private PostgreSQL that HDD manages, so the build, the tests and the local profile all run against real Postgres.
**Steps.**
1. Spike and ADR: choose between the `postgresql_embedded` crate and an equivalent (own downloader over a pinned binary distribution); require SHA-256 and signature verification against the distributor's published checksums, a pinned download host that must be in `egress_allowlist`, an offline bundle path (`--bundle <file>`), and per-OS binaries (Windows x64, macOS arm64 and x64, Linux x64 and arm64).
2. Implement `hdd-local::pg`: install into the data directory, `initdb` with a generated superuser password (not echoed), `scram-sha-256` only, `listen_addresses` loopback (or a Unix socket where available), a restrictive `pg_hba.conf`, `fsync` on, data checksums on, memory settings sized from the host, and a unique port chosen from a configured range.
3. Implement lifecycle: start, wait for readiness, fast shutdown on exit, crash recovery messages, stale `postmaster.pid` handling, and a version marker so a future major-version upgrade runs through dump and restore (never an in-place guess).
4. Create the database and the `hdd_owner` role with a generated password stored in the data directory (0600); the migrations of T-0105 create the other roles, whose generated passwords the manager stores the same way; expose connection URLs to the services through files, not command lines or environment variables.
5. Implement `cargo xtask db up|down|reset|status` for builders (default data directory under `target/` or a configured path), used by tests when Docker is absent, and `hdd-local backup|restore` (logical dump with `pg_dump -Fc --no-unlogged-table-data` via the bundled tools, as `hdd_backup` once T-0105 creates it and as the embedded superuser before that, encrypted at rest with a key from the data directory).
6. Implement ports-in-use detection and clear errors (`ERR-LOCAL-004` guidance), disk-space preflight (at least 2 GiB free), and antivirus-friendly behavior notes for Windows.
7. Add `MET-hdd_embedded_db_up` and `AUD-runtime.embedded_db` events; add the supply-chain record (versions, digests) to the SBOM.
8. Add the embedded server to CI on all three operating systems with a sample migration; when T-0105 and T-0128 land, their migration, RLS and BOLA suites are added to the same jobs and run unchanged (they depend on this task, not the reverse).
**Deliverables.**
- `hdd-local::pg`, xtask commands, ADR, backup and restore, CI jobs
**Acceptance.**
- A1: on a clean Windows runner with no Docker and no Postgres, `cargo xtask db up` produces a working database that accepts a sample migration as `hdd_owner`.
- A2: a binary with a wrong checksum is refused and nothing is started (negative test).
- A3: from another local user account or a LAN address, the database accepts no connection (listener and `pg_hba` tests).
- A4: backup then restore into a fresh data directory reproduces the schema and data (hash comparison).
- A5: once T-0105 and T-0128 exist, their migrations and the RLS cross-tenant tests pass unchanged against the embedded server (a CI job those tasks add).
**Tests.**
- Integration on three OS runners; negative checksum test; listener scan; restore test.
**Notes.** Embedded does not mean weaker: same migrations, same roles, same RLS (R-31). If the embedded route proves unreliable on an OS, the ADR records the substitute (an external server or Compose) and `hdd-local doctor` says so.

### T-0564 · `hdd-local` supervisor: lifecycle, readiness, crash policy, first run, doctor and self-test
`P33` `[OPS][SEC][DP]` · deps: T-0562, T-0563, T-0073, T-0134, T-0208, T-0211 · size: XL · owner: infra
**Objective.** One command that starts, supervises and stops the whole product on a personal computer, safely, with honest status.
**Steps.**
1. Create the `hdd-local` binary with the commands of C18.4 and the in-process service runner: each service crate exposes `run(ctx)`; the supervisor owns the shared `MemoryKv`, the configuration, the data directory and the embedded database handle.
2. Implement the start order and readiness gates of C18.4 (lock, light doctor, database, migrations, rehydrate, snapshot compile and cache, api/web/worker, listeners, DNS), with a 60 s database timeout and precise error messages.
3. Implement task supervision: panic isolation per task (R-09), exponential backoff restarts (1 s to 30 s), the five-in-ten-minutes stop rule with a UI banner and `AUD-` event, and `MET-hdd_watchdog_restarts_total`.
4. Implement graceful shutdown (signal and console-close handling per OS, 10 s drain, database fast shutdown, lock release; on Windows the abbreviated path and a Job Object, C18.4) and the single-instance lock with stale-lock detection.
5. Implement first run: secret generation into the data directory, one-time bootstrap token file (hash stored, 15-minute expiry), printing only the setup URL and the token file path, and `hdd-local token show` for interactive terminals.
6. Implement sleep and wake detection (OS power events with the late-ticker fallback), re-validation of listeners and database, correct expiry of time-bound state, and `resumed_after_seconds` in the runtime page.
7. Implement `hdd-local doctor` (ports, disk, permissions, clock, antivirus or firewall hints, database, certificates, listeners) and `hdd-local selftest` (starts a temporary instance, runs the six mandated payloads through the inspect API and a sandbox route, verifies loopback-only binding of the control plane, verifies backup and restore of a scratch database, and prints PASS/FAIL per item with evidence).
8. Implement `status` with real values only (profile, stores, uptime, listeners, last restarts, snapshot age) and `logs --follow`, with JSON logs rotating at 10 MiB × 5.
**Deliverables.**
- `hdd-local` binary and library, supervisor, doctor, self-test, tests
**Acceptance.**
- A1: from an empty data directory, `hdd-local run` reaches "ready" and `selftest` passes on Windows, macOS and Linux CI runners without Docker.
- A2: killing any single service task results in a restart within 5 s and no outage of the other services (fault injection).
- A3: `Ctrl+C`, SIGINT and SIGTERM produce a clean shutdown within 15 s; on Windows console-close, logoff and shutdown produce the abbreviated shutdown within 5 s; in every case no database process is orphaned, and a stale one is stopped at the next start.
- A4: a second `hdd-local run` against the same data directory refuses to start with a clear message.
- A5: a simulated 10-minute sleep triggers the resume path, and bans that expired during the sleep are treated as expired.
- A6: after a restart of `hdd-local`, bans and sessions created earlier are enforced before the first request is accepted (restart test with the real tables).
**Tests.**
- Integration with real processes; fault injection; clock-jump test; per-OS signal tests.
**Notes.** The supervisor never needs administrator rights for its default configuration.

### T-0565 · Loopback client identity, local ban semantics and the tunnel listener
`P33` `[DP][SEC]` · deps: T-0564, T-0315, T-0316, T-0318, T-0327 · size: M · owner: dp
**Objective.** Make bans, rate limits and reputation work when every local client is `127.0.0.1`, without banning the operator's own browser.

2. Implement the dedicated `tunnel_http` listener (default loopback port 8081) with provider header mappings (`CF-Connecting-IP`, `X-Forwarded-For`, configurable header) and strict header parsing (single value, valid address, no private ranges accepted as client addresses from the internet side).

5. Make the never-ban rules (T-0318) profile-aware: in `local`, loopback is not never-banned, platform addresses and the operator's configured LAN addresses are.
6. Add the UI explanation in S-067/S-068 ("This is a local identity: browser and tool, not an internet address") and the honest limit text of C18.5.
7. Write tests: sqlmap-like user agent banned while the browser identity is unaffected; same user agent from two tools shares an identity (documented); registry flood stays bounded; header spoofing on the normal listener is ignored; spoofing on the tunnel listener uses the header only when the provider is configured; label rotation through the tunnel listener creates no new identities; a tunnel-listener request without the provider header gets 421.
**Deliverables.**
- identity resolver changes, tunnel listener, ban scoping, unban paths, tests
**Acceptance.**
- A1: sending M1 to M6 from a `sqlmap` user agent bans `lo:<hash>` and the dashboard (same machine, browser user agent) stays fully usable.
- A2: a banned `lo:` identity is not blocked on `app` and `admin` surfaces, with `dogfood` off and on.
- A3: `X-Forwarded-For` on the normal listener never changes the client identity (property test).
- A4: 100,000 distinct user agents keep registry memory within its cap.
- A5: `single` mode is refused while any site is in `block` mode.
**Tests.**
- Integration against `hdd-local`; property tests; memory-bound test.
**Notes.** Honest limit: a local process can change its user agent; these bans demonstrate and test the shield, they do not contain a hostile local process.

### T-0566 · Local certificate authority, trust installation and TLS modes
`P33` `[SEC][OPS]` · deps: T-0564, T-0375, T-0354 · size: L · owner: sec
**Objective.** Serve `https://*.hdd.localhost` with certificates a browser can trust, without weakening anyone's trust store.
**Steps.**
1. Implement the name-constrained local CA of C18.6 with `rcgen` (ECDSA P-256, 2-year validity, name constraints for `localhost`, the configured suffix, `127.0.0.0/8` and `::1/128`), key wrapping by DPAPI on Windows, Keychain on macOS and a 0600 file on Linux, and key rotation with overlap.
2. Implement a `local_ca` certificate source in the certificate store (T-0375) alongside `acme`: per-site leaves, 90-day validity, renewal at two thirds, hot reload through the same SNI resolver.
3. Implement `hdd-local trust install|remove|status`: display the fingerprint, require explicit consent, use only non-elevated mechanisms (Windows current-user root store, macOS login keychain, NSS databases for Chrome on Linux, and the Firefox profile database on every OS), record exactly what was installed, and remove exactly that; system-wide Linux install is documented, never automatic.
4. Implement `http_only` mode with its cookie differences (C18.6), the readiness warning, and the refusal when `lan_exposure` is true.
5. Add a verification test that a leaf for a name outside the constraints (`example.com`) fails path validation in a constraint-aware client, and that the CA certificate carries the critical name-constraints extension.
6. Add `AUD-runtime.trust_installed` and `trust_removed`, and the S-136 setup step with the three options (install, browser exception instructions, HTTP-only).
7. Write the browser tests: Chromium trusts a leaf after install in a profile-scoped NSS database; without install the browser shows the expected interstitial; Safari behavior is documented (manual).
**Deliverables.**
- local CA, `local_ca` certificate source, trust commands, tests, docs
**Acceptance.**
- A1: the CA certificate has critical name constraints limiting it to the configured names and loopback addresses (certificate inspection test).
- A2: a certificate for `example.com` signed by the local CA is rejected by a constraint-aware verifier.
- A3: `trust remove` leaves the OS and browser stores exactly as before (before/after snapshots).
- A4: the CA private key is never present in plaintext on disk on Windows and macOS.
- A5: no trust-store change occurs without an explicit consent step (interactive test with consent denied).
**Tests.**
- Unit and integration; browser tests with `chromiumoxide`; negative validation test.
**Notes.** HDD never installs a trust root silently, and never asks for elevation by default.

### T-0567 · Local control-plane hardening: rebinding, CSRF, Private Network Access, bootstrap and loopback-only proof
`P33` `[UI][SEC]` · deps: T-0564, T-0075, T-0080, T-0134 · size: L · owner: sec
**Objective.** Make a browser-reachable control plane safe against hostile web pages and rebinding.
**Steps.**
1. Implement the exact `Host` allowlist (`HDD_ALLOWED_HOSTS`, derived from the surface names only) as the first middleware on every control-plane listener, answering `ERR-LOCAL-003` without routing or detail, plus the loopback-alias behavior of C18.7 item 1 (308 to the surface name, no cookies, `/healthz` only).
2. Implement the `Origin` and `Sec-Fetch-Site` checks of C18.7 item 2 for cookie-authenticated requests only (bearer-only requests are exempt), with the separate rules for WebSocket upgrades, SSE and other GET requests (browsers send no `Origin` on same-origin GET) and mutations, including browsers that omit `Sec-Fetch-*` (fall back to a strict `Origin`/`Referer` rule; missing both on a cookie-authenticated mutation is refused).
3. Ensure no CORS headers are ever emitted by the control plane and that Private Network Access preflights (`Access-Control-Request-Private-Network`) are answered without an allow header; add tests for each.
4. Implement the `/setup` flow (S-136 local): bootstrap token verification (constant time, hash compare, single use, 15-minute expiry, rate limit), disappearance after the first platform owner exists, and MFA enrollment before the first admin session is usable.
5. Implement the loopback-only verification used by `hdd-local selftest`: enumerate own listeners, then from a non-loopback local address try to connect to each control-plane port and fail on any success.
6. Ensure secrets never appear on command lines or child-process environments (inspect the process table in a test).
7. Build a **hostile-page test fixture**: a page served from another origin (and a DNS rebinding server in the lab) that tries fetch, form POST, EventSource, WebSocket and image-beacon CSRF against the local control plane; every attempt must fail.
8. Document the shared-machine limitation and the residual risks in `docs/LOCAL.md`.
**Deliverables.**
- middleware, `/setup` flow, verification routines, hostile-page fixture, tests, docs
**Acceptance.**
- A1: requests with a rebinding `Host` header receive `ERR-LOCAL-003` before any handler runs (test with 50 shapes: case, trailing dot, port variants, IDN, IPv6 literal).
- A2: the hostile-page fixture cannot read or mutate anything through fetch, form, SSE or WebSocket (browser test).
- A3: the bootstrap token works once, expires after 15 minutes, and `/setup` returns 404 after the first owner exists.
- A4: the self-test fails when a control-plane port is deliberately bound to `0.0.0.0` (injected-fault test).
- A5: no secret appears in the process table or `/proc`-equivalent listings during a run.
**Tests.**
- Browser tests; lab rebinding server; fault injection; process-listing test.
**Notes.** This is AC-55's security core; a failure here blocks the local profile from release.

### T-0568 · Local sites, names and the hosts helper; `local_only` onboarding and embedded DNS

**Tests.**
- Browser end-to-end; hosts-file golden tests; DNS conformance subset; SSRF-range tests.
**Notes.** Local sites make the product demonstrable in minutes; they are not a substitute for the hosted onboarding checks.

### T-0569 · Packaging, installers, autostart and the cross-platform CI matrix
`P33` `[OPS][QA]` · deps: T-0564, T-0566, T-0516, T-0518 · size: L · owner: infra
**Objective.** Produce signed, verifiable local-run artifacts for Windows, macOS and Linux, and prove them on each operating system in CI.
