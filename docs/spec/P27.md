## PHASE P27: Vulnerability management, virtual patching and posture scanning (T-0481 to T-0490) · milestone M10 · gate G27

Requirement prefix `VLN`. Goal: help owners find and fix what is actually vulnerable, while the WAF buys time. Vulnerability intelligence feeds, an inventory of what runs on the origin, a matching engine with evidence and VEX, an exposure board with SLA clocks, a virtual-patch lifecycle with expiry, passive fingerprinting, a read-only posture scanner, the generated origin-hardening report, and the acceptance tests.

Non-negotiables: a WAF reduces exposure, it does not fix code (R-11): a `virtually_patched` item is never "resolved" and its SLA clock never stops; HDD does not patch, rewrite or deploy changes to the origin; feed content is data, never instructions; the scanner is read-only, rate limited (≤ 5 req/s), allowlisted to the owner's verified domains (and opted in per domain in `saas` mode) and never exploits, fuzzes or brute-forces the real application; unknown versions are recorded as unknown, never guessed; virtual patches hold minimal detection patterns, not working exploit code.

Gate G27 passes when: feeds ingest from pinned sources (or offline files) with verification; matching reproduces a fixture set with documented false-positive handling; SLA clocks and alerts behave per policy; virtual-patch lifecycle enforces preconditions and expiry; the posture scanner produces the generated report from the sandbox/test hostname without exceeding its rate or leaving its allowlist; and AC-30, AC-31 and AC-32 pass or are UNVERIFIED with exact reasons.

### T-0481 · `hdd-vuln` feed ingestion: OSV, NVD, CISA KEV, EPSS, RustSec and operator-named advisories
`P27` `[DP][API][OPS]` · deps: T-0348, T-0413, T-0214 · size: L · owner: sec
**Objective.** Keep a local, verified, bounded copy of the vulnerability intelligence that matching depends on.
**Steps.**
1. Implement feed adapters in `hdd-vuln`: OSV (bulk ecosystem archives and the API for targeted queries), NVD (JSON 2.0 API with the operator's API key if supplied, rate-limit aware), CISA KEV (JSON catalog), EPSS (daily CSV), RustSec advisory database (git or archive snapshot, for HDD's own dependencies), and a generic "vendor/ecosystem advisory" adapter for operator-named JSON/Atom/CSAF feeds.
2. Fetch only through the egress client from **pinned hosts** (configuration allowlist such as `api.osv.dev`, `osv-vulnerabilities.storage.googleapis.com`, `services.nvd.nist.gov`, `www.cisa.gov`, `epss.cyentia.com`/`epss.empiricalsecurity.com`, `github.com/rustsec/advisory-db` archive URL), HTTPS only, TLS verified, size-bounded (per-feed caps), time-bounded, with `If-None-Match`/`If-Modified-Since` conditional requests and checksum or signature verification where the source offers it (for example OSV archive checksums, git commit signatures for RustSec when feasible); verification failures reject the update and alert.
3. Implement **offline mode** (`vuln_feed_mode: offline`): `hddctl vuln import --file <archive> --sha256 <hash>` imports operator-supplied feed files after verification; the UI states the age of the data (`as_of`) prominently, and staleness thresholds (OSV 48 h, KEV 48 h, EPSS 7 d, NVD 7 d) raise attention items.
4. Normalize into a local schema (`advisories`, `advisory_affected`, `advisory_references`, `epss_scores`, `kev_entries`) with idempotent upserts, source provenance, ranges in a canonical form (ecosystem, package name/purl, introduced/fixed/last_affected events) and aliases (CVE/GHSA/RUSTSEC/OSV ids) merged by alias graph; store only the fields needed (no large descriptions beyond 4 KiB, references capped) to keep storage bounded.
5. Implement content-safety rules: descriptions are treated as untrusted text (escaped in UI, truncated, stripped of HTML), URLs are validated and displayed as text with `rel=noopener noreferrer` links only to allowlisted advisory domains, and feed entries can never change configuration or trigger actions beyond creating matches.
6. Implement scheduling in `hdd-worker`: OSV/KEV daily with jitter, EPSS daily, NVD incremental every 2 hours when a key exists (otherwise daily), RustSec daily; backoff on failures; per-feed health metrics and attention items (`feed_failing`, `feed_stale`).
7. Provide `xtask vulnfeeds verify-ids` used at build time by other tasks (for example virtual-patch packs) to verify CVE identifiers and affected/fixed versions against OSV/NVD, recording `UNVERIFIED(capability_not_supplied)` for any identifier that cannot be verified offline.
8. Write tests: adapter parsing against saved real-format fixtures (OSV, NVD 2.0, KEV, EPSS, RustSec), range normalization (semver, PEP 440, Maven, npm, Packagist, Go pseudo-versions), alias merging, conditional requests, checksum failure rejection, oversize and malformed feed handling, hostile description strings (XSS/CRLF), pinned-host enforcement (a request to an unlisted host is refused), and offline import verification.
**Deliverables.**
- `hdd-vuln` feed layer, schema migrations, `hddctl vuln import`, `xtask vulnfeeds`, tests, docs
**Acceptance.**
- A1: a corrupted or checksum-mismatched feed update is rejected and the previous data keeps serving.
- A2: requests to hosts outside the pinned list are refused by the egress client (negative test).
- A3: all fixture formats normalize into identical canonical ranges where the underlying advisory is the same (alias merge tests).
- A4: feed staleness thresholds produce attention items.
- A5: untrusted advisory text is escaped everywhere it is displayed (XSS corpus).
**Tests.**
- Unit (parsers, ranges), integration (local feed server), security, offline import tests.
**Notes.** NVD's rate limits and API-key policy are checked at build time; do not assume them.

### T-0483 · Matching engine: purl-based matching, version ranges, CPE low confidence and VEX
`P27` `[DP][API]` · deps: T-0481, T-0482 · size: L · owner: sec
**Objective.** Produce accurate, explainable matches between components and advisories with human-reviewable false-positive handling.
**Steps.**
1. Implement the matcher: primary path matches by purl (ecosystem + normalized name) against advisory affected packages with ecosystem-specific version comparison (semver, PEP 440, Maven ComparableVersion, npm semver, Packagist, RubyGems, Go modules, NuGet, Debian dpkg version, RPM); `introduced`/`fixed`/`last_affected` events are evaluated exactly per OSV semantics.
2. Implement the **CPE path** for NVD-only records: matches are marked `confidence=low` with the CPE configuration evidence, require review before alerts, and are excluded from SLA clocks until confirmed (documented to avoid alert fatigue).
3. Record **evidence** for each match: component id and provenance, advisory id and aliases, the matched range and event that matched, the component's version source and confidence, and timestamps; the UI shows an "Why is this a match?" panel.
4. Implement **VEX** support: statements `not_affected` (with justification codes: component_not_present, vulnerable_code_not_present, vulnerable_code_not_in_execute_path, vulnerable_code_cannot_be_controlled_by_adversary, inline_mitigations_already_exist), `affected`, `fixed`, `under_investigation`; each requires a reviewer, a free-text justification, an optional expiry (default 180 days, then re-review), and an audit event; importing OpenVEX/CycloneDX VEX documents is supported with validation.
5. Implement **update triggers**: re-match when advisories change, components change, or VEX expires; incremental matching (only affected components) with batch limits; deduplicate matches per (component, advisory alias set).
6. Implement handling of unknown versions: produce `possible` matches only when the advisory affects all versions or the package has no fixed release; otherwise record "version unknown: cannot assess" counters per component, shown in the exposure views.
7. Implement safe handling of large result sets (cap 10,000 open matches per org with a warning), ranking by risk (KEV, EPSS, CVSS, internet-facing), and pagination.
8. Write tests with a **fixture matrix** (≥ 150 cases): known vulnerable versions across ecosystems with expected matches (for example log4j-core 2.14.1, spring-framework 5.3.17, Django 3.2.0, jQuery 1.12.4, lodash 4.17.15, WordPress core and a plugin version, openssl package versions, Struts 2.3.x), boundary versions (just before/after fix), pre-release/epoch/build metadata cases, multiple ranges per advisory, alias dedupe, VEX transitions and expiry, and false-positive controls.
**Deliverables.**
- matcher, VEX handling, evidence model, tests, docs `docs/EXPOSURE-POLICY.md`
**Acceptance.**
- A1: the fixture matrix produces exactly the expected matches (precision and recall 100% on the fixtures).
- A2: CPE-only matches never raise alerts or start SLA clocks until confirmed.
- A3: VEX statements require justification and reviewer and expire as configured.
- A4: unknown versions never produce confirmed matches.
- A5: re-matching is incremental and idempotent (property tests).
**Tests.**
- Unit matrix, property, integration.
**Notes.** Version comparison libraries are validated against reference datasets per ecosystem.

### T-0484 · Exposure board backend, SLA clocks, alerts and the R-11 invariant
`P27` `[API][DB][UI]` · deps: T-0483, T-0453, T-0436 · size: L · owner: api
**Objective.** Track what remains unpatched, who owns it and how overdue it is, and make it impossible to hide a bug behind a virtual patch.
**Steps.**
1. Implement `vuln_matches` lifecycle with statuses `unpatched | virtually_patched | patched | not_affected`, transitions with preconditions: `patched` requires the component inventory to show a fixed version (or a manual attestation with evidence and reviewer), `not_affected` requires VEX, `virtually_patched` requires an active virtual patch in `monitor` or `block` state (T-0485); a lapsed virtual patch automatically reverts the status to `unpatched` with an alert.
2. Implement **SLA policy** from the profile: KEV or known-exploited 48 h, critical 7 d, high 30 d, medium 90 d, low 180 d (configurable with floors), clock start at match creation, **clock never stops while `unpatched` or `virtually_patched`** (R-11 enforced in code by a single function and a database constraint that forbids setting `closed_at` for `virtually_patched`), days overdue computed server-side.
3. Implement alerts at 50% and 90% of SLA and when overdue (trigger catalog entries `vuln_sla_*`), plus KEV additions affecting known components (`kev_added`) with immediate notification, routed through the notification core (T-0453).
4. Implement the platform **Exposure board** wiring (S-125): components view (all orgs, counts only for tenants without `platform.tenant.read`), matches view with filters, SLA/overdue columns, owner, VEX actions; replace the contract-fixture mode of T-0436 with real data.
5. Implement the tenant **Exposure tab** (S-043): summary tiles (open, overdue, mitigated-not-fixed, unknown-version components), match table, per-item detail with remediation steps (upgrade to fixed-in, vendor links), owner assignment, snooze (max 7 days, reason, cannot snooze KEV/critical overdue), and export.
6. Implement the **virtual-patch debt** metric (count, age, oldest expiry, components needing a real fix) and show it on both views and in weekly digests.
7. Integrate with the **readiness score** (T-0172) and the **cutover gate** indicator (no overdue KEV/critical for the origin and no expired virtual patch); expose `GET /api/v1/.../exposure/summary`.
8. Write tests: SLA math with time injection (including weekends, no business-day calendar), R-11 invariant tests (try to close a virtually patched item through API, SQL and bulk operations; all must fail), alert thresholds, automatic reversion on virtual-patch expiry, snooze rules, RLS, and UI e2e.
**Deliverables.**
- lifecycle service, SLA engine, alerts, UI wiring, tests
**Acceptance.**
- A1: no path (API, UI, direct SQL with the app role) can mark a `virtually_patched` item as closed or stop its clock.
- A2: SLA alerts fire exactly at 50%, 90% and overdue (injected time).
- A3: expiry of a virtual patch reverts the item to `unpatched` and alerts.
- A4: the tenant and platform views agree on counts.
- A5: KEV/critical overdue items cannot be snoozed.
**Tests.**
- Unit (SLA), DB constraint tests, integration, browser e2e.
**Notes.** "Mitigated, not fixed" is the permanent label for virtually patched items.

### T-0485 · Virtual-patch lifecycle engine, evidence harness and signed packs (V10)
`P27` `[DP][API][SEC]` · deps: T-0484, T-0310, T-0245, T-0425 · size: XL · owner: sec
**Objective.** Make scoped CVE mitigations safe to create, test, deploy, expire and retire, without giving anyone a false sense of security.
**Steps.**
1. Implement the `virtual_patches` lifecycle: `draft → monitor → block → retired`, with fields `cve`, `component_id`, `affected_range`, `fixed_in`, `created`, `expires` (default 90 days, max 180), `owner`, `evidence`, `rule_id`, `scope` (path/parameter/method constraints), and `would_block_count` in monitor; transitions enforce preconditions (evidence present, monitor ran at least 24 h with zero benign hits on the baseline replay before `block`, owner assigned).
2. Define the **evidence format**: exploit-shaped request vectors that must block (Class A inert shapes, or Class B/C vectors kept to the inspect API), benign requests that must pass, and the target path/parameter scoping; the harness runs both sets through `hdd-waf-core` in CI for packs and on demand for tenant-authored patches; **minimal detection patterns only**, never working exploit code (lint rejects payloads over size limits or matching a denylist of weaponized artifacts).
3. Provide the **authoring assistant** (human-reviewed): builds a draft rule from an advisory (path/parameter hints, known vulnerable endpoint patterns from advisory references, scoped to the component's detected paths), requires manual completion and review; platform-authored packs are signed (T-0425) and distributed as the "virtual patch pack"; tenant-authored patches live in the tenant's rule set with the same lifecycle.
4. Implement **expiry enforcement**: patches past `expires` raise an alert and block release gates (`xtask verify` fails if a shipped pack contains expired patches); extension requires an explicit audited decision with reason (max 2 extensions); expiring-soon notifications at 14 and 3 days.
5. Implement **retirement**: automatic suggestion when the inventory shows the component at or above `fixed_in`; confirmation by the owner; retirement keeps history; retirement of a patch also re-evaluates the match status.
6. Implement pack integration: virtual patch rules compile into the policy snapshot with their own category (`virtual_patch`), scoped; rollbacks via config revisions; auto-rollback triggers apply as for other rules (C14.8) and false-positive reports link back to the patch.
7. Implement the **debt dashboard** data (count, age, oldest expiry, components still needing a real fix) for admin and tenant views, and metrics (`MET-hdd_vpatch_*`).
8. Write tests: lifecycle preconditions, evidence harness with a seeded pack (≥ 25 patches with block/pass vectors), scope narrowness tests (a patch scoped to `/vuln.php?id=` must not affect other paths), expiry and extension flows, release-gate failure on expired patches, retirement suggestion logic, and signed-pack tamper tests.
**Deliverables.**
- lifecycle engine, evidence harness, authoring assistant, pack tooling, tests, docs
**Acceptance.**
- A1: moving a patch to `block` without monitor evidence or baseline replay is refused.
- A2: each seeded patch blocks its evidence vectors and passes its benign set (100%).
- A3: expired patches fail `xtask verify` and create alerts.
- A4: patches are path/parameter scoped and do not affect unrelated requests in the baseline corpus.
- A5: the lint prevents weaponized payloads from entering evidence.
**Tests.**
- Unit, harness runs, CI gate tests, tamper tests.
**Notes.** AC-31 verifies the lifecycle end to end.

### T-0486 · Passive origin fingerprinting and client-side library detection
`P27` `[DP][API]` · deps: T-0482, T-0164 · size: M · owner: sec
**Objective.** Learn component versions from what the origin already reveals, without probing aggressively, and keep confidence honest.
**Steps.**
1. Implement **passive fingerprinting from observed responses** (headers and sampled HTML only, no extra requests beyond the owner's connectivity test and the posture scanner's allowed requests): `Server`, `X-Powered-By`, `X-Generator`, `<meta name="generator">`, WordPress `?ver=` asset query strings and `/wp-content/plugins/<slug>/` paths with readme versions only if observed in responses, Drupal/Joomla markers, framework cookies (`laravel_session`, `JSESSIONID`), error-page signatures, and static asset names with versions (`jquery-3.5.1.min.js`, `bootstrap.bundle.4.3.1.js`).
2. Implement **client-side library detection** (retire.js-style, but data-driven and offline): a signed fingerprint database mapping file name patterns, content hashes (SHA-256 of known versions), and in-file version comment regexes to library/version; apply to third-party scripts discovered by the CSP/crawl inventory (T-0412) and to the origin's own scripts when the owner opts in; output components with `source=scan`, `confidence=inferred|verified` (hash match = verified).
3. Treat sources of truth: `Server` banners and generators are **claims by the origin** (low confidence); hashes and distinctive file contents are strong evidence; the UI labels confidence and encourages replacing with SBOM data.
4. Implement privacy and limits: sample at most 1 response per distinct path template per hour per site, response bodies are processed in memory for the first 64 KiB only, only extracted tokens are stored, never page content.
5. Implement the **fingerprint database tooling** (`xtask fingerprints build|verify`): sources are open-licensed data; build from release artifacts with hash tables; sign the DB; versioned updates through the same pack mechanism with staged rollout.
6. Integrate with inventory: scan-sourced components are proposed to the owner ("We noticed jQuery 1.12.4 on /shop; add to inventory?") with accept/ignore; accepted items are matched; ignoring is remembered; scan-sourced items auto-expire if not seen for 30 days.
7. Add guard rails: fingerprinting never triggers extra requests to third-party hosts (no fetching of external scripts to hash them, except the SRI advisor's explicit fetch under its own limits), and honors the egress allowlist.
8. Write tests: fixtures of real-world-shaped HTML/headers for ≥ 40 stacks, hash-match verification, false positive tests (strings in documentation pages), confidence assignments, expiry, privacy greps (no page content stored), and DB signature verification.
**Deliverables.**
- fingerprint engine, DB tooling, proposal UI, tests
**Acceptance.**
- A1: fixture stacks yield the expected components with the documented confidence levels.
- A2: no response content beyond extracted tokens is stored.
- A3: tampered fingerprint databases are rejected.
- A4: proposals are accepted/ignored with memory and auto-expiry.
- A5: no extra outbound requests are made to third-party hosts.
**Tests.**
- Unit, fixtures, privacy greps, signature tests.
**Notes.** AG-16 coverage (client-side supply chain) completes here together with T-0412.

### T-0487 · `hdd-scan`: read-only posture scanner with allowlist, consent and rate limits
`P27` `[DP][SEC][API]` · deps: T-0413, T-0164, T-0410 · size: XL · owner: sec
**Objective.** Check the owner's own sites for common misconfigurations safely and repeatably.

2. Enforce **limits**: ≤ 5 requests/s per target, ≤ 300 requests per scan, concurrency 2, 10 s timeout per request, scan duration cap 10 minutes, identification via `User-Agent: HackDevDefence-PostureScan/1 (+https://<public_host>/docs/scanner)` and a documented source IP set so owners can allowlist it; scans are rate-limited per domain (1/hour manual, 1/day scheduled by default).
3. Implement **checks (read-only)**: security headers (HSTS, CSP, XFO/frame-ancestors, nosniff, Referrer-Policy, Permissions-Policy), cookie flags (from responses seen), TLS configuration (versions, ciphers, certificate chain/validity, HSTS preload readiness, ALPN) using the in-house TLS probe (no external service), version disclosure headers, directory listing on common paths **only** on the sandbox/test hostname or paths that responded with indexes, default pages (server welcome pages), risky HTTP methods (`OPTIONS` read, `TRACE` check), CORS misconfiguration (reflect arbitrary Origin with credentials), open redirect probes **only against the canary**, `robots.txt`/`security.txt` presence, HTTP→HTTPS redirect behavior, mixed content hints in fetched HTML, and dangling CNAME/takeover candidates in managed zones (DNS resolution only; no HTTP requests to third-party hosts).
4. Implement **sensitive-path probes** (backup files, `.git/`, `.env`, admin panels) as an opt-in *origin-direct* check run from the VPS (which is on the origin allowlist) so it does not trip HDD's honeypots or bans; results report existence (status/size class) only and never download or store contents beyond the first 256 bytes signature check.
5. Implement **no-exploitation guarantees**: no payload injection, no fuzzing, no authentication attempts, no brute force; the scanner's request builder only supports a fixed set of benign request templates; a static test enumerates all templates and fails on any parameterization beyond the canary token.
6. Output a normalized **findings model** (`scan_runs`, `scan_findings`: id, check id, severity, evidence (headers/status only), remediation key, first_seen, last_seen, status `open|accepted_risk|fixed`), diffing between runs, and accepted-risk with reason and expiry.
7. Wire into UI: S-043 scan summary card, S-044 readiness inputs, a scan history list, "Run scan now" with the consent/allowlist explanation, and links to remediation text (T-0488).
8. Write tests: allowlist enforcement (attempts to scan non-allowed targets abort and are audited), rate-limit adherence (token bucket verified against a counting server), check correctness against fixture origins (good and bad configurations for each check, ≥ 60 fixtures), no-exploitation template test, TLS probe against lab servers with various configs, consent flows in `saas` mode, and BOLA tests.
**Deliverables.**
- `hdd-scan`, `hddctl scan`, findings model, UI cards, tests, docs `docs/SCANNER.md`
**Acceptance.**
- A1: scans of non-allowlisted or non-consented targets are refused and audited.
- A2: measured request rate never exceeds 5 req/s (counting server over 20 scans).
- A3: every check yields correct pass/fail on the fixture origins.
- A4: the scanner sends no payloads beyond the benign templates (static enumeration test).
- A5: findings diff correctly between runs and accepted-risk expires.
**Tests.**
- Unit, fixture-origin integration, rate tests, static gates.
**Notes.** Active exploit-class testing happens only against the sandbox canary or the Vuln-Lab (C12.5).
