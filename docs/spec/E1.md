# Part E: Appendices

## E0. How to use the appendices

The appendices are normative data for the tasks in Part D. Where a task says "the fixture set", "the benign corpus", "the acceptance matrix", "the thresholds", "the gate report" or "the canonical names", it means the corresponding appendix section here. Appendix values may be **tightened** freely by the agent; **loosening** any value requires the operator's approval in chat and an entry in `docs/DEVIATIONS.md` (rule R-15). Every fixture in these appendices is data for tests: the agent writes it into `tests/fixtures/` with the metadata header defined in E1.0, never inlines it into production code, and never sends it anywhere the payload class does not allow (section 2.2).

## E1. Fixtures and payload seeds

### E1.0 Fixture file format and rules

Every fixture file under `tests/fixtures/` starts with a header block of `#`-prefixed metadata lines, followed by one payload per line (lines are literal; leading/trailing spaces are significant and are shown with `␠` in this document only, the real files contain actual spaces). A blank line or a line starting with `#` is metadata. Multi-line payloads use the escape `\n` and are decoded by the loader. Encoded payloads are stored in their encoded form exactly as they appear on the wire. Invisible or control characters are written in this document as `⟦U+XXXX⟧` (for example `⟦U+0000⟧` is a NUL byte); the fixture generator expands each marker to the literal code point, so the committed fixture files contain the real characters. Visible non-ASCII quote lookalikes are shown literally.

```text
# class: A                      # A | B | C (section 2.2); loader rejects files without a class
# category: sqli                # matrix group slug: sqli, xss, traversal, rce, ssti, xxe, ssrf, crlf, redirect, nosql, ldap, jndi, deser, upload, protocol, scanner, honeypot, cms
# subtype: tautology            # optional; see C4 families H1..H8 for sqli
# hardness: hard                # hard | soft | none (benign)
# vectors: query,form,json,xml,multipart,cookie,header,path   # allowed placements
# expect: would_block           # would_block | allow | challenge | would_ban | gated | not_gated | rejected_early | gated_or_rejected
# field_kinds: any              # any | username | password | search | numeric_id | free_text | email
# dialects: mysql,postgres,mssql,oracle,sqlite   # optional
# source: authored | operator | public-corpus   # provenance; public corpora keep their license in lab/LICENSES.md
# heldout: false                # true => never used for tuning (E1.9)
' OR 1=1--
```

Rules: (1) hosts inside payloads use `.invalid` or reserved example names, never a resolvable name; (2) Class C content (resource exhaustion, billion-laughs, zip bombs, heavy queries) is generated at test time by builders in the test crate and is never committed as a file; (3) fixtures are append-only within a gate, a removed line needs a reason in `tests/fixtures/CHANGELOG.md`; (4) `heldout/` files are listed in `.heldout-manifest` with SHA-256 and the loader refuses to include them in tuning runs; (5) every fixture line gets a stable id `fx_<file>_<line-hash>` used in evidence.

### E1.1 The mandated SQL injection set (M1 to M6)

The operator supplied these six payloads. v4.1 referred to "7 required payloads"; the operator's message lists six, so v5 treats the six below as the authoritative mandated set and keeps the seventh v4.1 item (the `#`-terminated tautology) inside the variant family E1.2 where it is covered 100% anyway (`DEV-V5-003`).

| ID | Payload (literal) | Intent | Families (C4) | Dialect validity | Expected verdict |
| --- | --- | --- | --- | --- | --- |
| M1 | `' OR 1=1--` | Quote breakout, always-true predicate, comment truncation | H1 + H2 | MySQL requires a space or control char after `--`; PostgreSQL, MSSQL, Oracle, SQLite accept `--` | hard, `sqli`, would_block, would_ban |
| M2 | `' OR '1'='1` | Quote breakout, string tautology, relies on the application's closing quote | H1 | All dialects | hard, `sqli` |
| M3 | `admin' --` | Authentication bypass by comment truncation after a known username | H2 + H7 | All dialects (MySQL needs trailing space, present) | hard in username and free-text; soft 4 in password field (Balanced), hard in Paranoid |
| M4 | `admin' #` | MySQL-style comment truncation | H2 + H7 | MySQL/MariaDB only; still hard everywhere (intent) | hard, `sqli` |
| M5 | `admin'/*` | Block-comment truncation | H2 + H7 | MySQL, PostgreSQL (nested), MSSQL, Oracle, SQLite | hard, `sqli` |
| M6 | `' or 1=1 LIMIT 1 --` | Lowercase tautology plus row limiter to defeat single-row checks | H1 + H2 | MySQL, PostgreSQL, SQLite; MSSQL uses TOP | hard, `sqli` |

**Matrix obligations (AC-39):** each of M1 to M6 must be a hard hit in every vector of C4.2, in every field kind except the documented password-field softening, after each transformation in E1.2, with the same verdict under the three views (raw, decoded, canonical). The expected ban is created once per source (TTL ladder step 1 = 1 h; test bans 60 s), outside cross-site subresource context.
