# PART C: SECURITY ARCHITECTURE

## C1. Defense in depth

HDD protects the origin even when the origin is vulnerable by stacking independent layers. A failure in one layer must not disable the others, and each layer states how it fails.

| Layer | Threat addressed | Mechanism | Fails | Verified by |
| --- | --- | --- | --- | --- |
| L0 Upstream scrubbing | Volumetric floods larger than the VPS uplink | Provider service (documented, escalation-tested, never claimed beyond contract) | Cannot be fixed locally; alert and DNS failover | AC-25 |
| L1 Early drop | Cheap floods, banned sources, invalid packets | XDP program (`hdd-xdp`) with nftables `raw` fallback | To `XDP_PASS`; kernel baseline remains | AC-26 |
| L2 Stack tuning | SYN floods, state exhaustion | SYN cookies, backlog sizing, NOTRACK for 53/80/443, conntrack sizing, `rp_filter` | Default kernel behavior | AC-29 |
| L3 Amplification-proofing | Reflection through HDD's DNS | No recursion, minimal `ANY`, RRL, cookies, TC=1 | Refuses | AC-28 |
| L4 DNS survivability | Loss of the VPS | External secondary, hidden-primary topology | Secondary keeps answering | AC-21, AC-28 |
| L5 Protocol hardening | Request smuggling, h2 floods, slow attacks, parser abuse | Strict HTTP/1 and HTTP/2 front end with hard limits | Rejects the request/connection | AC-14 |
| L6 Jail | Known attackers | L7 jail (platform, org, site), kernel set for proxied ports, XDP map | Local cache keeps working if Redis is down | AC-08, AC-34, AC-51 |
| L7 Behavior | Floods, brute force, scrapers, scanners | Sliding-window rate limits, bot scoring, proof-of-work challenge, credential-stuffing detection, campaign detection | Local limiter if Redis is down | AC-11, AC-44, AC-48 |
| L8 Request inspection | Injection, XSS, traversal, RCE, upload abuse, protocol/API abuse | Normalizer, hard and soft signatures, structural tokenizers, positive-security hints, virtual patches | **Never fails open** (R-26) | AC-06, AC-07, AC-09, AC-38, AC-39 |
| L9 Response inspection | Data leaks from vulnerable code | Outbound filter (DB errors, traces, secrets, versions), header policy | Passes with `partial_scan` tag beyond the window (documented limit) | AC-10 |
| L10 Origin protection | Bypass of HDD, origin discovery | Secret header, mTLS option, firewall allowlist, no origin data in DNS | Origin refuses non-HDD traffic when lockdown is applied | AC-18 |
| L11 Detection and response | Silent compromise, bad rules | Events, alerts, auto-rollback, revisions, forensics, heartbeat | Local queue; alert via heartbeat absence | AC-13, AC-16, AC-20 |
| L12 Exposure management | Unpatched components | Inventory, feeds, SLAs, virtual patches with expiry | Items stay open (R-11) | AC-30, AC-31 |
| L13 Self-protection | Attacks on HDD itself | Admin-plane isolation, MFA, hardened identity, supply-chain checks, signed updates | Locked down | AC-01, AC-33, AC-35, AC-42 |
| L14 Sensitive paths, API surface and business flows | Exposed admin areas, shadow or over-permissive APIs, abuse of valid business functions | Access gate (C19.2), API discovery and positive security (C19.3), business-flow signals (C19.4) | Gate fails closed; API and flow controls start in `monitor` and never ban on schema errors alone | AC-57 |

## C2. Request lifecycle (data-plane pipeline)

Each stage is a separately testable function with a time budget, a metric, and a defined failure behavior. Any stage can short-circuit with a response. Budgets are initial and re-baselined at the P18 gate.

| # | Stage | Input to output | Budget | On error or overload |
| --- | --- | --- | --- | --- |
| 0 | Accept and connection limits | socket to connection (per-IP caps, global caps) | 10 µs | Drop; `MET-hdd_proxy_shed_total` |
| 1 | TLS handshake | ClientHello to session; SNI to certificate | handshake | Unknown or absent SNI: `unrecognized_name` alert or failure |
| 2 | HTTP framing validation | bytes to parsed request | 50 µs | 400/431/413/501; connection closed on smuggling shapes |
| 3 | Host and route resolution | Host + SNI to site snapshot | 5 µs | Branded 404 (never a default tenant); h2 authority mismatch: 421 |
| 4 | Client IP resolution | peer + headers to `ClientIp` | 2 µs | Peer IP if peer not trusted; strip spoofable headers |
| 5 | Safe-mode check | flag to pass-through | 1 µs | n/a |
| 6 | Jail and allowlist | `ClientIp` to jail verdict | 5 µs (local), 1 ms (Redis fallback) | Local ban cache used; branded 403 with Ray ID |
| 7 | Reputation and geo policy | `ClientIp` to policy action | 10 µs | Allow if lists unavailable (documented); log |
| 8 | Reserved paths | `/__hdd/*`, ACME, verification | 20 µs | Handled by data plane, never forwarded |
| 8a | Access gate (C19.2) | site gate rules to allow, challenge or deny | 20 µs p99 for paths up to 2 KiB (longer paths are decided as gated without full canonicalization); gate sessions come from an in-process cache (5 to 10 s, invalidated over the `Bus`), Redis only on a miss | Fails closed: deny with `ERR-GATE-002` |
| 9 | Rate limiter and business-flow signals | key to allow/429/ban; flow signals (C19.4) | 5 µs p99 in-process; 1 ms p99 with Redis (counters are batched; monitor and challenge decisions never wait on the store, T-0333) | In-process limiter (the `Limiter` trait falls back to `MemoryKv` semantics) |
| 10 | Challenge and clearance | cookie + site mode to pass/challenge | 10 µs | Challenge page |
| 11 | Body acquisition | stream to bounded buffer (prefix) | per policy | `over_limit_policy` (inspect_prefix default) |
| 12 | Normalization and extraction | request to `Vec<Vector>` with raw/decoded/canonical views | 100 to 400 µs | Over budget: `over_limit_policy` |
| 12a | Flow field signals (C19.4 phase B) | declared fields to flow signals | 30 µs | Skipped with a counter; never delays the response |
| 13 | Detection | vectors to matches | p50 under 1 ms | Budget exceeded: block with 503 (never silently pass) unless mode is `monitor` |
| 14 | Decision | matches + policy + mode + exceptions to `Verdict` | 20 µs | n/a |
| 15 | Enforcement | `Verdict` to response, ban intent, event | 100 µs | Event queue full: drop event, count, still enforce |
| 16 | Upstream request build | request to origin request (strip/set headers, secret header) | 20 µs | n/a |
| 17 | Origin exchange | pool, health, timeouts, no redirects | origin | Branded 502/504; serve-stale when enabled |
| 18 | Response processing | origin response to client response | 100 µs CPU + hold window (origin body-wait during the hold is origin time, C14.9) | Outbound modes; header policy |
| 18a | Flow outcome recording (C19.4 phase C) | response status or declared marker to counters | asynchronous | Dropped with a counter; never delays the response |
| 19 | Emission | event, metrics, logs | async | Never awaited on the hot path |

### C2.1 The `Verdict` contract (`hdd-waf-core`)

```
Verdict {
  action: Pass | Block | Challenge | RateLimit | Log
  mode_applied: Off | Monitor | Log | Block
  category: Category            // sqli, xss, ... (B8 list in Appendix E7)
  subtype: Option<Subtype>      // tautology, comment_termination, union, ...
  rule_id: RuleId, rule_version: u32
  hardness: Hard | Soft | Custom | VirtualPatch
  severity: Critical | Error | Warning | Notice
  score: u16, threshold: u16
  vector: Vector                // path, query, form, json, xml, multipart, cookie, header, graphql, ws
  field: FieldRef               // name only; never the value
  field_kind: FieldKind         // password, username, email, numeric_id, search, free_text, header, filename, unknown
  evidence: Evidence            // canonical snippet <= 512 bytes after redaction, with match span
  ban: Option<BanIntent>        // reason, scope, ttl_step_hint, cross_site: bool, explain: PolicyBranch
  config_revision: u64
  truncated: bool, partial: bool
}
```

`BanIntent` is a *proposal*; the proxy's ban policy engine (C6) decides whether it becomes a ban, applying cross-site context, never-ban, allowlists and the TTL ladder. `hdd-waf-core` never performs I/O.

### C2.2 Fail-closed rules

1. An inspection error, panic caught at the task boundary, or budget overrun yields: `Block` (503 with Ray ID) in `block` mode; `Pass` plus a critical event in `monitor`/`log` modes. Never a silent pass in `block` mode.
2. Redis down: local ban cache + local limiter. Postgres down: serve from snapshot, queue events with a bounded disk spill.
3. Snapshot compile failure on update: keep the last good snapshot, alert, and mark the revision `failed`.
4. Config bus gap: resync from Postgres immediately.

## C3. Vulnerable-Origin Shield (doctrine)

### C3.1 Premise

Assume the origin application is exploitable and that its developers will not patch quickly. HDD must still prevent the attack from reaching the application, remove the attacker from the network path, and hide evidence of the vulnerability from the attacker. The shield is a **profile of HDD settings plus extra mechanisms**, not a separate engine.

### C3.2 Honest limits (must appear in `S-003`, `S-057` and docs)

1. Signature and structure based detection can be evaded by techniques not yet in the rules.
2. The shield cannot see attacks that do not traverse HDD (direct-to-origin traffic), so origin lockdown is part of the profile.
3. It cannot detect logic flaws (authorization bugs, business logic) except through heuristics in log mode.
4. Second-order attacks (stored now, used later) are mitigated only on the write path and by response inspection.
5. A virtual patch or the shield never marks a vulnerability fixed.

### C3.3 Mechanisms (V1 to V16)

| ID | Mechanism | Behavior | Tasks |
| --- | --- | --- | --- |
| V1 | Ban on first clear attack | Any **hard** signature hit in `block` mode returns 403 and bans the client IP (outside cross-site subresource context) | T-0273, T-0317 |
| V2 | Declared and detected auth endpoints | Login, signup, reset, API auth paths get strict inspection, tighter rate limits, credential-stuffing detection, failure-response learning | T-0225, T-0274, T-0343 |
| V3 | Field-kind awareness | Parameter names map to field kinds (password, username, email, numeric id, search, free text) with per-kind policy (C4.6) | T-0251 |
| V4 | Learned parameter shapes | Opt-in learning mode observes legitimate traffic (type, charset, max length) per path and parameter; enforcement flags deviations | T-0272 |
| V5 | Outbound leak control | Database error strings, stack traces, secrets and version banners in responses are masked or blocked | T-0408, T-0409 |
| V6 | Write-path hardening | Bodies of POST/PUT/PATCH are always inspected (no prefix skipping below a configurable minimum), with stricter rules on fields likely to be stored (comments, profile, names) to blunt second-order injection and stored XSS | T-0276, T-0287 |
| V7 | Time-based attack detection | Parameter-correlated origin latency anomalies raise events; optional tarpit | T-0277 |
| V8 | Method and content-type hardening | Only declared methods per path; JSON endpoints require JSON content type; unexpected content types in login forms flagged | T-0298, T-0302 |
| V9 | Tripwires | Honeypot paths and parameters (`/.env`, `/phpmyadmin`, decoy login) ban on touch outside cross-site context | T-0233, T-0309 |
| V10 | Virtual patches | Scoped mitigations for specific CVEs with evidence and expiry | T-0310, T-0485 |
| V11 | Admin path restriction | Optional allowlist for `/admin`, `/wp-admin`, `/manager`, other declared admin paths | T-0232 |
| V12 | Upload quarantine | Executable and webshell uploads blocked; archive and image bombs rejected | T-0297 |
| V13 | Success-after-attack tripwire | In `monitor` mode, a 2xx/3xx login success following a request that matched hard SQLi raises a critical "possible authentication bypass" event | T-0274 |
| V14 | Origin lockdown | Direct-to-origin traffic is refused; secret header enforced | T-0405, T-0406 |
| V15 | Attack-diversity ban | One IP triggering three or more distinct attack categories within ten minutes is banned even if each was soft | T-0317 |
| V16 | Campaign detection | Many IPs hitting one endpoint with one attack signature raises the site to elevated protection (challenge for new clients on that endpoint) | T-0325 |

### C3.5 Proof obligations (acceptance)

1. **AC-38 Vulnerable-origin proof (lab).** For each Vuln-Lab endpoint class (login SQLi, search SQLi, numeric-ID SQLi, reflected XSS, LFI, command injection, SSRF fetcher, upload, deserialization): (a) direct exploit succeeds against the Vuln-Lab (Class A proof, non-destructive); (b) the same exploit through HDD in `block` mode with the shield fails (403) and the client IP is banned; (c) a legitimate request on the same endpoint through HDD still succeeds.
2. **AC-39 SQLi ban matrix.** Cross product of the six mandated payloads and variants against every vector in C4.2 and each field kind: 100% `would_block` with category `sqli` and 100% bans in live enforcement outside cross-site context; benign suite 0 false positives.
3. **Oracle campaign (lab).** sqlmap (levels 1 to 3, risk 1 to 2, default tampers plus a published tamper list) through HDD: in `block` mode no data extraction succeeds and the source is banned within the first hard hit; in `monitor` mode, at least 95% of injection-bearing requests are flagged `would_block` (report the exact figure and the un-flagged request classes).

## C4. SQL injection doctrine

### C4.1 Goals

1. Every payload in the **mandated set** (Appendix E1.1) is a hard hit with category `sqli`, in every vector and every field kind except the documented password-field exception, regardless of case, whitespace, comment placement or encoding.
2. A hard hit in `block` mode returns 403 and bans the client IP (progressive TTL), unless the request carries cross-site subresource context (C6.5).
3. Legitimate input containing apostrophes, SQL words in prose, code samples and punctuation does not trigger (benign suite, zero false positives).
4. The detector is explainable: subtype, rule ID, evidence span, and policy branch are recorded.

The **mandated set** is the six payloads supplied by the operator:

| # | Payload | Expected tokens (conceptual) | Hard family |
| --- | --- | --- | --- |
| M1 | `' OR 1=1--` | quote, OR, 1, =, 1, comment | H1 tautology + H2 comment breakout |
| M2 | `' OR '1'='1` | quote, OR, string, =, unterminated string | H1 tautology |
| M3 | `admin' --` | identifier, quote, comment | H2 comment breakout (auth bypass) |
| M4 | `admin' #` | identifier, quote, hash comment | H2 |
| M5 | `admin'/*` | identifier, quote, comment-open | H2 |
| M6 | `' or 1=1 LIMIT 1 --` | quote, or, 1, =, 1, LIMIT, 1, comment | H1 + H2 |

(The v4.1 specification referred to seven payloads while listing six; this edition fixes the mandated set at these six plus the variant families below and records the discrepancy in `docs/DEVIATIONS.md` as `DEV-V5-003`.)

### C4.2 Input surfaces (vectors)

Every one of these is extracted, normalized and inspected with the same detector set, each with its own vector label:

1. URL path segments (decoded per segment), including matrix parameters (`;jsessionid=`).
2. Query string keys and values (duplicates inspected individually and concatenated).
3. `application/x-www-form-urlencoded` bodies (keys, values).
4. `multipart/form-data` text parts, part headers, filenames.
5. JSON (keys and every string leaf; numbers and booleans converted to strings for the numeric-context check; arrays and nested objects up to depth 32), including NoSQL operator keys.
6. XML text nodes, attributes, CDATA (no entity resolution).
7. GraphQL query text and `variables`.
8. Cookies (names and values).
9. Request headers: `User-Agent`, `Referer`, `Origin`, `X-Forwarded-For` (when untrusted it is already stripped; when trusted each hop is inspected), `Accept-Language`, `Content-Type` parameters, custom configured headers, and any header value not on a documented safe list.
10. WebSocket handshake and (opt-in) text frames.
11. Content under `Content-Encoding` (bounded decompression) and chunk-reassembled bodies.

### C4.3 Normalization pipeline (shared by all detectors; `hdd-waf-core::normalize`)

Three views per string (v4.1 rule retained and extended):

1. `raw`: bytes as received, lossily decoded for display only.
2. `decoded`: iterate to fixed point (maximum 3 layers) of: percent-decoding, `%uXXXX`, `+` to space (in query/form), HTML entities (named, decimal, hex, with or without trailing semicolon), JSON `\uXXXX` and `\xNN`, backslash escapes (`\'`), overlong UTF-8 rejected (flag `evasion.overlong_utf8`), invalid UTF-8 handled per policy (flag `evasion.invalid_utf8`), NFKC normalization, null-byte removal (flag `evasion.null_byte`), case folding. **Quote folding:** U+02BC, U+2018, U+2019, U+201B, U+FF07, U+00B4, U+2032 map to `'`; U+201C, U+201D, U+FF02 to `"`; U+FF1D to `=`; U+FF0D and U+2010-U+2015 to `-` (so fullwidth/lookalike payloads fold into ASCII). **Wide-byte (GBK-style) sequences** `%bf%27`, `%df%27`, `%a1%27`... flagged `evasion.multibyte_quote` and also decoded as `'`. Comment tokens (`--`, `#`, `/*`) remain visible because they are signals.
3. `canonical`: `decoded` plus: MySQL versioned comments unwrapped (`/*!50000 union*/` becomes ` union `), inline comments `/**/` replaced by a single space (their presence is recorded as a flag), whitespace variants (`%09 %0a %0b %0c %0d %a0` and Unicode spaces) collapsed to one space, adjacent string concatenations joined (`'un'+'ion'`, `'un' 'ion'`, `CONCAT('un','ion')` where trivially evaluable), `CHAR(39)`, `CHR(39)`, `0x27` evaluated to their literal characters in suspected-SQL context, `${lower:x}`-style lookups unwrapped (shared with JNDI detection), repeated whitespace/punctuation noise bounded.

Rules: the normalizer is **idempotent**, **panic-free**, and **size-bounded** (output at most 4x input, hard cap 1 MiB per string; truncated strings are flagged and handled by `over_limit_policy`). Detectors run on `decoded` and `canonical` and take the union of matches. Evidence snippets come from `decoded` (closest to what the attacker sent).

### C4.4 Detection layers

| Layer | Purpose | Notes |
| --- | --- | --- |
| D0 Prefilter | Aho-Corasick over SQL-relevant tokens; strings with none skip D1 to D3 | Tokens: `'`, `"`, `` ` ``, `--`, `#`, `/*`, `;`, `union`, `select`, `insert`, `update`, `delete`, `drop`, `exec`, `sleep(`, `benchmark(`, `waitfor`, `information_schema`, `0x`, `char(`, `or `, `and `, `\|\|`, `&&`, `xp_`, `sp_`, etc. |
| D1 Hard signature set | Linear-time regex automata for H1 to H8 (C4.5) | Each rule has an ID, subtype, examples, counter-examples |

### C4.5 Hard signature families

Each family lists intent and canonical examples (fixtures hold the full sets, Appendix E1). Matching is case-insensitive, whitespace-tolerant (any run of whitespace, comments, `+`, or `%`-encoded spaces), and applied after normalization.

**H1 Tautology / always-true predicate.** A boolean connector (`or`, `and`, `xor`, `||`, `&&`, or an opening/closing parenthesis sequence preceding them) followed by a comparison whose operands are literals or identical identifiers and which evaluates to true (or is trivially true: `1`, `true`, `'x'`).
Examples: `' OR 1=1--`, `' OR '1'='1`, `" or ""="`, `' or 'a'='a`, `1' or '1'='1`, `') or ('1'='1`, `')) or (('1'='1`, `' || '1'='1`, `' OR 1=1 LIMIT 1 --`, `or 1=1`, `or 2>1`, `' or 'x' like 'x`, `' or 1 --`, `' OR TRUE--`, `' or 1 in (1)--`, `' or 1 between 0 and 2--`.
Notes: bare `or 1=1` with no quote/parenthesis break-out is hard only in numeric contexts or when preceded by a SQL-ish token; otherwise soft 4.

**H2 Quote break-out followed by comment or terminator.** A quote/paren-closing token that closes a context, then a comment starter or statement terminator, with an identifier, string, number or `)` immediately before the quote.
Examples: `admin'--`, `admin' --`, `admin' #`, `admin'/*`, `admin')--`, `admin"--`, `' --`, `'--`, `') --`, `'; --`, `1'#`, `admin' -- -`, `admin'%23`.
Counter-examples (must not match as hard): `O'Brien`, `rock 'n' roll`, `it's -- fine` (quote not directly followed by a comment starter), `'Hello' -- he said`. **Deterministic `#` rule:** a `#` directly after a closing quote is a hard H2 match in every field kind except `password` (soft 4 under Balanced), because MySQL ignores everything after `#` and `admin'#x` is as dangerous as `admin'# `. The one exception: `'#<digit>` (for example `l'#1`, `I'#1 fan`) is **soft 2** when the field kind is `free_text` or `search` (numbering in prose), and stays hard in `username`, `email`, `numeric_id`, `unknown` kinds and on declared auth endpoints. No rule is "borderline": every boundary case lives in `tests/fixtures/sqli/h2-boundary.txt` (listed in E1.11) with its field kind and expected hardness, and the unit tests read that file.
In password fields H2 is **soft 4** (Balanced) or hard (Paranoid) because legitimate passwords may contain such sequences (C4.6).

**H3 UNION-based extraction.** `union` followed by optional `all`/`distinct` then `select`, with arbitrary comment/whitespace between; or an `ORDER BY`/`GROUP BY` ordinal probe after a break-out; `select` list with `null,null` padding or SQL metadata functions.
Examples: `' UNION SELECT NULL,NULL--`, `1 UNION ALL SELECT username,password FROM users`, `' ORDER BY 5--`, `-1 union/**/select 1,@@version,3`.

**H4 Stacked queries and dangerous statements.** `;` followed by a DDL/DML/administrative keyword; known dangerous procedures.
Examples: `'; DROP TABLE users--`, `1; UPDATE users SET`, `; EXEC xp_cmdshell('...')`, `; shutdown --`, `'; INSERT INTO`, `; DECLARE @q`, `; COPY ... TO PROGRAM`.

**H5 Blind, time-based, error-based and out-of-band functions.** Function-call syntax of: `sleep`, `benchmark`, `pg_sleep`, `waitfor delay`, `dbms_pipe.receive_message`, `dbms_lock.sleep`, `randomblob` (large), `extractvalue`, `updatexml`, `exp(~`, `floor(rand`, `utl_inaddr`, `utl_http`, `xp_dirtree`, `xp_fileexist`, `load_file`, `into outfile`, `into dumpfile`, `lo_import`, `pg_read_file`, `openrowset`, `opendatasource`, boolean-extraction shapes like `if(ascii(substring(...)))`, `case when ... then ... else ... end` with `sleep`.
Examples: `1 AND SLEEP(5)`, `'; WAITFOR DELAY '0:0:5'--`, `' AND (SELECT 1 FROM (SELECT SLEEP(5))a)--`, `' || pg_sleep(5)--`.

**H6 Schema and metadata discovery in SQL context.** `information_schema`, `pg_catalog`, `pg_tables`, `sysobjects`, `syscolumns`, `sys.tables`, `sqlite_master`, `all_tables`, `user_tables`, `mysql.user`, `@@version`, `version()`, `database()`, `current_user`, `@@datadir`, only when accompanied by SQL syntax (select/from/union/concat) so prose does not trigger.

**H7 Authentication-bypass idioms.** `admin' or '1'='1'--`, `' or ''='`, `'='`, `' or username like '%admin%'--`, `' having 1=1--`, `' group by x having 1=1--`, `admin' and 1=1--`. Largely covered by H1/H2; listed so each has an explicit fixture and subtype `auth_bypass`.

**H8 Evasion constructs in SQL context.** Versioned comments with SQL keywords, hex/CHAR/CHR construction of quotes or keywords near SQL tokens, scientific-notation keyword glue (`1e0union`), `/*!50000select*/`, `%00` inside keywords, concatenation of keyword parts, nested comment tricks, mixed-case keyword with comment-as-space.

### C4.6 Context policy (field kinds)

Field kind is inferred from parameter name (case-insensitive tokens), declared mappings in S-057, learned shapes, and header/cookie vector.

| Field kind | Name hints | Policy |
| --- | --- | --- |
| `password` | `pass`, `passwd`, `pwd`, `password`, `secret`, `pin` | H1 (with break-out), H3, H4, H5, H6 hard. H2 soft 4 (Balanced) or hard (Paranoid). All other soft signals disabled. |
| `username` / `email` | `user`, `login`, `uname`, `email`, `mail` | All hard families. Apostrophes inside email local parts and names allowed unless followed by SQL syntax. |
| `numeric_id` | `id`, `*_id`, `uid`, `pid`, `page`, `limit`, `offset`, `num`, `qty`, `count` or learned numeric | Any quote, comment, or SQL keyword is at least soft 4; any H-family is hard. |
| `search` | `q`, `s`, `search`, `query`, `keyword`, `term` | H1, H3, H4, H5, H6, H7 hard; H2 hard only when preceded by an identifier/number and followed immediately by a comment; soft signals halved for natural-language-looking input (long, high word ratio, no SQL punctuation). |
| `free_text` | `comment`, `message`, `body`, `description`, `bio`, `note` | Same as search, plus stored-content hardening (V6): `<script`, SQL stacked patterns scored harder. |
| `filename` | multipart filename | H3, H4, H5 hard. |
| `header` / `cookie` | | All hard families. |
| `unknown` | | Treated as `search`. |

### C4.7 Soft signals (additive; weights default; scoring in `docs/SCORING.md`)

| Signal | Weight |
| --- | --- |
| Quote or comment character in a `numeric_id` field | 3 |
| `--`, `#`, `/*` in a non-prose field | 2 |
| `select` and `from` both present, SQL-looking | 3 |
| `insert into`, `update ... set`, `delete from` shapes | 3 |
| `;` followed by SQL keyword (not in H4 list) | 2 |
| Boolean operator adjacent to a quote | 2 |
| `order by <n>` / `group by <n>` after break-out | 2 |
| SQL function-call syntax (`concat(`, `substring(`, `ascii(`, `char(`, `hex(`, `ifnull(`) each, capped | 2 |
| `null,null,...` padding | 3 |
| `@@` system variables | 3 |

### C4.8 Evasion catalog the detector must handle (each has fixtures)

1. Case: `SeLeCt`, `oR`. 2. Whitespace: tabs, newlines, `/**/`, `%0a`, `+`, non-breaking space. 3. Comments: `--`, `-- -`, `#`, `/* */`, `/*!`, nested. 4. Encoding: single, double, triple URL encoding; `%u0027`; HTML entities; JSON escapes; mixed. 5. Unicode: fullwidth and lookalike quotes; right-single-quote U+2019; U+02BC modifier letter apostrophe. 6. Wide-byte: `%bf%27`. 7. Numeric: `1e0`, hex numbers, `0b1`. 8. Concatenation: `'a'+'b'`, `CONCAT`, `||`, adjacent literals. 9. Hex/char construction. 10. Parameter pollution: payload split across duplicate params or across array parameters `a[]=...`. 11. Content-type confusion: JSON payload in a form or vice versa; wrong content type with correct body. 12. Method override headers. 13. Chunked and padded bodies placing the payload after `inspect_body_max_bytes` (policy handles it). 14. Multipart tricks: unusual boundaries, duplicate Content-Disposition, `filename*`. 15. HTTP/2 header casing/dups. 16. Path-based injection: `/item/1'or'1'='1`. 17. Cookie-borne injection. 18. Header-borne injection (`User-Agent`, `Referer`, `X-Forwarded-For`). 19. Second-order: stored value later reused (write-path hardening + outbound). 20. Out-of-band via DNS exfil functions.

### C4.9 False-positive controls

1. The benign suite (Appendix E2) is run on every detector change; **zero** matches allowed (R-23).
2. Counter-example lists are part of every rule's test file.
3. Prose heuristics: a string with at least 5 words, sentence punctuation, and no SQL operators is treated as prose for soft signals; hard families still apply.
4. Names and addresses (apostrophes, hyphens, `#` as number sign in addresses like `Apt #4`) are explicit counter-examples; `#` is a comment signal only after a quote.
5. Developer-oriented sites (Q&A, docs) can set the `code_friendly` site option that lowers soft weights in `free_text` and requires a break-out context for H1 and H2 (hard families that need no break-out remain).
6. A per-rule, per-path exception (S-064) is the only supported way to remove a detection locally, and it requires an expiry.

### C4.10 Ban policy for SQLi (decision table; full policy engine in C6)

| Situation | Response | Ban |
| --- | --- | --- |
| Mode `off` | pass | none |
| Mode `monitor` or `log`, hard hit | pass; event with `would_block=true` and `would_ban=true` | none |
| Mode `block`, hard hit, normal browsing context | 403 with Ray ID | **Yes**: IP key (IPv4 /32, IPv6 /64), ladder step by offence count; kernel set; global-jail evaluation |
| Mode `block`, hard hit, `Sec-Fetch-Site: cross-site\|same-site` with subresource `Sec-Fetch-Dest`, or cross-origin `Referer` | 403 with Ray ID | **No** (anti-poisoning); counted in `cross_site` counter; three in 60 s from one IP escalates to a rate-limit ban |
| Mode `block`, soft score at or above threshold | 403 | After 3 within 10 min (Balanced) or immediately (Paranoid) |
| Hard hit from a never-ban IP | 403 | **No**; critical alert "never-ban IP attempted an attack" |
| Hard hit from a tenant-allowlisted IP (`skip_inspection=false`) | pass; event `would_block` | none |
| Hard hit from a tenant-allowlisted IP with `skip_inspection=true` | pass; not inspected | none (documented risk) |
| Hard hit within a Vuln-Lab or acceptance run | 403 | Yes, with TTL 60 s (test bans) |

### C4.11 Auth-endpoint behavior

For declared or detected authentication endpoints (`auth_endpoints`): every parameter is inspected (no prefix skipping), the strict profile applies, rate limits use the auth class (Balanced default 10/min per IP per path, Paranoid 5/min), failures feed credential-stuffing detection (P17), and the V13 tripwire applies in `monitor` mode. Responses to blocked login attempts are identical to other blocks (no hint that the endpoint is special).

### C4.12 Telemetry and evidence

Every hard hit stores: Ray ID, site, client IP key, subtype, rule ID/version, vector, field name, field kind, canonical evidence window (up to 512 B, redacted), policy branch, ban ID, config revision. Metrics: `MET-hdd_sqli_hard_hits_total{subtype,vector,field_kind}`, `MET-hdd_sqli_bans_total`, `MET-hdd_sqli_cross_site_nobans_total`. The UI (S-054, S-057, S-065, S-066) shows these without the raw payload beyond the redacted evidence.
