## PHASE P30: Deployment, backup, upgrade and operations (T-0521 to T-0530) · milestone M11 · gate G30

Requirement prefix `OPS`. Goal: make production operation boring: a final deployment architecture and installer, a complete `hddctl deploy`, backups with restore drills, upgrade and migration discipline, monitoring and alerting with runbooks, key rotation, environment management and a full disaster-recovery drill.

Non-negotiables: binaries are built on the builder and installed signed (never compiled on the VPS); every host-changing command has `--dry-run`, an exact undo and the timed auto-revert pattern where connectivity could be lost (section 2.5); backups are encrypted and restore-tested; secrets are generated and stored per policy (0600 files, systemd credentials, never in images or compose files); production changes follow the announced-window rules (section 2.7).

Gate G30 passes when: a clean VPS can be brought to a working production-shaped deployment by `hddctl deploy` alone; a total-loss disaster recovery drill meets the stated RTO/RPO; an upgrade and a forced rollback succeed; key rotations complete without downtime; monitoring, alert rules and runbooks cover every alert; and AC-54 passes.

### T-0521 · Deployment path ADR and the production artifact set (systemd units, container images, installer)
`P30` `[OPS][DOC]` · deps: T-0212, T-0518 · size: L · owner: ops
**Objective.** Decide the default production topology and produce the artifacts that realize it.
**Steps.**
1. Write the **deployment path ADR**: systemd with signed release binaries (default; best for `network_mode: host`, XDP/nftables privileges and port 53) versus container compose for the control plane (acceptable for web/api/worker/mailer) versus full compose; decision matrix covering security, privilege model, upgrade/rollback, observability, resource isolation, operator skill; final recommendation: **hybrid** — data plane and host agents (proxy, DNS, fw-agent, XDP, shield) as systemd services with hardened units; control plane services as systemd services too by default, with a compose profile for operators who prefer containers; Postgres and Redis from distro packages bound to loopback/Unix sockets.
2. Produce final **systemd units** for all services with sandboxing (`DynamicUser` where state is not needed, otherwise dedicated users), dependency ordering (`After`/`Requires`/`PartOf`), restart policies with backoff and rate limits, `LimitNOFILE`, `MemoryMax`, `CPUWeight`, watchdog integration (`sd_notify` `WATCHDOG=1`, `Type=notify`), credentials via `LoadCredential`, and `systemd-analyze security` targets; units are generated from templates by `xtask units` and golden-tested.
3. Produce **container images** (multi-stage `cargo-chef`, non-root, read-only root filesystem, digest-pinned bases, minimal runtime such as distroless or scratch with CA bundle, no shell), health checks, and SBOM/provenance per image; compose files: `docker-compose.yml` (dev), `docker-compose.lab.yml` (lab, includes Vuln-Lab profile guarded), `docker-compose.prod.yml` (control-plane profile only, no host-network data plane), with secrets via files not env, `internal` networks, and no published DB/Redis ports.
4. Produce `deploy/install.sh` (thin, auditable, checksum-verifying bootstrapper that downloads `hddctl` and verifies its signature, then hands over to `hddctl deploy`), with `--dry-run` and no piped-to-shell patterns in documentation (instead: download, verify, inspect, run).
5. Define the **filesystem layout** and ownership (`/etc/hdd`, `/var/lib/hdd`, `/var/log/hdd` (or journald), `/run/hdd`, `/opt/hdd/releases`), tmpfiles.d rules, logrotate, and journald limits.
6. Define the **network layout** and port map (authoritative in Appendix E7) with bind addresses per service; verify with a script that listens on only intended ports.
7. Document **resource sizing** profiles (S/M/L VPS) tied to the capacity model (T-0512) and cgroup limits per service.
8. Write tests: unit-file golden tests, `systemd-analyze verify` in CI, image build reproducibility and non-root checks (`docker run --user` tests), compose config validation (`docker compose config` with policies: no `privileged`, no `latest` tags, no published DB ports) via a policy test.
**Deliverables.**
- ADR, `xtask units`, systemd templates, Dockerfiles/compose, installer, layout docs
**Acceptance.**
- A1: all units pass `systemd-analyze verify` and meet the security score targets.
- A2: compose policy test rejects seeded violations (privileged, latest, published DB port).
- A3: images run as non-root with read-only roots (test).
- A4: the installer verifies signatures before executing anything and supports `--dry-run`.
- A5: the port map in docs matches an actual listening-port scan of a test install.
**Tests.**
- Golden, policy, VM install test.
**Notes.** The ADR slot referenced in P00 (deployment path) is settled here; T-0212's earlier ADR is superseded by this final decision.

### T-0522 · `hddctl deploy` v1: full production deployment, idempotent, with dry-run, health checks and rollback
`P30` `[OPS][SEC]` · deps: T-0521, T-0468, T-0469 · size: XL · owner: ops
**Objective.** One command takes a clean Debian/Ubuntu VPS to a hardened, working HDD deployment, and can undo it.
**Steps.**
1. Extend `hddctl deploy` to the full stack: users and directories, Postgres and Redis (hardened configuration, authentication, Unix sockets/loopback, TLS optional), database roles per service (least privilege: `hdd_api`, `hdd_worker`, `hdd_proxy` (config read, `waf_events_ingest` insert only), `hdd_dns` (read-only views plus `waf_events_ingest` insert only), `hdd_readonly` (analytics), `hdd_backup` (backup jobs only), `hdd_owner` for migrations only), migrations, secret generation (`xtask gen-secrets` equivalents in `hddctl`), certificate stores, systemd units from release artifacts, firewall baseline (T-0468), kernel tuning, hardening (T-0469), XDP loader (if supported and enabled), fw-agent, shield, mailer/SMTP config, admin bootstrap (`hddctl admin bootstrap` with MFA enrollment link), and initial health checks.
2. Implement **phases with checkpoints:** preflight → plan (`--dry-run` prints the complete plan with diffs) → apply by stage with persisted state (`/var/lib/hdd/deploy-state.json`) so a failed run resumes idempotently; each stage has an `undo` and a verification.
3. Implement **remote execution** over SSH (`russh`) with host key pinning, a connection through the operator's bastion if configured, sudo handling, and strict command construction (argument arrays); no password logins; the second-session confirmation mechanism for lockout-prone stages.
4. Implement **config rendering** from `hdd.live.yaml`/`hdd.yaml` with validation (schema version 5), secrets only by reference, and a diff view; changes to running systems use `hddctl config apply` with the same safeguards.
5. Implement **post-deploy verification suite:** service readiness, port exposure scan (only intended ports), TLS endpoint check (staging certs in pilot), DNS self-query, proxy-to-canary path, database role privilege assertions (`has_table_privilege` checks), file permission audit, systemd security scores, `smoke` acceptance tier, and a deploy report with hashes (no secrets).
6. Implement **rollback**: `hddctl deploy --rollback` returns to the previous release/config (binaries, units, config); `--uninstall` removes HDD cleanly (documented data retention options) and restores firewall/resolver settings from the pre-deploy backup.
7. Implement **multi-host awareness (Tier 1: single host)**: the state model is host-scoped so future multi-node deployments reuse it; deploying a standby edge (T-0478) uses the same command with `--role edge-standby`.
8. Write VM-based integration tests (Debian 12 and Ubuntu 22.04/24.04): clean install, re-run no-op, interrupted run resume, rollback, uninstall, lockout simulation, failure injection per stage, and idempotency under partial state.
**Deliverables.**
- `hddctl deploy` v1, state machine, verification suite, tests, runbook
**Acceptance.**
- A1: a clean VM reaches a healthy deployment in one command (≤ 15 minutes excluding downloads) and passes the post-deploy suite.
- A2: re-running changes nothing; interrupted runs resume correctly.
- A3: injected failures at every stage lead to a clean rollback or resumable state.
- A4: no secret appears in output, logs or state files except in 0600 secret files.
- A5: role privilege assertions confirm the least-privilege model.
**Tests.**
- VM integration (CI nightly), failure injection.
**Notes.** The operator's production deployment uses this command in P31 after approvals.

### T-0523 · Backup, encryption and restore-drill automation (AC-54, part 1)
`P30` `[OPS][SEC]` · deps: T-0522, T-0435 · size: L · owner: ops
**Objective.** Make backups routine, encrypted and proven restorable.
**Steps.**
1. Define the **backup set:** Postgres (base backups + WAL archiving via `pgBackRest` or `wal-g`, or `pg_dump` custom format run as `hdd_backup` for small installs (`BYPASSRLS` is required because `FORCE ROW LEVEL SECURITY` would otherwise dump zero tenant rows; restore tests compare tenant row counts, not only the schema); choose in an ADR with RPO targets: 15 minutes with WAL, 24 h with dumps), the encrypted certificate and key store, `/etc/hdd` configuration (secrets separately escrowed), DNS snapshot (reconstructible from Postgres), audit anchors, deletion ledger, and Redis (not authoritative: optional RDB snapshot for ban continuity; documented that bans also live in Postgres).
2. Implement `hddctl backup run|list|verify|prune`: encryption with `age` (recipient public keys stored on the host; private key escrowed offline by the operator, never on the VPS), compression (zstd), integrity manifests (SHA-256), destinations (local directory, SFTP, S3-compatible with object-lock option), retention (daily 14, weekly 8, monthly 12 by default), and bandwidth throttling; backups run from a systemd timer with random delay; failures alert via notification routing.
3. Implement **secrets escrow guidance:** master key/pepper/PKI backups are stored separately from data backups (operator-held), with a printed recovery sheet template; losing the master key means encrypted data (certificates, integration secrets) is unrecoverable — stated plainly in the docs and the UI before first use.
4. Implement `hddctl restore-drill` (and the S-124 UI action): provisions an isolated scratch environment (compose profile `drill` or a throwaway VM/namespace), restores the latest backup, runs integrity checks (row counts per table vs manifest, audit chain verification, certificate decryption test with the escrowed key, deletion ledger replay, DNS answers for sample zones from the restored snapshot, migrations state), measures RTO and RPO, and writes a signed drill report; failure raises attention items; drills are scheduled monthly.
5. Implement `hddctl restore` for real recovery (maintenance mode required, typed confirmation, pre-restore safety backup of the current state, ledger replay, post-restore verification); restore to a new host is supported (T-0529).
6. Protect backups: backup destination credentials stored encrypted; backup files never contain plaintext secrets (scan); access logging; periodic verification of random backup objects (decrypt + checksum) without full restore.
7. Document **backup security** (what an attacker with a backup can/cannot do), immutable/offsite recommendations, and a restore checklist.
8. Write tests: backup/restore roundtrip with real Postgres, WAL point-in-time recovery to a timestamp, encryption verification (wrong key fails), tamper detection, retention pruning, ledger replay, plaintext-secret scan, and drill automation in CI with a small dataset.
**Deliverables.**
- `hddctl backup|restore|restore-drill`, systemd timers, drill reports, docs
**Acceptance.**
- A1: a restore drill completes with all integrity checks passing and measured RTO/RPO recorded.
- A2: point-in-time recovery restores to the requested timestamp (within WAL granularity).
- A3: backups contain no plaintext secrets (scanner) and fail decryption with the wrong key.
- A4: tampered backups are detected on verify.
- A5: failed backups raise alerts within one schedule interval.
**Tests.**
- Integration with Postgres, PITR tests, drill in CI.
**Notes.** AC-54 completes in T-0529 with the full DR drill and T-0524 upgrade tests.

### T-0524 · Upgrade and migration discipline: expand/contract, version skew, canary upgrade and rollback tests (AC-54, part 2)
`P30` `[OPS][DB][QA]` · deps: T-0518, T-0522 · size: L · owner: ops
**Objective.** Make upgrades safe by construction: schema changes that tolerate version skew, tested rollbacks and a staged rollout.
**Steps.**
1. Define the **migration policy** (`docs/MIGRATIONS.md`): every migration is classified `expand` (additive, backward compatible), `backfill`, or `contract` (removal after all code stopped using it); `contract` migrations ship at least one minor release after the code change; migrations are forward-only in production with documented compensating procedures, except those marked reversible and tested; destructive operations require two-release deprecation.
2. Implement **migration linting** (`xtask migrations lint`): blocks risky patterns without justification (`DROP COLUMN/TABLE`, `ALTER COLUMN TYPE` that rewrites large tables, `NOT NULL` additions without defaults, non-concurrent index creation on large tables, long locks), requires `SET lock_timeout`/`statement_timeout`, checks RLS policy presence for new tenant tables, and ensures partitioned table handling.
3. Define **version skew rules**: control plane and data plane may differ by one minor version during an upgrade window; message and snapshot formats are versioned and tolerant (unknown fields ignored, required fields additive); the proxy/DNS refuse snapshots with a newer major schema; tests run old binaries against new schemas and vice versa for the supported skew.
4. Implement the **upgrade orchestration** in `hddctl upgrade` for multi-service sequences: database expand migrations first, then data plane (proxy/DNS) with connection draining and zero dropped connections beyond the documented cap, then control plane, then contract migrations on a later release; each step has health gates and abort/rollback logic; canary upgrade option (upgrade one proxy listener first / one worker) with automatic comparison of error rates and latency before proceeding.
5. Implement **config schema migrations** (`schema_version` upgrades with `hddctl config migrate --dry-run`) and policy document upgrades with fixtures from every past version.
6. Build the **upgrade test matrix** in CI: N-1 → N upgrade with live traffic generator (error budget < 0.01%), N → N-1 rollback (reversible migrations only), skipped versions policy (supported N-2 → N via sequential), and failure injection at every step.
7. Implement **maintenance communication**: pre-upgrade announcement banner (T-0433), status page note, and post-upgrade verification summary.
8. Write the **zero-downtime verification**: during an upgrade, a synthetic client sends 500 rps through the proxy and the success rate must remain ≥ 99.99% with no block-mode fail-open (mandated payload still blocked throughout).
**Deliverables.**
- migration policy and linter, orchestration, test matrix, docs
**Acceptance.**
- A1: the migration linter rejects seeded risky migrations and accepts expand-style ones.
- A2: N-1 → N upgrade under traffic meets the error budget and never fails open.
- A3: rollback tests pass for reversible releases and the forward-only path is documented.
- A4: skewed versions interoperate for the supported window (tests).
- A5: config and policy migrations round-trip all historical fixtures.
**Tests.**
- Upgrade matrix on VMs, linter tests.
**Notes.** The proxy keeps serving from its last snapshot throughout control-plane upgrades.

5. Implement **rotation scheduling and reminders:** attention items when a key exceeds its rotation period; audit events for every rotation; S-119 shows key age (not values).
6. Test **zero-downtime**: rotate each class under 500 rps traffic and admin activity, verifying no 5xx increase, no forced logouts (except emergency mode), no failed webhook verifications beyond overlap rules, and data readable after rewrap (sampling verification across all encrypted tables).
7. Test **failure modes:** interrupted rewrap resumes; corrupted new key detected before retiring old; lost old key after rotation completes is non-impacting; lost master key is unrecoverable (documented and tested via a restore attempt).
8. Provide the **break-glass tooling** for lost admin MFA (`hddctl admin mfa-reset`) with audit and operator verification steps, and for lost session keys.

**Acceptance.**

- A2: rotation under load causes no error-rate increase beyond 0.01% (except documented emergency effects).
- A3: rewrap verification confirms 100% of encrypted rows decrypt with the new key.
- A4: interrupted rotations resume safely.
- A5: rotation events are audited and visible without exposing key material.
**Tests.**

- A5: config apply is atomic and produces a revision with hash.
**Tests.**

### T-0529 · Disaster-recovery drill: total VPS loss to rebuilt service (AC-54, part 3)
`P30` `[QA][OPS]` · deps: T-0523, T-0522, T-0394 · size: L · owner: ops
**Objective.** Prove the platform can be rebuilt from backups on a new host within the stated objectives, with DNS surviving in the meantime.
**Steps.**
1. Define objectives: RTO ≤ 2 h (operator-adjustable) for restoring the control plane and data plane on a fresh VPS from backups and escrowed keys; RPO ≤ 15 minutes with WAL archiving (24 h with dumps); DNS availability during the outage via the external secondary (when configured) — otherwise stated as unavailable.
2. Execute the drill in the lab and, with approval, on the pilot: provision a clean host (second VPS or VM), run `hddctl deploy --role restore`, restore from the latest encrypted backup using the escrowed key material, replay the deletion ledger, re-establish certificates (hot reload from the restored store; ACME renewal verified), restore config and secrets, bring up services, switch the pilot subzone's NS/A records (human step) or test via `--resolve`, and run the `smoke` and `nondestructive` tiers.
3. Measure each phase's duration (provision, deploy, restore, verify, cutover) and the data loss window; compare with RTO/RPO; record bottlenecks and optimization tasks.
4. Verify **DNS survivability**: with HDD stopped, the secondary continues to answer (when configured), then HDD returns with serials ahead of the secondary and IXFR resumes; document the sequence for NOTIFY/TSIG after restore (TSIG key continuity, serial policy to avoid serial regression: serial must never move backwards; the restore procedure bumps the serial beyond the last published).
