## PHASE P34: Learned detection, Bypass Guard and known-vulnerability coverage (T-0579 to T-0599) · milestone M14 · gate G34

Requirement prefix `HRD`. Goal: close the three gaps that remain after the deterministic engine: (1) **unusual techniques** that no signature knows, with bounded and explainable machine-learning assistance (Sentinel, C20); (2) **bypass**: after a domain and its requirements are set, no request reaches the origin except through HDD, enforced structurally where possible and verified continuously everywhere else (Bypass Guard, C21, rule R-34); (3) **well-known vulnerabilities**: a knowledge base and pipeline that turn named CVEs and vulnerability classes into tested, signed, staged rules, plus the hardening measures of C22.5. Read C20, C21, C22 and rules R-33 and R-34 first.

Design rules for this phase:
- The deterministic engine stays authoritative. Learned components are advisory-first, bounded, explainable, signed, shadow-tested and never the only reason to ban (R-33).
- Nothing in this phase claims that attacks cannot succeed or that bypass is impossible. Claims cite measurements and verification dates (section 4).
- The analyst (a language model) is optional, off by default, never on the request path and never applies anything by itself.
- Where a task needs the runtime state, it uses the `KvStore`, `Bus` and `Limiter` traits (R-31).

**Execution order within P34 (the numbering is not the order).** T-0579 to T-0587 run after P13 and P14 (the engine and the SQLi shield) and P17 (behavior). T-0588 to T-0592 run after P21 (origin protection) and should be scheduled early in delivery slice DS3, because they decide whether a site may be called protected. T-0593, T-0597 and T-0598 run after P15. T-0594 and T-0595 run after P27; T-0596 runs after T-0595, T-0597 and T-0598. T-0599 and gate G34 close the phase.

Gate G34 passes when (each criterion PASS, or UNVERIFIED only with the enumerated reasons the operator has accepted in writing): AC-59 (Sentinel safety, robustness and shadow evidence), AC-60 (Bypass Guard: signed authentication, tunnel, firewall generators, continuous verification and the go-live gate), AC-61 (known-vulnerability coverage: VKB pipeline and ATK-301 to ATK-390) and AC-62 (additional hardening: parser differentials, inspection-window evasion, cache guard, deception, AI-endpoint protections) pass; no learned component can ban alone (tested); a site cannot enter `block` mode while its lockdown is not verified (tested); the held-out evaluation, including leave-one-family-out runs, is published with its limits; and the coverage map (E15) is regenerated with the new rows.

### T-0579 · Sentinel doctrine, threat model and runtime decision (ADR)
`P34` `[SEC][DOC][DP]` · deps: T-0246, T-0252, T-0253, T-0254, T-0255 · size: M · owner: sec
**Objective.** Fix what learned components may and may not do before any model is written, and choose the inference runtime.
**Steps.**
1. Write the ADR "Learned detection under a deterministic core" recording R-33, the layers and the modes of C20.2 and C20.5, and the explicit non-goals: no opaque blocking, no training on tenant raw data, no model on the request path that cannot be skipped within budget.
2. Write the ML threat model (C20.7) into `docs/STRIDE.md` as abuse cases: evasion, poisoning, extraction, prompt injection into the analyst, drift, resource exhaustion; each with a planned test (T-0585).
3. Spike the inference runtime: an inference-only Rust path (`tract`, ONNX Runtime bindings, or a hand-written tree-ensemble evaluator), comparing p99 latency, memory, binary size, supply-chain surface and `unsafe` exposure; prefer a pure-Rust evaluator for tree models; record the choice and the FFI justification if any (R-08).
4. Define the model artifact format (versioned, hash-pinned, signed with the release key, with a model card reference) and the verification rules at load (reject unsigned, wrong schema version, oversize).
5. Define the evaluation protocol: fixed splits, the leave-one-family-out procedure, operating-point selection at a false-positive budget, and which numbers appear in public statements.
6. Define the claims language (approved patterns in section 4.3) and add the forbidden forms to claims-lint (T-0005 rules).
7. Define the data-governance policy: what is stored for a finding (feature classes only, redacted snippet through T-0253), retention (30 days; sequence-model state 24 hours), and the opt-in aggregate-feature sharing rule (default off, minimum population of 50 distinct clients per cell, noise added).
8. Record the decisions in `ARCHITECTURE.md` and seed the capability-matrix rows.
**Deliverables.**
- ADR, STRIDE additions, runtime spike report, artifact format, evaluation protocol, claims rules
**Acceptance.**
- A1: the ADR states the bounds of C20.5 and a reviewer can derive from it that no learned component bans alone.
- A2: the runtime choice has measured p99 numbers on the reference hardware named in `docs/ml/BENCH.md` (fixed CPU model, input cap of 8 KiB per vector) for a 200-tree ensemble and a small convolutional model; tree ensembles are the default and a convolutional model is shipped only if its measured p99 fits the budget.
- A3: the artifact verification rules reject an unsigned and a tampered artifact in a test.
- A4: claims-lint fails on "AI-powered protection" and passes on the approved phrasing.
- A5: the evaluation protocol document defines leave-one-family-out for at least five attack families.
**Tests.**
- Unit tests for artifact verification; claims-lint tests; documentation review.
**Notes.** If the spike shows a model cannot meet the 200 µs budget, the ADR records which layers run only in `shadow` or asynchronously.

### T-0580 · Structural features and the privacy-safe feature extractor
`P34` `[DP][SEC]` · deps: T-0240, T-0241, T-0242, T-0253, T-0263, T-0579 · size: L · owner: waf
**Objective.** Turn a normalized request into a small, privacy-safe feature vector that models can score cheaply.
**Steps.**
1. Implement the feature extractor in `hdd-waf-core::features` (pure, no I/O) over the three views and the SQL, HTML and shell tokenizers: hashed token n-grams (2^18 buckets), token-class sequences, character-class ratios, entropy, nesting depth, encoding-layer count, view-disagreement measures, keyword density, header order and set, content-type versus body-shape agreement. Per-site terms (shape novelty, length z-scores per template) are computed by T-0582 and plugged into the prefilter there; here they are stubbed to neutral.
2. Implement the cheap prefilter (entropy, view mismatch, token-class anomaly, with the per-site novelty hook) that decides whether the models run, with a target of under 5 µs for 95% of requests.
3. Guarantee privacy: features are computed in memory and dropped; the only retained artifacts are the top contributing feature classes (never hashed n-gram buckets) and the redacted evidence snippet; add a test that no feature vector or raw value reaches storage or logs.
4. Keep feature definitions versioned (`feature_schema_version`) so models refuse to load against a different schema.
5. Bound memory and time: per-request feature budget, caps on tokens per vector, behavior on oversized input (skip with a counter).
6. Add deterministic property tests (arbitrary Unicode never panics, features are stable across runs) and a fuzz target.
7. Benchmark (criterion) the extractor on the benign corpora and the attack fixtures.
8. Document the features in `docs/ml/FEATURES.md`.
**Deliverables.**
- feature extractor, prefilter, schema version, tests, benchmarks, docs
**Acceptance.**
- A1: the extractor is deterministic and panic-free on the fuzz corpus.
- A2: the prefilter lets at most 10% of the benign corpus reach the models while passing at least 98% of the attack fixtures of AG-01 to AG-07.
- A3: p99 extraction plus prefilter time is at most 50 µs on the reference hardware of `docs/ml/BENCH.md` for requests up to the input cap, and the combined p99 of extraction, prefilter and inference stays within 200 µs.
- A4: the privacy test finds no raw value or feature vector in any store or log after a 100,000-request run.
- A5: a model built against another schema version is refused at load.
**Tests.**
- Unit, property and fuzz tests; benchmarks; privacy grep over a run.
**Notes.** Features describe *shape*, not content; the same feature vector is produced for the same shape regardless of tenant.

### T-0581 · `hdd-sentinel` runtime: bounded inference, model registry, hot swap and fail-safe behavior
`P34` `[DP][SEC]` · deps: T-0579, T-0580, T-0261, T-0256 · size: L · owner: dp
**Objective.** Run models inside the pipeline at stage 13b without ever hurting latency or correctness.
**Steps.**
1. Create the `hdd-sentinel` crate (forbid unsafe) with a model registry, a loader that verifies signatures and schema, and a typed `Detector` interface returning `(score, calibrated_probability, top_features)`.
2. Integrate as pipeline stage 13b (C2): runs after the deterministic detection, only when the prefilter passes, under a hard 200 µs p99 budget per request and a global concurrency cap.
3. Implement fail-safe behavior: any error, timeout, oversize input or missing model skips Sentinel with `MET-hdd_sentinel_fallback_total{reason}`; the deterministic verdict is never altered by a failure; there is no panic path (R-09).
4. Implement atomic hot swap of models (`ArcSwap`) with canary versions per site, instant rollback, and version recorded in each finding.
5. Implement the mode state machine (`off`, `shadow`, `assist`, `block`) per site with the promotion rules of C20.5 enforced in code (not only in UI) and audit events.
6. Implement metrics (`MET-hdd_sentinel_score`, `MET-hdd_sentinel_findings_total`, `MET-hdd_sentinel_fallback_total`, `MET-hdd_sentinel_inference_seconds`), audit events `AUD-sentinel.mode_changed`, `AUD-sentinel.auto_demoted`, `AUD-sentinel.model_loaded` and `AUD-sentinel.model_rejected`, the findings table writer (`sentinel_findings`, batched through the event pipeline T-0368), and the retention job (30 days).
7. Add `hddctl sentinel off|status` break-glass commands working without the API.
8. Add chaos tests: corrupt model file, slow model, memory pressure, thousands of concurrent requests.
**Deliverables.**
- `hdd-sentinel` crate, stage 13b, registry, mode machine, metrics, `hddctl` commands, tests
**Acceptance.**
- A1: with Sentinel enabled the proxy-added p99 stays within the budget of E4 (functional profile benchmark).
- A2: a corrupt, slow (simulated with an injected clock, so the test is deterministic) or missing model leaves every deterministic verdict byte-identical (differential test over 10,000 requests).
- A3: `shadow` mode never changes a response (differential test with models returning maximal scores).
- A4: promotion to `assist` or `block` is refused in code when its prerequisites are missing (`ERR-SENT-002`), a model that fails signature or schema checks is refused (`ERR-SENT-001`), and each refusal names the unmet prerequisite.
- A5: `hddctl sentinel off` takes effect within 2 s without the database.
**Tests.**
- Integration, differential, chaos and benchmark tests.
**Notes.** The Sentinel crate depends on `hdd-waf-core` but nothing in `hdd-waf-core` depends on it, preserving the purity rule.

### T-0582 · Per-site baselines and poisoning-resistant learning
`P34` `[DP][SEC]` · deps: T-0580, T-0581, T-0272, T-0349 · size: L · owner: dp
**Objective.** Learn what normal looks like for each site, without letting an attacker teach the model that attacks are normal.
**Steps.**
1. Implement the bounded per-(template, parameter) profile of C20.4: t-digest lengths, character-class histograms, token-class bigram count-min sketch, plus the site-wide isolation forest over aggregated features, with fixed memory per template and a global cap per site.
2. Implement the **learning eligibility rule**: only requests that the deterministic engine allowed with no soft score, from cleared clients or established sessions, with a 2xx or 3xx outcome, update the baseline; flagged, challenged, banned and low-reputation requests never do.
3. Implement poisoning controls: trimmed updates, a per-identity contribution cap per hour, an **aggregate cap on movement per template** (so many identities cannot add up to a large shift), a requirement that learning events be spread over time and come from established sessions, a global rate cap on baseline movement, and a drift alarm when a baseline shifts faster than a bound.
4. Implement cold start (no influence before 10,000 requests and 7 days) and the "mark as normal" feedback path with owner confirmation (rate limited, audited).
5. Persist baselines compactly (sketch snapshots every 10 minutes to Postgres, loaded at start; in the local profile also to the data directory) with versioning and a reset command.
6. Implement the novelty score and length z-scores and plug them into the T-0580 prefilter; calibrate against the benign replay of the site.
6a. Implement the session-sequence layer (Layer D of C20.2): a bounded first-order model of path-template transitions with a 24-hour state limit, advisory only, with its own tests and privacy check (no values, only template ids).
7. Test with realistic traffic generators and with an adversary generator that tries to drift the baseline.
8. Document the privacy properties (no values, only distributions) in `docs/ml/BASELINES.md`.
**Deliverables.**
- baseline engine, eligibility and poisoning controls, persistence, calibration, tests, docs
**Acceptance.**
- A1: an adversary sending 100,000 crafted requests from 500 identities over 24 hours moves any template's length median and token-class histogram by less than 5% (the stated bound) and does not make a held-out attack unflagged.
- A6: the sequence layer flags a scripted login-to-export sequence at machine speed in the fixtures, never alters a verdict, and stores no request value.
- A2: flagged and challenged requests never alter the baseline (property test).
- A3: memory per site stays within the cap for 10,000 templates.
- A4: restart restores baselines within 5 s and scoring resumes without a cold start.
- A5: no stored sketch can be inverted to a raw value in the privacy test (canary values never appear).
**Tests.**
- Unit, property, adversary-generator and persistence tests.
**Notes.** The baseline is advisory input; it never blocks on its own.

### T-0583 · Global attack-shape classifier and the reproducible training pipeline
`P34` `[QA][SEC][DP]` · deps: T-0579, T-0580, T-0254, T-0255, T-0278, T-0496 · size: XL · owner: sec
**Objective.** Train, evaluate and ship an attack-shape classifier whose claims about unseen techniques are measured honestly.
**Steps.**
1. Assemble training data: public corpora (licenses recorded in `lab/LICENSES.md`), HDD fixtures of all attack groups, benign corpora, Vuln-Lab captures, and the synthetic mutation generator (case, whitespace, comments, encodings, homoglyphs, splitting, padding); keep the held-out sets of E1.9 strictly out of training and freeze them with hashes in `tests/fixtures/heldout/MANIFEST.sha256` (at least 200 SQLi, 100 XSS, 60 traversal, 60 command-injection and 60 SSTI items), together with the benign replay sets; `xtask verify` fails if a frozen file changes, a training run that opens one fails in a sandbox test, and every published metric cites the manifest hash it came from.
2. Implement `cargo xtask ml train|eval|export` with pinned data hashes, fixed seeds, recorded toolchain, and reproducible artifacts; training may use Rust (`linfa`, `smartcore`, `xgboost` bindings by ADR) or an offline tool whose output is exported to the supported runtime; the trainer is never shipped to production.
3. Implement the evaluation protocol: per-family metrics, calibration, operating point at a false-positive budget of at most 0.01% on the benign corpora, and **leave-one-family-out** runs for at least five families (SQLi, XSS, command injection, traversal, SSTI) reporting detection of the unseen family.
4. Implement adversarial augmentation (mimicry with benign text, homoglyph and padding mutations) and report robustness (T-0585 consumes it).
5. Produce the model card (`docs/ml/MODEL-CARD.md`): intended use, data, metrics with confidence intervals, known failure modes, fairness-style bias checks across languages and character sets (non-Latin text must not look anomalous), and the explicit statement of what the model cannot do.
6. Sign and package the artifact; store metrics in `sentinel_models`.
7. Add a regression gate: a candidate model that raises the benign false-positive count, or lowers held-out detection, is rejected. Because repeated use of one frozen set leaks it into model selection, each release round adds a fresh held-out slice (kept sealed until the round) and the report states which slice each number came from.
8. Document how to retrain and how to add an attack family.
**Deliverables.**
- training pipeline, evaluation reports, model card, signed artifact, regression gate, docs
**Acceptance.**
- A1: the pipeline rebuilds a bit-identical **unsigned** artifact from pinned inputs and single-threaded fixed seeds (reproducibility test; signing is a separate step and signatures are not compared).
- A2: on benign replays of at least 100,000 requests each (`benign-general`, `benign-sql-prose`), the observed false-positive rate at the operating point is at most 0.01% and the 95% upper confidence bound is stated next to it.
- A3: leave-one-family-out detection is published for five families; whatever it is, it is stated (the task fails if it is not measured or not published).
- A4: non-Latin benign text (at least 10 scripts) does not exceed the false-positive budget.
- A5: the regression gate rejects a deliberately degraded model in a test.
- A6: modifying a frozen evaluation file fails `xtask verify`, and the model card cites a manifest hash for every metric.
**Tests.**
- Reproducibility test; evaluation harness tests; regression-gate test.
**Notes.** The unseen-family number is expected to be modest; it is reported as measured and never rounded up.

### T-0584 · Score integration, influence caps, corroboration and explainable findings
`P34` `[DP][SEC][API]` · deps: T-0581, T-0582, T-0583, T-0317, T-0273, T-0246 · size: L · owner: waf
**Objective.** Make the influence policy of C20.5 real: bounded, corroborated and explainable.
**Steps.**
1. Integrate Sentinel scores into the scoring engine (T-0246) as a separate, capped component (maximum 3 points, and clamped so that the total with the deterministic score never reaches the block threshold: Sentinel can raise a request to a challenge but cannot turn a deterministic `pass` into a `block` in `assist`) that appears separately in `Verdict` and events.

3. Implement ban rules: no ban from Sentinel alone, ever; a ban needs a deterministic signal in the same request, and repeated high-confidence findings only raise that identity's challenge level and review priority; never in cross-site subresource context, never for password fields (hooks into the ban policy engine T-0317).
4. Generate the plain-language explanation from the top five features with a message catalog (i18n keys), shown in event detail and appeals.
5. Implement the feedback loop: owner labels (`attack`, `normal`), appeal outcomes, and automatic demotion triggers (appeal spike, label spike, drift; appeals counted only from distinct cleared or verified clients with capped weight; re-promotion needs owner confirmation) with audit events.
6. Implement the promotion checklist API and UI hooks (14 days in shadow, review of the top 100 findings, replay false-positive rate, held-out uplift).
7. Add the replay tool: run any model against a site's recorded event summaries and report what it would have done.
8. Test that every combination of mode, field kind and context follows the policy table (generated matrix test).
**Deliverables.**
- scoring integration, policy engine, explanations, feedback and demotion logic, replay tool, matrix tests
**Acceptance.**
- A1: no combination in the generated matrix (every mode, field kind, context and score) produces a ban from Sentinel alone, and no `assist` combination turns a deterministic `pass` into a `block`.
- A2: `assist` mode never changes the response to an authentication POST.
- A3: every Sentinel-influenced block or challenge event carries at least three human-readable feature explanations.
- A4: an injected appeal spike demotes the site to `shadow` and raises an alert within 5 minutes.
- A5: the replay tool reproduces the live findings for a recorded hour (differential test).
**Tests.**
- Matrix and property tests; integration with the ban engine; demotion tests.
**Notes.** The policy table lives in `docs/ml/POLICY.md` and is generated from the code that enforces it.

### T-0585 · Adversarial robustness suite for learned components (AC-59)
`P34` `[QA][SEC][LAB]` · deps: T-0583, T-0584, T-0586, T-0496 · size: L · owner: qa
**Objective.** Attack the learned components the way an attacker would, and publish what happens.
**Steps.**
1. Build the evasion harness: mimicry (benign prefix/suffix), padding, homoglyphs, token insertion, case and whitespace mutation, encoding layers, splitting across vectors; measure the share of malicious requests that drop below the operating point and whether the deterministic layer still catches them.
2. Build the poisoning harness: drift attempts against baselines from rotating identities, from cleared clients, and through the feedback path (forged "mark as normal").
3. Build the extraction harness: probing to infer thresholds through response differences; verify scores never appear in responses and timing differences stay below a bound.
4. Build the resource harness: inputs designed to maximize inference time and memory.
5. Build the prompt-injection harness for the analyst (T-0586): payloads in evidence fields that instruct the model to ignore rules, reveal context, or propose permissive rules.
6. Run each campaign in the lab with the Vuln-Lab, record results as `lab-proven` with limits, and add every successful evasion to the fixtures for the next training round.
7. Define thresholds: across the enumerated campaigns and the stated number of runs, no campaign may cause a ban, a response change in `shadow`, or a latency violation; evasion rates are published, not hidden.
8. Wire the suite into the nightly lab run and the AC-59 acceptance check.
**Deliverables.**
- five harnesses, campaign reports, fixtures from found evasions, acceptance wiring
**Acceptance.**
- A1: no poisoning campaign moves a baseline beyond the T-0582 bound.
- A2: no extraction probe obtains a score or a threshold from a response; timing differences stay below the stated bound.
- A3: the worst-case inference time stays within budget (skip counter increments instead of delay).
- A4: prompt-injection payloads never change an analyst output into an applied rule or reveal other-tenant data (T-0586 tests).
- A5: the evasion report lists measured evasion rates per technique, with the deterministic layer's coverage of the evaded set.
**Tests.**
- The campaigns themselves; nightly runs; fixture round-trip.
**Notes.** A published evasion rate is a success of the suite: it tells owners where not to rely on Sentinel.

### T-0588 · Signed origin authentication and generated origin verifiers
`P34` `[SEC][DP][API]` · deps: T-0405, T-0361, T-0365, T-0384, T-0210 · size: XL · owner: sec
**Objective.** Make a direct request to the origin useless: only HDD can produce a request the origin will accept.
**Steps.**
1. Define the `HDD-Origin-Auth` v1 format of C21.3 and the canonical string to sign (newline-terminated, length-prefixed fields exactly as in C21.3: version, kid, method, host, port, raw request-target, body hash or `nobody`, timestamp, nonce, Ray ID, `via` marker), with byte-level test vectors in `docs/ORIGIN-AUTH.md`.
2. Implement signing in the origin client (stage 16): per-site keys in `origin_auth_keys` (envelope encrypted), key ids, rotation with overlap, strip of any inbound `HDD-Origin-*` header, and guarantees that keys and signatures never appear in logs, events or responses.
3. Implement the **verifier reference** in Rust (`hdd-origin-guard` library and a small standalone sidecar) with replay protection (nonce retention of at least twice the skew window, fail closed when full, a shared store option for multi-instance origins), skew window of 30 s, clock requirement and reason code, constant-time comparison, generic 403 responses and rejection of the static header of T-0361 in signed mode.
4. Generate **verifier modules** from templates for nginx (njs or Lua), Apache, Caddy, HAProxy, Express and Fastify, WSGI and ASGI, PHP `auto_prepend_file`, Java servlet filter and .NET middleware; every template ships with tests that run against a real instance of that server in the lab.
5. Extend the lockdown wizard (T-0406) with the verifier choice, the key download (shown once, `PERM-bypass.key_view`, audited), a copy-ready snippet and a verification probe that sends a valid, an expired, a replayed and a forged request and checks the four outcomes.
6. Implement rotation: new key, both accepted, switch after every verifier instance acknowledges or a rolling probe confirms every origin target, retire the old only then; reminders and audit (`AUD-origin_auth.key_viewed`, `key_rotated`, `key_retired`).
7. Report rejected requests (attempts, aggregated by rate) and confirmed bypasses (site content served without a valid signature) from verifiers to HDD in a heartbeat signed with its own key, to be consumed by T-0591, and expose `MET-hdd_origin_unsigned_total`.
8. Keep the static secret header (T-0361) as a documented weaker mode and show it as such in readiness.
**Deliverables.**
- signing, key management, `hdd-origin-guard`, verifier templates with tests, wizard changes, docs
