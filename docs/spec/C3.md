## C6. Ban, jail and appeal doctrine

### C6.1 What a ban is

A ban is a time-limited denial for one **IP key** at three possible scopes, enforced in up to four places.

| Scope | Meaning | Created by |
| --- | --- | --- |
| Site | One domain denies the key | Detection on that domain; manual |
| Org | All of the org's domains deny the key | Manual; org-level policy "propagate hard-hit bans to all my domains" (default on) |
| Platform | Every domain on the installation denies the key | Platform admin; automatic global jail (C6.7) |

| Enforcement point | Mechanism | Latency budget |
| --- | --- | --- |
| L7 local cache | `ArcSwap` snapshot + `moka` cache in each proxy node, checked at pipeline stage 6 | effective within 2 s of creation across nodes (initial target 100 ms) |
| Redis | `hdd:banned_ips` zset + detail hash; pub/sub `hdd:events:ban` with revision numbers | write under 5 ms |
| Kernel | nftables set with native timeout, rule applies to TCP 80/443 and UDP 443 only | within 2 s |
| XDP | LPM-trie map (same ban stream) | within 2 s |

Postgres `ip_bans` is the durable source of truth; all other copies reconcile from it (host agent every 30 s; proxies on revision gap).

### C6.2 IP keys

IPv4 `/32`; IPv6 `/64` by default (configurable per site: `/56`, `/48`, or `/128`); API accepts either the address or the key. Bans on IPv6 /64 show the member address that triggered it. Shared-address hints (CGNAT, mobile carriers, university, corporate NAT, Tor exits, public proxies) come from ASN class data and observed distinct session counts, and are displayed in the ban dialog and the IP jail table.

### C6.3 Ban reasons and the TTL ladder

Reasons: `waf_hard_hit`, `waf_score`, `honeypot`, `rate_limit`, `credential_stuffing`, `scanner`, `manual`, `global_jail`, `reputation`, `campaign`, `attack_diversity`.

Progressive TTL by **offence count per org and IP key** within a decay window (default 30 days of quiet resets the counter):

| Offence | Default TTL | Notes |
| --- | --- | --- |
| 1st | 1 hour | Hard hits and honeypot hits ban on first occurrence |
| 2nd | 6 hours | |
| 3rd | 24 hours | |
| 4th and later | 7 days (cap) | Cap is configurable down, never above 30 days without operator approval |
| Test bans (acceptance, Vuln-Lab) | 60 seconds | Dead-man TTL |
| Rate-limit bans | 10 minutes first, then ladder | Softer first step |

The ladder is per site configurable (`ban_ttl_ladder`) and shown on S-057/S-067.

### C6.4 Ban policy engine (single place that turns intents into bans)

Inputs: `BanIntent` (from detection, rate limiter, honeypot, shield), `ClientIp`, request browsing context, site policy, allowlists, never-ban list, offence counters, platform policy. Output: `Ban { scope, key, ttl, reason, evidence }` or `NoBan { reason }`. Decision table:

1. IP in platform never-ban list or org never-ban: `NoBan(never_ban)`, event severity critical, alert (a trusted address attempted an attack).
2. IP in org allowlist with `skip_inspection=false`: inspection ran; verdict recorded as `would_block`; `NoBan(allowlisted)`.
3. Mode not `block`: `NoBan(mode)`, record `would_ban`.
4. Cross-site subresource context (C6.5): block the request, `NoBan(cross_site)`, increment `cross_site` counter; if the counter reaches 3 within 60 s for the same key, convert to a `rate_limit` ban.
5. Otherwise create a ban at the scope implied by the site/org policy with the ladder TTL, set `evidence`, emit audit `AUD-ban.created`, publish to Redis and the host agent, evaluate global-jail promotion (C6.7).
6. Self-protection: a ban whose key matches the **acting admin's session IP** is refused for manual bans (`ERR-BAN-002`) unless `acknowledge_self_ban=true`; automatic bans of the acceptance runner are expected and carry the 60 s TTL.

### C6.5 Ban-poisoning resistance (cross-site context)

A detection or honeypot hit creates a ban only when the request lacks cross-site browser context. Cross-site context means: `Sec-Fetch-Site` is `cross-site` or `same-site` **and** `Sec-Fetch-Dest` is a subresource destination (`image`, `script`, `style`, `iframe`, `frame`, `font`, `audio`, `video`, `track`, `object`, `embed`, `manifest`, `worker`, `sharedworker`, `serviceworker`, `report`, `xslt`), or the `Referer` origin differs from the site origin on a subresource-style request. Such requests are blocked (403 with Ray ID), recorded, counted, and **not** banned (configurable alternative: challenge, or a 60 second ban). Forging headers only avoids the instant ban; the rate limiter's auto-ban still applies, and top-level navigations (`Sec-Fetch-Dest: document`) with attack payloads are banned. Requests with no `Sec-Fetch-*` headers (tools, scanners, curl) are treated as no browser context and ban normally. Tests: AC-34.

### C6.6 Collateral-damage controls

1. Per-site option **challenge-instead-of-ban for shared addresses**: if the IP's ASN is flagged as mobile/CGNAT/corporate or the address has had more than N distinct sessions with legitimate traffic in 24 h, soft-score blocks challenge rather than ban; hard hits still ban unless the option "never hard-ban shared addresses" is on (then 5-minute bans).
2. Ban preview on manual ban and access-list changes (S-063/S-067): who else probably shares the address.
3. Appeals (C6.8).
4. Mass-ban anomaly alert: more than `max(50, 5%)` of the active ban set created within 5 minutes triggers a critical alert and an "investigate possible poisoning" banner.
5. Ban-set cap (default 100,000 per node) with oldest-expiry eviction and a metric; eviction never removes manual or platform-wide bans.

### C6.7 Platform-wide (global) jail

Automatic promotion: the same IP key receiving **hard-hit bans on three or more distinct orgs within one hour** (not counting orgs that share an owner) is promoted to a platform ban at the ladder TTL, because it is scanning the platform's customers. Promotion is on by default in `saas` mode, off in `owner_only`, and every promoted ban is explainable (list of site-level bans as evidence) and appealable. Platform admins can add, extend or remove global bans (S-106) and manage the never-ban list (S-109), with a guard that rejects entries colliding with `test_runner.public_ip`.

### C6.8 Appeals

1. The block page offers "Report a mistaken block" if the site enabled appeals (default on).
2. The appeal form requires the Ray ID, accepts an optional contact email and a note (500 chars), and uses a light proof-of-work; rate limit 3 per hour per IP key and 10 per day per site.
3. The server verifies the Ray ID exists and belongs to the same site and the same IP key (visitors cannot appeal other people's bans); the response is identical whether verification succeeds or not (no oracle).
4. The owner sees appeals in S-069 with evidence and four actions: unban, allowlist for N days (max 30), create a scoped exception for the rule, decline with a reason. Auto-expiry after 14 days.
5. Contact emails are encrypted at rest and deleted when the appeal is resolved or expires.
6. Appeal flows never reveal rule names or detection details to the visitor.

### C6.9 Campaign and evasion defenses

1. **Campaign detector:** many distinct IP keys sending the same attack signature (rule + endpoint) within 10 minutes (default 20 keys) opens a `campaign_cluster`, raises the site to elevated protection for that endpoint (challenge new clients), and alerts.
2. **Fingerprint-linked bans:** after a hard-hit ban, the request's header-order hash and UA hash are remembered for the ban duration; new IPs presenting the same hashes together with the same attack signature are challenged first, then banned on a second hit (fingerprints are never used alone to ban).
3. **Ban evasion via IPv6 rotation:** /64 key by default; optional /56 escalation after repeated bans within a /56.
4. **Residential proxy rotation:** handled by campaign detection and challenge, not by per-IP bans alone.

### C6.10 Unban

`DELETE /bans/{ip}` clears Redis, local caches (via pub/sub), the kernel set, and the XDP map, then a verification probe confirms L7 and kernel state; target at most 2 s. Unban of a non-banned key returns 404. Every unban records who and why. Dead-man: acceptance bans have a 60 s TTL regardless.

## C7. Challenge, bot and reputation doctrine

### C7.1 Principles

1. No third-party CAPTCHA, no tracking, no cognitive puzzles (WCAG 3.3.8). The challenge is an automatic proof of work plus lightweight signals.
2. Challenge is a **response option** everywhere a block would be too harsh (shared addresses, soft scores, bot suspicion, under-attack mode, signup/contact abuse).
3. Bot management is policy: the site owner picks per-class actions (allow, log, challenge, block). Verified search engines are allowed by default.

### C7.2 Proof-of-work design (`hdd-challenge`)

1. The server issues a token: `{v, site_id, ip_bucket, ua_hash, issued_at, expires_at (60 s), difficulty_bits, nonce}` signed with HMAC-SHA-256 under `HDD_CHALLENGE_KEY` (rotation with overlap).
2. The client computes the smallest counter such that `SHA-256(nonce || counter)` has at least `difficulty_bits` leading zero bits, in a Web Worker if available, with progress text and a cancel button; no data leaves the page beyond the solution.
3. The server verifies signature, expiry, one-time use (`hdd:chal:nonce:{nonce}`), difficulty, then issues a **clearance cookie** `__Host-hdd_cl` (`Secure; HttpOnly; SameSite=Lax; Path=/`) containing `{v, site_id, ip_bucket, ua_hash, exp, hmac}` valid for 30 minutes (configurable 5 minutes to 24 hours).
4. `ip_bucket` is the IPv4 /24 or IPv6 /56 of the client to tolerate carrier-grade address changes; `ua_hash` binds to the user agent string.
5. Difficulty is adaptive and comes from **one table** (T-0337 calibrates it; T-0324 and E4.6 cite it): tier `baseline` 14 bits (about tens of milliseconds on a laptop), tier `appeal` 14 bits, tier `elevated` 18 bits (under elevated protection or `under_attack`), tier `automation` 20 to 22 bits (suspected automation), never above a cap that would exceed 10 s on a mid-range phone, measured by a built-in calibration. Pass-rate and solve-time histograms drive tuning (metrics).
6. **Accessibility:** automatic; screen reader announcements ("Checking your browser. This usually takes a few seconds."); reduced-motion spinner replaced by text; `noscript` explains the requirement and offers the appeal path; keyboard-complete.
7. **Abuse resistance:** replay is blocked by nonce use; clearance cookies are not transferable across IP buckets or user agents; clearance does not bypass inspection or bans, only the challenge prompt.

### C7.3 Bot scoring features

Each feature adds to a 0 to 100 score and is logged with the decision.

| Feature | Notes |
| --- | --- |
| Known scanner/tool UA | Immediate class `scanner` (policy: block and ban) |
| Missing or inconsistent headers (`Accept`, `Accept-Language`, `Accept-Encoding`, `Sec-Fetch-*` on browser UAs) | Weighted |
| Header order and casing fingerprint vs UA family | Weighted |
| HTTP/2 SETTINGS fingerprint vs UA family | Needs frame sniffer; documented limits |
| TLS fingerprint (JA3/JA4) vs UA family and against known automation families | Spike-first (T-0342); optional |
| No cookie support after challenge, missing clearance | Weighted |
| Request timing and rhythm (constant intervals) | Weighted |
| Path diversity and 404 ratio | Weighted |
| Honeypot touch | Immediate class `malicious` |
| Reputation (local score, feeds) | Weighted |
| ASN class (datacenter, hosting) | Weighted, policy-dependent |

Classes: `human_likely`, `unknown`, `automation_suspected`, `scanner`, `malicious`, `verified_bot`. Default policy per class is in S-062; defaults: verified bots allow, scanner and malicious block (and ban), automation challenge, unknown allow with log.

### C7.4 Verified bots

Forward-confirmed reverse DNS (PTR then A/AAAA matching the original IP, domain suffix match for the claimed crawler) plus optionally published IP ranges (fetched through the egress allowlist, signed or checksummed). Cache results with TTL; fail closed (treat as unverified) when DNS fails; a UA claiming Googlebot (and similar) that fails verification is class `automation_suspected` and challenged.

### C7.5 Reputation sources

1. Local reputation: score built from the installation's own events (hard hits, bans, honeypots) with exponential decay (half-life default 7 days).
2. Tor exit list, public proxy/VPN lists, datacenter ASN lists, and threat feeds (operator-enabled, signed or pinned, size-bounded, expiry per entry); policy per site: allow, challenge, block. Defaults: allow for Tor and VPN, challenge for flagged datacenter ASNs only on auth endpoints.
3. All feeds go through the egress client; entries expire; every use is explainable in the event.

### C7.6 Credential-stuffing and brute-force logic

1. Per-IP distinct-username counter on auth endpoints (HMAC'd usernames; sliding window 10 minutes): more than 5 distinct usernames with failures from one IP triggers challenge, more than 15 triggers a ban.
2. Per-username failure counter across IPs (HMAC keyed per site): more than 10 failures in 10 minutes from at least 3 IPs flags a distributed attack on that account: step-up challenge for logins to that username (the site owner is alerted; HDD cannot lock the origin's account).
3. Failure detection uses learned response patterns per auth endpoint (status codes, redirect targets, size classes) with an owner override; unknown patterns reduce confidence and are reported.
4. Responses are never altered by HDD for real users except challenge/429/403 pages.

## C8. Data protection and privacy

| Data | Where | Retention | Protection |
| --- | --- | --- | --- |
| Passwords | `users.password_hash` | until change/delete | Argon2id with pepper; never logged; breached-password check at set time |
| Sessions | `user_sessions`, Redis | idle 60 min / absolute 12 h (platform staff 15 min / 8 h) | opaque IDs hashed at rest; rotated on auth change |
| TOTP secrets, recovery codes | `mfa_*` | until removed | secret encrypted (AES-256-GCM envelope), codes Argon2id-hashed |
| API keys | `api_keys` | until revoked | hash only, prefix visible |
| TLS private keys, ACME keys | `certificates`, `acme_accounts` | lifetime | envelope encryption; decrypted only in proxy memory |
| SMTP and webhook secrets, provider tokens | encrypted columns | lifetime | envelope encryption; write-only in UI |
| Request evidence | `waf_events.matched_payload` | `events_retention_days` (default 30) | at most 512 bytes, redacted (Authorization, cookies, password/token-like values), HTML-escaped on display |
| Client IPs | events, bans | with the event/ban | optional truncation (IPv4 /24, IPv6 /48) per org; full IP kept only for active bans |
| Email addresses | users, invitations, appeals | account lifetime / short | normalized; HMAC in attempt tables; encrypted in appeals and mail outbox |
| Audit log | `audit_log` | `audit_retention_days` (default 400, floor 180) | hash chain; no secrets or payloads |
| Backups | encrypted archives | per schedule | AES-256-GCM, key escrowed offline; restore drills |
| Logs | JSON on disk | 14 days default | redaction filter; no bodies; no tokens |

**Subject rights.** Users can export their data and request deletion (S-090) with a 14-day grace period; orgs can export events and audit logs; deletion removes personal data but retains hash-chained audit entries with identifiers replaced by irreversible tokens. **No tracking:** the public site and app set only essential cookies (session, CSRF, theme, locale); no third-party scripts, fonts, or analytics. **Subprocessors** (SMTP relay, CA, DNS secondary, GeoIP provider) are listed on S-013 from the live profile. **Data minimization** applies to all analytics (rollups store aggregates, not request content).

## C9. Hardening baseline (carried forward from v4.1 section 8 and extended; implement all of it)

### C9.1 Admin plane isolation and identity hardening

1. API and web bind to loopback or a private interface; public surfaces are reached only through the HDD proxy (dogfood) or an explicit reverse proxy; the admin surface is never public by default: SSH tunnel/WireGuard, or a routed hostname with `admin_cidrs` **and** MFA, plus step-up for mutations.
2. Session cookie `__Host-hdd_session` (no `Domain` attribute, `Path=/`, `Secure`, `HttpOnly`, `SameSite=Lax`, Strict on admin) accepted only on the same-origin `/api/v1/*` mounts of `app` and `admin` (B2.1); the `api` host accepts bearer API keys only and never sets or reads cookies; CSRF token on every mutation; strict CSP with nonces; HSTS (`max-age` 2 years, `includeSubDomains`, preload only after operator approval; the local profile sends none or `max-age=300`, C18.6); `Referrer-Policy: strict-origin-when-cross-origin`; `Permissions-Policy` denying unused features; `X-Content-Type-Options: nosniff`; `Cross-Origin-Opener-Policy: same-origin`; `Cross-Origin-Resource-Policy: same-origin`; frame-ancestors `none`; all output escaped; HTMX runs with `allowEval=false`, `allowScriptTags=false`, `selfRequestsOnly=true`, no inline handlers.
3. Login rate limiting with progressive backoff keyed by IP, account-HMAC, and IP-account pair; lockout messaging identical for existing and non-existing accounts; breached-password rejection; MFA mandatory for platform roles; passkeys preferred.
4. An SSH-tunnel break-glass path always exists, so a proxy outage never locks out administration. `hddctl admin mfa-reset` is the only MFA reset for platform staff and writes an audit event.

### C9.2 Anti-self-harm

Never-ban list (admin CIDRs, loopback, platform IPs, origin IPs) plus DB allowlist; the runner IP is deliberately excluded (section 2.4). Bans only on the resolved client IP. Ban-set size cap with oldest-expiry eviction. Rule dry-run against known-good probes before activation. Per-domain monitor-first rollout. Progressive ban TTL, capped.

### C9.3 Client IP and header spoofing

Client IP is the TCP peer unless the peer is in `HDD_TRUSTED_PROXIES`/`upstream_cdn.trusted_cidrs`, then `X-Forwarded-For` is parsed right to left to the first untrusted entry. Default trusts nothing. HDD **strips** inbound `X-Forwarded-*`, `Forwarded`, `X-Real-IP`, `X-Original-URL`, `X-Rewrite-URL`, and `HDD-*` headers from untrusted peers before setting its own. Real client IP preservation requires proxy and DNS to bind directly on the host network; Docker NAT or the userland proxy is forbidden for 53/80/443 (AC-22).

### C9.4 IPv6 and shared addresses

IPv6 bans and rate limits key on /64 (configurable); per-domain challenge-instead-of-ban for shared addresses; collateral risk shown in the UI.

### C9.5 WAF self-DoS defenses

Global memory and CPU inspection budgets; regex size limits and linear-time engines only; decompression ratio and size caps; JSON depth 32; multipart part and size limits; per-IP connection caps; header and body limits; header-read and idle timeouts; request-smuggling rejection; bounded event queue with drop counters and per-IP aggregation. `over_limit_policy` for bodies larger than `inspect_body_max_bytes`: `inspect_prefix` (default; inspect the first N bytes, tag `truncated`), `block`, or `pass`; the choice is surfaced in metrics and in the UI with a warning for `pass`.

### C9.6 HTTP/1 and HTTP/2 attack surface

Mitigate Rapid Reset (stream-reset rate limits), CONTINUATION flood (header-block size cap), HPACK bombs (dynamic table and decoded size caps), SETTINGS/PING/empty-frame floods, h2-to-h1 downgrade smuggling (reject pseudo-header, `Transfer-Encoding` and CRLF anomalies), h2c upgrade (disabled), absolute-form and obs-fold request lines, chunk-extension abuse. Each has a raw-socket test (AC-14).

### C9.7 Internal trust

Services talk over a private network with authenticated, encrypted channels (mTLS from `hddctl pki`, or Unix sockets on one host). The proxy's dogfood path to `hdd-web` and `hdd-api` uses Unix domain sockets by default (`origin_kind=platform_internal`, section 2.9), with permissions limited to the service users. Redis and Postgres are never published. DB roles are least privilege (proxy and DNS read-only on config tables). Tenant isolation uses Postgres row-level security keyed on `org_id`.

### C9.8 Secrets at rest

TLS private keys and ACME account keys encrypted with AES-256-GCM using an envelope scheme (`HDD_MASTER_KEY` wraps per-key data keys). The master key is escrowed offline by the operator (documented in `OPERATIONS.md`; a restore drill proves a backup restores with the escrowed key); key rotation is tested; an external KMS hook is documented.

### C9.9 Privacy of stored events

`matched_payload` at most 512 bytes with redaction of `Authorization`, cookies, password-like and token-like values before storage; optional IP truncation; configurable retention with automatic partition drop; request bodies are never logged in full.

### C9.10 Supply chain

`Cargo.lock` committed; `cargo deny`/`audit`/`vet` clean or exceptions documented with expiry; digest-pinned images; SBOM; `cargo-auditable` binaries; checksums and `cosign` signatures on release artifacts; secret scanning in `xtask verify`; vendored front-end files (HTMX, axe-core, fonts) with recorded checksums and licenses.

### C9.11 Audit

Every mutation logged with actor, source IP, request ID; hash-chained `audit_log` with `hddctl audit verify`; the UI shows the verification state.

### C9.12 Origin protection

Per-domain secret origin header (`HDD-Origin-Auth`) and/or mTLS; origin firewall allowlist of HDD IPs only; strict origin certificate verification; SSRF guard on origin URLs; if the origin IP was ever exposed in DNS history, mail headers or CT-visible names, assume it is known: the firewall allowlist is then the only real protection and re-IPing the origin is recommended in `ORIGIN-HARDENING.md`.

### C9.13 Domain ownership

Before onboarding a hostname, require a DNS TXT or HTTP proof of control (waived only for domains listed in the profile in `owner_only` mode), so a tenant cannot claim someone else's domain and dangling records cannot be hijacked. Periodic re-verification; a domain failing re-verification for 7 days is moved to `pending_verification` and traffic continues for 14 more days with warnings before pause.

### C9.14 Certificate hygiene

Budget ACME issuance against the CA's current rate limits (duplicate-certificate and failed-validation limits included, verified at build time), pre-check CAA, monitor Certificate Transparency for unexpected issuance for managed names, run own expiry monitoring (do not depend on CA reminder emails). Renewal at one third of lifetime remaining or when ARI says so; alert at one quarter remaining.
