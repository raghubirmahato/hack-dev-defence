## PHASE P20: Authoritative DNS, full data plane (T-0387 to T-0404) · milestone M8 · gate G20

Requirement prefix `DNS`. Goal: turn the walking-skeleton `hdd-dns` into the production authoritative server: ADR-backed server core, immutable snapshot serving with hot swap, complete protocol correctness, orange-cloud (proxied) answers, CNAME flattening, hardened UDP/TCP transport, response-rate limiting and cookies, TSIG zone transfers and NOTIFY, both topologies (`self_authoritative`, `hidden_primary`), ACME DNS-01 serving, fuzzing, amplification measurement, tenant isolation, observability, an independent conformance suite and the live DNS acceptance checks (AC-03 full, AC-21, AC-28 preparation).

Non-negotiables: the query path never touches Postgres, Redis or the network (snapshot only; the flattening resolver is a separate bounded task whose results are cached into the snapshot-adjacent cache); `hdd-dns` never recurses for clients and never acts as a reflector (R-08/C11.3 L3); a malformed packet never panics or leaks memory; every table, cache and queue is bounded; tenants cannot read or alter each other's zones, and a zone that is deleted, suspended or decommissioned stops answering within 2 s of the snapshot revision.

Gate G20 passes when: AC-03 (DNS protocol and parity) passes in full on the pilot subzone with `dig`, `kdig`, `delv` where applicable and the independent hickory-client suite; AC-21 (secondary and TSIG) passes or is `UNVERIFIED(human_step_pending)` only for the external secondary's availability; AC-28 amplification ratio and RRL checks pass in the closed lab; the DNS fuzz smoke is clean; qps and memory budgets are met; and DNSSEC is not claimed anywhere unless `delv` validates it.

### T-0387 · ADR: DNS server core (hickory-server customization versus own packet loop) and workspace wiring
`P20` `[DP][DOC]` · deps: T-0207, T-0179 · size: M · owner: dns
**Objective.** Decide, with evidence, how `hdd-dns` receives, parses and answers packets, so every later task builds on a justified core.
**Steps.**
1. Read the T-0207 spike report. Build a decision matrix with measured data for three candidates: (a) `hickory-server` with a custom `RequestHandler` and our `hdd-common::dns` answer engine as the only source of truth, (b) `hickory-proto` for wire encode/decode with our own UDP/TCP socket loops (`tokio`, `SO_REUSEPORT`, `recvmmsg` batching where available), (c) a fully own minimal parser. Criteria: protocol correctness risk, ability to enforce RRL/cookies/truncation exactly as specified, memory per query, p99 latency at 20k qps on the builder, fuzzability, maintenance burden, `unsafe` in dependency tree, MSRV and license.
2. Write the ADR in `docs/adr/` with the chosen option, the rejected options and the reversal cost. Default expectation: (b) or (a) with the handler bypassing hickory's own zone catalog entirely; record the reason if (a) cannot meet cookies/RRL/minimal-response control.
3. Define the crate internal layout: `transport/` (udp, tcp, limits), `wire/` (decode, encode, EDNS, cookies), `engine/` (calls the pure answer engine from T-0179), `snapshot/` (store, swap), `xfr/` (TSIG, AXFR/IXFR, NOTIFY), `flatten/` (CNAME resolver), `rrl/`, `metrics/`. No module outside `engine/` may know about tenants or proxying semantics.
4. Define the **single answer contract**: `fn answer(snapshot: &ZoneSet, q: &Question, ctx: &QueryCtx) -> AnswerPlan` is pure and shared by the server, the control-plane preview (T-0182) and the tests, so preview and production cannot diverge.
5. Pin dependency versions, add `deny.toml` entries and verify `cargo geiger` shows no `unsafe` in our own code.
6. Create a benchmark harness skeleton (`benches/dns_wire.rs`) used by T-0400.
7. Record unknowns as ADR follow-ups (for example DoT/DoH are explicitly out of scope; document why).
**Deliverables.**
- `docs/adr/00NN-dns-core.md`, crate skeleton changes, bench harness skeleton
**Acceptance.**
- A1: the ADR contains measured numbers for all three options (or documents why an option was eliminated early with evidence).
- A2: the chosen core can express response-minimization, EDNS buffer capping, TC=1 behavior and per-response cookie handling (proof-of-concept tests).
- A3: the preview endpoint and the server call the same `answer` function (compile-time shared symbol, test asserts identical `AnswerPlan` on 10,000 generated questions).
- A4: no `unsafe` in `hdd-dns`.
**Tests.**
- Unit/PoC tests per A2; property test for A3.
**Notes.** DNS over TLS/HTTPS/QUIC are not part of v5 (authoritative servers do not need them); record that in the capability matrix as `not_planned`.

### T-0388 · Snapshot ingestion, atomic swap and the DNS data-plane role
`P20` `[DP][DB][SEC]` · deps: T-0387, T-0211, T-0177 · size: L · owner: dns
**Objective.** Make zone changes visible within 2 s without any database access from the query path and without ever serving a half-applied zone.
**Steps.**
1. Implement the snapshot store as `ArcSwap<ZoneSet>` where `ZoneSet` holds immutable per-zone structures: sorted name tree (canonical DNS order), RRsets indexed by (name, type), wildcard index, delegation points, empty-non-terminal markers, precomputed SOA/NS answers, per-zone limits and flags (`state`, `proxied_defaults`, `topology`).
2. Implement ingestion from the config bus (T-0211): full snapshot on boot (from a signed local cache file, then verify against Postgres through the read-only role `hdd_dns_ro`), and incremental revision messages (zone id, version, content hash). Fetch the new zone version, build the new structure off the hot path, validate invariants (CNAME exclusivity, SOA present, NS present, no duplicate tuples, apex rules), then swap atomically.
3. Enforce monotonic versions: a revision lower than the current is ignored with a metric; a gap triggers a resync of that zone; a hash mismatch quarantines the zone revision (keep serving the previous version) and raises an alert (`MET-hdd_dns_snapshot_rejected_total`).
4. Create the database role `hdd_dns_ro` with `SELECT` only on the views `dns_zone_export_v` and `dns_record_export_v` (no access to org, user or audit tables), and ensure the service refuses to start if it detects write privileges (self-check query against `has_table_privilege`).
5. Persist the last good snapshot to `/var/lib/hdd/dns/snapshot.bin` (0600, owned by the service user), written atomically (`rename`), with a header containing schema version, content hash and Ed25519 signature from the control plane; on boot with the database unreachable, serve from that file and report `degraded=cache` in `/healthz` and metrics.
6. Implement apply latency measurement: control plane stamps `published_at`; the DNS service records `applied_at` and exports the histogram `MET-hdd_dns_apply_seconds`; alert above 2 s p95.
7. Implement memory accounting per zone and a global cap (default 512 MiB); zones that would exceed the cap are rejected at ingestion with an alert instead of crashing.
8. Implement graceful removal: a zone with `state in (deleted, suspended, decommissioned)` answers `REFUSED` (suspended: `REFUSED` with an EDE 18 "Prohibited" extended error where supported) after the swap.
9. Write the chaos tests: kill Postgres, kill Redis, corrupt the cache file, deliver revisions out of order and duplicated, deliver a poisoned revision (invalid CNAME coexistence) and verify the previous version keeps serving.
**Deliverables.**
- `snapshot/` module, migration for the read-only role and export views, cache file format doc, tests
**Acceptance.**
- A1: with Postgres and Redis stopped, queries for existing zones are answered from the cache without errors for 10 minutes.
- A2: a record change appears in answers within 2 s p95 (measured on the pilot with a probe).
- A3: a corrupted or unsigned cache file is rejected (service starts empty and degraded, never serves unsigned data).
- A4: the service fails to start when its database role has `INSERT/UPDATE/DELETE` privileges (test with a deliberately over-privileged role).
- A5: out-of-order or duplicate revisions never cause a rollback of served data.
**Tests.**
- Integration with real Postgres; chaos suite; property test for monotonic version handling.
**Notes.** The control plane never pushes record data through Redis; Redis carries only revision pointers (zone id, version, hash).

### T-0389 · Protocol-correct answering: rcodes, wildcards, ANY, delegation, CNAME and DNAME-free semantics
`P20` `[DP]` · deps: T-0387, T-0388 · size: L · owner: dns
**Objective.** Answer every query shape exactly as an authoritative server must, and prove it with a table-driven corpus.
**Steps.**
1. Implement the response construction per RFC 1034/1035/2181/2308/4592/6891/8482/9619: AA set for authoritative answers, RA=0 always, RD ignored, QR/opcode handling (`NOTIMP` for opcodes other than QUERY, NOTIFY and — where enabled — none other), `FORMERR` for malformed or QDCOUNT≠1 (RFC 9619), `REFUSED` for names outside any served zone, class IN only (CH `version.bind`/`hostname.bind` answered `REFUSED`, no version disclosure).
2. Implement lookups: exact match; wildcard synthesis per RFC 4592 with the "closest encloser" rule and the correct behavior for empty non-terminals (NODATA, not NXDOMAIN, and no wildcard expansion beneath an existing name); CNAME chasing inside the zone (bounded depth 8) returning the chain in the answer section; out-of-zone CNAME targets are returned unchanged; CNAME at a queried type `CNAME` returns the record itself.
3. Implement negative answers: NXDOMAIN and NODATA with the SOA in the authority section with TTL = min(SOA TTL, SOA MINIMUM) (RFC 2308), and no NSEC/NSEC3 (zones are unsigned).
4. Implement delegation: queries at or below a delegation point return the referral (NS in authority, glue in additional only when the glue lies within our zone), `AA=0` for referrals, and the DS-absent behavior documented.
5. Implement `ANY` per RFC 8482: return a single minimal RRset (HINFO "RFC8482" with TTL 3600, or the first available RRset per documented policy) and never the full set; `AXFR/IXFR` over UDP gets `REFUSED` or `NOTIMP` as documented; `RRSIG/DNSKEY/NSEC` queries return NODATA (unsigned).
6. Implement type coverage: A, AAAA, CNAME, MX, TXT (multi-string), NS, SOA, CAA, SRV, HTTPS and SVCB (RFC 9460, including `alpn`, `port`, `ipv4hint/ipv6hint`, `ech` passthrough as opaque), PTR within served reverse zones, and unknown types answered as NODATA for existing names. Additional-section processing: A/AAAA for MX/SRV/NS targets within our zones only when it does not enlarge the answer past the size policy.
7. Implement case-insensitive name matching with the question's original case echoed in the answer (0x20-safe) and compression that never points forward and never loops.
8. Implement the response-minimization policy: authority and additional sections omitted unless required (referrals, negative answers, glue), RFC 8482 minimal ANY, and a documented rule when the answer would exceed the negotiated size (set TC=1 and return only the question and header).
9. Build the **protocol table corpus** (`tests/dns/protocol_table.yaml`, at least 400 rows: query, zone fixture, expected rcode/flags/sections) including every edge in the steps, wildcards under empty non-terminals, CNAME loops, apex NS/SOA/CAA, long names (253 bytes), 63-byte labels, IDN A-labels, underscore labels and mixed-case queries.
10. Wire `xtask dns-table` to run the corpus against both the pure `answer` function and a live server on an ephemeral port, and require identical results.
**Deliverables.**
- engine glue in `hdd-dns`, protocol table corpus, `docs/dns/PROTOCOL.md`
**Acceptance.**
- A1: all 400+ corpus rows pass on the pure engine and on the live server.
- A2: queries for names outside served zones yield `REFUSED` with AA=0 and RA=0 (never `NXDOMAIN`).
- A3: `ANY` over UDP never returns more than one RRset and the ratio test in T-0398 stays below the threshold.
- A4: `version.bind`, `hostname.bind` and `id.server` never disclose information.
- A5: a wildcard never synthesizes under an existing empty non-terminal.
**Tests.**
- Table-driven; property tests (generated zones: lookup result equals a naive reference implementation written in the test crate); differential test against `named-checkzone`/`knot` semantic expectations through captured vectors.
**Notes.** The reference implementation in tests is deliberately naive (linear scans) so it is easy to audit.

### T-0390 · Proxied (orange-cloud) answers, edge/ACME/preview synthetic names and origin non-disclosure
`P20` `[DP][SEC]` · deps: T-0389, T-0158, T-0204 · size: L · owner: dns
**Objective.** Make a proxied record answer with HDD addresses only, and make the platform-operated helper names work, without ever exposing origin data.
**Steps.**
1. Implement the proxied-answer rule in the engine glue: for `proxied=true` A/AAAA/CNAME records, answer with `platform.public_ipv4` / `public_ipv6` (a shuffled subset, stable per query-name per 60 s bucket to keep caches coherent), TTL = the record's virtual TTL (default 300 s, never above the zone `proxied_ttl_max`).
2. If `platform.public_ipv6` is empty, a proxied AAAA query is **NODATA** (never the origin's IPv6, never NXDOMAIN); assert the stored origin value never appears on the wire (a unit test greps encoded packets for the stored origin bytes over a generated corpus).
3. Implement proxied CNAME handling: a proxied CNAME is answered as A/AAAA at the same name (the platform IPs), the CNAME target is never emitted; non-proxied CNAMEs return the stored chain.
4. Implement HTTPS/SVCB rewriting for proxied names: `ipv4hint`/`ipv6hint` replaced by HDD addresses or removed; `ech` and `alpn` preserved only when the TLS settings of the site allow (`h2`/`http/1.1`; `h3` only if HTTP/3 is enabled for the site); a parameter whose value cannot be verified is dropped.
5. Implement grey-cloud behavior: the stored value is returned unchanged; records for `non_http_services` are forced grey at import and the engine asserts this (a proxied record with a non-HTTP port annotation is an invariant violation that quarantines the revision).
6. Implement the synthetic zones operated by the platform: `<site-id>.edge.<platform_domain>` (CNAME target for `cname_partial`, always answers HDD addresses), `<zone-id>.acme.<platform_domain>` (target for delegated `_acme-challenge`, answers the live DNS-01 TXT set for that zone only), and `<site-id>.preview.<platform_domain>` (preview host, answers HDD addresses). These are generated from the snapshot, are read-only, and are not stored as tenant records.
7. Implement reserved-name protection: tenants cannot create records that collide with `ns1/ns2`, `www/app/admin/api/status` of the platform domain, `*.edge`, `*.acme`, `*.preview` (enforced in the control plane; the data plane also refuses to serve a tenant zone whose apex equals or lies under the platform domain unless the org is the platform org).
8. Implement a "no origin leakage" guard in the encoder: every outgoing A/AAAA answer for a proxied name passes through a final check that the address belongs to the platform address set; otherwise the answer is replaced by SERVFAIL and a critical alert (`dns_origin_leak_guard`) is raised and counted.
9. Add per-name overrides for staging: during `pending_delegation` a site may serve preview answers only to `test_hostname`-style queries listed in the pilot profile (no global effect).
10. Add the pilot-specific behavior for `test_hostname` and `sandbox_hostname` (always proxied, exact canary behavior).
**Deliverables.**
- proxied answer module, synthetic zone generator, encoder guard, tests
**Acceptance.**
- A1: across 100,000 generated proxied queries no origin address appears in any response (wire grep test).
- A2: a proxied AAAA with empty `public_ipv6` is NODATA with the SOA in authority.
- A3: HTTPS records of proxied names never contain origin hints.
- A4: `<site-id>.edge`, `<zone-id>.acme` and `<site-id>.preview` names answer correctly and never contain tenant record data.
- A5: the leak guard fires in a fault-injection test and results in SERVFAIL plus an alert, never in a leaked answer.
**Tests.**
- Unit, property, fault-injection; live check on the pilot with `dig +short` for proxied names (compared with the platform address set).
**Notes.** This task is where "orange cloud hides the origin" becomes machine-checked rather than documented.

### T-0391 · CNAME flattening resolver (bounded, cached, loop-safe, never recursive for clients)
`P20` `[DP][SEC]` · deps: T-0389, T-0388 · size: L · owner: dns
**Objective.** Support apex CNAME-like behavior (ALIAS semantics) safely, without turning the server into a recursive resolver.
**Steps.**
1. Implement a separate `flatten` task pool that resolves targets for flattened records (apex CNAME records stored as `source=flatten` per T-0178) via a configured upstream resolver list (`dns.flatten_resolvers`, default the system resolver of the host; must be local or explicitly configured), over UDP with TCP fallback, with DNSSEC validation off (documented) and a strict response size cap.
2. Enforce limits: depth 8, total lookups per flatten operation 16, wall time 3 s, target must be a valid hostname, resolved addresses must not fall into disallowed ranges (private, loopback, link-local, metadata) **unless** the zone owner is the platform org; results from blocked ranges are dropped and an event is recorded (`dns_flatten_blocked_range`).
3. Implement caching: positive results honor the minimum TTL of the chain bounded to [30 s, 3,600 s]; negative results cached 30 s; stale-while-revalidate (serve the last value up to 10 minutes past expiry if resolution fails, with a metric and a dashboard flag).
4. Implement refresh scheduling: a background tick refreshes flattened targets at 80% of the TTL with jitter; at most `flatten.max_targets` (default 5,000) globally and `flatten_per_zone_max` (default 20) per zone; excess targets are rejected at the control plane (`ERR-DNS-007`).
5. Implement loop and abuse protection: a flatten target that (transitively) points at a name in an HDD zone is resolved against the local snapshot with a visited-set; cycles are detected and the record is marked `failing(loop)`; a target that is a wildcard or random-subdomain pattern is rejected at record creation.
6. Ensure a flattened name's answers in the query path come only from the cache (never block on resolution): a cache miss for a flattened name triggers an asynchronous refresh and the query is answered with SERVFAIL only when no stale value exists (rare, counted).
7. Expose per-record flatten health in the API (`last_ok`, `last_error`, `ttl_remaining`) for the DNS records screen (S-045) and raise alerts after 3 consecutive failures.
8. Write tests with a controllable stub upstream server (a real UDP/TCP DNS server process started by the test) covering: normal chain, long chain over the depth limit, loop, slow upstream, oversized response, truncated response with TCP fallback, upstream returning private addresses, upstream returning SERVFAIL and stale serving.
**Deliverables.**
- `flatten/` module, API fields, alerts, tests
**Acceptance.**
- A1: queries never block on resolution (p99 latency identical with the upstream down).
- A2: loops and over-deep chains are detected within limits and surfaced as record health.
- A3: private-range answers are dropped for tenant zones.
- A4: stale values are served up to 10 minutes and then SERVFAIL, with metrics for each state.
- A5: the server never answers a client query by recursing (negative test: a query for an unknown external name is `REFUSED`).
**Tests.**
- Integration with the stub upstream; property tests for loop detection; chaos test killing the upstream mid-refresh.
**Notes.** CNAME flattening is the only place `hdd-dns` makes outbound DNS queries, and it does so through the egress client rules (section 2.9) with an allowlist of resolver addresses.

### T-0392 · Transport hardening: UDP/TCP listeners, EDNS0, truncation and connection limits
`P20` `[DP][SEC]` · deps: T-0387, T-0389 · size: L · owner: dns
**Objective.** Make the sockets and wire handling resistant to resource exhaustion and amplification.
**Steps.**
1. Implement UDP listeners with `SO_REUSEPORT` (one socket per worker thread), bounded receive buffers, batching (`recvmmsg` through a safe wrapper crate or per-datagram `recv_from` if no safe option exists; record in the ADR), and per-packet maximum size 4,096 bytes inbound; larger packets are dropped with a counter.
2. Implement EDNS0 per RFC 6891: parse OPT, honor the requestor's UDP payload size but **cap the response at 1,232 bytes** by default (`dns.udp_payload_cap`), minimum 512; unknown EDNS versions get `BADVERS`; unknown options ignored (except cookies); NSID is not sent; client subnet (ECS) options are ignored and not echoed; EDNS padding not applied (UDP) but supported on TCP if requested.
3. Implement truncation: if the encoded answer exceeds the effective limit, return a minimal response with TC=1 and no records (documented as "empty TC") so truncated responses are never larger than the query by more than the OPT/cookie bytes.
4. Implement TCP listeners (RFC 7766): length-prefixed framing with strict validation (2-byte length ≤ 65,535, zero-length rejected), maximum concurrent connections (default 2,000 total, 20 per source), idle timeout 10 s, per-connection query limit (default 100) then close, per-connection read/write deadlines, pipelined queries answered in order (or out of order only if the ID matching is proven safe), and `edns-tcp-keepalive` support with a 10 s hint.
5. Implement a global cap on in-flight work (bounded `Semaphore`) and a documented shed policy: when overloaded, drop UDP queries from sources without valid cookies first, then the rest; TCP accepts beyond the cap are closed immediately.
6. Implement source-address validation for TCP-only operations (AXFR) separately in T-0394; here, ensure that a TCP query from an address that cannot complete the handshake never consumes more than the SYN backlog (relies on kernel tuning T-0213/T-0468).
7. Implement IPv6 dual-stack listening (both `0.0.0.0` and `::` with `IPV6_V6ONLY` set on the v6 socket) and per-family metrics.
8. Implement privilege handling: bind port 53 with `CAP_NET_BIND_SERVICE` only, drop all other capabilities, set `PR_SET_NO_NEW_PRIVS`, and validate systemd hardening settings from `hddctl deploy` (read-only filesystem, `ProtectSystem=strict`, `PrivateTmp`, `SystemCallFilter`).
9. Write tests with raw sockets for each framing and EDNS edge: zero-length TCP frames, half-open connections, slowloris on TCP (1 byte/s), 65,535-byte frames, EDNS with 0 or 65,535 payload sizes, duplicate OPT records, OPT in the wrong section, compression pointers to the header, truncated names, and a flood of connections from one source.
**Deliverables.**
- `transport/` and `wire/` modules, systemd unit hardening settings, tests
**Acceptance.**
- A1: the server never emits a UDP response larger than min(requested size, 1,232) bytes.
- A2: slowloris-style TCP clients are disconnected at the idle timeout and never exceed per-source caps.
- A3: every malformed-frame case in the test list yields the specified behavior (FORMERR or close) without panic.
- A4: capabilities in `/proc/<pid>/status` show only `CAP_NET_BIND_SERVICE` (checked in the deploy verification).
- A5: IPv6 and IPv4 serve identical answers for identical questions (differential test).
**Tests.**
- Raw-socket integration tests; fuzz seeds feed T-0397.
**Notes.** The 1,232-byte cap follows DNS Flag Day 2020 guidance; the value is configuration but changing it is audited.

### T-0393 · Abuse controls: response-rate limiting, DNS cookies, per-source caps and random-subdomain detection
`P20` `[DP][SEC]` · deps: T-0392 · size: L · owner: dns
**Objective.** Ensure HDD cannot be used as a reflector, and that floods of valid-looking queries degrade gracefully.
**Steps.**
1. Implement **RRL** modeled on the BIND/Knot algorithm: key = (client prefix /24 for IPv4, /56 for IPv6, qname-class bucket, response type: positive/NXDOMAIN/error), token bucket default 5 responses/s per key, window 15 s, `slip=2` (every second dropped response is replaced by an empty TC=1 response so legitimate clients retry over TCP), exempt list for `admin_cidrs`, the secondary's addresses and the platform's own resolvers.
2. Implement **DNS cookies** (RFC 7873/9018): server secret rotated every 24 h with a 1 h overlap, client+server cookie validation; queries with a valid server cookie bypass RRL and the lower per-source cap; queries with only a client cookie get a `BADCOOKIE`-free normal answer including the server cookie; queries without cookies are allowed but rate-limited more strictly.
3. Implement per-source query caps: 50 qps default for sources without a valid cookie, 500 qps with a valid cookie, burst equal to 2 s of rate; counters stored in a bounded LRU (default 1,000,000 entries) with eviction that favors dropping idle sources, never panicking, and sized to ≤128 MiB.
4. Implement the **random-subdomain (water-torture) detector** per zone and per source: when the NXDOMAIN ratio for a zone exceeds 70% over 10 s with more than 500 qps, enter `zone_nxdomain_defense`: (a) apply a stricter RRL to NXDOMAIN responses for that zone, (b) answer NXDOMAIN with minimal responses only, (c) raise a `dns_random_subdomain_flood` alert with the top sources (/24, /56 aggregates only), and (d) automatically exit after 5 minutes below the threshold. Zones with wildcard records are excluded from the ratio (wildcards answer positively).
5. Implement a **reflection source-port guard** (UDP queries whose source port is 53, 123, 389, 1900, 11211, 19 or in the configurable list are answered only with cookie validation, else dropped) to avoid DNS-to-DNS reflection loops.
6. Implement an **attack-mode toggle** controlled by the shield (T-0475): in `ATTACK` state, queries without valid cookies are answered with a TC=1 empty response for non-exempt sources, forcing TCP (documented as an emergency measure with effects on resolvers).
7. Ensure every limit is configurable in `hdd.yaml`/settings with validation and sane maxima, and that every drop is counted by reason (`rrl`, `cap`, `cookie`, `malformed`, `reflection_port`, `overload`) in `MET-hdd_dns_dropped_total{reason}`.
8. Document the effects on legitimate resolvers (large resolvers share addresses; the /24 and /56 aggregation, slip behavior and the exemption procedure) in `docs/dns/ABUSE-CONTROLS.md`.
9. Write the test plan: unit tests for token buckets (time-injected), RRL behavior tables, cookie validation vectors from RFC 7873 appendix, simulated resolver populations (a legitimate resolver pool must keep ≥99% success while an attacker pool is limited), and a regression test that RRL never limits the secondary's NOTIFY/transfer.
**Deliverables.**
- `rrl/` module, cookie module, detectors, docs, tests
**Acceptance.**
- A1: a flood of identical queries from one source yields at most the configured response rate plus slip responses (measured).
- A2: a legitimate-resolver simulation (500 resolvers at 10 qps each plus a 50k qps attacker pool) sees ≥99% of legitimate queries answered.
- A3: cookie vectors from the RFC pass; invalid server cookies are treated as no cookie.
- A4: the random-subdomain defense enters and exits as specified and is visible in S-113/S-127.
- A5: the secondary's addresses are never rate limited (test).
**Tests.**
- Deterministic time-injected unit tests; lab simulation using `hdd-loadgen` (closed lab only, section 2.6).
**Notes.** The cap for sources without cookies is intentionally conservative; recursive resolvers behind NAT can exceed it, hence the /24 aggregation and cookie fast path.

### T-0394 · TSIG zone transfers (AXFR/IXFR) and NOTIFY for external secondaries
`P20` `[DP][SEC]` · deps: T-0388, T-0389, T-0191 · size: XL · owner: dns
**Objective.** Let an external provider serve as secondary so the customer's DNS survives loss of the VPS, with transfers authenticated and incremental.
**Steps.**
1. Implement TSIG (RFC 8945) verification and signing with HMAC-SHA256 (and SHA512), key names and secrets from the `secondary_dns` settings (secrets decrypted from the envelope store at service start only, zeroized after use, never logged), time-fudge window of 300 s, replay protection per (key, MAC, time), and the `BADKEY/BADSIG/BADTIME` error responses.
2. Implement **AXFR** over TCP only: allowed only for (a) a zone with a configured secondary, (b) a source address in that secondary's allowlist **and** a valid TSIG; every other attempt is refused (`REFUSED`) and counted as `axfr_denied` with a security event (rate limited). Stream the zone in multiple messages respecting the 64 KiB limit; include SOA first and last; honor global transfer concurrency (default 4) and per-zone rate limits.
3. Implement **IXFR** (RFC 1995) from the zone version history (T-0185): the server keeps the last N (default 20) deltas per zone in the snapshot service; if the requested serial is older or the delta chain is incomplete, fall back to full AXFR in the same message sequence; TCP preferred, UDP IXFR answered with the SOA only per RFC when the response would not fit.
4. Implement outbound **NOTIFY** (RFC 1996): on each published revision, send NOTIFY (opcode 4) with the new SOA to every configured secondary address over UDP, with retries (5 s, 15 s, 60 s, 5 min, then stop and alert), record success when the secondary answers; track `notify_sent_total`, `notify_acked_total`, latency histograms, and the **lag** (time between publish and secondary's first IXFR/AXFR request or SOA poll match).
