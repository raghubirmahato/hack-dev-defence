### B12.2 Detailed specifications of critical screens

#### S-042 Add-domain wizard

Eight resumable steps; URL `/app/o/{org}/domains/new?step=n`; the draft `sites` row is created at step 1; leaving shows a leave-guard only when unsaved fields exist.

1. **Enter domain.** Field accepts `example.org`, `https://example.org/path` (stripped), `www.example.org` (offers apex), Unicode (shows punycode). Validation: IDNA, registrable domain via the public-suffix list, not the platform domain, not reserved, not already claimed (dispute link), plan quota (`ERR-DOM-006`). Bulk add via multi-line paste (max 20).
2. **Scan existing DNS.** Async job with progress text; results grouped: web (A/AAAA/CNAME), mail (MX/SPF/DKIM/DMARC), other (TXT/SRV/CAA/NS), unknown. Shows the current nameservers and provider guess. Offers "Import from zone file" and "Add manually". Errors: scan blocked by resolver outage shows partial results with a retry.
3. **Choose how to connect.** Cards: Full nameserver delegation (recommended), Keep my DNS provider (CNAME/A), Subdomain only. Each card lists what changes, what stays, rollback time, and prerequisites. Recommendation logic is deterministic: apex wanted and provider unknown gives full; provider supports ALIAS/CNAME flattening gives partial.
4. **Review records.** Full mode: imported records with proxy toggles (web records default orange, mail and SRV and unknown grey), parity banner, unsupported types needing acknowledgment, origin-leak warnings ("This MX record exposes your origin IP 203.0.113.10"). Partial mode: the exact records to create (CNAME or A, verification TXT, optional `_acme-challenge` CNAME) in "Do this at your DNS provider" boxes with copy buttons.
5. **Prove ownership.** TXT or HTTP file; live status; "Check now" (rate-limited). Full mode can defer proof until delegation is detected because controlling DNS is itself proof only if the registrar NS points to HDD (the platform still requires TXT first in `saas` mode).
6. **Origin.** Fields: address (hostname or IP), port, scheme, Host header (defaults to domain), SNI name, TLS verification mode, health path. "Test connection" shows DNS result, connect, TLS, status, and clear remedies; SSRF guard errors explain without echoing internal details.
7. **TLS and protection level.** Certificate plan: pre-issue via DNS-01 (full mode, or partial with the CNAME) or issue on first request (warning). Preset cards: Monitor first (default), Balanced, Strict, Vulnerable-Origin Shield; each says what it logs and bans.
8. **Go live.** Checklist of verified facts, preview commands (`curl --resolve`, hosts-file snippet, preview URL), final warnings (DS record, TTLs), rollback instructions shown before the button. After activation, a delegation or CNAME status poller runs until detected; the page then shows the first requests arriving.

States: draft resume list on S-041; failure at any step keeps previous inputs; network error shows retry.

#### S-044 Protection readiness

Score 0 to 100 with ring and the footnote. Groups and example checks (weights sum to 100; exact weights in T-0172):
- **Traffic** (20): traffic flows through HDD (last proxied request within 24 h), delegation or CNAME verified, no grey web records that expose the same hostnames.
- **Encryption** (15): valid certificate with more than one quarter lifetime remaining, HTTPS redirect on, origin verification mode strict, HSTS enabled (partial credit by max-age).
- **Origin** (20): lockdown applied, secret header verified, origin IP not found in own DNS/headers/mail, origin health check passing.
- **Detection** (25): WAF in block mode (monitor gives partial), SQLi shield enabled, all hard categories on, auth endpoints declared, outbound filter on.
- **Abuse controls** (10): rate limits on auth endpoints, challenge configured, scanner policy on.
- **Operations** (10): alert channel tested, MFA required for org, DNS backup exported, appeals enabled.
Each check shows `Pass`, `Partial`, `Fail` or `Unknown (reason)`, a plain "why it matters", and a fix link. Unknown never scores as pass.

#### S-057 Vulnerable-Origin Shield

Regions: (1) explainer card using `shield-title/body/limit`; (2) master toggle with strictness `Balanced` or `Paranoid` and consequence text; (3) **Ban behavior** panel: "Ban on first clear attack" (on by default), TTL ladder editor (1 h, 6 h, 24 h, 7 d), cross-site handling explanation, CGNAT option "challenge instead of ban"; (4) **Declared login and form endpoints** table (path, method, kind, detected or declared, strict) with auto-detected suggestions; (5) **SQL injection** panel listing subtypes (tautology, comment termination, UNION, stacked, time-based, error-based, out-of-band, schema discovery, evasion) each with an enable toggle (default on, cannot all be disabled in Paranoid) and counters; (6) **Learned parameter shapes** (opt-in) with enforce toggle in log or block; (7) **Try a payload** box: textarea + vector selector + field type; submit calls the inspect API and shows verdict, matched subtype, ban-would-apply, no request is sent to the origin; includes quick fills of the six canonical payloads; (8) **Outbound leak protection** link; (9) **Limits** statement with link to S-003.

#### S-059 Rule builder

Header: name, description, priority, scope (path pattern and methods), expiry (required for `allow` rules). Conditions: rows of `[field] [operator] [value]` joined by AND within a group and OR between groups; fields: URI path, query, any parameter name/value, header, cookie, method, client IP/CIDR, country, ASN, user agent, body contains, JSON path, request size; operators: equals, contains, starts/ends with, matches regex (restricted subset with diagnostics), in list, in CIDR, greater/less than. Actions: block, ban, challenge, log, allow. Preview panel: human-readable sentence ("Block when the path starts with /admin and the country is not NL"), validation messages from the server with source positions, sample tester (paste a request or URL) calling `/rules/test`, link to dry-run. Self-lockout warning if the rule would match the current IP. Save creates a revision with the author and note.

#### S-065 Live threat monitor

Table columns: time, Ray ID chip, IP chip (country, ASN), domain, category + subtype, action, rule, vector/field, redacted payload excerpt (escaped, 120 characters, expand in drawer), status. Controls: Pause/Resume, "N new events", filters (category, action, severity, IP, rule, vector, country), density, column visibility, saved views, export. SSE connection status indicator in text ("Live", "Reconnecting in 4 s", "Paused"). Row Enter opens S-066 in a drawer (focus returns to row). Stored-XSS payloads render escaped. Bulk selection supports ban and exception creation. Virtualization applies above 500 rows with `aria-rowcount`.

#### S-067 IP jail

Columns: IP/CIDR, reason, rule and subtype, created, expires with countdown, hits since ban, scope (domain, org, platform), source (auto or manual). Actions: Unban, extend, convert to allowlist exception (with reason), add manual ban (form with self-lockout guard and collateral-risk hint: estimated shared-address risk from rDNS/ASN class and recent distinct sessions). Unban shows "Effective within 2 seconds" and then a live verification status (L7, kernel). Empty state: "No active bans".

#### S-140 Block page (visitor)

Server-rendered by the proxy from a compiled template; no external requests; inline critical CSS with a nonce (the data-plane CSP allows only that nonce); dark/light via `prefers-color-scheme`; elements: tenant logo (if configured), title, body, Ray ID with copy button (progressive enhancement), "Report a mistaken block" link (if appeals enabled), footer "Protected by Hack Dev Defence" (configurable off on paid plans). For `Accept: application/json` returns `{error:"access_denied", ray_id}`. Status 403. Content never includes which rule fired.

#### S-102 Tenant detail (admin)

Header with org name, plan, status, created; tabs: Overview (usage vs quota), Domains (state, WAF mode, abuse flags), Members (roles, last active, MFA state), Abuse (reports and actions), Notes, Audit (filtered). Actions: change plan (step-up), suspend/unsuspend (reason required; customer email preview), impersonate (reason, duration), export tenant summary. Every action shows the audit event that will be written.

#### S-100 Admin overview

Cards: edge health (proxy/DNS up, config revision, p99 added latency), control health (API/web/worker, queue depth), data stores (Postgres/Redis), certificates expiring within a quarter lifetime, ban set size and kernel enforcement, shield state, attack summary last hour (top categories, top ASNs), abuse queue, signups (24 h), pending upgrades. All numbers come from real metrics; missing sources display "Unknown (reason)".

#### S-110/S-111 Infra and services

Nodes table: role, version, build commit, last heartbeat, config revision, drift indicator; services list with readiness probes and last restart; queues with depth, oldest job age, failure counts and retry actions (with confirmation).

#### S-131 Access gate

Two columns on wide screens: the rule list (path pattern, methods, policy chip, on-fail behavior, hits in 24 h, enabled toggle) and a detail editor. The template picker offers WordPress admin, phpMyAdmin and Adminer, Spring actuator, generic `/admin`, `/server-status`, `/.env` and `/.git` denial, API documentation pages. Creating a rule shows the **self-lockout preview** ("Your current address would be allowed / blocked / asked to sign in") before saving (R-19). Credentials are created with a one-time reveal; the screen never shows a stored secret. Signed links show their expiry and are revocable.

#### S-132 API discovery and schemas

Top tiles: endpoints total, approved, shadow (seen but not in any approved spec), schema coverage. Table columns: method, path template, state chip, calls (7 d), authenticated share, schema status. Row drawer: observed parameter shapes (types and length bounds only; never values), the proposed schema, approve or block actions. The enforcement panel offers `off`, `monitor`, `block`; switching to `block` first runs the preview and requires acknowledging any would-have-blocked traffic (`ERR-APIDISC-002`).

#### S-133 Business flows

Flow cards show kind, matched endpoints, active signals (velocity, time-to-complete, honey field, sequence, distinct-credential ratio, response-ratio), mode, and a sparkline of triggers. A flow opens a form with conditions and limits in plain language, plus **Simulate**, which replays recent events and lists the actions that would have fired. Defaults ship in `monitor`.

#### S-134 Coverage map

Grouped accordions per standard. Each row: category, status chip (Covered, Partial, Signal only, Not covered) with text as well as color, what is detected, how it is tested (AC and ATK IDs linking to the evidence summary), and limits. A fixed section at the end, "What HDD does not cover", is never collapsed. The page shows the date and commit of the data it was generated from.

#### S-135/S-136 Runtime, hosting and first-run setup

S-135 is a status page, not a control panel: every number is a real metric. S-136 (hosted) lists each hosting check with pass, fail or unknown (reason) and a remediation link to the exact `docs/HOSTING.md` section; it never claims uptime it cannot measure. S-136 (local `/setup`) is a four-step flow: enter the bootstrap token, create the platform owner (strong password, MFA enrollment), choose the trust option for the local certificate authority (install into the OS store with consent, or use the browser exception instructions, or HTTP-only on loopback), and run a self-test that reports its own results.

(The remaining screens follow the same structure; their task blocks in Part D specify fields, validations, states and tests in detail.)
