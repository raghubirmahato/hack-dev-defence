# UXD-002: Server-rendered UI

Status: accepted
Date: 2026-10-19

Part of the [UX charter](../CHARTER.md), principle 5. Source: the technology table of the build specification (section 5).

## Context

HDD must be fast on a modest phone connection, work with a strict content security policy, run on a small personal
computer or a server, and stay inspectable by one operator. A client-side application framework adds weight, a second
build chain and a larger attack surface to a product whose job is security.

## Decision

Pages are rendered on the server from templates (`axum` with `askama`) and use first-party components. Interactivity is
added in small steps: one vendored HTMX file and a few first-party ES-module islands for things a form cannot do (theme
switch, toasts, clipboard, live feed). Every page must work, in a reduced form, without JavaScript. Charts are drawn as
SVG on the server. Fonts and icons are self-hosted. The T-0071 spike may replace the HTMX plus islands choice with
another server-rendered approach, but not with a client-only application.

## Consequences

- Performance budgets (page weight, layout shift, time to interactive on a throttled 4G profile) are tests (R-29, AC-41).
- Forms post to the server and return full pages or fragments; state lives on the server, which also keeps the API and
  the UI on the same authorization path (R-27).
- Some interactions, such as drag to reorder, need a keyboard-operable alternative that does not depend on a framework.
- A feature that cannot be built within the island budget is redesigned or recorded as a deviation.
