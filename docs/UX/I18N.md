## Message format

Messages use the Fluent format: a semantic key, an equals sign and one message with placeables and selectors. A key is
never a sentence, one sentence is one message, and a message that needs two variants owns them with a selector. The
table gives real examples from the files that exist today; the check verifies that each key is defined in the named
file and that the value quoted here equals the value in the file.

| Key | File | Value |
| --- | --- | --- |
| `tagline` | `i18n/en/copy-deck.ftl` | Put a firewall in front of your website. See what it blocks. Undo anything. |
| `signup-title` | `i18n/en/copy-deck.ftl` | Create your account |
| `domain-add-title` | `i18n/en/copy-deck.ftl` | Add a website |
| `block-confirm-body` | `i18n/en/copy-deck.ftl` | HDD will block matching requests and ban the sending IP address. Visitors sharing an address with an attacker can be affected. You can switch back at any time. |
| `empty-domains` | `i18n/en/copy-deck.ftl` | You have not added a website yet. Add one to get started. |
| `unknown-value` | `i18n/en/copy-deck.ftl` | Unknown ({reason}) |
| `domain-remove-confirm` | `i18n/en/security-ux.ftl` | Type { $domain } to remove it. The zone export and the revert steps stay available after the removal. |
| `org-delete-confirm` | `i18n/en/security-ux.ftl` | Type { $org } to delete the organisation. Domains, members and keys are deleted; the export stays downloadable. |
| `block-mode-confirm` | `i18n/en/security-ux.ftl` | Switch { $domain } to block mode? Matching requests are refused and the sending address is banned. You can switch back at any time. |

| `empty-alerts` | `i18n/en/onboarding.ftl` | No alert rule exists yet. Create one so the team hears about the events that matter. |

A message never builds a sentence from two keys: `{$domain}` is a placeholder inside the sentence, and a count uses a
selector. No shipped message uses a count today; the first one takes the shape below, which is the example in
[CONTENT.md](CONTENT.md) and not yet a key:

```fluent
# shape only; the key is defined when the first count message lands
{ $count ->
    [one] { $count } event
   *[other] { $count } events
}
```

## Key naming

A key matches `^[a-z0-9]+(-[a-z0-9]+)*$`: lower-case words joined by hyphens, at least two parts, and the area word
comes first (`domain-add-title`, `block-page-body`). A key is semantic and never sentences, so a translator reads the
meaning without seeing the screen. Keys are not numbered to make two variants differ, because two variants of one
sentence belong in one message with a selector. A new area prefix is added with its file, not inside another area's
keys. The one single-word key in the shipped deck, `tagline`, is grandfathered and is not renamed; no new single-word
key is added.

duplicate key across the files is a check finding.

## Fallback and missing keys

The fallback chain is `locale → language → en`: a message missing in `pt-BR` is read from `pt` and then from `en`.
T-0082 loads the files at build time (compile-time embedding) and falls back at runtime, so a message that is shipped
in one locale only still renders in English instead of failing a request. A missing key fails the build or test in CI
(T-0082 A1), and that is the primary control; the runtime path is the second line. At runtime the loader renders the
key with a marker, increments a counter and records the stable log event `i18n.missing_key` with the key and locale,
and the request continues. A missing key is never rendered as an empty string, because an empty label looks like a
layout bug. A placeholder mismatch is not a fallback case: it fails the lint, because a missing argument changes the
sentence. The runtime that performs all of this is delivered by T-0082 and does not run today.

## Pseudo-locale

The pseudo-locale exposes text that is too long and text that was copied instead of translated. It is a build
artifact: the generator writes `i18n/pseudo/` and that locale is not shipped in the profile `locales`, so nobody can
select it. The transform is fixed, and this table and the accent table below are evaluated by the `ux-docs` check
against the reference implementation in `i18n_plan.rs`, which is the same function T-0082 implements.

1. A placeable reference — a `$var`, a term `-term`, or a function call such as `NUMBER($n)` — is copied unchanged
   and does not expand.
2. In a select expression the selector reference and the `[one]` and `*[other]` variant keys are copied, and the
   variant text is transformed like the rest of the message: a plural or select is accented and expanded too, so the
   pseudo locale can test it.
3. A maximal run of ASCII letters is accented letter by letter with the table below, case preserved, and receives
   `ceil(40%)` of its letter count as `·` filler characters. The count is the number of letters in the word, the
   rounding is up per word (`ceil(2n / 5)` for `n` letters), and the filler is capped at 8 characters per word.
4. Digits, punctuation, spaces and other non-ASCII characters are copied unchanged and do not count towards the 40%.
5. The whole message is wrapped in `[[` and `]]` bracket markers, so a translator can see a message boundary and a
   clipped string loses a visible marker.

The 8-character cap is a deliberate limit rather than part of the 40% rule: a longer word would otherwise produce an
unreadable run of filler, and the cap is exactly why the 30-letter example below measures 27% instead of 40%. The
`Measured expansion` column gives `fillers/letters = percent%` for every worked example, the percentage rounded half
up, so a reader can see both ordinary words and the capped one. The expansion is measured against the letter count,
not the byte length; the four marker characters sit outside the 40% target and outside the measured value. Worked
examples, evaluated by the check:

| Input | Expected pseudo | Measured expansion |
| --- | --- | --- |
| `Save` | `[[Šáṽé··]]` | 2/4 = 50% |
| `Domain added.` | `[[Ðóɱáíñ··· áððéð··.]]` | 5/11 = 45% |
| `Switch { $domain } to block mode?` | `[[Šŵíţçĥ··· { $domain } ţó· ƀĺóçķ·· ɱóðé··?]]` | 8/17 = 47% |
| `0 events` | `[[0 éṽéñţš···]]` | 3/6 = 50% |
| `OK` | `[[ÓĶ·]]` | 1/2 = 50% |
| `a` | `[[á·]]` | 1/1 = 100% |

## RTL readiness

The direction follows the locale, and the direction is server-rendered from it. The response renders the `<html>`
element with
`lang` and `dir` already set from the negotiated locale (for example `<html lang="ar" dir="rtl">`), so no client
script flips the page after paint and there is no flash of the wrong direction. Localised components inherit the
direction from `<html>`. Two exceptions are
explicit: a user-provided value (a domain name, an organisation name, a display name) gets `dir="auto"` so a right-to-
left name reads correctly inside a left-to-right paragraph, and a machine identifier (a Ray ID, a rule ID, an API key,
a hostname, a code sample) gets `dir="ltr"` so the bidirectional algorithm does not reorder it. For the same reason a
copied identifier is wrapped in `unicode-bidi: isolate`, not merely styled to look left to right. The
`LocaleSwitcher`, `ThemeToggle` and `DensityToggle` components own the display choices and `MarkdownRender` sets
`dir="auto"` on a user block; those are the owners that [ACCESSIBILITY.md](ACCESSIBILITY.md) maps to WCAG 3.1.1
through the `Locale and language` page pattern and to WCAG 3.1.2 through the components.

A component stylesheet uses the logical property, never the physical one. The physical property in the second column
is not allowed in a component stylesheet:

| Logical property | Replaces | Use |
| --- | --- | --- |
| `margin-inline-start` | `margin-left` | start margin of a card |
| `margin-inline-end` | `margin-right` | end margin of a card |
| `margin-block-start` | `margin-top` | space above a section |
| `margin-block-end` | `margin-bottom` | space below a section |
| `padding-inline-start` | `padding-left` | start padding of a row |
| `padding-inline-end` | `padding-right` | end padding of a row |
| `padding-block-start` | `padding-top` | top padding of a cell |
| `padding-block-end` | `padding-bottom` | bottom padding of a cell |
| `border-inline-start` | `border-left` | start edge of a table cell |
| `border-inline-end` | `border-right` | end edge of a table cell |
| `inset-inline-start` | `left` | drawer edge and pinned bar |
| `inset-inline-end` | `right` | drawer edge and pinned bar |

The same rule bans `text-align: left` and `float: left` in a component stylesheet, and it bans the shorthand
`margin` only where its two-value form would assume a physical side; the four logical longhands are used instead. A
physical value survives only in the exceptions list of [RESPONSIVE.md](RESPONSIVE.md), for example a printed sheet,
never in a product component.

**Mirrored icons.** The list below names icon roles, not files, because no icon inventory exists yet: `design/` holds
no icon files, and T-0034 owns the icon system and must give every directional icon a mirror flag and an inventory
entry before the first RTL screen ships. The check reads `design/` at run time: while it holds no icon files this
document must keep the honest statement, and once T-0034 adds them the table must name the real files. A directional
icon that points along the reading direction mirrors; a non-directional icon does not.

| Icon role | Mirrors in RTL | Why |
| --- | --- | --- |
| back | yes | points against the reading direction |
| forward | yes | points along the reading direction |
| chevron start | yes | points to the start edge |
| chevron end | yes | points to the end edge |
| undo | yes | restores the previous state in reading order |
| redo | yes | replays the change in reading order |
| indent | yes | moves text towards the start edge |
| outdent | yes | moves text towards the start edge |
| sidebar collapse | yes | collapses towards the start edge |
| external link | no | the destination does not change direction |
| search | no | a magnifier has no direction |
| status dot | no | a state marker has no direction |

The visual run is `pseudo-RTL` at the seven viewports of [RESPONSIVE.md](RESPONSIVE.md): 360x740, 390x844, 768x1024,
1024x768, 1280x800, 1536x864 and 1920x1080, using the `--direction rtl` harness flag. The list is compared with the
device matrix of RESPONSIVE.md, not copied. The pseudo-locale run above is combined with it in the same capture pass,
so an overflow and a mirrored layout are visible together.

Printing follows the canonical rule of RESPONSIVE.md: A4 portrait with 12 mm margins on every edge, 210 x 297 mm.
The audit export and the report pages keep the same logical margins when the document direction is right to left,
and a bidi identifier keeps its isolation on paper. Locale-dependent Letter paper for a United States locale is an
open item for T-0048 and is not fixed here; when it lands it must be stated in RESPONSIVE.md and this document must
point there instead of holding its own value.

## Locale negotiation

The server negotiates one locale per request, in this order:

1. the account setting (`users.locale`, edited through `PATCH /me`), which is the only source an authenticated user
   has chosen explicitly;
2. the signed preference cookie (`hdd_locale`), HMAC-signed with `HDD_SESSION_KEY`, size-capped and ignored when
   tampered with (T-0081), which keeps the choice of an anonymous visitor;
3. the `Accept-Language` header, highest quality value first with the base language tried before a region variant;
4. the default `HDD_I18N_DEFAULT_LOCALE`, which is `en`.

The choice is server-rendered: the response carries `lang` and `dir` on the `<html>` element, the `Content-Language`
header names the chosen locale and the response sends `Vary: Accept-Language, Cookie` so a shared cache cannot serve
one locale in place of another. A locale is never put in the URL of the app and no redirect is used to switch it. A
public page carries `hreflang` link tags for the shipped locales, so a search engine can index each language variant.
The account setting outranks the cookie because a signed-in user expects the profile choice to follow them to another
device, and the cookie outranks `Accept-Language` because it is the same browser that already chose.

## Formatting

T-0083 fixes the rule: keep all stored timestamps in UTC and display them in the user time zone. The stored column is
`timestamptz`, an API response carries ISO 8601 with `Z`, and the display zone is an IANA zone name. The user zone
comes from the account setting, then a browser hint stored once, then UTC; reports use the org's configured zone and
state it in the report header. Half-hour offsets such as Asia/Kathmandu (+05:45) are test cases, because an offset is
not always a whole hour. An absent value renders as `Unknown (reason)` from B13, never as zero or as a dash that
looks like data. B11.9 fixes the screen rule: relative time with the absolute time in `<time datetime>` and `title`,
the UTC offset visible, and the user time zone from the profile; large numbers are abbreviated only in cards and exact
in tables, with units explicit.

| Item | Rule (en) | Fluent message | Example |
| --- | --- | --- | --- |
| Date | year first, month, day | `DATETIME($ts, dateStyle: "medium")` | 2026-10-19 |
| Time | 24-hour clock with the zone on the same line | `DATETIME($ts, timeStyle: "short", timeZone: $zone)` | 14:05 UTC |
| Number | whole number grouped in threes | `NUMBER($count)` | 1,204 requests |
| Percentage | at most one decimal place | `NUMBER($ratio, style: "percent", maximumFractionDigits: 1)` | 98.6% |
| Bytes | decimal unit with one decimal place | `NUMBER($bytes, style: "unit", unit: "megabyte", unitDisplay: "short")` | 1.2 MB |
| Duration | number and unit, spelled out under one minute | `{ $count -> [one] { $count } second *[other] { $count } seconds }` | 45 seconds |
| Duration, compound | one message with both placeables so the translator can reorder them | `{ $hours } h { $minutes } min` | 2 h 10 min |
| Relative time | absolute time plus a relative span | `{ $count -> [one] { $count } minute ago *[other] { $count } minutes ago }` | 12 minutes ago (14:05 UTC) |
| Time zone | IANA name shown with the time, UTC for storage | `DATETIME($ts, timeZone: $zone, timeStyle: "long")` | 14:05 UTC |
| Address | the address as written, in a monospace field | no formatter; the value is copied | 203.0.113.10 |

A counted message is one Fluent selector, so the same key renders `1 event` or `2 events` and no second key or
concatenation is needed; the content-strategy table above names the same rule.

The examples are the format table of [CONTENT.md](CONTENT.md), and the check compares the two tables instead of
trusting this copy. A duration over an hour is one message, not two formatted fragments joined in code, because a
translator must be able to put the hours and minutes in the other order. Sorting is done by collation, not by code
point: a name list sorts with the locale's collation rules.

## Not translated

These values are machine text and are never translated, because the API, the log search and support scripts compare
them byte for byte. A translated identifier would break a lookup or a signature.

| Category | Example | Why it stays the same |
| --- | --- | --- |
| Ray ID | `0123456789abcdef-HDD1` | 16 hex characters plus `-HDD1`; the visitor, the appeal and support all quote it |
| Rule ID | `rule_ab2cd3ef4gh5jk6mn7pq2rs3tu` | `rule_` plus 26 lower-case base32 characters; the log and the API agree on it |
| API identifier | `ray_id` | JSON field names and endpoint paths are the client contract |
| Log line | a JSON log line with `event` and `ray_id` | operator searches and support scripts match JSON logs |
| Error code | `ERR-SYS-001` | the code is stable; the sentence next to it is translated |
| Audit event id | `AUD-domain.created` | the hash-chained audit names the event and a rename breaks the chain check |
| Metric id | `MET-hdd_panics_total` | the exported metric name is the monitoring contract |
| User data | a domain name or an organisation name | user text is shown as written, never translated or reordered |

**What is translated:** the UI strings (every user-visible string is a Fluent key), the emails (subject and body), the
user-facing error sentences (a code selects the key, then the message is translated) and the user documentation (the
English page stays the source and stays available). What is not translated is the list above, and a screen never
puts a translated word in place of an identifier.

## Email localization

An email has one subject message and one body message in the area file of its family. The notification catalog of
T-0110 lives in `i18n/<locale>/email.ftl`; the four activation emails are the onboarding family and live in
`i18n/<locale>/onboarding.ftl`, as [ONBOARDING.md](ONBOARDING.md) declares. The split is deliberate: the activation
family is designed and reviewed with the onboarding journey, so its copy stays in that area file, while the
notification catalog is one file owned by T-0110. Every email has an HTML and a text variant, a 600 px maximum width,
no remote image and a golden file per locale. The whole email falls back to `en` when
its locale lacks a message, never half of it, because a half-translated email reads worse than an English one.
`mail_outbox` stores the requested locale with the message, and a fallback records the stable log event
`i18n.email_fallback` so the gap is visible before a customer reports it.

| verify | subject and body | whole email to `en` |
| first domain | subject and body | whole email to `en` |
| weekly summary | subject and body | whole email to `en` |

## Translator workflow

The hand-off is a directory in the repository: no account, no external service and no network egress, so a translator
needs no third-party platform and the product keeps its one egress path. A translator receives the exported files,
edits them offline and returns them in a branch; the reviewer reads the same files in the same diff. Each exported key
carries a `# context:` note with the screen id, the maximum length, the placeholder list and the screenshot path, so a
translator never has to guess the space a string has to fit.

| Step | Who | Artifact | Gate |
| --- | --- | --- | --- |
| export | owner | `i18n/<locale>/<area>.ftl` with one `# context:` note per key | every key has the screen, the maximum length and the placeholder list |
| translate | translator | the same file, edited offline | the translator reads the glossary and the claims rules |
| import | translator | a branch of the repository | the diff names every changed key and no other change |
| lint | owner | the lint report | missing keys, unused keys and placeholder mismatches are findings |
| review | a native speaker | the review note in the branch | the glossary and the claims policy pass before merge |

The lint is `cargo xtask i18n check`, which is a stub until T-0082; today the `ux-docs` style check runs on the
English deck only. The lint finds six kinds: a missing key per locale, an unused key, a placeholder mismatch between
two locales, a forbidden concatenation pattern, a string over its length limit and a key that breaks the naming
convention. Every string is an i18n key in `i18n/en/*.ftl`, keys are semantic stems such as `domain-add-step2-title`,
never sentences, and a translator never concatenates sentence fragments. A message puts a Fluent placeable such as
`{$domain}` or `{$ray_id}` inside the sentence, and a count gets a selector with `[one]` and `[other]`; that is the
guidance of [CONTENT.md](CONTENT.md), and the check compares this document with the actual guidance section instead
of restating it from memory. A placeholder is never translated and never dropped.

## Test strategy

The tests below are the gates for T-0082 and T-0083. The browser part is `UNVERIFIED(capability_not_supplied)` until
T-0082 lands, and this document says so instead of presenting a plan as a result.

| Test | What it proves | Runs in |
| --- | --- | --- |
| pseudo-locale overflow | no clipped text: scroll width vs client width at the seven viewports | T-0082 browser |
| truncation | an ellipsis appears only with an accessible full text | T-0082 browser |
| missing key | a missing key fails the build or test in CI | T-0082 unit |
| unused key | a key that no template uses is a finding | T-0082 lint |
| placeholder | a placeholder mismatch between locales is a finding | T-0082 lint |
| plural | `[one]` and `[other]` for English plus a synthetic few and many locale | T-0082 unit |
| negotiation | the four sources are tried in the order account, cookie, `Accept-Language`, default | T-0082 unit |
| lang and dir | the attributes follow the negotiated locale and a user value gets `dir="auto"` | T-0082 integration |
| email golden | one golden file per locale for every activation email | T-0110 |
| formatting | date, number, relative time and duration per zone, including a half-hour offset | T-0083 unit |
| proptest | no formatting function panics on extreme input | T-0083 proptest |
| collation | a name list sorts with the locale rules | T-0083 unit |

The overflow test is the pseudo-locale visual test of A5: the harness renders the gallery in the pseudo locale, reads
`scroll width` and `client width` for every text container, and fails when the content is wider than the box. A
button may wrap but may not clip; a table cell may scroll inside a focusable region but may not hide a word; a
truncated value must expose its full text in `title` or in an adjacent accessible description. The missing-key test
fails the build in CI, and the plural tests cover English and a synthetic locale with `few` and `many` categories, so
the selector path is exercised before a real language needs it.
