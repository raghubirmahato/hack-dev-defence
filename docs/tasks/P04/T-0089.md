### T-0089 · Browser end-to-end harness: real server, real databases, helpers
`P04` `[QA]` · deps: T-0047, T-0073 · size: L · owner: qa
**Objective.** Make browser-driven tests reliable, fast and realistic.
**Steps.**
1. Extend the v0 harness: start `hdd-web` (and later `hdd-api`) on ephemeral ports with real Postgres and Redis from `testcontainers` (Track H) or the embedded PostgreSQL and in-process stores started by `cargo xtask db up` (Track L, T-0563), migrations applied, a real SMTP sink container (Mailpit-class), and per-test isolated schemas or databases.
2. Provide a `TestApp` fixture with helpers: create user, org, domain via the real API or service layer (never raw SQL except for time travel), log in through the UI or a trusted test seam that uses the same code path as the login handler (documented, not a bypass), capture emails from the sink.
3. Provide browser helpers: navigate, click by accessible name/role, fill by label, wait for network idle and HTMX settle, assert accessible tree snapshots (`insta`), capture screenshots on failure with the HTML and console log.
4. Provide traps: console errors, CSP violations, failed requests, request log, unexpected downloads; each fails the test unless explicitly allowed.
5. Provide parallelism controls and flake handling: retries are not allowed to hide failures; flaky tests are quarantined only with a diagnosis file (R-14).
6. Provide time control: a server-side test clock for session expiry, ban TTL and token expiry tests, implemented through an injectable `Clock` trait in services (production uses the system clock).
7. Provide the viewport and theme matrix runner reused by visual tests.
8. Document how to write a browser test and the performance expectations (suite under 10 minutes on the builder).
**Deliverables.**
- `crates/hdd-xtask/src/browser/*` (shared), `tests/e2e/` scaffolding, docs
**Acceptance.**
- A1: a sample test logs in (through the real flow once P06 lands; before that through the gallery) and passes in isolation and in parallel.
- A2: a console error or CSP violation fails a test unless allowlisted with a comment.
- A3: failures produce artifacts (HTML, screenshot, console, network) under `acceptance-ui/failures/`.
- A4: the clock injection works without global state hacks.
- A5: the suite can run N tests in parallel without cross-talk (isolation test).
**Tests.**
- Meta-tests: a deliberately failing test produces artifacts; an isolation test creates two orgs in parallel and proves no leakage.
**Notes.** No browser test uses mocked network responses; the server and stores are real.
