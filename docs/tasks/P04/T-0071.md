### T-0071 · UI stack spike and ADR: askama + HTMX + vanilla islands versus Leptos SSR
`P04` `[UI][DOC]` · deps: T-0052 · size: M · owner: ui
**Objective.** Decide the interactive UI stack with evidence rather than preference, within the Rust-first constraints.
**Steps.**
1. Define evaluation criteria with weights: total shipped bytes (JS+WASM) on a representative screen, accessibility of generated markup, server-render simplicity, form handling and progressive enhancement without JS, testability with `chromiumoxide`, build time, maintenance risk (crate activity, MSRV), compile times, hot-path memory, and fit with CSP (no `unsafe-eval`, no inline script).
2. Build two minimal vertical slices of the same screen (a data table with filters, a modal confirm, a live feed list, and a form with server validation): slice A with `axum` + `askama` + HTMX + 2 islands, slice B with Leptos SSR (and islands/WASM only if required).
3. Measure: bytes over the wire, time to interactive in the harness, markup quality via axe, lines of code, build time, test ergonomics, and behavior with JavaScript disabled.
4. Evaluate CSP compatibility specifically: nonce propagation, WASM instantiation requirements (`wasm-unsafe-eval`), and Trusted Types.
5. Evaluate the maintenance risk: release cadence, breaking-change history (from the registries and changelogs, read through the egress client if allowlisted, otherwise from the repositories' tags), license, and bus-factor notes.
6. Score both options and write the ADR with the decision, the rejected alternative and why, risks, and the rollback plan (how to switch if the decision proves wrong).
7. Record the default (askama + HTMX + islands) as the baseline if the spike is inconclusive and note `DEV-V5-005` if Leptos is chosen (rust-share implications).
8. Delete the spike code or move it to `design/spikes/` (not part of the workspace build).
**Deliverables.**
- `docs/adr/00NN-ui-stack.md`, `design/spikes/ui-stack/` (non-shipping), measurement tables
**Acceptance.**
- A1: both slices are measured with the same harness and conditions; numbers are in the ADR.
- A2: JS-disabled behavior is evaluated and recorded for both.
- A3: CSP implications (including WASM) are explicit.
- A4: the ADR includes a concrete rollback plan.
- A5: the decision does not violate the JS and CSS caps of DEV-V5-002 and Part A budgets.
**Tests.**
- Spike measurement script outputs are stored with SHA-256 under `acceptance-ui/`.
- ADR review checklist: every criterion has a measured or documented value.
**Notes.** The rest of this specification assumes the default (askama + HTMX + islands); if the ADR chooses otherwise, the affected tasks are revised through `docs/UX/spec-patches.md` before use.

## Definition of done for this task's tags (section 0.7)

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.

### `[DOC]`: Documentation

Every claim backed by a test ID or a command the reader can run; passes claims-lint; included in the docs site if user-facing.
