### T-0008 · ADR process and the initial decision queue
`P00` `[DOC][SEC]` · deps: T-0002 · size: S · owner: docs
**Objective.** Make design decisions explicit, reviewable and scheduled.
**Steps.**
1. Finalize the ADR template (context, options with pros/cons, decision, consequences, security impact, rollback plan, status, links to spikes and tests).
2. Create `docs/adr/INDEX.md` with status columns (proposed, spiking, accepted, superseded).
3. Seed the queue with these ADRs and the task that decides each: crypto provider (T-0354), YAML vs TOML (T-0006), UI stack (T-0071), password-strength estimator (T-0106), i18n library (T-0082), HTML sanitizer (T-0097), PDF path (T-0448), session store layout (T-0113), WebAuthn FFI (T-0116), chart renderer (T-0088), icon set licensing (T-0034), docs search (T-0097), hickory server customization (T-0387), `instant-acme` ARI (T-0376), `tls-parser` peeking (T-0342), Pingora vs own proxy (T-0353), `aya` and nightly (T-0466), `cargo-geiger` viability (T-0517), deployment path (T-0521), rate limiter keys (T-0333), challenge cryptography (T-0337), `wasmtime` (T-0547), `quinn`/`h3` (T-0549), ClickHouse (T-0551).
4. Write the rule: an ADR is required before adding any crate that is FFI, unmaintained for over a year, or has `unsafe` in its public API.
5. Add a lint in `xtask verify`: a new dependency in `Cargo.toml` without a matching ADR reference or vetting note in the commit body is flagged.
6. Add a small `docs/adr/README.md` explaining how to propose, spike, accept, and supersede.
7. Link ADR numbers into `STATUS.md` Open risks when status is `spiking`.
8. Commit.
**Deliverables.**
- `docs/adr/0000-template.md`, `docs/adr/INDEX.md`, `docs/adr/README.md`
- the 24 queued ADR stubs (title, task link, status `proposed`)
**Acceptance.**
- A1: every ADR in the queue names the task that decides it.
- A2: `xtask verify` flags a dependency addition lacking vetting.
- A3: the template includes a rollback plan field.
- A4: ADR numbers are monotonic and referenced from the index.
- A5: no ADR is marked accepted without a spike link or a stated reason.
**Tests.**
- Unit test for the dependency-vetting lint (adds a crate to a temp manifest, expects a finding).
**Notes.** Substitutions of fixed stack choices (section 6) always need an ADR.

## Definition of done for this task's tags (section 0.7)

### `[DOC]`: Documentation

Every claim backed by a test ID or a command the reader can run; passes claims-lint; included in the docs site if user-facing.

### `[SEC]`: Security-relevant logic

Abuse cases written as tests; STRIDE delta in `docs/STRIDE.md`; no secret in logs; constant-time comparison where secrets are compared; failure modes fail closed; panic-free on hostile input (proptest or fuzz target).

## Per-task protocol (section 0.6)

1. [ ] Read the task block and every registry row it references; copy the acceptance criteria into `STATUS.md`.
2. [ ] Decide the tests first (unit, property, integration with real local services, browser e2e, lab, live); write them failing (`red`) and commit.
3. [ ] Implement the minimum that satisfies the acceptance criteria; reuse, do not duplicate.
4. [ ] Run `cargo xtask verify` (and `cargo xtask ui verify` for `[UI]`); fix root causes (failure budget R-14: at most 3 attempts, then `docs/diagnoses/`).
