### T-0003 · Environment discovery with read-only commands
`P00` `[OPS]` · deps: T-0002 · size: S · owner: infra
**Objective.** Record what the builder, VPS (when reachable) and runner can and cannot do, and state what degrades.
**Steps.**
1. On the builder, record the operating system and architecture (Windows, macOS or Linux; PowerShell equivalents of the commands below on Windows) and run read-only commands: `rustc -V`, `cargo -V`, nightly and `bpf-linker` presence, `docker -v` and compose, `dig -v`, `delv -v`, `openssl version`, `ssh -V`, `nft --version`, `iptables -V`, kernel version, `/sys/kernel/btf/vmlinux` presence, virtualization (`systemd-detect-virt`), CPU, RAM, disk.
2. Record browser readiness: Chromium path (`/opt/pw-browsers/chromium` in cloud sessions), headless launch test, fonts installed; confirm Node is **not** required.
3. If `deploy_mode: ssh`, run the same read-only commands on the VPS through the configured SSH account and add NIC driver, link speed (`ethtool`), XDP native/generic support (read-only probe), ability to bind 53/80/443 (checked with `ss -ltn` and capability inspection, not by binding), NTP sync (`timedatectl`).
4. Test outbound connectivity **only** to hosts on the egress allowlist; record failures as `environment_unsupported` rather than trying other hosts.
5. For each missing tool, write what degrades (for example "no nightly toolchain: XDP crate cannot build, AC-26 becomes UNVERIFIED(environment_unsupported)"). Status words: a missing optional tool (`dig`, `delv`, `openssl`, a nightly toolchain) is `UNVERIFIED(tool_unavailable)`, a capability the platform cannot offer (Docker on this builder, `nft`, binding port 53) is `UNVERIFIED(environment_unsupported)`, and FAIL is reserved for a check that ran and failed; reason codes belong to UNVERIFIED, so `FAIL(environment_unsupported)` is never written.
6. Save full logs under git-ignored `acceptance-env/` with SHA-256 and write the summary to `docs/ENV.md` with command, output tail (last 5 lines), and status per item.
7. Add the degradation list to `STATUS.md` UNVERIFIED section.
8. Decide and record the **build track**: *Track H* (Linux builder with Docker: testcontainers) or *Track L* (no Docker: the embedded PostgreSQL and in-process stores of `hdd-local`, started by `cargo xtask db up` once T-0563 lands). Until T-0563, a Track L builder uses a locally installed PostgreSQL if present, otherwise marks the database-dependent checks UNVERIFIED(`environment_unsupported`) and continues with the tasks that do not need it.
9. Commit `docs/ENV.md`.
**Deliverables.**
- `docs/ENV.md` (table of items, commands, tails, status)
- `acceptance-env/*.log` (ignored) with `SHA256SUMS`
- STATUS.md update
**Acceptance.**
- A1: every item listed in R-05 has a row with a status of PASS, FAIL or UNVERIFIED(reason).
- A2: no command in the discovery set writes outside the scratch directories or changes system state.
- A3: degradation statements exist for every non-PASS row.
- A4: outbound checks touched only allowlisted hosts (verified from the egress client log once T-0009 exists; before that, a manual list is included).
- A5: secrets and key paths are not printed in any output.
**Tests.**
- Re-run the discovery script twice; outputs must be identical except timestamps.
- A review confirms that no command used `sudo` or modified configuration.
**Notes.** Discovery is repeated at the start of P11 (VPS) and P28 (lab) with the same checklist.
