### T-0524 · Upgrade and migration discipline: expand/contract, version skew, canary upgrade and rollback tests (AC-54, part 2)
`P30` `[OPS][DB][QA]` · deps: T-0518, T-0522 · size: L · owner: ops
**Objective.** Make upgrades safe by construction: schema changes that tolerate version skew, tested rollbacks and a staged rollout.
**Steps.**
1. Define the **migration policy** (`docs/MIGRATIONS.md`): every migration is classified `expand` (additive, backward compatible), `backfill`, or `contract` (removal after all code stopped using it); `contract` migrations ship at least one minor release after the code change; migrations are forward-only in production with documented compensating procedures, except those marked reversible and tested; destructive operations require two-release deprecation.
2. Implement **migration linting** (`xtask migrations lint`): blocks risky patterns without justification (`DROP COLUMN/TABLE`, `ALTER COLUMN TYPE` that rewrites large tables, `NOT NULL` additions without defaults, non-concurrent index creation on large tables, long locks), requires `SET lock_timeout`/`statement_timeout`, checks RLS policy presence for new tenant tables, and ensures partitioned table handling.
3. Define **version skew rules**: control plane and data plane may differ by one minor version during an upgrade window; message and snapshot formats are versioned and tolerant (unknown fields ignored, required fields additive); the proxy/DNS refuse snapshots with a newer major schema; tests run old binaries against new schemas and vice versa for the supported skew.
4. Implement the **upgrade orchestration** in `hddctl upgrade` for multi-service sequences: database expand migrations first, then data plane (proxy/DNS) with connection draining and zero dropped connections beyond the documented cap, then control plane, then contract migrations on a later release; each step has health gates and abort/rollback logic; canary upgrade option (upgrade one proxy listener first / one worker) with automatic comparison of error rates and latency before proceeding.
5. Implement **config schema migrations** (`schema_version` upgrades with `hddctl config migrate --dry-run`) and policy document upgrades with fixtures from every past version.
6. Build the **upgrade test matrix** in CI: N-1 → N upgrade with live traffic generator (error budget < 0.01%), N → N-1 rollback (reversible migrations only), skipped versions policy (supported N-2 → N via sequential), and failure injection at every step.
7. Implement **maintenance communication**: pre-upgrade announcement banner (T-0433), status page note, and post-upgrade verification summary.
8. Write the **zero-downtime verification**: during an upgrade, a synthetic client sends 500 rps through the proxy and the success rate must remain ≥ 99.99% with no block-mode fail-open (mandated payload still blocked throughout).
**Deliverables.**
- migration policy and linter, orchestration, test matrix, docs
**Acceptance.**
- A1: the migration linter rejects seeded risky migrations and accepts expand-style ones.
- A2: N-1 → N upgrade under traffic meets the error budget and never fails open.
- A3: rollback tests pass for reversible releases and the forward-only path is documented.
- A4: skewed versions interoperate for the supported window (tests).
- A5: config and policy migrations round-trip all historical fixtures.
**Tests.**
- Upgrade matrix on VMs, linter tests.
**Notes.** The proxy keeps serving from its last snapshot throughout control-plane upgrades.
