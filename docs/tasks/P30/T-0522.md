### T-0522 · `hddctl deploy` v1: full production deployment, idempotent, with dry-run, health checks and rollback
`P30` `[OPS][SEC]` · deps: T-0521, T-0468, T-0469 · size: XL · owner: ops
**Objective.** One command takes a clean Debian/Ubuntu VPS to a hardened, working HDD deployment, and can undo it.
**Steps.**
1. Extend `hddctl deploy` to the full stack: users and directories, Postgres and Redis (hardened configuration, authentication, Unix sockets/loopback, TLS optional), database roles per service (least privilege: `hdd_api`, `hdd_worker`, `hdd_proxy` (config read, `waf_events_ingest` insert only), `hdd_dns` (read-only views plus `waf_events_ingest` insert only), `hdd_readonly` (analytics), `hdd_backup` (backup jobs only), `hdd_owner` for migrations only), migrations, secret generation (`xtask gen-secrets` equivalents in `hddctl`), certificate stores, systemd units from release artifacts, firewall baseline (T-0468), kernel tuning, hardening (T-0469), XDP loader (if supported and enabled), fw-agent, shield, mailer/SMTP config, admin bootstrap (`hddctl admin bootstrap` with MFA enrollment link), and initial health checks.
2. Implement **phases with checkpoints:** preflight → plan (`--dry-run` prints the complete plan with diffs) → apply by stage with persisted state (`/var/lib/hdd/deploy-state.json`) so a failed run resumes idempotently; each stage has an `undo` and a verification.
3. Implement **remote execution** over SSH (`russh`) with host key pinning, a connection through the operator's bastion if configured, sudo handling, and strict command construction (argument arrays); no password logins; the second-session confirmation mechanism for lockout-prone stages.
4. Implement **config rendering** from `hdd.live.yaml`/`hdd.yaml` with validation (schema version 5), secrets only by reference, and a diff view; changes to running systems use `hddctl config apply` with the same safeguards.
5. Implement **post-deploy verification suite:** service readiness, port exposure scan (only intended ports), TLS endpoint check (staging certs in pilot), DNS self-query, proxy-to-canary path, database role privilege assertions (`has_table_privilege` checks), file permission audit, systemd security scores, `smoke` acceptance tier, and a deploy report with hashes (no secrets).
6. Implement **rollback**: `hddctl deploy --rollback` returns to the previous release/config (binaries, units, config); `--uninstall` removes HDD cleanly (documented data retention options) and restores firewall/resolver settings from the pre-deploy backup.
7. Implement **multi-host awareness (Tier 1: single host)**: the state model is host-scoped so future multi-node deployments reuse it; deploying a standby edge (T-0478) uses the same command with `--role edge-standby`.
8. Write VM-based integration tests (Debian 12 and Ubuntu 22.04/24.04): clean install, re-run no-op, interrupted run resume, rollback, uninstall, lockout simulation, failure injection per stage, and idempotency under partial state.
**Deliverables.**
- `hddctl deploy` v1, state machine, verification suite, tests, runbook
**Acceptance.**
- A1: a clean VM reaches a healthy deployment in one command (≤ 15 minutes excluding downloads) and passes the post-deploy suite.
- A2: re-running changes nothing; interrupted runs resume correctly.
- A3: injected failures at every stage lead to a clean rollback or resumable state.
- A4: no secret appears in output, logs or state files except in 0600 secret files.
- A5: role privilege assertions confirm the least-privilege model.
**Tests.**
- VM integration (CI nightly), failure injection.
**Notes.** The operator's production deployment uses this command in P31 after approvals.
