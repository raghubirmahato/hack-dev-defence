### T-0525 · Monitoring, alerting and dashboards: provisioning and runbook mapping
`P30` `[OPS][DOC]` · deps: T-0400, T-0473, T-0453, T-0522 · size: L · owner: ops
**Objective.** Ensure the operator sees problems before customers do and knows what to do about each alert.
**Steps.**
1. Provide the **monitoring stack** (optional but recommended; compose or systemd): Prometheus (or VictoriaMetrics) scraping local metrics endpoints (loopback/private), Alertmanager (or HDD's own notification routing for platform alerts), Grafana provisioned from files (`deploy/grafana/`) with dashboards: Overview, Edge (proxy latency, errors, shed), WAF (verdicts, categories, SQLi, bans), DNS, TLS/ACME, Origin health, Database/Redis, Host (CPU, mem, disk, network, conntrack), Shield/XDP, Queues/jobs, Webhooks/notifications, Security (auth anomalies, admin activity); generated with `xtask grafana` and validated (JSON schema + `promtool` for rules).
2. Define the **alert rule set** (`deploy/prometheus/rules/*.yml`) with severity, thresholds, `for` durations and runbook links: proxy down, high 5xx rate, added latency above budget, snapshot stale, config drift, origin health failing, certificate expiring (lifetime-relative), ACME failures, DNS drops/serving failures, secondary lag, queue stuck, DB connections saturation, replication/WAL archive failure, backup stale, disk usage, memory pressure, fd exhaustion, conntrack near full, XDP self-test failure, shield state ≥ ATTACK, heartbeat missing, audit chain verification failure, mass-ban anomaly, login anomaly spikes on admin, outbound call failures, mail delivery failures; thresholds tuned using soak data.
3. Provide the **external monitoring** guidance and tooling: external uptime checks of `www/app/api/status` and of a proxied canary hostname from outside the VPS (operator-supplied monitor or a small self-hostable checker script `hdd-probe` deployable on a different machine), the status page probes (T-0100) hosted off-box, and the heartbeat dead-man endpoint.
4. Write **runbooks** for every alert (`docs/runbooks/<alert>.md`): meaning, impact, quick checks (commands), common causes, remediation steps with undo, escalation, and verification of recovery; a lint ensures every alert rule has a runbook link and every runbook has a matching alert.
5. Implement **alert testing**: `xtask alerts test` fires synthetic conditions (via metric injection into a test registry or the chaos suite) and verifies rule evaluation and routing; fire drills run quarterly (checklist).
6. Implement **log management:** structured JSON logs to journald, retention limits, optional shipping via the sink (T-0460) to the operator's stack, correlation via Ray ID/request ID, log level controls, and sensitive-field redaction tests.
7. Implement **SLO definitions** (availability of proxy path, latency, DNS availability) with burn-rate alerts and a monthly SLO report generator (computed from real metrics, with gaps labeled).
8. Write tests: dashboard JSON validation, `promtool test rules` unit tests for each rule, runbook coverage lint, alert routing integration tests.
**Deliverables.**
- Grafana/Prometheus provisioning, rule set with tests, runbooks, probe tool, SLO report
**Acceptance.**
- A1: every alert has a runbook and a rule unit test.
- A2: dashboards load without errors against a live deployment (provisioning test).
- A3: synthetic alert drills route to the configured channels.
- A4: external probe detects an induced outage and reports via the dead-man path.
- A5: SLO report generation matches computed values on seeded metrics.
**Tests.**
- `promtool`, JSON schema, integration.
**Notes.** Monitoring components are optional to deploy but strongly recommended; the preflight warns if absent.
