### T-0528 · Environment management: dev, lab, pilot and production configuration, drift detection and promotion
`P30` `[OPS]` · deps: T-0522, T-0215 · size: M · owner: ops
**Objective.** Keep environments separate, reproducible and verifiably consistent.
**Steps.**
1. Define the environment matrix (`docs/ENVIRONMENTS.md`): `dev` (developer laptop, Docker compose, no public ingress), `lab` (closed lab: Vuln-Lab, oracles, floods), `pilot` (real VPS with pilot subzone delegation), `production` (apex delegated); each with allowed activities (matrix of acceptance tiers, payload classes, load profiles), data policy, secrets sources, and promotion rules.
2. Implement **config layering:** base defaults < environment overlay < host overlay < secrets references; `hddctl config render|validate|diff|apply` with schema validation and secrets-by-reference; configuration is stored in git-ignored profile files plus a `deploy/envs/<env>.example.yaml` template; every applied config produces a `config_revisions` entry with hash.
3. Implement **drift detection:** `hddctl config drift` compares the deployed state (units, binaries hashes, sysctl, firewall, config values, DB role privileges, installed packages) with the expected state computed from the release and config; a systemd timer runs it daily and raises attention items on drift; exceptions are explicit and expiring.
4. Implement **promotion workflow:** pilot → production requires: acceptance `release` tier green for the commit, signed artifacts, approvals recorded (operator confirmation in chat for production-affecting steps), backups fresh, change record; `hddctl promote` writes the record and refuses without prerequisites.
5. Implement **secret segregation:** different secrets per environment (checked by fingerprint comparison across environments: identical fingerprints fail), dev/test secrets rejected in pilot/production (weak or default detection), and `lifecycle_stage` consistency checks in preflight.
6. Implement **data safety:** production data never copied to lab/dev; restore drills use production backups only inside the drill environment on the production host or approved clean room; test data generators produce synthetic data only.
7. Implement **time-travel safety for testing**: the clock-injection facilities used in tests are compiled out of release builds (feature check in `xtask release`).
8. Write tests: layering precedence, validation matrix, drift detection on seeded changes, secret fingerprint collision detection, promotion refusals, release feature checks.
**Deliverables.**
- environment docs, `hddctl config`/`promote`, drift timer, tests
**Acceptance.**
- A1: seeded drift (sysctl change, modified unit, extra open port) is detected and reported.
- A2: identical secrets across environments are detected and refused.
- A3: promotion without green release evidence is refused.
- A4: test-only features are absent from release binaries (symbol and feature checks).
- A5: config apply is atomic and produces a revision with hash.
**Tests.**
- Unit, VM integration, release checks.
**Notes.** The `owner_only` and `saas` deployment modes are configuration choices within this framework.
