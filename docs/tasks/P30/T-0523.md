### T-0523 · Backup, encryption and restore-drill automation (AC-54, part 1)
`P30` `[OPS][SEC]` · deps: T-0522, T-0435 · size: L · owner: ops
**Objective.** Make backups routine, encrypted and proven restorable.
**Steps.**
1. Define the **backup set:** Postgres (base backups + WAL archiving via `pgBackRest` or `wal-g`, or `pg_dump` custom format run as `hdd_backup` for small installs (`BYPASSRLS` is required because `FORCE ROW LEVEL SECURITY` would otherwise dump zero tenant rows; restore tests compare tenant row counts, not only the schema); choose in an ADR with RPO targets: 15 minutes with WAL, 24 h with dumps), the encrypted certificate and key store, `/etc/hdd` configuration (secrets separately escrowed), DNS snapshot (reconstructible from Postgres), audit anchors, deletion ledger, and Redis (not authoritative: optional RDB snapshot for ban continuity; documented that bans also live in Postgres).
2. Implement `hddctl backup run|list|verify|prune`: encryption with `age` (recipient public keys stored on the host; private key escrowed offline by the operator, never on the VPS), compression (zstd), integrity manifests (SHA-256), destinations (local directory, SFTP, S3-compatible with object-lock option), retention (daily 14, weekly 8, monthly 12 by default), and bandwidth throttling; backups run from a systemd timer with random delay; failures alert via notification routing.
3. Implement **secrets escrow guidance:** master key/pepper/PKI backups are stored separately from data backups (operator-held), with a printed recovery sheet template; losing the master key means encrypted data (certificates, integration secrets) is unrecoverable — stated plainly in the docs and the UI before first use.
4. Implement `hddctl restore-drill` (and the S-124 UI action): provisions an isolated scratch environment (compose profile `drill` or a throwaway VM/namespace), restores the latest backup, runs integrity checks (row counts per table vs manifest, audit chain verification, certificate decryption test with the escrowed key, deletion ledger replay, DNS answers for sample zones from the restored snapshot, migrations state), measures RTO and RPO, and writes a signed drill report; failure raises attention items; drills are scheduled monthly.
5. Implement `hddctl restore` for real recovery (maintenance mode required, typed confirmation, pre-restore safety backup of the current state, ledger replay, post-restore verification); restore to a new host is supported (T-0529).
6. Protect backups: backup destination credentials stored encrypted; backup files never contain plaintext secrets (scan); access logging; periodic verification of random backup objects (decrypt + checksum) without full restore.
7. Document **backup security** (what an attacker with a backup can/cannot do), immutable/offsite recommendations, and a restore checklist.
8. Write tests: backup/restore roundtrip with real Postgres, WAL point-in-time recovery to a timestamp, encryption verification (wrong key fails), tamper detection, retention pruning, ledger replay, plaintext-secret scan, and drill automation in CI with a small dataset.
**Deliverables.**
- `hddctl backup|restore|restore-drill`, systemd timers, drill reports, docs
**Acceptance.**
- A1: a restore drill completes with all integrity checks passing and measured RTO/RPO recorded.
- A2: point-in-time recovery restores to the requested timestamp (within WAL granularity).
- A3: backups contain no plaintext secrets (scanner) and fail decryption with the wrong key.
- A4: tampered backups are detected on verify.
- A5: failed backups raise alerts within one schedule interval.
**Tests.**
- Integration with Postgres, PITR tests, drill in CI.
**Notes.** AC-54 completes in T-0529 with the full DR drill and T-0524 upgrade tests.
