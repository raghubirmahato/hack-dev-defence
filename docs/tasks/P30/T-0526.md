### T-0526 · Key management and rotation: `hddctl rotate-keys` without downtime
`P30` `[SEC][OPS]` · deps: T-0195, T-0384, T-0394, T-0522 · size: L · owner: sec
**Objective.** Make every secret rotatable on a schedule and on compromise, with tested procedures.
**Steps.**
1. Inventory all **keys and secrets** with type, storage, rotation period, blast radius and rotation method (`docs/KEYS.md`): master key (envelope encryption), password pepper, session signing/HMAC keys, CSRF keys, email-hash HMAC key, IP-key HMAC for analytics, API key hashing keys, internal ban-stream HMAC key, TSIG keys, DNS cookie secret, internal PKI (CA + service certificates), webhook secrets (per endpoint), SMTP credentials, provider API keys, release signing keys (offline), backup `age` recipients, database passwords, Redis password, challenge secrets, ACME account key.
2. Implement the **key ring** abstraction (`hdd-common::keys`): versioned keys (`kid`), encrypt with current, decrypt with any non-retired, rewrap jobs, usage counters, and a "retire after all data rewrapped" state; keys loaded from systemd credentials/files; memory zeroization; tests.
3. Implement `hddctl rotate-keys <key-class> [--dry-run]` per class: master key (create new version, background rewrap of all envelope-encrypted rows with progress and verification, then retire old), pepper (versioned by `users.password_pepper_kid`: set `HDD_PEPPER_PREV`/`HDD_PEPPER_PREV_KID`, verify with the stored kid, rehash with the current pepper on the next successful login; after the window an admin can force reset for rows still on the old kid), session keys (dual-key validation window, sessions remain valid), HMAC keys for ban-stream (both accepted for 5 minutes during rotation), cookie secrets, internal PKI service certificates (rolling with overlap), TSIG keys (two active keys per secondary), database/Redis passwords (rolling reconnect), ACME account key rollover (RFC 8555 key change).
4. Implement **compromise procedures:** emergency rotation with session revocation, `hddctl rotate-keys --emergency` which invalidates all sessions, API keys optional, webhook secrets (customers notified), and rebuild of derived secrets; incident checklist and communication templates.
5. Implement **rotation scheduling and reminders:** attention items when a key exceeds its rotation period; audit events for every rotation; S-119 shows key age (not values).
6. Test **zero-downtime**: rotate each class under 500 rps traffic and admin activity, verifying no 5xx increase, no forced logouts (except emergency mode), no failed webhook verifications beyond overlap rules, and data readable after rewrap (sampling verification across all encrypted tables).
7. Test **failure modes:** interrupted rewrap resumes; corrupted new key detected before retiring old; lost old key after rotation completes is non-impacting; lost master key is unrecoverable (documented and tested via a restore attempt).
8. Provide the **break-glass tooling** for lost admin MFA (`hddctl admin mfa-reset`) with audit and operator verification steps, and for lost session keys.
**Deliverables.**
- key ring crate, `hddctl rotate-keys`, `docs/KEYS.md`, tests, runbooks
**Acceptance.**
- A1: every key class in the inventory has a tested rotation procedure.
- A2: rotation under load causes no error-rate increase beyond 0.01% (except documented emergency effects).
- A3: rewrap verification confirms 100% of encrypted rows decrypt with the new key.
- A4: interrupted rotations resume safely.
- A5: rotation events are audited and visible without exposing key material.
**Tests.**
- Integration under load, failure injection, crypto unit tests.
**Notes.** The `hddctl rotate-keys` stubs referenced from P06/P10 are completed here.
