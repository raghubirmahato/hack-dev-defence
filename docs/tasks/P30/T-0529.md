### T-0529 · Disaster-recovery drill: total VPS loss to rebuilt service (AC-54, part 3)
`P30` `[QA][OPS]` · deps: T-0523, T-0522, T-0394 · size: L · owner: ops
**Objective.** Prove the platform can be rebuilt from backups on a new host within the stated objectives, with DNS surviving in the meantime.
**Steps.**
1. Define objectives: RTO ≤ 2 h (operator-adjustable) for restoring the control plane and data plane on a fresh VPS from backups and escrowed keys; RPO ≤ 15 minutes with WAL archiving (24 h with dumps); DNS availability during the outage via the external secondary (when configured) — otherwise stated as unavailable.
2. Execute the drill in the lab and, with approval, on the pilot: provision a clean host (second VPS or VM), run `hddctl deploy --role restore`, restore from the latest encrypted backup using the escrowed key material, replay the deletion ledger, re-establish certificates (hot reload from the restored store; ACME renewal verified), restore config and secrets, bring up services, switch the pilot subzone's NS/A records (human step) or test via `--resolve`, and run the `smoke` and `nondestructive` tiers.
3. Measure each phase's duration (provision, deploy, restore, verify, cutover) and the data loss window; compare with RTO/RPO; record bottlenecks and optimization tasks.
4. Verify **DNS survivability**: with HDD stopped, the secondary continues to answer (when configured), then HDD returns with serials ahead of the secondary and IXFR resumes; document the sequence for NOTIFY/TSIG after restore (TSIG key continuity, serial policy to avoid serial regression: serial must never move backwards; the restore procedure bumps the serial beyond the last published).
5. Verify **ban state continuity**: bans restored from Postgres, re-enforced in L7 and kernel; global jail intact; never-ban entries intact.
6. Verify **customer-facing communication**: status page switch to incident mode (hosted externally), banner/email templates, post-incident report generator populated from the audit and timeline.
7. Document **gaps and decisions**: what cannot be restored (Redis ephemeral state, in-flight events), what changes (IP address of the new edge: customers' A records and origin allowlists must be updated — the egress IP publication/overlap policy), and how to minimize (reserved/floating IPs if the provider supports them).
8. Produce the DR drill report with measured RTO/RPO, issues found and fixes; schedule the recurring drill (annual full, monthly partial restore drills already automated in T-0523).
**Deliverables.**
- DR drill report, updated runbooks, optimization tasks
**Acceptance.**
- A1: the rebuilt environment passes `smoke` and `nondestructive` acceptance tiers.
- A2: measured RTO and RPO are within objectives or documented deviations with plans exist.
- A3: DNS serial never regresses and secondary resumes transfers.
- A4: bans and deletion ledger are intact after restore.
- A5: AC-54 evidence (backup, restore, upgrade, rollback) is complete and recorded.
**Tests.**
- The drill itself (lab, plus pilot with approval).
**Notes.** IP address changes on rebuild are the main customer-visible impact; the report quantifies the effect.
