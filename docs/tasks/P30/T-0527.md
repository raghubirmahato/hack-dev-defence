### T-0527 · Operations runbooks, incident response and change management
`P30` `[DOC][OPS]` · deps: T-0525, T-0526 · size: M · owner: docs
**Objective.** Give the operator a complete, tested playbook for running HDD day to day and in emergencies.
**Steps.**
1. Write `OPERATIONS.md` as the index: daily/weekly/monthly checklists (review attention items, backups, drills, certificate budgets, advisory SLAs, key ages, access reviews), on-call model suggestions, contact lists, escalation paths, and maintenance windows.
2. Write **incident response playbooks:** (a) application attack on a customer site, (b) volumetric attack/shield escalation, (c) HDD outage (proxy/DNS/DB), (d) suspected platform breach (containment, key rotation, forensics collection with hashes, customer notification obligations template, regulator timelines noted as operator's legal responsibility), (e) certificate emergency (mis-issuance, CT anomaly), (f) DNS hijack/registrar compromise, (g) data leak report from a tenant, (h) abuse report handling, (i) ban poisoning/false-positive wave (mass unban procedure with audit), (j) supply-chain advisory affecting HDD dependencies.
3. Provide **change management:** change types (standard, normal, emergency), required evidence (acceptance tier results, backup recency), approval fields, announcement templates (status page, banners, email), rollback criteria, and post-change review template; integrate with the audit log (change tickets as references).
4. Provide **capacity and cost planning**: monitoring signals that indicate when to scale, how to resize the VPS, when to deploy a standby edge, and how to add a secondary DNS provider.
5. Create **tabletop exercise scripts** (3 scenarios) with injects, expected decisions and scoring sheets; the operator runs at least one exercise before cutover (recorded in the final report).
6. Write **customer-facing operational docs:** status page usage, incident communication policy, maintenance policy, data retention and deletion timelines, support contact flows, SLAs (none promised unless the operator defines them; template with placeholders marked "operator must define").
7. Add **knowledge base structure** (`docs/site/`) with troubleshooting trees: "my site shows a block page", "my domain is stuck pending", "certificate not issued", "DNS not resolving", "origin 502", "I locked myself out", each validated against real product behavior by the docs tests.
8. Verify runbook accuracy by **executing** a sample of runbook steps in the lab (checklist with outcomes) and fix discrepancies.
**Deliverables.**
- `OPERATIONS.md`, runbooks, tabletop scripts, customer ops docs, execution log
**Acceptance.**
- A1: every playbook step has a command or UI path that exists (docs test resolves them against `hddctl --help` output and route registry).
- A2: at least 10 runbook procedures are executed in the lab with recorded outcomes.
- A3: the tabletop scripts have clear injects and expected decisions.
- A4: customer-facing docs contain no unqualified guarantees (claims-lint).
- A5: contact/escalation fields are placeholders marked for the operator.
**Tests.**
- Docs tests, runbook execution log, claims-lint.
**Notes.** Legal obligations (breach notification) are described as questions for the operator's counsel, not advice.
