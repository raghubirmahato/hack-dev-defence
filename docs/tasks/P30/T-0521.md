### T-0521 · Deployment path ADR and the production artifact set (systemd units, container images, installer)
`P30` `[OPS][DOC]` · deps: T-0212, T-0518 · size: L · owner: ops
**Objective.** Decide the default production topology and produce the artifacts that realize it.
**Steps.**
1. Write the **deployment path ADR**: systemd with signed release binaries (default; best for `network_mode: host`, XDP/nftables privileges and port 53) versus container compose for the control plane (acceptable for web/api/worker/mailer) versus full compose; decision matrix covering security, privilege model, upgrade/rollback, observability, resource isolation, operator skill; final recommendation: **hybrid** — data plane and host agents (proxy, DNS, fw-agent, XDP, shield) as systemd services with hardened units; control plane services as systemd services too by default, with a compose profile for operators who prefer containers; Postgres and Redis from distro packages bound to loopback/Unix sockets.
2. Produce final **systemd units** for all services with sandboxing (`DynamicUser` where state is not needed, otherwise dedicated users), dependency ordering (`After`/`Requires`/`PartOf`), restart policies with backoff and rate limits, `LimitNOFILE`, `MemoryMax`, `CPUWeight`, watchdog integration (`sd_notify` `WATCHDOG=1`, `Type=notify`), credentials via `LoadCredential`, and `systemd-analyze security` targets; units are generated from templates by `xtask units` and golden-tested.
3. Produce **container images** (multi-stage `cargo-chef`, non-root, read-only root filesystem, digest-pinned bases, minimal runtime such as distroless or scratch with CA bundle, no shell), health checks, and SBOM/provenance per image; compose files: `docker-compose.yml` (dev), `docker-compose.lab.yml` (lab, includes Vuln-Lab profile guarded), `docker-compose.prod.yml` (control-plane profile only, no host-network data plane), with secrets via files not env, `internal` networks, and no published DB/Redis ports.
4. Produce `deploy/install.sh` (thin, auditable, checksum-verifying bootstrapper that downloads `hddctl` and verifies its signature, then hands over to `hddctl deploy`), with `--dry-run` and no piped-to-shell patterns in documentation (instead: download, verify, inspect, run).
5. Define the **filesystem layout** and ownership (`/etc/hdd`, `/var/lib/hdd`, `/var/log/hdd` (or journald), `/run/hdd`, `/opt/hdd/releases`), tmpfiles.d rules, logrotate, and journald limits.
6. Define the **network layout** and port map (authoritative in Appendix E7) with bind addresses per service; verify with a script that listens on only intended ports.
7. Document **resource sizing** profiles (S/M/L VPS) tied to the capacity model (T-0512) and cgroup limits per service.
8. Write tests: unit-file golden tests, `systemd-analyze verify` in CI, image build reproducibility and non-root checks (`docker run --user` tests), compose config validation (`docker compose config` with policies: no `privileged`, no `latest` tags, no published DB ports) via a policy test.
**Deliverables.**
- ADR, `xtask units`, systemd templates, Dockerfiles/compose, installer, layout docs
**Acceptance.**
- A1: all units pass `systemd-analyze verify` and meet the security score targets.
- A2: compose policy test rejects seeded violations (privileged, latest, published DB port).
- A3: images run as non-root with read-only roots (test).
- A4: the installer verifies signatures before executing anything and supports `--dry-run`.
- A5: the port map in docs matches an actual listening-port scan of a test install.
**Tests.**
- Golden, policy, VM install test.
**Notes.** The ADR slot referenced in P00 (deployment path) is settled here; T-0212's earlier ADR is superseded by this final decision.
