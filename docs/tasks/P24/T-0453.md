### T-0453 · Alert rules (S-076) and notification routing core
`P24` `[API][DB][UI]` · deps: T-0141, T-0368, T-0441 · size: XL · owner: api
**Objective.** Turn platform events into the right notifications with controlled volume.
**Steps.**
1. Define the **trigger catalog** (each with a stable key, default severity, parameters and the event source): `sqli_hard_hit_auth_endpoint`, `possible_auth_bypass` (V13), `data_leak_detected`, `exposure_detected`, `mass_ban` / `ban_spike`, `campaign_detected`, `never_ban_attack_attempt`, `global_jail_promoted`, `rate_limit_spike`, `challenge_failure_spike`, `origin_down` / `origin_degraded`, `certificate_expiring`, `certificate_issue_failed`, `dns_secondary_lag`, `domain_verification_failed`, `readiness_score_drop`, `rule_pack_rollback`, `safe_mode_enabled`, `appeal_received`, `member_added`/`role_changed`, `api_key_created`, `login_anomaly`, `shield_state_change`, `vuln_sla_overdue`, `virtual_patch_expiring`, `report_failed`, `backup_stale` (platform).
2. Implement the **rule model**: scope (org/domain/all domains), trigger, parameters (threshold, window, minimum severity, category filter), channels (list), schedule (always, business hours, custom), quiet hours with critical override, grouping key, cooldown, and escalation policy (if not acknowledged in X minutes, notify an escalation channel). System-default rules are seeded per org on creation (conservative set, editable, deletable with warnings) so a new org has alerts without configuration.
3. Implement the **routing pipeline** in `hdd-notify`: consumes domain events from the outbox, evaluates rules (windowed counting using Redis with a database fallback), creates durable notifications (S-075) and enqueues channel deliveries; delivery records are idempotent per (rule, event group, channel).
4. Implement **flood control**: per-rule cooldown, per-channel rate caps (default 10/h for chat channels, 60/h for email), grouping ("12 SQLi attempts from 3 IPs in 5 minutes" as one notification with a count that updates until the group closes), digest mode when caps are hit with a final "N more events suppressed" message, and a global per-org cap with an alert to the owner by email that suppression occurred.
5. Implement acknowledgment and snooze: acknowledge via UI/API/button links in messages (signed single-use links with expiry), snooze a rule or trigger for N hours with a reason, escalate on no acknowledgment, and mark resolved when the source condition clears (for state-based triggers).
6. Build S-076: rule list with search and status, rule editor with plain-language preview ("When 5 or more hard SQL injection attempts hit your login endpoints within 10 minutes, email Alex and post to #security"), threshold sanity hints, a **test event** button that generates a synthetic notification clearly labeled "Test", and a channel health indicator (last success/failure).
7. Respect user preferences (S-087): per-user notification channels and per-severity opt-outs, with enforced minimums for security-critical account notifications.
8. Implement the API (`/alert-rules`, `/notifications`, `POST /notifications/{id}:ack`), permissions (`PERM-alertrule.write`, `PERM-notify.read`), audit events, and metrics (notifications created, suppressed, delivered, failed by channel).
9. Write tests: trigger evaluation with time-injected windows, grouping and cooldown properties, flood simulation (10,000 events → bounded notifications), quiet hours and critical override, escalation flows, idempotency under retries and crashes, RLS/BOLA, and UI e2e for the editor.
**Deliverables.**
- trigger catalog, rule engine, routing, S-076, API, tests, docs `docs/ALERTS.md`
**Acceptance.**
- A1: a simulated SQLi campaign of 10,000 events produces a bounded number of notifications per channel (caps respected) with the suppression summary.
- A2: seeded default rules exist for a new org and can be edited or removed.
- A3: escalation triggers exactly once when unacknowledged and stops upon acknowledgment.
- A4: notification creation is idempotent across worker restarts (crash test).
- A5: the editor preview text matches the evaluated behavior (golden tests).
**Tests.**
- Unit, property, integration with Redis/Postgres, browser e2e.
**Notes.** Message content rules are enforced here (no sensitive data) and re-verified by T-0454.

## Definition of done for this task's tags (section 0.7)

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.

### `[DB]`: Adds or changes schema

Expand/contract migration only; `org_id` and RLS policy for tenant-owned tables; indexes justified; `sqlx` offline data refreshed; forward migration plus restore-from-backup test; data-retention rule documented.

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.
