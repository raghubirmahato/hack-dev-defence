### T-0459 · Developer documentation: API reference, guides, examples and sandbox "Try it"
`P24` `[DOC][UI]` · deps: T-0457, T-0458, T-0099 · size: M · owner: docs
**Objective.** Make the API easy to adopt and keep documentation executable.
**Steps.**
1. Render the API reference page (S-007) from the OpenAPI document: grouped by tag, search, per-endpoint permission requirement, request/response examples generated from schemas and verified by contract tests, error catalog (`ERR-*`) with remedies, rate limit and idempotency docs, pagination docs, versioning and deprecation policy, and a changelog.
2. Write guides: "Authentication and API keys", "Add a domain via API and verify it", "Automate DNS changes safely" (using `If-Match` and bulk endpoints), "Manage bans programmatically", "Receive and verify webhooks", "Stream live events", "Export your data", "Use the Rust SDK", "Infrastructure as code with the API" (Terraform-style patterns documented, provider is Tier 6), "Rate limits and retries".
3. Make every code sample executable: samples are stored as files with a test annotation, run in CI (`xtask docs-test`) against the local stack with fixture keys, and the docs build fails if a sample breaks.
4. Provide Postman and Bruno collections generated from OpenAPI with environment variables for base URL and API key.
5. Implement the in-docs **"Try it" panel** (island): sends requests from the user's browser to the API with a user-provided API key kept in memory only (not stored), limited to GET and dry-run endpoints by default with explicit opt-in for mutations; CORS for this use is handled via an allowlisted docs origin; the panel shows the equivalent `curl` command and redacts the key in displays.
6. Add the quickstart: 5-minute path from signup to a protected domain using the dashboard, followed by the equivalent API path; both are validated in e2e tests (UI path in browser, API path via SDK).
7. Add accessibility and SEO basics for the docs (landmarks, headings, code block labels, skip links, copy buttons with announcements), and i18n-ready structure (English first).
8. Write tests: link checker, sample execution, OpenAPI-to-docs completeness (every endpoint documented), claims-lint, a11y on docs pages, and Try-it key handling (no key in localStorage, no key in URLs, no key in logs).
**Deliverables.**
- docs content, collections, Try-it island, `xtask docs-test`, tests
**Acceptance.**
- A1: all documentation samples execute successfully in CI.
- A2: every endpoint appears in the reference with an example and error list.
- A3: the Try-it panel never persists the API key (storage and network assertions).
- A4: quickstart paths pass the e2e tests.
- A5: docs pages pass axe and keyboard checks.
**Tests.**
- Executable docs tests, e2e, a11y, security checks.
**Notes.** The documentation engine (T-0097) renders; this task supplies content and executable verification.

## Definition of done for this task's tags (section 0.7)

### `[DOC]`: Documentation

Every claim backed by a test ID or a command the reader can run; passes claims-lint; included in the docs site if user-facing.

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.
