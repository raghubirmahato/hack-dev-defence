### T-0168 · Go-live checklist and activation (step 8)
`P08` `[UI][API][SEC]` · deps: T-0161, T-0162, T-0163, T-0166, T-0167 · size: L · owner: api
**Objective.** Let the owner activate with confidence, seeing exactly what is verified and what is not.
**Steps.**
1. Implement the checklist computation from real state: ownership verified, origin test passed within 24 hours, certificate plan ready or acknowledged risk, DS warnings acknowledged, records applied (delegation or CNAME/A checks passing or pending), origin leak warnings acknowledged, preset chosen, rollback instructions viewed.
2. Implement hard blockers (ownership, origin reachable unless overridden by platform admin) and soft blockers (warnings that need acknowledgment).
3. Implement the activation action: transitions state to `active` (or `pending_delegation` if the DNS change has not propagated), publishes the site snapshot revision, enqueues certificate issuance if not yet issued, writes audit events, and shows what happens next.
4. Display the rollback instructions (exact, per mode, with TTL-bound times) before the activation button is enabled.
5. Implement the post-activation poller showing delegation/CNAME status and "first requests" arrival (from rollups/events) with a timeout message and troubleshooting.
6. Implement idempotency and concurrency control.
7. Implement a dry-run mode ("Check readiness without activating").
8. Add tests across modes with fixtures for each checklist item.
**Deliverables.**
- checklist engine, activation service, UI, tests
**Acceptance.**
- A1: activation is impossible with an unverified domain (hard blocker).
- A2: rollback instructions appear before the final button and are mode-specific.
- A3: activation twice is a no-op (idempotent).
- A4: the poller reports first requests only from real events.
- A5: audit events exist for each state change.
**Tests.**
- Integration scenario tests per mode; browser wizard completion; unit: checklist rules.
**Notes.** The `curl --resolve` helpers are in T-0169.

## Definition of done for this task's tags (section 0.7)

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.

### `[SEC]`: Security-relevant logic

Abuse cases written as tests; STRIDE delta in `docs/STRIDE.md`; no secret in logs; constant-time comparison where secrets are compared; failure modes fail closed; panic-free on hostile input (proptest or fuzz target).
