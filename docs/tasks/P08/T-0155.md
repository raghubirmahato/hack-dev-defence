### T-0155 · Add-domain wizard step 1: enter domains (S-042)
`P08` `[UI][API]` · deps: T-0154, T-0043, T-0058 · size: M · owner: ui
**Objective.** Implement the first wizard step and the draft lifecycle.
**Steps.**
1. Implement the wizard shell (URL per step, resume, progress, leave-guard, back/next) with server-side state in the draft `sites` row and a `wizard_state` JSON column validated per step.
2. Implement step 1: textarea or single input with normalization hints, live validation via HTMX (debounced), display of punycode, bulk add, per-line errors, and quota display.
3. On submit, create draft sites (one per apex group) and redirect to step 2 for the first; others appear in a queue list.
4. Implement the draft resume list on S-041 with continue/discard actions.
5. Implement discard (deletes draft and cascades) with confirmation when data was entered.
6. Implement the dispute entry point (link to `ERR-DOM-002` flow T-0174).
7. Add tests for idempotency (double submit), draft cleanup, quota errors.
8. Add accessibility and responsive checks.
**Deliverables.**
- wizard shell, step 1, templates, tests
**Acceptance.**
- A1: refreshing or navigating away and back resumes the wizard at the same step with values intact.
- A2: double submission creates one draft (idempotency).
- A3: validation errors map to `ERR-DOM-*` codes with human copy.
- A4: discard removes all child records.
- A5: step 1 works without JavaScript.
**Tests.**
- Browser flows; integration: idempotency; unit: wizard state validation.
**Notes.** The wizard is a series of independent routes so steps remain individually testable.

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.
