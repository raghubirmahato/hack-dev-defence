### T-0159 · Integration mode selector and requirement computation (step 3)
`P08` `[UI][API]` · deps: T-0158, T-0058 · size: M · owner: api
**Objective.** Help owners choose the right way to connect and compute the exact required changes.
**Steps.**
1. Implement the recommendation logic (decision list): apex requested and provider unknown or unsupported ALIAS → `full_ns`; provider supports CNAME flattening/ALIAS → `cname_partial` or `a_record_partial`; only a subdomain needed → `subdomain_only`; operator-level hidden primary configured → `hidden_primary` offered to platform admins only.
2. Implement requirement computation for each mode: required records (names, types, values, TTLs) including the verification TXT and optional `_acme-challenge` CNAME, values referencing the site's edge name `<site-id>.edge.{{PLATFORM_DOMAIN}}` or HDD IPs, with warnings about IP changes.
3. Implement the selector UI (RadioCards) with consequences per mode (what changes, what stays, rollback time, prerequisites) from B12.2.
4. Implement mode switching rules (allowed in draft and pending states; switching after activation requires re-verification and shows impact).
5. Validate prerequisites (for `full_ns` the DS warning; for `a_record_partial` the apex limitation text; for `cname_partial` the CNAME-at-apex warning).
6. Persist the choice and the computed requirement set in the draft.
7. Add tests across scan fixtures.
8. Document modes in the docs site.
**Deliverables.**
- decision module, requirement generator, UI, docs
**Acceptance.**
- A1: recommendations match the decision list for 20 scenario fixtures.
- A2: required records are exact and copy-safe (no trailing dot errors, TXT quoting handled).
- A3: a CNAME at the apex is never suggested.
- A4: switching modes after activation requires re-verification.
- A5: the selector is keyboard accessible with descriptive labels.
**Tests.**
- Unit: scenario table tests; browser: selector flows.
**Notes.** Requirement text is also exposed through the API for automation.

## Definition of done for this task's tags (section 0.7)

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.
