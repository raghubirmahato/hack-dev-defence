### T-0166 · TLS planning step: pre-issuance paths and CAA checks
`P08` `[UI][API]` · deps: T-0162, T-0161 · size: M · owner: api
**Objective.** Ensure certificates can be issued before traffic cuts over wherever possible.
**Steps.**
1. Determine the available issuance paths per mode: `full_ns` (DNS-01 on HDD's own DNS before cutover), `cname_partial` / `a_record_partial` (DNS-01 via `_acme-challenge` CNAME delegation to `<zone-id>.acme.{{PLATFORM_DOMAIN}}`, otherwise HTTP-01 after cutover), `hidden_primary` (DNS-01 via secondary after TXT is served).
2. Check CAA records of the domain and parents (via resolvers) and compute whether the configured ACME CA is permitted; propose exact CAA additions when needed.
3. Present the choice with consequences (pre-issued: no TLS gap; on-first-request: brief errors during switch), persist the choice, and schedule issuance jobs (T-0198).
4. Show certificate readiness states (not requested, pending DNS, issued, failed with reason).
5. Pre-check CA rate limits via the budget service (T-0198) to avoid failing issuance on duplicates.
6. For custom certificate mode, offer the upload step.
7. Provide the wildcard option (DNS-01 only) with warnings.
8. Test with the ACME staging directory (live egress) or a local ACME server (Pebble-class) in CI.
**Deliverables.**
- planner, UI, tests
**Acceptance.**
- A1: the planner selects the correct path for every mode (table tests).
- A2: CAA conflicts produce exact fix instructions.
- A3: pre-issued certificates are visible before activation.
- A4: rate-limit budget exhaustion is surfaced before submission.
- A5: choices are persisted and editable.
**Tests.**
- Unit: planner; integration: local ACME test server (real protocol implementation, listed in the test dependencies); live: staging issuance in P11.
**Notes.** Certificates for the operator's pilot use the staging CA first (R-04, section 4).
