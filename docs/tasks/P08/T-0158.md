### T-0158 · Record classification, proxy defaults and origin-leak hints
`P08` `[API][SEC]` · deps: T-0157 · size: M · owner: dns
**Objective.** Decide sensible defaults for what to proxy and warn about exposures.
**Steps.**
1. Implement classification rules: proxiable (A/AAAA/CNAME for web hostnames), never proxied (MX, TXT, NS, CAA, SRV), forced grey for `non_http_services` hostnames and common mail/FTP/SSH names (`mail`, `smtp`, `imap`, `pop`, `ftp`, `ssh`, `vpn`, `autodiscover` when pointing at mail hosts), wildcard handling options.
2. Compute proxy defaults: apex and `www` orange when pointing at a web origin; names whose address equals an MX target's address are grey with an explanation.
3. Implement origin-leak detection: any grey record (A/AAAA) pointing at the same IP as the origin, MX targets resolving to the origin IP, SPF `ip4:`/`ip6:` entries containing the origin IP, TXT records mentioning the IP, subdomains resolving to the origin (e.g., `direct`, `cpanel`, `ftp`), and historical-exposure hints supplied by the user.
4. Generate warnings with severity and remediation text (move mail to another IP, use a different origin IP, enable lockdown).
5. Implement the "risk summary" for the review step and for readiness.
6. Implement user overrides with confirmation for risky choices (proxying a mail host is refused).
7. Implement unit tests across scenarios.
8. Document the rules.
**Deliverables.**
- classifier module, warnings model, tests, docs
**Acceptance.**
- A1: mail-related records are never proxied.
- A2: a grey A record sharing the origin IP triggers a leak warning.
- A3: SPF with the origin IP triggers a warning and suggested remediation.
- A4: overrides that would break mail are refused with `ERR-DNS-004`.
- A5: classification is deterministic and documented.
**Tests.**
- Table-driven scenarios (40); proptest on classification stability.
**Notes.** The detection helps with ATK-244.
