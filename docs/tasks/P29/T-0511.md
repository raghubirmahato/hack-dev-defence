### T-0511 · Performance measurement suite and budgets (AC-24)
`P29` `[QA][DP]` · deps: T-0372, T-0400, T-0470 · size: L · owner: perf
**Objective.** Measure latency, throughput and resource use of the real data plane with a repeatable method, so every performance statement cites AC-24.
**Steps.**
1. Define the **methodology** in `docs/PERFORMANCE.md`: hardware description captured automatically (CPU model, cores, RAM, kernel, NIC, virtualization), warm-up rules, steady-state windows (≥ 120 s), open-loop load generation (constant arrival rate to avoid coordinated omission), HDR histograms for latency, multiple runs with variance reporting (≥ 5 runs, median and range), and a statement that numbers are valid only for the recorded environment.
2. Extend `hdd-loadgen http` with scenarios: static GET pass-through, mixed GET/POST bodies (1 KB/64 KB/1 MB), HTTP/1.1 keep-alive and h2 multiplexing (100 concurrent streams), TLS handshakes per second (full and resumed), WebSocket idle connections (10k), blocked traffic (WAF verdict block, ban hits through the L7 jail), challenge issuance, large response streaming, and outbound-filter-on text responses; each against a local origin stub that is a real HTTP server with deterministic behavior (lab and builder only; on the pilot the canary files are the origin).
3. Measure and record **proxy-added latency** (time inside HDD excluding origin) at p50/p95/p99/p99.9 using server-side histograms, plus end-to-end client latency; budget: p99 ≤ 5 ms added at the functional load (2,000 rps) and p99 ≤ 15 ms at 80% of the measured saturation point; inspection p50 < 1 ms.
4. Measure **throughput and saturation**: max sustainable rps per core for pass-through and for full-inspection `block` mode, CPU utilization per mode, memory (RSS) per 10,000 idle connections (documented), allocation per request in steady state (counting allocator: zero heap growth), p99 degradation curves, behavior at overload (shed policy, 503 rate, recovery time).
5. Measure **per-feature cost**: marginal latency of each pipeline stage (histograms from T-0372), SQLi tokenizer on worst-case inputs, body inspection costs by size (1 KB to 8 MiB), outbound scan cost, challenge verification cost, ban lookup cost with 100k entries, and the cost of snapshot swaps on live traffic (latency spike ≤ 5 ms).
6. Run on three environments and report them separately: builder (developer-grade), lab machine (if supplied), and the pilot VPS (in an announced window with the `load` profile and operator approval; UNVERIFIED(`skipped_by_operator`) otherwise).
7. Add a **regression gate**: baselines stored in `tests/baselines/perf-<env>.json`; `xtask bench http --compare` fails when p99 added latency or throughput regresses by more than 10% without an approved baseline update (reviewed in the PR, recorded in `docs/DEVIATIONS.md` if a budget changes).
8. Publish the results: tables, charts (SVG with table alternatives) in `docs/PERFORMANCE.md` and the S-127 capacity panel's "lab-proven" figures; ensure marketing and docs cite only these numbers (claims-lint pattern `perf_claim`).
**Deliverables.**
- loadgen scenarios, methodology doc, baselines, regression gate, results
**Acceptance.**
- A1: budgets are met in the builder and lab environments, or deviations are documented with tracked tasks.
- A2: no per-request heap growth in steady state (counting allocator test).
- A3: the regression gate fails on a seeded 15% regression in a test branch.
- A4: all published numbers carry environment tags and variance.
- A5: pilot VPS measurement is performed (with approval) or marked UNVERIFIED with reason.
**Tests.**
- The benchmarks themselves; unit tests for histogram math and comparison logic.
**Notes.** Coordinated omission is avoided by open-loop arrival scheduling.

## Definition of done for this task's tags (section 0.7)

### `[QA]`: Test infrastructure

Real services only (no mocks); deterministic or seeded; evidence output stored under git-ignored `acceptance-*/` with sha256.

### `[DP]`: On the data-plane hot path (proxy, DNS, WAF, firewall)

Hot path never awaits the database; bounded memory and queues; criterion benchmark or histogram; fuzz or proptest; behavior when Redis or Postgres is down specified and tested; metric with drop counter.
