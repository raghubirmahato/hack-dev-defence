### T-0518 · Release signing, artifact pipeline and signed self-update with rollback (AC-33, part 2)
`P29` `[SEC][OPS]` · deps: T-0516, T-0435, T-0212 · size: L · owner: ops
**Objective.** Ensure only authentic, intended software ever runs, and that upgrades are reversible.
**Steps.**
1. Implement `xtask release`: build with the locked toolchain, produce per-target tarballs (binaries, migrations, units, docs), SHA-256 checksums, SBOMs, provenance, and `cosign` signatures (keyless via OIDC if a hosted CI exists, otherwise a long-lived release key held offline or in a hardware token with a documented ceremony); fail if `hdd-vulnlab`/`lab/` crates appear in any graph, if claims-lint fails, if expired virtual patches exist, if `xtask verify` is red, or if the acceptance report for the commit is missing.
2. Define **key management** for release signing: key generation ceremony, storage (offline/HSM/YubiKey), public key distribution (embedded in `hddctl` and published in `SECURITY.md` and the status site), rotation procedure, revocation list handling, and compromise response; the verification code lives in `hdd-common::release` and is unit-tested with fixtures.
3. Implement **`hddctl upgrade`**: fetches a release manifest from the pinned release host (or reads an operator-provided bundle), verifies signature, checksums, SBOM presence and version monotonicity (no downgrade unless `--allow-downgrade` with confirmation), stages binaries beside the current ones (`/opt/hdd/releases/<ver>`), runs pre-flight (disk, backups recent, health), executes migrations with the expand/contract rules, switches the `current` symlink atomically, restarts services in the documented order, runs health and smoke checks (`smoke` acceptance tier), and **automatically rolls back** on any failed check (binaries and, if reversible, migrations); upgrades never run unattended unless `auto_update` is explicitly enabled.
4. Implement **rollback**: `hddctl upgrade --rollback` restores the previous release and config; the rollback path is exercised in CI on a VM for every release candidate (failure injected at each step: signature, checksum, migration, health, smoke).
5. Implement **tamper tests**: modified binary, modified manifest, replayed old manifest, wrong signer, truncated download, unsigned artifact, mismatched checksums, expired signature (if timestamped): all rejected with specific errors, no partial installation.
6. Implement **update channel policy:** `stable`/`candidate` channels, minimum delay for stable (soak period), and pinned version windows; UI S-123 shows channel and signature verification status.
7. Publish `SECURITY.md` (disclosure policy, PGP/age key for reports, response SLAs), `security.txt` template, and the release signing public keys with fingerprints.
8. Verify end to end on the pilot: upgrade from release N to N+1 with injected failure (rollback verified) and a clean upgrade; record in AC-33 evidence.
**Deliverables.**
- `xtask release`, `hddctl upgrade`, key ceremony doc, tamper test suite, SECURITY.md/security.txt
**Acceptance.**
- A1: all tamper cases are rejected and leave the system on the old version.
- A2: injected failures at each upgrade step roll back to a healthy state.
- A3: `xtask release` refuses to produce artifacts when any release gate is red.
- A4: downgrades require explicit confirmation and are audited.
- A5: AC-33 evidence (supply-chain checks green plus a signed-update rollback exercise) is recorded.
**Tests.**
- VM-based upgrade/rollback tests, tamper suite, release gate tests.
**Notes.** Signed self-update is required for cutover gate item 5 (C17.2).
