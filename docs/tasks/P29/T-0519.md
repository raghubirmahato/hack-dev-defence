### T-0519 · HDD self-security review program: STRIDE delta, lab pentest with oracles and disclosure readiness
`P29` `[SEC][QA]` · deps: T-0503, T-0501, T-0514 · size: L · owner: sec
**Objective.** Attack HDD itself in the lab with the same rigor it applies to customers' sites, and close the findings.
**Steps.**
1. Update `docs/STRIDE.md` with the delta for features added since P00 (multi-tenant control plane, webhooks, exports, scanner, DNS transfers, shield, XDP loader, report renderer, SDK), listing threats, mitigations, tests and residual risks with owners.
2. Stand up the **HDD-on-HDD lab target**: a full HDD deployment in the lab (control plane, admin and app surfaces, API, proxy, DNS) and run oracles against its own web surfaces (ZAP baseline and active scan in lab mode, nuclei templates, nikto, wapiti, ffuf for content discovery, testssl.sh, h2spec, `sqlmap` against forms, JWT/session tools): triage every finding as true/false positive with evidence; HDD's own WAF protecting HDD's surfaces is part of the test (and so is a run with the shield in monitor mode to see what it would block and what the application itself resists).
3. Run **authenticated testing**: with accounts in each role, test authorization (BOLA/BFLA), business-logic abuse (quota bypass, plan escalation, domain claim races, DNS record limit bypass, impersonation boundaries), file upload endpoints (logo upload, SBOM import), SSRF-capable features (origin config, webhooks, feeds, log sinks, flattening), template injection in email/report editors, CSV/formula injection in exports, XXE in SBOM/SPDX imports, ReDoS in rule expression evaluators and regexes (using `regex` crate guarantees plus custom DSL review), and race conditions (TOCTOU in verification, ban/unban races).
4. Perform **assume-breach exercises** in the lab: a compromised proxy process (what can it reach? DB role limits), a compromised worker, a compromised tenant API key, a compromised platform-support account, a compromised Redis (forged ban messages rejected by HMAC), a compromised secondary DNS (TSIG scope), and document blast radius and detection.
5. Run **secrets and crypto review**: key hierarchy, nonce handling in envelope encryption (AES-GCM nonces or XChaCha20-Poly1305), Argon2 parameters vs hardware, constant-time comparisons, JWT/session token design (opaque tokens only), random number sources, TLS configuration of internal links, cookie attributes, CSRF token binding, zeroization checks.
6. Establish **vulnerability disclosure readiness:** `SECURITY.md`, `security.txt` with expiry, intake mailbox via `hdd-mailer` with encryption key instructions, triage workflow (acknowledge in 3 business days), CVE request process notes, coordinated disclosure timeline, and a "hall of thanks" optional page; test that the intake form (S-014) is abuse-resistant.
7. Track all findings in `docs/diagnoses/` with severity (CVSS), exploitability, fix commits, regression tests and verification evidence; high/critical must be fixed or have documented risk acceptance signed by the operator before M12.
8. Re-run the relevant acceptance checks after fixes, and archive the review report `docs/SECURITY-REVIEW-v1.md` with scope, method, results and limitations (explicitly not a certification).
**Deliverables.**
- STRIDE update, lab pentest report, assume-breach report, disclosure readiness artifacts, fixes
**Acceptance.**
- A1: no open critical/high finding at the gate (fixed or operator-signed risk acceptance).
- A2: every oracle finding is triaged with evidence.
- A3: assume-breach blast-radius statements are verified by tests.
- A4: disclosure intake works end to end and is abuse-resistant.
- A5: the review report states scope and limits and makes no certification claim.
**Tests.**
- Oracle runs, authenticated test scripts, race tests.
**Notes.** Oracles run only against the lab deployment of HDD, never against live profile hosts.
