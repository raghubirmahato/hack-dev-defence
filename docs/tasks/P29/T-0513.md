### T-0513 · Automated chaos suite (network faults, resource faults, time faults)
`P29` `[QA][LAB][OPS]` · deps: T-0498, T-0470, T-0511 · size: L · owner: qa
**Objective.** Systematically inject faults beyond the scripted AC-15 scenarios and prove invariants hold.
**Steps.**
1. Build `hdd-chaos` (lab-only tool under `lab/`) driven by `xtask chaos run <experiment>`: experiments as YAML (fault, target, duration, steady-state hypothesis, abort conditions); faults implemented with `tc netem` (delay, jitter, loss, duplication, reordering, corruption, bandwidth caps), `iptables/nft` partitions (Redis/Postgres/origin/DNS secondary), cgroup limits (CPU throttling, memory limits with OOM), disk faults via `dm-flakey`/`fallocate` filling, `libfaketime`-style clock jumps for test processes, process signals (SIGKILL/STOP/CONT), and file descriptor exhaustion.
2. Define **steady-state hypotheses** checked continuously: legitimate request success ≥ threshold, the mandated SQLi payload always blocked in `block` mode (no fail-open), ban enforcement active, DNS answers correct, no data corruption (ban/rules/audit chain verified after each experiment), alerts raised as documented.
3. Implement the **experiment catalog** (≥ 40): Redis latency 200 ms/loss 20%, Redis partition, Postgres partition with queued events, Postgres slow queries (lock contention), origin latency spikes and resets, DNS secondary unreachable, packet loss on client side, ACME CA unreachable during renewal, SMTP down during signup spikes, webhook endpoint black hole, clock skew ±10 min and clock jump back 1 h (token expiry, sessions, audit chain monotonicity, ACME), disk full for events/logs/backups, memory pressure on proxy (OOM kill and restart), CPU starvation of the proxy (inspection budgets and shed), fd exhaustion, config bus message loss/reordering, certificate store corruption, snapshot corruption, kernel module missing, XDP detach, fw-agent crash, shield crash, time zone/DST changes.
4. For each experiment capture the timeline (fault start/stop, detection time, alert time, recovery time), invariants evaluation, and any data loss counters; produce a report with a pass/fail per hypothesis.
5. Implement **safety:** chaos runs only against lab or the pilot in announced windows; blast radius limits; automatic abort when legitimate success drops below an emergency threshold or when the operator kill-switch file appears; never executes against production stage without approval.
6. Integrate the experiments with the CI nightly (subset of 10 quick ones) and the gate (full catalog).
7. Fix issues found at the root cause (examples likely: unbounded retries, missing timeouts, lock ordering) and add regression tests; record in `docs/diagnoses/`.
8. Write tests for the chaos tool's own safety (abort conditions, scope limits, cleanup of injected faults even on crash).
**Deliverables.**
- `hdd-chaos`, experiment catalog, reports, diagnoses
**Acceptance.**
- A1: no experiment results in an inspection fail-open in `block` mode or data corruption.
- A2: all experiments clean up their faults (post-run network/cgroup state verified identical to pre-run).
- A3: detection and alert times are within documented targets for each experiment.
- A4: abort conditions work (seeded test).
- A5: findings are fixed or tracked with severity.
**Tests.**
- Lab runs; unit tests for the tool's safety logic.
**Notes.** The chaos tool never runs on shipped hosts by default (feature `chaos` not built into release artifacts).
