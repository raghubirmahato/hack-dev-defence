### T-0514 · Fuzzing program: target inventory, corpora, nightly campaigns and crash triage
`P29` `[SEC][QA]` · deps: T-0259, T-0397, T-0243 · size: L · owner: sec
**Objective.** Make fuzzing a continuous, managed practice across every parser and protocol surface.
**Steps.**
1. Produce the **target inventory** (`fuzz/TARGETS.md`, generated by `xtask fuzz list`): HTTP/1 parser, HTTP/2 frame handling, multipart, JSON/XML/form bodies, normalizer and canonicalizer, SQL tokenizer and fingerprints, XSS tokenizer, shell lexer, template/EL detectors, GraphQL parser, URL/host/IP parsers, cookie and header parsers, redaction library, outbound leak scanner, DNS wire/TSIG/EDNS/zone-text/SVCB, XDP logic, config/YAML/policy document parsers, rule-pack loader, SBOM/lockfile importers, CSP report parser, PROXY protocol parser (if enabled), webhook signature verifier, template engines (askama inputs), CSV/zone import, markdown renderer (docs).
2. Standardize harness conventions: deterministic seeds, bounded runtime per input (timeouts), allocation caps, structured inputs via `arbitrary` where useful, dictionaries for protocol keywords, and invariants (no panics, no unbounded memory, encode/decode round trips, idempotent normalization, verdict determinism).
3. Set up **campaign automation**: CI smoke (60 s per target on PR), nightly (30 min per target) on the builder, weekly extended (4 h) on high-risk targets; corpora persisted in a separate repository directory (`fuzz/corpus/` managed with `xtask fuzz corpus sync`, minimization via `cargo fuzz cmin`), coverage reports (llvm-cov) to track progress, and sanitizer builds (ASan, UBSan where applicable).
4. Implement **crash triage workflow**: automatic minimization (`cargo fuzz tmin`), deduplication by stack hash, filing as a diagnosis task with reproducer, severity classification (memory safety, DoS, logic), SLA (security-relevant within 72 h), and mandatory regression test addition before closing; crashes block the gate and release.
5. Add **differential fuzzing** where reference exists: normalizer vs reference decoders (percent-decoding, unicode normalization), DNS parser vs `hickory-proto` (and vice versa), HTTP parser vs `httparse`/`h2`, SQL tokenizer vs `sqlparser-rs` for syntactically valid statements (disagreements triaged), and URL parsing vs `url` crate.
6. Add **structure-aware protocol fuzzers**: HTTP/2 frame sequences (state machine fuzz for rapid reset, continuation floods, settings floods) against the real listener in the lab, with process health assertions.
7. Provide a quarterly **fuzz health report**: executions, new coverage, crashes found/fixed, stale targets (no new coverage in 30 days → corpus or harness improvement task).
8. Ensure all fuzz targets build in CI (`cargo fuzz build`) so they do not rot, and document how operators can run them.
**Deliverables.**
- target inventory, automation, triage workflow, differential fuzzers, reports
**Acceptance.**
- A1: every parser in the inventory has a fuzz target that builds in CI and runs in the nightly.
- A2: CI smoke completes with zero crashes; nightly campaigns have no open crash older than the SLA.
- A3: each fixed crash has a regression test committed.
- A4: differential fuzzers produce reports with all disagreements triaged.
- A5: coverage growth is tracked (report generated).
**Tests.**
- Campaigns themselves; unit tests for triage tooling.
**Notes.** Fuzzing on the production VPS is forbidden (C12.6).
