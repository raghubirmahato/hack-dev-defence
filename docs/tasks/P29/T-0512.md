### T-0512 · Soak, capacity model and resource-leak detection
`P29` `[QA][OPS]` · deps: T-0511, T-0214 · size: M · owner: perf
**Objective.** Show that the system runs for days without degradation and describe how much load a given machine can take.
**Steps.**
1. Define soak scenarios (lab and pilot): 24 h and 72 h at 30% of measured saturation with a realistic mix (95% benign, 4% scanners and bots, 1% hard attack payloads from a rotating lab source pool, config changes every 15 minutes, certificate renewals via short-lived staging certs, daily rollup and retention jobs).
2. Collect time series every 10 s: RSS and heap by service, open file descriptors, threads, sockets by state, goroutine-equivalent task counts (tokio metrics), event queue depth, Redis memory and key counts, Postgres connections/locks/bloat/WAL, disk usage, ban-set sizes (L7, Redis, kernel), conntrack counts, latency percentiles and error rates.
3. Define leak criteria: linear regression on steady-state windows; RSS growth ≤ 2% over 24 h after warm-up, fd and socket counts flat (±5%), task counts flat, queue depths bounded, disk growth explained by retention policy; alert thresholds validated by injecting a deliberate leak into a test build (the detector must flag it within 6 h).
4. Verify **retention and housekeeping** under soak: partition creation/drop, rollups, log rotation, cache expiry, ban expiry, session cleanup, webhook delivery pruning; confirm no table or index bloat beyond thresholds (autovacuum behavior documented, settings tuned).
5. Build the **capacity model**: from the measured saturation and per-feature costs derive rps-per-core, connections-per-GB, DNS qps-per-core, ban-set capacity, event ingestion limits, and recommended VPS sizing tiers (S/M/L) with caveats; publish as `docs/CAPACITY.md` (lab-derived, explicitly not a guarantee) and surface in the S-127 capacity panel as "lab-proven".
6. Test **graceful degradation** at 120–200% of saturation: shed policy, priority of ban enforcement and health endpoints, recovery time after load drops, no cascading failures (Redis/Postgres connection storms).
7. Run **cert/ACME and config churn** during the soak and ensure hot reloads cause no errors (error rate delta < 0.01%).
8. Write the automated soak harness with a final report (graphs with table alternatives), plus a shortened 1-hour variant for CI nightly.
**Deliverables.**
- soak harness, reports, capacity model doc, nightly short soak
**Acceptance.**
- A1: no leak criteria violated in the 24 h run (and 72 h run before release).
- A2: the leak detector flags the seeded leak.
- A3: retention jobs keep storage within predicted bounds.
- A4: graceful degradation keeps ban enforcement and health endpoints responsive at 200% load.
- A5: capacity model values are traceable to measurements.
**Tests.**
- Soak runs and the CI short variant.
**Notes.** 72 h soak is a release-gate item executed once near M12.
