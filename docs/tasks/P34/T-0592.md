### T-0592 · Go-live gate, coverage invariants and the protected-state contract
`P34` `[SEC][API][UI]` · deps: T-0591, T-0168, T-0172, T-0222, T-0235 · size: M · owner: product
**Objective.** Enforce R-34 in code: a site is not "protected" and cannot enter `block` mode while it can be bypassed.
**Steps.**
1. Add the lockdown requirement to go-live (T-0168) and to the switch-to-block dialog (T-0222): `block` mode is refused with `ERR-BYPASS-001` unless the lockdown state is `verified`, or the owner records a typed risk acceptance (step-up, audited), after which the site is labeled "bypassable" in every surface until its state becomes `verified` (the acceptance is then cleared).
2. Implement the **coverage invariants** check: every hostname of the site is proxied or explicitly grey with a stated reason; no unproxied record shares the origin address; every published port of the origin is either closed to the world or listed; every invariant violation is a readiness blocker with a link to the fix.
3. Implement the protected-state contract: one function `protection_state(site)` returning `protected`, `monitoring`, `bypassable` or `unverified` through the mapping table of C21.4 (a test covers every state), used by the dashboard, reports, the public status of S-003 claims and the API; no surface computes its own wording.
4. Implement the periodic re-check: a `verified` state expires after 24 hours without a clean verification and becomes `degraded`, with notifications.
5. Implement platform-level enforcement for `saas` mode: platform admins can see the share of bypassable sites; plans cannot disable the gate.
6. Update the readiness score (T-0172) so that bypassable sites cannot exceed a fixed ceiling and the footnote explains why.
7. Add tests for every transition and every surface string; add a lint that fails when a template says "protected" without calling the state function.
8. Write the user documentation "Why your site is not yet protected".
**Deliverables.**
- gate enforcement, invariants, state function, expiry job, readiness changes, docs, tests
**Acceptance.**
- A1: in the tested paths (UI, API, `hddctl`, import, bulk edit) block mode cannot be enabled for an unverified site without the typed risk acceptance.
- A2: in the template lint and browser tests no surface displays "protected" for a site in any other state.
- A3: a site whose last clean verification is older than 24 hours becomes `degraded` automatically.
- A4: a grey record that shares the origin address blocks go-live with a precise fix message.
- A5: an owner with a risk acceptance sees "bypassable" on the dashboard, in reports and in the API.
**Tests.**
- State-machine and surface tests; template lint; browser tests.
**Notes.** This task is the answer to the requirement that requests should not bypass HDD: HDD cannot force the origin host, so it refuses to call the result protected until the evidence says so.

## Definition of done for this task's tags (section 0.7)

### `[SEC]`: Security-relevant logic

Abuse cases written as tests; STRIDE delta in `docs/STRIDE.md`; no secret in logs; constant-time comparison where secrets are compared; failure modes fail closed; panic-free on hostile input (proptest or fuzz target).

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.
