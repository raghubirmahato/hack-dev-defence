### T-0579 · Sentinel doctrine, threat model and runtime decision (ADR)
`P34` `[SEC][DOC][DP]` · deps: T-0246, T-0252, T-0253, T-0254, T-0255 · size: M · owner: sec
**Objective.** Fix what learned components may and may not do before any model is written, and choose the inference runtime.
**Steps.**
1. Write the ADR "Learned detection under a deterministic core" recording R-33, the layers and the modes of C20.2 and C20.5, and the explicit non-goals: no opaque blocking, no training on tenant raw data, no model on the request path that cannot be skipped within budget.
2. Write the ML threat model (C20.7) into `docs/STRIDE.md` as abuse cases: evasion, poisoning, extraction, prompt injection into the analyst, drift, resource exhaustion; each with a planned test (T-0585).
3. Spike the inference runtime: an inference-only Rust path (`tract`, ONNX Runtime bindings, or a hand-written tree-ensemble evaluator), comparing p99 latency, memory, binary size, supply-chain surface and `unsafe` exposure; prefer a pure-Rust evaluator for tree models; record the choice and the FFI justification if any (R-08).
4. Define the model artifact format (versioned, hash-pinned, signed with the release key, with a model card reference) and the verification rules at load (reject unsigned, wrong schema version, oversize).
5. Define the evaluation protocol: fixed splits, the leave-one-family-out procedure, operating-point selection at a false-positive budget, and which numbers appear in public statements.
6. Define the claims language (approved patterns in section 4.3) and add the forbidden forms to claims-lint (T-0005 rules).
7. Define the data-governance policy: what is stored for a finding (feature classes only, redacted snippet through T-0253), retention (30 days; sequence-model state 24 hours), and the opt-in aggregate-feature sharing rule (default off, minimum population of 50 distinct clients per cell, noise added).
8. Record the decisions in `ARCHITECTURE.md` and seed the capability-matrix rows.
**Deliverables.**
- ADR, STRIDE additions, runtime spike report, artifact format, evaluation protocol, claims rules
**Acceptance.**
- A1: the ADR states the bounds of C20.5 and a reviewer can derive from it that no learned component bans alone.
- A2: the runtime choice has measured p99 numbers on the reference hardware named in `docs/ml/BENCH.md` (fixed CPU model, input cap of 8 KiB per vector) for a 200-tree ensemble and a small convolutional model; tree ensembles are the default and a convolutional model is shipped only if its measured p99 fits the budget.
- A3: the artifact verification rules reject an unsigned and a tampered artifact in a test.
- A4: claims-lint fails on "AI-powered protection" and passes on the approved phrasing.
- A5: the evaluation protocol document defines leave-one-family-out for at least five attack families.
**Tests.**
- Unit tests for artifact verification; claims-lint tests; documentation review.
**Notes.** If the spike shows a model cannot meet the 200 µs budget, the ADR records which layers run only in `shadow` or asynchronously.

## Definition of done for this task's tags (section 0.7)

### `[SEC]`: Security-relevant logic

Abuse cases written as tests; STRIDE delta in `docs/STRIDE.md`; no secret in logs; constant-time comparison where secrets are compared; failure modes fail closed; panic-free on hostile input (proptest or fuzz target).

### `[DOC]`: Documentation

Every claim backed by a test ID or a command the reader can run; passes claims-lint; included in the docs site if user-facing.

### `[DP]`: On the data-plane hot path (proxy, DNS, WAF, firewall)

Hot path never awaits the database; bounded memory and queues; criterion benchmark or histogram; fuzz or proptest; behavior when Redis or Postgres is down specified and tested; metric with drop counter.
