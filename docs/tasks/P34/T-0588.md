### T-0588 · Signed origin authentication and generated origin verifiers
`P34` `[SEC][DP][API]` · deps: T-0405, T-0361, T-0365, T-0384, T-0210 · size: XL · owner: sec
**Objective.** Make a direct request to the origin useless: only HDD can produce a request the origin will accept.
**Steps.**
1. Define the `HDD-Origin-Auth` v1 format of C21.3 and the canonical string to sign (newline-terminated, length-prefixed fields exactly as in C21.3: version, kid, method, host, port, raw request-target, body hash or `nobody`, timestamp, nonce, Ray ID, `via` marker), with byte-level test vectors in `docs/ORIGIN-AUTH.md`.
2. Implement signing in the origin client (stage 16): per-site keys in `origin_auth_keys` (envelope encrypted), key ids, rotation with overlap, strip of any inbound `HDD-Origin-*` header, and guarantees that keys and signatures never appear in logs, events or responses.
3. Implement the **verifier reference** in Rust (`hdd-origin-guard` library and a small standalone sidecar) with replay protection (nonce retention of at least twice the skew window, fail closed when full, a shared store option for multi-instance origins), skew window of 30 s, clock requirement and reason code, constant-time comparison, generic 403 responses and rejection of the static header of T-0361 in signed mode.
4. Generate **verifier modules** from templates for nginx (njs or Lua), Apache, Caddy, HAProxy, Express and Fastify, WSGI and ASGI, PHP `auto_prepend_file`, Java servlet filter and .NET middleware; every template ships with tests that run against a real instance of that server in the lab.
5. Extend the lockdown wizard (T-0406) with the verifier choice, the key download (shown once, `PERM-bypass.key_view`, audited), a copy-ready snippet and a verification probe that sends a valid, an expired, a replayed and a forged request and checks the four outcomes.
6. Implement rotation: new key, both accepted, switch after every verifier instance acknowledges or a rolling probe confirms every origin target, retire the old only then; reminders and audit (`AUD-origin_auth.key_viewed`, `key_rotated`, `key_retired`).
7. Report rejected requests (attempts, aggregated by rate) and confirmed bypasses (site content served without a valid signature) from verifiers to HDD in a heartbeat signed with its own key, to be consumed by T-0591, and expose `MET-hdd_origin_unsigned_total`.
8. Keep the static secret header (T-0361) as a documented weaker mode and show it as such in readiness.
**Deliverables.**
- signing, key management, `hdd-origin-guard`, verifier templates with tests, wizard changes, docs
**Acceptance.**
- A1: for every verifier template, a valid request passes and expired, replayed, forged and unsigned requests are rejected (lab matrix per server).
- A2: the signature covers every field of the canonical string: changing the method, host, port, request-target, body or `Content-Length` invalidates it (property test), and field-boundary shifting does not produce a valid signature.
- A3: key rotation completes with no failed legitimate request (traffic test).
- A4: keys never appear in logs, events, errors or responses (grep over a 10,000-request corpus).
- A5: a captured signed request replayed after 30 s, or twice, including across two verifier workers and after a verifier restart within the window, is rejected.
**Tests.**
- Cross-implementation test vectors; lab matrix against real servers; rotation test; log grep.
**Notes.** A stolen key lets an attacker forge requests until rotation (C21.5); keys are stored with web-server-only permissions and rotated on suspicion.

## Definition of done for this task's tags (section 0.7)

### `[SEC]`: Security-relevant logic

Abuse cases written as tests; STRIDE delta in `docs/STRIDE.md`; no secret in logs; constant-time comparison where secrets are compared; failure modes fail closed; panic-free on hostile input (proptest or fuzz target).

### `[DP]`: On the data-plane hot path (proxy, DNS, WAF, firewall)

Hot path never awaits the database; bounded memory and queues; criterion benchmark or histogram; fuzz or proptest; behavior when Redis or Postgres is down specified and tested; metric with drop counter.

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.
