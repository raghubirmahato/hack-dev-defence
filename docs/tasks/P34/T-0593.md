### T-0593 · Stack-aware normalization profiles
`P34` `[DP][SEC]` · deps: T-0241, T-0242, T-0299, T-0358, T-0486 · size: L · owner: waf
**Objective.** Narrow the parser differentials between HDD and the origin by interpreting each request the way the origin's stack would, for the stacks and variants tested.
**Steps.**
1. Define the profile model: `origin_stack` per site (generic, php, java, dotnet, node, python, ruby, nginx, apache, iis, combinations) detected passively (T-0486) and confirmable by the owner.
2. Implement per-profile canonicalization differences: IIS `%u` and `%` quirks, Tomcat path parameters and `..;/`, PHP parameter-name mangling and array syntax, ASP.NET cookieless sessions, Windows path rules (backslash, trailing dots and spaces, 8.3 names, alternate data streams), Apache and nginx decoding order, case sensitivity of paths, duplicate-parameter selection (first, last, array), JSON duplicate-key choice, charset defaults.
3. Make detection run on the canonical view of the *active profile* plus the generic view; a hit on either counts, and a disagreement between them is itself a soft signal (ATK-356, ATK-357).
4. Build a lab stack matrix of real servers and frameworks (containers) and a differential test harness: for each fixture, send to the real stack and to HDD's profile and compare the interpreted path, parameters and body.
5. Add the profile selector and detection evidence to the domain settings and readiness (a wrong profile is shown as a warning).
6. Add benchmarks (profile overhead below 10% of normalization time and below an absolute 20 µs per request on the reference hardware of `docs/ml/BENCH.md`).
7. Add regression tests for known stack-specific bypasses of public WAF rule sets.
8. Document the profiles and how to add one.
**Deliverables.**
- profile model and detection, per-stack canonicalizers, lab stack matrix, differential harness, docs
**Acceptance.**
- A1: for each of nine stacks, the differential harness shows HDD's interpreted request equal to the stack's on 2,000 generated requests except for a listed set of at most 20 documented differences, each with a rule or a limit; a difference not on the list fails the run.
- A2: each stack-specific bypass fixture (ATK-357) is detected under its expected profile, and the fixture list records for each fixture whether the generic profile also detects it.
- A3: profile overhead is within 10% of normalization time.
- A4: the set of detections under any profile contains the generic profile's detections (property test over all fixtures and profiles).
- A5: profile detection from passive data is correct for the lab stack matrix.
**Tests.**
- Differential harness against real stacks; property tests; benchmarks.
**Notes.** Unknown stacks use the generic profile; the readiness view recommends confirming the stack.
