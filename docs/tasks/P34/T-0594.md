### T-0594 · Known-Vulnerability Knowledge Base (VKB) and its screen (S-139)
`P34` `[DB][API][UI][SEC]` · deps: T-0481, T-0482, T-0483, T-0485, T-0063 · size: L · owner: sec
**Objective.** Track named vulnerabilities and vulnerability classes in one place, tied to rules, products and sites.
**Steps.**
1. Add `vkb_entries` and `vkb_rules` (added to B5.11 by this task: key, kind, product purl/CPE, version range, CWE, CAPEC, severity, KEV, EPSS, request_visible, rule_ref, status, source, license, source_commit, reviewed_by, lab_tested_at) with migrations, the status machine (`candidate`, `monitor`, `block`, `retired`, `not_applicable`) and the audit trail.
2. Implement importers in `hdd-vuln` (worker, egress client, signature-verified where offered; upstream commits pinned by SHA and diffs reviewed, never floating branches): CISA KEV, NVD, OSV, GitHub advisories, Exploit-DB metadata, CWE, CAPEC, and the community detection-template repositories permitted by license review (license and provenance recorded per entry; unreviewed licenses are rejected).
3. Implement classification of request-visibility with a reviewable heuristic plus human confirmation, because only some vulnerabilities leave a request pattern.
4. Link entries to products and versions (purl, CPE) and match them against sites' inventories (T-0483) so relevant entries are prioritized and auto-enabled in `monitor` for sites that run the product.
5. Implement the per-domain coverage view of S-139: which known issues apply to this site's components, which have an HDD rule (state), which have none (and why), with the R-11 banner that a rule is not a fix.
6. Implement the API (`/security/known-vulns*`, `P/vkb*`) with `PERM-vkb.read`, `PERM-vkb.review`, `PERM-vkb.publish` and `PERM-vkb.emergency` (step-up, two-person for the last two), audit events `AUD-vkb.entry_status_changed`, `AUD-vkb.rule_published`, `AUD-vkb.rule_rolled_back`, `AUD-vkb.emergency_push` and `AUD-vkb.feed_rejected`, and metrics (`MET-hdd_vkb_entries`, `MET-hdd_vkb_rule_rollout_total`, `MET-hdd_vkb_feed_rejected_total`).
7. Implement the platform admin view for feed health and the time-to-rule SLO tracker.
8. Add tests with recorded feed fixtures including malformed, hostile and license-conflicting entries.
**Deliverables.**
- VKB schema, importers, classification, matching, S-139, API, tests
**Acceptance.**
- A1: importing the recorded KEV fixture creates entries with correct fields and flags request-visible ones for review.
- A2: an entry with an unreviewed license is rejected with `ERR-VKB-001` and a logged reason.
- A3: a site with a matching inventory component sees the entry on S-139 with the correct rule state.
- A4: S-139 never shows "protected" for an entry; it shows the rule state and the R-11 banner.
- A5: malformed and oversize feed items are rejected with `ERR-VKB-001` without affecting other entries.
**Tests.**
- Importer fixtures; matching tests; browser and API contract tests.
**Notes.** The VKB tracks, it does not promise; its coverage numbers cite the date of the last feed run.

## Definition of done for this task's tags (section 0.7)

### `[DB]`: Adds or changes schema

Expand/contract migration only; `org_id` and RLS policy for tenant-owned tables; indexes justified; `sqlx` offline data refreshed; forward migration plus restore-from-backup test; data-retention rule documented.

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.

### `[SEC]`: Security-relevant logic

Abuse cases written as tests; STRIDE delta in `docs/STRIDE.md`; no secret in logs; constant-time comparison where secrets are compared; failure modes fail closed; panic-free on hostile input (proptest or fuzz target).
