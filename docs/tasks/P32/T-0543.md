### T-0543 · Tier 2: tenant-pinned rule-pack versions and staged tenant rollouts
`P32` `[API][UI][DP]` · deps: T-0425, T-0237 · size: M · owner: web
**Objective.** Give cautious tenants control over when platform rule updates apply to their sites.
**Steps.**
1. Extend policy documents with `rule_packs.pin` (pack → version or `latest-stable`/`latest`), constraints (security-critical hotfix packs may override pins for `critical` CVE-class patches only, with notice), and update windows (apply updates only during a chosen window or manually).
2. Implement the **tenant update flow**: a new platform version appears as "available update" with release notes and dry-run results on the tenant's own recent traffic (baseline replay); one-click "apply to monitor first" (shadow mode: rules log `would_block` without enforcing) for N days; then promote to enforce; rollback available at any time.
3. Implement **shadow evaluation** in the data plane: dual evaluation of old and new pack with only the old affecting verdicts while new results are recorded; bounded overhead (≤ 20% inspection CPU while active; automatically disabled under load); results aggregated for the diff report.
4. Add UI (S-058 pack section, S-092 revisions integration) and API; the platform admin console (S-107) shows pin distribution and lagging tenants; security-critical packs have a maximum pin lag (30 days) after which the platform forces the update with notice.
5. Implement compatibility rules: pins cannot reference versions older than N-2 or retired for security reasons; the engine keeps multiple compiled pack versions in memory bounded by the number of distinct pins in use.
6. Write tests: pin resolution, forced-update policy, shadow evaluation accuracy (verdicts identical to single evaluation of the pinned version), memory bounds with many pins, rollback, audit events, permissions.
7. Document trade-offs (older pins lack new protections) in the UI with plain language and in claims-lint terms.
8. Update the capability matrix and the owner docs.
**Deliverables.**
- policy extensions, shadow evaluator, UI/API, tests
**Acceptance.**
- A1: pinned tenants receive only their pinned version's verdicts (differential test).
- A2: shadow mode records `would_block` without affecting responses.
- A3: forced updates for critical packs occur at the policy deadline with notification.
- A4: memory use is bounded by distinct pins (test with 50 pins).
- A5: UI explains the security trade-off of pinning.
**Tests.**
- Differential, statistical, integration.
**Notes.** Pinning is opt-in; the default remains platform-managed rollout.
