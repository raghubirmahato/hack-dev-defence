### T-0555 · Tier 4: BGP/RTBH and anycast integration guidance and tooling for ASN operators
`P32` `[OPS][DOC][SEC]` · deps: T-0476, T-0474 · size: L · owner: ops
**Objective.** Support operators who own an ASN with remotely triggered blackhole (RTBH) and optional scrubbing diversion, safely and in the lab first.
**Steps.**
1. ADR on scope: HDD does not run a full BGP stack by default; it integrates with the operator's routers via (a) a BGP speaker sidecar (BIRD or GoBGP) controlled by `hdd-shield` through a narrow API, or (b) provider/router APIs; RTBH only for destination prefixes the operator owns (never customer ranges), with community tags documented; guardrails to prevent self-blackholing the HDD edge.
2. Implement the **control interface:** `hddctl shield rtbh announce|withdraw <prefix> [--ttl]` with strict validation (prefix must be in `owned_prefixes`, not the edge's own service addresses unless `--i-understand-self-blackhole` is present for a single /32 attack target in an anycast context), TTLs, audit events, and automatic withdrawal when the attack subsides or at TTL expiry.
3. Integrate with the shield actions registry as an optional action with human approval by default (`rtbh.require_approval: true`) and a dry-run mode that renders the exact BGP announcements.
4. Document **anycast** designs (multiple edges announcing the same prefix, health-gated withdrawal), limits and operational complexity; provide BIRD/GoBGP configuration templates and a lab topology (`xtask lab --scenario bgp`) with FRR/BIRD containers for rehearsal.
5. Implement monitoring: BGP session state, announced prefixes inventory vs expected, unexpected announcements alerts (route leak detection by comparing against the allowlist), and RPKI ROA status checks against public data (read-only, egress allowlisted).
6. Safety: the integration refuses to start without explicit ASN/prefix configuration; all announcements require signed internal commands; state is reconciled on startup (no orphaned blackholes), and a break-glass withdraw-all command exists.
7. Test in the BGP lab: announce/withdraw correctness, TTL expiry, refusal of non-owned prefixes, reconciliation after restart, failure of the speaker, and dry-run output goldens.
8. Update the DDoS-readiness document with the new layer and its prerequisites, keeping claims honest (depends on upstream acceptance of communities).
**Deliverables.**
- ADR, `hddctl shield rtbh`, sidecar integration, lab scenario, docs, tests
**Acceptance.**
- A1: announcements for non-owned or self-service prefixes are refused (tests).
- A2: dry-run prints exact announcements and performs no changes.
- A3: TTL expiry withdraws routes and reconciliation prevents orphan blackholes.
- A4: unexpected announcement detection triggers alerts in the lab.
- A5: docs state prerequisites and limits and make no capacity claims.
**Tests.**
- BGP lab (BIRD/FRR), unit tests, goldens.
**Notes.** Requires operator ASN and upstream cooperation: otherwise UNVERIFIED(`capability_not_supplied`).
