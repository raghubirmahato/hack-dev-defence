### T-0547 · Tier 5: WebAssembly plugin runtime (`wasmtime`) for custom detectors and transformations
`P32` `[DP][SEC][API]` · deps: T-0245, T-0248, T-0517 · size: XL · owner: sec
**Objective.** Allow safe extension of the pipeline with sandboxed, resource-limited plugins without risking the data plane.
**Steps.**
1. ADR on the extension model and threat analysis: plugin stages limited to **pure inspection hooks** (`inspect_request(view) -> Findings`, `transform_response_headers`) operating on read-only views; no I/O, no clock, no randomness, no network; deterministic execution; why `wasmtime` (fuel metering, memory limits, WASI-free, component model) versus alternatives (`wasmer`, `wasm3`, native dynamic libraries rejected).
2. Define the **plugin ABI** (WIT/component model): inputs are normalized views (raw/decoded/canonical slices with explicit lengths), outputs are structured findings (category, score, evidence span ranges) validated and capped (max findings, max evidence length); versioned ABI with compatibility rules.
3. Implement the **host runtime:** per-plugin instance pools, fuel limits per invocation (e.g., 2 M instructions), memory cap (e.g., 16 MiB), wall-clock watchdog via epoch interruption, trap handling (a trapping plugin is treated as `no finding` plus a metric and auto-disable after repeated traps, never as fail-open of core rules), compile caching with signature verification, and per-tenant isolation (instances are never shared across tenants).
4. Implement **signing and distribution:** plugins are signed by the platform key (platform plugins) or by tenant keys (tenant plugins in enterprise plans) and uploaded through the API with validation (ABI conformance, size ≤ 2 MiB, static analysis for imports: only allowed host functions), lifecycle states (draft → monitor → enforce → retired) identical to rules, and rollback.
5. Provide an **SDK** (`hdd-plugin-sdk`, Rust) with templates, local test harness (`xtask plugin test`) running fixtures against the same host runtime, benchmarks, and examples (custom header anomaly, app-specific token format validator).
6. Implement **performance and fairness:** plugin budgets added to inspection budgets (T-0256); global fuel accounting per tenant; shed plugin execution before core inspection under load.
7. Security review: plugin escape attempts (malicious wasm: infinite loops, memory growth, out-of-bounds, huge tables), side channels documented, supply chain of plugins, and a lab pentest note.
8. Write tests: ABI conformance, limit enforcement, determinism (same input same output), trap handling, signature enforcement, tenant isolation, load/fairness simulation, and a corpus of hostile wasm modules.
**Deliverables.**
- ADR, runtime, ABI, SDK, UI/API for plugin lifecycle, tests
**Acceptance.**
- A1: hostile modules cannot exceed fuel, memory or time limits and cannot affect other tenants (corpus).
- A2: plugin traps never cause fail-open of core detection.
- A3: unsigned/non-conforming plugins are rejected.
- A4: results are deterministic across runs.
- A5: overhead of a no-op plugin ≤ 20 µs per request.
**Tests.**
- Unit, hostile corpus, performance, integration.
**Notes.** The ADR slot referenced in P00 (`wasmtime`) is settled here.

## Definition of done for this task's tags (section 0.7)
