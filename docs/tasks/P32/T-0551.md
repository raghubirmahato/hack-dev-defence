### T-0551 · Tier 6: ClickHouse (or alternative) analytics backend ADR and optional implementation
`P32` `[DB][DP][OPS]` · deps: T-0441, T-0451 · size: XL · owner: data
**Objective.** Support high-volume event analytics beyond what Postgres partitions can sustain, as an optional backend.
**Steps.**
1. ADR with measured evidence: current Postgres limits from AC-52 scale tests; candidates ClickHouse, TimescaleDB, VictoriaLogs/Loki, DuckDB/Parquet; criteria: ingestion rate, query latency for the analytics catalog, retention economics, operational complexity on a single VPS, security (auth, TLS, RLS equivalents), backups, licensing; decision may be "not needed yet" with trigger thresholds recorded.
2. If adopted: define the **event sink abstraction** (`EventStore` trait) with Postgres default and ClickHouse implementation; dual-write migration path with verification; tenant isolation via row policies or per-tenant views enforced server-side (no direct client access), and API-layer enforcement as the primary control.
3. Implement ingestion (batched native protocol or HTTP with compression, schema with `LowCardinality` and TTL), rollups via materialized views, retention via TTL/partitions, and backfill tools from Postgres.
4. Implement the query layer for the analytics API (T-0442 to T-0445) with identical semantics; correctness proven by the AC-52 ground-truth suite running against both backends.
5. Security: ClickHouse bound to loopback/Unix socket with auth and TLS if remote, users per service with least privilege, no HTTP interface exposure, query limits and quotas per org, and backup integration.
6. Operations: installation via `hddctl deploy --with clickhouse`, resource limits, monitoring dashboards, upgrade procedure, restore drill coverage.
7. Performance: demonstrate ≥ 10x ingestion headroom and query latency targets at 1 billion events in the lab.
8. Document when to switch, how to migrate, and rollback to Postgres.
**Deliverables.**
- ADR, `EventStore` abstraction, backend implementation (if adopted), migration tooling, tests
**Acceptance.**
- A1: AC-52 passes on both backends.
- A2: dual-write verification shows zero divergence over a 24 h soak.
- A3: tenant isolation tests pass on the new backend (BOLA suite).
- A4: lab scale targets are met and recorded.
- A5: rollback to Postgres is rehearsed.
**Tests.**
- Ground-truth suite on both backends, soak, isolation tests.
**Notes.** The ClickHouse ADR slot referenced in P00 is settled here (including a possible "defer").

## Definition of done for this task's tags (section 0.7)

### `[DB]`: Adds or changes schema

Expand/contract migration only; `org_id` and RLS policy for tenant-owned tables; indexes justified; `sqlx` offline data refreshed; forward migration plus restore-from-backup test; data-retention rule documented.

### `[DP]`: On the data-plane hot path (proxy, DNS, WAF, firewall)

Hot path never awaits the database; bounded memory and queues; criterion benchmark or histogram; fuzz or proptest; behavior when Redis or Postgres is down specified and tested; metric with drop counter.

### `[OPS]`: Deployment, operations, runbooks

Idempotent; dry-run mode; documented undo; SSH-lockout protection for host-affecting changes; restore or rollback exercised.
