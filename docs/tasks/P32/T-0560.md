### T-0560 · Backlog governance: tier index, prioritization process and re-planning for later revisions
`P32` `[DOC][QA]` · deps: T-0540 · size: S · owner: pm
**Objective.** Keep the backlog healthy, ordered and linked to evidence so future work starts from facts.
**Steps.**
1. Maintain `docs/BACKLOG.md` as the single index of Tier 2 to Tier 6 items with: task id, tier, theme, value hypothesis, dependency on operator inputs, estimated size, risk class, status (`not_started|in_progress|done|deferred|dropped`), and links to ADRs and gate notes.
2. Define the **prioritization process**: inputs are operator feedback, support tickets, abuse trends, attack matrix gaps (from AC-07/AC-49 results), exposure/advisory events, performance limits (capacity model triggers), cost and complexity; scoring (value × urgency × confidence ÷ effort) recorded per item; quarterly review with the operator.
3. Define **triggers** that pull items forward: for example ClickHouse when sustained ingestion exceeds 60% of the measured Postgres limit; multi-node when availability SLO requires; HTTP/3 when client share exceeds a threshold in analytics; DNSSEC on customer demand with a secondary that supports it; WASM plugins when ≥ 3 customers request custom detectors that cannot be expressed as rules; cache when origin load or attack resilience needs it.
4. Define **entry criteria** for any backlog task: operator approval for architecture-changing items, STRIDE delta started, test plan, acceptance criteria, and rollback plan; and **exit criteria**: gate report, claims updates, docs, and evidence in the acceptance catalog (new AC ids appended after AC-54 without renumbering).
5. Provide a **re-planning template** for later spec revisions: process for adding new tasks beyond T-0560 while keeping `INDEX.md` consistent (new ids T-0579+ in new phases P34+), and for deprecating tasks.
6. Review the **attack matrix gaps** (ATK ids with status not PASS) and add backlog items with links to the failing fixtures; review the capability matrix for `planned` entries.
7. Review **DEVIATIONS.md** for deviations that should be reversed when the underlying constraint disappears (for example UI stack choice, PDF path, plugin-language policy) and schedule decisions.
8. Present the backlog summary to the operator at the end of the project and record the operator's priorities.
**Deliverables.**
- `docs/BACKLOG.md`, prioritization process doc, triggers list, v5.1 re-planning template
**Acceptance.**
- A1: every backlog item has all required fields and no orphan dependencies.
- A2: triggers are measurable and tied to metrics that exist.
- A3: attack-matrix gaps are represented as backlog items or accepted limits.
- A4: the operator's priorities are recorded.
- A5: `INDEX.md` includes the backlog tasks with correct statuses.
**Tests.**
- Index consistency checks (`xtask tasks index --check`).
**Notes.** This is the closing task of the specification; execution of backlog items continues under the same rules.
