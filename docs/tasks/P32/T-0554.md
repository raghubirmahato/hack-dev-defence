### T-0554 · Tier 4: multi-node data plane and highly available control plane
`P32` `[DP][DB][OPS]` · deps: T-0211, T-0524, T-0522 · size: XL · owner: infra
**Objective.** Scale beyond one VPS: several edge nodes serving the same configuration, with the control plane tolerant of node loss.
**Steps.**
1. ADR on topology: N edge nodes (proxy + DNS + agents) sharing configuration snapshots from a primary control plane with a replicated Postgres (streaming replication with automatic failover via Patroni or manual promotion procedure), Redis replication/Sentinel or per-node local Redis with bus federation, shared ban state distribution across nodes (cross-node ban propagation ≤ 2 s), certificate distribution (encrypted store replication; ACME issuance performed by a single leader with distributed locks), and clock/time sync requirements.
2. Implement **node registration and identity:** mTLS with the internal PKI, node roles and capabilities, join tokens (single use, short TTL), node inventory in S-110 with drift detection, and revocation.
3. Implement **snapshot distribution** with per-node acks and monotonic versions; nodes serve the last good snapshot when disconnected; partition behavior documented (nodes continue enforcing local bans and rules; ban propagation resumes on reconnect with reconciliation).
4. Implement **leader election** for singleton jobs (ACME, rollups, webhook scheduling, report scheduling) using Postgres advisory locks or Raft-lite via `etcd`-free approach; verify no duplicate runs (idempotency keys) and no stuck leadership (leases with fencing tokens).
5. Implement **DNS multi-node:** all nodes serve the same zones; NOTIFY/transfers to secondaries from a designated node; consistent SOA serial published by the control plane; anycast not required (multiple NS addresses).
6. Adjust **rate limiting and counters** for multi-node: Redis-shared sliding windows (already Redis-based) with local fallback; per-node fairness; rollups merge node counters idempotently.
7. Implement **rolling upgrades** across nodes using T-0524 orchestration with health gates and canary node, and capacity-aware draining.
8. Test in the lab with 3 edge nodes + 2 control nodes: node loss, partition, leader failover, snapshot lag, ban propagation across nodes, upgrade, restore; update the chaos suite with multi-node experiments; document operational runbooks.
**Deliverables.**
- ADR, node registration, distribution, leader election, runbooks, tests
**Acceptance.**
- A1: killing any single node (edge or control) does not interrupt protection; bans remain enforced on remaining nodes.
- A2: singleton jobs run exactly once under leader changes (fencing tests).
- A3: cross-node ban propagation ≤ 2 s p95 in the lab.
- A4: rolling upgrade across 3 edges has zero failed requests beyond the budget.
- A5: partitioned nodes serve safely and reconcile after healing.
**Tests.**
- Multi-node lab, chaos, upgrade tests.
**Notes.** Tier 1 is explicitly single-VPS; this task generalizes without changing Tier 1 behavior.

## Definition of done for this task's tags (section 0.7)

### `[DP]`: On the data-plane hot path (proxy, DNS, WAF, firewall)

Hot path never awaits the database; bounded memory and queues; criterion benchmark or histogram; fuzz or proptest; behavior when Redis or Postgres is down specified and tested; metric with drop counter.

### `[DB]`: Adds or changes schema

Expand/contract migration only; `org_id` and RLS policy for tenant-owned tables; indexes justified; `sqlx` offline data refreshed; forward migration plus restore-from-backup test; data-retention rule documented.

### `[OPS]`: Deployment, operations, runbooks

Idempotent; dry-run mode; documented undo; SSH-lockout protection for host-affecting changes; restore or rollback exercised.
