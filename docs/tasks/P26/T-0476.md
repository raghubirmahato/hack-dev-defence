### T-0476 · Upstream mitigation profile, provider activation runbook and the three capacity numbers
`P26` `[OPS][DOC][HUMAN]` · deps: T-0474, T-0216 · size: M · owner: ops
**Objective.** Make the dependency on upstream scrubbing explicit, rehearsed and honestly measured.
**Steps.**
1. Implement the `upstream_ddos` profile section reader and validator (mode `none|always_on|on_demand`, provider, advertised capacity, activation method, API endpoint/credentials reference, contact path, null-route policy, VPS uplink), integrated with preflight; `mode: none` is allowed for the pilot only, and the cutover gate treats it as NO-GO unless `risk_acceptance_volumetric: true` with a date is recorded by the operator (C11.2).
2. Implement the **first-response questions** (T-0216 mechanism) that gather: hosting provider and plan, whether mitigation is always-on or on-demand, advertised capacity, what happens when exceeded, uplink speed, presence of a mitigation API, ASN ownership and a second provider for standby/secondary DNS; answers are stored and quoted back in `docs/DDOS-READINESS.md`.
3. Implement a **provider API client abstraction** (`ProviderMitigation` trait: `status`, `activate`, `deactivate`, `dry_run`) with a generic HTTPS client configured per profile (URL templates, auth header reference, body templates) so operators can integrate their provider without code changes, and a documented "support ticket / call" manual procedure (no API) with prefilled message templates; calls use the egress client with allowlisted hosts and run in the provider's dry-run/test mode where available; otherwise the action is rehearsed as documentation only (UNVERIFIED).
4. Generate `docs/DDOS-READINESS.md`: the honest premise, current profile answers, the **three capacity numbers** table (lab-proven from T-0471, provider-advertised, verified-live which stays empty unless the provider supplies measurable evidence), layers present/absent, unknowns, and the activation runbook (who calls whom, what to say, expected time to effect, how to verify, how to deactivate).
5. Implement the S-127 upstream section from this data, including the activation procedure link and dry-run status.
6. Implement **activation rehearsal**: `hddctl shield rehearse provider` runs the dry-run call(s) (or simulated timeline) and records time-to-effect assumptions; results feed AC-27 and the cutover gate.
7. Implement claims-lint rules for DDoS statements: no "DDoS protection" claims beyond the exact measured/contracted facts; allowed patterns listed in section 4.
8. Write tests: profile validation matrix, API client against a fake provider (success, auth failure, timeout), no secrets in logs, document generation golden test, claims-lint tests.
**Deliverables.**
- profile reader, provider client, readiness doc generator, rehearsal command, tests
**Acceptance.**
- A1: the readiness document always shows the three numbers with provenance, leaving verified-live empty without evidence.
- A2: the dry-run path never calls a provider's live mitigation endpoint (fake provider asserts the dry-run header/flag).
- A3: `mode: none` yields NO-GO at the cutover gate unless risk acceptance is recorded.
- A4: claims-lint rejects unqualified DDoS claims in docs and UI.
- A5: provider credentials are never logged or rendered.
**Tests.**
- Unit, fake-provider integration, golden doc tests.
**Notes.** AC-25 is documentation plus dry-run only; capacity remains UNVERIFIED.
