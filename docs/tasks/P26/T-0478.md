### T-0478 · Edge failover (L6, Tier 1): standby edge swap of proxied answers, TTL-aware, with rehearsal
`P26` `[DP][OPS][API]` · deps: T-0475, T-0390, T-0394 · size: L · owner: dns
**Objective.** Provide a manual and shield-driven way to move proxied answers to standby edge addresses when the primary edge is lost or saturated.
**Steps.**
1. Define the **standby model**: `standby_edge_ips` (IPv4/IPv6) in the profile and platform settings, optional second provider/region metadata, readiness state (`unconfigured | configured | verified | active`), and the rule that the standby must run a compatible `hdd-proxy` with the same configuration snapshot (documented: Tier 1 provides the DNS mechanism; keeping the standby's configuration in sync is an operator-run replica using the same signed snapshot distribution or a read-only replica; Tier 4 automates).
2. Implement the **failover operation** (`hddctl dns failover to-standby|to-primary [--zones <list>|--all] [--dry-run]` and API/UI equivalents with step-up): the control plane publishes a platform-wide `edge_address_set` revision in which proxied answers resolve to the standby set instead of the primary; DNS answers change within 2 s of the revision; NOTIFY goes to secondaries (hidden_primary topology) and the operation reports the **expected propagation delay** computed from the effective TTLs (proxied TTL default 300 s, or lower when pre-lowered) and observed resolver behavior.
3. Implement **pre-failover verification**: the standby edge must pass health probes (TLS handshake with SNI for a sample of hosts, HTTP checks with the secret origin header, certificate validity, snapshot revision parity) before activation; `--force` is allowed only with an explicit typed confirmation and is audited.
4. Implement the **origin allowlist note**: the origin must allow the standby addresses (T-0405 egress IP set includes the standby set when configured), and the failover command refuses if the lockdown allowlist is `verified` without the standby set (warns and requires acknowledgment).
5. Implement **failback** with the same checks and a cool-down (default 30 minutes) to prevent oscillation; the shield-driven failover action (`dns.failover_standby`) respects a minimum interval and requires the `auto_failover_enabled` flag (off by default) in the profile; otherwise it alerts and prints the exact manual command.
6. Implement TTL strategy: guidance and tooling to pre-lower proxied TTLs (`hddctl dns ttl-prepare`), measurement of actual cache decay via the propagation checker, and honest messaging ("clients may take up to X minutes").
7. Implement the S-127 failover panel: current edge set, standby readiness, last rehearsal result, estimated propagation, and buttons with typed confirmation.
8. Write tests: dry-run output correctness, revision publication and DNS answer change in ≤ 2 s (integration), pre-verification failures blocking activation, failback cool-down, oscillation prevention, interaction with the origin lockdown note, audit completeness, and a pilot rehearsal using a second pilot address (or the same host's second IP) measured from public resolvers.
**Deliverables.**
- failover command/API/UI, verification probes, TTL tooling, tests, runbook `docs/FAILOVER.md`
**Acceptance.**
- A1: failover changes DNS answers within 2 s of the command and reports expected propagation bounded by TTL.
- A2: activation is refused when the standby fails verification unless forced with confirmation.
- A3: failback respects the cool-down.
- A4: auto-failover remains disabled unless explicitly enabled and then respects minimum intervals.
- A5: the pilot rehearsal records measured resolver convergence times (UNVERIFIED if no second address is available).
**Tests.**
- Integration, dry-run goldens, pilot rehearsal.
**Notes.** Tier 4 (T-0553) adds health-probed automatic failover.
