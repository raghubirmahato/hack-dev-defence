### T-0477 · External heartbeat, incident bundle and timeline
`P26` `[OPS][DP]` · deps: T-0474, T-0473 · size: M · owner: infra
**Objective.** Make sure the operator learns about saturation even when the VPS cannot send alerts, and capture what happened.
**Steps.**
1. Implement the **heartbeat sender**: periodic HTTPS GET/POST (default every 60 s, jittered) to `alerts.heartbeat_url_env` (an external dead-man monitor such as a cron-monitoring service or self-hosted checker the operator runs), including a compact JSON body with state, version and a monotonically increasing counter; failure handling with backoff; the heartbeat uses the egress client (allowlisted host) and never blocks the shield loop.
2. Document the **missed-heartbeat interpretation**: a missing heartbeat means saturation, outage, or host failure; the operator runbook has the checklist and escalation contacts; provide ready-made configurations for common dead-man services (documentation only).
3. Implement **incident bundles**: on entering ATTACK/SATURATED the shield starts recording a rolling trace (T-0473) plus top sources (/24 and /56 aggregates), XDP and nftables counters, DNS stats, proxy shed counts, and action results; at incident end it writes `incident-<ts>.tar.zst` containing the trace, timeline, config snapshot (secrets redacted), and a generated Markdown summary; bundles are stored with a size cap (50 MB each, 10 retained) and listed in S-127.
4. Implement the **incident timeline** model (`shield_incidents`, `shield_events`) in Postgres through the API (queued locally when the API is unreachable and flushed after) and the UI timeline in S-127 with filtering and export.
5. Implement notifications: transition alerts via routing core and direct fallback channels that do not require the VPS's saturated uplink to be healthy (queue + retry; the external heartbeat is the primary signal for total loss); email/SMS provider hooks are documented rather than implemented.
6. Implement privacy: bundles contain aggregated source prefixes only (no full IPs of visitors), and have a retention policy (30 days) with deletion tooling.
7. Add `hddctl shield bundle <incident>` to export a bundle, `verify` to check its manifest (hash list), and import for support analysis offline.
8. Write tests: heartbeat scheduling and backoff (injected clock), failure isolation (a blocked heartbeat endpoint never delays state decisions), bundle content and size caps, redaction tests (no secrets/IPs), queue-and-flush behavior when the API is down, and timeline correctness against trace replays.
**Deliverables.**
- heartbeat sender, bundle writer, timeline persistence, UI hooks, tests, runbook
**Acceptance.**
- A1: stopping the shield (or blocking its network) produces a missed-heartbeat condition detected by the fake external monitor within 3 intervals.
- A2: bundles contain the documented files and pass manifest verification.
- A3: bundle redaction scan finds no secrets or full visitor IPs.
- A4: heartbeat failures never delay state evaluation (timing test).
- A5: incidents are visible in S-127 after API recovery.
**Tests.**
- Unit, trace replay integration, redaction scans.
**Notes.** A saturated VPS cannot reliably alert; the heartbeat absence is the design answer.
