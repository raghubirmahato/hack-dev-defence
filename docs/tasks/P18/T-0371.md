### T-0371 · Automatic rollback engine for rule and policy changes
`P18` `[DP][API][SEC]` · deps: T-0229, T-0237, T-0362 · size: L · owner: waf
**Objective.** Revert harmful rule/pack changes automatically without letting attackers trigger removals.
**Steps.**
1. Implement the **post-change watch** for each new `config_revision` that changes detection behavior (rules, packs, exceptions, categories, thresholds): for a window (default 10 minutes) track the changed rule's own hits and decisions.
2. Implement known-good probe replays: after applying a change (and before marking it stable) replay the site's known-good probes (configured URLs/requests, plus a small sample from the traffic sample with 2xx outcomes) through the pipeline in monitor semantics; if any probe would be blocked by the changed rule, revert immediately and alert (`auto_rolled_back`).
3. Implement rule-hit anomaly detection: if the changed rule blocks at least `rollback.min_distinct_ips` (default 5) **distinct IP keys** within the window with a block-to-pass ratio above the threshold (default 0.8 for requests of that route class that previously had 2xx), revert; **site-wide 403/5xx rates alone never trigger rollback** so an attacker cannot force removal of a security rule.
4. Implement revert mechanics: create a new revision restoring the previous document, mark the failed revision `rolled_back` with the reason, record evidence (probe IDs, counts), publish within 2 s, and notify owners; guard against rollback loops (a reverted change cannot be auto-reapplied; manual re-apply requires acknowledgment).
5. Implement the acceptance control: `rollback.min_distinct_ips=1` can be set on the sandbox site through normal configuration for AC-13 (documented as the only way to test it).
6. Implement exclusions: changes that only tighten security for attack-only signatures flagged `monitor_first` are not auto-reverted unless probes fail.
7. Test scenarios: bad rule blocks a known-good probe → revert; attacker generates many 403s via legitimate rules → no revert; rule blocks many distinct legitimate IPs → revert.
8. Add UI (S-092) display of auto-rollbacks with evidence.
**Deliverables.**
- watcher, probe replay, revert logic, tests
**Acceptance.**
- A1: a rule that blocks a known-good probe is reverted automatically within the probe cycle and alerts fire.
- A2: an attacker-generated flood of blocks from one IP does not trigger rollback.
- A3: distinct-IP anomaly triggers rollback only when the threshold and ratio are met.
- A4: rollback loops are prevented.
- A5: the sandbox acceptance configuration works as documented.
**Tests.**
- Integration with the pipeline harness; simulation tests; unit: decision logic.
**Notes.** AC-13 verifies; evidence is shown in the revision timeline.
