### T-0364 · Resilience: Redis and Postgres failure behavior, restarts and recovery
`P18` `[DP][OPS][QA]` · deps: T-0362, T-0316 · size: L · owner: ops
**Objective.** Prove the data plane degrades gracefully and recovers cleanly.
**Steps.**
1. Specify and implement behaviors: Redis down → local bans and limiter continue, challenge nonce store falls back to local with weaker replay protection (documented), ACME tokens served from Postgres fallback, pub/sub resync on reconnect; Postgres down → serve from the last snapshot, queue events to a bounded on-disk spill (size cap 1 GiB, drop with metrics beyond), config updates paused, readiness reports degraded; both down → continue with local state, no new tenants' changes.
2. Implement circuit breakers with half-open probes for Redis/Postgres clients and backoff; ensure no request path awaits these on failure (timeouts ≤ 5 ms where touched).
3. Implement process restart recovery: load snapshot from Postgres (or the last on-disk snapshot cache if Postgres is down at boot), rebuild ban set from Redis/Postgres, resume operation; cold-start readiness gating (do not accept traffic until snapshot loaded, or accept with fail-closed decisions).
4. Implement chaos tests for each scenario (pilot-stage allowed): stop/start Redis and Postgres, network loss, disk full for the event spill, clock jumps, process kill -9.
5. Measure recovery times and request error rates during failures; define SLOs (error rate under 0.1% for legitimate traffic during Redis outage).
6. Implement alerting for degraded modes (platform and tenant visibility on S-100 and status).
7. Document runbooks for each failure.
8. Add the AC-15 implementation (T-0498 in the acceptance suite) hooks.
**Deliverables.**
- failure handling, spill queue, chaos tests, runbooks
**Acceptance.**
- A1: with Redis stopped, bans persist and legitimate traffic flows with error rate < 0.1%; recovery is automatic after restart.
- A2: with Postgres stopped, routing continues from the snapshot, events queue to disk, and flush after recovery without loss up to caps.
- A3: kill -9 of the proxy restarts under systemd and resumes serving within the bound (≤ 5 s downtime).
- A4: disk-full spill behavior drops events with counters but keeps enforcing.
- A5: runbooks exist and are linked from OPERATIONS.
**Tests.**
- Chaos suite (builder and pilot stage); unit: spill queue.
**Notes.** AC-15 runs these on the pilot with warnings.
