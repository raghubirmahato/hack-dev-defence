### T-0362 · Pipeline integration: stages 6 to 15 ordering, failure modes and end-to-end behavior tests
`P18` `[DP][QA]` · deps: T-0319, T-0335, T-0337, T-0360, T-0361 · size: L · owner: dp
**Objective.** Compose jail, reputation, reserved paths, rate limiter, challenge, body handling, inspection, decision and enforcement into one verified flow.
**Steps.**
1. Assemble stages in the order of C2: safe-mode check, jail/allowlist, reputation/geo policy, reserved paths (`/__hdd/*`, ACME, verification, preview), rate limiter, challenge/clearance, body acquisition, normalization/detection, decision, enforcement.
2. Write the cross-stage semantics doc and tests: allowlisted keys skip jail/limiter but inspection records `would_block`; clearance modifies limits but not inspection; reserved paths bypass inspection but not jail/rate limits (with their own limits); safe mode bypasses inspection, jail, reputation and limits but never the access gate or reserved paths (TLS, routing and headers stay).
3. Implement the failure matrix tests: Redis down, Postgres down, engine panic, budget exceeded, event queue full, origin down, config compile failure, for each of the modes (off/monitor/log/block) and expected behaviors.
4. Implement decision logging and the `Verdict` to response mapping (403 vs 429 vs challenge vs 503) in one place.
5. Implement end-to-end performance tests: p50/p99 added latency for typical requests (GET with cookies, POST login) with full stack; compare against budgets (≤ 5 ms p99 server-side).
6. Implement correctness fuzzing: random request sequences from multiple clients with random config updates; invariants (no request reaches the origin if a jail/hard-block decision was made; no response lacks Ray ID).
7. Implement cross-feature regression tests from earlier phases as a permanent suite (`tests/pipeline`).
8. Update ARCHITECTURE.md with the final sequence diagram.
**Deliverables.**
- composed pipeline, failure-matrix tests, perf results
**Acceptance.**
- A1: failure matrix passes for all combinations (documented table).
- A2: invariants hold under randomized sequences (10 minutes of fuzzing).
- A3: p99 added latency ≤ 5 ms for the typical request mix.
- A4: the origin sees no request when the jail/hard-block decided otherwise (capture origin counters).
- A5: architecture docs are generated/updated and reviewed.
**Tests.**
- Integration and randomized invariant tests; benchmarks.
**Notes.** This is the first end-to-end proof of the defense chain.
