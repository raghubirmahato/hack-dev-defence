### T-0144 · Empty-state implementations and honest-data guards
`P07` `[UI][QA]` · deps: T-0139, T-0021 · size: M · owner: ui
**Objective.** Ensure every list and chart handles absence of data truthfully.
**Steps.**
1. Implement the shared `EmptyState` content registry (title key, explanation key, primary action, secondary link) per screen and per cause (no data yet, filters excluded all, no permission, feature disabled, plan limit).
2. Implement a repository-level `Unknown(reason)` type used by services where a metric cannot be computed (source missing, GeoIP absent, data plane not connected), propagating to UI components that render it.
3. Add a lint/test that scans templates for numeric literals in place of data, and a test that renders every screen with an empty database and asserts no zeros are presented as measurements.
4. Implement the "waiting for traffic" state for newly activated domains with a countdown of expected delay and troubleshooting steps (DNS not yet propagated, caching, wrong origin).
5. Implement the "filters excluded everything" state with a clear-filters button.
6. Implement the disabled-feature state (for example GeoIP-dependent features) with the exact capability the operator must supply.
7. Add visual baselines for empty states.
8. Document how to add empty states for new screens.
**Deliverables.**
- registry, `Unknown` type, tests, docs
**Acceptance.**
- A1: rendering all screens against an empty database yields no fabricated numbers (automated scan).
- A2: each empty state names the next action.
- A3: GeoIP-dependent widgets show the capability requirement when the database is missing.
- A4: waiting-for-traffic state shows relevant troubleshooting links.
- A5: new screens cannot be merged without an empty-state entry (registry check).
**Tests.**
- Browser/e2e: empty-DB sweep over the route table; unit tests for `Unknown` propagation.
**Notes.** This enforces R-16 across the app.
