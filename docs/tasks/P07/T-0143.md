### T-0143 · Onboarding checklist component and persistence
`P07` `[UI][API]` · deps: T-0139, T-0026 · size: M · owner: ui
**Objective.** Guide new organizations to a protected domain without nagging.
**Steps.**
1. Define checklist items as derived state, not stored flags: profile complete, MFA enrolled (owner), first domain added, ownership verified, origin configured, domain active, first requests seen, monitor-mode review done (viewed would-block panel), block mode decision made (enabled or consciously deferred), alert channel tested, teammate invited (optional), DNS backup exported.
2. Implement derivation from real data (domains, events, settings) with caching and explanations; each item shows status, the reason, and a link; unknown data shows `Unknown (reason)`.
3. Implement dismissal per user and per org with re-surface rules (not before 14 days; critical items such as certificate expiry appear in the attention list instead).
4. Implement the "next best action" card using the deterministic rules from T-0026 (decision list), shown on the overview and domain pages.
5. Implement the reminder emails (weekly cap one) only for unfinished critical steps, opt-out in preferences.
6. Implement local counters for step completion times (no per-user tracking beyond the org's own).
7. Add tests for derivation correctness over scenario fixtures.
8. Add accessibility: the checklist is an ordered list with status text.
**Deliverables.**
- derivation module, components, jobs, tests
**Acceptance.**
- A1: completing a step in the UI updates the checklist without manual flags (derived).
- A2: the next-best-action returns the expected item for 20 scenario fixtures.
- A3: dismissal and re-surface follow the specified timing.
- A4: reminder emails respect caps and opt-outs.
- A5: no item can show as complete when its data is unknown.
**Tests.**
- Unit: scenario table tests; integration: email caps with the test clock; browser: dismiss/restore.
**Notes.** No dark patterns: the checklist never blocks product use.
