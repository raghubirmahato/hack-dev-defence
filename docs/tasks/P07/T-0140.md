### T-0140 · Rollup pipeline v0 and the metrics foundation for analytics
`P07` `[DB][OPS][API]` · deps: T-0105 · size: L · owner: api
**Objective.** Create the aggregate tables and jobs that every analytics screen will use.
**Steps.**
1. Write migration 0005: `rollup_minute`, `rollup_hour`, `rollup_day` (yearly partitions for hour/day, daily partitions for minute with 48-hour retention), dimensions (`all`, `category`, `status_class`, `country`, `asn`, `rule`, `path_group`), columns per B5.8, indexes for time-range queries.
2. Define the **ingest contract**: the proxy writes counters to Redis hashes per minute bucket (`hdd:ctr:{site}:{minute}:{dim}`) using atomic increments (cheap, off the critical path via batching), and events to the event queue; the worker drains counters into `rollup_minute` and rolls up hour/day.
3. Implement the rollup jobs with idempotency keys (bucket + site), lag metric (`MET-hdd_rollup_lag_seconds`), backfill command, and correctness tests (sum of minutes equals hour).
4. Implement query services with time-range, dimension filters and downsampling, enforcing RLS through `OrgTx`.
5. Implement plan-based retention for rollups and the partition maintenance job.
6. Implement "Unknown" semantics: missing buckets are gaps, not zeros; the services return gap markers.
7. Implement a synthetic-data guard: no code path inserts non-proxy-sourced counters outside tests (test-only module behind `cfg(test)`).
8. Document the schema and the counter key design.
**Deliverables.**
- migration, worker jobs, query services, docs, tests
**Acceptance.**
- A1: rolling up 1,000 minute buckets into hour and day yields exact sums (property test).
- A2: replaying a rollup job is idempotent (no double counting).
- A3: gaps remain gaps in query results.
- A4: RLS prevents cross-org reads in rollup queries.
- A5: query p95 for 30-day hourly series is under 30 ms on the builder with 1M rows.
**Tests.**
- Integration (Postgres + Redis); proptest on rollup arithmetic; load test on query performance.
**Notes.** Until the data plane exists, only tests write counters; production tables stay empty (honest empty states).

### `[OPS]`: Deployment, operations, runbooks

Idempotent; dry-run mode; documented undo; SSH-lockout protection for host-affecting changes; restore or rollback exercised.

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.
