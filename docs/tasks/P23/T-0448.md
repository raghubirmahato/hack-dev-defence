### T-0448 · PDF pipeline decision, report builder and scheduling (S-074)
`P23` `[API][UI][OPS][DOC]` · deps: T-0447, T-0109, T-0110 · size: XL · owner: data
**Objective.** Produce accessible, deterministic PDF reports and deliver them on schedule.
**Steps.**
1. Run the PDF path **ADR**: candidates (a) headless Chromium print-to-PDF via `chromiumoxide` reusing the HTML renderer and design tokens, executed in a sandboxed worker (no network, read-only filesystem, dedicated user, seccomp, memory/time limits), (b) a Rust-native typesetting approach (for example the `typst` library or `printpdf`/`genpdf`) with dedicated templates, (c) delegating to an external service (rejected by default, violates the data-sovereignty goal). Criteria: fidelity with the design system, **tagged PDF / PDF/UA** capability, font embedding and licensing, determinism (same snapshot → same bytes modulo timestamp), memory and time per 30-page report, attack surface of the renderer, dependency footprint. Record measured results and the decision.
2. Implement the chosen pipeline as an isolated worker task with a strict contract: input = snapshot JSON + template id; output = PDF bytes; resource limits (60 s, 512 MiB, 50 MB output); no network egress (enforced by namespace or by the HTML renderer using only embedded assets); failure leaves no partial artifact.
3. Embed fonts and the logo, set document metadata (title, language, author = org), bookmarks and a table of contents, tagged structure (headings, tables with headers, figure alt text from the chart descriptions), and a fixed A4/Letter selection by locale.
4. Render charts in reports as static SVG with accompanying data tables; ensure the table appears in the PDF for each chart (accessibility) and that colors have pattern differentiation in grayscale printing.
5. Build S-074 (report builder and schedule): choose template, period (last 7/30 days, calendar month, custom), domains, sections and order, locale/time zone, recipients (org members and external addresses with confirmation emails to external recipients before the first delivery), format (PDF, HTML, CSV bundle), schedule (weekly/monthly/custom cron with time zone, next-run preview), delivery (email with a signed expiring link by default; attachment option ≤ 10 MB), and a **live preview** rendered from a snapshot of current data.
6. Implement the scheduler in `hdd-worker`: next-run computation with DST correctness, missed-run catch-up policy (run once on recovery), concurrency limits, retry/backoff, failure notifications to the schedule owner, per-plan limits via `QuotaGuard`, and pause/resume.
7. Implement delivery safety: external recipients must confirm opt-in; unsubscribe links in emails; delivery logs; bounce handling (suppression via `hdd-mailer`).
8. Implement PDF accessibility validation in CI using an oracle (veraPDF PDF/UA profile or `pdfua` checker; UNVERIFIED(`oracle_unavailable`) if absent) and visual diff of the first pages against goldens.
9. Write tests: pipeline limits (oversized input, hostile text, huge tables, RTL strings), isolation (no network access attempt succeeds in the sandbox), determinism, schedule math (DST transitions, month ends, leap years), delivery confirmation flow, and permission checks.
**Deliverables.**
- ADR, PDF worker, S-074, scheduler, validation tooling, tests
**Acceptance.**
- A1: the same snapshot renders to identical PDF content streams across two runs (metadata timestamps excluded).
- A2: the sandboxed renderer cannot open network connections (test attempts DNS and TCP and fails).
- A3: PDF passes the chosen accessibility validator or the gap list is documented as UNVERIFIED with reason.
- A4: schedules fire at the correct local times across two DST transitions in tests.
- A5: external recipients receive nothing until they confirm.
**Tests.**
- Unit, integration, sandbox tests, golden visual diffs.
**Notes.** The ADR slot referenced from P00 (PDF path) is settled here.

## Definition of done for this task's tags (section 0.7)

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.

### `[OPS]`: Deployment, operations, runbooks

Idempotent; dry-run mode; documented undo; SSH-lockout protection for host-affecting changes; restore or rollback exercised.

### `[DOC]`: Documentation

Every claim backed by a test ID or a command the reader can run; passes claims-lint; included in the docs site if user-facing.
