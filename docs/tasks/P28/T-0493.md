### T-0493 · Vuln-Lab foundation: crate, self-guard, canary databases and release exclusion
`P28` `[LAB][SEC]` · deps: T-0491, T-0470 · size: L · owner: lab
**Objective.** Create the sanctioned vulnerable environment safely, so nothing about it can leak into production or be pointed at the internet.
**Steps.**
1. Create `lab/vulnlab/` containing the `hdd-vulnlab` workspace member (excluded from the default workspace members used by `xtask release`), with a `lab-only` cargo feature gate and a `compile_error!` when built with `--release` features used for shipping artifacts.
2. Implement the **self-guard** (section 2.8) in a single `guard::enforce()` called first in `main`: requires `HDD_LAB_ACK=I-OWN-THIS-LAB`; verifies each bind address is loopback or inside `HDD_LAB_CIDR` (parsed, must be RFC 1918/ULA/loopback); inspects network interfaces and refuses if any interface outside the lab namespace carries a globally routable address; prints a prominent banner "HDD VULN-LAB: INTENTIONALLY VULNERABLE: LAB ONLY"; unit-test every refusal path and the happy path.
3. Create the **canary data stack**: databases per dialect (SQLite embedded, MySQL/MariaDB and PostgreSQL containers or embedded test servers, MSSQL optional if license permits) loaded with synthetic canary schemas (`users` with canary admin `labadmin` and hashed canary password, `products`, `orders`, `secrets_canary` table with a unique canary string per run), with snapshot/restore (`xtask lab reset`) before every test and unique per-run canary tokens used to prove exfiltration (if the token appears in a response, extraction occurred).
4. Implement the **network isolation**: compose `internal: true` network or netns with no default gateway; the Vuln-Lab cannot resolve or reach external hosts (egress blocked by namespace rules; tested by attempting outbound connections from within the lab apps, which must fail).
5. Implement **release exclusion**: `xtask release` inspects `cargo metadata` for any shipped binary's dependency graph and fails if `hdd-vulnlab` (or any `lab/` path crate) is present; CI test builds a release artifact and asserts absence in the SBOM; container image build files for the VPS never copy `lab/`.
6. Implement **license and provenance records** for optional third-party vulnerable containers (for example DVWA, OWASP Juice Shop, WebGoat; digest-pinned; license text copied to `lab/LICENSES.md`); they are optional extras for additional oracle coverage and are never required for gates.
7. Provide `lab/vulnlab/README.md` with the safety statement and the explicit "never run outside the lab" instructions, plus a banner in every HTTP response (`X-Vuln-Lab: intentionally-vulnerable`).
8. Write tests: guard refusal matrix (≥ 12 cases), isolation test (outbound connection attempts fail), release-exclusion test, snapshot/restore determinism, canary-token uniqueness, and a test that the binary refuses to start when run with a public bind address.
**Deliverables.**
- `hdd-vulnlab` skeleton, guard, data stack, release gate, docs
**Acceptance.**
- A1: the Vuln-Lab refuses to start in all unsafe configurations (matrix).
- A2: outbound connections from lab apps fail (isolation test).
- A3: release builds fail the gate if the lab crate appears in a shipped dependency graph (negative test).
- A4: database resets restore the canary state exactly (hash compare).
- A5: every response carries the lab header and no real data exists in the lab databases.
**Tests.**
- Unit (guard), integration (netns/compose), CI release-gate tests.
**Notes.** The Vuln-Lab is the one sanctioned exception to "no dummy origin" and exists only to prove protection claims (R-02).
