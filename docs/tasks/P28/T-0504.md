### T-0504 · AC-37 and AC-46: onboarding live for all feasible modes, and email security
`P28` `[QA][HUMAN]` · deps: T-0175, T-0216, T-0491 · size: L · owner: qa
**Objective.** Prove that a new domain can actually be onboarded and protected in each integration mode, and that HDD's own email is trustworthy.
**Steps.**
1. **AC-37 (live onboarding):** using the operator's pilot subzone and any extra operator-supplied domains, execute the wizard end to end (UI via browser automation and API) for: `full_ns` (subzone NS delegation: STOP-style instructions for the operator when needed), `cname_partial` (`www` CNAME to `<site-id>.edge`, TXT verification, `_acme-challenge` CNAME-delegation — requires operator DNS access: `human_step_pending`), `a_record_partial` (A/AAAA to HDD IPs), `subdomain_only` (NS delegation of a single subdomain), and `hidden_primary` (if the external secondary exists); for each mode verify ownership verification, import/parity, origin config and test, TLS issuance (staging) and HTTPS served, protection preset selection, go-live checklist, readiness score values, and that a Class A attack shape is blocked once in block mode (sandbox) and logged in monitor mode.
2. Execute **negative onboarding tests:** attempting to add a domain the org does not control (verification fails), a domain already claimed by another org (conflict flow), disposable/abusive patterns, SSRF origin values, loopback/private origins, platform-address origins, invalid DNS imports, a `CNAME` loop, and plan limit exceedance.
3. Execute **decommission and revert:** the decommission wizard with revert instructions, DNS cool-down, certificate deletion and zone reservation behavior.
4. **AC-46 (email security):** HDD's sending domain has SPF, DKIM and DMARC configured (instructions provided; checked by DNS lookups; `UNVERIFIED(human_step_pending)` until the operator publishes records), message authentication results verified on a test mailbox if the operator provides one (header analysis), TLS to the SMTP relay enforced, templates pass link-safety checks (no open redirects, tokens in URL fragments or POST pages to avoid referrer leaks), header-injection fuzz (CRLF in names/subjects), rate limits and suppression list behavior (bounces/complaints), and verification-token security (entropy, single use, expiry).
5. Verify **email content rules:** no sensitive data, accessibility of HTML emails, plain-text alternatives, unsubscribe handling for non-security emails, locale selection.
6. Capture screenshots (both themes) of each wizard step for the evidence bundle and the documentation.
7. Record AC-37/AC-46 statuses with exact UNVERIFIED reasons (operator DNS actions, mailbox access).
8. Feed any wizard friction found into backlog tasks (UX improvements) without delaying the gate unless a defect is found.
**Deliverables.**
- onboarding evidence per mode, email-security report, instructions to operator for pending human steps
**Acceptance.**
- A1: each feasible mode completes onboarding with a served, protected test hostname (or UNVERIFIED with `human_step_pending` for operator DNS steps only).
- A2: negative onboarding cases are refused with the documented error codes.
- A3: decommission restores a clean state and respects cool-down rules.
- A4: email security checks pass or are UNVERIFIED with exact steps required.
- A5: the evidence includes both-theme screenshots for every wizard step.
**Tests.**
- Browser e2e on pilot, API checks, DNS lookups.
**Notes.** The operator's DNS access is the main dependency; instructions are generated, copy-pasteable and time-boxed.
