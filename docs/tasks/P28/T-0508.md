### T-0508 · AC-06, AC-07, AC-09, AC-49 and AC-50: false-positive baseline, attack-matrix coverage and API/GraphQL/WebSocket protection
`P28` `[QA][SEC]` · deps: T-0313, T-0255, T-0302, T-0305, T-0496 · size: XL · owner: qa
**Objective.** Measure detection coverage across the whole attack matrix with honest statuses per ATK id, and prove the false-positive baseline.
**Steps.**
1. **AC-06 (false-positive baseline):** replay the benign corpora (general 500+, SQL prose 400+, code samples, internationalized text, JSON/XML bodies, common frameworks' real request shapes captured from the pilot in monitor mode — personal data removed by the redaction library) through the pipeline in `block` mode at each preset; require 0 blocks; replay captured pilot traffic (opt-in) and review `would_block` entries; apply the held-out benign set separately.
2. **AC-07 / AC-09 / AC-49 (matrix coverage):** execute every ATK-001..ATK-390 fixture according to its action code and payload class: in-process and inspect-API for all; live sandbox for Class A/B/C allowed on the sandbox; Vuln-Lab for exploit classes; record per ATK id: detected? action as expected (BB/B/S/C/L/R/T/P/Q)? hardness? false positives? status PASS/FAIL/UNVERIFIED(reason); `xtask attack-matrix-check` generates the coverage table from fixtures and results and fails if any ATK id lacks a fixture or a status.
3. **AC-50 (API/GraphQL/WebSocket):** OpenAPI positive-security enforcement (unknown paths/params/types rejected in block mode), content-type enforcement, JSON depth/size limits, mass-assignment signals, BOLA/IDOR enumeration heuristics (sequential ids), GraphQL protection (depth, complexity, batching, introspection policy, alias overloading), WebSocket handshake checks (origin validation, message size/rate caps, subprotocol rules), gRPC reflection policy, and API key abuse patterns; run against the Vuln-Lab API apps and the pilot sandbox canary where applicable.
4. Run the **protocol-level suites** referenced by ATK groups (request smuggling shapes, header injection, HTTP/2 abuse) against the sandbox hostname within the protocol-abuse profile; ensure process health is maintained.
5. Run **tuning-drift check:** compare detection results against the previous gate baseline to detect regressions (`tests/baselines/detections.json`), with an allowlist of intentional changes.
6. Identify **coverage gaps:** every ATK id not PASS is listed with reason and a backlog task (P32) or a fix task now (if the id is Tier 1 required); Tier 1 FAIL blocks the gate.
7. Produce the coverage report with a heat map by group (AG-01 to AG-21), exact counts, and the list of limits (what signature-based detection cannot see).
8. Archive evidence and update AC statuses.
**Deliverables.**
- coverage report, FP baseline report, regression baselines
**Acceptance.**
- A1: 0 false positives in `block` mode across all benign corpora.
- A2: every ATK id has a fixture and a status; all Tier 1 (`PL 1`) ids are PASS or UNVERIFIED with reasons (no FAIL).
- A3: AC-50 checks pass on the lab API apps.
- A4: regression comparison shows no unexplained loss in detections.
- A5: the limits statement is included in the report.
**Tests.**
- In-process, inspect API, sandbox live subset, Vuln-Lab.
**Notes.** "PASS" means the control behaved as specified for that fixture, not that the attack class is eliminated.
