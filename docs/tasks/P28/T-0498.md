### T-0498 · AC-15: resilience and failure-mode scenarios (announced, pilot stage)
`P28` `[QA][OPS]` · deps: T-0364, T-0370, T-0371, T-0491 · size: L · owner: qa
**Objective.** Verify behavior under component failure, with the guarantees stated in the spec.
**Steps.**
1. Execute scenarios on the pilot (announced, `lifecycle_stage: pilot` only; refused in production without operator approval) and in the lab: Redis killed and restarted (local ban cache and limiter fallback, no fail-open of inspection, bans enforced from local copy, metric `MET-hdd_rate_limiter_fallback_total`), Postgres killed (serve from snapshot, queue events locally, no hot-path DB await, resync after recovery), both down simultaneously, API/worker down (data plane unaffected), DNS service restart (answers resume ≤ 2 s from cache snapshot), proxy graceful restart (in-flight requests drain, no dropped connections beyond the documented cap), origin down/slow/flapping (branded 502/504, health checks, serve-stale if enabled), snapshot corruption (previous version retained), disk full on the event spool (backpressure and drop policy, no crash), clock skew ±5 min (ACME and session behavior documented), certificate store decryption failure for one site (others unaffected), memory pressure (shed policy), and file-descriptor exhaustion.
2. For each scenario record: expected behavior (from the spec), observed behavior, time to detect (alert), time to recover, data loss (events dropped counters), and security impact (never fail open in `block` mode: run the mandated payload during each failure and require a block).
3. Verify **auto-rollback** safety under failure: injected origin 5xx storms and block storms do not trigger rollback of security rules (C14.8: site-wide 403/5xx alone never triggers rollback).
4. Verify **safe mode** interplay: entering safe mode during failures is possible via `hddctl` with the API down; the same attack passes in safe mode and is blocked again after exit.
5. Verify observability: each failure creates the expected alerts (platform and tenant) and S-100 attention items within thresholds; heartbeat continues.
6. Run **recovery drills**: restore from backup into a scratch instance in parallel (T-0435 tooling) and compare health.
7. Capture evidence and update the failure-mode table in `docs/OPERATIONS.md` with measured values.
8. Fix failures under the failure budget (R-14) and re-run; any residual FAIL blocks the gate.
**Deliverables.**
- AC-15 report with the failure-mode table, evidence
**Acceptance.**
- A1: no scenario results in an inspection fail-open in `block` mode (the mandated payload is blocked in every scenario).
- A2: the hot path never awaits the database (trace evidence under Postgres failure).
- A3: recovery times meet the documented targets (stated per scenario).
- A4: rollback is not triggered by block/5xx storms.
- A5: all scenarios produce the documented alerts.
**Tests.**
- Live pilot and lab fault injection.
**Notes.** Production-stage runs require announced windows and operator approval (section 2.7).
