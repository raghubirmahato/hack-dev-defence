### T-0497 · AC-38: vulnerable-origin proof (direct exploit works, through HDD it fails and the IP is banned)
`P28` `[QA][LAB][SEC]` · deps: T-0496, T-0273, T-0317, T-0319, T-0463 · size: XL · owner: qa
**Objective.** Demonstrate in the lab the product's core promise on a genuinely vulnerable site.
**Steps.**
1. For every Vuln-Lab endpoint class (login SQLi, search SQLi, numeric-ID SQLi, reflected XSS, LFI, command injection, SSRF fetcher, upload, deserialization, XXE, open redirect, IDOR, etc.) run the **three-part test**: (a) **direct exploit** against the Vuln-Lab succeeds (control proof, must succeed or the test is invalid); (b) the same exploit through HDD in `block` mode with the **Vulnerable-Origin Shield (Balanced)** preset fails (403 or branded block page), no malicious query appears in the Vuln-Lab access log, and the attacker's IP is banned (L7 jail within 2 s; kernel set when the agent is present); (c) a legitimate request on the same endpoint through HDD still succeeds (and a subsequent legitimate request from a **different** IP is unaffected).
2. Repeat (b) with the preset matrix: Monitor first (event recorded as `would_block`, exploit succeeds by design, `would_ban` recorded), Balanced, Strict, Shield Paranoid; document expected outcomes in the matrix and assert them.
3. Execute the **user's scenario explicitly**: every one of the six mandated payloads (M1–M6) submitted to the login form, the search form, the JSON login and the cookie/header contexts of the vulnerable app; each through HDD in `block` mode returns 403, shows the block page with a Ray ID, results in a ban of the source IP with the correct reason and TTL ladder step (1 h first offense), the following request from the same IP (even benign) receives the jail response, and the Vuln-Lab never executes the injected query.
4. Verify **ban semantics:** repeat offenders escalate the ladder (1 h → 6 h → 24 h → 7 d) using time-accelerated bookkeeping; ban expiry unblocks; manual unban restores access ≤ 2 s; bans survive proxy restart and Redis flush (Postgres reload); cross-site subresource context cases return 403 without ban (AC-34 detail tested in T-0500).
5. Verify **V13 tripwire** in monitor mode: a payload that actually bypasses the lab login (direct control) followed by a 2xx/3xx login success produces the `possible_auth_bypass` critical event when sent through HDD in monitor mode.
6. Verify **outbound shield** behavior: error-based SQLi endpoint leaking database errors is masked/blocked in outbound `block` mode even when the request-side detection is disabled for the test (defense-in-depth proof), and the leak event is recorded.
7. Verify **virtual patch** behavior on a lab-known vulnerable component endpoint (T-0485 pack) in monitor and block states.
8. Record the results as `lab-proven` (for command injection, deserialization, SSRF and upload execution: "lab-proven at the injection level using inert interpreters") with evidence (pcap, logs, ban records, Vuln-Lab access logs), update the claims evidence appendix ("Tested against N payloads in our lab; novel techniques can evade signature-based detection"), and produce the AC-38 table (class × preset × outcome).
**Deliverables.**
- AC-38 evidence bundle and table, claims evidence entries
**Acceptance.**
- A1: for 100% of endpoint classes the control exploit succeeds directly and fails through HDD in block mode with a ban.
- A2: all six mandated payloads are blocked and ban the source in every applicable context.
- A3: the Vuln-Lab database log shows zero malicious queries executed through HDD in block mode.
- A4: legitimate requests succeed on every endpoint, including from the same network for non-banned IPs.
- A5: outcomes match the preset matrix exactly.
**Tests.**
- Lab runs (the heart of the gate).
**Notes.** This is the evidence that supports the headline claim, within the stated lab limits.
