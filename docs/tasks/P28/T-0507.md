### T-0507 · AC-02 and AC-23: import parity at scale and cutover rehearsal checks
`P28` `[QA][HUMAN]` · deps: T-0184, T-0403, T-0402, T-0491 · size: L · owner: qa
**Objective.** Prove the zone import/parity machinery on realistic data and rehearse every pre-cutover check without touching the operator's live apex delegation.
**Steps.**
1. **AC-02 (import and parity):** import zone files covering all record types and provider quirks (Cloudflare-style export, Route 53 JSON-to-zone converters, BIND with `$ORIGIN/$TTL/$INCLUDE` edge cases, wildcard, CNAME flattening ALIAS records, SRV/CAA/TLSA/SSHFP/NAPTR, long TXT, DKIM multi-string, unusual TTLs, duplicate records, relative/absolute names, IDN), large zones (50,000 records), and the operator's real apex zone **exported by the operator** (read-only copy): parity report lists supported, unsupported and provider-proprietary types; parity FAILS until each unsupported type is acknowledged; verify every record in the import answers identically from the HDD DNS server in a lab instance (compare with the source zone loaded in a reference implementation).
2. **AC-23 (cutover parity gates):** with the real zone copy in the lab instance: mail records (MX, SPF, DKIM, DMARC) match, `non_http_services` are grey, DS check logic (T-0403) correct against the real parent state (read-only DS lookups), TTL strategy (pre-lowering plan), propagation probe tooling, apex certificate pre-issuance plan (CNAME-delegated `_acme-challenge`; staging dry-run), secondary DNS plan present or risk accepted in writing, and the rollback plan rehearsed in the lab (fast path with safe mode and grey records; slow path documented).
3. Run the **cutover rehearsal script** (`xtask cutover rehearse`) in the lab: a full simulated cutover from "old provider zone" to HDD with scripted resolvers observing continuity of answers (no NXDOMAIN gaps, mail routing unchanged), measuring the worst-case answer inconsistency window.
4. Generate the **operator cutover pack** (`RUNBOOK-CUTOVER.md` with values filled from the profile, the exact registrar steps (host objects/glue, NS change), the monitoring checklist, rollback commands) and verify with the claims-lint and a checklist test that every step has a verification command and an undo.
5. Verify that **nothing in this task touched production delegation** (audit trail: no registrar API calls exist in the product; DNS probes are read-only lookups).
6. Capture evidence; mark AC-23 as PASS only for the checks executable without the live delegation, and list the live-only items as `UNVERIFIED(human_step_pending)` (they execute during the actual cutover in P31).
7. Review risks with the operator via the first-response protocol (decision confirmations: secondary DNS, volumetric acceptance, maintenance window).
8. Update the cutover gate checklist with the current status of each gate item.
**Deliverables.**
- parity reports, rehearsal logs, operator cutover pack draft, gate checklist
**Acceptance.**
- A1: import of all fixture and real-copy zones yields identical answers (differential check) for every supported record.
- A2: unsupported types block parity until acknowledged.
- A3: the rehearsal shows no answer gaps for mail and web records in the simulation.
- A4: every runbook step has a verification and an undo (checklist test).
- A5: audit proves no live delegation changes were attempted.
**Tests.**
- Differential DNS tests, lab rehearsal, doc checks.
**Notes.** The actual apex cutover is a human-gated action in P31 (STOP #2).
