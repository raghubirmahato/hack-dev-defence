### T-0496 · Lab topology and oracle harness: HDD in front of the Vuln-Lab with pinned external oracles
`P28` `[LAB][OPS]` · deps: T-0494, T-0495, T-0470, T-0208 · size: L · owner: lab
**Objective.** Build the repeatable test rig in which attackers and legitimate clients talk to the Vuln-Lab through the real HDD stack.
**Steps.**
1. Define the topology via `xtask lab up --scenario vuln`: namespaces `attacker`, `legit`, `edge` (real `hdd-proxy`, `hdd-dns`, `hdd-api`/`hdd-worker`, Postgres, Redis, optional `hdd-fw-agent` and XDP with veth), `origin` (Vuln-Lab); the edge terminates TLS with an internal lab CA (never a public cert) and routes lab hostnames (`login.lab.test`, `shop.lab.test`, ... resolved by the lab's own DNS) to origins; the origin is firewalled to accept only the edge (lockdown applied in the lab to exercise the same path).
2. Provision HDD for the lab using the real onboarding flow driven through the API (create org, add domains in `full_ns`-like lab mode with ownership verification via lab DNS TXT), apply presets (Monitor first, Balanced, Strict, Shield Balanced, Shield Paranoid) to measure each; **no mocks of HDD components**.
3. Pin and install **oracles** in `lab/oracles/` (versions + SHA-256 + license notes): `sqlmap`, `nikto`, `wapiti`, `nuclei` (with a pinned template set), `OWASP ZAP` baseline scan, `ffuf` with pinned wordlists, `dalfox`/XSS tools optional, `commix` for command injection optional, `jwt_tool` optional, `testssl.sh` for TLS, `slowhttptest` for slow attacks (lab only), `h2spec`/`nghttp2` for HTTP/2, `dig/kdig/delv`; wrapper scripts expressed as `xtask lab oracle <name> -- <args>` enforcing the lab-only target allowlist.
4. Implement the **evidence capture**: pcap of attacker↔edge↔origin traffic for each test (bounded size), the proxy events, ban records, firewall counters, Vuln-Lab access logs (to prove what reached the database), oracle outputs and tool versions.
5. Implement the **assertion library** for lab tests: `assert_exploit_blocked(proof, via_hdd)` (the proof fails through HDD, a 403 or branded block page is observed, the Vuln-Lab log shows no malicious query, a ban exists with the right reason and TTL, kernel enforcement acknowledged when present), `assert_legit_passes(endpoint)`, `assert_no_extraction(canary)`, `assert_banned(ip, within)`.
6. Implement the **scenario matrix runner** that executes a proof set under each preset and each mode (monitor, block), collecting results into a table (class × preset × mode → outcome).
7. Add safety: the harness's egress allowlist contains only lab addresses; oracles run with seccomp-like restrictions where feasible (unprivileged user, no access to host secrets); the harness refuses to run if the topology guard sees a route to the internet from the attacker namespace.
8. Write tests: topology bring-up/tear-down idempotency, route-to-internet guard (attacker ns cannot reach outside), assertion library unit tests against recorded runs, oracle wrapper allowlist enforcement.
**Deliverables.**
- lab scenario `vuln`, oracle manifests/wrappers, assertion library, docs `docs/lab/VULN-LAB.md`
**Acceptance.**
- A1: `xtask lab up --scenario vuln` brings up a working rig in under 5 minutes on the lab machine and tears down cleanly.
- A2: the attacker namespace cannot reach the internet (guard test).
- A3: oracle wrappers refuse non-lab targets.
- A4: assertion library correctly classifies recorded success/failure runs.
- A5: evidence capture produces pcap, logs and manifests for each test.
**Tests.**
- Lab integration, unit tests for assertions.
**Notes.** Third-party oracles are used strictly as oracles in the lab; their output is never presented as live results.
