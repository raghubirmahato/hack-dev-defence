### T-0494 · Vuln-Lab application set A: SQL injection family with direct-exploit proofs
`P28` `[LAB][QA]` · deps: T-0493 · size: XL · owner: lab
**Objective.** Provide authentically vulnerable SQLi endpoints in every context HDD must protect, each with a non-destructive proof that it is exploitable without HDD.
**Steps.**
1. Implement the **login family** (the user's scenario): a classic login form (`POST /login`, `username`, `password`) building SQL by string concatenation (`SELECT * FROM users WHERE username='$u' AND password='$p'`), a JSON login (`POST /api/login` JSON body), a login with the credentials in HTTP Basic auth, an "admin panel" login variant with a `LIMIT 1` query, and a "remember me" cookie lookup; each ships in MySQL, PostgreSQL and SQLite dialect variants where syntax differs (comment styles `--`, `#`, `/* */`).
2. Implement the **query context family**: search (`GET /search?q=` using `LIKE '%$q%'`), numeric ID (`GET /item?id=`), sort/order parameter (`ORDER BY $col`), pagination `LIMIT $n`, `IN (...)` lists, header-based (User-Agent and X-Forwarded-For stored in a visit-log INSERT), cookie-based (`session` cookie used in a lookup), path-parameter (`/user/{id}`), form-urlencoded and multipart fields, JSON nested field, and XML SOAP-style body.
3. Implement the **advanced family:** error-based (database errors echoed in HTML or JSON), UNION-capable (column count 4 with a string column), boolean-blind, time-based (SLEEP/`pg_sleep`/`randomblob` loop capped at 2 s by a lab-side guard), stacked queries (PostgreSQL/MSSQL variant only, against canary tables), and **second-order** (profile name stored, later concatenated into an admin report query).
4. For each endpoint publish a **direct-exploit proof** (`lab/vulnlab/proofs/sqli/*.yaml`): Class A, non-destructive only: login bypass returning the canary admin session marker; UNION extraction of the per-run canary token; boolean/time differential with ≤ 2 s sleeps; no `DROP`, no writes to non-canary tables; the proof runner executes against the Vuln-Lab directly and **must succeed** (a failing proof means the endpoint is not vulnerable and the test environment is invalid).
5. Include the **mandated payload set** M1–M6 (`' OR 1=1--`, `' OR '1'='1`, `admin' --`, `admin' #`, `admin'/*`, `' or 1=1 LIMIT 1 --`) in each applicable context with the dialect-correct form, and verify each succeeds as a direct exploit where syntax is valid (some are dialect-invalid; the proof matrix records which are valid for which endpoint, so "direct exploit failed because of syntax" is distinguished from "blocked").
6. Add **legitimate-use endpoints** next to each vulnerable one (normal login with valid canary credentials, search for ordinary words, apostrophe names such as `O'Brien`, a SQL tutorial comment form) used for false-positive checks and for ensuring HDD does not break the app.
7. Add structured **access logging** in the Vuln-Lab (request, query executed, rows returned) so tests can assert what reached the database; the log is part of the evidence (proves that blocked requests never hit the database).
8. Write self-tests: every proof succeeds on a fresh reset; legitimate flows succeed; the guard keeps the app lab-only; the app code is annotated as intentionally vulnerable with a static marker test so scanners do not mistake it for product code.
**Deliverables.**
- vulnerable SQLi apps, proof definitions, legit endpoints, logs, self-tests
**Acceptance.**
- A1: all direct-exploit proofs succeed on a fresh canary state (≥ 30 proofs across contexts and dialects).
- A2: the proof matrix records which of M1–M6 are valid per endpoint with expected direct outcomes.
- A3: time-based endpoints never sleep more than 2 s (lab guard).
- A4: legitimate flows succeed, including apostrophe inputs.
- A5: the access log shows exactly which queries reached the database for each test.
**Tests.**
- Self-tests; used by T-0497 and T-0499.
**Notes.** Only Class A proofs exist; no destructive exploit chain is implemented anywhere in the lab.
