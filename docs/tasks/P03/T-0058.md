### T-0058 · Add-domain wizard, all eight steps (S-042)
`P03` `[UI][SEC]` · deps: T-0053, T-0056 · size: XL · owner: ux
**Objective.** Design the highest-risk flow in the product so a non-expert can complete it safely.
**Steps.**
1. Design step 1 (enter domain): normalization hints, bulk add, validation messages for each `ERR-DOM-*` code, dispute link.
2. Design step 2 (scan): progress states, grouped findings (web, mail, other, unknown), provider guess, import options.
3. Design step 3 (connect method): the three cards with what changes/stays, rollback time, prerequisites, recommendation badge logic and an "Not sure?" helper.
4. Design step 4 (review records): record table with proxy toggles and risk notes, mail-forced-grey explanation, origin-leak warnings, parity banner; partial mode view with "Do this at your DNS provider" boxes and copy buttons.
5. Design step 5 (ownership): TXT and HTTP file methods, live status, next-check time, manual check, troubleshooting accordion.
6. Design step 6 (origin): form with test results panel, SSRF-guard errors, TLS mode explanation, plaintext origin acknowledgment pattern.
7. Design step 7 (TLS and protection level): certificate plan options with consequences, preset cards (Monitor first default), shield explanation.
8. Design step 8 (go live): verified-facts checklist, preview commands, rollback instructions, DS-record warning, delegation/CNAME poller after activation, and the success state showing first requests.
**Deliverables.**
- prototype pages for every step and state; copy drafts; flow diagram
**Acceptance.**
- A1: every step has success, validation-error, system-error, loading and resume states.
- A2: rollback instructions appear before the final activation control.
- A3: partial-mode instructions include exact record names/types with copy buttons.
- A4: the plaintext-origin option requires explicit acknowledgment and is flagged in readiness.
- A5: the wizard is completable by keyboard and screen reader (walkthrough script).
**Tests.**
- Axe; keyboard walkthrough; heuristic evaluation with the "Maya" scenario scripted step by step.
**Notes.** This wizard defines the acceptance criteria for T-0153 to T-0176.

## Definition of done for this task's tags (section 0.7)

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.

### `[SEC]`: Security-relevant logic

Abuse cases written as tests; STRIDE delta in `docs/STRIDE.md`; no secret in logs; constant-time comparison where secrets are compared; failure modes fail closed; panic-free on hostile input (proptest or fuzz target).
