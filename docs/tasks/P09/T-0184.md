### T-0184 · Import/export and the parity report UI (S-047)
`P09` `[UI][API]` · deps: T-0157, T-0182 · size: L · owner: dns
**Objective.** Make migration of an existing zone auditable and reversible.
**Steps.**
1. Implement the import UI: upload zone file, paste records, import from scan, AXFR option; show progress and parse results.
2. Implement the parity engine: compare imported source records with HDD records, producing identical, intentionally-proxied (answer differs by design), missing, extra, and unsupported categories with reasons; compute a verdict.
3. Implement acknowledgment of unsupported/provider-proprietary types (ALIAS/ANAME, URL redirect, etc.) with explanation of alternatives; parity fails until acknowledged (AC-02).
4. Implement the live comparison against the source's authoritative servers (query allowlisted resolvers for the same names) after import to catch unseen records; report differences.
5. Implement export in BIND format (round-trip stable), JSON, and CSV; exports include a header comment with generation time and version; proxied records export both stored and served values with explanation.
6. Implement re-import of an export to verify equality (self-test button available to admins).
7. Implement the permission and audit events.
8. Add tests with real zone corpora.
**Deliverables.**
- import/export UI and services, parity engine, tests
**Acceptance.**
- A1: export then re-import produces an identical zone (round-trip test over 50 corpora).
- A2: unacknowledged unsupported types block activation in full-NS mode.
- A3: parity differences are categorized and explained.
- A4: exported files contain no secrets.
- A5: UI shows the live comparison with timestamps and resolvers used.
**Tests.**
- Round-trip property tests; integration: parity vs loopback source servers; browser flows.
**Notes.** Parity gating is part of the cutover checklist (C17.2).
