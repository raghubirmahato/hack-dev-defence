### T-0187 · Record templates library with provenance
`P09` `[UI][DOC]` · deps: T-0182 · size: M · owner: dns
**Objective.** Offer starter templates without pretending to know third-party services' current requirements.
**Steps.**
1. Define the template format (parameters, records generated, warnings, provenance: source URL or "generic best practice", last reviewed date, reviewer) and a registry with schema validation.
2. Write generic templates: static website (A/AAAA + www CNAME), mail forwarding basics (MX placeholder with parameters), SPF/DKIM/DMARC scaffolds, `security.txt` guidance (not DNS), domain verification TXT placeholders, CAA scaffolds, SRV scaffolds.
3. Provider-specific templates (for example common mail or hosting providers) are included only when the operator supplies a verified source document; otherwise the registry contains none and the UI says "No provider templates installed".
4. Implement parameter forms with validation and previews using the answer engine, then apply via the normal record API with safety checks.
5. Display the provenance and review date on each template and warn when older than 365 days.
6. Provide an `xtask templates check` validating schema, freshness and records.
7. Add tests for generation.
8. Document how operators add templates.
**Deliverables.**
- registry, UI, xtask check, docs, tests
**Acceptance.**
- A1: every template shows provenance and review date.
- A2: no template contains a provider-specific value without a recorded source.
- A3: applying a template runs the safety engine.
- A4: stale templates are flagged.
- A5: parameters are validated server-side.
**Tests.**
- Schema tests; integration: apply and rollback; browser flow.
**Notes.** Avoid guessing: wrong provider instructions break mail.
