### T-0183 · Mail safety panel and the CAA wizard
`P09` `[UI][API][SEC]` · deps: T-0180, T-0182 · size: M · owner: dns
**Objective.** Protect email and certificate issuance policy from accidental breakage.
**Steps.**
1. Implement the mail-safety panel: detect MX presence, MX targets, provider guess (informational), SPF/DKIM/DMARC state, and flag risky actions in the current change set (deleting MX/SPF/DKIM, proxying mail hostnames, changing nameservers when MX exists without importing mail records).
2. Implement guard rails: deleting MX records requires a confirmation that lists consequences; bulk changes touching mail records show a dedicated warning.
3. Implement the CAA wizard: list existing CAA (including parents), explain `issue`/`issuewild`/`iodef`, propose records permitting the platform's ACME CA(s) (from settings) and the owner's other CAs, and warn when CAA would block HDD issuance.
4. Implement mail test guidance (steps for the owner to send test mail; HDD never sends mail to third parties, section 2.5).
5. Add attention items for missing DMARC or expiring DKIM keys (informational).
6. Add API endpoints exposing the panel data.
7. Add tests with scenarios (no mail domain, Google-like and Microsoft-like record patterns as fixtures).
8. Add accessibility checks.
**Deliverables.**
- panels, wizard, tests
**Acceptance.**
- A1: deleting MX/SPF records triggers a warning dialog listing impact.
- A2: CAA proposals never exclude the platform CA unless the owner insists with acknowledgment.
- A3: the panel works for domains without mail (shows "No mail records").
- A4: no outbound mail is sent by this feature.
- A5: wording makes no deliverability promise.
**Tests.**
- Scenario tests; browser tests of dialogs; unit: CAA computation.
**Notes.** Mail MX continuity is also verified at cutover (AC-23).
