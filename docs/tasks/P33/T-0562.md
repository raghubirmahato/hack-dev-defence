### T-0562 · `KvStore`, `Bus` and `Limiter` traits with Redis and in-process backends, and the conformance suite
`P33` `[DP][SEC][QA]` · deps: T-0561 · size: XL · owner: dp
**Objective.** Let every runtime-state feature work against Redis (hosted) or in-process memory (local) with identical semantics, proven by one shared suite.
**Steps.**
1. Define the traits in `hdd-common::kv` exactly as C18.3: `KvStore` operations, the named atomic operations (`rate_window_check`, `challenge_nonce_consume`, `offence_incr_with_decay`, `flow_signal_update`), `Bus` with revisioned messages and gap detection, `Limiter` with `counter`, `exact` and `gcra` algorithms. Keys follow B5.12.
2. Implement `RedisKv` on `fred` with Lua scripts for the named operations (`EVALSHA`, `NOSCRIPT` recovery), pipelining, a circuit breaker with half-open probes, and TLS/auth required.
3. Implement `MemoryKv`: sharded maps with per-key TTL (hierarchical timing wheel or lazy expiry plus a sweeper), named operations under shard locks, a bounded `Bus` on `tokio::sync::broadcast` with revision counters and drop counters, size caps with eviction by TTL then LRU, and **pinned namespaces** (bans, sessions) that are never evicted but are capped with a clear error.
4. Implement the restart contract of C18.3: a `rehydrate(ctx)` step that loads bans, offences and sessions from Postgres into `MemoryKv` before listeners open, with a metric for rows loaded and time taken.
5. Write the conformance suite `kv_conformance` (TTL accuracy ±50 ms, atomicity under 64 concurrent tasks, bus ordering, gap detection and resync, eviction rules, pinned namespaces, large-value limits, key-length limits) and run it against both backends in CI; the Redis run uses testcontainers on Track H and is `UNVERIFIED(environment_unsupported)` on Track L.
6. Publish the usage contract for the tasks that consume the traits: ban store (T-0316), rate limiter (T-0333, including the exact algorithm for auth endpoints and the counter bound), challenge nonces (T-0108, T-0337), session cache (T-0113), config bus (T-0211), live event feed (T-0446), credential-stuffing counters (T-0343), campaign detection (T-0325) and the gate and flow engines (T-0575, T-0577). Those tasks use the traits from the start (section 0.9; `xtask kv-lint` fails any direct Redis use), so there is no later port; this task provides the traits, both backends, the helpers and the suite.
7. Add `MET-hdd_kv_ops_total` and `MET-hdd_kv_latency_seconds`, and a startup refusal: `HDD_KV_BACKEND=memory` with `runtime.profile: hosted` and more than one registered service process.
8. Benchmark both backends (criterion): `MemoryKv` limiter check ≤ 5 µs p99, `RedisKv` ≤ 1 ms p99 in-datacenter.
**Deliverables.**
- `hdd-common::kv` (traits, two backends), conformance suite, ports, metrics, benchmarks
**Acceptance.**
- A1: the conformance suite passes on `MemoryKv` and, where Redis is available, on `RedisKv` with identical results.
- A2: `rate_window_check` agrees with a reference model on 10,000 random request sequences for the counter algorithm (within its documented bound) and exactly for the exact algorithm, on both backends.
- A3: the `rehydrate` contract is tested against a fixture durable source (bans, offences, sessions); the end-to-end restart test with real tables is acceptance A6 of T-0564.
- A4: the bus delivers revisions in order and signals a resync on a forced gap.
- A5: memory use is bounded under a key flood (cap and eviction counters verified); pinned namespaces never evict.
**Tests.**
- Conformance, property tests of TTL and eviction, loom or shuttle tests on the shard-lock logic, chaos (kill Redis), benchmarks.
**Notes.** This task changes how existing tasks store state; it must not change what they decide. The differential check is `profile-parity`.
