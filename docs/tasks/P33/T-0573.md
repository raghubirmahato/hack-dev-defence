### T-0573 · One-command server bootstrap: `deploy/cloud-init.yaml`, hardened base, firewall with SSH-lockout protection, unattended updates
`P33` `[OPS][SEC]` · deps: T-0522, T-0468, T-0469, T-0571 · size: L · owner: ops
**Objective.** Take a fresh server to a hardened, ready-to-deploy host with one reviewed file and one command, safely.
**Steps.**
1. Generate `deploy/cloud-init.yaml` from Rust structs (no hand-written YAML drift): creates the service users, directories with modes, swap, time sync, the unattended-security-upgrades configuration with a kernel-reboot window, journald limits, log rotation, SSH hardening (keys only, no root login, rate limits) applied with the auto-revert timer, and a base nftables ruleset that allows only SSH from `ssh_allow_cidrs` plus the HDD ports.
2. Implement `hddctl bootstrap --host <h>` (SSH via `russh`, dry-run by default, `--apply` to execute) that uploads the verified `hddctl` and runs the same steps idempotently for providers without cloud-init.
3. Resolve the port-53 conflict automatically but safely: detect `systemd-resolved`, configure `DNSStubListener=no` and a working local resolver config with an undo, verified before and after.
4. Implement the provider-notes matrix (outbound SMTP blocks, reverse DNS, IPv6, firewall in front of the VM) as warnings in the plan output and in `docs/HOSTING.md`.
5. Add the post-bootstrap verification that runs `hosting check` and prints the remaining operator actions (secrets escrow, DNS records, STOP #1 items).
6. Test on disposable VMs: apply, re-apply (idempotent), simulate a lockout (auto-revert within the timer), undo, and compare rulesets before and after.
**Deliverables.**
- cloud-init generator, `hddctl bootstrap`, resolver handling, provider notes, VM tests
**Acceptance.**
- A1: a fresh Debian or Ubuntu VM reaches `hosting check` with no FAIL from HC-01 to HC-06 and HC-12 to HC-14 after one command.
- A2: re-running the command changes nothing (state hash equal).
- A3: a deliberately lock-out-causing SSH change reverts itself within the timer.
- A4: the plan output (dry run) lists every file, package and service it would change.
- A5: the generated cloud-init file passes `cloud-init schema` validation.
**Tests.**
- Disposable-VM integration; idempotence and undo tests; schema validation.
**Notes.** Nothing here touches DNS or the registrar; those stay human-gated (R-04).
