### T-0578 · Coverage map, completeness audit and the acceptance of AC-55 to AC-58 (S-134)
`P33` `[QA][DOC][UI]` · deps: T-0313, T-0508, T-0509, T-0564, T-0565, T-0566, T-0567, T-0568, T-0569, T-0570, T-0571, T-0572, T-0573, T-0574, T-0575, T-0576, T-0577 · size: L · owner: qa
**Objective.** Replace adjectives with a generated, tested map of what is covered, partially covered and not covered, and prove the new capabilities.
**Steps.**
1. Create `design/coverage/*.toml` from the E15 table: OWASP Top 10 2021, OWASP API Security Top 10 2023, OWASP Automated Threats OAT-001 to OAT-021, a CWE Top 25 grouping, and the HTTP/DNS/TLS/L3-L4 layers, each item with status, mechanism, ATK groups, AC IDs, task IDs and limits.
2. Implement `cargo xtask coverage` (generate `docs/COVERAGE.md`, the S-134 data and `GET /public/coverage`) and `cargo xtask coverage check` with the failure rules of C19.5; wire it into `xtask verify`.
3. Build S-134 (public and domain variants) with the always-open "What HDD does not cover" section, date and commit stamp, and domain-scoped active/partial/off states computed from the site configuration.
4. Extend claims-lint with the new forbidden phrases (section 4.2) and add a test that fails on any "absolute", "complete" or "total" protection wording in docs, UI strings, i18n catalogs, OpenAPI descriptions, report templates and the coverage text.
5. Implement acceptance AC-55 (local runtime: self-test on three OS runners, `profile-parity`, hostile-page and rebinding tests, loopback-only proof, first-run flow), AC-56 (24/7: hosting check on the pilot, reboot test, chaos subset, backup and restore, LKG autonomy), AC-57 (access gate bypass suite, API discovery, business-flow scenarios) and AC-58 (coverage check and wording lint), with evidence per section 0.4.
6. Run a **completeness audit**: for each E15 row marked covered or partial, confirm a passing test or UNVERIFIED with a reason; list any row without evidence and fix or downgrade its status; record the result in `docs/COVERAGE.md` with counts ("N of M rows with PASS evidence").
7. Run the end-to-end demo script for the operator: local install on a clean machine, add a site, send the six mandated payloads, show the ban, then the same on the hosted pilot; capture the evidence bundle.
8. Close gate G33 with the report in the E5.1 format.
**Deliverables.**
- coverage sources and generator, S-134, claims-lint extension, AC-55 to AC-58 implementations, audit, gate report
**Acceptance.**
- A1: `xtask coverage check` fails on an injected `covered` item without an ATK group, AC or task, and passes on the real data.
- A2: the public coverage page renders every E15 row, the "does not cover" section, and the generation date and commit.
- A3: claims-lint fails on an injected "absolute protection" string in each scanned surface.
- A4: AC-55 to AC-58 each end PASS or UNVERIFIED with enumerated reasons; none ends FAIL.
- A5: the completeness audit reports its counts and no covered row without evidence.
**Tests.**
- xtask tests with injected failures; browser tests for S-134; the AC suites themselves.
**Notes.** The goal is an honest, auditable statement of coverage, not a perfect score. A row downgraded to `partial` is a success of the audit.

## Definition of done for this task's tags (section 0.7)

### `[QA]`: Test infrastructure

Real services only (no mocks); deterministic or seeded; evidence output stored under git-ignored `acceptance-*/` with sha256.

### `[DOC]`: Documentation

Every claim backed by a test ID or a command the reader can run; passes claims-lint; included in the docs site if user-facing.

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.
