### T-0572 · 24/7 supervision: systemd watchdog, restart policy, last-known-good snapshot autonomy, disk guard
`P33` `[DP][OPS]` · deps: T-0522, T-0364, T-0211, T-0375, T-0388 · size: L · owner: dp
**Objective.** Make the data plane survive crashes, reboots and control-plane outages without human action, and say so only as far as it is tested.
**Steps.**
1. Generate systemd units with the settings of C18.11 item 1 (`Type=notify`, restart policy with `StartLimitIntervalSec=0` in `[Unit]`, `WatchdogSec`, `OnFailure=hdd-alert@%n` plus a restart-rate alert, `RestartSteps` only where systemd is 254 or newer, `MemoryMax`, `OOMScoreAdjust`, `Wants=` not `Requires=` on stores) and Compose equivalents (restart policy, healthchecks).
2. Implement `sd_notify` watchdog pings from every service main loop in a way that stops pinging when the event loop is blocked (test with an injected stall).
3. Implement the last-known-good snapshot: atomic write after each swap to `HDD_SNAPSHOT_CACHE_DIR` (write temp, fsync, rename), integrity hash, schema version, and startup loading in proxy and DNS when Postgres or Redis is unavailable, with the degraded banner, disabled config changes, and `MET-hdd_snapshot_lkg_age_seconds`.
4. Implement the bounded disk spool for events during store outages (256 MiB, oldest dropped with counters) and replay on recovery with deduplication by `(ray_id, ts)`.
5. Implement the disk guard of C18.11 item 4 (`HDD_DISK_GUARD_PCT`) with `MET-hdd_disk_guard_active`, alerts, and the rule that bans, audit rows and the database are never auto-deleted.
6. Add chaos tests: kill each service, kill Postgres, kill Redis, fill the disk, stall an event loop, reboot the VM; assert enforcement continues from the snapshot and local ban cache, inspection never fails open (R-26), and recovery needs no manual step.
7. Add the metrics and alert rules (T-0525 family) for restarts, watchdog misses, snapshot age and spool depth.
8. Document the exact degraded-mode behavior table in `docs/HOSTING.md`.
**Deliverables.**
- unit generators, watchdog integration, snapshot cache, spool, disk guard, chaos tests, alerts
**Acceptance.**
- A1: with Postgres and Redis stopped, restarting proxy and DNS yields correct answers and enforcement from the cached snapshot within 10 s.
- A2: an injected event-loop stall makes systemd restart the service within `WatchdogSec` plus 5 s.
- A3: during a 10-minute store outage no request is passed uninspected (differential test), and events spooled during it appear after recovery without duplicates.
- A4: at 90% simulated disk usage events are sampled and exports refused; bans still write.
- A5: a VM reboot returns all services to ready with no manual step (HC-19 evidence).
**Tests.**
- Chaos suite on a VM; unit tests on snapshot atomicity (power-cut simulation); spool replay tests.
**Notes.** This task proves resilience of the single-node design; it does not make one node highly available.
