### T-0577 · Business-flow protection (S-133)
`P33` `[UI][API][DP][SEC]` · deps: T-0312, T-0333, T-0337, T-0343, T-0345, T-0350 · size: XL · owner: dp
**Objective.** Detect and limit abuse of legitimate business functions (credential stuffing, fake signups, OTP/SMS pumping, carding, scraping, coupon guessing, form spam) with explainable signals.
**Steps.**
1. Add `business_flows` (B5.6), `PERM-flow.*`, `AUD-flow.*`, `ERR-FLOW-001`, `MET-hdd_flow_events_total`, the Redis/kv keys of B5.12 and the migrations with RLS.
2. Implement the flow engine in three phases (C19.4): Phase A at stages 9 and 10 (request-line and header signals, template match, lookups), Phase B at the new stage 12a (declared-field signals after extraction), Phase C at the new stage 18a (outcome recording from status, redirect or declared body marker, with asynchronous counter updates); all signal computation goes through `KvStore.flow_signal_update`; a combined score and the action ladder (`monitor`, `challenge`, `block`, `ban` for high-confidence classes only) integrate with the ban policy (C6.4) and rate limiter (T-0333). Phase C actions apply to subsequent requests.
3. Implement the signal library of C19.4 by flow kind: velocity and distinct-credential ratios, time-to-complete, honey fields (site-declared hidden field populated), sequence integrity, per-destination OTP caps, declined-to-approved ratios using declared card-hint fields restricted to the last four digits or the first six plus last four (Luhn-valid 13-to-19-digit values are dropped unhashed with a misconfiguration alert; hints are HMAC-SHA-256 truncated to 32 bits under a per-site key, held in `KvStore` only, never persisted or logged), scraping breadth and timing regularity, coupon guess rates, duplicate-content hashes.
4. Implement templates for login, signup, reset, OTP, checkout, search, contact, coupon and gift card with sensible defaults, shipped in `monitor`.
5. Implement guards against false positives: clearance cookies relax limits, verified bots and allowlisted addresses bypass flow signals, per-flow allowlists, and a maximum action per signal class until the owner raises it.
6. Implement **Simulate** (replays recent event summaries against a definition and reports would-be actions) and the S-133 screen and API of B6.7.
7. Add explainability: every flow event stores the signals and values that fired (counts, ratios, durations), never request values, and the event drawer shows them in plain language.
8. Write lab tests with synthetic traffic generators: credential stuffing from rotating IPs, signup flood with disposable domains, OTP pumping to many destinations, carding-shaped checkout bursts, price scraping with realistic timing, coupon enumeration, and a benign replay that must produce zero blocks.
**Deliverables.**
- flow engine, signal library, templates, simulate, S-133, API, lab tests
**Acceptance.**
- A1: each synthetic abuse scenario triggers its intended signal and, in `block` mode, its intended action; the benign replay produces zero challenges and zero blocks.
- A2: flows in `monitor` never change a response (differential test).
- A3: the OAT items marked covered in E15 each map to at least one passing scenario.
- A4: no card hint, credential or form value appears in events or logs (privacy test with canary values).
- A5: flow evaluation adds at most 50 µs p99 CPU time per matched request with the in-process store; Redis-backed counters are pipelined asynchronously and never delay the response (benchmark).
**Tests.**
- Lab generators; benign replay; privacy test; benchmark; browser tests for S-133.
**Notes.** Business-flow controls reduce abuse; they cannot know an application's intent, and E15 says so.

## Definition of done for this task's tags (section 0.7)

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.

### `[DP]`: On the data-plane hot path (proxy, DNS, WAF, firewall)

Hot path never awaits the database; bounded memory and queues; criterion benchmark or histogram; fuzz or proptest; behavior when Redis or Postgres is down specified and tested; metric with drop counter.

### `[SEC]`: Security-relevant logic

Abuse cases written as tests; STRIDE delta in `docs/STRIDE.md`; no secret in logs; constant-time comparison where secrets are compared; failure modes fail closed; panic-free on hostile input (proptest or fuzz target).
