### T-0539 · Post-cutover stabilization: from monitor to block, tuning and sign-off
`P31` `[OPS][SEC]` · deps: T-0537 · size: M · owner: ops
**Objective.** Move the live site to enforcement confidently and close the cutover.
**Steps.**
1. After the monitor-first baseline, review false-positive families and the effect of each fix with dry-run replays on the captured baseline (T-0229); require zero unexplained `would_block` on known-good traffic before switching.
2. Present the **block switch proposal** (impact summary: expected blocks per day, categories, top paths, any risky rules) and obtain the operator's confirmation; switch to `block` with the chosen preset (Balanced or Strict or the Vulnerable-Origin Shield presets if the origin is known-weak), with the safe-mode and rollback commands at hand; observe for 2 hours at heightened attention.
3. Enable **ban enforcement layers** progressively (L7 jail, kernel set, XDP if available and confirmed), verifying the runner and operator IPs are protected, and test ban/unban end to end with a safe test source.
4. Enable outbound filter `block` after a monitor period with zero false positives, response header policy, cookie policy `report` mode; keep intrusive options off unless validated.
5. Verify **operational health**: alert noise review (tune thresholds), dashboards, backup jobs, certificate renewals scheduled, secondary DNS sync, shield state NORMAL, resource usage under real traffic, and DNS query patterns (abuse detectors quiet).
6. Conduct a **post-cutover review** with the operator: incidents, surprises, UX friction, documentation gaps; produce action items; decide the decommission plan for the old DNS provider (kept per TTL policy).
7. Update **STATUS.md and the capability matrix** with live observations; keep clear that live traffic observations are the operator's environment's numbers.
8. Mark the cutover complete only when two consecutive days show stable error rates, no unresolved P1/P2 incidents and the operator's written sign-off.
**Deliverables.**
- stabilization report, tuning changes, sign-off record
**Acceptance.**
- A1: the block switch happens only after the recorded confirmation and with a clean baseline replay.
- A2: error rates and latency remain within budgets after enforcement (dashboards).
- A3: alert noise is within the documented target (≤ 3 non-actionable alerts/day).
- A4: all enforcement layers verified with safe tests.
- A5: sign-off is recorded.
**Tests.**
- Live monitoring and safe verification tests.
**Notes.** If cutover is deferred, this task is UNVERIFIED(`human_step_pending`) and the pilot remains in monitor/block per the operator's choice.
