### T-0534 · Launch readiness review and claims audit across all surfaces
`P31` `[DOC][QA]` · deps: T-0531, T-0532, T-0533 · size: M · owner: qa
**Objective.** Confirm that what the product says matches what has been proven, everywhere.
**Steps.**
1. Build the **claims inventory** automatically: scan UI strings (Fluent files), templates, docs, emails, PDFs, API descriptions, error messages, marketing pages and README for any statement about protection capability, performance, availability, compliance and security; each claim must map to an evidence id (acceptance result) and carry a limits statement where needed; unmapped claims fail the build (`xtask claims-audit`).
2. Review **forbidden/approved phrase patterns** (section 4): "protects against SQL injection" must read as the approved pattern with N payloads/lab statement; "DDoS protection" only with contract facts; "secure/unhackable/complete" forbidden; "compliant/certified" forbidden; performance statements must cite AC-24 numbers with environment tags; DNSSEC claims forbidden unless `delv` passes.
3. Verify the **required UI disclosures** exist where specified: the readiness score footnote ("Measures configuration completeness, not security"), the "Mitigated, not fixed" label, the monitor-mode explanation, partial scan note, geolocation approximation note, capacity provenance labels, and the lab-proven label on lab-derived figures.
4. Run the **launch readiness checklist** (`docs/LAUNCH-CHECKLIST.md`): capability matrix has no `planned` items in Tier 1 scope; all gates G00..G30, G33 and G34 tagged; acceptance report complete with only enumerated UNVERIFIED; docs complete; legal approved or signup closed; monitoring active; backups and drills green; keys rotated from bootstrap values; admin accounts MFA enforced; default credentials absent; status page live; abuse intake works; support contact works; on-call ownership recorded; incident playbooks exercised.
5. Decide **public exposure level** with the operator: `owner_only` private use, invite-only SaaS, or open signup (needs `signup.mode: open` approval), and set the profile accordingly; confirm that surface exposure (`admin_exposure`) matches the decision.
6. Run **cutover gate 7** (C17.2): AC-35, AC-36, AC-40, AC-42 pass if product surfaces will be public; verify with the latest acceptance run.
7. Produce the **launch decision record**: go/no-go per item, residual risk acceptances, owner names, date; keep it in `docs/LAUNCH-DECISION.md` (operator-signed in chat).
8. Fix every discovered mismatch (text change or evidence) and re-run the audit.
**Deliverables.**
- claims audit report, launch checklist results, launch decision record
**Acceptance.**
- A1: `claims-audit` reports zero unmapped or forbidden claims.
- A2: all required disclosures are present in the right places (UI tests).
- A3: the launch checklist has every item PASS or accepted by the operator in writing.
- A4: public exposure level matches profile and guards (signup mode, legal approval).
- A5: the decision record is complete.
**Tests.**
- `claims-audit`, UI disclosure tests, checklist verification script.
**Notes.** This is the last internal gate before human-gated production steps.
