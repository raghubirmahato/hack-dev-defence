### T-0538 · Production ACME issuance (one event, operator-approved) and certificate verification
`P31` `[HUMAN][SEC][OPS]` · deps: T-0385, T-0536 · size: M · owner: ops
**Objective.** Issue the real certificates once, safely, with the CA's rate limits respected and no gap at cutover.
**Steps.**
1. Present the **issuance request** to the operator (drafted at T-0385): exact hostnames (apex, wildcard if needed, `www`, app surfaces), challenge types (DNS-01 with CNAME-delegated `_acme-challenge` for the apex; HTTP-01 for pilot names), CA directory, account key handling, expected rate-limit consumption (duplicate certificate and failed validation budgets checked against the current CA documentation at this time), fallback plans, and rollback (revoke/abandon).
2. Wait for the operator's explicit written approval of this one issuance (R-04); record it verbatim in `docs/OPERATOR-CONFIRMATIONS.md`; set `acme.directory=production` and `acme_production_enabled=true` only after approval, through an audited, time-boxed flag that auto-resets after the issuance window.
3. Verify prerequisites: staging end-to-end success in the last 7 days (T-0385), CAA records permit the CA (checked), secondary DNS serves the challenge TXT (secondary-aware wait), CNAME-delegation works for the apex name (observed), budgets OK, certificate store healthy, backups of the ACME account key.
4. Issue: run the order via the production scheduler path with detailed logging (no secrets), watch for failures, apply the failed-validation budget guard (stop after the first failure for diagnosis, no retries loops), and store the certificate and key through the envelope store.
5. Verify the issued certificates: chain validation against public trust (using the platform's TLS probe and an external oracle such as `openssl s_client` and `testssl.sh` against a pre-cutover test name with `--resolve`), SAN/lifetime/key type, SCT presence, CT log observation (if a CT service is configured), OCSP/CRL per decision T-0382, HSTS state unchanged until the cutover is stable.
6. Reset the production flag, record issuance in the audit log and the final report (counts against limits), set renewal scheduling with ARI, and alert thresholds for expiry; verify renewal works on a staging-clone path (no extra production orders).
7. If issuance fails: diagnose, record failure counts, do not retry beyond the safe budget without operator approval, and propose alternatives (HTTP-01 fallback names, waiting for limit windows).
8. Update the cutover gate evaluation (apex certificate pre-issued).
**Deliverables.**
- approval record, issuance log, verification evidence
**Acceptance.**
- A1: production issuance happens only after the recorded approval and only once per approved request.
- A2: issued certificates validate against public trust and cover the approved names.
- A3: failed-validation budget is never exceeded.
- A4: the production flag auto-resets and the audit log shows the full sequence.
- A5: renewal scheduling is active with expiry alerts.
**Tests.**
- Live issuance with verification (operator-approved); dry-run in staging beforehand.
**Notes.** Placed before the cutover in execution order: T-0537 depends on this task's output even though the numbering follows the runbook.
