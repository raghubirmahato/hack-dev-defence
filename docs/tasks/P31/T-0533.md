### T-0533 · Pre-launch hardening review and external-style testing close-out
`P31` `[SEC][QA]` · deps: T-0519, T-0510, T-0530 · size: L · owner: sec
**Objective.** Re-attack the finished system with fresh eyes before real exposure and close the remaining findings.
**Steps.**
1. Re-run the full lab pentest (T-0519) against the release candidate with updated oracle versions and templates; compare with the earlier baseline; verify every previous finding is fixed with its regression test.
2. Run a **configuration review** of the pilot/production-shaped deployment: exposed ports, TLS posture (testssl, SSL Labs-like offline checks), headers, cookies, CSP, admin exposure mode, default accounts, debug endpoints, error pages, metrics exposure, CORS, rate limits, backup permissions, secrets file permissions, systemd scores, kernel parameters, DNS zone transfer restrictions, mail authentication.
3. Run a **red-team style exercise** in the lab with a written scenario: attacker with no access attempts to bypass the shield on the Vuln-Lab with creative techniques (the evasion catalog plus novel variants developed during the exercise by a separate "red" role that does not use the training fixtures), documenting each bypass found; every bypass becomes a rule/test task, fixed or consciously accepted with documented limits; results update the limits statements.
4. Run **abuse-of-features analysis**: how could an attacker use HDD as a weapon? (reflection via DNS, open proxy, SSRF via origin config, webhook SSRF, scanner abuse, feeds poisoning, ban poisoning, email abuse through invitations, resource exhaustion via zone/record creation, certificate issuance abuse, PoW challenge farming) and verify the controls with tests; add missing controls.
5. Verify **privacy controls** with data-flow tests: no request bodies stored, evidence redaction, IP truncation settings, retention jobs, deletion completeness, subprocessors only as configured, and no outbound calls outside the allowlist (egress audit over a 24 h soak).
6. Perform a **dependency and image review**: SBOM diff since last review, new transitive dependencies assessment, base image CVE scan (Trivy/Grype oracle), container hardening verification.
7. Re-evaluate **residual risks** and produce the risk register update (probability/impact/owner/mitigation/acceptance), including the explicit statement of what is not covered (zero-days in the origin application, volumetric attacks beyond upstream capacity, registrar compromise, insider threats at the operator).
8. Obtain the **operator's sign-off** on residual risks (written confirmation in chat) or record outstanding items with deadlines.
**Deliverables.**
- `docs/SECURITY-REVIEW-v2.md`, risk register update, fixed findings, sign-off record
**Acceptance.**
- A1: no open critical/high finding; mediums have owners and dates.
- A2: every bypass found in the red-team exercise has a tracked task or documented acceptance.
- A3: abuse-of-features controls are verified by tests.
- A4: privacy data-flow tests pass and egress audit shows only allowlisted destinations.
- A5: operator sign-off (or UNVERIFIED(`human_step_pending`)) is recorded.
**Tests.**
- Lab pentest, exercises, automated reviews.
**Notes.** The red role must not tune detection with the held-out or red-exercise payloads until the exercise is closed.
