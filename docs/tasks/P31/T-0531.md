### T-0531 · Documentation completion: user, operator, API, architecture and security docs with freshness tests
`P31` `[DOC]` · deps: T-0459, T-0527, T-0098 · size: L · owner: docs
**Objective.** Make the documentation complete, accurate and kept honest by tests.
**Steps.**
1. Complete the **user documentation** (`docs/site/`): getting started (5-minute path), adding a domain in each integration mode with screenshots (both themes), DNS management, TLS and certificates, origin lockdown, protection modes and presets (including the Vulnerable-Origin Shield explained plainly with limits), reading events and bans, handling false positives and appeals, rate limiting and bots, notifications and integrations, reports, API and SDK, team and roles, security best practices for site owners (fix your SQLi, not only block it), billing/plans (if any), and FAQs/troubleshooting.
2. Complete the **operator documentation:** installation and deployment, profile reference (`hdd.live.yaml` fields with examples), upgrade, backup/restore, monitoring, key management, incident response, tuning, capacity, scaling out roadmap, uninstall.
3. Complete the **architecture and security docs:** `ARCHITECTURE.md` (components, data flows, trust boundaries, diagrams as SVG with text alternatives), `SECURITY.md`, threat model (`docs/STRIDE.md`), security controls reference mapping defenses to the attack matrix with evidence links, limits and known bypass classes, privacy and data-handling description (what is collected, retention, redaction), and the secure-development statement.
4. Complete **developer docs:** repository layout, build and test (`xtask`), coding standards, ADR index, how to add a detector/rule/pack/virtual patch, how to add a screen following the design system, how to add an API endpoint with contract tests, fixtures and payload policy (classes A/B/C), lab usage.
5. Implement **docs freshness tests:** every `hddctl` command referenced exists with matching flags (parsed from `--help`), every route/screen id exists, every configuration key appears in the profile schema, every metric/alert name exists, every screenshot is generated by the e2e suite (no stale images; hash recorded), every command sample executes in the docs test harness; `xtask docs-test` is part of verify.
6. Implement **docs accessibility and quality:** link checker, spelling and style lint (Vale-style rules for plain language, no forbidden claims), heading structure, image alt text, code block language labels, reading level target, and printable PDF export of the operator guide through the PDF pipeline.
7. Build the **spec assembly**: `docs/SPEC.md` (this specification as shipped) with the `docs/spec/` split and `xtask spec` checks that the generated task index matches the task blocks.
8. Run a **documentation walkthrough**: a fresh reader follows the quick start on a clean pilot environment using only the docs; record friction points and fix them; repeat for the operator install guide on a VM.
**Deliverables.**
- complete docs set, freshness tests, walkthrough report
**Acceptance.**
- A1: `xtask docs-test` passes (commands, routes, metrics, config keys, screenshots all resolve).
- A2: no unqualified protection claims anywhere in docs (claims-lint).
- A3: the quick start works end to end on a clean environment without undocumented steps.
- A4: the operator guide supports a clean VM install following the docs only.
- A5: every acceptance criterion is documented with how to run it.
**Tests.**
- Docs tests, walkthroughs, link/lint checks.
**Notes.** Documentation is a product surface; stale docs are failing tests.
