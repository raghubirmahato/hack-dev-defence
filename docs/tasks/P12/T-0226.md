### T-0226 · Exceptions manager (S-064)
`P12` `[UI][API][SEC]` · deps: T-0237 · size: M · owner: api
**Objective.** Resolve false positives with scoped, expiring exceptions instead of weakening rules.
**Steps.**
1. Define the exception model: rule reference (rule ID, category/subtype, or "any soft score"), scope (path pattern, methods, parameter name/vector, optional CIDR), mandatory reason (10 to 500 chars), mandatory expiry (maximum 90 days, default 14), created from event (link) or manually.
2. Implement validation: exceptions cannot target hard SQLi/RCE families globally; they must be scoped to a path and parameter (`ERR-WAF-005` family for missing expiry/scope); a hard-hit exception on an auth endpoint is refused unless the owner acknowledges the risk with a typed confirmation.
3. Implement creation from the event drawer (S-066) with prefilled scope from the event (vector, field name, normalized path) and a preview of how many past events would have been excepted.
4. Implement the list with hits since creation, expiry countdown, and renewal flow (requires a new reason).
5. Implement expiry job with notifications 3 days before and on expiry.
6. Implement audit events and revision creation.
7. Implement the engine contract: exceptions compile into the snapshot as a sorted structure consumed by the scoring stage (P13).
8. Add tests for scope matching and the safeguards.
**Deliverables.**
- model, UI, job, tests
**Acceptance.**
- A1: exceptions without expiry or reason cannot be saved.
- A2: broad exceptions on hard families are refused.
- A3: the preview count equals the actual number of matching past events (test with seeded events).
- A4: expired exceptions stop applying within the next snapshot (test clock).
- A5: exception creation from an event pre-fills scope correctly.
**Tests.**
- Unit: scope matching; integration: expiry job; browser: creation from event.
**Notes.** Platform-published rules can only be overridden by scoped exceptions.
