### T-0225 · Auth endpoint manager: declared and detected endpoints
`P12` `[UI][API][SEC]` · deps: T-0237 · size: L · owner: api
**Objective.** Identify login, signup, reset and API-auth endpoints so stricter protection can apply.
**Steps.**
1. Define the `auth_endpoints` model (path pattern with `{param}` and `*` wildcards, methods, kind: login/signup/reset/mfa/api_auth, strict flag, source: declared/detected/profile).
2. Seed defaults from the profile `site.auth_paths` and platform presets (WordPress: `/wp-login.php`, `/xmlrpc.php`; generic: `/login`, `/signin`, `/user/login`, `/admin/login`, `/api/auth/login`, `/api/login`, `/oauth/token`, `/session`).
3. Implement **detection suggestions** from observed traffic (from event/rollup data, not request bodies): POST routes with low-cardinality paths whose response status distribution looks like authentication (401/403 vs 302/200 patterns), path names matching login words, and parameters named like passwords (name only, learned by the WAF as field names, never values).
4. Implement the UI: table of endpoints with kind, strictness, hits, 24-hour attack counts, and accept/reject controls on suggestions; edit with pattern validation and a tester ("does this URL match?").
5. Implement the effect summary ("These endpoints get stricter inspection, tighter rate limits and credential-stuffing detection") and links to S-057 and S-061.
6. Implement caps (max 100 endpoints per domain) and validation preventing overly broad patterns (`/*` is rejected unless explicitly confirmed with a warning).
7. Publish changes through the policy service and revisions.
8. Add tests for pattern matching semantics shared with the proxy matcher.
**Deliverables.**
- model, matcher library, UI, tests
**Acceptance.**
- A1: the matcher semantics are identical in the control plane tester and the data plane (shared crate, property tests).
- A2: suggestions never use request body values.
- A3: broad patterns require an explicit confirmation.
- A4: changes appear in the next snapshot revision.
- A5: WordPress defaults are applied when `site.platform=wordpress`.
**Tests.**
- Unit: matcher table tests and proptest; browser: table and tester; integration: suggestion generation from seeded events.
**Notes.** The strict profile behavior is implemented in T-0274 and T-0343.

## Definition of done for this task's tags (section 0.7)

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.

### `[SEC]`: Security-relevant logic

Abuse cases written as tests; STRIDE delta in `docs/STRIDE.md`; no secret in logs; constant-time comparison where secrets are compared; failure modes fail closed; panic-free on hostile input (proptest or fuzz target).
