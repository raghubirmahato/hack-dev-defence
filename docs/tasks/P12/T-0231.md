### T-0231 · Bots and challenge screen (S-062)
`P12` `[UI][API]` · deps: T-0237 · size: L · owner: ui
**Objective.** Let owners set policy per bot class and manage the challenge.
**Steps.**
1. Implement the class policy table (human-likely, unknown, automation-suspected, scanner, malicious, verified bot) with actions (allow, log, challenge, block, block and ban) and defaults per preset, with explanations and 7-day counts per class.
2. Implement verified bot management: enable search-engine allow with FCrDNS verification, additional bot entries (name, UA pattern, rDNS suffixes), and a test tool that checks an IP/UA against the verification logic (read-only).
3. Implement challenge settings: difficulty mode (auto adaptive or fixed bits within bounds), clearance duration (5 min to 24 h), path scoping (apply to all, only auth endpoints, only specific paths), and a preview of the challenge page.
4. Implement under-attack mode control (manual enable with duration, automatic triggers from shield signals, auto-disable) with consequences copy.
5. Implement reputation policies (Tor, VPN/proxy, datacenter ASN, threat feeds, local reputation threshold) with per-source action selects and explanations of false-positive risk.
6. Implement scraping protection options (aggressive crawl detection thresholds).
7. Publish through the policy service; audit events.
8. Add tests for constraints (scanner class cannot be set to allow under Paranoid).
**Deliverables.**
- screen, API, tests
**Acceptance.**
- A1: class policies persist and compile into the snapshot.
- A2: verified-bot test tool never performs requests to the tested IP (DNS lookups only).
- A3: challenge preview matches the real challenge page template.
- A4: constraints under Paranoid are enforced and explained.
- A5: under-attack mode shows its end time and auto-disables.
**Tests.**
- Unit: policy validation; browser flows; integration: snapshot publication.
**Notes.** Engines: T-0337 to T-0350.

## Definition of done for this task's tags (section 0.7)

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.
