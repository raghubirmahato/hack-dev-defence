### T-0224 · Vulnerable-Origin Shield screen (S-057) and the "Try a payload" tool
`P12` `[UI][API][SEC]` · deps: T-0237, T-0225, T-0260 · size: XL · owner: ui
**Objective.** Make the shield understandable and testable without risk.
**Steps.**
1. Implement the nine regions of B12.2: explainer, master toggle with strictness, ban behavior panel, auth endpoints table, SQL injection subtype panel, learned shapes, try-a-payload box, outbound link, limits statement.
2. Implement the ban behavior panel: "Ban on first clear attack" toggle (default on), TTL ladder editor (validated, capped), explanation of cross-site handling ("requests from other websites' pages block but do not ban"), the shared-address option (challenge instead of ban), and the attack-diversity ban toggle.
3. Implement the SQL injection subtype panel: toggles per subtype with counts from the last 7 days and examples of what each blocks (benign descriptions, no exploit instructions); constraints under Paranoid (cannot disable all).
4. Implement the **Try a payload** tool: a textarea, vector selector (query, form field, JSON field, cookie, header, path), field-name input with field-kind inference preview, and Submit; it calls the dry-run inspect endpoint and displays verdict (blocked/passed), category, subtype, rule ID (for the owner only), score, "would ban" with the TTL step, and the evidence span; includes quick-fill buttons for the six mandated payloads and note that nothing is sent to the origin.
5. Implement the comparison to the current mode: if the domain is in monitor mode, show "In block mode this would be blocked and the IP banned".
6. Implement rate limiting of the tool (30 per minute per user) and size limits (4 KB), with no storage of tested payloads except an audit event with a hash.
7. Implement the strictness switch effects preview (diff of what Paranoid adds) and the preset interplay.
8. Add tests across the six mandated payloads and benign samples.
**Deliverables.**
- screen, tool endpoints, tests
**Acceptance.**
- A1: all six mandated payloads show `blocked` with category SQL injection and would-ban in block mode (dry run through the real engine from P14 onward; before that the tool shows a clear "detector not yet deployed" state).
- A2: benign samples (O'Brien, normal prose) show passed.
- A3: tool inputs are never forwarded or stored beyond a hash in audit.
- A4: the screen explains limits using the approved copy and links to S-003.
- A5: the screen passes axe, keyboard and reflow checks.
**Tests.**
- Browser flows; integration with the inspect API; unit: field-kind preview; security: rate-limit and size-cap tests.
**Notes.** This is the screen that answers the user story "even if my login is vulnerable, will it block `admin' --`?".

## Definition of done for this task's tags (section 0.7)

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.

### `[SEC]`: Security-relevant logic

Abuse cases written as tests; STRIDE delta in `docs/STRIDE.md`; no secret in logs; constant-time comparison where secrets are compared; failure modes fail closed; panic-free on hostile input (proptest or fuzz target).
