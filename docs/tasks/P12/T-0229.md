### T-0229 · Rule dry-run and baseline replay (S-060)
`P12` `[UI][API][DP]` · deps: T-0228, T-0254 · size: L · owner: waf
**Objective.** Show the effect of a rule on recent real traffic before activation.
**Steps.**
1. Define the replay data source: recent events and sampled request metadata stored by the data plane (a bounded, privacy-preserving **traffic sample** of request metadata only: method, path, normalized parameter names and kinds, headers subset, client IP key, country; no bodies or values), with sampling rate and retention (24 h) configured per domain and clearly disclosed.
2. Implement the dry-run engine: evaluate the proposed rule (alone and combined with the current rule set) over the sample using the pure engine, producing counts of matches, affected IPs/paths, and false-positive candidates (matches on requests that originally returned 2xx/3xx and were not flagged by other detections).
3. Implement known-good probe evaluation: the domain's configured known-good requests (from HAR/crawl in the profile for the operator's domains, or user-declared probe URLs) must all pass; any block is shown prominently and prevents activation in `block` mode.
4. Present results: summary, top affected paths/IPs/ASNs, sample rows with redacted metadata, comparison against the current behavior, and a recommendation (activate in log mode / not recommended).
5. Implement limits (sample size, run time budget 5 s, concurrency) and background job fallback for large samples.
6. Implement the API and the activation flow integration (the rule builder links to the dry-run, and activation requires a fresh dry-run for `block`/`ban` actions).
7. Add tests with synthetic-but-real-pipeline samples (generated through the proxy test harness).
8. Document the privacy model of the traffic sample.
**Deliverables.**
- dry-run service, sampling contract, UI, tests, docs
**Acceptance.**
- A1: a rule matching known-good probes is flagged and blocked from activation.
- A2: dry-run results are reproducible for a fixed sample.
- A3: the traffic sample contains no request bodies or parameter values (schema test).
- A4: activation of a blocking rule requires a dry-run less than 15 minutes old.
- A5: runs are bounded in time and memory.
**Tests.**
- Unit: evaluation over samples; integration: sample ingestion and replay; privacy schema test.
**Notes.** The sample is also the base for the automatic-rollback probes (T-0371).

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.
