### T-0230 · Rate limiting screen (S-061) and rule model
`P12` `[UI][API]` · deps: T-0237, T-0225 · size: L · owner: ui
**Objective.** Let owners define rate limits that protect logins and expensive endpoints without harming users.
**Steps.**
1. Define the `rate_limit_rules` model (name, scope: ip, ip+path, session, ASN, fingerprint, api key; path pattern; methods; limit; window; action: 429, challenge, ban after N violations; burst allowance; enabled) and the default rule (60 requests per 10 s per IP per domain).
2. Implement presets: "Login protection" (applies to declared auth endpoints: 10/min per IP per path Balanced, 5/min Paranoid, with progressive ban), "API", "Search", "Contact/signup forms", "Expensive exports"; each previews the generated rules.
3. Implement the rule table, editor with validation (minimum window 1 s, maximum 1 h, limit bounds), and consequences panel (what a legitimate user sees, 429 page with `Retry-After`, shared-IP risk).
4. Implement a **burst test helper**: generates a copyable `curl` loop limited to the owner's own domain and canary path guidance (no HDD-originated load on tenant domains), and a "simulate" mode that computes from historical rollups how many requests would have been limited.
5. Implement conflicts (overlapping rules) detection and precedence explanation (most specific path wins, then lowest limit).
6. Implement quotas by plan and audit events.
7. Publish through the policy service and revisions.
8. Add tests for validation and the simulation.
**Deliverables.**
- model, UI, simulation, tests
**Acceptance.**
- A1: presets generate exactly the documented rules (golden tests).
- A2: simulation results match recomputation from seeded rollups.
- A3: no feature generates traffic to tenant domains from HDD.
- A4: overlap detection explains precedence.
- A5: screen passes axe and keyboard checks.
**Tests.**
- Unit: validation and simulation; browser: preset application; integration: snapshot publication.
**Notes.** The limiter itself is T-0333.
