### T-0227 · Rules list screen (S-058) and rule model
`P12` `[UI][API]` · deps: T-0237, T-0049 · size: M · owner: ui
**Objective.** Manage custom rules in priority order with clear status.
**Steps.**
1. Define the rule model (match tree, action, scope, priority, enabled, expiry, description, source: custom/pack/virtual patch, revision, hits cached) and priorities (lower number first; unique per domain; gaps allowed).
2. Implement the list with priority order, enable toggles, hits in 24 h/7 d, last hit time, action pills, status (active, disabled, expired, rolled back, read-only pack rule), and filters.
3. Implement reordering via move up/down buttons and an optional pointer drag, posting the full ordered list to `POST D/security/rules:reorder` with optimistic concurrency; show a diff of precedence changes before saving for rules whose order changes outcomes.
4. Implement bulk enable/disable/delete with confirmation, and export/import as JSON with validation preview.
5. Implement platform-pack rules display (read-only, with pack and version, how to override via exceptions).
6. Implement quota guards (rules per domain by plan).
7. Implement audit events and revisions.
8. Add tests for ordering semantics and accessibility.
**Deliverables.**
- rules list, reorder API, import/export, tests
**Acceptance.**
- A1: reordering is possible without drag and announces the new position.
- A2: imports show row-level errors before commit.
- A3: pack rules are visibly read-only with explanations.
- A4: quotas are enforced with `ERR-RATE-002`.
- A5: concurrent reorders produce `ERR-CONC-001` with a recoverable UI.
**Tests.**
- Browser: reorder with keyboard; integration: concurrency; unit: import validator.
**Notes.** Rules are evaluated by priority; the first terminal action (`block`, `allow`, `ban`) wins, `log` and `challenge` semantics are documented in `docs/SCORING.md`.
