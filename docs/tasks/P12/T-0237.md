### T-0237 · Security policy document, validation, compile and versioning (execute first in P12)
`P12` `[API][DB][DP]` · deps: T-0206, T-0211 · size: XL · owner: api
**Objective.** Define the policy schema all security screens and engines share, with a single choke point for changes.
**Steps.**
1. Define the policy document schema v1 (JSON, versioned, `schemars` generated): `mode`, `preset`, `paranoia_level`, `block_threshold`, `over_limit {inspect_body_max_bytes, policy}`, `categories {id: {enabled, action}}`, `shield {...}`, `bans {ladder_s, scope, propagate_to_org, ip_v6_prefix, cgnat_challenge_instead_of_ban}`, `bots`, `challenge`, `outbound`, `headers`, `reputation`, `geo`, `learned_shapes`, `known_good_probes`, and references to separate tables (rules, exceptions, access entries, rate limits, honeypots, auth endpoints, block page).
2. Implement `PolicyService::apply(change)` as the **only** mutation path: loads the current effective document and ancillary tables, applies a typed change, validates (cross-field invariants: paranoid shield constraints, category action compatibility, quota limits, self-lockout checks), writes a new `config_revisions` row and `waf_policies` row in one transaction, increments the site revision, inserts the config outbox row, writes the audit event, and returns the diff.
3. Implement the compile step to the data-plane `SitePolicy` structure: pre-built regex automata registry references, category action table, matchers for access/honeypot/auth endpoints (shared crates), rate-limit rule table, exception structures, block page assets; compile errors fail the change without publishing.
4. Implement optimistic concurrency (`If-Match` on revision) and idempotency.
5. Implement the preset application functions and the migration framework for schema changes (document `schema` version upgrades with tested upgrade functions).
6. Implement size caps and per-plan limits; defaults for new domains.
7. Implement golden tests: preset documents equal C3.4; schema round trip; compile determinism.
8. Document the schema in `docs/POLICY.md` generated from the types.
**Deliverables.**
- `hdd-common::policy` crate module, `PolicyService`, JSON Schema, docs, tests
**Acceptance.**
- A1: every P12 mutation goes through `PolicyService` (route audit test).
- A2: invalid cross-field combinations are rejected with specific codes.
- A3: compile failure leaves the previous revision active and returns a diagnostic.
- A4: a change reaches the proxy snapshot within 2 s (integration with T-0211).
- A5: schema upgrades are tested from v1 fixtures.
**Tests.**
- Unit/golden/proptest (random valid changes keep invariants); integration with Postgres and Redis; schema stability test.
**Notes.** This service is the heart of AC-12, AC-13 and AC-16.

## Definition of done for this task's tags (section 0.7)

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.

### `[DB]`: Adds or changes schema

Expand/contract migration only; `org_id` and RLS policy for tenant-owned tables; indexes justified; `sqlx` offline data refreshed; forward migration plus restore-from-backup test; data-retention rule documented.

### `[DP]`: On the data-plane hot path (proxy, DNS, WAF, firewall)

Hot path never awaits the database; bounded memory and queues; criterion benchmark or histogram; fuzz or proptest; behavior when Redis or Postgres is down specified and tested; metric with drop counter.
