### T-0429 · Plans and quotas editor (S-116)
`P22` `[UI][API][DB]` · deps: T-0417, T-0146 · size: M · owner: web
**Objective.** Let platform owners define plans and limits, and apply them safely to tenants.
**Steps.**
1. Implement the plan list and editor: name, slug, description, visibility (public/private/internal), limits (domains, members, API keys, rules per domain, rate rules, webhooks, report schedules, custom certificates, DNS records per zone, zones, request retention days, event retention days, API requests per minute, exports per day), feature flags (e.g., `custom_block_page`, `advanced_api_protection`, `audit_export`), and the `unlimited` plan for `owner_only` mode.
2. Implement validation: monotonic constraints (a higher tier cannot have lower limits for the same item), required fields, bounds per limit type, and a preview "who is affected" (tenants on the plan, how many exceed new limits).
3. Implement changes with versioning: editing a plan creates a new version with effective date; existing tenants stay on the previous version until migrated or the change is non-reducing; reducing limits require a grace period (default 30 days) and tenant notification; limit enforcement never deletes data, it only blocks new creations and warns.
4. Implement plan assignment from tenant detail (T-0419) and bulk migration with dry-run summary.
5. Implement per-tenant overrides (expiring) with reasons and display in S-085 as "custom limit set by platform".
6. Implement the integration hooks for billing providers (Tier 2/ T-0558): fields reserved (`external_price_id`), disabled by default; no payment processing in v5.
7. Write tests: validation, versioning semantics, enforcement edge cases (exactly at limit, over limit after reduction, grace), migration dry-run accuracy, permission gating (`platform.plan.write` with step-up), audit diffs, concurrency, and a11y of the editor form.
**Deliverables.**
- API, editor UI, migration tooling, tests
**Acceptance.**
- A1: reducing a limit never deletes existing resources and blocks only new creations after the grace date.
- A2: the "affected tenants" preview matches the later effects in the fixture scenario.
- A3: tenant notifications are sent for reductions with the effective date.
- A4: version history shows diffs and actors.
- A5: owner_only mode works with only the `unlimited` plan present.
**Tests.**
- Integration, unit, browser e2e.
**Notes.** Billing is out of scope for v5 (T-0558 is optional backlog).
