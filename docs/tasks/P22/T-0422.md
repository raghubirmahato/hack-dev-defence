### T-0422 · Impersonation (S-118): read-only view-as with time box and banner
`P22` `[UI][API][SEC]` · deps: T-0419, T-0420, T-0118 · size: M · owner: sec
**Objective.** Let support see what a customer sees without being able to change anything or read sensitive data.
**Steps.**
1. Implement `POST P/impersonation` (target org + optional user, reason required, duration choice 15/30/60 minutes max 60, step-up required) creating an `impersonation_sessions` row and a derived session with scope `read_only_view_as`.
2. Implement the derived-session semantics: all non-GET requests are rejected with `ERR-PERM-003`; sensitive views (API keys, webhook secrets, TLS key material, MFA details, recovery codes, session lists, audit export, data export) are hidden or return 403; request-body-bearing data (event snippets) are masked in the same way a viewer role would see them.
3. Render a **persistent impersonation banner** on every page (not dismissible, text + icon, `role="status"`), showing the org, remaining time, reason and an "End now" button; the favicon/title prefix changes (`[View-as]`).
4. Notify the customer: an email and an in-app notification to org owners at the start and end ("A platform support person viewed your account for support, reason category X"), unless the org is under an abuse investigation flagged by `platform_admin` (suppression recorded in audit with justification; auditors can see it).
5. Record every page view during impersonation in the platform audit (route templates, not content).
6. Prevent chaining and escalation: no impersonating platform users; no impersonation of orgs by non-platform sessions; the derived session cannot start another impersonation; absolute cap of 5 impersonations per staff per day.
7. Implement the S-118 screen: start form, active sessions, history with filters, and revoke for admins.
8. Write tests: write attempt blocked (all verbs), hidden sensitive views matrix, banner presence on all templates (render test over the template registry), timeout expiry (time-injected), notification delivery, audit completeness, privilege checks, and a deliberate attempt to use the derived cookie on the API to perform a mutation.
**Deliverables.**
- impersonation service, derived session type, banner component, screen, tests
**Acceptance.**
- A1: every mutation attempt during impersonation fails with `ERR-PERM-003` (generated over all mutating routes).
- A2: the banner appears on 100% of app templates in the render test.
- A3: owners are notified at start and end, except suppressed cases which are audited.
- A4: expiry ends the session within 5 s of the deadline.
- A5: sensitive views are inaccessible (matrix).
**Tests.**
- Route-registry generated test; integration; browser e2e.
**Notes.** Impersonation is a privacy-sensitive power; the product docs describe it plainly (T-0098/T-0101).
