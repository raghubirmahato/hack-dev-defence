### T-0426 · Threat-intel feeds management (S-108)
`P22` `[UI][API][OPS]` · deps: T-0417, T-0348 · size: M · owner: web
**Objective.** Operate the feeds that populate reputation and blocklists with transparency and bounded risk.
**Steps.**
1. Implement the feeds list: name, type (IP blocklist, Tor exit list, datacenter ranges, ASN list, verified-bot ranges, disposable-email domains, CVE/KEV data), URL host (full URL only for staff with `platform.intel.write`), schedule, last success/failure, entries count, size, age, expiry policy, license note, and status (`ok`, `stale`, `failing`, `disabled`).
2. Implement create/edit/delete/refresh: URL must pass the egress allowlist (HTTPS only, hosts allowlisted by the operator, size limit 50 MB, timeout 30 s), parser selection with sample preview (first 20 parsed entries and rejected lines count), validation of entry classes (a feed may not contain private/reserved ranges, `admin_cidrs`, the runner IP or egress IPs; offending lines are dropped and counted).
3. Implement safety valves: a feed update that would change more than 30% of its entries or exceed the max entries (default 500,000) is held for review (not applied) and an alert is raised; poisoning protection prevents feed entries from creating bans directly (feeds only influence scores and optional challenge actions; a feed-origin ban requires the "feed may ban" flag with `platform_owner` approval and a /32 limit).
4. Implement per-feed metrics and history chart (entries over time, failures), with links to the effects (how many requests were scored by the feed in the last 24 h, counts only).
5. Implement licensing/attribution fields and a UI notice when a feed's license requires attribution; export the attributions to the public docs page via the sub-processor/attribution list.
6. Implement offline mode (file import) for airgapped installations, with checksum and signature options.
7. Write tests: parser fixtures (CSV, line-delimited, JSON, CIDR lists), unsafe-entry filtering, hold-for-review logic, SSRF/egress allowlist enforcement, scheduling and retries with jitter, permission gating, and XSS in feed names.
**Deliverables.**
- API, screen, parsers, tests
**Acceptance.**
- A1: entries covering private ranges, admin CIDRs or the runner are dropped and counted in 100% of fixtures.
- A2: a large change is held and not applied until approved.
- A3: a feed host not in the egress allowlist cannot be saved.
- A4: feed-origin bans are impossible without the explicit flag and approval.
- A5: failures raise alerts after 3 consecutive errors.
**Tests.**
- Unit, integration with a local feed server, browser e2e.
**Notes.** Feeds are data, never instructions (C12.3).

## Definition of done for this task's tags (section 0.7)

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.

### `[OPS]`: Deployment, operations, runbooks

Idempotent; dry-run mode; documented undo; SSH-lockout protection for host-affecting changes; restore or rollback exercised.
