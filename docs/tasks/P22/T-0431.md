### T-0431 · System settings (S-119): SMTP, branding, legal links, retention defaults and secrets handling
`P22` `[UI][API][SEC]` · deps: T-0417, T-0109, T-0101 · size: M · owner: web
**Objective.** Configure platform-wide behavior safely from the UI with secrets handled correctly.
**Steps.**
1. Implement settings sections: Mail (SMTP host, port, TLS mode, username, password write-only, from address and name, reply-to, DKIM selector info, test send), Branding (product name displayed in emails/pages, logo upload with type and size checks and sanitization, accent color from the allowed token set), Legal (links to terms, privacy, AUP, DPA pages and their effective dates, with the rule that publishing legal text requires the operator's explicit confirmation), Retention defaults (events, rollups, audit, notifications, session history) with minimums and plan overrides, Security (HIBP/k-anonymity password check endpoint toggle, IP truncation default, password policy minimums), Surfaces (hostnames, read-only reflection of the profile), Integrations (CT service URL allowlist, external uptime heartbeat URL, alert email recipients).
2. Implement secrets handling: values stored with envelope encryption, never returned by the API (only `set: true` and a fingerprint), changed through replace-only fields, and rotation timestamps displayed; a failed decryption is a visible error state, not a silent default.
3. Implement validation of every field (hostnames via the egress allowlist rules, ports, email addresses, URL schemes) and a **dry-run test** for SMTP: test send to a platform-owner-confirmed address with step-by-step diagnostics (DNS, connect, STARTTLS, auth, send), with no secret leakage in diagnostics.
4. Implement settings versioning: every change creates a `settings_revisions` row (diff without secrets), a rollback action for non-secret fields, and step-up requirement for changes flagged sensitive (SMTP, legal, security).
5. Implement the **claims guard**: branding and legal text fields are scanned by claims-lint at save for forbidden phrases (e.g., "unhackable"), and violations are rejected with an explanation.
6. Implement email deliverability helper cards: SPF/DKIM/DMARC status of the sending domain (DNS lookups), with instructions (AC-46 ties in).
7. Write tests: secret non-disclosure (schema + grep), validation matrix, SMTP diagnostics against a local SMTP server with failure modes, revision history, rollback semantics, claims-lint integration, upload sanitization (SVG/PNG polyglots rejected), permission gating (`platform.settings.write`), and a11y.
**Deliverables.**
- API, UI, revisions, SMTP diagnostics, tests
**Acceptance.**
- A1: no API response, log or audit diff contains a secret value (fuzzed grep over 1,000 saves).
- A2: SMTP diagnostics report each stage and succeed against a TLS-enabled local server.
- A3: logo uploads reject polyglot and oversized files and serve with `nosniff` from the asset domain.
- A4: rollback of non-secret settings restores prior behavior.
- A5: claims-lint rejects forbidden phrases in branding/legal fields.
**Tests.**
- Integration, security tests, browser e2e.
**Notes.** Legal pages ship as templates marked "operator must review"; this screen does not generate legal advice.
