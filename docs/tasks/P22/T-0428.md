### T-0428 · Abuse reports (S-114) and signup policy (S-115)
`P22` `[UI][API][SEC]` · deps: T-0417, T-0102, T-0108 · size: L · owner: web
**Objective.** Handle abuse intake and control who can sign up, with friction proportional to risk.
**Steps.**
1. Implement the abuse report intake pipeline (public form S-009 and email-to-form): fields (reported hostname/URL, category: phishing, malware, spam, copyright, illegal content, attack source, other; description; reporter contact optional), anti-abuse (PoW, rate limits, duplicate detection by hostname + category), storage with privacy controls, auto-acknowledgement email with a reference.
2. Implement S-114 triage: queue with filters (status, category, age, hostname), assignment, SLA timers (acknowledge 24 h, resolve 7 d configurable), detail view with linked tenant/domain (when the hostname is a protected domain), evidence attachments (text and screenshots up to 2 MB each, scanned for type and stored as inert files), actions (request clarification, notify owner with a template, suspend domain (T-0421), suspend tenant (T-0423), dismiss with reason, escalate), timeline of changes.
3. Implement outcome communication: owner notices with category and required action deadline, reporter notice optional (no personal data of the owner disclosed), appeals from owners handled via normal support.
4. Implement S-115 signup policy: modes (`open`, `invite_only`, `allowlist_domains`, `closed`), disposable-email handling (`block`/`challenge`/`allow`) with list management (import, add/remove, source/license), allowed/blocked email domain lists, per-IP and per-subnet signup rate limits, proof-of-work difficulty, verification requirements (email verification before first domain), new-account friction tiers (limits on domains, challenge on first domain, probation period of 7 days for new accounts with reduced quotas), country/ASN risk rules (optional, off by default, explained), and a **signup freeze** switch shown in S-122.
5. Implement abuse heuristics feeding the policy: accounts adding many domains quickly, domains with phishing-like names (brand lookalike detection against a configurable brand list, similarity metric documented), tenants whose origins match known-bad feeds; heuristics produce reviews, never auto-suspensions in v5.
6. Provide the audit for every policy change (before/after diff) with step-up for changes that loosen policy.
7. Write tests: intake validation and rate limits, duplicate collapse, SLA timers (time-injected), state machine of reports, policy evaluation matrix (≥ 80 cases across modes and lists), disposable list import/license fields, lookalike detector fixtures (including IDN homographs), permission matrix.
**Deliverables.**
- intake pipeline, triage UI, policy UI, evaluator, tests
**Acceptance.**
- A1: a report on a protected domain links to the correct tenant and offers suspend actions with reasons.
- A2: policy changes that loosen controls require step-up and are audited.
- A3: the evaluator matrix passes; blocked disposable domains cannot sign up even via API.
- A4: lookalike detection flags the fixture brand-lookalike set without flagging benign domains.
- A5: SLA breach raises attention items.
**Tests.**
- Integration, unit matrix, browser e2e, fixtures.
**Notes.** The abuse workflow is also the DMCA-style process; legal text lives in S-011/S-013 and is reviewed by the operator.

## Definition of done for this task's tags (section 0.7)

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.

### `[SEC]`: Security-relevant logic

Abuse cases written as tests; STRIDE delta in `docs/STRIDE.md`; no secret in logs; constant-time comparison where secrets are compared; failure modes fail closed; panic-free on hostile input (proptest or fuzz target).
