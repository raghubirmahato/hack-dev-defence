### T-0423 · Tenant lifecycle: suspend, delete with grace, data export hold and purge
`P22` `[API][DB][SEC][OPS]` · deps: T-0419, T-0130, T-0421 · size: L · owner: api
**Objective.** Make every way a tenant can end or be stopped safe, reversible where it should be, and complete in data handling.
**Steps.**
1. Define the tenant state machine: `active → suspended → active` (reversible), `active/suspended → deletion_scheduled (grace 14 days) → deleting → deleted`, with `legal_hold` as an orthogonal flag blocking deletion. Document legal effects and customer-visible messages.
2. Implement suspend semantics: sign-in allowed for read-only access to export data (configurable), all domains switch to the neutral suspended page (S-148), DNS continues serving unless the reason is DNS abuse (admin choice), API keys return `ERR-TENANT-001`, ACME renewals pause, notifications continue to owners, webhook deliveries pause.
3. Implement deletion scheduling by org owner (typed confirmation, step-up, owner transfer prerequisite) or by platform (reason, step-up): 14-day grace, daily reminder emails (3 times), cancellation by owner at any time in grace, immediate effects on traffic only if the domains are removed by the owner first (the wizard warns about traffic impact and offers decommission guidance: revert DNS before deletion).
4. Implement the purge job: after grace, delete domain-scoped data in dependency order (events, bans, rules, DNS records and zones, certificates and keys (secure erase of key material), analytics rollups, API keys, webhooks, invitations, members), anonymize audit references (keep hashed identifiers for the chain), delete user accounts that have no other membership after their own grace, and emit a signed deletion receipt (JSON with counts, no content).
5. Implement DNS zone cool-down interplay (T-0399: apex reserved 24 h) and NS pair release.
6. Implement data export for owners before deletion (T-0130 reuse) and a platform-initiated export for legal requests with `platform_owner` approval and audit.
7. Implement backups and deletion: document that backups age out within the retention period (30 days default) and that restores must re-apply the deletion ledger (a `deletion_ledger` table replayed after any restore; restore drill test T-0435/T-0436 verifies this).
8. Implement abuse-driven immediate suspension path with a post-hoc review queue and a customer appeal contact.
9. Write tests: all transitions including illegal ones, grace cancellation, purge completeness (a table-scanner test asserts zero rows containing the org id across all tables after purge, except the ledger/receipt), key erasure verification, restore + ledger replay, legal hold block, and email timeline.
**Deliverables.**
- lifecycle service, jobs, API, UI flows, receipts, tests, docs
**Acceptance.**
- A1: after purge, the scanner test finds zero org-scoped rows except the deletion receipt and ledger.
- A2: deletion cannot start without owner transfer or typed confirmation; platform deletion requires step-up and reason.
- A3: restore from backup replays the ledger and the tenant stays deleted (drill).
- A4: suspended orgs serve S-148 within 2 s and send no origin traffic.
- A5: certificate private keys of deleted tenants are unrecoverable (store scan).
**Tests.**
- Integration with the real database; scanner test across all tables; drill; browser e2e.
**Notes.** AC-42 verifies the lifecycle end to end including data deletion and receipts.
