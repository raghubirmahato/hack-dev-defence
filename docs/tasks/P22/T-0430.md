### T-0430 · Platform audit (S-117): filters, chain verification and export
`P22` `[UI][API][SEC]` · deps: T-0417, T-0131, T-0147 · size: M · owner: web
**Objective.** Make the platform audit trail searchable, verifiable and exportable without becoming a data leak.
**Steps.**
1. Implement `GET P/audit` with filters (time range, actor, actor role, org, event type from the AUD-* catalog, outcome, resource id, IP /24, reason text contains), cursor pagination and saved filters; results show event, actor, target, outcome, and a diff viewer for before/after (secrets redacted).
2. Implement the **chain verification** UI: shows the last verified position, verification result, and a "Verify now" action (runs `GET P/audit/verify`, which recomputes hashes from a given range, bounded by time); a failure displays the first inconsistent sequence number and raises a critical alert; the verification also compares against the externally stored chain anchors (daily anchor hash written to an append-only file and optionally e-mailed to `platform_owner`).
3. Implement export: `POST P/audit/export` (JSON Lines/CSV), asynchronous with job status, size cap, signed manifest with SHA-256 and chain proof (first/last hash), expiry of the download link (24 h), and audit of the export itself.
4. Implement role-specific views: `platform_auditor` sees all audit but no other admin data; org-level audit events for tenants are visible to platform staff only in redacted form (no member emails, no request details) unless the viewer holds support permission with a reason.
5. Implement retention controls (default 400 days, minimum 180) with monthly partitioning and archival to compressed files with chain continuity (archival does not break verification; archived segments carry their anchors).
6. Implement alerting on suspicious audit patterns: many failed step-ups, impersonation volume, bulk exports, jail removals outside business hours (configurable), changes to never-ban entries, signup policy loosening.
7. Write tests: hash-chain integrity under concurrent writers, tamper detection (modify a row, delete a row, reorder rows) in a test database, export manifest verification, filter correctness, pagination under inserts, retention archival with verification, role-based redaction, and performance (10 million events: filtered query ≤ 500 ms with indexes).
**Deliverables.**
- API, UI, verification tooling (`hddctl audit verify` parity), export job, tests
**Acceptance.**
- A1: any tampering with a stored audit row is detected by verification (three tamper cases).
- A2: exports are signed (manifest) and verification of an export passes offline with `hddctl audit verify-export`.
- A3: auditor role sees no non-audit admin screens.
- A4: archival keeps verification passing across segments.
- A5: suspicious-pattern alerts fire in the simulation.
**Tests.**
- Integration, tamper tests, performance, browser e2e.
**Notes.** The audit log is itself a sensitive dataset; exports are rate limited and logged.
