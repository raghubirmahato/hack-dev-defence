### T-0438 · Support lookup (S-130): Ray ID, IP, domain and user timelines with privacy limits
`P22` `[UI][API][SEC]` · deps: T-0417, T-0329, T-0420 · size: M · owner: web
**Objective.** Help support answer "why was I blocked" and "what happened to my site" quickly, with minimal data exposure.
**Steps.**
1. Implement lookups: by Ray ID (`GET P/support/ray/{ray}`), by IP (`/ip/{ip}`), by domain name (`/domain/{name}`) and by user email (`/user?email=`), each requiring a `reason` header (min 10 chars) logged in the platform audit and shown to the user in a confirmation dialog ("This lookup will be recorded").
2. Define the result shapes with strict field limits: Ray ID lookup returns the event (time, host, path template, verdict, category, rule ids visible to platform staff only, ban state, appeal state) without bodies or full cookies; IP lookup returns the ban status across orgs (counts, not tenant names unless the viewer has `platform.tenant.read`), global jail membership, reputation summary, recent categories; domain lookup returns state, mode, recent attention items, certificate status, recent blocks summary; user lookup returns membership and security events (reusing T-0420 masks).
3. Implement **timeline assembly**: merge events, bans, appeals, rule changes, and configuration revisions relevant to the lookup into a chronological view with filters and "copy as support note" (text with no sensitive details).
4. Implement a "Why was this blocked?" explanation generator for platform staff: shows the rule ids and scoring components that led to the verdict, the evidence snippet (redacted, ≤ 512 B), and suggested next actions (create tenant exception request, report false positive to rules team, unban); the *visitor-facing* pages remain free of rule names.
5. Implement safe actions from the lookup: create a global unban (via jail screen rules), create an exception proposal for the tenant (message to owners, never auto-applied), open a false-positive ticket (stored locally with a rule id and fixture hash for the rules team to build regression tests).
6. Implement abuse controls: rate limits per staff (60 lookups/h), alerts on bulk lookups, and mandatory second reason for IP lookups of addresses with tenant-specific context.
7. Write tests: reason requirement, redaction, field-limit schema tests, cross-tenant leak tests (support cannot learn tenant names from IP lookup unless permitted), timeline correctness against seeded data, rate limits, and a11y.
**Deliverables.**
- API, UI, explanation generator, tests
**Acceptance.**
- A1: no lookup works without a reason; every lookup appears in the audit with the reason.
- A2: IP lookup responses contain no tenant identifiers for roles lacking `platform.tenant.read` (schema test).
- A3: the "why blocked" explanation matches the stored verdict components for 100 seeded events.
- A4: the false-positive ticket stores the fixture hash and rule id, with no request content.
- A5: bulk lookup alerts fire in the simulation.
**Tests.**
- Integration, schema, browser e2e.
**Notes.** The explanation view is staff-only; visitors and tenants see only what S-140 and their own event views allow.
