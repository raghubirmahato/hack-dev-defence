### T-0420 · Users list and user detail (S-103, S-104)
`P22` `[UI][API][SEC]` · deps: T-0417, T-0123, T-0121 · size: M · owner: web
**Objective.** Support account issues safely, with minimal personal data exposure.
**Steps.**
1. Implement `GET P/users` supporting lookup by exact email (the server computes the HMAC email hash and queries by hash; the typed value is never logged), by `usr_` id, or by org membership; the list shows masked emails (`m***@example.com`) and status (active, locked, unverified, deleted-pending) unless the viewer has `platform.support` and enters a reason, which reveals the full email for that session view only and writes an audit event.
2. Implement user detail (S-104): profile (name, locale), memberships (org, role, joined), security events (last 50 sign-ins with masked IP /24, outcome, device label), MFA state (TOTP enrolled, passkeys count, recovery codes remaining — counts only), active sessions list (device, last seen, coarse location class) with revoke, and account flags.
3. Implement actions with reasons and step-up: lock/unlock account (T-0123 semantics), revoke all sessions, require MFA re-enrollment at next login, resend verification email, trigger password reset email (never set or view passwords), and anonymize on deletion request completion (flow in T-0423). MFA removal is not available in the UI (hddctl only).
4. Implement "contact-safe" email actions: the UI shows the email preview that would be sent to the user for any action that notifies them.
5. Enforce that platform users (staff accounts) are visible only to `platform_owner` (the staff screen), and that staff accounts cannot be locked by lower roles.
6. Implement abuse guards: lookups are rate limited (30/min per staff), enumeration attempts (e.g., 100 distinct emails in 10 minutes) raise a `staff_enumeration` audit alert.
7. Add the "recent actions on this user" timeline from the platform audit.
8. Write tests: masking, hash lookup correctness, reason requirement, role matrix, rate limits and enumeration alert, XSS-safe rendering of names, no email leakage in logs (grep), deletion pending state display, and a11y.
**Deliverables.**
- API, screens, tests
**Acceptance.**
- A1: no log, metric or error contains a plaintext email typed in the lookup field.
- A2: unmasking requires a reason, is audited and is limited to the view.
- A3: staff accounts cannot be modified by `platform_admin` or `platform_support`.
- A4: all actions require the specified permission and step-up where flagged.
- A5: the enumeration alert fires in the abuse simulation.
**Tests.**
- Integration; log greps; browser e2e; rate-limit tests.
**Notes.** Platform-staff management lives in a small `P/staff` screen under Platform settings (owner only).

## Definition of done for this task's tags (section 0.7)

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.

### `[SEC]`: Security-relevant logic

Abuse cases written as tests; STRIDE delta in `docs/STRIDE.md`; no secret in logs; constant-time comparison where secrets are compared; failure modes fail closed; panic-free on hostile input (proptest or fuzz target).
