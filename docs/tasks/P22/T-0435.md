### T-0435 · Releases and updates (S-123) and backups and restore drills (S-124)
`P22` `[UI][API][OPS]` · deps: T-0417, T-0427 · size: L · owner: ops
**Objective.** Operate upgrades and backups from the console with verification and rollback built in.
**Steps.**
1. Implement S-123 releases: installed versions per component and node, available versions (from a signed release manifest fetched via the egress client from the pinned release host or imported offline), release notes, signature and SBOM verification results (cosign verification output summary), migration plan (database migrations that will run, reversible or not), and compatibility checks (minimum previous version, config schema changes).
2. Implement the upgrade workflow: pre-flight (health, backups recent, disk space, no active emergency), stage new binaries beside old (`hddctl upgrade --stage`), run migrations with the expand/contract pattern, health checks, atomic switch, automatic rollback on failure, post-upgrade smoke tests; the UI displays the steps and logs live (SSE), requires step-up and a typed confirmation, and refuses unsigned artifacts.
3. Implement the rollback action (previous version retained; DB migrations rolled back only when marked reversible; otherwise the UI explains the forward-only constraint and the restore path).
4. Implement S-124 backups: schedules (daily full, 15-minute WAL archiving if configured), destinations (local path, S3-compatible with encryption, SFTP), encryption (age/gpg-style envelope with a key not stored with the backup), retention, last result, size trend, verification status; backup includes Postgres, secrets (separately encrypted), certificates store, config, DNS snapshot, ledger of deletions.
5. Implement **restore drills**: run a restore into an isolated scratch instance (compose profile `drill`), verify integrity (row counts, audit chain verification, certificate decryption test, a DNS answer check), record RTO/RPO measured and results; failing drills raise attention items; drill history is displayed.
6. Implement safety: backups never include `hdd.live.yaml` secrets in plaintext; restore into the live system is CLI-only (`hddctl restore`), requires maintenance mode and a typed confirmation, and replays the deletion ledger.
7. Implement alerts: backup stale (> 26 h), drill stale (> 35 days), upgrade available (info), signature failure (critical).
8. Write tests: signature verification (valid/invalid), upgrade state machine with injected failures at each step, automatic rollback, migration reversibility labeling, backup encryption/decryption roundtrip, drill pipeline in CI with a small dataset, ledger replay, permission gating (`platform.release` for owner only, `platform.backup`), and UI flows.
**Deliverables.**
- API, UI, workflows, drill tooling, tests, runbooks
**Acceptance.**
- A1: an unsigned or tampered artifact is refused in the UI and CLI (negative tests).
- A2: an injected failure at each upgrade step triggers automatic rollback to a healthy state (7 failure points tested).
- A3: restore drill reports measured RTO/RPO and verifies audit chain and certificate decryption.
- A4: backups are encrypted and the plaintext secrets scan finds nothing.
- A5: alerts fire for stale backups and drills.
**Tests.**
- Integration with the lab (compose), failure injection, browser e2e.
**Notes.** AC-54 (backups, restore, upgrade, disaster recovery) and AC-33 (signed updates) are completed in P28/P30; the UI here depends on tooling from P30 and ships with simulated manifests in tests only.

## Definition of done for this task's tags (section 0.7)

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.

### `[OPS]`: Deployment, operations, runbooks

Idempotent; dry-run mode; documented undo; SSH-lockout protection for host-affecting changes; restore or rollback exercised.
