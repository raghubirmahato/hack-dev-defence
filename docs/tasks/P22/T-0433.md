### T-0433 · Announcements (S-129), feature flags and maintenance mode (S-121)
`P22` `[UI][API]` · deps: T-0417, T-0149, T-0431 · size: M · owner: web
**Objective.** Communicate with users and control platform behavior without deployments.
**Steps.**
1. Implement announcements: compose (title, body markdown-lite sanitized, severity info/warn/critical, audience: all, org plan, specific orgs, admin surface), schedule (start/end, time zone aware), dismissibility rules (critical not dismissible), preview in the app shell (both themes), and display in the app banner area built in T-0149; announcement history and edit with revision notes.
2. Implement feature flags: key, description, type (boolean/percentage/org-list), default, environments, owner, expiry (flags must have an expiry or a justification "permanent"), a read-only evaluation endpoint for the app, and a check that removes stale flags (alert after expiry); changing a flag that affects security behavior requires step-up.
3. Implement maintenance mode: scope (app surface only, API read-only, full), message with ETA, allowlist of operator CIDRs, behavior (maintenance never affects the data plane: protected sites keep being proxied; only the control-plane surfaces are affected), time-boxed with auto-end and a banner on all surfaces; status page integration (T-0100) shows maintenance.
4. Implement the public status banner for incidents reuse (only operators can post; plain text; time-stamped updates).
5. Implement safe guards: the admin surface remains accessible during maintenance; sign-in remains possible for platform roles; the maintenance toggle writes an audit event and notifies platform staff.
6. Implement flag and announcement APIs with caching and ETags for efficient app reads, with cache invalidation on change.
7. Write tests: audience targeting, scheduling edges (DST changes), sanitizer fuzz (XSS in announcement bodies), flag evaluation determinism (percentage rollouts stable per org), expiry alerts, maintenance modes against all routes (generated), data plane unaffected check (proxy keeps serving during maintenance), and permission gating (`platform.flags.write`).
**Deliverables.**
- API, UI, evaluation library, tests
**Acceptance.**
- A1: percentage flags assign orgs stably (same org, same result across restarts and nodes).
- A2: maintenance mode never interrupts the data plane in an integration test.
- A3: critical announcements cannot be dismissed; others remember dismissal per user.
- A4: sanitizer blocks scripts, event handlers and `javascript:` URLs in 100% of the XSS corpus.
- A5: expired flags raise attention items.
**Tests.**
- Integration, fuzz, browser e2e, data-plane check.
**Notes.** Flags are not a substitute for configuration of security controls; the list of flags that may touch security is short and reviewed.

## Definition of done for this task's tags (section 0.7)

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.
