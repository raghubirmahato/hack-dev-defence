### T-0425 · Global rule packs and rollout (S-107)
`P22` `[UI][API][SEC]` · deps: T-0417, T-0245, T-0261 · size: L · owner: web
**Objective.** Let operators publish, stage, compare and roll back platform rule packs safely.
**Steps.**
1. Implement the pack catalog screen: packs (core SQLi, XSS, traversal, scanner fingerprints, virtual patches, outbound patterns, bot signatures), installed version, available versions, signature status (verified/failed), release notes, rule counts by category and severity.
2. Implement version detail: diff view between versions (added/removed/changed rules with before/after expressions rendered as code with syntax-neutral highlight, no execution), benchmarks (inspect time p50/p99 on the standard corpus), false-positive report from the benign corpus run, and ATK coverage delta.
3. Implement staged rollout: stages (internal canary org(s) → 5% of domains in `monitor` → 25% → 100%), each stage with a minimum dwell time, automatic gates (no increase in false-positive proxies: user-created exceptions rate, auto-rollback triggers), manual approval with step-up, and an abort button; rollout state is stored and visible.
4. Implement rollback (one click, reason, step-up) that restores the previous signed pack through `config_revisions`, with propagation display and the automatic-rollback explanation (C14.8).
5. Implement pack upload for platform-authored packs: signature required (platform signing key; verify at upload), schema validation, dry-run against fixtures, and refusal of unsigned or invalid packs; rule authoring remains a development workflow, not a UI free-text editor (the UI supports enabling/disabling individual rules platform-wide with reasons, and tenant-level exceptions remain in P12).
6. Implement the **canary evaluation**: run the new version in shadow against the last 24 h of sampled request vectors (stored as anonymized vector hashes and feature sets, not raw requests) to estimate block-rate changes before rollout; show the delta by category and top changed rules.
7. Wire alerts: rollout stalled, auto-rollback fired, signature failure, pack older than N days.
8. Write tests: signature verification (valid/invalid/tampered), staged rollout state machine, rollback, diff correctness, permission gating (`platform.rules.publish` with step-up), shadow-evaluation determinism, and propagation tests to the proxy.
**Deliverables.**
- API, screens, rollout engine, tests
**Acceptance.**
- A1: an unsigned or tampered pack cannot be installed (negative tests).
- A2: staged rollout advances only after dwell and gates and can be aborted at any stage.
- A3: rollback restores the previous version within 2 s of confirmation across proxies.
- A4: the diff view matches the pack's rule files byte-for-byte (property test).
- A5: shadow evaluation produces a deterministic delta for the same input.
**Tests.**
- Integration with proxy snapshots, unit, browser e2e.
**Notes.** Tenants can pin a pack version in Tier 2 (P32); in v5 platform packs apply to all tenants after rollout.

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.

Abuse cases written as tests; STRIDE delta in `docs/STRIDE.md`; no secret in logs; constant-time comparison where secrets are compared; failure modes fail closed; panic-free on hostile input (proptest or fuzz target).
