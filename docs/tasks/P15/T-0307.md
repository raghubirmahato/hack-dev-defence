### T-0307 · Directory and file enumeration (forced browsing) detector
`P15` `[DP][SEC]` · deps: T-0262 · size: M · owner: dp
**Objective.** Detect wordlist-driven path brute forcing.
**Steps.**
1. Maintain per (site, client key) sliding counters of responses with status 404 (and 403) for distinct paths, extension diversity (many extensions on one stem), and similarity of sequential paths, using bounded sketches (HyperLogLog for distinct count, small Bloom filter for recent paths).
2. Define thresholds (defaults): ≥ 20 distinct 404 paths in 60 s → challenge; ≥ 60 → ban (`directory_enumeration`); ≥ 10 distinct sensitive-extension probes (`.bak`, `.old`, `.zip`, `.sql`, `.tar.gz`, `.swp`, `~`, `.env`, `.git`) → ban.
3. Account for legitimate crawlers (verified bots) and broken sites with many 404s (learn per-site baseline 404 rate; adjust thresholds; exempt known asset 404 patterns).
4. Detect known wordlist ordering fingerprints (alphabetical or common wordlist sequences) as an additional soft signal.
5. Link with honeypot hits (T-0309) and scanner fingerprints (T-0306) in a unified `recon_score` per client key.
6. Implement events with aggregated counts rather than per-request events to bound storage.
7. Link ATK-191, ATK-192, ATK-088, ATK-087.
8. Test with scripted enumeration (a wordlist of 5,000 paths) in lab/builder against a local origin, and legitimate browsing with broken links.
**Deliverables.**
- detector, thresholds, UI wiring, tests
**Acceptance.**
- A1: a 5,000-path wordlist scan is challenged within 20 requests and banned by 60.
- A2: a legitimate user clicking 5 broken links is unaffected.
- A3: verified bots are exempt.
- A4: memory per client key stays under 2 KB (measured).
- A5: events are aggregated.
**Tests.**
- Simulation tests; proptest on sketches; memory bound tests.
**Notes.** Thresholds are configurable per site (S-062).
