### T-0310 · Virtual patch pack v1 (known-component exploits)
`P15` `[DP][SEC][DOC]` · deps: T-0245, T-0291, T-0308 · size: L · owner: waf
**Objective.** Ship scoped mitigations for widely exploited vulnerabilities, with evidence and expiry, without pretending they fix anything.
**Steps.**
1. Create the `virtual_patch` pack with one rule family per vulnerability, each carrying `cve`, `component`, `affected_range`, `fixed_in`, `created`, `expires` (default 90 days after pack publication, renewable by explicit audited decision), `owner` (platform), and evidence tests (exploit-shaped inert requests that must block; benign requests that must pass): Log4Shell (CVE-2021-44228 and nested-lookup variants, with related CVE-2021-45046 context), Spring4Shell (CVE-2022-22965), Spring Cloud Function (CVE-2022-22963), Struts S2-045 (CVE-2017-5638), Shellshock (CVE-2014-6271 family), PHPUnit `eval-stdin.php` (CVE-2017-9841), Confluence OGNL (CVE-2022-26134), Apache 2.4.49/2.4.50 traversal (CVE-2021-41773, CVE-2021-42013), Text4Shell (CVE-2022-42889), Drupalgeddon2 (CVE-2018-7600), edge-device path shapes (CVE-2019-11510, CVE-2018-13379, CVE-2020-5902, CVE-2022-1388), ThinkPHP invokefunction RCE shapes.
2. Verify CVE identifiers and affected/fixed versions against OSV/NVD through the vulnerability feed tooling (T-0481) at build time, recording `UNVERIFIED(capability_not_supplied)` for any not verified.
3. Scope each rule narrowly (path/parameter/header) to limit false positives and document the matched shape in non-exploit terms; **store minimal detection patterns, never working exploit code** (C12.4).
4. Implement the lifecycle in the pack metadata (`draft/monitor/block/retired`), default `monitor` for tenant sites that have declared the affected component or none declared (platform decision: log-only unless the component is declared or the shape is unambiguous), and `block` for unambiguous exploit shapes (jndi lookups) by default.
5. Implement expiry alerts and gate release if expired packs are published (platform).
6. Add the banner copy `virtual-patch-banner` wherever virtual patches appear in the UI.
7. Add evidence tests and benign counterparts; run the AC-06 baseline for each rule.
8. Document each patch in the docs site (what it blocks, what it does not).
**Deliverables.**
- pack v1 (≥ 12 families), evidence tests, docs
**Acceptance.**
- A1: each family has at least 5 blocking examples and 5 benign counterparts verified in CI.
- A2: pack entries record `cve`, `component`, `affected_range`, `fixed_in`, `expires`.
- A3: expired entries are flagged and block the release gate.
- A4: no rule includes working exploit code (review checklist).
- A5: the UI shows the virtual-patch banner on every related screen.
**Tests.**
- Table (≥ 120 evidence cases) / benign gate / expiry tests with clock.
**Notes.** R-11: a virtual patch never resolves the vulnerability.

## Definition of done for this task's tags (section 0.7)

### `[DP]`: On the data-plane hot path (proxy, DNS, WAF, firewall)

Hot path never awaits the database; bounded memory and queues; criterion benchmark or histogram; fuzz or proptest; behavior when Redis or Postgres is down specified and tested; metric with drop counter.

### `[SEC]`: Security-relevant logic

Abuse cases written as tests; STRIDE delta in `docs/STRIDE.md`; no secret in logs; constant-time comparison where secrets are compared; failure modes fail closed; panic-free on hostile input (proptest or fuzz target).

### `[DOC]`: Documentation

Every claim backed by a test ID or a command the reader can run; passes claims-lint; included in the docs site if user-facing.
