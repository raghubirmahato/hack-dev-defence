### T-0302 · API protection: positive security from OpenAPI/JSON Schema, content-type enforcement
`P15` `[DP][API][SEC]` · deps: T-0249, T-0262 · size: XL · owner: waf
**Objective.** Let API-heavy sites define what valid requests look like and block the rest.
**Steps.**
1. Implement OpenAPI import (3.0/3.1) per site: parse paths, methods, parameters, request body schemas (JSON Schema subset: types, enums, formats, min/max, patterns (linear regex subset), required, additionalProperties), content types; store the compiled schema set in the policy snapshot with size limits (10 MB spec, compiled caps).
2. Implement validation modes per path: `off`, `log`, `block`; violations produce soft/hard signals: unknown path/method (`unknown_operation`), missing required fields, type mismatches, extra properties (mass assignment signal), out-of-range values, enum violations, oversized arrays/strings, wrong content type.
3. Implement content-type enforcement (V8): JSON endpoints require `application/json`; mismatched or ambiguous content types are blocked in enforce mode.
4. Implement per-endpoint limits (body size, array length, string length, nesting depth) derived from schemas.
5. Implement the **learned-schema** fallback (T-0272 learner) generating draft schemas from observed traffic aggregates for sites without OpenAPI, requiring owner review before enforcement.
6. Implement UI (API protection section in S-056/S-057): import/upload, coverage view (operations imported, observed but undocumented endpoints), violation counts, dry-run replay against the traffic sample, enforcement toggles per tag/path.
7. Link ATK-049, ATK-175 to ATK-178 and OWASP API Top 10 (API3, API4, API8) in docs.
8. Test with 20 real-world-style OpenAPI documents (generated) and hostile specs (deep refs, huge enums, regex bombs rejected at compile).
**Deliverables.**
- schema compiler, validator, UI, tests
**Acceptance.**
- A1: requests violating schema constraints are logged or blocked per mode.
- A2: hostile specs (cycles, huge enums, regex bombs) are rejected with diagnostics.
- A3: undocumented endpoints are listed with counts.
- A4: validation overhead stays under 50 µs for typical 2 KB bodies (benchmark).
- A5: the dry-run replay shows would-block counts before enforcement.
**Tests.**
- Table (300 request/schema pairs) / fuzz on spec parser / benchmarks.
**Notes.** Positive security reduces reliance on signatures for APIs.

## Definition of done for this task's tags (section 0.7)

### `[DP]`: On the data-plane hot path (proxy, DNS, WAF, firewall)

Hot path never awaits the database; bounded memory and queues; criterion benchmark or histogram; fuzz or proptest; behavior when Redis or Postgres is down specified and tested; metric with drop counter.

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.

### `[SEC]`: Security-relevant logic

Abuse cases written as tests; STRIDE delta in `docs/STRIDE.md`; no secret in logs; constant-time comparison where secrets are compared; failure modes fail closed; panic-free on hostile input (proptest or fuzz target).
