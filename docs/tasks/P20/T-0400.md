### T-0400 · DNS observability, performance and capacity benchmarks
`P20` `[OPS][QA]` · deps: T-0393, T-0388, T-0214 · size: M · owner: dns
**Objective.** Make the DNS service measurable and prove it meets its budgets.
**Steps.**
1. Implement metrics: `MET-hdd_dns_queries_total{proto,qtype,rcode}` (B9 labels; `qtype` is bucketed into known types plus `other`), `MET-hdd_dns_latency_seconds` (histogram, wire-in to wire-out), `MET-hdd_dns_dropped_total{reason}`, `MET-hdd_dns_truncated_total`, `MET-hdd_dns_apply_seconds`, `MET-hdd_dns_snapshot_bytes`, `MET-hdd_dns_zones`, `MET-hdd_dns_flatten_*`, `MET-hdd_dns_xfr_*`, `MET-hdd_dns_cookie_*`, `MET-hdd_dns_nxdomain_ratio{zone_class}` (zone ids hashed in labels with a cardinality cap and an `other` bucket).
2. Implement aggregated per-zone counters flushed to the control plane every 60 s over the queue (queries, NXDOMAIN, top types, top 10 qnames limited to the tenant's own zone names, never client addresses) for the DNS analytics views (T-0193) and billing counters.
3. Implement the DNS dashboard feed for S-113 and S-127: qps, drops by reason, RRL active, cookie adoption, secondary lag, snapshot age, flatten health.
4. Create the Grafana dashboard `dns.json` and Prometheus alert rules (snapshot stale > 10 min, apply latency > 2 s, drops by RRL > 30% for 5 min, secondary lag, random-subdomain defense active, origin leak guard fired, cookie secret rotation failing).
5. Implement `hdd-loadgen dns` (closed lab / private link only): UDP and TCP query generators with realistic mixes, using multiple source addresses via namespaces, rate profile `load` limited to operator-owned machines; record qps, p50/p99 latency, CPU and memory.
6. Run benchmarks on the builder and on the VPS-class profile machine: target ≥ 50,000 qps UDP per core on cached snapshot answers, p99 ≤ 2 ms at 20,000 qps, memory ≤ 150 MiB for 10,000 zones × 20 records, snapshot swap ≤ 200 ms for a 100,000-record zone with no query latency spike above 5 ms.
7. Profile with `perf`/flamegraph and fix hot spots (allocation per query must be zero on the cached path; test with a counting allocator).
8. Publish `docs/dns/PERFORMANCE.md` with methodology, hardware description and the numbers (labeled lab-only; production capacity is whatever the VPS proves, reported as UNVERIFIED until measured live in an operator-approved window).
**Deliverables.**
- metrics, dashboards, alert rules, loadgen subcommand, performance doc
**Acceptance.**
- A1: budgets in step 6 are met or documented as deviations with rationale.
- A2: no allocation on the cached query path (counting allocator test).
- A3: zone id label cardinality is capped (test with 100k zones).
- A4: alert rules validate with `promtool check rules`.
- A5: the swap latency test shows no latency spike above the threshold.
**Tests.**
- Benchmarks as `xtask bench dns`; unit tests for aggregation; `promtool`.
**Notes.** qps numbers are reported separately per environment (lab, pilot VPS) and are never presented as internet-scale capacity.
