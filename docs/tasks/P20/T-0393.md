### T-0393 · Abuse controls: response-rate limiting, DNS cookies, per-source caps and random-subdomain detection
`P20` `[DP][SEC]` · deps: T-0392 · size: L · owner: dns
**Objective.** Ensure HDD cannot be used as a reflector, and that floods of valid-looking queries degrade gracefully.
**Steps.**
1. Implement **RRL** modeled on the BIND/Knot algorithm: key = (client prefix /24 for IPv4, /56 for IPv6, qname-class bucket, response type: positive/NXDOMAIN/error), token bucket default 5 responses/s per key, window 15 s, `slip=2` (every second dropped response is replaced by an empty TC=1 response so legitimate clients retry over TCP), exempt list for `admin_cidrs`, the secondary's addresses and the platform's own resolvers.
2. Implement **DNS cookies** (RFC 7873/9018): server secret rotated every 24 h with a 1 h overlap, client+server cookie validation; queries with a valid server cookie bypass RRL and the lower per-source cap; queries with only a client cookie get a `BADCOOKIE`-free normal answer including the server cookie; queries without cookies are allowed but rate-limited more strictly.
3. Implement per-source query caps: 50 qps default for sources without a valid cookie, 500 qps with a valid cookie, burst equal to 2 s of rate; counters stored in a bounded LRU (default 1,000,000 entries) with eviction that favors dropping idle sources, never panicking, and sized to ≤128 MiB.
4. Implement the **random-subdomain (water-torture) detector** per zone and per source: when the NXDOMAIN ratio for a zone exceeds 70% over 10 s with more than 500 qps, enter `zone_nxdomain_defense`: (a) apply a stricter RRL to NXDOMAIN responses for that zone, (b) answer NXDOMAIN with minimal responses only, (c) raise a `dns_random_subdomain_flood` alert with the top sources (/24, /56 aggregates only), and (d) automatically exit after 5 minutes below the threshold. Zones with wildcard records are excluded from the ratio (wildcards answer positively).
5. Implement a **reflection source-port guard** (UDP queries whose source port is 53, 123, 389, 1900, 11211, 19 or in the configurable list are answered only with cookie validation, else dropped) to avoid DNS-to-DNS reflection loops.
6. Implement an **attack-mode toggle** controlled by the shield (T-0475): in `ATTACK` state, queries without valid cookies are answered with a TC=1 empty response for non-exempt sources, forcing TCP (documented as an emergency measure with effects on resolvers).
7. Ensure every limit is configurable in `hdd.yaml`/settings with validation and sane maxima, and that every drop is counted by reason (`rrl`, `cap`, `cookie`, `malformed`, `reflection_port`, `overload`) in `MET-hdd_dns_dropped_total{reason}`.
8. Document the effects on legitimate resolvers (large resolvers share addresses; the /24 and /56 aggregation, slip behavior and the exemption procedure) in `docs/dns/ABUSE-CONTROLS.md`.
9. Write the test plan: unit tests for token buckets (time-injected), RRL behavior tables, cookie validation vectors from RFC 7873 appendix, simulated resolver populations (a legitimate resolver pool must keep ≥99% success while an attacker pool is limited), and a regression test that RRL never limits the secondary's NOTIFY/transfer.
**Deliverables.**
- `rrl/` module, cookie module, detectors, docs, tests
**Acceptance.**
- A1: a flood of identical queries from one source yields at most the configured response rate plus slip responses (measured).
- A2: a legitimate-resolver simulation (500 resolvers at 10 qps each plus a 50k qps attacker pool) sees ≥99% of legitimate queries answered.
- A3: cookie vectors from the RFC pass; invalid server cookies are treated as no cookie.
- A4: the random-subdomain defense enters and exits as specified and is visible in S-113/S-127.
- A5: the secondary's addresses are never rate limited (test).
**Tests.**
- Deterministic time-injected unit tests; lab simulation using `hdd-loadgen` (closed lab only, section 2.6).
**Notes.** The cap for sources without cookies is intentionally conservative; recursive resolvers behind NAT can exceed it, hence the /24 aggregation and cookie fast path.
