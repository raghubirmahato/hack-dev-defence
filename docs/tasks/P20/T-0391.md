### T-0391 · CNAME flattening resolver (bounded, cached, loop-safe, never recursive for clients)
`P20` `[DP][SEC]` · deps: T-0389, T-0388 · size: L · owner: dns
**Objective.** Support apex CNAME-like behavior (ALIAS semantics) safely, without turning the server into a recursive resolver.
**Steps.**
1. Implement a separate `flatten` task pool that resolves targets for flattened records (apex CNAME records stored as `source=flatten` per T-0178) via a configured upstream resolver list (`dns.flatten_resolvers`, default the system resolver of the host; must be local or explicitly configured), over UDP with TCP fallback, with DNSSEC validation off (documented) and a strict response size cap.
2. Enforce limits: depth 8, total lookups per flatten operation 16, wall time 3 s, target must be a valid hostname, resolved addresses must not fall into disallowed ranges (private, loopback, link-local, metadata) **unless** the zone owner is the platform org; results from blocked ranges are dropped and an event is recorded (`dns_flatten_blocked_range`).
3. Implement caching: positive results honor the minimum TTL of the chain bounded to [30 s, 3,600 s]; negative results cached 30 s; stale-while-revalidate (serve the last value up to 10 minutes past expiry if resolution fails, with a metric and a dashboard flag).
4. Implement refresh scheduling: a background tick refreshes flattened targets at 80% of the TTL with jitter; at most `flatten.max_targets` (default 5,000) globally and `flatten_per_zone_max` (default 20) per zone; excess targets are rejected at the control plane (`ERR-DNS-007`).
5. Implement loop and abuse protection: a flatten target that (transitively) points at a name in an HDD zone is resolved against the local snapshot with a visited-set; cycles are detected and the record is marked `failing(loop)`; a target that is a wildcard or random-subdomain pattern is rejected at record creation.
6. Ensure a flattened name's answers in the query path come only from the cache (never block on resolution): a cache miss for a flattened name triggers an asynchronous refresh and the query is answered with SERVFAIL only when no stale value exists (rare, counted).
7. Expose per-record flatten health in the API (`last_ok`, `last_error`, `ttl_remaining`) for the DNS records screen (S-045) and raise alerts after 3 consecutive failures.
8. Write tests with a controllable stub upstream server (a real UDP/TCP DNS server process started by the test) covering: normal chain, long chain over the depth limit, loop, slow upstream, oversized response, truncated response with TCP fallback, upstream returning private addresses, upstream returning SERVFAIL and stale serving.
**Deliverables.**
- `flatten/` module, API fields, alerts, tests
**Acceptance.**
- A1: queries never block on resolution (p99 latency identical with the upstream down).
- A2: loops and over-deep chains are detected within limits and surfaced as record health.
- A3: private-range answers are dropped for tenant zones.
- A4: stale values are served up to 10 minutes and then SERVFAIL, with metrics for each state.
- A5: the server never answers a client query by recursing (negative test: a query for an unknown external name is `REFUSED`).
**Tests.**
- Integration with the stub upstream; property tests for loop detection; chaos test killing the upstream mid-refresh.
**Notes.** CNAME flattening is the only place `hdd-dns` makes outbound DNS queries, and it does so through the egress client rules (section 2.9) with an allowlist of resolver addresses.
