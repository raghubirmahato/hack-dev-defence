### T-0399 · Tenant isolation, zone lifecycle in the data plane and takeover prevention
`P20` `[DP][SEC]` · deps: T-0388, T-0390, T-0160 · size: M · owner: sec
**Objective.** Ensure a zone can be served only for the org that owns and has verified it, and that retired zones cannot be hijacked.
**Steps.**
1. Enforce at ingestion: one zone ↔ one org; an apex that is a public suffix or lies under another org's apex is rejected unless delegated by explicit NS records inside the parent (subzone delegation within the same org); reserved suffixes (`platform_domain`, `.edge.`, `.acme.`, `.preview.`) are blocked for tenants.
2. Implement lifecycle states in the data plane: `active` (serve), `pending_delegation` (serve, flagged `awaiting_ns`), `paused` (serve DNS but proxied answers become grey if the site is paused per T-0170 semantics), `suspended` (REFUSED), `decommissioned` (REFUSED after a cool-down of 24 h during which the apex stays reserved for the same org), `quarantined` (REFUSED, platform admin action).
3. Implement **NS pair hygiene**: when a zone is deleted, the NS pair assignment remains reserved to that org for 24 h; a new zone with the same apex by another org requires re-verification of ownership and cannot reuse the same pair within the cool-down. This blocks the "stale delegation" takeover where a registrar still delegates to HDD after a customer left.
4. Implement protection against **delegated-NS takeover**: if the observed delegation (control-plane probe) points at HDD for an apex that has no active zone, HDD answers REFUSED but records a `dangling_delegation` finding (surfaced to platform admins and, if the former owner is known, to them) and never creates a zone automatically.
5. Implement zone-count and record-count enforcement at the data plane as a defense-in-depth: a snapshot revision exceeding the org's plan limits is quarantined (control-plane bugs cannot create unlimited zones).
6. Implement a **query attribution firewall**: query logs and counters aggregate per zone only (no client IP storage beyond rolling counters; top-source reports are /24 and /56 aggregates held 24 h and then dropped), per privacy rules (C8).
7. Add tests: cross-tenant creation of the same apex, subzone delegation across orgs, reserved names, takeover cool-down, plan-limit bypass attempts via direct database writes (the DNS service must still reject), and the lifecycle state table.
8. Document the lifecycle in `docs/dns/LIFECYCLE.md` with a state diagram and the exact user-visible effects.
**Deliverables.**
- validation in control plane and data plane, tests, docs
**Acceptance.**
- A1: org B cannot serve a zone for a domain that org A has verified (control plane and direct-DB test).
- A2: a deleted zone answers REFUSED within 2 s and its apex stays reserved for 24 h.
- A3: dangling delegations are detected and reported without auto-creating a zone.
- A4: plan limits are enforced by the data plane even when the control plane is bypassed.
- A5: no client IPs appear in DNS logs or in the database beyond the /24 and /56 24-hour aggregates.
**Tests.**
- Integration with direct DB manipulation; BOLA suite additions; privacy test greps logs and tables.
**Notes.** This complements T-0192 (dangling record scanner) which looks at records, whereas this task protects delegation and apex ownership.
