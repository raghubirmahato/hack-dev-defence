### T-0096 · Features and "How protection works, and its limits" (S-002, S-003) with claims evidence
`P05` `[UI][DOC][SEC]` · deps: T-0095 · size: M · owner: docs
**Objective.** Publish accurate, test-backed statements and the limits of the product.
**Steps.**
1. Implement S-002 describing capabilities by area (domains, DNS, TLS, WAF, shield, bans, analytics, API) with links to docs.
2. Implement S-003 with the request-path diagram (SVG with long description and ordered-list alternative), explanation of what is inspected and what happens on a hit, and the "what this does not cover" section from C3.2 plus volumetric DDoS limits, logic flaws, patching, shared-IP collateral, and DNS availability.
3. Implement the **claims evidence** mechanism: `xtask claims-evidence` produces `docs/generated/claims-evidence.json` from the latest gate/acceptance results (AC ID, status, date, summary, payload set size) at release time; pages render claims only if evidence exists, otherwise show "Results will be published after acceptance testing" instead of numbers.
4. Implement a build-time check that every numeric claim on public pages references an evidence entry key; unreferenced numbers fail claims-lint.
5. Write copy using the approved patterns of section 4.3.
6. Add a "Report an inaccuracy" link that goes to the contact form with a prefilled subject.
7. Add the downloadable "Security overview" in HTML print form (S-003 print stylesheet).
8. Add visual and accessibility tests for the diagram.
**Deliverables.**
- templates, diagram asset, evidence generator, tests
**Acceptance.**
- A1: S-003 lists all five limits of C3.2 and the volumetric statement.
- A2: any number on the page traces to an evidence entry (test).
- A3: without evidence, no numeric claim is displayed.
- A4: the diagram has a text alternative and passes contrast.
- A5: claims-lint passes.
**Tests.**
- Unit: evidence loader and claim-reference checker; browser: with and without evidence file.
**Notes.** This is the mechanism that keeps marketing honest (R-10).

## Definition of done for this task's tags (section 0.7)

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.

### `[DOC]`: Documentation

Every claim backed by a test ID or a command the reader can run; passes claims-lint; included in the docs site if user-facing.

### `[SEC]`: Security-relevant logic

Abuse cases written as tests; STRIDE delta in `docs/STRIDE.md`; no secret in logs; constant-time comparison where secrets are compared; failure modes fail closed; panic-free on hostile input (proptest or fuzz target).
