### T-0118 · Step-up re-authentication (S-032)
`P06` `[UI][API][SEC]` · deps: T-0117 · size: M · owner: sec
**Objective.** Require fresh authentication for sensitive actions.
**Steps.**
1. Define the sensitive action list from the permission matrix (`S` entries) and implement a declarative annotation on handlers (`requires_step_up(max_age)`); platform actions use 5 minutes, org actions 10 minutes.
2. Implement `POST /auth/reauth` accepting password (plus MFA if enrolled) or a passkey, setting `step_up_until` on the session and rotating the session ID.
3. Implement the modal flow for HTMX (the action returns `ERR-AUTH-008` with an HX header that opens the modal; after success the original request is retried with its idempotency key) and a full-page fallback preserving the form.
4. Ensure step-up cannot be satisfied by "remember device".
5. Add rate limits and throttling equal to login.
6. Add audit events `AUD-auth.stepup` with the action name.
7. Ensure API-key authenticated calls cannot perform step-up-required actions unless the key was created with step-up proof (documented limitation: keys cannot do `S` actions by default).
8. Test with the clock for expiry boundaries.
**Deliverables.**
- annotation macro, middleware, modal and page templates, tests
**Acceptance.**
- A1: an `S` action after expiry returns `ERR-AUTH-008` and succeeds after re-auth without losing form input.
- A2: the retry carries the same idempotency key (no double side effects).
- A3: step-up is not satisfiable by device trust.
- A4: API keys cannot execute `S` permission routes (explicit tests).
- A5: the modal is keyboard accessible and focus returns properly.
**Tests.**
- Browser flows for modal and fallback; unit: expiry boundary tests; integration: idempotent retry.
**Notes.** The permission matrix test (T-0125) cross-checks the annotation against the table.
