### T-0111 · Email verification flow (S-021, S-022)
`P06` `[UI][API][SEC]` · deps: T-0107, T-0110 · size: M · owner: api
**Objective.** Verify addresses safely and create the account's organization.
**Steps.**
1. Implement token creation: 32 random bytes, base32 or base64url, SHA-256 hash stored, 24-hour expiry, purpose `verify`, binding to user ID; previous tokens for the same purpose are invalidated on new issuance.
2. Implement `GET /verify-email/{token}` rendering the confirm page (no state change, `no-referrer`, `no-store`) and `POST` consumption with CSRF (anonymous pre-session token), so link scanners cannot consume tokens.
3. On success: mark `email_verified_at`, set status `active`, create the organization (name derived from the user's chosen name or email local part, slug generated and checked against the reserved list), create membership as owner, write audit events, and sign the user in (or redirect to login according to risk policy for platform roles).
4. Implement resend with cooldown (10 minutes) and daily cap; the resend page is enumeration-safe.
5. Handle expired/used tokens with the neutral error and resend form.
6. Handle invite-bound users (join existing org, skip org creation).
7. Emit metrics and security timeline event.
8. Add browser tests for happy path, scanner prefetch, expiry, resend.
**Deliverables.**
- handlers, templates, tests
**Acceptance.**
- A1: a GET (prefetch) never verifies the account.
- A2: used or expired tokens fail identically (`ERR-AUTH-009`).
- A3: token hashes only are stored (database inspection test).
- A4: verification creates exactly one org and one owner membership (idempotent under double submit).
- A5: reserved slugs (`admin`, `api`, `app`, `www`, `status`, `ns1`, etc.) are never assigned.
**Tests.**
- Integration: concurrency (double POST), expiry with the test clock; browser flows with the SMTP sink.
- Unit: slug generation table and collision handling.
**Notes.** Platform staff accounts are created by `hddctl` and never through this flow.

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.
