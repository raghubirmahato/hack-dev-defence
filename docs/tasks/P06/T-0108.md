### T-0108 · Signup abuse controls and the proof-of-work core library
`P06` `[SEC]` · deps: T-0107 · size: L · owner: sec
**Objective.** Make mass signup and email bombing impractical without third-party CAPTCHAs.
**Steps.**
1. Implement the `hdd-challenge` core (pure library): issue signed challenge tokens (HMAC-SHA-256, `HDD_CHALLENGE_KEY`), parameters (`difficulty_bits`, expiry 60 s, context binding to route and IP bucket), SHA-256 hashcash verification, one-time use via Redis nonce, and test vectors; the data-plane integration and clearance cookies come in T-0337.
2. Implement the signup friction ladder: baseline rate limits (per IP /24 or /56: 5 per hour; per email-HMAC: 3 per day; per email domain: 50 per hour), then PoW required when thresholds are approached, then temporary blocks.
3. Implement the honeypot field (hidden, label `Leave this empty`, off-screen but not `display:none`) and timing check (form render time to submit time minimum 2 s) as soft signals feeding the friction ladder, never as sole blockers.
4. Implement disposable-email policy (`block`/`challenge`/`allow`) with list import (`xtask disposable import`) and platform admin management (T-0428).
5. Implement signup freeze (platform emergency control) and invite-only enforcement.
6. Implement email-bombing protection: at most 1 verification email per address per 10 minutes and 5 per day; "account exists" notices limited similarly; global outbound mail budget with alerts.
7. Implement metrics and alerts for signup spikes (`MET-hdd_signups_total` anomaly rule).
8. Document tuning guidance and the accessibility of the PoW (automatic, no puzzle).
**Deliverables.**
- `crates/hdd-challenge/src/core.rs`, signup friction module, import tools, tests
**Acceptance.**
- A1: scripted signups at 100/min from one IP are slowed to the baseline and then challenged.
- A2: PoW tokens cannot be replayed or used for another route.
- A3: honeypot/timing signals alone never block a legitimate user (test with filled honeypot only increasing friction).
- A4: email bombing attempts against one victim address send at most the configured number of emails.
- A5: the friction ladder works with Redis down by falling back to local limits.
**Tests.**
- Unit: PoW verification vectors, difficulty boundaries; integration: Redis nonce replay; behavioral tests of the ladder.
- Load: 1,000 signup attempts across 50 IPs on the builder (functional profile) with assertions on emails sent.
**Notes.** Difficulty tuning for phones is calibrated in T-0337.
