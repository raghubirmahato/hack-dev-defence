### T-0120 · Change password and change email
`P06` `[UI][API][SEC]` · deps: T-0118 · size: M · owner: api
**Objective.** Let users manage credentials safely.
**Steps.**
1. Implement `POST /me/password` requiring step-up and the current password (even after step-up, to defend against hijacked sessions), enforcing the policy, rotating the session, offering "sign out other sessions" (default on), and sending a notification.
2. Implement `POST /me/email/change`: step-up, send a confirmation token to the new address and a notification to the old address with a cancel link (valid 7 days), keep the old email active until confirmation.
3. Implement `POST /me/email/confirm` consuming the token; on success update the normalized email, revoke other sessions, and write audit events; handle collisions with existing accounts by a neutral failure message and a notice to the existing owner.
4. Implement the "undo" window: the old address can reverse the change for 7 days (restore flow requires step-up on login).
5. Prevent changes to platform staff emails except by `platform_owner` with step-up.
6. Provide UI in S-088 with clear states.
7. Add rate limits and audit events.
8. Test race conditions (two simultaneous changes).
**Deliverables.**
- handlers, templates, emails, tests
**Acceptance.**
- A1: changing the password without the correct current password fails even with fresh step-up.
- A2: both addresses receive appropriate notices.
- A3: email collision does not reveal the other account's existence.
- A4: the cancel link from the old address works within 7 days.
- A5: concurrent changes serialize correctly.
**Tests.**
- Integration: race tests, notifications; browser flows.
**Notes.** These are common account-takeover persistence points, hence the redundancy.
