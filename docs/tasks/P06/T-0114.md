### T-0114 · TOTP enrollment and verification (S-030, S-024)
`P06` `[UI][API][SEC]` · deps: T-0113, T-0040 · size: M · owner: sec
**Objective.** Provide standards-based TOTP with replay protection and safe storage.
**Steps.**
1. Generate a 160-bit secret, store encrypted (AES-256-GCM envelope, AAD = user ID), and create the provisioning URI (`otpauth://`) with issuer from branding; render the QR as server-side SVG and show the manual key (grouped) with a copy field.
2. Verify codes (6 digits, 30 s period, SHA-1 default for app compatibility) with a ±1 step window, constant-time compare, and store `last_used_step` to reject replays.
3. Rate limit verification (5 attempts per 5 minutes per user, then backoff) and notify on repeated failures.
4. Implement the login flow second step (S-024) and enrollment confirmation (cannot enable MFA until a correct code is submitted).
5. Implement removal and reset flows requiring step-up and sending notifications; platform staff cannot remove their own MFA through the UI.
6. Implement clock-drift guidance in the UI when a code is repeatedly wrong near boundaries.
7. Write audit and security timeline events for enroll/remove.
8. Test with an RFC 6238 test-vector set and a headless authenticator emulation.
**Deliverables.**
- TOTP module, handlers, templates, tests
**Acceptance.**
- A1: RFC test vectors pass.
- A2: replay of an accepted code within the same step fails.
- A3: secrets are never present in logs or HTML except the enrollment page for the enrolling user.
- A4: removal requires step-up and triggers a notification email.
- A5: platform roles cannot proceed without enrolled MFA (enforced in T-0117).
**Tests.**
- Unit: vector tests and drift windows; integration: enrollment flow with the test clock; browser: QR page has text alternative and passes axe.
**Notes.** Passkeys are preferred when enrolled (T-0116); TOTP remains the universal fallback.
