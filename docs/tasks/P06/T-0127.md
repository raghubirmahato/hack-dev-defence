### T-0127 · Team invitations and role management (S-081 to S-083)
`P06` `[UI][API][SEC]` · deps: T-0126, T-0110 · size: L · owner: api
**Objective.** Let owners and admins build teams safely.
**Steps.**
1. Implement invitations: create (email, role), token (32 bytes hashed, 7-day expiry), email, resend (rate-limited), revoke; duplicates handled (`ERR-ORG-003`); inviting an existing member is refused neutrally.
2. Implement acceptance (S-029): existing user signs in with the invited email or new user signs up with the email locked; role granted at acceptance; token single use; email mismatch handled with neutral error.
3. Implement role changes with rules: admins cannot grant owner or change owners; owners can; changes require step-up for admins per matrix; at least one owner remains (`ERR-ORG-004`).
4. Implement member removal and leaving the org (with last-owner protection and transfer prompt).
5. Implement S-081 (members table with last active and MFA state), S-082 (pending invitations), S-083 (role cards and generated permission matrix view).
6. Implement ownership transfer flow (S-086 integration) requiring the target to accept and step-up.
7. Implement notifications to owners on role changes and removals.
8. Add audit events.
**Deliverables.**
- handlers, templates, tests
**Acceptance.**
- A1: an admin cannot escalate to owner (test).
- A2: invitation tokens are single use and expire.
- A3: the matrix view is generated from the permission source (no hand copy).
- A4: removing the last owner is blocked at API and UI levels.
- A5: invites to emails with existing accounts do not reveal account existence to the inviter beyond normal invite semantics.
**Tests.**
- Integration: matrix of role changes (who can change whom); browser flows; security tests for token misuse.
**Notes.** Org-level MFA enforcement (T-0117) applies to invited members at acceptance.
