### T-0119 · Password reset (S-027, S-028)
`P06` `[UI][API][SEC]` · deps: T-0111, T-0110 · size: M · owner: api
**Objective.** Provide safe recovery without enabling account takeover or enumeration.
**Steps.**
1. Implement `POST /auth/forgot-password`: always responds with the same message and 202; for existing active users queues a reset email, for others no email (or a neutral "no account" notice only if the sender policy allows; default none); timing equalized.
2. Implement tokens: 32 random bytes, hashed, 60-minute expiry, single use, old reset tokens invalidated on new issuance, bound to the user's current password hash version (a password change invalidates outstanding tokens).
3. Implement the confirm page (GET shows form after token check without consuming; POST sets the password) with policy checks and the strength endpoint.
4. On success: revoke all sessions, keep MFA requirements (MFA must be satisfied at next login; reset does not bypass MFA), send "password changed" notification, add timeline event.
5. Build reset links from configured base URL, never from the Host header (poisoning defense).
6. Rate limit by IP bucket, email HMAC and globally; cap email volume.
7. For platform roles: reset via email is allowed only with MFA at next login; recovery of lost MFA is `hddctl` only.
8. Test the host-header poisoning attempt and link generation.
**Deliverables.**
- handlers, templates, tests
**Acceptance.**
- A1: the response is identical for existing and non-existing accounts.
- A2: using an old token after a new request fails.
- A3: a hostile `Host` or `X-Forwarded-Host` header cannot alter generated links (test).
- A4: a successful reset revokes all sessions and notifies the owner.
- A5: reset does not disable MFA.
**Tests.**
- Integration with sink; statistical enumeration test; unit: token binding to password version.
**Notes.** Email access alone must never be sufficient to remove MFA.
