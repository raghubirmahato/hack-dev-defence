### T-0112 · Login API and UI (S-023)
`P06` `[UI][API][SEC]` · deps: T-0106, T-0113, T-0055 · size: L · owner: api
**Objective.** Implement login with layered throttling, uniform errors and clear next steps.
**Steps.**
1. Implement `POST /auth/login`: normalize email, look up user (or use the dummy), verify password with the concurrency limiter, evaluate status (active, locked, disabled), and decide the next step (`mfa`, `passkey`, `done`) based on enrollment and policy.
2. Implement throttling keyed by (a) IP bucket, (b) account HMAC, (c) IP+account pair: exponential backoff on failures (1 s, 2 s, 4 s … up to 15 min) for the pair; after 10 failures per account in 15 minutes require a PoW and email notification to the owner; after 20 failures per IP bucket in 15 minutes require PoW for all attempts from that bucket; never lock an account hard for unauthenticated attackers (prevents lockout DoS), but require step-up for sign-in from unfamiliar devices during an attack.
3. Implement uniform failure responses (`ERR-AUTH-002`) with the same shape and equalized timing, and `Retry-After` only on rate-limit responses.
4. Implement the device cookie (opaque ID, hashed in `user_devices`) used to reduce friction for known devices and to flag new devices.
5. Validate the post-login return URL: only same-origin relative paths matching an allowlist pattern; everything else goes to the default landing.
6. Implement the S-023 page with passkey option, password manager support, error summary, and links.
7. Record `login_attempts` (HMAC email, IP key, outcome class) and audit events; metrics by result.
8. Add the tests for backoff timing with the injectable clock, uniform responses, and return URL handling.
**Deliverables.**
- handlers, throttling module, templates, tests
**Acceptance.**
- A1: unknown user and wrong password produce identical responses (status, body shape, headers) and similar timing.
- A2: after 6 failures the same IP+account pair receives backoff delays per schedule.
- A3: an attacker cannot lock out the victim's own logins from a known device (test).
- A4: open redirect attempts in `next` are neutralized (40+ variants).
- A5: login works with JavaScript disabled.
**Tests.**
- Integration with test clock; unit: throttle state machine (proptest on sequences); browser: flows incl. MFA branching.
- Security: enumeration and timing tests (statistical).
**Notes.** The in-app throttling is the second layer; HDD's own WAF/rate limiter protects these endpoints first when dogfooding.

## Definition of done for this task's tags (section 0.7)

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.

### `[SEC]`: Security-relevant logic

Abuse cases written as tests; STRIDE delta in `docs/STRIDE.md`; no secret in logs; constant-time comparison where secrets are compared; failure modes fail closed; panic-free on hostile input (proptest or fuzz target).
