### T-0123 · Account lock, unlock and recovery policy
`P06` `[SEC][OPS]` · deps: T-0113, T-0134 · size: M · owner: sec
**Objective.** Define and implement account lifecycle controls for abuse and compromise.
**Steps.**
1. Implement account statuses (`pending`, `active`, `locked`, `disabled`, `deleted`) and transitions with audit events and notification rules.
2. Implement admin-initiated lock/unlock/disable with reason (platform permission, step-up), revoking sessions immediately.
3. Implement self-service "secure my account" action (locks login except via recovery, requires reset and MFA recheck).
4. Implement `hddctl admin mfa-reset <email>` for staff and tenant owners (requires local root access, prints a one-time enrollment link, audits, notifies the account email).
5. Define and document the recovery policy: no email-only MFA reset; owner-assisted reset for org members (an owner can reset a member's MFA enrollment after identity check, with notification and cooling period of 24 h before the member can access sensitive settings); platform staff only via `hddctl`.
6. Implement the cooling-period mechanism (reduced privileges, banner).
7. Implement lock messaging uniform with login errors.
8. Test all transitions and notifications.
**Deliverables.**
- lifecycle module, CLI command, UI actions, docs, tests
**Acceptance.**
- A1: a locked account cannot log in and sees the same message as other failures.
- A2: sessions are revoked on lock.
- A3: MFA reset notifies the account owner and enforces the cooling period.
- A4: `hddctl admin mfa-reset` requires root and logs an audit event.
- A5: owner-assisted resets cannot target owners (only another owner or `hddctl`).
**Tests.**
- Integration: transition matrix; CLI test in a container; unit: cooling-period logic.
**Notes.** Recovery of the last owner of an org without MFA requires platform support with identity verification outside the product (documented).
