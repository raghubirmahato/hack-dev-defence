### T-0107 · Signup: API and UI (S-020)
`P06` `[UI][API][SEC]` · deps: T-0106, T-0079, T-0055 · size: L · owner: api
**Objective.** Implement enumeration-safe signup under the platform's signup policy.
**Steps.**
1. Implement `POST /auth/signup` and the S-020 page for modes `open` and `invite_only` (invite tokens bind email); `disabled` returns the closed message without a form.
2. Normalize email (NFKC, lowercase, trim; reject control characters, overlong local parts, IP-literal domains), validate syntax strictly (no regex abuse), IDNA-normalize domains, apply `allowed_email_domains` and the disposable-domain policy.
3. Record consent to the current Terms and Privacy versions (T-0101) and refuse signup if they are unpublished.
4. For a new address: create `users` in `pending`, hash the password, queue a verification email; for an existing address: queue an "account exists" notice email (no state change) instead; in both cases respond identically (202, same body, equalized timing by always performing a hash and an outbox insert).
5. Create the organization only after verification (T-0111) to avoid orphan orgs from abuse.
6. Implement the invite-bound signup path (email fixed, role from invitation).
7. Add the audit event, metrics (`MET-hdd_signups_total{outcome}`), and the user-facing copy keys.
8. Add browser flows for desktop and 360 px, including password manager attributes and error summary.
**Deliverables.**
- handlers, templates, copy, tests
**Acceptance.**
- A1: responses for new and existing emails are byte-identical except request ID and timing within the equalization bound.
- A2: closed mode shows no form and the API returns `ERR-SYS-004`/closed message.
- A3: an unpublished legal state blocks signup with an operator-facing banner.
- A4: invite signups lock the email field server-side (tampering rejected).
- A5: a user enumerating 1,000 emails learns nothing (statistical test over body, status, headers, timing).
**Tests.**
- Integration with the SMTP sink verifying both email variants; browser flow; unit: email normalization table (50 cases) with proptest.
- Security: enumeration oracle test described above.
**Notes.** Account-exists email text tells the real owner "someone tried to sign up with your address" and offers login/reset links.

## Definition of done for this task's tags (section 0.7)

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.

### `[SEC]`: Security-relevant logic

Abuse cases written as tests; STRIDE delta in `docs/STRIDE.md`; no secret in logs; constant-time comparison where secrets are compared; failure modes fail closed; panic-free on hostile input (proptest or fuzz target).
