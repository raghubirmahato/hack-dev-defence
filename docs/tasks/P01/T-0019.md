### T-0019 · Content strategy, microcopy guide and the claims dictionary
`P01` `[DOC][SEC]` · deps: T-0011 · size: M · owner: ux
**Objective.** Make every sentence in the product consistent, honest, translatable and lint-checked.
**Steps.**
1. Write `docs/UX/CONTENT.md`: voice and tone (B11.12), vocabulary (one canonical term per concept: domain vs site, orange cloud vs proxied, block vs deny, ban vs jail entry), capitalization, punctuation, number and date formats.
2. Write the glossary used in the UI with plain-language definitions for security terms (WAF, SQL injection, XSS, DNS, nameserver, CNAME, TLS, HSTS, origin, ban, challenge, Ray ID).
3. Define patterns for messages: success, validation error, system error, destructive confirmation, empty state, limit reached, security notice, email subject lines.
4. Extend `docs/claims-lint.toml` with context rules (for example the word "protect" must be accompanied by a scope within 12 words in marketing pages) and add test fixtures of passing and failing sentences.
5. Draft the copy deck keys of B13 in `i18n/en/*.ftl` skeletons (empty values flagged) with naming conventions.
6. Define placeholders and plural rules for translators (Fluent selectors), forbidding string concatenation for sentences.
7. Define the error-message tone for visitors (block pages never blame, never reveal detection logic).
8. Review all B13 strings against the claims policy.
**Deliverables.**
- `docs/UX/CONTENT.md`, `docs/UX/glossary.md`, `i18n/glossary.md`
- extended `docs/claims-lint.toml` and fixtures
**Acceptance.**
- A1: every term in the glossary has a one-sentence plain definition.
- A2: B13 strings pass claims-lint and the style rules.
- A3: message patterns include at least ten examples each with the i18n key.
- A4: translation guidance forbids concatenated sentences and includes plural examples.
- A5: claims-lint context rules have passing and failing fixtures.
**Tests.**
- `cargo xtask claims-lint` with the new fixtures; unit tests for context rules.
**Notes.** This document is the reference for all later copywriting tasks.

## Definition of done for this task's tags (section 0.7)

### `[DOC]`: Documentation

Every claim backed by a test ID or a command the reader can run; passes claims-lint; included in the docs site if user-facing.

### `[SEC]`: Security-relevant logic

Abuse cases written as tests; STRIDE delta in `docs/STRIDE.md`; no secret in logs; constant-time comparison where secrets are compared; failure modes fail closed; panic-free on hostile input (proptest or fuzz target).
