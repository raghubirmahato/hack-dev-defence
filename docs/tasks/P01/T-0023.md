### T-0023 · Internationalization and localization strategy
`P01` `[DOC]` · deps: T-0019 · size: S · owner: ux
**Objective.** Make the UI translatable from day one without committing to many languages.
**Steps.**
1. Choose the message format (Fluent) and define key naming, file layout (`i18n/<locale>/<area>.ftl`), fallbacks, pseudo-locale for testing (accented, expanded 40%), and RTL readiness (logical CSS properties, `dir` handling, mirrored icons list).
2. Define locale negotiation order (account setting, cookie, `Accept-Language`, default) and how the `lang` attribute is set.
3. Define date, time, number, relative-time and unit formatting rules, and time zone handling (UTC storage, user zone display).
4. Define what is not translated (Ray IDs, rule IDs, API identifiers, log lines) and what is (UI, emails, errors, docs).
5. Define email localization (templates per locale, fallback).
6. Define the translator workflow without external SaaS: export keys with context notes, import, lint for missing/unused keys and placeholders.
7. Define the locales to ship at launch (from `locales` in the profile; default English only) and the criteria to add one.
8. Define test strategy: pseudo-locale visual test for overflow, missing key detection, plural tests.
**Deliverables.**
- `docs/UX/I18N.md`
**Acceptance.**
- A1: the key naming convention has at least 10 examples.
- A2: RTL readiness list is concrete (CSS logical properties, icon mirroring list).
- A3: the translator workflow needs no external service.
- A4: not-translated list is explicit.
- A5: test strategy includes pseudo-locale overflow checks.
**Tests.**
- Implemented by T-0082 and the `xtask i18n check`.
**Notes.** Shipping additional languages is a product decision (Appendix E8).
