### T-0020 · Error-handling UX model and visitor-facing error philosophy
`P01` `[DOC][SEC]` · deps: T-0019 · size: S · owner: ux
**Objective.** Define how errors look, what they reveal, and how users recover.
**Steps.**
1. Map error classes (validation, permission, not found, conflict, rate limit, quota, upstream, system, maintenance) to UI patterns (inline, summary, toast, banner, page) with decision rules.
2. Define the request ID display and copy pattern, and what support can do with it.
3. Define retry and idempotency behavior for user-initiated actions and background polls.
4. Define the visitor-facing error pages (S-140 to S-148) tone and content constraints: no rule names, no stack traces, no internal hostnames, no tenant leakage.
5. Define offline and flaky-network behavior for HTMX partial updates (retry affordances, no silent failure).
6. Define how long-running job failures surface (notification plus inline status).
7. Define the logging of errors (what is logged client-side: nothing; server-side: structured).
8. Define the accessibility of errors (focus, `role="alert"`, text, not color only).
**Deliverables.**
- `docs/UX/ERRORS.md`
**Acceptance.**
- A1: each class has a pattern and an example from the ERR catalog.
- A2: the visitor-page constraints are testable statements.
- A3: retry rules differentiate safe from unsafe actions.
- A4: accessibility requirements are stated per pattern.
- A5: security review notes: no enumeration, no stack traces.
**Tests.**
- Review checklist; implemented by T-0079 and T-0085.
**Notes.** Offline behavior for the PWA is deferred to P32 but the patterns are defined now.
