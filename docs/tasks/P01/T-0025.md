### T-0025 · Security UX: dangerous actions, lockout prevention, honest warnings
`P01` `[DOC][SEC]` · deps: T-0017 · size: M · owner: ux
**Objective.** Make it hard to hurt yourself with a security product.
**Steps.**
1. Catalog every dangerous action (domain removal, DNS delete, NS change guidance, block-mode switch, ban, access-list deny, geo-block, rule with broad scope, safe mode, origin lockdown, API key creation, MFA removal, org deletion, global changes).
2. For each define: risk, safeguard (preview, dry-run, typed confirmation, time box, step-up), undo path, audit event, and the copy.
3. Define the self-lockout guard algorithm requirements (detect acting IP, session, admin CIDR collisions; where the check runs; how it is displayed).
4. Define the preview ("what would change") patterns for DNS, rules, access lists and policies.
5. Define typed-confirmation rules (exact resource name; case-sensitive; paste allowed).
6. Define the time-box pattern (auto-revert timer visible; extend explicitly).
7. Define the honest-limits placements (shield, virtual patches, readiness, block mode collateral).
8. Define the abuse cases of the UI itself (clickjacking, CSRF, UI redress, confused deputy in impersonation) and requirements that counter them.
**Deliverables.**
- `docs/UX/SECURITY-UX.md`, `docs/UX/dangerous-actions.md`
**Acceptance.**
- A1: at least 20 dangerous actions are cataloged with all fields.
- A2: the self-lockout guard has testable requirements.
- A3: each time-boxed feature specifies the revert behavior if the browser closes.
- A4: abuse cases link to ATK-285 to ATK-300.
- A5: copy for each confirmation exists as i18n keys.
**Tests.**
- Implemented as acceptance criteria in T-0327 (self-lockout), T-0235, T-0094 and others.
**Notes.** R-19 and R-28 are enforced here.
