### T-0487 · `hdd-scan`: read-only posture scanner with allowlist, consent and rate limits
`P27` `[DP][SEC][API]` · deps: T-0413, T-0164, T-0410 · size: XL · owner: sec
**Objective.** Check the owner's own sites for common misconfigurations safely and repeatably.
**Steps.**
1. Implement `hdd-scan` as a worker-hosted scanner (and `hddctl scan` CLI) with a **target allowlist enforced in code**: in `owner_only` mode `test_hostname`, `sandbox_hostname` and the operator's declared origin; in `saas` mode only verified domains of the requesting org with explicit per-domain consent (`posture_scan_enabled`), and the platform's own surfaces for self-checks; every scan writes an audit record with target and checks run.
2. Enforce **limits**: ≤ 5 requests/s per target, ≤ 300 requests per scan, concurrency 2, 10 s timeout per request, scan duration cap 10 minutes, identification via `User-Agent: HackDevDefence-PostureScan/1 (+https://<public_host>/docs/scanner)` and a documented source IP set so owners can allowlist it; scans are rate-limited per domain (1/hour manual, 1/day scheduled by default).
3. Implement **checks (read-only)**: security headers (HSTS, CSP, XFO/frame-ancestors, nosniff, Referrer-Policy, Permissions-Policy), cookie flags (from responses seen), TLS configuration (versions, ciphers, certificate chain/validity, HSTS preload readiness, ALPN) using the in-house TLS probe (no external service), version disclosure headers, directory listing on common paths **only** on the sandbox/test hostname or paths that responded with indexes, default pages (server welcome pages), risky HTTP methods (`OPTIONS` read, `TRACE` check), CORS misconfiguration (reflect arbitrary Origin with credentials), open redirect probes **only against the canary**, `robots.txt`/`security.txt` presence, HTTP→HTTPS redirect behavior, mixed content hints in fetched HTML, and dangling CNAME/takeover candidates in managed zones (DNS resolution only; no HTTP requests to third-party hosts).
4. Implement **sensitive-path probes** (backup files, `.git/`, `.env`, admin panels) as an opt-in *origin-direct* check run from the VPS (which is on the origin allowlist) so it does not trip HDD's honeypots or bans; results report existence (status/size class) only and never download or store contents beyond the first 256 bytes signature check.
5. Implement **no-exploitation guarantees**: no payload injection, no fuzzing, no authentication attempts, no brute force; the scanner's request builder only supports a fixed set of benign request templates; a static test enumerates all templates and fails on any parameterization beyond the canary token.
6. Output a normalized **findings model** (`scan_runs`, `scan_findings`: id, check id, severity, evidence (headers/status only), remediation key, first_seen, last_seen, status `open|accepted_risk|fixed`), diffing between runs, and accepted-risk with reason and expiry.
7. Wire into UI: S-043 scan summary card, S-044 readiness inputs, a scan history list, "Run scan now" with the consent/allowlist explanation, and links to remediation text (T-0488).
8. Write tests: allowlist enforcement (attempts to scan non-allowed targets abort and are audited), rate-limit adherence (token bucket verified against a counting server), check correctness against fixture origins (good and bad configurations for each check, ≥ 60 fixtures), no-exploitation template test, TLS probe against lab servers with various configs, consent flows in `saas` mode, and BOLA tests.
**Deliverables.**
- `hdd-scan`, `hddctl scan`, findings model, UI cards, tests, docs `docs/SCANNER.md`
**Acceptance.**
- A1: scans of non-allowlisted or non-consented targets are refused and audited.
- A2: measured request rate never exceeds 5 req/s (counting server over 20 scans).
- A3: every check yields correct pass/fail on the fixture origins.
- A4: the scanner sends no payloads beyond the benign templates (static enumeration test).
- A5: findings diff correctly between runs and accepted-risk expires.
**Tests.**
- Unit, fixture-origin integration, rate tests, static gates.
**Notes.** Active exploit-class testing happens only against the sandbox canary or the Vuln-Lab (C12.5).
