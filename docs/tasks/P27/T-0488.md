### T-0488 · Origin-hardening report generator and remediation library
`P27` `[DOC][API][UI]` · deps: T-0487, T-0484, T-0165 · size: M · owner: docs
**Objective.** Turn findings into a prioritized, actionable report the owner can hand to a developer.
**Steps.**
1. Build the **remediation library**: a versioned set of remediation entries keyed by check id (`hdr.hsts.missing`, `cookie.flags`, `tls.min_version`, `dir.listing`, `cors.reflect`, `disclosure.version`, `db.least_privilege`, `sql.parameterized`, `input.validation`, `secrets.management`, `auth.hardening`, `backups`, `logging`, etc.) with: why it matters, how to fix for common stacks (nginx, Apache, Express, Django, Rails, Laravel, Spring, ASP.NET, WordPress), verification steps, references, effort and impact estimates.
2. Implement the generator for `docs/ORIGIN-HARDENING.md` (operator, owner_only mode) and per-domain downloadable reports (HTML/PDF/Markdown) assembled from scan findings, exposure board items, origin exposure findings (T-0407), lockdown state and readiness score inputs: sections Summary, Top risks, Findings by category, Dependencies requiring real fixes (links to exposure items), Application-level recommendations (parameterized queries, least-privilege DB credentials, input validation, secrets management, authentication hardening, backups, logging), and a **"What HDD does and does not do"** box (WAF reduces exposure; the application still needs the fixes).
3. Rank findings with a deterministic priority score (severity × exposure × ease of fix) documented in `docs/EXPOSURE-POLICY.md`; ties broken by id; the top 10 appear in S-043 and S-044.
4. Add **tracking**: each finding/recommendation can be assigned to an owner, marked accepted risk (reason, expiry) or fixed (verified by the next scan), with history and a burn-down chart (table alternative).
5. Include **SQL-injection-specific guidance** because the product emphasizes it: parameterized queries examples per language, ORM caveats, stored procedure pitfalls, least-privilege DB user template (SQL snippets for MySQL/PostgreSQL/SQL Server), error message suppression, and how to verify with the Vuln-Lab-style tests (links to HDD docs, not tools that attack third parties).
6. Ensure claims discipline: wording is "recommendations"; HDD tracks but does not perform them; the claims-lint covers the library and generated reports.
7. Support localization structure and accessibility of generated HTML/PDF (reuse T-0448 pipeline).
8. Write tests: golden report snapshots for three scenario fixtures, priority scoring unit tests, tracking state transitions, claims-lint, remediation coverage (every check id has an entry; CI fails on missing), and PDF accessibility validation reuse.
**Deliverables.**
- remediation library, generators, tracking UI, tests, docs
**Acceptance.**
- A1: every scanner check and exposure item type has a remediation entry (coverage test).
- A2: golden reports render deterministically from fixture findings.
- A3: the report always contains the "what HDD does and does not do" box.
- A4: marking a finding fixed is verified (or flagged unverified) by the next scan.
- A5: claims-lint passes on the library and reports.
**Tests.**
- Golden, unit, claims-lint, coverage tests.
**Notes.** This is the document the operator reviews before cutover (C17.2 gate 4).

## Definition of done for this task's tags (section 0.7)

### `[DOC]`: Documentation

Every claim backed by a test ID or a command the reader can run; passes claims-lint; included in the docs site if user-facing.

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.
