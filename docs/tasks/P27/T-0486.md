### T-0486 · Passive origin fingerprinting and client-side library detection
`P27` `[DP][API]` · deps: T-0482, T-0164 · size: M · owner: sec
**Objective.** Learn component versions from what the origin already reveals, without probing aggressively, and keep confidence honest.
**Steps.**
1. Implement **passive fingerprinting from observed responses** (headers and sampled HTML only, no extra requests beyond the owner's connectivity test and the posture scanner's allowed requests): `Server`, `X-Powered-By`, `X-Generator`, `<meta name="generator">`, WordPress `?ver=` asset query strings and `/wp-content/plugins/<slug>/` paths with readme versions only if observed in responses, Drupal/Joomla markers, framework cookies (`laravel_session`, `JSESSIONID`), error-page signatures, and static asset names with versions (`jquery-3.5.1.min.js`, `bootstrap.bundle.4.3.1.js`).
2. Implement **client-side library detection** (retire.js-style, but data-driven and offline): a signed fingerprint database mapping file name patterns, content hashes (SHA-256 of known versions), and in-file version comment regexes to library/version; apply to third-party scripts discovered by the CSP/crawl inventory (T-0412) and to the origin's own scripts when the owner opts in; output components with `source=scan`, `confidence=inferred|verified` (hash match = verified).
3. Treat sources of truth: `Server` banners and generators are **claims by the origin** (low confidence); hashes and distinctive file contents are strong evidence; the UI labels confidence and encourages replacing with SBOM data.
4. Implement privacy and limits: sample at most 1 response per distinct path template per hour per site, response bodies are processed in memory for the first 64 KiB only, only extracted tokens are stored, never page content.
5. Implement the **fingerprint database tooling** (`xtask fingerprints build|verify`): sources are open-licensed data; build from release artifacts with hash tables; sign the DB; versioned updates through the same pack mechanism with staged rollout.
6. Integrate with inventory: scan-sourced components are proposed to the owner ("We noticed jQuery 1.12.4 on /shop; add to inventory?") with accept/ignore; accepted items are matched; ignoring is remembered; scan-sourced items auto-expire if not seen for 30 days.
7. Add guard rails: fingerprinting never triggers extra requests to third-party hosts (no fetching of external scripts to hash them, except the SRI advisor's explicit fetch under its own limits), and honors the egress allowlist.
8. Write tests: fixtures of real-world-shaped HTML/headers for ≥ 40 stacks, hash-match verification, false positive tests (strings in documentation pages), confidence assignments, expiry, privacy greps (no page content stored), and DB signature verification.
**Deliverables.**
- fingerprint engine, DB tooling, proposal UI, tests
**Acceptance.**
- A1: fixture stacks yield the expected components with the documented confidence levels.
- A2: no response content beyond extracted tokens is stored.
- A3: tampered fingerprint databases are rejected.
- A4: proposals are accepted/ignored with memory and auto-expiry.
- A5: no extra outbound requests are made to third-party hosts.
**Tests.**
- Unit, fixtures, privacy greps, signature tests.
**Notes.** AG-16 coverage (client-side supply chain) completes here together with T-0412.
