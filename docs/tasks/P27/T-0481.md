### T-0481 · `hdd-vuln` feed ingestion: OSV, NVD, CISA KEV, EPSS, RustSec and operator-named advisories
`P27` `[DP][API][OPS]` · deps: T-0348, T-0413, T-0214 · size: L · owner: sec
**Objective.** Keep a local, verified, bounded copy of the vulnerability intelligence that matching depends on.
**Steps.**
1. Implement feed adapters in `hdd-vuln`: OSV (bulk ecosystem archives and the API for targeted queries), NVD (JSON 2.0 API with the operator's API key if supplied, rate-limit aware), CISA KEV (JSON catalog), EPSS (daily CSV), RustSec advisory database (git or archive snapshot, for HDD's own dependencies), and a generic "vendor/ecosystem advisory" adapter for operator-named JSON/Atom/CSAF feeds.
2. Fetch only through the egress client from **pinned hosts** (configuration allowlist such as `api.osv.dev`, `osv-vulnerabilities.storage.googleapis.com`, `services.nvd.nist.gov`, `www.cisa.gov`, `epss.cyentia.com`/`epss.empiricalsecurity.com`, `github.com/rustsec/advisory-db` archive URL), HTTPS only, TLS verified, size-bounded (per-feed caps), time-bounded, with `If-None-Match`/`If-Modified-Since` conditional requests and checksum or signature verification where the source offers it (for example OSV archive checksums, git commit signatures for RustSec when feasible); verification failures reject the update and alert.
3. Implement **offline mode** (`vuln_feed_mode: offline`): `hddctl vuln import --file <archive> --sha256 <hash>` imports operator-supplied feed files after verification; the UI states the age of the data (`as_of`) prominently, and staleness thresholds (OSV 48 h, KEV 48 h, EPSS 7 d, NVD 7 d) raise attention items.
4. Normalize into a local schema (`advisories`, `advisory_affected`, `advisory_references`, `epss_scores`, `kev_entries`) with idempotent upserts, source provenance, ranges in a canonical form (ecosystem, package name/purl, introduced/fixed/last_affected events) and aliases (CVE/GHSA/RUSTSEC/OSV ids) merged by alias graph; store only the fields needed (no large descriptions beyond 4 KiB, references capped) to keep storage bounded.
5. Implement content-safety rules: descriptions are treated as untrusted text (escaped in UI, truncated, stripped of HTML), URLs are validated and displayed as text with `rel=noopener noreferrer` links only to allowlisted advisory domains, and feed entries can never change configuration or trigger actions beyond creating matches.
6. Implement scheduling in `hdd-worker`: OSV/KEV daily with jitter, EPSS daily, NVD incremental every 2 hours when a key exists (otherwise daily), RustSec daily; backoff on failures; per-feed health metrics and attention items (`feed_failing`, `feed_stale`).
7. Provide `xtask vulnfeeds verify-ids` used at build time by other tasks (for example virtual-patch packs) to verify CVE identifiers and affected/fixed versions against OSV/NVD, recording `UNVERIFIED(capability_not_supplied)` for any identifier that cannot be verified offline.
8. Write tests: adapter parsing against saved real-format fixtures (OSV, NVD 2.0, KEV, EPSS, RustSec), range normalization (semver, PEP 440, Maven, npm, Packagist, Go pseudo-versions), alias merging, conditional requests, checksum failure rejection, oversize and malformed feed handling, hostile description strings (XSS/CRLF), pinned-host enforcement (a request to an unlisted host is refused), and offline import verification.
**Deliverables.**
- `hdd-vuln` feed layer, schema migrations, `hddctl vuln import`, `xtask vulnfeeds`, tests, docs
**Acceptance.**
- A1: a corrupted or checksum-mismatched feed update is rejected and the previous data keeps serving.
- A2: requests to hosts outside the pinned list are refused by the egress client (negative test).
- A3: all fixture formats normalize into identical canonical ranges where the underlying advisory is the same (alias merge tests).
- A4: feed staleness thresholds produce attention items.
- A5: untrusted advisory text is escaped everywhere it is displayed (XSS corpus).
**Tests.**
- Unit (parsers, ranges), integration (local feed server), security, offline import tests.
**Notes.** NVD's rate limits and API-key policy are checked at build time; do not assume them.

## Definition of done for this task's tags (section 0.7)

### `[DP]`: On the data-plane hot path (proxy, DNS, WAF, firewall)

Hot path never awaits the database; bounded memory and queues; criterion benchmark or histogram; fuzz or proptest; behavior when Redis or Postgres is down specified and tested; metric with drop counter.

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.

### `[OPS]`: Deployment, operations, runbooks

Idempotent; dry-run mode; documented undo; SSH-lockout protection for host-affecting changes; restore or rollback exercised.
