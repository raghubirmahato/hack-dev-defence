### T-0489 · Vulnerability management acceptance: AC-30, AC-31, AC-32
`P27` `[QA][LAB]` · deps: T-0485, T-0486, T-0487, T-0488 · size: L · owner: qa
**Objective.** Prove inventory, matching, SLA behavior, virtual patches and posture scanning work together on realistic inputs.
**Steps.**
1. **AC-30 (inventory and exposure):** import fixture SBOMs/lockfiles (log4j 2.14.1, Struts 2.3.x, Spring 5.3.17, Django 3.2.0, jQuery 1.12.4, WordPress plugin versions, OpenSSL package) and a pilot-origin component list supplied by the operator (UNVERIFIED(`capability_not_supplied`) if absent); verify matches, KEV/EPSS enrichment from the current feed snapshot (or the offline snapshot fixture with its date), SLA clocks, alerts at 50%/90%/overdue (time-accelerated) and attention items; verify that the cutover gate indicator reflects overdue KEV/critical items.
2. **AC-31 (virtual patches):** run the evidence harness for the seeded pack; deploy patches through monitor to block on the sandbox host with Class A shapes; verify `would_block` counts, benign pass rates on the baseline replay, expiry alerts (time-accelerated), automatic status reversion on expiry, retirement flow, signed-pack tamper rejection and rollback; verify R-11 (virtually patched items remain open with ticking clocks).
3. **AC-32 (posture and hardening):** run `hdd-scan` against the sandbox/test hostname and the operator's origin (if allowlisted) and compare findings to a known-state fixture origin in the lab (good/bad configurations); verify rate adherence (counting server), allowlist refusals, consent flow, generated `docs/ORIGIN-HARDENING.md` content and tracking transitions; record the sensitive-path origin-direct check results for the pilot origin as opt-in.
4. Verify **feeds in the field:** run live feed updates from pinned hosts if egress is allowed on the pilot, with timing and size metrics; otherwise exercise offline import and mark live pulls UNVERIFIED(`capability_not_supplied`).
5. Run the **secure-development hooks** for HDD itself that relate to this phase: `cargo audit` against the RustSec snapshot ingested by `hdd-vuln`, advisory SLA computation for HDD dependencies (72 h for exploited/critical, 14 days others), and verification that exceptions have expiry.
6. Hostile review: feed poisoning (malformed advisories crafted to match everything, huge ranges), VEX abuse (mass `not_affected` without justification), scanner SSRF attempts (redirects to internal targets, DNS rebinding), and tenant cross-visibility of components.
7. Archive evidence with SHA-256 and update STATUS for AC-30, AC-31, AC-32.
8. Update `docs/EXPOSURE-POLICY.md` with the measured behavior and limitations.
**Deliverables.**
- evidence bundle, updated docs and status lines
**Acceptance.**
- A1: AC-30 PASS on fixtures (and pilot inputs if supplied).
- A2: AC-31 PASS including R-11 invariants and expiry behavior.
- A3: AC-32 PASS on the lab fixture origin and the sandbox host; rate and allowlist guarantees hold.
- A4: feed poisoning and VEX abuse attempts are contained (tests).
- A5: UNVERIFIED items list exact reasons.
**Tests.**
- Live and lab runs, time-accelerated tests.
**Notes.** Matches are only as good as the inventory; the report says so.
