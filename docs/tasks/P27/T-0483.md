### T-0483 · Matching engine: purl-based matching, version ranges, CPE low confidence and VEX
`P27` `[DP][API]` · deps: T-0481, T-0482 · size: L · owner: sec
**Objective.** Produce accurate, explainable matches between components and advisories with human-reviewable false-positive handling.
**Steps.**
1. Implement the matcher: primary path matches by purl (ecosystem + normalized name) against advisory affected packages with ecosystem-specific version comparison (semver, PEP 440, Maven ComparableVersion, npm semver, Packagist, RubyGems, Go modules, NuGet, Debian dpkg version, RPM); `introduced`/`fixed`/`last_affected` events are evaluated exactly per OSV semantics.
2. Implement the **CPE path** for NVD-only records: matches are marked `confidence=low` with the CPE configuration evidence, require review before alerts, and are excluded from SLA clocks until confirmed (documented to avoid alert fatigue).
3. Record **evidence** for each match: component id and provenance, advisory id and aliases, the matched range and event that matched, the component's version source and confidence, and timestamps; the UI shows an "Why is this a match?" panel.
4. Implement **VEX** support: statements `not_affected` (with justification codes: component_not_present, vulnerable_code_not_present, vulnerable_code_not_in_execute_path, vulnerable_code_cannot_be_controlled_by_adversary, inline_mitigations_already_exist), `affected`, `fixed`, `under_investigation`; each requires a reviewer, a free-text justification, an optional expiry (default 180 days, then re-review), and an audit event; importing OpenVEX/CycloneDX VEX documents is supported with validation.
5. Implement **update triggers**: re-match when advisories change, components change, or VEX expires; incremental matching (only affected components) with batch limits; deduplicate matches per (component, advisory alias set).
6. Implement handling of unknown versions: produce `possible` matches only when the advisory affects all versions or the package has no fixed release; otherwise record "version unknown: cannot assess" counters per component, shown in the exposure views.
7. Implement safe handling of large result sets (cap 10,000 open matches per org with a warning), ranking by risk (KEV, EPSS, CVSS, internet-facing), and pagination.
8. Write tests with a **fixture matrix** (≥ 150 cases): known vulnerable versions across ecosystems with expected matches (for example log4j-core 2.14.1, spring-framework 5.3.17, Django 3.2.0, jQuery 1.12.4, lodash 4.17.15, WordPress core and a plugin version, openssl package versions, Struts 2.3.x), boundary versions (just before/after fix), pre-release/epoch/build metadata cases, multiple ranges per advisory, alias dedupe, VEX transitions and expiry, and false-positive controls.
**Deliverables.**
- matcher, VEX handling, evidence model, tests, docs `docs/EXPOSURE-POLICY.md`
**Acceptance.**
- A1: the fixture matrix produces exactly the expected matches (precision and recall 100% on the fixtures).
- A2: CPE-only matches never raise alerts or start SLA clocks until confirmed.
- A3: VEX statements require justification and reviewer and expire as configured.
- A4: unknown versions never produce confirmed matches.
- A5: re-matching is incremental and idempotent (property tests).
**Tests.**
- Unit matrix, property, integration.
**Notes.** Version comparison libraries are validated against reference datasets per ecosystem.
