### T-0334 · Per-path and auth-endpoint rate rules (engine side)
`P17` `[DP][SEC]` · deps: T-0333, T-0230 · size: M · owner: dp
**Objective.** Apply the owner's rate rules and the auth-endpoint presets accurately.
**Steps.**
1. Compile `rate_limit_rules` into an indexed structure: exact paths and prefixes in a radix tree, glob patterns, method sets, scope/limit/window/action, ordered by specificity then priority, with caching of match results per route key.
2. Implement the **auth-endpoint presets**: for declared/detected auth endpoints apply Balanced 10/min per IP per path, Paranoid 5/min, with an additional per-account-HMAC counter (T-0343) and burst allowance 3; apply session-scoped limits for authenticated APIs when configured.
3. Implement conflict resolution (most specific rule wins; if equal, lowest limit) and explain the effective rule in the verdict/event.
4. Implement action semantics: `429` (default), `challenge` (serve challenge instead), `ban after N violations` (default 5 violations in 10 minutes with the rate-limit ladder first step 10 min).
5. Implement dry-run simulation support: compute from the traffic sample what would have been limited (used by S-061).
6. Implement special exemptions: ACME challenge paths, `/__hdd/*`, health checks, allowlisted keys.
7. Add table tests (60 rule sets) and a differential test comparing compiled matching to a naive evaluator on random paths.
8. Document rule semantics.
**Deliverables.**
- compiler, matcher, tests
**Acceptance.**
- A1: effective rule selection matches the naive evaluator on 100k random cases.
- A2: auth-endpoint presets apply to declared endpoints only.
- A3: exemptions work and cannot be abused by path tricks (`/__hdd/../login` normalizes first).
- A4: simulation counts equal actual replays against the limiter in tests.
- A5: rule changes apply within 2 s.
**Tests.**
- Differential/property tests; integration.
**Notes.** Path normalization happens before matching to avoid bypass (ATK-153).
