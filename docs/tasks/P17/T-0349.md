### T-0349 · Adaptive thresholds and baselines
`P17` `[DP][API]` · deps: T-0333, T-0140 · size: M · owner: dp
**Objective.** Detect abnormal traffic relative to each site's own normal.
**Steps.**
1. Maintain per-site baselines (EWMA and robust percentile estimates) for request rate, error rate, 404 ratio, unique client keys per minute, origin latency and bytes, by hour-of-week seasonality (168 buckets) learned over time with minimum history before use.
2. Compute anomaly scores (z-score with MAD scaling) and define states: normal, elevated (> 3), severe (> 5); require sustained duration (≥ 2 minutes) to avoid flapping; expose through metrics and the shield input (P26).
3. Use baselines to adapt actions: per-site automatic tightening of rate limits (temporary multipliers 0.5) during severe states, triggering under-attack mode (T-0339) per configuration, and campaign thresholds scaling with traffic volume.
4. Provide owner visibility: baseline charts with bands in S-070, explanations for adaptive actions, opt-out per site.
5. Ensure learning excludes known attack periods (do not learn from bans/under-attack intervals) to avoid poisoning baselines.
6. Implement storage (compact rollups in Postgres) and warm start after restarts.
7. Test with synthetic seasonality and attack injections.
8. Document limits and guidance for small sites with sparse traffic.
**Deliverables.**
- baseline engine, adaptive hooks, UI bands, tests
**Acceptance.**
- A1: a 10x request spike for 3 minutes on a stable site produces `severe` and triggers configured actions.
- A2: daily seasonality does not trigger false alarms across a simulated week.
- A3: attack periods are excluded from learning.
- A4: sparse sites do not trigger spurious adaptation (minimum history rule).
- A5: owners can disable adaptation.
**Tests.**
- Simulation tests (time series generators); unit: MAD/EWMA math; property tests.
**Notes.** Provides input to ATK-208.
