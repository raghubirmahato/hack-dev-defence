### T-0470 · Closed-lab flood harness (`hdd-loadgen` lab mode, namespaces, xtask lab)
`P25` `[LAB][QA]` · deps: T-0463, T-0467 · size: L · owner: qa
**Objective.** Generate realistic L3/L4 attack traffic safely and repeatably, only inside infrastructure the operator owns.
**Steps.**
1. Implement `xtask lab up|down|status` creating a network-namespace topology (attacker ns, victim ns hosting the real HDD stack or the real proxy/DNS binaries on veth/bridge links, optional "legit client" ns) using netlink via a Rust crate or `ip` invoked with argument arrays; a two-machine mode supports operator-owned machines on a private link (explicit configuration and confirmation phrase).
2. Implement `hdd-loadgen lab` generators (raw sockets / AF_XDP-free simple generators first, optionally `pktgen` guidance): SYN floods with spoofed and unspoofed sources, ACK/RST floods, UDP floods to published and unpublished ports, fragment floods, invalid TCP flag combinations, ICMP floods, reflection-pattern floods (UDP packets with source ports 53/123/389/1900/11211 to published ports), and mixed legitimate-client traffic generators (HTTP/1.1 and HTTP/2 GETs, DNS queries) to measure collateral damage.
3. Enforce the **lab guard rails in code**: generators refuse to send unless the target address is inside the lab namespaces (RFC 1918/ULA ranges attached to lab interfaces) or on the operator-confirmed private link; they check that the egress interface is the lab veth; they enforce maximum rates and durations; they never open sockets to the default route; a kill-switch file stops them; any attempt to target a non-lab address aborts and writes an audit record.
4. Implement measurement: legitimate-traffic success rate and latency, drop ratios by reason (XDP counters, nftables counters), pps/bps handled, CPU and memory of the stack, conntrack occupancy, with a recorder producing JSON and Markdown reports and Prometheus snapshots.
5. Implement scenario files (`lab/scenarios/*.yaml`): baseline (no mitigations), nftables-only, XDP generic, XDP native (if the lab NIC supports it), each with the same attack set, plus an escalation scenario that replays traffic against `hdd-shield` (P26).
6. Publish `docs/lab/` with the topology diagrams (SVG), prerequisites (kernel features, privileges), safety notes, hardware notes, and instructions for two-machine setups; mark all numbers produced as lab-only.
7. Add CI integration: unprivileged smoke (guards and generators unit-tested without sending) and privileged nightly runs on a lab runner if available (UNVERIFIED(`capability_not_supplied`) otherwise).
8. Write tests for the guards: attempts to target public addresses, loopback of the host (outside lab), default-route interfaces, and rate/duration overruns must all abort; log lines prove no packet was sent.
**Deliverables.**
- `xtask lab`, `hdd-loadgen lab`, scenarios, docs, guard tests
**Acceptance.**
- A1: every guard-violating invocation aborts before sending a packet (tests capture the socket layer).
- A2: scenarios run reproducibly (same seed → same traffic schedule) and produce reports with required fields.
- A3: legitimate traffic metrics are collected in parallel to attacks.
- A4: the lab can be torn down cleanly leaving no namespaces, interfaces or rules behind.
- A5: documentation states clearly that no flood traffic may leave the closed lab.
**Tests.**
- Unit (guards), privileged integration (lab runner), teardown tests.
**Notes.** This is the only sanctioned way to generate volumetric traffic (section 2.6).
