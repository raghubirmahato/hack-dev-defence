### T-0463 · `hdd-firewall`: Enforcer trait and nftables, ipset/iptables and no-op backends
`P25` `[DP][OPS][SEC]` · deps: T-0322, T-0212 · size: L · owner: infra
**Objective.** Implement kernel-level IP bans behind one trait with a primary and a fallback backend.
**Steps.**
1. Define `trait Enforcer { fn probe() -> Capability; fn ban(&self, key: BanKey, ttl: Duration, meta: BanMeta) -> Result<Applied>; fn unban(&self, key: BanKey) -> Result<()>; fn list(&self) -> Result<Vec<Entry>>; fn reconcile(&self, desired: &[Entry]) -> Result<ReconcileReport>; fn stats(&self) -> Stats; }` with `BanKey` = IPv4 /32 or IPv6 /64 (never anything wider by default; CIDR bans of up to /24 and /48 allowed only from the platform jail with a flag).
2. Implement the **`Nftables` backend** (primary): a dedicated table `inet hdd` with sets `banned4` (`ipv4_addr`, flags `timeout`) and `banned6` (`ipv6_addr`, prefix-aware via `interval` set for /64), element timeouts natively handled by the kernel, rules in a base chain with priority before conntrack (`raw` hook prerouting at `-300`) that `drop` packets from banned addresses to the destination ports in a `proxied_ports` set (80, 443, and UDP 443 when enabled); application via `nft -f -` with a generated script passed on stdin (argument arrays only, never a shell string) or via the netlink crate if the ADR prefers it; atomic updates with `nft -c` validation before commit.
3. Implement the **`IpsetIptables` backend** (legacy fallback): `ipset` hash:ip / hash:net with timeouts, idempotent `iptables -C`/`-I` (and `ip6tables`) rules in a dedicated `HDD_BAN` chain jumped from `PREROUTING` raw; the backend is used only when `nft` is unavailable; both backends are never active simultaneously (probe order documented, mutual exclusion enforced).
4. Implement the **`Noop` backend** for hosts without capabilities: records requested bans, reports `unsupported` acknowledgments, and surfaces a WARN in preflight and the admin console (S-128).
5. Implement the **capability probe**: root/`CAP_NET_ADMIN` check, kernel module availability (`nf_tables`, `nft_set_hash`, `nft_set_rbtree`), nft version, IPv6 support, container detection (refuse to run inside an unprivileged container with a clear message), and interplay with Docker chains (the agent never touches Docker's chains and detects Docker's `FORWARD` policy to warn about published ports bypassing input rules).
6. Implement the **safety rules in code**: refuse to ban loopback, link-local, the host's own addresses, `admin_cidrs`, `ssh_allow_cidrs`, provider health-probe ranges and the DNS secondary's addresses (checked against the never-ban list on every call); refuse sets over the configured cap (default 100,000 elements) and report overflow; ban TTL bounds (60 s to 30 d).
7. Implement set-size and memory accounting, element-count metrics, and the reconcile algorithm (diff desired vs actual; add missing, remove expired/extra, bounded batch sizes of 500 per `nft` transaction).
8. Write tests: unit tests for script generation (golden files, including IPv6 /64 handling and timeout formatting); integration tests inside a network namespace with real `nft` (requires privileged lab, marked `#[ignore]` outside it) verifying drop behavior using `hdd-loadgen` TCP connects before/after ban and after TTL expiry; the shared contract suite from T-0322 run against each backend; negative tests for refused keys.
**Deliverables.**
- `hdd-firewall` crate, backends, probes, tests, docs `docs/FIREWALL.md`
**Acceptance.**
- A1: a banned IPv4 address cannot complete a TCP handshake to :443 within 2 s of `ban` and can again after `unban` (netns test).
- A2: element timeouts expire bans in the kernel without agent action (timing test).
- A3: bans for never-ban keys and for non-proxied ports are refused by code.
- A4: the contract suite passes for `Nftables`, `IpsetIptables` (where available) and `Noop`.
- A5: no shell invocation exists in the crate (static grep gate).
**Tests.**
- Unit (golden), privileged integration in netns, contract, static gate.
**Notes.** The proxy's L7 jail remains authoritative; the kernel layer is an accelerator that sheds attackers cheaply (C11.3 L1).
