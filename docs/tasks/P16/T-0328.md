### T-0328 · Ban ladder decay, caps and eviction
`P16` `[DP][OPS]` · deps: T-0317 · size: S · owner: dp
**Objective.** Keep the ban system bounded and fair over time.
**Steps.**
1. Implement decay: offence counters expire after the quiet window (default 30 days) and decrement gradually (optional "forgiveness" mode: after 7 quiet days reduce one step) configurable per site.
2. Implement caps: per node 100,000 active bans; per org 50,000; per site 20,000 (plan-adjustable); exceeding triggers oldest-expiry eviction of automatic bans (never manual/platform) with `MET-hdd_ban_eviction_total` and an alert at 80% usage.
3. Implement TTL maximums (cap 30 days; ladder cap 7 d by default) and minimums (60 s tests).
4. Implement periodic cleanup of expired Postgres rows (retain history 90 days as `released/expired` for forensics, then archive aggregates).
5. Implement capacity planning guidance (memory per ban entry measured).
6. Add tests for decay with the clock and eviction ordering.
7. Add dashboards (admin) for ban set sizes.
8. Document the policy.
**Deliverables.**
- decay and eviction logic, tests, docs
**Acceptance.**
- A1: decay follows the configured schedule (test clock).
- A2: eviction removes the soonest-to-expire automatic bans first.
- A3: manual and platform bans are never evicted.
- A4: caps are enforced at all three levels.
- A5: memory per entry is documented from measurement.
**Tests.**
- Unit/property tests; load test at cap.
**Notes.** Prevents unbounded growth under flood or poisoning (ATK-291).
