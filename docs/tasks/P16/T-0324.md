### T-0324 · Appeals: visitor flow, workflow and owner inbox (S-145, S-146, S-069)
`P16` `[UI][API][SEC]` · deps: T-0320, T-0065 · size: XL · owner: ui
**Objective.** Let wrongly blocked visitors report it without opening abuse vectors.
**Steps.**
1. Implement the visitor endpoints on customer domains: `GET /__hdd/appeal` (form), `POST /__hdd/appeal` (submit): fields Ray ID (prefilled via query param or hidden), optional contact email, note (500 chars), proof-of-work token (tier `appeal`, 14 bits, from the single difficulty table in C7) from `hdd-challenge`; served by the proxy (data plane), not the origin.
2. Verify the Ray ID: exists, belongs to the same site, and the submitter's IP key equals the event's key or the request is from a trusted flow (e.g., a different IP with proof) — the default rule is **IP key must match**; if it does not match, still accept but flag `ip_mismatch`; responses are identical regardless of verification result (no oracle); rate limits: 3 per hour per IP key, 10 per day per site, 100 per day per site globally.
3. Store appeals (`ban_appeals`) with encrypted contact email (deleted on resolution/expiry), snapshot of the relevant event metadata (no payloads beyond redacted evidence), and notify owners (in-app, email per alert rules).
4. Implement the owner inbox (S-069): list with status, Ray ID link to event drawer, evidence, and four actions: **Unban** (also optional "unban and allowlist for N days (max 30)"), **Create exception** (prefilled scope from event), **Decline** (reason, optional message to visitor if contact provided), auto-expire after 14 days.
5. Implement visitor notification (optional): if a contact email is provided and verified by a confirmation link (anti-abuse), send a status email via the outbox with generic text; unverified addresses never receive mail.
6. Implement abuse defenses: appeals cannot be used to enumerate Ray IDs (identical responses), cannot trigger email to arbitrary addresses (double opt-in), cannot flood owners (aggregation: group by key), and cannot bypass bans.
7. Implement visitor pages S-145/S-146 with accessibility, JSON variants, and no tenant HTML injection.
8. Add tests including abuse cases (mass submissions, Ray ID guessing, email bombing attempts).
**Deliverables.**
- data-plane endpoints, workflow, S-069, visitor pages, tests
**Acceptance.**
- A1: appeal submissions with valid and invalid Ray IDs yield identical responses and timing.
- A2: rate limits prevent mass submissions (tests at all three levels).
- A3: unverified contact emails never receive mail.
- A4: resolving an appeal with unban takes effect within 2 s.
- A5: contact emails are deleted on resolution/expiry (database inspection test).
**Tests.**
- Integration with proxy and API; abuse-case suite; browser flows for visitor pages and owner inbox.
**Notes.** AC-43 verifies the whole flow; appeals never reveal rule names.

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.
