### T-0319 · IP Jail pipeline stage and branded 403
`P16` `[DP]` · deps: T-0316, T-0318 · size: M · owner: dp
**Objective.** Reject banned clients at the earliest possible point with a consistent response.
**Steps.**
1. Implement pipeline stage 6: resolve client key, check never-ban/allowlist, then jail lookup (platform → org → site); on hit return the branded 403 immediately (HTML or JSON by `Accept`, `HDD-Ray-ID` header, `Cache-Control: no-store`, `Retry-After` not set, no hint of remaining time), connection `close` for HTTP/1.1 after the response to discourage keep-alive abuse.
2. Count jail hits per key in memory with aggregation (flush every 10 s to `event_aggregates` and metrics) instead of one event per hit; sample 1 in N full events for forensics (configurable) to avoid write amplification during floods.
3. Implement cheap early rejection at connection level for floods: if a key accumulates more than M jail hits per second (default 50), drop the TCP connection without a response (RST/close) and count it, reducing per-request work; the kernel/XDP layer takes over via P25.
4. Ensure the jail stage runs before body reading (no request body buffering for banned clients) and before TLS session resumption leaks (TLS handshake still occurs because SNI is needed; plan to drop pre-handshake via kernel when available).
5. Implement the block page rendering with the shared visitor template (S-140), Ray ID, appeals link when enabled.
6. Implement response uniformity: identical for all banned reasons (no reason leakage).
7. Add metrics (`MET-hdd_jail_hits_total`) and latency tests (jail hit path under 50 µs).
8. Test HTTP/2 behavior (RST_STREAM vs response), HEAD requests, and websocket upgrade attempts from banned clients.
**Deliverables.**
- pipeline stage, aggregation, tests
**Acceptance.**
- A1: a banned client's request receives 403 with Ray ID and never reaches inspection or origin (origin counter zero).
- A2: jail-hit flood of 100k requests generates bounded events (aggregation test).
- A3: the response is identical regardless of ban reason.
- A4: jail hit path latency p99 under 50 µs.
- A5: banned WebSocket upgrades are refused before upgrade.
**Tests.**
- Integration with load generator (functional profile), unit: aggregation; h2 tests.
**Notes.** Jail hits do not extend the ban or increment offences.
