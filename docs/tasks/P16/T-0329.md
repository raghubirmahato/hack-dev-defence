### T-0329 · Ban forensics: evidence capture, event aggregation and privacy
`P16` `[DP][API][SEC]` · deps: T-0252, T-0317 · size: M · owner: waf
**Objective.** Make every ban explainable while minimizing stored data.
**Steps.**
1. Define the ban evidence record: first triggering Ray ID, rule ID/version, category/subtype, vector and field name, redacted evidence (≤ 512 B), policy branch, config revision, TTL step, node ID, request metadata (method, path pattern, status, user agent hash), and cross-references to related events.
2. Implement per-key event aggregation: after a ban, further blocked requests increment counters; keep the first N=20 events fully and sample the rest to bound storage during floods.
3. Implement data retention and IP truncation per org policy for historical records; active bans keep the full key for enforcement but the UI honors truncation for display where configured (platform admins see full).
4. Implement the forensic bundle export for incidents (JSON/CSV) with redaction guarantees and hash chain of the export for integrity.
5. Implement UI integration: ban detail evidence panel, event drawer "Why was this IP banned?" explanation with ladder info.
6. Implement tests that evidence contains no secrets for payloads in password fields, JWTs, cookies, and Authorization headers.
7. Document privacy and legal considerations (IP as personal data), retention defaults.
8. Add metrics for evidence size distribution.
**Deliverables.**
- evidence model, aggregation, exports, tests, docs
**Acceptance.**
- A1: evidence never exceeds 512 bytes and contains no unredacted secrets (scanner over 100k events).
- A2: flood scenario stores bounded rows (aggregation test).
- A3: IP truncation settings are honored in UI/API for non-platform roles.
- A4: exports are integrity-protected.
- A5: the "why banned" explanation matches the policy branch.
**Tests.**
- Scanner tests; load tests; unit: aggregation.
**Notes.** Relates to R-24 and R-25.
