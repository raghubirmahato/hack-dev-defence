### T-0330 · Ban end-to-end tests with a builder-local vulnerable test origin
`P16` `[QA][SEC]` · deps: T-0319, T-0324, T-0327 · size: XL · owner: qa
**Objective.** Prove the product promise in a controlled local environment before the lab and pilot runs.
**Steps.**
1. Build a **test-only vulnerable origin** under `tests/support/vuln_origin/` (never shipped, loopback-bound, disposable SQLite or Postgres container): endpoints with intentionally unsafe string-built SQL for login (`/login`), search (`/search?q=`), numeric ID (`/item?id=`), plus reflection for XSS and a file read for traversal; includes canary rows and an admin account for non-destructive proofs.
2. Start HDD (proxy, API, Redis, Postgres) on the builder with the origin behind it in `monitor` and `block` modes.
3. Execute the proof matrix: (a) **direct** exploit proofs against the origin (Class A only: auth bypass as canary admin, UNION extraction of a canary table, sleep ≤ 2 s) succeed — demonstrating vulnerability; (b) the same through HDD in `block` mode with the Vulnerable-Origin Shield: 403 with Ray ID, **client IP banned**, subsequent benign requests from the IP get 403, origin access counter unchanged by the exploit attempts; (c) legitimate login/search/ID requests from another IP succeed; (d) the six mandated payloads against the login form via POST body and via query string each ban a fresh source address (using loopback aliases 127.0.0.2+ as distinct clients); (e) cross-site subresource requests with attack-shaped URLs are blocked without ban; (f) unban restores access within 2 s.
4. Include IPv6 sources (loopback aliases `::1`-range /64 members) to prove /64 keys.
5. Include resilience: Redis stopped mid-test (local bans persist), proxy restarted (bans reload from Postgres), second proxy node receives bans.
6. Capture timing: time from payload to enforcement on the same node and on the second node.
7. Produce a report with evidence: origin logs, proxy events, ban records, timings; assert numbers against thresholds (≤ 100 ms same node, ≤ 2 s other node).
8. Wire the suite into `cargo xtask acceptance --only AC-38-local` and mark the Vuln-Lab version for P28.
**Deliverables.**
- `tests/support/vuln_origin`, e2e suite, report
**Acceptance.**
- A1: direct exploits succeed against the test origin (proof of vulnerability) and fail through HDD with a ban.
- A2: each of the six mandated payloads bans a fresh source in POST and GET forms.
- A3: cross-site subresource attack URLs do not ban.
- A4: enforcement latency thresholds are met.
- A5: the suite survives Redis stop/start and proxy restart without losing bans.
**Tests.**
- The suite itself, run 5 times for stability.
**Notes.** The test origin is intentionally insecure; it binds loopback only, refuses to start otherwise, and is excluded from release builds (guard test).
