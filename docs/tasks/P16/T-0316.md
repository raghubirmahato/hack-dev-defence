### T-0316 · Ban store: local enforcement copy, Redis, Postgres and resync
`P16` `[DP][DB]` · deps: T-0315, T-0211 · size: XL · owner: dp
**Objective.** Make bans fast to check, durable, and consistent across nodes.
**Steps.**
1. Write migration for `ip_bans`, `ban_offences`, `ban_appeals` (if not yet present), and `campaign_clusters` per B5.7 with RLS (platform bans have `org_id` null and use platform-owned access paths).
2. Implement the local enforcement structure in each proxy node: three sharded maps (platform, org, site) keyed by `IpKey` with `expires_at` and a compact `BanInfo`, wrapped for lock-free reads (`ArcSwap` snapshots for bulk resync plus a sharded concurrent map for incremental updates), size cap 100,000 entries with oldest-expiry eviction that never evicts manual or platform bans, and a background reaper for expired entries.
3. Implement the **hot path check**: O(1) local lookup (platform, org, site in order) with no network I/O; a miss means not banned; Redis is not consulted on the request path.
4. Implement creation: write local immediately, then asynchronously (a) Redis (`hdd:banned_ips` zset score=expiry plus `hdd:ban:{scope}:{key}` hash with TTL), (b) publish `hdd:events:ban` with a monotonic revision, (c) enqueue the durable Postgres insert through the event pipeline with an idempotency key; failures retry with backoff and surface in metrics.
5. Implement subscribers: on `ban`/`unban` messages apply to the local structure; on a revision gap or reconnect, resync the full active set from Redis and verify against Postgres periodically (every 30 s incremental check, every 5 minutes full reconciliation) to heal divergence.
6. Implement unban: remove locally, Redis, publish, mark Postgres `released_at` with actor; ensure unban beats stale create messages (tombstones with revision ordering).
7. Implement Redis-down behavior: local bans continue to work; creation continues locally and queues Redis writes (bounded); node restarts rebuild from Postgres.
8. Add loom/shuttle tests for the concurrent structure and chaos tests (drop messages, restart nodes, partition Redis).
**Deliverables.**
- `hdd-common::banstore`, migration, tests, docs
**Acceptance.**
- A1: the hot-path check performs no I/O (verified by a test harness that panics on socket use) and costs under 200 ns p99 for 100k entries.
- A2: a ban created on node A is enforced on node B within 2 s p95 (integration with two proxy instances).
- A3: dropped pub/sub messages heal via gap resync or reconciliation.
- A4: unban wins over delayed create messages (ordering test).
- A5: eviction never removes manual or platform bans (property test).
**Tests.**
- loom/shuttle model tests; chaos integration (Redis/Postgres restarts); benchmark.
**Notes.** The store implements the "never await the DB on the hot path" rule (C2).
