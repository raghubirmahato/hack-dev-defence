### T-0331 · Ban metrics, alerts and mass-ban (poisoning) anomaly detection
`P16` `[OPS][API]` · deps: T-0320, T-0328 · size: M · owner: ops
**Objective.** Notice when bans behave abnormally, including deliberate poisoning attempts.
**Steps.**
1. Implement the metrics set from B9 (`MET-hdd_bans_active`, `created_total{reason}`, `released_total{by}`, `jail_hits_total`, `ban_propagation_seconds`, `unban_effect_seconds`, eviction).
2. Implement anomaly detection: more than `max(50, 5% of active)` bans created within 5 minutes for a site, or ban creation rate exceeding a learned baseline by z-score > 4, triggers a critical alert "possible ban poisoning or attack surge", a banner on S-067, and recommended actions (switch cross-site handling to challenge, review recent bans, enable shared-address policy).
3. Implement alert rules integration: events of kind `mass_ban`, `never_ban_attack_attempt`, `global_jail_promoted`, `propagation_slow` (> 2 s p95) with channels (T-0453).
4. Implement dashboards-as-code panels for the above (Grafana JSON from Rust).
5. Implement SLO measurement for unban effect and ban propagation with alerts on regression.
6. Implement tests with simulated floods and slow subscribers.
7. Document operator runbooks (what to do on mass-ban alert).
8. Link ATK-291.
**Deliverables.**
- metrics, anomaly detector, alert rules, runbook, tests
**Acceptance.**
- A1: a burst of 200 cross-site poisoning attempts triggers the anomaly alert once.
- A2: slow propagation triggers `propagation_slow`.
- A3: dashboards render in a Grafana instance during integration (smoke).
- A4: runbook steps are testable.
- A5: baselines adapt without alert spam (hysteresis tested).
**Tests.**
- Simulation tests; unit: z-score logic; dashboard JSON schema validation.
**Notes.** Poisoning exercises are also part of AC-34.
