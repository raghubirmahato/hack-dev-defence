### T-0274 · Auth-endpoint SQLi mode and the success-after-attack tripwire
`P14` `[DP][SEC]` · deps: T-0225, T-0273 · size: L · owner: waf
**Objective.** Treat login and similar endpoints with extra strictness and detect actual bypasses in monitor mode.
**Steps.**
1. Implement the strict profile for declared/detected auth endpoints: every parameter is inspected (no prefix shortcuts), password-kind soft relaxations apply per strictness, hard families unchanged, and thresholds tightened by 1 (min 3) for soft scores.
2. Implement response-based learning per auth endpoint: record the distribution of response status classes and `Location` patterns (status 302 to dashboard vs 200 login page with errors, 401/403) as aggregates, and classify outcomes into `success_like`, `failure_like`, `unknown` (confidence tracked); owner can correct via UI.
3. Implement the **V13 tripwire** in `monitor`/`log` modes: if a request matching a hard SQLi family to an auth endpoint is followed by a `success_like` response from the origin, emit a **critical** event `possible_auth_bypass` with Ray ID, endpoint and subtype, create an attention item, and notify owners immediately; in `block` mode such requests are blocked so the tripwire cannot fire (the event type `blocked_auth_bypass_attempt` is used instead).
4. Implement per-account/IP interplay hooks: attempts with hard SQLi against auth endpoints also count toward credential-stuffing detection (P17).
5. Ensure that error responses for blocked auth requests are identical to other blocks (no hint of special treatment).
6. Test with the Vuln-Lab login endpoint in lab mode later; now with a controllable local origin that implements a vulnerable-like login (test fixture inside tests only, not shipped).
7. Add metrics (`MET-hdd_auth_endpoint_attacks_total{kind}`).
8. Document how the tripwire helps owners discover that their site was exploitable.
**Deliverables.**
- strict profile, response learner, tripwire, tests
**Acceptance.**
- A1: in monitor mode, a hard SQLi login request that the (test) origin accepts triggers the critical `possible_auth_bypass` event once.
- A2: in block mode, the same request is blocked and no tripwire fires.
- A3: the response learner classifies success/failure patterns after N samples with confidence.
- A4: block responses on auth endpoints are indistinguishable from other blocks.
- A5: metrics increment correctly.
**Tests.**
- Integration with a test-only vulnerable-like origin and the proxy harness; unit: classifier; browser: attention item display.
**Notes.** The test origin lives under `tests/` and is never shipped; the shipped lab app is `hdd-vulnlab` (P28).
