### T-0280 · sqlmap campaign harness (lab-only) and coverage measurement
`P14` `[QA][LAB][SEC]` · deps: T-0261, T-0278 · size: L · owner: qa
**Objective.** Measure how well the shield withstands a real automated SQL injection tool, safely.
**Steps.**
1. Define the lab scope: the harness runs only in `lab` mode against Vuln-Lab addresses or a builder-local deliberately vulnerable test origin, through HDD in `monitor` mode (coverage measurement) and `block` mode (containment), never against live profile hosts (TargetGuard enforced; oracle tools are invoked only via `hdd-acceptance` lab mode).
2. Implement the campaign runner that drives sqlmap with documented parameters: levels 1 to 3, risk 1 to 2, techniques `BEUSTQ` as lab allows, `--batch`, threads 1, delay set to respect the lab profile (500 req/s cap, 10 minutes), user agent default and `--random-agent`, `--tamper` lists (a published set: `space2comment`, `randomcase`, `charencode`, `charunicodeencode`, `between`, `equaltolike`, `apostrophemask`, `apostrophenullencode`, `base64encode`, `percentage`, `space2plus`, `space2randomblank`, `versionedkeywords`, `versionedmorekeywords`), and separate runs per tamper and one combined.
3. Capture every request sqlmap sends via HDD's event stream in `monitor` mode (`would_block` flags) and the origin-side log (the lab app records requests), then compute: total requests, injection-bearing requests (heuristic: contains the injection marker or payload shape per sqlmap's payload files as understood from request logs, labeled by the lab origin), flagged vs unflagged counts, unflagged classes with examples, per-tamper coverage, time to first hard hit.
4. In `block` mode run the same campaigns and measure: whether any data extraction succeeded (the lab app logs canary extraction events), time until the IP ban (once P16 lands; before that, until first 403), and the number of requests that reached the origin.
5. Record results in `acceptance-lab/sqlmap/*.json` with raw logs and SHA-256; produce a Markdown summary with the target thresholds: coverage ≥ 95% of injection-bearing requests in monitor mode; zero extraction in block mode.
6. Analyze unflagged request classes, create new fixtures (not tuned on held-out) and rule improvements; rerun until thresholds are met or document the residual with a diagnosis (failure budget R-14).
7. Add similar harness stubs for other oracles (nikto, wapiti, nuclei, ZAP baseline, ffuf) used in later phases.
8. Document how to reproduce and the safety constraints (lab only).
**Deliverables.**
- campaign runner in `hdd-acceptance` lab mode, reports, new fixtures
**Acceptance.**
- A1: the harness refuses non-lab targets (guard test).
- A2: monitor-mode coverage report is produced with the exact figure and unflagged classes.
- A3: block-mode runs show zero successful extraction (lab canary log).
- A4: results are reproducible with the same seeds and recorded tool versions.
- A5: improvements are fed back as fixtures without using held-out data.
**Tests.**
- Harness self-tests with a recorded local fixture of sqlmap-like requests (inert); the real campaign is a lab run (`UNVERIFIED(capability_not_supplied)` without a lab).
**Notes.** The harness is the source for the claim wording in S-003 (tested claim with exact figures and limits).
