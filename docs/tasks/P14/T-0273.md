### T-0273 · SQLi ban policy: from hard hit to `BanIntent`
`P14` `[DP][SEC]` · deps: T-0252, T-0265, T-0266 · size: L · owner: waf
**Objective.** Encode C4.10 as an explicit, testable decision table inside the engine and policy layer.
**Steps.**
1. Implement `sqli_ban_intent(verdict_matches, request_ctx, site_policy) -> Option<BanIntent>` that applies the decision table of C4.10 (mode, hardness, cross-site context, soft score blocks, allowlists, never-ban hints) and returns the intent with `PolicyBranch` identifiers (`hard_hit`, `hard_hit_cross_site`, `soft_score_repeat`, `password_h2_soft`, `paranoid_hard`, `monitor_would_ban`).
2. Implement cross-site context extraction from the request context: `Sec-Fetch-Site` (`cross-site`, `same-site`), `Sec-Fetch-Dest` (subresource destinations), `Sec-Fetch-Mode`, `Referer`/`Origin` mismatch heuristics (documented), treating missing headers as no browser context.
3. Implement the soft-score repeat rule (three score-blocks from the same key within 10 minutes → ban intent in Balanced; first in Paranoid), reading the recent-activity counters through an injected trait (the real store arrives in P16/P17).
4. Implement attack-diversity input (distinct categories within 10 minutes) as an injected counter query (V15).
5. Implement the TTL ladder hint (`ttl_step_hint`) from offence counts (injected) and scope selection (site vs org) from policy.
6. Write a decision-table test with ≥ 120 rows covering all combinations (mode x hardness x context x allowlist x kind x strictness) and property tests (a cross-site request never yields a ban intent; a hard hit in block mode outside cross-site context always yields one unless never-ban).
7. Document the table in `docs/BAN-POLICY.md` with the same IDs as test rows.
8. Surface `would_ban` in monitor/log modes for the UI.
**Deliverables.**
- policy module, docs, decision-table tests
**Acceptance.**
- A1: all 120 rows pass; the table in docs is generated from the test data (no drift).
- A2: no ban intent arises from cross-site subresource requests (property test).
- A3: monitor mode yields `would_ban` without bans.
- A4: password H2 behavior matches C4.6 under both strictness levels.
- A5: the soft-score repeat rule behaves per specification with an injected clock.
**Tests.**
- Table/proptest; doc-generation test.
**Notes.** The ban storage/enforcement and TTL ladder are P16 (T-0315 to T-0332); this task is the decision logic.
