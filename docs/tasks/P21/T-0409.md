### T-0409 · Outbound filter in the proxy: modes, buffering window, actions and S-097
`P21` `[DP][UI][API]` · deps: T-0408, T-0362, T-0363, T-0222 · size: L · owner: dp
**Objective.** Apply the leak engine safely to live responses and let owners control it.
**Steps.**
1. Implement the response-phase stage (pipeline stage 17): eligibility rules — only `GET/POST/...` responses with status 2xx/4xx/5xx and text-like content types (`text/*`, `application/json`, `application/xml`, `application/javascript` configurable), `Content-Encoding` of identity/gzip/br/deflate/zstd decompressed in a bounded streaming decoder (decompression bomb limits: decompressed size ≤ 10 MiB and ratio ≤ 20:1 per Appendix E4), skip for `Range`/`206`, WebSocket upgrades, server-sent events, gRPC, `Content-Length` > the large-body threshold (stream through, tag `skipped_large`), and per-path exclusions.
2. Implement the **hold window**: buffer up to the first 64 KiB of the decompressed body (configurable 16–256 KiB) before releasing headers; bodies larger than the window are scanned over the prefix and tagged `partial_scan`; the proxy documents the latency effect (added time to first byte bounded by origin send time of the first window, with a 250 ms hold timeout after which streaming proceeds and the response is tagged `scan_timeout`).
3. Implement modes: `off`, `monitor` (record events, pass body), `block` (high-confidence findings replace the response with the branded 500 `S-143`-style page and record a `critical` `data_leak` event; medium findings are masked or recorded per policy, see below), plus `mask` (replace only the matched span with a fixed marker when the content type is JSON/text and the replacement preserves syntactic validity; otherwise fall back to block). Masking is limited to database error and path patterns; secrets always block.
4. Recompute `Content-Length`, strip `Content-Encoding` only when the body had to be rewritten (recompress is not attempted; document the cost), keep `ETag`/`Last-Modified` semantics sane (drop the strong `ETag` on rewritten bodies), preserve `Vary`, never touch HEAD or 304 responses.
5. Implement the **fail-safe**: scanner errors or panics fall back to pass-through with a metric and an alert (the outbound filter fails open for availability by design because it is a secondary control; this is documented and the opposite of the request-side rule R-26; the readiness page states it).
6. Implement `S-097` backend: mode, exclusions (path + method + content type), pattern pack version, per-category toggles (database errors, stack traces, secrets, source code, directory listings, paths), confidence thresholds, test tool ("scan a pasted response" using the pure engine with redaction), event table, and the canary `leak.txt` verification button that runs the AC-10 probe via the pilot path.
7. Record events with ray id, path template, category, confidence, mode, action, response status, `partial_scan`, and the redacted snippet (≤ 512 B), applying the 30-day default retention; send `critical` findings to notifications (owner may opt out of snippet storage).
8. Emit metrics: scanned bytes, hold latency histogram, findings by category/action, skipped reasons, timeouts, masking successes/failures.
9. Write tests: origins returning each pattern in plain/gzip/br/chunked/HTTP2, boundary-spanning patterns, large bodies, binary data (images, PDFs, zips) untouched, streaming responses untouched, SSE untouched, HEAD/304 untouched, JSON validity after masking, monitor vs block behavior, exclusions, panic injection.
**Deliverables.**
- proxy stage, S-097 backend and screen wiring, metrics, tests
**Acceptance.**
- A1: AC-10 canary leak is blocked in `block` mode and recorded in `monitor` mode.
- A2: binary/streaming/Range/HEAD/304 responses are byte-identical to the origin response (differential test).
- A3: HDD-side scan and mask time p99 ≤ 3 ms per 64 KiB window on the builder (origin body-wait during the hold is origin time, C14.9); hold timeout behavior verified.
- A4: scanner panic injection leads to pass-through with an alert and no connection reset.
- A5: masked JSON responses remain valid JSON in 100% of fixtures.
**Tests.**
- Integration (proxy + fault origins), differential, property (chunking), performance.
**Notes.** The documented limit (prefix-only scan beyond the window) is shown in S-097 and the readiness page.

## Definition of done for this task's tags (section 0.7)

### `[DP]`: On the data-plane hot path (proxy, DNS, WAF, firewall)

Hot path never awaits the database; bounded memory and queues; criterion benchmark or histogram; fuzz or proptest; behavior when Redis or Postgres is down specified and tested; metric with drop counter.

### `[UI]`: Renders HTML to a human

Server-side escaped output only; empty, loading, error, offline and permission-denied states implemented honestly (no fake data); keyboard-only operation verified; focus order and visible focus; WCAG 2.2 AA via the axe oracle with zero serious or critical findings; contrast tokens only (no ad-hoc colors); responsive screenshots at 360, 768, 1280 px in dark and light; i18n keys only (no literal user-facing strings in templates); CSP clean (no inline script or style, no console errors); size budgets (E4) respected; visual-regression baseline updated with reviewer note.

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.
