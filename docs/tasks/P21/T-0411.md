### T-0411 · Cookie and session protection (flag upgrades, scope hardening, fixation signals)
`P21` `[DP][SEC][UI]` · deps: T-0410, T-0361 · size: M · owner: dp
**Objective.** Reduce the damage of weak session handling in the protected application without changing application logic.
**Steps.**
1. Implement the cookie policy per site (all opt-in, default `report` mode): `secure_upgrade` (add `Secure` when the request was HTTPS), `httponly_upgrade` (add `HttpOnly` to cookies whose names match a configurable session-like pattern: `sess`, `sid`, `token`, `auth`, `PHPSESSID`, `JSESSIONID`, `connect.sid`, `laravel_session`, `ASP.NET_SessionId`, excluding cookies the app reads from JavaScript, listed by the owner), `samesite_default` (add `SameSite=Lax` when absent; `None` requires `Secure`), `prefix_hardening` (suggest `__Host-` prefixes; only report), `domain_narrowing` (drop broad `Domain=` attributes when the owner enables it), and `max_age_cap` (cap session cookie lifetime).
2. In `report` mode, record findings (cookie name hashed + attribute gaps, never values) in a per-site `cookie_audit` aggregate, displayed in S-043/S-097 with remediation text ("set these flags in your framework: …") for the common stacks.
3. Implement **session-fixation and hijack signals** (monitor first): the same session cookie value (HMAC'd keyed hash, never stored raw) seen from a new IP /24 and a new user-agent family within 60 s raises `session_anomaly` (soft score) with a tunable sensitivity; a session cookie value presented after the origin set a new value for the same cookie name on the same client (fixation indicator) is recorded; optional step-up (challenge) on high-risk anomalies for configured sensitive paths.
4. Implement a **session binding option** for strict sites (off by default): HDD adds a signed binding cookie (`__Host-hdd_bind`) containing a keyed hash of (client IP /24 or /56, UA family) and, if the application cookie arrives with a mismatching binding, applies the configured action (log, challenge, block). The option explains its drawbacks (mobile networks, privacy) and is rate limited to avoid lockouts; it fails open on missing binding to avoid breaking logged-in users during enablement (grace period 7 days).
5. Implement **cookie size/count protections**: reject responses with more than the configured number or total size of cookies (protects browsers and origin from cookie bombing), and strip cookies with invalid names.
6. Add **admin-path token tripwires**: the HDD-issued challenge clearance cookie (`__Host-hdd_cl`) is never forwarded to the origin (strip on the upstream request) and never logged.
7. Wire controls and explanations in the UI with a "what changes for your users" summary and a "revert" button; log every enablement as an audit event.
8. Write tests: attribute rewriting matrix (≥ 150 cases including multiple `Set-Cookie` headers, folded values, quoted values, unusual casing, partitioned cookies, `__Host-` and `__Secure-` prefixes), no mutation in `report` mode, binding behavior with grace period, clearance cookie stripping, performance (rewriting adds ≤ 50 µs per response with cookies).
**Deliverables.**
- cookie policy module, signals, UI, tests, docs
**Acceptance.**
- A1: in `report` mode no `Set-Cookie` header is modified (differential test over 10,000 responses).
- A2: with upgrades enabled all matrix cases produce the documented output; `SameSite=None` without `Secure` is never emitted.
- A3: the clearance cookie never reaches the origin or logs.
- A4: session binding with a mismatch triggers the configured action only after the grace period.
- A5: cookie values never appear in events, logs or metrics (grep test).
**Tests.**
- Unit matrix; integration with test origins; privacy greps.
**Notes.** Session binding is an advanced option marked "may log out users on network changes".
