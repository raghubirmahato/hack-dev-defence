### T-0414 · Bulk-exfiltration and scraping-of-data guard (response volume and record-count anomalies)
`P21` `[DP][SEC]` · deps: T-0408, T-0349, T-0312 · size: M · owner: dp
**Objective.** Limit damage when an injection or authorization flaw exists and the attacker starts pulling data.
**Steps.**
1. Implement per-client (IP /32,/64 plus session-hash when available) **response-volume tracking** on configured sensitive path classes (API collections, export endpoints, search, user listings): rolling counters for response bytes, response count, distinct resource ids observed in paths/queries (bounded sets), and JSON array element counts for responses within the scan window (only counts, never content).
2. Define anomaly rules with adaptive baselines (T-0349): a single client retrieving more than `k` times the p99 volume of normal clients within a window, sequential-id enumeration across many distinct ids, large JSON arrays returned repeatedly to the same client, and export endpoint usage bursts. Actions: soft score, rate limit, challenge, and (on high confidence) ban with attack category `data_exfiltration`.
3. Implement **response-size ceilings** (owner-configurable per path class): a response above the ceiling is replaced with a 502-style error when `block` is selected (default `monitor`), preventing accidental or malicious dumps from vulnerable endpoints.
4. Add **sensitive-data shape alarms** (optional, `monitor` by default): in the scan window, count occurrences of email addresses, 13–19 digit sequences passing the Luhn check (payment card shapes), SSN-like patterns and IBAN shapes; produce counts only (no content, no storage of matches). Events fire when a single response contains more than a configured count, flagged as "possible mass data disclosure" with the path template and Ray ID.
5. Integrate with the SQLi shield: when a hard SQLi hit was recorded for the same client in the last 10 minutes and an anomalous volume follows, escalate the ban TTL one rung and raise `possible_data_exfiltration`.
6. Expose UI controls in S-097/S-057 (path classes, ceilings, shapes toggle, thresholds) with plain-language descriptions and false-positive guidance (legitimate exports, mobile apps with paging).
7. Ensure privacy: counters are keyed with HMAC'd identifiers, retention 24 h, no content stored; the shape alarms are disclosed in the privacy docs (data processed in memory only).
8. Write tests: simulated enumeration, legitimate paging users, export usage, Luhn/IBAN validators (property tests with known valid/invalid sets), ceiling behavior, interaction with SQLi ban escalation, performance (≤ 0.2 ms added at p99 for scanned responses).
**Deliverables.**
- guard module, schema/settings, UI wiring, tests, docs
**Acceptance.**
- A1: sequential-id enumeration of 500 ids by one client is flagged within the configured window with zero flags for 1,000 simulated normal clients.
- A2: Luhn-valid test card numbers in a response trigger the alarm; non-valid 16-digit numbers do not (fixtures).
- A3: no match content is stored anywhere (storage/log grep).
- A4: ceiling `block` mode returns the branded error and records an event.
- A5: SQLi-ban escalation integration test passes.
**Tests.**
- Unit/property (validators), simulation tests, integration, privacy greps.
**Notes.** This is a mitigation, not a data-loss-prevention product; the UI says so.
