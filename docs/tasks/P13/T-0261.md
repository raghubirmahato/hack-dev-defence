### T-0261 · Proxy integration: pipeline stages 11 to 15 in monitor, log and block modes
`P13` `[DP][SEC]` · deps: T-0208, T-0260, T-0237 · size: XL · owner: dp
**Objective.** Run the engine inside the live request path with safe, observable behavior.
**Steps.**
1. Implement body acquisition (stage 11): buffer the request prefix up to `inspect_body_max_bytes` without delaying the upstream beyond the decision; for requests with bodies, hold headers until the decision (bounded by the inspection timeout 50 ms soft target), stream the remainder after the decision; for large uploads with `Expect: 100-continue`, evaluate headers/URL first.
2. Implement stages 12 to 14: build `InspectRequest` from the parsed HTTP request, call the engine with the site's `SitePolicy`, apply mode semantics (`off` skips; `monitor`/`log` pass and record `would_block`; `block` returns the branded 403) and the exceptions/allowlist semantics.
3. Implement stage 15 enforcement: branded 403/JSON with Ray ID, `HDD-Ray-ID` header, event emission to the bounded channel with per-IP aggregation, metrics, and the `BanIntent` hand-off to the ban policy engine (a no-op sink until P16, with the intent recorded in events as `would_ban`).
4. Implement failure semantics (R-26): engine panic or budget overrun → 503 with Ray ID in `block` mode; `pass` with critical event in `monitor` mode; never silent pass in `block`.
5. Implement the global inspection concurrency budget and shed behavior (T-0256).
6. Implement response headers for blocks and the cross-site context extraction (`Sec-Fetch-*`, `Referer`) into the request context.
7. Implement a differential harness in tests comparing proxy verdicts with the inspect API.
8. Add integration tests for modes, exceptions, truncation, fail-closed behavior, event emission and dropped-event accounting.
**Deliverables.**
- proxy pipeline stages, event emitter, tests
**Acceptance.**
- A1: in `monitor` mode attack requests pass and produce `would_block` events; in `block` mode they get 403 with Ray ID.
- A2: induced engine failure in `block` mode yields 503 and never forwards the request (origin counter zero).
- A3: event queue saturation drops events with counters but still enforces decisions.
- A4: added latency p99 stays within the budget (functional profile benchmark).
- A5: the verdict equals the inspect API result for 500 differential samples.
**Tests.**
- Integration with local origins and real Redis/Postgres; chaos: kill the event consumer; fuzz the HTTP framing path.
**Notes.** Bans, rate limiting and the jail stage are added in P16 and P17.
