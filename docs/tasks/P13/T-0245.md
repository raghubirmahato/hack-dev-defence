### T-0245 · Rule model, rule files and packs
`P13` `[DP][API][DOC]` · deps: T-0244 · size: L · owner: waf
**Objective.** Define how detections are authored, tested, versioned and shipped.
**Steps.**
1. Define rule files (`crates/hdd-waf-core/rules/<category>/*.toml`): `id` (`HDD-<CAT>-<nnnn>`), `title`, `category`, `subtype`, `atk` references, `severity` (critical, error, warning, notice), `hardness` (hard, soft), `paranoia` (1 to 4), `targets` (vectors and field kinds), `views` (decoded, canonical, raw), `pattern` or `structural` reference, `transforms`, `tags`, `message_key`, `examples` (must match), `counter_examples` (must not match), `references` (CWE/CVE), `since`, `status`.
2. Implement the pack linter (`xtask rules lint`): every rule has at least 3 examples and 3 counter-examples (or an explicit justification for fewer), IDs unique, references valid, patterns compile within budgets, examples actually match (and counter-examples do not) under the real engine, hard rules cover category policy constraints.
3. Define pack manifests (name, version semver, kind: core, virtual_patch, bot, custom), signatures (minisign-compatible detached signature over the canonical manifest) and the verification hook used by platform rollout (P22).
4. Implement rule overrides at site level (disable via exception only, severity unchanged) and platform staged rollout metadata.
5. Implement coverage reporting: ATK to rules mapping (`xtask attack-matrix check` consumes it).
6. Implement documentation generation: a rules reference page (rule IDs, titles, examples) for the docs site (examples are inert shapes only).
7. Implement the `custom` pack kind used by tenant custom rules (T-0248), isolated per site.
8. Add migration/versioning rules for rule IDs (never reuse IDs; deprecations keep tombstones).
**Deliverables.**
- rule schema, linter, pack manifest format, docs generator, initial empty core pack structure
**Acceptance.**
- A1: the linter fails a rule lacking counter-examples.
- A2: examples/counter-examples are verified against the real engine in CI.
- A3: rule IDs are unique and never reused (tombstone test).
- A4: packs verify their signatures with a test key.
- A5: generated docs contain only inert example shapes (no destructive payloads) because Class B/C examples are excluded by tag.
**Tests.**
- Linter tests with deliberately broken rule files; integration: pack load and verification.
**Notes.** Class B/C fixtures live in test fixtures, not in rule `examples` that appear in docs.

## Definition of done for this task's tags (section 0.7)

### `[DP]`: On the data-plane hot path (proxy, DNS, WAF, firewall)

Hot path never awaits the database; bounded memory and queues; criterion benchmark or histogram; fuzz or proptest; behavior when Redis or Postgres is down specified and tested; metric with drop counter.

### `[API]`: Adds or changes an HTTP endpoint

OpenAPI entry via `utoipa`; RFC 9457 problem responses using the error catalog; authz check by permission ID (deny by default); tenant scoping test (BOLA); input validation with explicit limits; idempotency key on create; `ETag`/`If-Match` on update; rate limit class assigned; audit event; metric; contract test generated from the OpenAPI document.

### `[DOC]`: Documentation

Every claim backed by a test ID or a command the reader can run; passes claims-lint; included in the docs site if user-facing.
