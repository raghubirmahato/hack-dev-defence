## P-5 (shutdown could block ~25 s)

NOT REPRODUCED end-to-end on this host, stated explicitly: the old worst case needs four workers each holding a full 5 s
connection deadline while the listener stays open, i.e. a multi-client in-flight/queued pattern whose exact 25 s timing
the test harness cannot hold deterministically on a loopback host with a 300 ms test deadline. The new behaviour is
demonstrated by the tests that exercise the stop path: `non_closing_clients_do_not_delay_a_fifth` (the 200 ms drain cap
frees a worker instead of holding it for the whole deadline) and every test whose `Running` is dropped/stopped (the
suite has no hanging stop). The structural fix is visible in `serve_loop`: it closes the listener first, then drops the
queue, then joins the workers.
